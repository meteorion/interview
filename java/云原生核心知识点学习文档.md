## 一、Docker

Docker 解决「构建一次，到处运行」：把应用与依赖打成不可变镜像，用 Namespace 做隔离、Cgroups 做资源限制。Java 后端还需额外关注镜像体积、JVM 内存感知和容器资源上限。

### 1.1 镜像分层与写时复制【重点】

镜像由多个**只读层**叠加，Dockerfile 中每条 `RUN`、`COPY`、`ADD` 生成一层，联合文件系统（UnionFS，生产常用 overlay2）把它们叠成一个完整文件系统；容器启动时在最上面加一个**可写层**，修改都写在这一层，读取沿层自上而下查找，即**写时复制（Copy-on-Write）**。

| 概念 | 说明 |
| --- | --- |
| 层（Layer） | 只读，层 ID 是内容哈希，可被多个镜像共享并复用构建缓存 |
| 可写层 | 每个容器独有，容器删除即丢失，这是数据必须放数据卷的根本原因 |
| 写时复制 | 修改文件时先复制到可写层再改，原层不变 |

由此得到核心原则：**变化少的放前面，变化多的放后面**。把 `COPY pom.xml` 与依赖下载放在源码复制之前，改一行代码时依赖层仍命中缓存。

### 1.2 容器与虚拟机的区别【重点】

| 维度 | 容器 | 虚拟机 |
| --- | --- | --- |
| 隔离实现 | Namespace（视图隔离）+ Cgroups（资源限制） | Hypervisor 虚拟硬件，Guest OS 独立内核 |
| 内核 | 与宿主机共享内核 | 每个虚机自带完整内核 |
| 启动速度 | 秒级甚至百毫秒 | 数十秒到分钟级 |
| 安全边界 | 较弱，内核漏洞可逃逸，需 seccomp / capabilities 加固 | 较强，硬件级隔离 |

### 1.3 Dockerfile 指令与最佳实践【重点】

| 指令 | 要点 |
| --- | --- |
| `FROM` | 固定版本或 digest，禁止 `latest` |
| `RUN` | 合并多条并清理缓存（`rm -rf /var/lib/apt/lists/*`），避免层里残留安装包 |
| `COPY` | 复制本地文件，首选；`ADD` 额外支持 URL 与自动解压，语义不明确，一般不用 |
| `CMD` | 默认启动命令，可被 `docker run` 参数覆盖；用 exec 形式 `["java","-jar","app.jar"]` 才能正确接收 SIGTERM |
| `ENTRYPOINT` | 入口命令，不被覆盖，常与 `CMD` 配合做默认参数 |
| `ENV` / `ARG` | `ENV` 进镜像且运行可见，`ARG` 仅构建期；**密钥不能放这两者**，会留在镜像历史 |
| `USER` | 切换运行用户，生产必须非 root；配套 `.dockerignore` 排除 `target/`、`.git/` 等无关文件 |

### 1.4 多阶段构建与 Java 镜像优化【重点】

多阶段构建在一个 Dockerfile 里写多个 `FROM`：构建阶段用带 JDK 与 Maven 的大镜像编译，运行阶段只复制产物，最终镜像不含源码、构建工具与中间文件。

```dockerfile
FROM eclipse-temurin:17-jdk AS build
WORKDIR /src
COPY . .
RUN ./mvnw -q package -DskipTests

FROM eclipse-temurin:17-jre
WORKDIR /app
RUN groupadd -r app && useradd -r -g app app
COPY --from=build /src/target/app.jar app.jar
USER app
ENV TZ=Asia/Shanghai LANG=C.UTF-8
ENTRYPOINT ["java","-XX:MaxRAMPercentage=75","-Duser.timezone=Asia/Shanghai","-jar","app.jar"]
```

| 优化项 | 做法 | 原因 |
| --- | --- | --- |
| 基础镜像 | JRE 而非 JDK，或 distroless；避开 Alpine 的 musl 兼容问题 | 体积小、攻击面小 |
| 分层缓存 | 先复制 `pom.xml` 下载依赖，再复制源码 | 改代码不重新下载依赖 |
| 分层 jar | `java -Djarmode=layertools -jar app.jar extract`，按 dependencies、loader、snapshot、application 依次 `COPY` | 依赖层几乎不变，发版只推几百 KB |
| 堆内存 | `-XX:MaxRAMPercentage=75` 而非写死 `-Xmx` | 随 limit 自动调整，避免 OOMKilled |
| 运行用户 | `USER app` | 降低逃逸后的权限 |
| 时区字符集 | `TZ`、`-Duser.timezone`、`LANG=C.UTF-8`、`-Dfile.encoding=UTF-8` | 避免日志差 8 小时与中文乱码 |
| 镜像扫描 | Trivy / Grype 接入流水线 | 阻断高危 CVE 进生产 |

### 1.5 docker-compose 与网络模式【了解】

| 模式 | 行为 | 适用 |
| --- | --- | --- |
| `bridge`（默认） | 独立网络命名空间，docker0 网桥 + NAT + 端口映射；默认 bridge 不支持容器名解析 | 单机默认 |
| 自定义 bridge | 自带内嵌 DNS（127.0.0.11），容器间用服务名互访 | **最推荐**，compose 默认创建 |
| `host` | 共享宿主网络栈，无 NAT 开销，端口直接占用宿主 | 高性能且端口不冲突 |
| `none` | 只有 loopback | 离线计算、安全隔离 |
| `container:xxx` | 共享指定容器的网络命名空间 | sidecar 式共享网络 |

compose 的 `depends_on` 只保证启动顺序，不保证依赖就绪，需配合 `healthcheck` 与 `condition: service_healthy`；服务名即容器内 DNS 名，端口映射写作 `ports: "8080:8080"`。

### 1.6 数据卷与持久化【了解】

| 类型 | 存储位置 | 特点 | 场景 |
| --- | --- | --- | --- |
| volume | `/var/lib/docker/volumes`，Docker 管理 | 跨容器共享、可备份迁移、性能好 | 生产数据，**推荐** |
| bind mount | 宿主机任意目录 | 依赖宿主路径与权限，可直接改 | 开发调试、挂配置文件 |
| tmpfs | 内存 | 不落盘，容器停止即消失 | 临时敏感数据 |

### 1.7 cgroup 资源限制与 JVM 内存感知【重点】

| 参数 | 作用 | 超限后果 |
| --- | --- | --- |
| `-m` / `--memory` | 内存上限 | cgroup OOM Killer 杀进程，退出码 137 |
| `--cpus` | CPU 核数上限（CFS 配额折算） | 被 throttle，不杀进程 |
| `--cpu-shares` | 相对权重，仅争抢时生效 | 无硬上限 |
| `--pids-limit` | 线程/进程数上限 | 无法建线程，抛 `OutOfMemoryError: unable to create native thread` |

关键点：`-Xmx` 只约束**堆**，容器内存还包括 Metaspace、直接内存、线程栈、Code Cache、GC 结构与 JVM 自身开销。容器 limit 1G、`MaxRAMPercentage=75` 时堆约 750M，剩余 25% 留给堆外；200 线程 × 1M 栈 ≈ 200M，堆外偏紧时要下调堆比例。JDK 8u191 后 `UseContainerSupport` 默认开启，能读 cgroup limit；更早版本会把宿主内存当可用内存。`-XX:ActiveProcessorCount=N` 用于旧版本或 `--cpus` 非整数时显式对齐 CPU 数，否则 GC 与公共线程池按宿主核数创建，引发上下文切换与 throttle。退出码 137 = 128 + 9（SIGKILL），内存超 limit 与 liveness 失败被杀都可能，需要结合 `describe` 的 Last State 判断。

### 1.8 安全加固【了解】

- 非 root 运行（`USER`、K8s `runAsNonRoot`），根文件系统只读（`--read-only` 配 `--tmpfs /tmp`）。
- 去掉多余 capabilities（`--cap-drop ALL` 后按需加回），禁止 `--privileged`，启用 seccomp / AppArmor 默认策略。
- 密钥不写进镜像、`ENV`、`ARG`，改用 Secret、挂载文件或外部密钥管理；镜像仓库开启漏洞扫描与签名。
- 固定基础镜像 digest，限制 `pids` 防 fork bomb，生产不挂载 `docker.sock`。

## 二、Kubernetes

K8s 的核心是**声明式 API + 控制器调谐**：你提交期望状态，控制器不断把实际状态拉回期望状态。Pod、Deployment、探针、HPA 都是在回答「期望状态是什么、如何判断、偏差如何修正」。

### 2.1 核心对象【重点】

| 对象 | 定位 | 关键特性 |
| --- | --- | --- |
| Pod | 最小调度单位 | 一个或多个容器共享网络命名空间与存储卷，Pod 内用 localhost 互访；本身不自愈 |
| Deployment | 无状态应用 | 管理 ReplicaSet，维持副本数，滚动更新与回滚；Pod 名字随机、可随意替换 |
| StatefulSet | 有状态应用 | 稳定有序名称（`mysql-0`）、Headless Service 固定 DNS、`volumeClaimTemplates` 独立存储、有序启停 |
| DaemonSet | 节点级守护进程 | 每个（或符合条件的）节点一个 Pod：日志采集、监控 Agent、CNI 插件 |
| Job / CronJob | 批处理 | `completions`、`parallelism`、`backoffLimit`；CronJob 按 cron 周期创建 Job |

### 2.2 Service 四种类型与 Ingress【重点】

| 类型 | 作用 | 说明 |
| --- | --- | --- |
| ClusterIP | 集群内访问 | 稳定虚拟 IP + DNS，默认类型，kube-proxy 做四层负载均衡 |
| NodePort | 节点端口暴露 | 每节点开 30000-32767 端口，适合测试或自建 LB |
| LoadBalancer | 云厂商 LB | 自动创建外部负载均衡并绑定 NodePort |
| ExternalName | 映射外部域名 | CNAME 指向集群外服务，无代理与负载均衡 |

**Headless Service**（`clusterIP: None`）不做 VIP，DNS 直接返回 Pod IP 列表，StatefulSet 靠它获得稳定网络标识。Service 通过标签选择器选中 Pod，后端列表落在 Endpoints / EndpointSlice；kube-proxy 的 iptables / IPVS 负载均衡是**连接级**的，不是请求级。**Ingress 是七层入口**，按域名与路径把 HTTP 流量路由到不同 Service 并统一配 TLS；它只是规则声明，必须配合 Ingress Controller（Nginx Ingress、Traefik、云厂商 ALB）才生效。关系：外部请求 → Ingress Controller → Service → Pod。

### 2.3 控制面与调谐循环【重点】

| 组件 | 职责 |
| --- | --- |
| kube-apiserver | 唯一入口，认证、鉴权、准入控制、读写 etcd |
| etcd | 保存全部集群状态，强一致，需定期备份 |
| kube-scheduler | 按 requests、亲和性、污点等为 Pod 选节点 |
| controller-manager | Deployment、ReplicaSet、Node 等控制器，执行调谐 |
| kubelet | 节点代理，管理 Pod 生命周期、探针、容器运行时 |
| kube-proxy / CNI / CSI | 维护 Service 转发规则、网络插件、存储插件 |

控制器通过 List-Watch 从 apiserver 获取变更，经 Informer 缓存到本地，在 `reconcile` 中「读实际状态 → 与 spec 比较 → 执行动作」。调谐是**幂等**且**水平触发**（关注当前状态而非单次事件），即使事件丢失，下一轮也会自我修正，这是 K8s 自愈的根本原因。滚动更新由 Deployment 控制：`maxSurge`、`maxUnavailable`、`revisionHistoryLimit`，失败可 `kubectl rollout undo` 回滚。

### 2.4 三种探针与 Java 慢启动【重点】

| 探针 | 失败后果 | 回答的问题 | 典型用途 |
| --- | --- | --- | --- |
| `readinessProbe` | 摘除 Service 流量，**不重启** | 现在能接流量吗 | 启动未完成、过载、依赖暂不可用 |
| `livenessProbe` | 杀容器并按重启策略重启 | 进程还活着且能工作吗 | 死锁、线程池卡死、假死 |
| `startupProbe` | 杀容器重启；成功前屏蔽另外两个 | 启动完成了吗 | 启动慢的 Java 应用 |

```yaml
startupProbe:
  httpGet: { path: /actuator/health/liveness, port: 8080 }
  periodSeconds: 10
  failureThreshold: 30      # 10 × 30 = 300s，需大于最慢启动时间
livenessProbe:
  httpGet: { path: /actuator/health/liveness, port: 8080 }
  periodSeconds: 10
  timeoutSeconds: 3
  failureThreshold: 3
readinessProbe:
  httpGet: { path: /actuator/health/readiness, port: 8080 }
  periodSeconds: 5
  failureThreshold: 2
```

- Spring Boot 开启 `management.endpoint.health.probes.enabled=true` 后才有 liveness / readiness 分组端点。
- **liveness 不要检查数据库、Redis 等外部依赖**：外部抖动会让所有 Pod 同时重启，把小故障放大成雪崩；依赖状态放 readiness。
- liveness 的 `timeoutSeconds` 与 `failureThreshold` 要留余量，避免一次 Full GC 停顿误杀；startup 成功后 liveness 才生效，所以 liveness 不必设很长的 `initialDelaySeconds`。

### 2.5 resources requests / limits 与 QoS【重点】

| 配置 | 作用 |
| --- | --- |
| `requests` | 调度依据，节点按它预留资源；也是 HPA CPU 使用率的分母 |
| `limits` | 运行上限。CPU 超限被 throttle（变慢不致死），内存超限被 OOMKilled（退出码 137） |

QoS 由两者关系决定：**Guaranteed** 要求每个容器都设置且 requests = limits，最后被驱逐；**Burstable** 为至少设置一项但不满足 Guaranteed；**BestEffort** 为完全未设置，最先被驱逐。命名空间级还有 `ResourceQuota` 限制总量与对象数、`LimitRange` 补默认值。延迟敏感的 Java 服务建议 requests = limits，避免 CPU 争抢造成长尾抖动，并保证堆 + 堆外 < 内存 limit。

### 2.6 HPA 弹性伸缩【重点】

HPA 控制器默认每 15 秒从 metrics-server 或自定义指标适配器取数，按公式 `期望副本 = ceil(当前副本 × 当前指标值 / 目标值)` 计算，结果被 `minReplicas` / `maxReplicas` 截断，并带约 10% 容忍度避免抖动。CPU 使用率是**相对于 requests** 计算的，不配 requests 的 Pod 无法按 CPU 伸缩。

| 指标来源 | 内容 | 适用 |
| --- | --- | --- |
| metrics-server | CPU、内存（相对 requests） | 通用入门 |
| Prometheus Adapter | QPS、P99、MQ 积压 | 贴近真实业务压力 |
| 外部指标 | 云监控、队列长度 | 事件驱动型服务 |

`behavior` 防抖：`scaleUp` 可激进（如 30 秒窗口），`scaleDown` 默认 300 秒稳定窗口。扩容**滞后**无法消除：采集间隔 + 指标窗口 + 调度 + 拉镜像 + Java 启动与 JIT 预热，通常几十秒到数分钟，缓解手段是按 QPS 提前扩容、保持最小副本、预热池、配合 cluster-autoscaler 或 KEDA。Java 冷启动 CPU 偏高还可能触发「刚扩容又扩容」的误判，应结合 startup 探针与业务指标。

### 2.7 ConfigMap / Secret 与热更新【了解】

| 项 | 用法 | 热更新 |
| --- | --- | --- |
| ConfigMap | 非敏感配置，`--from-file` / `--from-literal`，以环境变量或卷挂载 | 卷挂载会更新（分钟级延迟），环境变量**不会** |
| Secret | 密码、Token、证书，值为 Base64 | 同 ConfigMap；`subPath` 挂载不更新 |

Secret 默认只是 Base64 编码而非加密，必须开启 etcd 静态加密、用 RBAC 限制读权限，或对接 Vault / External Secrets；`immutable: true` 可减少 watch 压力。卷挂载更新后应用不会自动重载，需监听文件变化或调 `/actuator/refresh`，环境变量方式必须重启 Pod。

### 2.8 调度与亲和性【了解】

| 机制 | 作用 |
| --- | --- |
| `nodeSelector` | 最简单的节点标签匹配 |
| `nodeAffinity` | required（硬约束）与 preferred（软约束）、操作符表达式 |
| `podAffinity` / `podAntiAffinity` | 按 `topologyKey` 决定靠近或远离，常用反亲和把副本打散到不同节点/可用区 |
| `taints` / `tolerations` | 节点排斥 Pod，`NoSchedule`、`PreferNoSchedule`、`NoExecute`，配合专用节点 |

### 2.9 CrashLoopBackOff 与 Pending 排查路径【重点】

顺序固定：`kubectl get pod -o wide` 看状态与节点 → `kubectl describe pod` 看 Events 与 Last State → `kubectl logs` / `logs --previous` → 必要时 `kubectl exec` 或 `kubectl debug`。Events 信息密度最高，`kubectl get events --sort-by=.lastTimestamp` 可看全量。

| 状态 | 常见原因 | 确认方式 |
| --- | --- | --- |
| Pending | 资源不足（`Insufficient cpu/memory`）、亲和性/污点无匹配节点、PVC 未绑定、超出 ResourceQuota | describe 的 Events、`kubectl describe pvc` |
| ImagePullBackOff | 镜像名或 tag 错误、私有仓库缺 `imagePullSecrets`、网络不通 | Events 中的拉取错误 |
| ContainerCreating 卡住 | 挂载卷失败、CNI 未就绪、ConfigMap / Secret 缺失 | describe 事件 |
| CrashLoopBackOff | 启动异常（配置缺失、连不上 DB）、OOMKilled、liveness 过早、启动命令错误 | `logs --previous`、Last State 的 Reason 与 Exit Code |

CrashLoopBackOff 是重启间隔指数退避（10s、20s、40s…最大 5 分钟），只说明「启动后不断退出」。日志看不出问题时，可临时把 command 改成 `sleep 3600` 进容器手工执行启动脚本。

### 2.10 Java 落地：优雅停机与容器感知【重点】

Pod 删除流程：状态变 Terminating → Endpoints 异步摘除 → 执行 `preStop` → 发送 SIGTERM → 等待 `terminationGracePeriodSeconds`（默认 30 秒）→ 超时 SIGKILL。**摘流量与发信号是并行的**，没有 `preStop` 缓冲时信号到达仍有请求被转发进来，表现为发布期间零星 502。

```yaml
lifecycle:
  preStop:
    exec: { command: ["sh", "-c", "sleep 8"] }
terminationGracePeriodSeconds: 40
```

应用侧设置 `server.shutdown=graceful` 与 `spring.lifecycle.timeout-per-shutdown-phase=20s`：`preStop` 睡眠 5-10 秒等待 kube-proxy 与 Ingress 规则收敛，总时长要小于 `terminationGracePeriodSeconds`；Spring Boot 2.3+ 收到 SIGTERM 后停止接收新请求并等待在途请求完成，`@PreDestroy` 中关闭线程池、注销注册中心、停止 MQ 消费者。JVM 侧 JDK 8u191+ 默认 `UseContainerSupport`，用 `MaxRAMPercentage` 按 limit 计算堆；老版本或特殊场景显式设置 `-Xmx` 与 `-XX:ActiveProcessorCount`。

## 三、监控告警

### 3.1 Prometheus 拉模型与 Exporter【重点】

Prometheus 按 `scrape_interval`（常用 15 秒）主动向目标的 HTTP 端点拉取 `/metrics`，写入本地时序库；目标可由静态配置、文件发现或 Kubernetes 服务发现自动生成。

| 场景 | 方案 |
| --- | --- |
| 应用指标 | 直接暴露 `/actuator/prometheus`（Micrometer） |
| 第三方系统 | Exporter 转换格式：node_exporter、mysqld_exporter、redis_exporter、jmx_exporter |
| 短生命周期任务 | 任务结束 push 到 Pushgateway，Prometheus 再从它拉取 |
| 黑盒探测 | blackbox_exporter 做 HTTP / TCP / ICMP 探活 |

拉模型的优点是目标由服务端掌控、`up == 0` 天然可判断目标存活、调试时浏览器直接访问端点即可；缺点是短任务与 NAT 后的目标不友好。Pushgateway 数据不会自动过期，必须由推送方或定时任务清理，否则残留旧指标。

### 3.2 四种指标类型与分位数计算差异【重点】

| 类型 | 语义 | 典型用法 | 注意 |
| --- | --- | --- | --- |
| Counter | 单调递增，重启归零 | 请求总数、错误总数，用 `rate()` 求速率 | 直接看值无意义；命名以 `_total` 结尾 |
| Gauge | 可增可减的瞬时值 | 内存使用、线程数、队列长度 | 用 `avg_over_time`、`max_over_time`、`delta` |
| Histogram | 按预设桶累计计数，另有 `_sum`、`_count` | 延迟、请求大小分布 | 服务端 `histogram_quantile` 计算，**可跨实例聚合**，结果是估算值 |
| Summary | 客户端算好的分位数 | 单实例精确分位 | **不可聚合**，多个实例 P99 不能求平均 |

Histogram 的桶边界决定精度，必须覆盖真实取值区间（默认 `.005、.01、.025、.05、.1、.25、.5、1、2.5、5、10`）；P99 落在最大桶之上时只能得到 `+Inf`，等于没测到。集群环境优先 Histogram，因为只有它能先聚合再算分位。**标签基数**是最易忽视的坑：把 `userId`、`orderId`、原始 URL、TraceId 作为标签会让时间序列爆炸，应使用路由模板（`/order/{id}`）、枚举值，并在采集端裁剪 label。

### 3.3 PromQL 常用查询【重点】

```promql
# 每秒请求数（按接口）
sum by (uri) (rate(http_server_requests_seconds_count[5m]))

# 错误率
sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m]))
  / sum(rate(http_server_requests_seconds_count[5m]))

# P99 延迟（先聚合桶再算分位）
histogram_quantile(0.99,
  sum by (le, uri) (rate(http_server_requests_seconds_bucket[5m])))

# 堆内存使用率 / 目标失联 / CPU Top5
sum(jvm_memory_used_bytes{area="heap"}) / sum(jvm_memory_max_bytes{area="heap"})
up == 0
topk(5, sum by (pod) (rate(container_cpu_usage_seconds_total{container!=""}[5m])))
```

### 3.4 Grafana 看板与 RED / USE【了解】

- **RED**（面向服务）：Rate 请求速率、Errors 错误率、Duration 延迟分位。
- **USE**（面向资源）：Utilization 使用率、Saturation 饱和度（排队、throttle）、Errors 错误。
- 看板分层：总览（SLO、错误预算、核心接口）→ 服务（RED）→ 实例（JVM、GC、线程池、连接池）→ 依赖（DB、Redis、MQ）；图表标注单位与 P99 口径，Tag 保持低基数。

### 3.5 告警设计：避免「狼来了」【重点】

告警疲劳的根源是「不可行动的告警太多」。原则：**基于用户可感知的症状告警，原因类指标只上大盘**。

| 手段 | 做法 |
| --- | --- |
| 症状告警 | 告警错误率、P99、成功率，而不是单机 CPU 80% |
| 可行动 | 每条告警附 runbook、影响面、当前值；收到后无事可做就删除或降级 |
| 分级 | P0 电话 + 短信（核心业务不可用），P1 IM 群（工作时间处理），P2 仅记录 |
| 防抖 | `for: 5m` 持续时间，避免瞬时抖动触发 |
| 分组 | `group_by: [cluster, service, alertname]`，配合 `group_wait`、`group_interval`、`repeat_interval` |
| 抑制 | `inhibit_rules`：节点宕机等根因告警抑制该节点上所有衍生告警 |
| 聚合与静默 | 同一故障只报一条；计划维护用 silence 并设置自动过期 |

反例：`CPU > 80%` 直接打夜间电话。CPU 高但用户无感知时不该叫醒人，它属于排查线索而非告警；正确的是「核心接口错误率 > 1% 持续 5 分钟」或「P99 > 1s 持续 10 分钟」。

### 3.6 SLI / SLO / 错误预算【了解】

| 概念 | 含义 | 示例 |
| --- | --- | --- |
| SLI | 服务质量指标，可测量的具体数值 | 30 天成功率、P99 延迟、可用性 |
| SLO | 对 SLI 设定的目标 | 30 天成功率 ≥ 99.9% |
| 错误预算 | `1 - SLO` 允许的失败额度 | 99.9% 对应 30 天约 43 分钟不可用 |

基于错误预算的**多窗口燃尽率告警**比固定阈值准确：短窗口（1h）快速燃尽说明急性故障，立即处理；长窗口（3d）缓慢燃尽说明慢性劣化，工作日处理。预算用完冻结功能发布、专注稳定性；预算充足可加快迭代，这是研发与运维之间可量化的契约。

### 3.7 JVM 与中间件关键指标【重点】

| 层面 | 关键指标 | 说明 |
| --- | --- | --- |
| JVM 内存 | `jvm_memory_used_bytes` / `max_bytes`（heap、nonheap） | 关注老年代与 Metaspace 增速 |
| GC | `jvm_gc_pause_seconds`、`jvm_gc_memory_promoted_bytes_total` | P99 停顿与 Full GC 频率是延迟杀手 |
| 线程 | `jvm_threads_live_threads`、`jvm_threads_states_threads` | 线程暴涨常意味着阻塞或泄漏 |
| Web 容器 | `tomcat_threads_busy_threads`、`tomcat_threads_config_max_threads` | busy 接近 max 说明线程池打满 |
| 连接池 | Hikari `active`、`idle`、`pending`、`timeout` | pending 持续大于 0 说明池小或 SQL 慢 |
| 容器 | `container_cpu_cfs_throttled_seconds_total`、`container_memory_working_set_bytes` | throttle 比例能解释「CPU 没满却变慢」 |
| 中间件 | 慢查询、主从延迟、Redis 命中率、MQ 消费 lag | lag 持续增长是最直接的事故信号 |

排查延迟的顺序：先看容器 CPU throttle 与 GC 停顿，再看线程池与连接池排队，最后看下游依赖耗时；只盯 CPU 使用率高低于事无补。

## 四、日志体系

### 4.1 ELK / EFK 与 Loki 的链路差异【重点】

| 方案 | 采集 | 缓冲 | 处理 | 存储 | 检索 |
| --- | --- | --- | --- | --- | --- |
| ELK | Filebeat | Kafka（可选） | Logstash | Elasticsearch | Kibana |
| EFK | Fluent Bit / Fluentd | Kafka（可选） | Fluent Bit filter / Fluentd | Elasticsearch | Kibana |
| Loki | Promtail / Fluent Bit | 一般不需要 | 采集端 label 与 pipeline | Loki + 对象存储 | Grafana（LogQL） |

Elasticsearch 对日志做**倒排索引**，全文检索与聚合能力强，但索引与存储成本高；Loki 只索引**标签**（service、namespace、pod、level），正文压缩成 chunk 存对象存储，查询时按标签过滤再扫描，成本可低一个数量级，代价是不支持高效全文检索与复杂聚合。选型：需要任意关键字搜索、安全审计与复杂统计选 ELK；以服务名 + TraceId 精确定位为主、追求低成本选 Loki。

### 4.2 采集组件【重点】

| 组件 | 特点 | 位置 |
| --- | --- | --- |
| Filebeat | Go 编写，轻量，Harvester 逐文件读取，registry 记录位点，支持背压 | 节点 DaemonSet |
| Fluent Bit | C 编写，内存占用极小，插件够用，K8s 元数据丰富 | 节点 DaemonSet，**容器场景首选** |
| Logstash | JVM，解析与清洗能力最强，单实例常需 2-4G 内存 | 中心处理层 |

容器日志默认写 stdout，由运行时落到节点 `/var/log/containers/*.log`（CRI 格式），DaemonSet 采集后附加 `namespace`、`pod`、`node`、`container` 等元数据。Java 异常堆栈是**多行日志**，必须在采集端配置 multiline 合并，否则一条异常被拆成几十条，既难看又浪费存储。

### 4.3 结构化 JSON 日志与字段规范【重点】

| 字段 | 示例 | 说明 |
| --- | --- | --- |
| `timestamp` | `2026-10-25T10:00:00.123+08:00` | ISO8601 带时区，全链路统一，不混用本地时间 |
| `level` | `INFO` | 统一大写，便于聚合 |
| `service` / `instance` | `order-service` / `order-7d9f-abc` | 与 K8s 标签对齐 |
| `traceId` / `spanId` | `4bf92f3577b34da6` | 全链路串联的关键 |
| `thread` / `logger` | `http-nio-8080-exec-3` | 排查并发问题必需 |
| `message` | `create order success` | 只放可读文本，不要塞整个报文 |

用 `logstash-logback-encoder` 或 Log4j2 JSON Layout 输出，避免手工拼 JSON（转义与换行极易出错）；字段名一旦确定就不要改，下游看板与告警都依赖它。

### 4.4 TraceId 串联与 MDC【重点】

链路：入口（网关/过滤器）从请求头读取 `traceparent` 或 `X-Trace-Id`，没有就生成 → 放入 MDC → 日志 pattern 用 `%X{traceId}` 输出 → 调下游时通过 Feign / RestTemplate 拦截器、MQ 消息属性透传 → 下游继续复用。

```java
try {
    MDC.put("traceId", traceId);
    chain.doFilter(request, response);
} finally {
    MDC.remove("traceId");   // 线程池复用必须清理，否则串号
}
```

三个易错点：**异步线程不继承 MDC**（需 `TaskDecorator` 或手动传递上下文）、**线程池未清理导致下个请求带上一个请求的 TraceId**、**MQ 消费端未从消息头恢复上下文**。MDC 底层是 ThreadLocal，跨线程必须显式传播。

### 4.5 日志级别与异步 Appender【重点】

| 级别 | 语义 | 生产建议 |
| --- | --- | --- |
| ERROR | 需要人工介入的错误 | 全量保留，接入告警 |
| WARN | 异常但可自恢复、触发降级 | 保留，关注突增 |
| INFO | 关键业务节点（下单、支付回调） | 生产默认级别，控制数量 |
| DEBUG | 排查细节 | 默认关闭，按需动态开启 |

Logback `AsyncAppender` 让业务线程只入队，`queueSize` 默认 256，`discardingThreshold` 默认在剩余 20% 时丢弃 INFO 及以下，`neverBlock` 可避免阻塞业务；Log4j2 `AsyncLogger` 基于 Disruptor 无锁队列，吞吐更高。性能杀手排序：同步刷盘 > 打印行号/方法名（`%L`、`%M` 需生成调用栈）> 大对象 `toString` > 字符串拼接 > 异常堆栈刷屏。用占位符 `log.info("orderId={}", id)`，重参数场景先用 `isDebugEnabled()` 判断；生产 root 设 INFO，关闭 `additivity` 防止重复输出。

### 4.6 日志脱敏【了解】

- 敏感字段：手机号、身份证、银行卡、邮箱、地址、姓名；凭据类：password、token、secret、cookie、authorization、连接串。
- 实现层次：日志框架自定义 Converter、logstash encoder 掩码装饰器、敏感字段注解 + 序列化器、AOP 对入参出参统一脱敏。
- 采集端（Logstash / Fluent Bit filter）再做一层兜底；红线是不打印完整请求响应体、带参数 SQL、含密码的异常与配置。

### 4.7 日志量与成本控制【了解】

| 手段 | 做法 |
| --- | --- |
| 动态调级别 | 通过配置中心或 `/actuator/loggers` 临时开 DEBUG，用完调回 |
| 采样与限流 | 同类错误每分钟最多 N 条，高频接口按比例采样 |
| 采集端过滤 | DaemonSet 直接 drop DEBUG / TRACE，减少传输与存储 |
| 冷热分层 | 热数据留 ES，冷数据转对象存储，用 ILM 自动滚动 |
| 保留期 | 业务日志 7-30 天，审计日志按合规要求单独保留 |

粗略估算：单条 300 字节、每请求 5 条、200 QPS，一天约 25 GB 原始日志，压缩后仍有数 GB。日志量应按「每秒字节数」列入容量评审，而不是等磁盘报警再处理。

## 五、可观测性边界

### 5.1 Service Mesh【了解】

Service Mesh 把流量治理与安全能力从业务代码下沉到**数据面代理**。

| 层次 | 组件 | 职责 |
| --- | --- | --- |
| 控制面 | Istiod（Pilot / Citadel / Galley 合并） | 下发 xDS 配置、签发与轮换证书、校验配置 |
| 数据面 | Envoy sidecar 或 ambient 模式的 ztunnel | 劫持进出流量，执行路由、重试、熔断、mTLS、指标采集 |

注入 sidecar 后通过 init container 配置 iptables，把进出流量重定向到 Envoy 端口，业务无感知。能力包括自动 mTLS 与证书轮换、按 header / 权重灰度、超时重试熔断、故障注入、统一指标。代价同样明确：每跳增加 1-3ms 延迟、每个 Pod 多一个 sidecar 的资源开销、排障复杂度上升。与 Spring Cloud 的分工是——Mesh 管**东西向通信的基础设施能力**（加密、重试、路由、指标），Spring Cloud 管**业务语义**（熔断降级的业务规则、业务灰度）；两者同时配重试会造成重试放大，只能保留一层。多语言、存量服务多、需要统一 mTLS 时选 Mesh；纯 Java 团队、规模不大时 SDK 更简单。

### 5.2 OpenTelemetry【了解】

OpenTelemetry 是厂商中立的可观测性标准，统一 Trace、Metrics、Logs 三类信号的 API、SDK 与传输协议（OTLP，gRPC 4317 / HTTP 4318）。

| 组件 | 作用 |
| --- | --- |
| API / SDK | 埋点接口与实现，负责采样、批处理、资源属性 |
| Java Agent | 字节码增强自动埋点，覆盖 Spring MVC、JDBC、Redis、Kafka、gRPC，零代码改造 |
| Collector | 接收、处理（批量、脱敏、尾部采样）、导出，可扇出到多个后端 |

上下文传播遵循 W3C `traceparent`（`version-traceId-spanId-flags`），跨服务跨语言一致。与 SkyWalking 的差异：

| 维度 | OpenTelemetry | SkyWalking |
| --- | --- | --- |
| 定位 | 采集标准与工具链，不绑定后端 | 端到端 APM 平台，自带存储与 UI |
| 协议 | OTLP 标准协议 | 私有协议（新版也支持 OTLP 接收） |
| 优势 | 厂商中立、指标日志链路统一、生态增长快 | 开箱即用、Java 生态成熟、拓扑与告警内置 |

常见落地组合是「OTel Agent 采集 + Collector 处理 + 后端选型」，采集与后端解耦，后续换后端不用改埋点。

### 5.3 Serverless【了解】

Serverless = FaaS（函数按事件触发、按调用计费）+ BaaS（托管后端服务，如对象存储、数据库、消息队列）。平台代表：AWS Lambda、阿里云函数计算、Knative（在 K8s 上把副本缩到 0）。**冷启动**链路为：调度与拉镜像 → 运行时初始化 → JVM 启动 → 框架初始化 → 类加载 → 首次请求 JIT；优化手段有 GraalVM native image（毫秒级启动、内存低）、平台预置并发 / SnapStart、Spring Boot 3 的 AOT 与 CDS、精简依赖与延迟初始化。

| 适用 | 不适用 |
| --- | --- |
| 事件驱动（上传触发处理、Webhook、消息消费） | 长连接（WebSocket、gRPC 流） |
| 定时任务与运维脚本 | 有状态、需要本地缓存与常驻线程池 |
| 流量波峰波谷明显、长尾低频接口 | 持续高并发（单价可能高于常驻实例） |
| 快速验证与轻量 API | P99 敏感、无法接受冷启动 |

成本模型是「调用次数 + 执行时长（GB·秒）+ 闲置资源」，低流量与突发流量下非常划算。
