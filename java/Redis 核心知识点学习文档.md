## 一、Redis 为什么快

单机 Redis 可以达到每秒 10 万级的 QPS，原因是：纯内存操作、高效的数据结构、单线程执行命令避免了锁和上下文切换、I/O 多路复用让一个线程能处理大量连接。

### 1.1 单线程模型【核心】

「Redis 是单线程的」指的是**接收请求 → 解析 → 执行命令 → 返回结果**这条主链路由一个线程完成。Redis 进程本身有多个后台线程：关闭文件、AOF 刷盘、释放内存（`UNLINK`、`FLUSHALL ASYNC` 等惰性删除）都由后台线程处理。

**为什么用单线程**：Redis 的瓶颈是内存和网络，不是 CPU；单线程没有锁竞争和线程切换开销，实现简单，并且天然保证单个命令的原子性。

**代价**：一个慢命令会阻塞所有请求。所以线上禁用 `KEYS *`（用 `SCAN` 替代）、避免对大集合执行 `HGETALL`、`SMEMBERS`、`LRANGE 0 -1`，删除大 Key 用 `UNLINK`。

### 1.2 I/O 多路复用【核心】

Redis 基于 Reactor 模式实现了自己的事件库（ae），Linux 上底层用 epoll。一个线程监听所有客户端 socket，哪个就绪就处理哪个，不会因为某个连接等待数据而阻塞。与 select / poll 相比，epoll 不需要每次传入全部文件描述符，也不用遍历全部连接找就绪者，在大量连接时效率高得多。

### 1.3 Redis 6.0 的多线程 I/O【核心】

随着网络带宽提升，单线程读写 socket 和协议解析成了瓶颈。Redis 6.0 引入多线程来处理**网络读写和协议解析**，但**命令执行仍然是单线程**，所以没有并发安全问题。默认关闭，需配置 `io-threads 4`（建议小于 CPU 核数）。对于小包、低并发场景收益不大。

### 1.4 其他「快」的原因【重点】

- 每种类型在数据量小时用紧凑编码（listpack、intset），大时自动切换为哈希表、跳表等，兼顾内存和速度。
- 全局哈希表按 key 查找 O(1)；扩容采用**渐进式 rehash**，把迁移成本分摊到每次读写和定时任务中，避免一次性阻塞。
- RESP 协议简单，解析开销小。

## 二、数据结构

面试考数据结构有两层：对外的 5 种基本类型各适合什么场景；对内每种类型用什么编码实现、何时切换。

### 2.1 五大基本类型与底层编码【核心】

| 类型 | 底层编码（Redis 7） | 典型场景 |
| --- | --- | --- |
| String | int、embstr（≤ 44 字节）、raw，都基于 SDS | 缓存对象、计数器、分布式锁、Session |
| List | quicklist（双向链表，每个节点是一个 listpack） | 消息队列、最新列表 |
| Hash | listpack（元素少且小）→ hashtable | 对象属性、购物车 |
| Set | intset（全是整数且少）→ listpack（7.2）→ hashtable | 去重、标签、共同好友（交集）、抽奖 |
| ZSet | listpack（元素少且小）→ skiplist + hashtable | 排行榜、延时队列、滑动窗口限流 |

Redis 7.0 用 listpack 全面替代了 ziplist。切换阈值可配置，如 Hash 默认 `hash-max-listpack-entries 128`、`hash-max-listpack-value 64`。

### 2.2 SDS【重点】

Redis 没有直接用 C 字符串，而是自定义了简单动态字符串 SDS（头部记录 len、alloc）：

- O(1) 获取长度，C 字符串需要遍历。
- 二进制安全：用 len 判断结束，可以存 `\0`，因此能存图片、序列化数据。
- 修改前自动检查空间并扩容，不会缓冲区溢出。
- 空间预分配和惰性释放，减少内存重分配次数。

### 2.3 跳表与 ZSet【重点】

跳表在有序链表上加了多层「索引」，查找时从最高层开始，遇到更大的值就下降一层，平均复杂度 O(log N)。Redis 中每个新节点的层数随机生成（每上升一层概率 1/4，最高 32 层）。

**ZSet 为什么同时用跳表和哈希表**：跳表按 score 有序，支持范围查询和排名；哈希表存 member → score，让 `ZSCORE` 变成 O(1)。

**为什么用跳表而不是红黑树 / B+ 树**：范围查询更简单（找到起点后顺着链表遍历）；实现和调试更简单；插入删除只改前后指针，不需要旋转或分裂；B+ 树为磁盘 I/O 设计，对内存数据库没有优势。

### 2.4 特殊类型【了解】

| 类型 | 原理 | 场景 |
| --- | --- | --- |
| Bitmap | 基于 String 的位数组 | 签到、在线状态，1 亿用户约 12 MB |
| HyperLogLog | 概率算法，每个 key 固定 12 KB，标准误差 0.81% | UV 统计（允许误差） |
| GEO | 基于 ZSet，score 为 GeoHash 编码 | 附近的人、门店距离 |
| Stream | 消息日志 + 消费组 + ACK | 轻量消息队列，支持持久化和确认 |

## 三、持久化

RDB 是某一时刻的内存快照，恢复快但会丢失两次快照之间的数据；AOF 记录每条写命令，数据更完整但文件大、恢复慢；生产上推荐开启混合持久化。

### 3.1 RDB【核心】

- **触发**：`SAVE`（主线程执行，阻塞，线上禁用）、`BGSAVE`（fork 子进程执行）、配置 `save 3600 1 300 100 60 10000` 自动触发、主从全量同步、正常关闭。
- **写时复制（COW）**：fork 时父子进程共享内存页，只有主进程修改某页时才复制该页。所以子进程写入的是 fork 那一刻的一致快照，主进程仍可继续处理请求。
- **风险**：fork 本身会阻塞主线程（需复制页表，内存越大越慢）；写多时 COW 可能让内存接近翻倍。所以单实例内存建议不超过 10 GB。
- **优缺点**：文件紧凑、恢复快、适合备份；但会丢失最后一次快照之后的数据。

### 3.2 AOF【核心】

Redis **先执行命令、再写 AOF**（与 MySQL WAL 相反）。好处是不用检查命令语法、不阻塞当前命令；代价是执行后、写入前宕机会丢这条命令。

**写回策略 `appendfsync`**：

| 策略 | 行为 | 可能丢失 | 性能 |
| --- | --- | --- | --- |
| always | 每条写命令都 fsync | 几乎不丢 | 最差 |
| **everysec（默认）** | 后台线程每秒 fsync | 约 1 秒 | 折中，推荐 |
| no | 由操作系统决定何时刷盘 | 可能较多 | 最好 |

**AOF 重写**：AOF 会越来越大（同一个 key 改 100 次就有 100 条）。重写时 fork 子进程，按当前内存数据生成最精简的命令集，**不读旧 AOF 文件**。重写期间的新命令同时写入 AOF 缓冲区和重写缓冲区，完成后追加到新文件再替换。Redis 7.0 改为 Multi Part AOF（一个 base 文件 + 多个 incr 文件），不再需要重写缓冲区。

### 3.3 混合持久化【核心】

Redis 4.0 引入，`aof-use-rdb-preamble yes`（5.0 起默认开启）。AOF 重写时先把当前数据以 RDB 格式写在开头，之后的增量命令以 AOF 格式追加。恢复时先加载 RDB 部分（快），再重放少量 AOF（丢得少），兼得两者优点。

### 3.4 如何选择【重点】

| 场景 | 建议 |
| --- | --- |
| 纯缓存，数据可从数据库重建 | 可以关闭持久化，或只用 RDB 备份 |
| 能容忍分钟级丢失 | RDB |
| 业务数据、丢失要尽量少 | AOF everysec + 混合持久化 |

Redis 的定位是缓存，即使开启 always 也不应当作唯一的数据源。

## 四、过期删除与内存淘汰

这是两个不同的机制：**过期删除**处理「设了 TTL 且已到期」的 key；**内存淘汰**处理「内存达到 maxmemory 上限」时该踢掉谁。面试中常被混在一起问。

### 4.1 过期删除策略【核心】

Redis 把设了过期时间的 key 存在一个单独的「过期字典」中，采用**惰性删除 + 定期删除**组合：

- **惰性删除**：访问 key 时才检查是否过期，过期就删除并返回空。对 CPU 友好，但不再被访问的过期 key 会一直占用内存。
- **定期删除**：默认每秒 10 次（`hz 10`），每次从过期字典中随机抽 20 个 key，删掉已过期的；如果过期比例超过 25% 就继续抽，单次执行有时间上限（默认 25 ms），避免阻塞。

**坑**：大量 key 同一时刻过期，定期删除会连续跑满时间上限，导致请求延迟上升。所以过期时间要加随机值打散（这也是防缓存雪崩的手段）。

**主从下的过期**：从库不主动删除过期 key，等主库删除后同步 `DEL` 命令。Redis 3.2 起从库读到已过期的 key 会返回空。

### 4.2 八种内存淘汰策略【核心】

通过 `maxmemory-policy` 配置，分为三类：

| 类别 | 策略 | 说明 |
| --- | --- | --- |
| 不淘汰 | noeviction（默认） | 内存满后写命令直接报错 |
| 在设了过期时间的 key 中挑 | volatile-lru | 最近最少使用 |
| 同上 | volatile-lfu | 最不常使用（4.0 新增） |
| 同上 | volatile-random | 随机 |
| 同上 | volatile-ttl | 优先淘汰剩余寿命短的 |
| 在所有 key 中挑 | allkeys-lru | 最近最少使用 |
| 同上 | allkeys-lfu | 最不常使用 |
| 同上 | allkeys-random | 随机 |

**选择建议**：纯缓存场景用 `allkeys-lru`；有明显热点、访问频率差异大时用 `allkeys-lfu`；缓存和不能丢的数据混用一个实例时用 `volatile-lru`（并把不能丢的数据不设 TTL）。生产环境一定要设置 `maxmemory`。

### 4.3 近似 LRU 与 LFU【重点】

**近似 LRU**：真正的 LRU 需要维护一个大链表，每次访问都移动节点，开销大。Redis 在每个对象里记录最后访问时间（24 位 lru 字段），淘汰时随机采样 `maxmemory-samples`（默认 5）个 key，淘汰其中最久未访问的，并用一个候选池提高准确度。

**LFU**：解决 LRU 的「缓存污染」问题（一次性扫描把大量冷数据变成「最近访问」）。同样复用 24 位字段：高 16 位记录上次递减时间，低 8 位记录访问频率的**对数计数器**（最大 255，越大越难增加），并随时间衰减，让「曾经热」的 key 能被淘汰。

## 五、高可用：主从、哨兵与 Cluster

三者是逐步演进的：主从解决数据备份和读扩展，哨兵在主从基础上实现自动故障转移，Cluster 再解决单机内存和写入的容量上限。

### 5.1 主从复制【核心】

**全量同步**（第一次连接或无法增量时）：

1. 从库发送 `PSYNC replid offset`（第一次为 `PSYNC ? -1`）。
2. 主库返回 `FULLRESYNC`，执行 `BGSAVE` 生成 RDB 发给从库；期间的新写命令存入该从库的 replication buffer。
3. 从库清空旧数据并加载 RDB。
4. 主库把 replication buffer 中的命令发给从库，之后进入**命令传播**（长连接实时发送）。

**增量同步**：主库维护一个环形的 `repl_backlog_buffer`（默认 1 MB）。从库短暂断线重连后带上自己的 offset，如果这段数据还在 backlog 中，就只补发差额；已被覆盖则退化为全量同步。写入量大的场景要调大 `repl-backlog-size`。

**特点**：复制是异步的，所以主库宕机时可能丢失少量未同步的数据；从库默认只读。从库太多时可以用「主-从-从」级联减轻主库压力。

### 5.2 哨兵【核心】

哨兵（Sentinel）是独立的进程集群（至少 3 个，奇数），负责监控、自动故障转移和通知客户端新主库地址。

1. **主观下线**：某个哨兵 PING 主库，超过 `down-after-milliseconds` 未收到有效回复，认为它下线。
2. **客观下线**：该哨兵询问其他哨兵，认为下线的数量达到 `quorum` 时，判定主库客观下线。
3. **选举领头哨兵**：基于 Raft 思想，得到超过半数且不小于 quorum 的票的哨兵成为 leader，由它执行切换。
4. **选新主库**：先过滤掉已下线或网络状况差的从库，再依次按**优先级**（`replica-priority` 越小越优先）→ **复制偏移量**（数据越全越优先）→ **runid 最小**选择。
5. **切换**：新主库执行 `REPLICAOF NO ONE`，其余从库改为复制新主库，通知客户端，旧主库恢复后变为从库。

**脑裂【重点】**：旧主库只是与哨兵网络隔离，客户端仍在往里写；哨兵选出新主后旧主重新加入变成从库，全量同步时清空了这段时间的写入。解决：配置 `min-replicas-to-write 1` 和 `min-replicas-max-lag 10`，主库连不上足够数量的从库时拒绝写入，把丢失控制在很短的窗口内。

### 5.3 Redis Cluster【核心】

- **数据分片**：共 16384 个哈希槽，`slot = CRC16(key) mod 16384`，每个主节点负责一部分槽，每个主节点有自己的从节点。
- **去中心化**：节点间用 Gossip 协议交换槽分布和健康状态，不需要哨兵；主节点故障时由其他主节点投票，把它的从节点提升为主。
- **客户端路由**：Smart Client（如 JedisCluster、Lettuce）缓存槽与节点的映射，直接发往正确节点。

**MOVED 与 ASK【重点】**：

| 重定向 | 含义 | 客户端行为 |
| --- | --- | --- |
| MOVED | 槽已经**永久**归另一个节点 | 更新本地槽映射并重发 |
| ASK | 槽**正在迁移**，这个 key 已经迁到新节点 | 先向新节点发 `ASKING` 再发命令，**不更新**本地映射 |

**为什么是 16384 个槽【重点】**：节点心跳包要携带一个槽位图，16384 位是 2 KB，65536 位则是 8 KB，心跳太大浪费带宽；作者建议集群不超过 1000 个主节点，16384 个槽足够分配。

**多 key 操作限制【重点】**：`MGET`、事务、Lua 脚本涉及的多个 key 必须在同一个槽。可以用 **hash tag** 强制：`{user:1001}:profile` 和 `{user:1001}:orders` 只对花括号内的部分计算槽。代价是可能造成数据倾斜。

**扩缩容【了解】**：新增节点后用 `redis-cli --cluster reshard` 迁移部分槽，迁移以 key 为单位进行，期间客户端靠 ASK 重定向保证可用。

## 六、缓存问题与一致性

这一章是方案设计题的重灾区，回答时要说清「现象 → 原因 → 方案 → 方案的代价」。

### 6.1 穿透、击穿、雪崩【核心】

| 问题 | 现象 | 解决方案 |
| --- | --- | --- |
| **缓存穿透** | 查询**根本不存在**的数据，缓存和数据库都没有，请求每次都打到数据库（常见于恶意攻击） | 缓存空值（设较短 TTL）；布隆过滤器前置拦截；参数校验与限流 |
| **缓存击穿** | 一个**热点 key** 过期的瞬间，大量并发请求同时去重建缓存 | 互斥锁重建（只让一个线程查库）；逻辑过期（不设 TTL，过期后异步重建，期间返回旧值）；热点 key 永不过期 |
| **缓存雪崩** | **大量 key 同时过期**，或 Redis 宕机，请求整体压向数据库 | 过期时间加随机值打散；Redis 高可用；多级缓存；熔断、限流、降级；缓存预热 |

**互斥锁重建与逻辑过期如何选**：互斥锁保证一致性，但其他线程要等待，可用性差一些；逻辑过期不阻塞、性能好，但会短暂返回旧数据。

### 6.2 布隆过滤器【重点】

一个很长的位数组 + k 个哈希函数。写入时把 k 个位置置 1；查询时 k 个位置全为 1 才认为可能存在。

- **特点**：说「不存在」就一定不存在；说「存在」可能误判。
- **误判率**与位数组大小、哈希函数个数、元素数量有关。例如 1 亿元素、误判率 1% 约需 114 MB。
- **不支持删除**（会影响其他元素），需要定期重建，或用带计数的变体。
- **实现**：Redisson `RBloomFilter`、RedisBloom 模块、Guava `BloomFilter`（本地）。

### 6.3 缓存与数据库双写一致性【核心】

标准做法是 **Cache Aside（旁路缓存）**：读时先读缓存，未命中则读库并写缓存；写时**先更新数据库，再删除缓存**。

**为什么是删缓存而不是更新缓存**：两个并发写可能以相反顺序更新缓存，导致缓存是旧值；缓存值可能需要复杂计算，而写后未必会被读，懒加载更省。

**为什么先更新库、再删缓存**：如果「先删缓存、再更新库」，在删除后、更新库前，另一个读请求会把旧值读出并重新写入缓存，且这个窗口很容易发生（写库比读库慢）。「先更新库、再删缓存」也存在不一致的可能：读请求在缓存失效时读到旧值，并且在写请求更新库和删缓存之后才把旧值写入缓存。这要求「读库 + 写缓存」比「写库 + 删缓存」还慢，概率很低。

&#91;embedded content: 先删缓存再更新库的并发问题 · 5 步\]

②\~④ 只是一次普通读，很容易在①和⑤之间完成；把顺序换成「先更新库、再删缓存」后，这个窗口就几乎不存在了。

**进一步保障**：

- **延迟双删**：删一次缓存 → 更新库 → 睡眠一小段时间（大于一次读请求的耗时）→ 再删一次。延迟时间不好确定，是一种尽力而为的方案。
- **删除失败重试**：删缓存失败时把 key 发到 MQ 重试，直到成功。
- **订阅 binlog**：用 Canal 监听 MySQL binlog，由独立服务异步删除缓存，业务代码无侵入，并可结合 MQ 重试。
- **充当底线的 TTL**：所有缓存都设置过期时间，即使出现不一致也能在有限时间内自愈。

**结论**：缓存与数据库只能做到**最终一致**。对强一致要求高的数据（如余额、库存扣减），应该以数据库为准或不缓存；用分布式读写锁可以做到强一致，但牺牲了缓存的性能意义。

其他模式【重点】：**Read/Write Through** 由缓存层代理读写数据库，应用只和缓存打交道；**Write Behind** 只写缓存，由缓存异步批量写库，性能最好但可能丢数据，适合计数类场景。

### 6.4 大 Key 与热 Key【重点】

|  | 大 Key | 热 Key |
| --- | --- | --- |
| 定义 | String 超过 10 KB，或集合元素超过 5000 个（经验值） | 某个 key 的访问量远高于其他 key |
| 危害 | 操作耗时阻塞主线程、网络带宽打满、集群内存倾斜、删除时卡顿 | 单个分片 CPU 和带宽打满，而其他分片空闲 |
| 发现 | `redis-cli --bigkeys`、`MEMORY USAGE`、离线分析 RDB | `redis-cli --hotkeys`（LFU 策略下）、客户端埋点统计、代理层统计、京东 hotkey 等探测框架 |
| 处理 | 拆分成多个小 key（如 Hash 按字段取模分桶）；压缩；用 `UNLINK` 异步删除；用 `HSCAN` 分批遍历 | 本地缓存兜底（多级缓存）；把一个 key 复制成多份（key\_1…key\_N）随机读；读写分离 |

## 七、分布式锁与原子性

一个可用的分布式锁要满足：互斥、不会死锁（持有者宕机能自动释放）、只能由加锁者解锁、业务没执行完不能提前过期。下面从最简单的写法逐步补齐这几条。

### 7.1 从 SETNX 到正确写法【核心】

| 版本 | 写法 | 问题 |
| --- | --- | --- |
| 1 | `SETNX lock 1`，用完 `DEL` | 加锁后进程宕机，锁永远不释放 |
| 2 | `SETNX` 后再 `EXPIRE` | 两条命令不是原子的，中间宕机仍会死锁 |
| 3 | `SET lock 1 NX EX 30` | 业务执行超过 30 秒时锁已过期，A 会把 B 的锁 DEL 掉 |
| 4 | `SET lock <uuid> NX EX 30`，解锁时用 Lua 比较 value 再删除 | 仍然存在「业务没做完锁就过期」的问题 |
| 5 | 版本 4 + 自动续期（看门狗） | 这就是 Redisson 的做法 |

```lua
-- 解锁：只有持有者才能删除，判断和删除必须原子
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

### 7.2 Redisson【核心】

```java
RLock lock = redisson.getLock("order:lock:" + orderId);
if (lock.tryLock(3, TimeUnit.SECONDS)) {   // 不指定 leaseTime 才会启用看门狗
    try {
        // 业务逻辑
    } finally {
        if (lock.isHeldByCurrentThread()) lock.unlock();
    }
}
```

- **可重入**：用 Hash 结构存锁，field 为 `UUID:线程ID`，value 为重入次数，加锁和解锁都用 Lua 脚本保证原子性。
- **看门狗**：未指定 leaseTime 时，默认锁过期时间 30 秒，后台每 10 秒（过期时间的 1/3）检查一次，只要客户端还持有锁就续期到 30 秒。客户端宕机后不再续期，锁自动到期释放。**显式指定 leaseTime 则不会启用看门狗。**
- **等待重试**：获取失败时订阅锁释放的 Pub/Sub 消息，而不是忙等自旋。
- 还提供公平锁、读写锁、信号量、联锁（MultiLock）等。

### 7.3 主从切换与 RedLock【重点】

**问题**：客户端 A 在主库加锁成功，主库还没同步给从库就宕机，从库升为主后客户端 B 也能加锁，互斥失效。

**RedLock**：部署 N 个（通常 5 个）完全独立的 Redis 主节点，客户端依次向它们加锁，在超过半数（≥ 3）节点上成功、且总耗时小于锁的有效期才算成功；否则向所有节点解锁。

**争议**：Martin Kleppmann 指出 RedLock 依赖时钟不跳变，且客户端 GC 停顿时仍可能持锁过期，建议用「fencing token」（单调递增的版本号，由存储系统校验）。Redisson 已将 `RedissonRedLock` 标为废弃。实际工程中的做法：大多数场景用单集群 Redisson 即可，并在数据库层用唯一索引或乐观锁兜底；对正确性要求极高时改用 ZooKeeper / etcd 等 CP 系统。

### 7.4 Pipeline、事务与 Lua【重点】

| 机制 | 作用 | 原子性 |
| --- | --- | --- |
| Pipeline | 把多条命令打包一次发送，减少网络往返（RTT） | 无，其他客户端的命令可能插在中间 |
| 事务 MULTI / EXEC | 命令入队，EXEC 时一次性顺序执行，不被打断；`WATCH` 实现乐观锁 | 部分：语法错误时整体不执行；**运行时错误时其他命令照常执行，不支持回滚** |
| Lua 脚本 | 脚本整体在服务端执行，可以包含判断逻辑 | 执行期间不会插入其他命令；但脚本中途报错，之前的写入不会回滚 |

**实践**：批量读写用 Pipeline；「先判断再修改」的场景（解锁、限流、扣库存）用 Lua。Lua 脚本要短小，长脚本会阻塞整个 Redis；Cluster 下脚本的所有 key 必须在同一个槽。

## 八、典型应用、多级缓存与使用规范

面试官常问「你们项目里 Redis 是怎么用的」，下面的场景要能说出对应的数据结构和命令。

### 8.1 典型应用场景【重点】

| 场景 | 做法 |
| --- | --- |
| 对象缓存 | String 存 JSON，或 Hash 存字段（便于局部更新） |
| 分布式 Session / Token | String + TTL，Spring Session 直接支持 |
| 计数器 / 点赞数 | `INCR`、`HINCRBY`，定时异步落库 |
| 排行榜 | ZSet：`ZINCRBY` 加分、`ZREVRANGE key 0 9 WITHSCORES` 取前 10 |
| 固定窗口限流 | `INCR` + `EXPIRE`（用 Lua 保证原子） |
| 滑动窗口限流 | ZSet，score 为时间戳，删掉窗口外的记录后 `ZCARD` 计数；或用 Redisson `RRateLimiter`（令牌桶） |
| 延时任务 | ZSet，score 为执行时间，轮询 `ZRANGEBYSCORE` 取到期任务；或 Redisson `RDelayedQueue` |
| 秒杀扣库存 | 库存预热到 Redis，Lua 脚本判断并扣减，成功后发 MQ 异步下单 |
| 共同关注 / 抽奖 | Set：`SINTER`、`SRANDMEMBER`、`SPOP` |
| 签到 / UV | Bitmap / HyperLogLog |

### 8.2 本地缓存与多级缓存【重点】

**多级缓存架构**：请求先查本地缓存（Caffeine，纳秒级）→ 再查 Redis（毫秒级）→ 最后查数据库。本地缓存适合放少量、极热、变化少的数据，是热 Key 和 Redis 故障时的兜底。

**一致性代价**：多台应用各有一份本地缓存，数据更新后需要通知所有节点失效，常用 Redis Pub/Sub 或 MQ 广播；同时给本地缓存设较短的过期时间兜底。堆内缓存过大会加重 GC，要限制容量。

**Caffeine**：采用 W-TinyLFU 淘汰算法（小的 LRU 窗口吸收新数据 + Count-Min Sketch 估算频率决定是否进入主区），命中率接近理论最优，性能优于 Guava Cache，Spring Boot 2.x 起用它替代 Guava 作为默认本地缓存实现。

### 8.3 使用规范【重点】

- **key 命名**：`业务:表:id`，如 `order:detail:1001`；不要太长。
- **必须设置过期时间**，并加随机值打散。
- **禁用危险命令**：`KEYS`、`FLUSHALL`、`FLUSHDB` 用 `rename-command` 或 ACL 禁用；遍历用 `SCAN`。
- **避免大 Key**，集合操作用分页命令（`HSCAN`、`ZRANGE` 带范围）。
- **批量操作**用 `MGET` / Pipeline，控制每批数量。
- **客户端**：Spring Boot 2.x 起默认 Lettuce（基于 Netty，线程安全）；配置连接池和超时，避免 Redis 抖动拖垮业务线程。
- **监控**：关注内存使用率、命中率（`keyspace_hits` / `keyspace_misses`）、连接数、慢查询（`SLOWLOG GET`）、主从延迟。
