## 一、运行时内存结构

JVM 运行时数据区分为线程私有的程序计数器、虚拟机栈、本地方法栈，以及线程共享的堆和方法区；直接内存不属于运行时数据区，但也会 OOM。

### 1.1 运行时数据区【核心】

| 区域 | 线程 | 存什么 | 异常 |
| --- | --- | --- | --- |
| 程序计数器 | 私有 | 当前线程执行的字节码行号，线程切换后靠它恢复 | 唯一不会 OOM 的区域 |
| 虚拟机栈 | 私有 | 每次方法调用一个栈帧：局部变量表、操作数栈、动态链接、返回地址 | StackOverflowError、OOM |
| 本地方法栈 | 私有 | native 方法调用；HotSpot 把它与虚拟机栈合二为一 | 同上 |
| 堆 | 共享 | 几乎所有对象实例和数组；字符串常量池、静态变量（JDK 7 起）；GC 的主要区域 | `Java heap space` |
| 方法区（元空间） | 共享 | 类的元信息、运行时常量池、JIT 编译后的代码 | `Metaspace` |
| 直接内存 | — | NIO `DirectByteBuffer` 分配的堆外内存，Netty 大量使用 | `Direct buffer memory` |

堆内默认比例：Eden : S0 : S1 = 8 : 1 : 1，新生代 : 老年代 = 1 : 2。

**堆的分代布局**：新生代（Eden + 2 个 Survivor，默认比例 8:1:1）+ 老年代，新生代与老年代默认 1:2。这是传统分代收集器的布局；G1 把堆划分成大小相等的 Region，分代只是逻辑概念。

### 1.2 永久代到元空间【重点】

方法区是规范，永久代和元空间是 HotSpot 的实现。JDK 7 把字符串常量池和静态变量移到堆；JDK 8 去掉永久代，用使用**本地内存**的元空间替代。原因：永久代大小固定、难以评估，容易 `PermGen space` OOM；元空间默认只受本机内存限制，建议用 `-XX:MaxMetaspaceSize` 设上限。

### 1.3 对象创建过程【重点】

1. **类加载检查**：检查 new 指令对应的类是否已加载，没有则先加载。
2. **分配内存**：堆规整时用**指针碰撞**（把指针向空闲一侧移动对象大小），不规整时用**空闲列表**。并发安全靠 **TLAB**（每个线程在 Eden 预先分到一小块专属区域），用完后再用 CAS + 失败重试。
3. **初始化零值**：字段设为 0 / null / false，保证字段不赋初值也能使用。
4. **设置对象头**：写入哈希码、GC 年龄、锁状态、类型指针等。
5. **执行 `<init>`**：按程序员的意愿初始化（字段赋值、构造方法）。

### 1.4 对象内存布局与访问定位【重点】

对象 = **对象头**（Mark Word 8 字节 + 类型指针，开启压缩指针时 4 字节；数组还有 4 字节长度）+ **实例数据** + **对齐填充**（对象大小必须是 8 字节的整数倍）。所以 `new Object()` 在 64 位 JVM 上占 16 字节。Mark Word 的结构见并发文档的 synchronized 章节。

**访问定位【了解】**：句柄方式（引用指向句柄池，对象移动时只改句柄）或直接指针（少一次寻址、更快），HotSpot 用直接指针。

### 1.5 哪些区域会 OOM【核心】

| 报错信息 | 常见原因 |
| --- | --- |
| `Java heap space` | 内存泄漏（集合只增不删、ThreadLocal 未清理）、一次查询大量数据、堆设置太小 |
| `GC overhead limit exceeded` | 98% 的时间在 GC 却只回收不到 2% 的堆，实际上就是堆快满了 |
| `Metaspace` | 动态代理、CGLIB、Groovy 脚本等大量生成类，类加载器泄漏 |
| `Direct buffer memory` | NIO / Netty 堆外内存未释放或上限太小 |
| `unable to create native thread` | 线程太多（无界线程池）或受操作系统 ulimit 限制 |
| `StackOverflowError` | 递归太深或无限递归；`-Xss` 太小 |

### 1.6 逃逸分析【重点】

「对象都在堆上分配」并不绝对。JIT 发现对象不会逃出方法（没有被返回、没有赋给字段）时，可以做三种优化：**标量替换**（把对象拆成几个局部变量，放在栈上或寄存器中，HotSpot 的「栈上分配」实际靠的就是它）、**锁消除**、减少 GC 压力。JDK 6u23 起默认开启（`-XX:+DoEscapeAnalysis`）。

## 二、垃圾回收基础

GC 要回答三个问题：哪些对象是垃圾（可达性分析）、怎么回收（三种算法）、什么时候回收（Minor / Full GC 触发条件）。

### 2.1 可达性分析与 GC Roots【核心】

**为什么不用引用计数**：无法处理循环引用（A 引用 B、B 引用 A，外界都不再引用它们，计数仍不为 0）。

**可达性分析**：从一系列 GC Roots 出发沿引用链遍历，不可达的对象就是垃圾。GC Roots 包括：

- 虚拟机栈中局部变量引用的对象（各线程正在调用的方法的参数、局部变量）
- 本地方法栈中 JNI 引用的对象
- 方法区中类静态变量、常量引用的对象
- 被 synchronized 持有的对象、JVM 内部引用（系统类加载器、常驻异常对象等）

**finalize 的「缓刑」【了解】**：不可达的对象如果重写了 `finalize()` 且未执行过，会被放入队列执行，在其中可以自救一次。`finalize` 在 JDK 9 已废弃，不要使用。

### 2.2 四种引用【核心】

| 引用 | 回收时机 | 典型用途 |
| --- | --- | --- |
| 强引用 | 只要还引用着就不回收，宁可 OOM | 普通对象 `Object o = new Object()` |
| 软引用 SoftReference | 内存不足、即将 OOM 前回收 | 内存敏感的缓存 |
| 弱引用 WeakReference | 下一次 GC 就回收 | ThreadLocalMap 的 key、`WeakHashMap` |
| 虚引用 PhantomReference | 无法通过它拿到对象，只用于在对象被回收时收到通知 | 管理堆外内存（`DirectByteBuffer` 的 Cleaner） |

### 2.3 三种回收算法【核心】

| 算法 | 做法 | 优点 | 缺点 | 适合 |
| --- | --- | --- | --- | --- |
| 标记-清除 | 标记存活对象，清除其余 | 简单、不移动对象 | 产生内存碎片 | CMS 老年代 |
| 复制 | 内存分两块，把存活对象复制到另一块 | 无碎片、存活少时很快 | 浪费一部分空间；存活多时复制成本高 | 新生代（绝大多数对象朝生夕死） |
| 标记-整理 | 标记后把存活对象往一端移动 | 无碎片、不浪费空间 | 移动对象要更新引用，停顿长 | 老年代 |

**分代收集理论**：基于「绝大多数对象朝生夕死」和「熬过越多次 GC 的对象越难死」两个假说，新生代用复制算法、老年代用标记-清除或标记-整理。Survivor 只占新生代 10% 就是因为每次 Minor GC 后存活的对象很少。

### 2.4 对象晋升与分配担保【核心】

1. **对象优先在 Eden 分配**，Eden 满时触发 Minor GC，存活对象复制到 Survivor，年龄 +1。
2. **年龄达到阈值晋升**：默认 15 次（`-XX:MaxTenuringThreshold`，对象头里年龄只有 4 位，所以最大 15）。
3. **大对象直接进老年代**：避免在 Survivor 间反复复制（`-XX:PretenureSizeThreshold`；G1 中放入 Humongous Region）。
4. **动态年龄判定**：Survivor 中某个年龄及以下的对象总大小超过 Survivor 的一半，大于等于该年龄的对象直接晋升。
5. **Survivor 放不下**：Minor GC 后存活对象 Survivor 放不下，直接进入老年代。

**空间分配担保**：Minor GC 前检查老年代最大连续可用空间是否大于新生代所有对象总大小，或大于历次晋升的平均大小；不满足则先进行 Full GC。

### 2.5 GC 的分类与触发条件【核心】

- **Minor GC / Young GC**：只回收新生代，Eden 空间不足时触发，频率高、速度快。
- **Major GC / Old GC**：只回收老年代，只有 CMS 有单独的老年代并发回收。
- **Mixed GC**：回收新生代 + 部分老年代，G1 特有。
- **Full GC**：回收整个堆和元空间，停顿最长。触发条件：老年代空间不足；元空间不足；分配担保失败；显式调用 `System.gc()`（只是建议）；CMS 的 Concurrent Mode Failure；G1 的并发标记跟不上分配速度。

### 2.6 GC 实现细节【重点】

**STW 与安全点**：枚举 GC Roots 和移动对象时必须暂停所有用户线程（Stop The World）。线程只能在「安全点」停下（方法调用、循环跳转、异常跳转等位置），此时 JVM 已通过 OopMap 知道栈上哪些位置是引用，不必全栈扫描。

**跨代引用与卡表**：Minor GC 只扫新生代，但老年代对象可能引用新生代对象。为了不扫描整个老年代，用**记忆集**记录哪些老年代区域存在跨代引用，卡表是它的一种实现（每 512 字节一个卡页），由写屏障在引用赋值时维护。

**三色标记与漏标**：并发标记把对象分为白（未访问）、灰（已访问但引用未扫完）、黑（已扫完）。用户线程同时修改引用可能导致**漏标**：黑色对象新增了指向白色对象的引用，同时灰色对象到该白色对象的引用被删除，结果存活对象被当成垃圾。两种解决方式：

- **增量更新**（CMS）：记录黑色对象新增的引用，重新标记时以它们为根再扫一次。
- **原始快照 SATB**（G1）：记录灰色对象被删除的引用，按标记开始时的快照处理，可能产生浮动垃圾但不会漏标。

## 三、垃圾收集器

收集器的演进主线是「停顿时间越来越短」：从全程 STW 的 Serial，到并发标记的 CMS，到可预测停顿的 G1，再到亚毫秒级停顿的 ZGC。JDK 9 起默认收集器为 G1。

### 3.1 收集器概览【重点】

| 收集器 | 区域 | 算法 | 特点 | 现状 |
| --- | --- | --- | --- | --- |
| Serial / Serial Old | 新生代 / 老年代 | 复制 / 标记-整理 | 单线程，全程 STW | 客户端、小内存 |
| Parallel Scavenge / Parallel Old | 新生代 / 老年代 | 复制 / 标记-整理 | 多线程，**吞吐量优先** | JDK 8 默认 |
| ParNew + CMS | 新生代 / 老年代 | 复制 / 标记-清除 | 并发标记、并发清除，**停顿优先** | JDK 9 废弃，JDK 14 移除 |
| G1 | 整堆（Region） | 整体标记-整理，Region 间复制 | 可设定停顿目标，兼顾吞吐 | JDK 9 起默认，主流 |
| ZGC | 整堆 | 并发标记-整理 | 停顿通常 < 1 ms，与堆大小无关 | JDK 15 正式，JDK 21 支持分代 |
| Shenandoah | 整堆 | 并发整理 | 低停顿，由 Red Hat 主导 | OpenJDK 12 引入 |

### 3.2 CMS【重点】

流程分四步：**初始标记**（STW，只标记 GC Roots 直接关联的对象，很快）→ **并发标记**（与用户线程同时运行，最耗时）→ **重新标记**（STW，修正并发期间的变动）→ **并发清除**。

三个缺点：

1. **CPU 敏感**：并发阶段占用一部分 CPU，降低吞吐。
2. **浮动垃圾与 Concurrent Mode Failure**：并发清除时新产生的垃圾只能等下次；老年代要预留空间，预留不足时会退化为 Serial Old 做单线程 Full GC，停顿很长。
3. **内存碎片**：标记-清除不压缩，碎片多时大对象分配失败会提前触发 Full GC。

### 3.3 G1【核心】

**Region**：把堆分成约 2048 个大小相等的 Region（1\~32 MB），每个 Region 可以是 Eden、Survivor、Old 或 Humongous（存大对象，超过 Region 一半即为大对象）。分代不再是连续的物理区域。

**可预测的停顿**：用 `-XX:MaxGCPauseMillis`（默认 200 ms）设定目标。G1 跟踪每个 Region 的回收价值（可回收空间 / 耗时），在目标时间内优先回收价值最大的 Region，这也是「Garbage First」名字的由来。

**回收过程**：

1. **Young GC**：Eden 满时触发，STW，多线程复制存活对象。
2. **并发标记周期**：老年代占堆比例达到 `-XX:InitiatingHeapOccupancyPercent`（默认 45%）时触发：初始标记（搭乘 Young GC）→ 并发标记（SATB）→ 最终标记（STW）→ 清理（统计各 Region 价值）。
3. **Mixed GC**：回收全部年轻代 + 部分高价值老年代 Region。
4. **Full GC**：回收速度跟不上分配速度时发生，JDK 10 起改为并行 Full GC，但仍应尽量避免。

**跨 Region 引用**：每个 Region 有自己的记忆集（RSet），记录「谁引用了我」，回收单个 Region 时不必扫全堆。代价是 RSet 占用额外内存，约为堆的 10%\~20%。

### 3.4 ZGC【重点】

**目标**：停顿时间不超过 1 ms，支持 TB 级堆，停顿时间不随堆大小增长。几乎所有工作（包括对象移动）都是并发的，STW 只用于处理 GC Roots。

**关键技术**：

- **染色指针**：在 64 位引用的高位中存放标记信息，不用访问对象本身就能知道它的 GC 状态。
- **读屏障**：用户线程从堆中读取引用时检查颜色，如果对象已被移动，就通过转发表找到新地址并顺便修正引用（自愈）。这是并发移动对象的基础。
- **代价**：读屏障带来一定吞吐损耗；不支持压缩指针。JDK 21 引入分代 ZGC（`-XX:+UseZGC -XX:+ZGenerational`），JDK 23 起分代模式成为默认。

### 3.5 如何选择【重点】

| 场景 | 推荐 |
| --- | --- |
| 小内存、单核、客户端工具 | Serial |
| 后台批处理、离线计算，只看吞吐 | Parallel |
| 绝大多数在线业务，堆 4\~32 GB | G1（默认即可） |
| 大堆（32 GB 以上）或对延迟非常敏感（交易、实时系统） | ZGC（JDK 21+） |

经验：不要一上来就调参。先用默认的 G1 加上合理的堆大小，根据 GC 日志发现问题再针对性调整。

## 四、类加载机制

类从被加载到卸载经历加载、验证、准备、解析、初始化、使用、卸载，其中验证、准备、解析合称「连接」。面试重点是前五步和双亲委派。

### 4.1 类加载五阶段【核心】

| 阶段 | 做什么 |
| --- | --- |
| 加载 | 通过全限定名获取二进制字节流（jar、网络、动态生成等），转为方法区的数据结构，并在堆中生成 `Class` 对象 |
| 验证 | 文件格式（魔数 `0xCAFEBABE`、版本号）、元数据、字节码、符号引用验证，确保不会危害 JVM |
| 准备 | 为**静态变量**分配内存并设**零值**；`static int a = 10` 此时 a 为 0，而 `static final int a = 10` 的常量此时就是 10 |
| 解析 | 把常量池中的符号引用替换为直接引用（内存地址） |
| 初始化 | 执行 `<clinit>()`：编译器收集静态变量赋值和 static 代码块生成，按代码顺序执行 |

**`<clinit>` 线程安全【重点】**：JVM 保证多线程下只有一个线程执行 `<clinit>`，其他线程阻塞等待。这就是「静态内部类单例」线程安全且懒加载的原理。反过来，`<clinit>` 里做耗时操作会阻塞所有用到该类的线程。

**初始化时机【重点】**（主动引用才触发）：`new` 对象、读写静态字段（非编译期常量）、调用静态方法、反射调用、初始化子类时先初始化父类、启动类（main 所在类）。**不会触发**：通过子类引用父类静态字段（只初始化父类）、定义对象数组、引用编译期常量。

### 4.2 类加载器与双亲委派【核心】

**三类内置加载器**（JDK 9+）：

- **启动类加载器 Bootstrap**：C++ 实现，加载 `java.base` 等核心模块，在 Java 中表示为 null。
- **平台类加载器 Platform**：加载其他 JDK 模块（JDK 8 及以前叫扩展类加载器 Extension，加载 `jre/lib/ext`）。
- **应用类加载器 Application**：加载 classpath 上的类，即我们的业务代码。

**双亲委派**：加载器收到请求后先交给父加载器，父加载器无法加载时自己才去加载。这里的「父」是组合关系（parent 字段），不是继承。

&#91;embedded content: 双亲委派 · 4 层类加载器\]

自己写的 `java.lang.String` 会被一路委派到 Bootstrap，由它加载 JDK 自带的版本，所以伪造的核心类永远不会生效。

```java
// ClassLoader.loadClass 核心逻辑（简化）
protected Class<?> loadClass(String name, boolean resolve) {
    synchronized (getClassLoadingLock(name)) {
        Class<?> c = findLoadedClass(name);           // 1. 已加载过直接返回
        if (c == null) {
            try {
                c = (parent != null) ? parent.loadClass(name, false)  // 2. 委派父加载器
                                     : findBootstrapClassOrNull(name);
            } catch (ClassNotFoundException ignored) {}
            if (c == null) c = findClass(name);       // 3. 父加载器找不到再自己加载
        }
        return c;
    }
}
```

**为什么要双亲委派**：保证核心类的安全（自己写的 `java.lang.String` 不会替换掉 JDK 的）；避免同一个类被重复加载。判断两个类是否相同，要看全限定名**和加载它的类加载器**都相同。

### 4.3 打破双亲委派【重点】

**自定义类加载器**：只想改变加载来源（如加密 class）就重写 `findClass`，保留双亲委派；要打破双亲委派就重写 `loadClass`。

| 场景 | 为什么要打破 | 怎么做 |
| --- | --- | --- |
| SPI（JDBC、JNDI） | `DriverManager` 由启动类加载器加载，却要加载 classpath 上厂商的驱动实现，父加载器看不到子加载器的类 | **线程上下文类加载器**：由父加载器请求子加载器去加载（`ServiceLoader` 就是这样做的） |
| Tomcat | 一个 Tomcat 部署多个 Web 应用，各自依赖同一个库的不同版本，需要相互隔离 | 每个应用一个 `WebappClassLoader`，优先加载自己 `WEB-INF` 下的类，找不到再委派（JDK 核心类仍先交给上层） |
| 热部署 / OSGi | 不重启进程替换代码 | 丢弃旧类加载器，用新的类加载器重新加载；OSGi 是网状委派结构 |

## 五、JVM 调优与问题排查

JVM 调优的目标不是把参数调到极致，而是让 GC 停顿和频率满足业务要求。大多数线上问题的根因在代码（内存泄漏、大对象、死循环），不在参数。

### 5.1 常用参数【核心】

| 参数 | 含义 | 建议 |
| --- | --- | --- |
| `-Xms` / `-Xmx` | 初始 / 最大堆 | 设成一样，避免运行时扩缩容 |
| `-Xmn` | 新生代大小 | G1 下不要设，会影响停顿目标的自动调整 |
| `-Xss` | 线程栈大小，默认 1 MB | 线程多时可调小 |
| `-XX:MetaspaceSize` / `-XX:MaxMetaspaceSize` | 元空间初始阈值 / 上限 | 如 256m / 512m |
| `-XX:+UseG1GC` / `-XX:+UseZGC` | 选择收集器 | JDK 9+ 默认 G1 |
| `-XX:MaxGCPauseMillis` | G1 停顿目标，默认 200 | 设太小会让每次回收太少，反而更频繁 |
| `-XX:+HeapDumpOnOutOfMemoryError` + `-XX:HeapDumpPath` | OOM 时自动转储堆 | **生产必开** |
| `-Xlog:gc*:file=gc.log` | GC 日志（JDK 9+ 统一日志） | JDK 8 用 `-XX:+PrintGCDetails -Xloggc` |
| `-XX:MaxRAMPercentage` | 容器中按容器内存百分比设置堆 | 容器环境推荐用它替代 -Xmx，如 75.0 |

**堆大小怎么定【重点】**：经验做法是线上观察 Full GC 后老年代的存活数据量，堆设为它的 3\~4 倍。容器里还要给元空间、线程栈、直接内存和操作系统留出空间，堆一般不超过容器内存的 75%，否则会被容器 OOM Kill。JDK 8u191 起 JVM 能正确识别容器的 CPU 和内存限制。

### 5.2 常用工具【重点】

| 工具 | 用途 | 常用命令 |
| --- | --- | --- |
| jps | 查看 Java 进程 | `jps -l` |
| jstat | GC 统计，看各区使用率和 GC 次数、耗时 | `jstat -gcutil <pid> 1000` |
| jstack | 线程堆栈，查死锁、阻塞、CPU 热点 | `jstack <pid> > t.txt` |
| jmap | 堆对象统计、导出堆 | `jmap -histo:live <pid>`、`jmap -dump:live,format=b,file=h.hprof <pid>` |
| jcmd | 上述功能的统一入口（官方推荐） | `jcmd <pid> GC.heap_dump`、`Thread.print` |
| Arthas | 在线诊断，不重启 | `dashboard`、`thread -n 3`、`trace`、`watch`、`jad` |
| MAT | 分析 hprof，找泄漏 | Leak Suspects、支配树（Dominator Tree） |
| JFR + JMC | 低开销持续采集运行数据 | `jcmd <pid> JFR.start duration=60s filename=r.jfr` |

注意：`jmap -dump` 和 `-histo:live` 会触发 Full GC 并暂停应用，大堆上可能持续数十秒，生产上应先把该实例摘掉流量。

### 5.3 CPU 飙高排查【核心】

1. `top` 找到 CPU 最高的 Java 进程 PID。
2. `top -Hp <pid>` 找到该进程内 CPU 最高的线程 TID。
3. `printf '%x\n' <tid>` 转为 16 进制。
4. `jstack <pid> | grep -A 30 'nid=0x<hex>'` 看这个线程在执行什么代码。
5. 如果是 GC 线程占用 CPU，转向「频繁 GC」排查；如果是业务线程，常见原因是死循环、正则回溯、大量序列化、CAS 空转。

用 Arthas 更快：`thread -n 3` 直接列出最忙的 3 个线程及堆栈。

### 5.4 OOM 排查【核心】

1. **看报错类型**：是 heap、Metaspace、Direct buffer 还是无法创建线程（见 1.5 节），决定往哪个方向查。
2. **拿到堆转储**：依赖 `-XX:+HeapDumpOnOutOfMemoryError` 自动生成的 hprof，或用 jcmd 手动导出。
3. **MAT 分析**：看 Leak Suspects 报告和支配树，找到占用最大的对象，再通过 Path to GC Roots 找到是谁引用着它。
4. **定位代码并修复**：常见原因是静态集合无限增长、本地缓存没有上限、ThreadLocal 未 remove、一次性从数据库查出百万行、无界队列堆积。
5. 若不是泄漏而是正常业务量增长，再考虑加大堆或扩容。

### 5.5 频繁 Full GC 排查【核心】

**观察**：`jstat -gcutil <pid> 1000` 看 FGC 次数增长和老年代（O）使用率；配合 GC 日志看每次 Full GC 的原因和回收后剩余量。

| 现象 | 可能原因 | 处理 |
| --- | --- | --- |
| Full GC 后老年代几乎不下降 | 内存泄漏或堆太小 | dump 堆用 MAT 分析；确实不够就加大堆 |
| 老年代增长很快，Full GC 后能降下来 | 对象过早晋升：Survivor 太小、大对象多 | 加大新生代或 Survivor；减少大对象（分页查询、流式处理） |
| 元空间触发 | 动态生成类过多 | 增大 MaxMetaspaceSize；检查反射、代理、脚本引擎的使用 |
| 代码中有 `System.gc()` | 第三方库或 RMI 定时调用 | `-XX:+DisableExplicitGC`（注意会影响依赖它回收直接内存的 NIO） |
| G1 出现 to-space exhausted | 并发标记启动太晚、大对象太多 | 调低 IHOP、增大 Region 或堆 |

**一个可用的面试案例框架**：告警现象（接口 RT 飙升、Full GC 每分钟多次）→ 用 jstat / GC 日志确认 → dump 堆用 MAT 定位到某个导出接口一次加载全量数据 → 改为分页 + 流式写出 → 验证指标恢复，并补上监控告警。

## 六、字节码与 JIT

这部分在图谱中是「了解」级别，面试中一般作为加分项出现，重点是能说清 Java 为什么「编译与解释并存」。

### 6.1 解释执行与 JIT【重点】

Java 源码先由 javac 编译成字节码，JVM 启动后先由解释器逐条解释执行（启动快）。当某个方法或循环被判定为**热点代码**（方法调用计数器、回边计数器超过阈值）时，JIT 把它编译成本地机器码并缓存，之后直接执行机器码。这就是服务刚启动时较慢、「预热」后变快的原因。

**分层编译**（JDK 8 起默认）：

- **C1（Client 编译器）**：编译快，优化简单，先让热点代码快速变成机器码，并收集性能数据。
- **C2（Server 编译器）**：编译慢，利用收集到的数据做激进优化，生成更高效的代码。如果优化假设不再成立，会**去优化**回到解释执行。

### 6.2 常见 JIT 优化【重点】

- **方法内联**：把短小的被调用方法的代码直接复制到调用处，省掉调用开销，并为其他优化创造条件。是最重要的优化，这也是 getter / setter 没有性能损耗的原因。
- **逃逸分析**：及其带来的标量替换、锁消除（见 1.6 节）。
- **公共子表达式消除、数组边界检查消除、循环展开**等。

### 6.3 Class 文件与字节码【了解】

Class 文件结构：魔数 `0xCAFEBABE` → 版本号 → 常量池 → 访问标志 → 类 / 父类 / 接口索引 → 字段表 → 方法表（字节码在方法的 Code 属性中）→ 属性表。用 `javap -v Xxx.class` 可以查看。

JVM 是基于栈的虚拟机，字节码指令从操作数栈取值计算。以 `i++` 为例，实际是 `getfield` → `iconst_1` → `iadd` → `putfield` 多条指令，这就是它不是原子操作的底层原因。方法调用指令有 `invokestatic`、`invokespecial`、`invokevirtual`、`invokeinterface`、`invokedynamic`（Lambda 底层使用）。

### 6.4 字节码增强与 AOT【了解】

- **字节码增强**：ASM（底层、性能高）、ByteBuddy、Javassist。Spring AOP 的 CGLIB 代理、Mockito、Arthas、SkyWalking 等 APM 探针（Java Agent + Instrumentation）都基于它们。
- **AOT**：GraalVM Native Image 在构建期把应用编译成本地可执行文件，启动快、内存小，适合 Serverless 和容器弹性扩缩容；代价是反射、动态代理需要提前配置，峰值性能可能不如 JIT。Spring Boot 3 已支持。
