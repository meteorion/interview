## 一、MQ 的作用、代价与选型

引入 MQ 是用「最终一致」换取解耦、异步和削峰。回答「为什么用 MQ」时，最好用自己项目里的场景说明。

### 1.1 三大作用【重点】

| 作用 | 含义 | 例子 |
| --- | --- | --- |
| 解耦 | 生产者只管发消息，不关心有哪些下游；新增下游不用改上游代码 | 下单后通知库存、积分、物流、数据分析 |
| 异步 | 非核心步骤放到后台执行，缩短主链路响应时间 | 注册后发短信、发邮件 |
| 削峰 | 流量洪峰先进队列，下游按自己的能力消费 | 秒杀请求先入队，异步创建订单 |

### 1.2 引入 MQ 的代价【了解】

- **可用性降低**：MQ 本身成了新的单点，需要集群化。
- **复杂度上升**：要处理消息丢失、重复、乱序、积压。
- **一致性问题**：上下游之间只能做到最终一致，需要补偿和对账。

### 1.3 Kafka、RocketMQ、RabbitMQ 选型【重点】

| 维度 | Kafka | RocketMQ | RabbitMQ |
| --- | --- | --- | --- |
| 语言 / 出身 | Scala + Java，LinkedIn | Java，阿里 | Erlang，实现 AMQP 协议 |
| 吞吐 | 最高，单机百万级 TPS | 高，单机十万级 | 较低，单机万级 |
| 延迟 | 毫秒级 | 毫秒级 | 微秒级，最低 |
| 消息模型 | 发布订阅，消费者自己拉取 | 发布订阅 | 灵活的 Exchange 路由 |
| 事务消息 | 有事务，但不是「本地事务 + 消息」的一致性 | **原生支持**（半消息 + 回查） | 无 |
| 延时消息 | 不支持 | 支持（5.x 任意时间） | 插件或 TTL + 死信 |
| 消息回溯 | 支持（重置 offset） | 支持（按时间） | 不支持，消费即删 |
| 典型场景 | 日志收集、埋点、大数据、流式计算 | 业务消息、交易、订单 | 中小规模业务、复杂路由 |

**一句话选型**：大数据和日志用 Kafka；对可靠性、事务消息和延时消息有要求的业务系统用 RocketMQ；规模不大、需要灵活路由的用 RabbitMQ。

### 1.4 Push 与 Pull【重点】

- **Push**：Broker 主动推给消费者，实时性好，但消费者处理不过来时会被压垮，RabbitMQ 用 `prefetch`（`basicQos` 的 `prefetchCount`）限制每个消费者手上**未 ack 的消息上限**。设得太大等于推了一堆没人处理的消息，消费者一挂就要大量重投；设得太小（如 1）则吞吐上不去，因为每次都要等 ack 才发下一条。经验值：按「单条处理耗时 × 期望吞吐」估算，批量消费可开到几十到几百。
- **Pull**：消费者主动拉，按自己的能力消费，Kafka 采用这种方式。为避免空轮询，用**长轮询**：没有消息时请求在 Broker 端挂起一段时间。RocketMQ 的 Push 消费者底层也是长轮询 Pull。

## 二、Kafka 核心

Kafka 本质上是一个分布式的、按分区追加写的提交日志。理解了「分区 + 副本 + offset」这三个概念，其余问题都能推导出来。

### 2.1 基本模型【核心】

| 概念 | 含义 |
| --- | --- |
| Broker | 一个 Kafka 服务节点 |
| Topic | 消息的逻辑分类 |
| Partition | Topic 的物理分片，是并行和扩展的单位；分区内消息有序、只追加 |
| Offset | 消息在分区内的序号；消费者自己记录消费到哪了 |
| Replica | 分区的副本，分为 Leader 和 Follower；**读写都经过 Leader**（可配置从最近的 Follower 读） |
| Consumer Group | 组内每个分区只由一个消费者消费；不同组之间互不影响，各自消费全量 |
| Controller | 负责分区 Leader 选举和集群元数据管理 |

若组内再加入第 4 个消费者，它会空闲，因为只有 3 个分区。

**推论**：同一个消费者组内，消费者数量超过分区数时，多出来的消费者是空闲的，所以**分区数决定了消费并行度上限**。

**KRaft【重点】**：早期 Kafka 依赖 ZooKeeper 存元数据和选 Controller。Kafka 2.8 引入 KRaft 模式（基于 Raft，由 Kafka 自己管理元数据），3.3 起可用于生产，**4.0 彻底移除了 ZooKeeper**。好处是部署更简单、支持的分区数更多、故障恢复更快。

### 2.2 副本、ISR 与 HW、LEO【核心】

- **ISR**（In-Sync Replicas）：与 Leader 保持同步的副本集合（包括 Leader 自己）。Follower 超过 `replica.lag.time.max.ms`（默认 30 秒）没跟上就被移出 ISR，追上后再加回来。
- **LEO**（Log End Offset）：每个副本下一条消息要写入的位置。
- **HW**（High Watermark）：ISR 中所有副本 LEO 的最小值。**消费者只能看到 HW 之前的消息**，即只有被 ISR 全部副本确认的消息才对消费者可见。这样 Leader 切换后消费者不会读到「新 Leader 上不存在」的消息。
- **Leader 选举**：Leader 宕机后从 ISR 中选新 Leader。如果 ISR 为空，`unclean.leader.election.enable`（默认 false）决定是否允许从非 ISR 副本选：允许则可用但可能丢数据，不允许则分区不可用直到原副本恢复。

### 2.3 高吞吐原理【核心】

1. **顺序写磁盘**：消息只追加到分区日志末尾，顺序 I/O 的速度远高于随机 I/O。
2. **利用 PageCache**：写入先进操作系统页缓存，由 OS 异步刷盘；刚写入的消息通常很快被消费，直接从页缓存读。数据不放 JVM 堆，也避免了 GC 问题。
3. **零拷贝**：消费时用 `sendfile`（Java 中是 `FileChannel.transferTo`）把数据从页缓存直接发到网卡，省掉了内核态与用户态之间的拷贝。
4. **批量与压缩**：生产者按批发送（`batch.size`、`linger.ms`），整批压缩（lz4 / zstd 等），Broker 不解压直接存储。
5. **分区并行**：多个分区分布在不同 Broker 上，读写水平扩展。
6. **稀疏索引**：日志分段（segment）存储，每段有 `.index`（offset→位置）和 `.timeindex`，用二分查找定位消息。

### 2.4 生产者：acks、幂等与事务【核心】

| acks | 含义 | 可靠性 |
| --- | --- | --- |
| 0 | 不等 Broker 响应 | 可能丢失，吞吐最高 |
| 1 | Leader 写入即返回 | Leader 宕机且 Follower 未同步时丢失 |
| **all（-1）** | ISR 中所有副本都写入才返回 | 最可靠；Kafka 3.0 起生产者默认值 |

**幂等生产者**：`enable.idempotence=true`（3.0 起默认开启）。每个生产者有唯一的 PID，每条消息带单调递增的序列号，Broker 按「PID + 分区 + 序列号」去重，解决重试导致的重复写入。**只保证单会话、单分区内不重复**，生产者重启后 PID 会变。

**Kafka 事务**：跨多个分区的原子写入，配合 `transactional.id`（重启后不变）和消费端 `isolation.level=read_committed`，实现「消费-处理-生产」流程的 Exactly-Once，主要用于 Kafka Streams / Flink 流处理。它**不能**保证「数据库本地事务 + 发消息」的一致，这是它与 RocketMQ 事务消息的本质区别。

**分区策略**：指定分区 > 按 key 哈希 > 无 key 时用粘性分区（一批消息发到同一分区，提高批量效率）。

### 2.5 消费者：位移提交与 Rebalance【核心】

**位移提交**：消费进度保存在内部 Topic `__consumer_offsets` 中。

| 方式 | 问题 |
| --- | --- |
| 自动提交（默认每 5 秒） | 提交后、处理完前宕机 → **丢消息**；处理完、提交前宕机 → **重复消费** |
| 手动提交（处理成功后 commitSync / commitAsync） | 不会丢，但仍可能重复，所以**消费者必须幂等** |

**Rebalance**：重新分配消费者组内分区与消费者的对应关系。

- **触发条件**：消费者加入或离开（包括崩溃）、订阅的 Topic 分区数变化、订阅的 Topic 变化。
- **常见「意外」触发**：心跳超时（`session.timeout.ms`）；单批消息处理太久，超过 `max.poll.interval.ms`（默认 5 分钟）被认为已死亡。
- **影响**：传统的 Eager 协议下整个组停止消费（Stop The World），并可能重复消费。
- **优化**：调小 `max.poll.records` 或加快处理速度；使用 `CooperativeStickyAssignor` 增量重平衡，只移动需要变更的分区；用静态成员 `group.instance.id` 避免重启引起重平衡。Kafka 4.0 起新的消费者重平衡协议（KIP-848）正式可用，分配由服务端完成，不再需要全组停顿。

## 三、RocketMQ 与 RabbitMQ

两者在图谱中是「重点」级别。面试一般问你项目里用的那一个，另一个能说出与 Kafka 的主要差异即可。

### 3.1 RocketMQ 架构【重点】

| 角色 | 作用 |
| --- | --- |
| NameServer | 轻量级注册中心，保存 Topic 与 Broker 的路由信息；各节点互不通信、无状态，Broker 定时向所有 NameServer 注册 |
| Broker | 存储和转发消息，分 Master / Slave |
| Producer / Consumer | 从 NameServer 拿到路由后直连 Broker |
| MessageQueue | 类似 Kafka 的分区，一个 Topic 分布在多个 Broker 的多个队列上 |

**存储结构【重点】**：所有 Topic 的消息都顺序写入同一个 **CommitLog** 文件（每个 1 GB），再异步为每个队列构建 **ConsumeQueue** 索引（存消息在 CommitLog 中的偏移、大小、tag 哈希）。与 Kafka 「每个分区一个文件」不同：Topic 很多时，Kafka 的顺序写会退化为大量文件的随机写，而 RocketMQ 始终是一个文件的顺序写，更适合业务系统「大量 Topic」的场景。另有 IndexFile 支持按 key 和时间查询消息。

**刷盘与复制**：同步刷盘 / 异步刷盘（默认）；同步复制 / 异步复制。核心业务常用「异步刷盘 + 同步复制」，在性能和可靠性之间取得平衡。主从自动切换早期依赖 DLedger（Raft），5.x 提供 Controller 模式。

**消费模式【了解】**：集群消费（默认，一条消息只被组内一个消费者消费）和广播消费（组内每个消费者都消费一次，适合刷新本地缓存）。

**重试与死信【重点】**：消费失败后，消息进入重试队列按阶梯时间重投（1s、5s、10s、30s…2h），默认重试 16 次后进入死信队列 `%DLQ%消费组名`，需要人工处理。

### 3.2 RabbitMQ 模型【重点】

生产者把消息发到 **Exchange**（交换机），交换机按 **Binding** 规则和 **RoutingKey** 把消息路由到 **Queue**，消费者从队列取消息。

| Exchange 类型 | 路由规则 | 场景 |
| --- | --- | --- |
| direct | RoutingKey 完全匹配 | 按类型分发，如日志级别 |
| topic | 通配符匹配：`*` 匹配一个单词，`#` 匹配零个或多个 | 多维度订阅，如 `order.*.paid` |
| fanout | 广播到所有绑定的队列，忽略 RoutingKey | 广播通知 |
| headers | 按消息头属性匹配 | 很少使用 |

**可靠性【重点】**：生产端用 **publisher confirm**（到达交换机的确认）+ **return callback**（路由不到队列时回调）；存储端对交换机、队列、消息都设为**持久化**；消费端用**手动 ack**，处理成功后再确认。

**高可用【了解】**：普通集群只同步元数据，队列数据只在一个节点；镜像队列在多节点保存副本，但已被弃用；3.8 起推荐基于 Raft 的**仲裁队列**（Quorum Queue）。

## 四、消息可靠性

四个问题的答题框架都一样：按「生产 → 存储 → 消费」三个环节逐一分析。记住一个结论：**MQ 只能做到「至少一次」，「恰好一次」要靠消费端幂等来保证**。

### 4.1 如何保证消息不丢失【核心】

| 环节 | 丢失原因 | Kafka | RocketMQ | RabbitMQ |
| --- | --- | --- | --- | --- |
| 生产 | 网络异常、Broker 未确认 | `acks=all` + `retries` + 回调中处理失败 | 同步发送并检查 SendStatus，失败重试 | publisher confirm + return callback |
| 存储 | Broker 宕机、未刷盘、未复制 | `replication.factor≥3` + `min.insync.replicas≥2` + 禁止 unclean 选举 | 同步刷盘或同步复制 | 交换机 / 队列 / 消息持久化 + 仲裁队列 |
| 消费 | 先提交位移再处理，处理中宕机 | 关闭自动提交，处理成功后手动提交 | 处理成功后才返回 CONSUME\_SUCCESS | 手动 ack |

**兜底**：生产端发送失败且重试用尽时，把消息记入数据库（本地消息表），由定时任务补发；关键业务定期对账。

### 4.2 重复消费与幂等【核心】

**重复的来源**：生产者重试（Broker 已存但确认丢了）、消费者处理完但位移未提交就宕机或 Rebalance、消费超时触发重投。这些都无法完全避免。

**幂等方案**（核心是给每条消息一个业务唯一键，如订单号、流水号）：

| 方案 | 做法 | 适用 |
| --- | --- | --- |
| 数据库唯一索引 | 插入时主键 / 唯一键冲突即说明已处理 | 新增类操作，最可靠 |
| 去重表 | 在同一个本地事务中写业务数据和「已消费记录」 | 通用 |
| 状态机 / 乐观锁 | `UPDATE ... SET status = '已支付' WHERE id = ? AND status = '待支付'`，影响行数为 0 就是重复 | 状态流转类业务 |
| Redis SETNX | 处理前 `SET msgId 1 NX EX 86400` | 高并发、能容忍极小概率不一致的场景 |

注意 Redis 方案的坑：先 SETNX 成功、再处理业务时崩溃，消息就「被标记但未处理」。可以记录「处理中 / 已完成」两种状态，或以数据库唯一索引为最终保障。

### 4.3 顺序消息【核心】

**全局有序**需要只用一个分区、一个消费者，吞吐极低，很少使用。实际需要的是**局部有序**：同一个订单的「创建 → 支付 → 发货」有序。

- **生产端**：用订单 ID 作为 key（Kafka）或 `MessageQueueSelector` 按订单 ID 取模（RocketMQ），让同一订单的消息进入同一个分区 / 队列。
- **存储端**：分区内天然有序。Kafka 开启幂等后重试也不会乱序（`max.in.flight.requests.per.connection` ≤ 5）。
- **消费端**：一个分区只由一个线程顺序处理。如果消费者用线程池并发处理，就要按 key 哈希分发到不同的内存队列，每个队列由一个线程处理。RocketMQ 用 `MessageListenerOrderly`，它会锁定队列。
- **代价**：顺序消费时一条消息失败会阻塞同队列后续消息；热点 key 会导致分区倾斜。业务上也可以用「状态机 + 版本号」容忍乱序，而不强求 MQ 有序。

### 4.4 消息积压【核心】

**先定位原因**：是生产量突增（促销、上游故障恢复后的补发），还是消费变慢（下游接口或数据库变慢、消费者报错不断重试）？后者更常见，要先修复消费端问题。

**处理方案**：

1. **扩容消费者**：在分区 / 队列数以内增加消费者实例。超过分区数时无效。
2. **提高单个消费者能力**：批量拉取、批量写库、消费者内部用线程池并发处理（顺序消息除外）、优化下游慢查询。
3. **临时扩分区转储**：消费者数量受限于分区数时，写一个只做转发的临时消费者，把积压消息快速转到一个分区数更多的新 Topic，再用大量消费者并行处理。
4. **降级**：非核心消息可暂时跳过或先落盘，低峰期再补处理。

**预防**：监控消费延迟（Kafka 的 consumer lag）并设告警；上线前压测消费能力；分区数预留余量。另外要关注消息保留时间，积压太久可能被自动清理。

## 五、事务消息、延时消息与死信队列

这一章解决的是「业务数据和消息如何一致」以及「消息处理不了怎么办」。

### 5.1 为什么需要事务消息【核心】

下单后要「写订单表」和「发消息通知下游」，两者无法在一个本地事务中完成：

- 先提交事务再发消息：发送失败，下游永远不知道。
- 在事务内发消息：消息发出后事务回滚，下游处理了一个不存在的订单；且发消息的网络耗时拉长了事务。

两种主流方案：RocketMQ 事务消息，或本地消息表。

### 5.2 RocketMQ 事务消息【核心】

1. 生产者发送**半消息**（Half Message），Broker 存储但对消费者不可见（存在内部 Topic 中）。
2. 半消息发送成功后，生产者执行**本地事务**（写订单表）。
3. 根据本地事务结果向 Broker 提交 **Commit**（消息变为可见，投递给消费者）或 **Rollback**（删除半消息）。
4. 如果 Broker 迟迟收不到第 3 步的结果（生产者宕机、网络故障），会主动**回查**生产者：调用 `checkLocalTransaction()`，生产者去数据库查订单是否存在来决定 Commit 还是 Rollback。默认最多回查 15 次。

&#91;embedded content: RocketMQ 事务消息 · 正常流程与回查\]

虚线是异常分支：只要本地事务结果能从数据库查到，生产者宕机也不会导致消息与业务不一致。

这样保证了「本地事务成功 ⇔ 消息最终被投递」。注意它只保证生产端的一致，**消费端仍然需要重试 + 幂等**，消费失败不会回滚生产端的事务。

### 5.3 本地消息表【核心】

不依赖 MQ 的特性，任何 MQ 都能用：

1. 在**同一个本地事务**中写业务表和消息表（消息状态为「待发送」）。
2. 事务提交后尝试发送消息，成功则把状态改为「已发送」。
3. 定时任务扫描超时未发送的消息并重试，超过次数告警人工处理。

优点是简单可靠、与 MQ 无关；缺点是消息表和业务表耦合在一个库里，高并发下消息表会成为压力点。也可以用 Canal 订阅消息表的 binlog 来发送（Outbox 模式 + CDC），省掉定时扫描。

### 5.4 延时消息【重点】

**典型场景**：订单下单后 30 分钟未支付自动取消、会议开始前提醒。

| 实现 | 做法 | 特点 |
| --- | --- | --- |
| RocketMQ 4.x | 固定 18 个延时等级（1s 5s 10s 30s 1m … 2h） | 不支持任意时间 |
| RocketMQ 5.x | 基于时间轮的任意时间定时消息 | 推荐 |
| RabbitMQ | 消息 TTL + 死信队列；或 `rabbitmq_delayed_message_exchange` 插件 | TTL 方案只检查队首消息，不同 TTL 混在一个队列会阻塞 |
| Redis | ZSet，score 为到期时间戳，定时轮询；或 Redisson `RDelayedQueue` | 轻量，可靠性靠 Redis 持久化 |
| 定时任务扫表 | 每分钟扫描超时未支付订单 | 简单，数据量大时压库且有延迟 |

实际工程中常用「延时消息 + 定时任务兜底扫描」的组合。取消订单时要带上状态条件（`WHERE status = '待支付'`），避免与刚刚完成的支付冲突。

### 5.5 重试与死信队列【重点】

消息多次重试仍失败，就进入死信队列（DLQ），避免「毒药消息」反复重试拖垮消费者。

- **RocketMQ**：默认重试 16 次后进入 `%DLQ%消费组`。
- **RabbitMQ**：消息被拒绝且不重新入队、TTL 过期、队列满时，转到队列配置的死信交换机。
- **Kafka**：没有内置 DLQ，由应用实现（Spring Kafka 的 `DeadLetterPublishingRecoverer` 发到 `xxx.DLT` Topic）。

死信消息需要监控告警、定位原因、修复后重新投递。

### 5.6 最大努力通知与对账【重点】

用于与外部系统交互（如支付结果通知商户）：按阶梯间隔（如 15s、1m、5m…30m）重复通知，直到对方返回成功或达到次数上限；同时提供查询接口让对方主动来查，并定期**对账**发现差异、补偿修正。
