## 一、分布式理论

理论部分要解决的是一个问题：网络一定会出问题，这时你选择「数据对」还是「服务可用」。

### 1.1 CAP【重点】

- **C（一致性）**：所有节点在同一时刻读到的数据相同（线性一致）。
- **A（可用性）**：每个请求都能在合理时间内得到非错误的响应。
- **P（分区容错）**：节点间网络断开时，系统仍能继续运行。

分布式系统中网络分区无法避免，**P 必须保证**，所以实际是在发生分区时选择 CP 还是 AP：

| 选择 | 发生分区时的行为 | 代表 |
| --- | --- | --- |
| CP | 拒绝请求或等待，保证数据不出错 | ZooKeeper（选举期间不可用）、etcd、Nacos 持久实例 |
| AP | 继续响应，可能返回旧数据，之后再同步 | Eureka、Nacos 临时实例（默认）、Redis Cluster |

**注册中心为什么更适合 AP**：服务列表短暂不一致只会导致少量请求失败（可以重试），而注册中心不可用会让所有服务无法发现彼此。而分布式锁、选主等场景必须保证正确，应选 CP。

### 1.2 BASE【重点】

BASE 是对 AP 的延伸，是互联网系统的实际做法：

- **BA（基本可用）**：出故障时允许损失部分功能或性能，如降级、响应变慢。
- **S（软状态）**：允许存在中间状态，如订单「支付中」。
- **E（最终一致）**：经过一段时间后数据达到一致。前面所有文档中的缓存双写、主从复制、MQ 异步处理，都是最终一致。

### 1.3 一致性协议：Raft 与 ZAB【重点】

**Raft**（etcd、Nacos CP、Kafka KRaft、Redis 哨兵选 leader 都借鉴了它）把问题拆成三部分：

1. **Leader 选举**：节点分 Leader、Follower、Candidate。Follower 在随机的选举超时时间内收不到 Leader 心跳，就把任期（term）加 1、成为 Candidate 并拉票，得到**超过半数**的票就成为 Leader。随机超时是为了避免同时发起选举导致分票。
2. **日志复制**：写请求只发给 Leader，Leader 把日志复制给 Follower，**超过半数**节点写入后即为已提交，再应用到状态机。
3. **安全性**：只有日志至少和大多数节点一样新的 Candidate 才能当选，保证已提交的日志不丢失。

**为什么集群节点数用奇数**：「超过半数」规则下，3 节点和 4 节点都只能容忍 1 个节点故障，多一台反而增加成本。半数机制也天然防止了脑裂：网络分成两半时只有一边能凑够半数。

**ZAB**（ZooKeeper 的协议）思想与 Raft 类似，分为**崩溃恢复**（选出日志最新的 Leader 并同步数据）和**消息广播**（类似两阶段提交：发 Proposal，超过半数 ACK 后发 Commit）两个阶段。Paxos 是更早、更通用的理论算法，但难以理解和工程实现，Raft 就是为易理解而设计的。

### 1.4 ZooKeeper【重点】

- **数据模型**：树形的 ZNode，类型有持久、临时（会话结束自动删除）、顺序（创建时自动加递增编号）以及它们的组合。
- **会话与临时节点**：客户端与任意节点建立会话并定期发心跳，会话超时（`sessionTimeout`）后临时节点被删除。分布式锁、服务注册都用临时节点，进程挂掉能自动清理。
- **Watch**：监听节点变化，触发后失效（一次性），需要重新注册；3.6 起支持持久递归 Watch。Watch 只通知「变了」，不携带变更后的数据，收到通知后要重新读取。
- **Leader 选举【重点】**：投票时比较 `(zxid, myid)`，zxid 越大说明数据越新，优先当选；集群按 `server.id` 配置，选举需要**过半数**票。Observer 不参与投票，只同步数据，用于提升读能力而不降低写性能。
- **为什么说 ZK 是 CP【重点】**：Leader 选举期间（会话超时 + 选举，通常几十秒）集群**不可写**。这也解释了为什么注册中心更适合 Nacos / Eureka 这类 AP 实现，而分布式锁、选主才用 ZK。
- **与 etcd 的取舍【了解】**：etcd 用 Raft + 租约（lease）+ 全局递增 revision，支持前缀范围和 Watch 增量事件；K8s 用 etcd 存集群状态。ZK 的 ZAB 只能全量/顺序节点遍历，运维更重；新系统优先 etcd，Java 生态做协调仍常见 ZK。

**典型应用**：分布式锁（临时顺序节点 + 监听前一个节点）、选主、配置中心、服务注册（Dubbo 早期、Kafka 早期）。

### 1.5 一致性模型与读己之写【重点】

CAP 讲的是分区时选 C 还是 A，一致性模型讲的是**在没有分区时，读操作允许看到什么**。面试里说「强一致」是口语，追问下去必须落到下面某一层。

| 模型 | 保证 | 关键限制 |
| --- | --- | --- |
| 强一致（strict serializability） | 事务级：所有事务串行化，且遵守真实时间先后 | 最强，单机数据库靠 2PL / MVCC + 串行化实现；分布式代价极高 |
| 线性一致（linearizability） | 单个对象：每个操作看起来在真实时间轴上原子生效，读能读到之前已完成的写 | ZK / etcd 的写、Redis 单实例可近似满足；不涉及多对象事务 |
| 顺序一致（sequential consistency） | 所有进程看到**相同**的操作顺序，但该顺序不必与真实时间一致 | 允许把并发操作任意排序，只要全局统一 |
| 因果一致（causal consistency） | 只保证有因果关系的操作按序，并发操作可以各节点顺序不同 | 比线性一致弱，但比最终一致强；实现靠版本 / 向量时钟 |
| 最终一致（eventual consistency） | 停止写入后，经过一段时间所有副本收敛到同一值 | 不保证中间读到的内容，几乎所有 AP 系统与缓存同步都属于这一层 |

**层次关系**：线性一致 > 顺序一致 > 因果一致 > 最终一致；强一致（可串行化 + 实时顺序）是事务级的最强模型，比线性一致还多一条「多对象事务」。面试被问「你们系统是强一致吗」，正确回答是先说业务对象，再说落到哪一层。

**因果关系（happens-before）**来自三条规则：同进程内的先后、消息发送先于接收、以及传递闭包。两条操作之间没有因果路径就是**并发**，并发操作不要求顺序，这也是「最终一致」能成立的前提。

**会话级一致性**：全局模型太贵，工程上常用「对当前用户保证某些性质」：

| 性质 | 含义 | 典型场景 | 实现 |
| --- | --- | --- | --- |
| 读己之写（read-your-writes） | 用户提交后，自己后续的读一定能看到这次写 | 修改资料后立刻刷新页面 | 写后短时间读主、按用户路由、按 GTID 位点等待 |
| 单调读（monotonic reads） | 同一个用户不会读到「越读越旧」的数据 | 列表刷新、分页 | 会话粘滞、按版本号只接受更高版本 |
| 单调写（monotonic writes） | 同一用户的多次写按提交顺序生效 | 连续修改收货地址 | 按用户串行化、版本号递增 |
| 读后写（writes-follow-reads） | 基于读到的版本做写，写必须基于不低于该版本的状态 | 乐观锁更新 | 读时带版本，写时校验版本 |

**主从延迟下实现读己之写的四种手段**：

1. **写后读主**：提交后 N 秒内（或本会话内）强制走主库，最简单，但窗口内仍可能读旧；
2. **按用户路由**：写主库的用户在短时间内固定读主库，避免随机落到延迟不同的从库；
3. **位点等待**：写时记录 GTID / binlog 位点，读前在从库执行 `WAIT_FOR_EXECUTED_GTID_SET`，追平再读；
4. **版本校验**：写成功返回新版本号，读时比较版本，低于期望值就重试或回源主库。

**业务落地对照**：

| 业务 | 需要的一致性 | 落地手段 |
| --- | --- | --- |
| 账户余额、库存扣减 | 线性一致 / 可串行化 | 单库事务 + 行锁、Redis 原子脚本 + 幂等落库、CP 协调服务 |
| 订单状态、个人资料 | 读己之写 + 单调读 | 写后读主、用户维度会话粘滞、版本号只进不退 |
| 配置、元数据、权限 | 单调读（不能回退到旧版本） | 版本号比较、配置中心推送、客户端只接受更高版本 |
| Feed、点赞数、推荐 | 因果一致 / 最终一致 | MQ 异步、读修复、业务上容忍短暂不一致 |
| 跨服务查询（订单 + 用户） | 不要求跨对象一致 | 分别保证单对象读己之写，前端组合展示 |

**一句话结论**：一致性不是「要么强要么弱」的开关，而是按对象和用户会话选择合适的一层，并在 UI 上把残余的不一致表达出来（如「支付结果确认中」）。

### 1.6 逻辑时钟与向量时钟【了解】

**物理时钟为什么不能定序**：NTP 校时可能让时间**回拨**；不同机器的晶振有漂移（drift），即使同步过也存在毫秒级偏差（skew）；跨机房、虚拟机迁移、闰秒都会破坏单调性。用 `System.currentTimeMillis()` 判断「谁先发生」在分布式里是不可靠的，它只能做超时和近似排序。

**Lamport 逻辑时钟**：每个进程维护一个整数 `L`，规则三条：

1. 本地发生事件，`L = L + 1`；
2. 发送消息时，把当前 `L` 附在消息上；
3. 接收消息时，`L = max(L, 消息中的 L) + 1`。

性质：若 `a → b`（a 因果先于 b），则 `L(a) < L(b)`；**反之不成立**——`L` 小不代表一定先发生，两个并发事件也可能得到不同数值。所以 Lamport 时钟只能给出**偏序的一个线性化**，无法判断两个事件是否并发。

**向量时钟（Vector Clock）**：每个进程维护长度为 N 的数组（N 为副本/进程数），规则与 Lamport 类似，但按分量更新：

1. 本地事件：自己那一维加 1；
2. 发送消息：带上整个向量；
3. 接收消息：逐分量取 `max`，再把自己的分量加 1。

比较规则：

| 关系 | 判定 |
| --- | --- |
| `V(a) < V(b)`（a 先于 b） | 所有分量都 ≤，且至少一个分量 < |
| `V(a) > V(b)`（a 后于 b） | 所有分量都 ≥，且至少一个分量 > |
| **并发** | 有的分量大、有的分量小 |
| 相等 | 同一个状态 |

**用途**：

- **冲突检测**：多副本各自写入后，用向量时钟判断是「有先后」还是「并发冲突」。并发时不能简单覆盖，需要应用层合并（如购物车取并集），否则用 Last Write Wins 会**丢更新**（Dynamo、Riak、Cassandra 都提供这一类选项）。
- **幂等与去重**：消息带 `(消息 ID, 版本向量)`，消费者按版本判断是否重复或过期，避免重复处理。
- **因果排序**：事件溯源、审计日志里还原因果关系。

**局限**：向量维度随节点数增长，动态扩缩容时元数据膨胀；只给偏序，不能当全局全序用；跨系统边界（如 HTTP 网关）通常退化为单版本号。

**与物理时钟的关系**：实际系统常用**混合逻辑时钟（HLC）**：用物理时间做主序，用逻辑计数处理同一毫秒和时钟回拨，CockroachDB 等采用。雪花 ID 也依赖时间戳，但它解决的是**唯一性**而不是因果关系——时钟回拨会破坏趋势递增，不能拿 ID 大小当事件顺序。

### 1.7 故障模型与拜占庭容错【了解】

设计分布式算法前必须先声明「假设节点会怎么坏」：

| 故障模型 | 表现 | 典型假设 |
| --- | --- | --- |
| 崩溃停止（crash-stop） | 节点一旦坏就永久不再响应 | Raft、ZAB、2PC 的默认假设 |
| 崩溃恢复（crash-recovery） | 节点会坏，但重启后能恢复，可能带着旧状态 | 需要考虑日志重放、幂等重做 |
| 遗漏（omission） | 消息可能丢失、延迟，但内容不会错 | 网络不可靠但节点诚实 |
| 时序（timing） | 消息延迟有上界，或最终有上界（部分同步） | 超时才能有意义 |
| 拜占庭（byzantine） | 节点可能返回错误结果、伪造消息、恶意串通 | PBFT、区块链 |

**网络分区**是独立于节点故障的另一维度：节点都活着但互相不可达，表现为超时，无法与「慢」区分。这也是**故障检测不可能精确**的根本原因。

**为什么常规分布式系统只按崩溃失败设计**：

- 硬件与软件故障通常表现为停止、重启或超时，不会主动伪造数据；机房内的节点是可信的；
- 拜占庭容错需要**3f+1 个副本**才能容忍 f 个作恶节点（崩溃容错只需 2f+1），消息复杂度从 O(n) 升到 O(n²)，视图切换与密钥管理复杂；
- 在异步网络下还有 FLP 不可能性：**无法同时保证安全性和活性**，工程上只能靠「部分同步 + 超时」做妥协。

**容错阈值对照**：

| 故障类型 | 最少副本 | 可容忍故障数 | 代表算法 |
| --- | --- | --- | --- |
| 崩溃失败 | 3 | 1 | Raft、ZAB、Multi-Paxos |
| 拜占庭失败 | 4 | 1 | PBFT |
| 拜占庭失败（一般式） | 3f+1 | f | PBFT、HotStuff |

**什么时候才需要拜占庭容错**：参与方互不信任、节点可能被攻破（公链、跨组织联盟链、开放金融网络）。普通微服务、注册中心、分布式锁都按崩溃失败设计，引入 BFT 只会带来数量级的性能损失。

### 1.8 Quorum 与 NWR 模型【重点】

把数据复制到 N 个副本，写成功需要 W 个副本确认，读需要读 R 个副本，就得到经典的 NWR 模型。

**W + R > N 为什么能读到最新写**：任意一个写集合与任意一个读集合，元素个数之和大于 N，根据抽屉原理**必然至少有一个副本同时属于两者**。这个交集副本上保存着最近一次成功写入的值，读时取各副本中版本最新的即可。

| N | W | R | 效果 |
| --- | --- | --- | --- |
| 3 | 2 | 2 | 2+2>3，强于多数派读写，兼顾读写的常用配置 |
| 3 | 3 | 1 | 读最快，写要全部副本成功，任一节点宕机写不可用 |
| 3 | 1 | 3 | 写最快，读要读全量，读放大严重 |
| 3 | 1 | 1 | 1+1<3，不保证读到最新写，最终一致 |
| 5 | 3 | 3 | 多数派，容忍 2 个节点故障 |

**多数派（majority）就是特殊情况**：`W = R = floor(N/2) + 1`，此时任意两个多数派必然相交，这也是 Raft 提交与选举的数学基础。

**四个容易答错的边界**：

1. **W+R>N 不等于线性一致**：它只保证「能读到某次已完成的写」，不保证实时顺序，也不解决并发写的冲突；并发写需要版本号或向量时钟，LWW 可能丢更新。
2. **节点宕机会破坏可用性**：严格 quorum 下 W 个副本不可用就写失败。Dynamo 用 **sloppy quorum + hinted handoff**：先写到临时节点并记录线索，节点恢复后补传，牺牲严格性换可用性。
3. **读到的可能是旧副本**：需要**读修复（read repair）**——读时比较各副本的版本，把新版本回写旧副本；后台再用反熵（anti-entropy）做全量/增量修复。
4. **与 Raft 的多数派不是一回事**：Raft 是 leader 串行提交 + 多数派确认，能给出线性一致；NWR 是无主（leaderless）多副本，只有概率意义上的正确性。Kafka 的 `acks=all` + `min.insync.replicas` 更像「带 leader 的写 quorum」，不是纯 NWR。

**工程使用**：Cassandra、DynamoDB、Riak 允许按查询指定一致性级别（如 `QUORUM`、`ONE`、`ALL`）；同一系统里「余额查询用 QUORUM、日志查询用 ONE」是很常见的取舍。

### 1.9 Gossip 协议【了解】

Gossip（也称 epidemic protocol）让每个节点周期性地随机选几个邻居交换状态，像谣言一样扩散，不需要中心节点。

**传播机制**：

| 方式 | 做法 | 特点 |
| --- | --- | --- |
| Push | 主动把自己的更新推给邻居 | 快，但可能推给已知节点 |
| Pull | 向邻居请求最新状态 | 能补齐漏掉的数据，成本高 |
| Push-Pull | 双向交换差异 | 收敛最快，常用于反熵 |
| Rumor mongering | 只传播「新变化」，带版本号，热度衰减后停止 | 减少冗余消息 |

**关键概念**：

- **收敛性**：每轮把状态传给 `fanout` 个随机节点，信息覆盖全集群的轮数约为 `O(log N)`；节点越多收敛越慢。
- **反熵（anti-entropy）**：周期性全量或摘要（Merkle 树 / digest）比对，修复长期未传播到的差异，解决「谣言停了但数据还没到」的问题。
- **故障检测**：节点定期发心跳，用「多久没听到某节点的 gossip」判断其可疑/下线，Consul 的 memberlist 就是这样做的。

**性质**：完全去中心、可扩展、天然容错（少数节点失联不影响整体）、最终一致；代价是消息冗余、收敛时间不确定、**不保证顺序**，也无法提供线性一致。

**典型使用方**：

| 系统 | 用途 |
| --- | --- |
| Consul / Serf（memberlist 库） | 集群成员列表、健康状态、跨机房拓扑 |
| Cassandra | 节点上下线、token 环、schema 版本等集群元数据 |
| Redis Cluster | 槽位归属、节点状态（gossip 总线） |
| 区块链（比特币、以太坊） | 区块与交易的广播扩散 |
| Akka Cluster | 成员状态与集群事件 |

**不该用在哪**：需要全序或强一致的场景（资金账务、库存扣减、分布式锁）。Gossip 适合「元数据、成员、配置、状态广播」，业务数据的一致要靠共识或事务。

### 1.10 Paxos 与 Multi-Paxos【重点】

Paxos 解决的是「多个节点如何对**一个值**达成一致」，是所有共识算法的理论源头。

**四种角色**：Client（提出请求）、Proposer（发起提案）、Acceptor（投票与保存）、Learner（学习最终结果，实践中常与 Proposer 合并）。

**Basic Paxos 两阶段**：

1. **Prepare(n)**：Proposer 选一个单调递增的提案号 n，向多数派 Acceptor 发送 Prepare；Acceptor 若 `n` 大于自己记录的 `promised`，就回复 Promise，并附上自己已接受过的最大提案号与值。
2. **Accept(n, v)**：Proposer 收到多数 Promise 后，若有 Acceptor 返回过值，**必须采用其中提案号最大的那个值**，否则用自己的值；随后发送 Accept(n, v)，多数派 Acceptor 接受后该值即被**选定**（chosen），再通知 Learner。

**安全性的核心**：提案号单调递增 + 「一旦某个值被选定，后续更高编号的提案只能沿用该值」+ 多数派投票，三者共同保证不会选出两个不同的值。Proposer 失败可以换更大的 n 重试；Acceptor 失败只要多数派还在，流程就能继续；消息丢失靠重试，但**重试要换新提案号**。

**Multi-Paxos 的优化**：每轮都做 Prepare 太浪费，于是选出一个**稳定的 Leader（distinguished proposer）**，只在选主或 Leader 变更时做一次 Phase 1，之后的请求只走 Phase 2（Accept），并可以批量、流水线化——这正是「日志复制」的雏形。

**Paxos 的工程留白**：Basic Paxos 只解决了单值共识，实际系统还需要 Leader 选举、日志存储与回放、成员变更、快照、客户端重试去重。Paxos 没有规定这些，各家实现差异很大（Chubby 用 Multi-Paxos，Cassandra 用 Paxos 做轻量事务）。

**为什么工程上更常听到 Raft**：Raft 把共识拆成「选举 / 日志复制 / 成员变更」三块并给出明确规范，任何人都能实现出一致行为，论文可读性高；Paxos 是更本质的数学模型，但落地时要补大量细节。ZAB 与 Raft 同属「主备 + 原子广播」，写都要经过 Leader、都要过半确认；区别在 ZAB 用 epoch + zxid 做恢复，恢复阶段会同步全量状态，而 Raft 靠日志回放。

| 维度 | Basic Paxos | Multi-Paxos | Raft | ZAB |
| --- | --- | --- | --- | --- |
| 写路径 | 每次两阶段 | Leader 常态只走 Phase 2 | Leader + 日志复制 | Leader + 提案广播 |
| 选举 | 无 | 需自行实现 | 任期 + 随机超时 + 过半投票 | 比较 `(zxid, myid)` |
| 恢复 | 重新提案 | 依赖 Leader 恢复 | 日志回放 | 崩溃恢复同步 |
| 工程复杂度 | 理论原型 | 高（留白多） | 中，规范完整 | 中 |

**面试落点**：能讲清「Prepare 为什么要带已接受的值」「为什么提案号必须单调」，再补一句「生产上直接用 Raft / ZAB 的实现（etcd、ZK），不要自己写 Paxos」。

## 二、微服务架构与组件

微服务把单体按业务能力拆成可以独立开发、部署和扩展的小服务。它解决的是团队和业务规模变大后的协作问题，代价是引入了分布式系统的全部复杂度（组件全景见下图）。

&#91;embedded content: 微服务组件全景 · Spring Cloud Alibaba\]

每个服务只访问自己的数据库；订单服务同步调用库存服务扣减库存，再通过 MQ 通知积分、物流等下游。

### 2.1 单体与微服务【核心】

| 维度 | 单体 | 微服务 |
| --- | --- | --- |
| 开发部署 | 简单，一次打包部署 | 各服务独立发布，需要 CI/CD 与容器化支撑 |
| 扩展 | 只能整体扩容 | 按服务单独扩容热点服务 |
| 故障隔离 | 一处内存泄漏拖垮整个应用 | 故障限制在单个服务（需要熔断隔离配合） |
| 技术栈 | 统一 | 可以异构 |
| 一致性 | 本地事务即可 | 需要分布式事务或最终一致 |
| 排障 | 一个进程的日志 | 跨服务调用链，需要链路追踪 |

小团队、业务初期用单体（或模块化单体）往往更合适。

**拆分原则【核心】**：按业务边界拆（DDD 的限界上下文），而不是按技术分层拆；高内聚、低耦合，一个需求尽量只改一个服务；**每个服务拥有自己的数据库**，禁止跨服务直接访问对方的表；粒度与团队规模匹配，避免拆得太细导致大量跨服务调用和分布式事务。

### 2.2 注册中心与配置中心：Nacos【重点】

**服务注册发现**：服务启动时注册地址，定时发送心跳；调用方拉取并**缓存**服务列表，列表变化时由服务端推送。即使注册中心全部宕机，已有的调用仍能靠本地缓存继续。

- **临时实例（默认）**：靠客户端心跳保活，超时自动剔除，用 Distro 协议（AP）。
- **持久实例**：由服务端主动探测健康状态，不健康也不删除，用 Raft（CP）。
- Nacos 2.x 把客户端与服务端的通信从 HTTP 短连接 + 心跳改为 gRPC 长连接，性能和推送及时性大幅提升。

**配置中心**：用「命名空间（环境）+ Group（项目）+ DataId（配置文件）」三级隔离。动态刷新靠长轮询（1.x）或 gRPC 推送（2.x），客户端用 `@RefreshScope` 或 `@ConfigurationProperties` 让 Bean 拿到新值。

**对比【重点】**：Eureka 只做注册、AP、已停止迭代；ZooKeeper 是 CP、选举期间不可用；Nacos 同时支持 AP / CP，并兼作配置中心，是国内主流选择。

### 2.3 API 网关：Spring Cloud Gateway【重点】

网关是所有外部请求的统一入口，负责**路由、鉴权、限流、日志、灰度**等通用能力，让业务服务不必重复实现。

- **三大概念**：Route（路由，目标服务）、Predicate（断言，匹配条件，如 `Path=/order/**`）、Filter（过滤器，转发前后的处理）。
- **全局过滤器**（GlobalFilter）作用于所有路由，常用于统一鉴权：解析 Token，把用户 ID 放入请求头传给下游。
- **基于 WebFlux + Netty 的非阻塞模型**：少量线程处理大量连接，所以**过滤器中绝对不能有阻塞操作**（同步查库、同步 HTTP 调用），否则整个网关吞吐会崩溃。
- **与 Nginx 的分工**：Nginx 作为流量入口做负载均衡、SSL 终止、静态资源；Gateway 在其后做业务级路由和鉴权。

**过滤器执行顺序【重点】**：全局过滤器（`GlobalFilter`）和路由自带的 `GatewayFilter` 会被合并，按 `getOrder()` 从小到大排序；请求进入时**正序**执行 `pre` 逻辑，响应返回时**逆序**执行 `post` 逻辑（像栈一样）。典型 order 值：`RemoveCachedBodyFilter`、`NettyWriteResponseFilter` 等内置过滤器分布在负数到正数区间，自定义鉴权一般放在 `-100` 到 `0` 之间，确保早于转发、晚于读请求体。常用内置过滤器：`StripPrefix`（去掉路径前缀）、`AddRequestHeader`、`Retry`、`CircuitBreaker`、`RequestRateLimiter`。

**网关限流【重点】**：`RequestRateLimiter` 基于 Redis + Lua 实现分布式令牌桶，`redis-rate-limiter.replenishRate` 是每秒补充令牌数、`burstCapacity` 是桶容量；`KeyResolver` 决定限流维度——按用户 ID、按 IP、按接口路径。超限返回 429，需要配合前端或调用方的重试策略。

**灰度与动态路由【了解】**：路由配置放在 Nacos 并通过监听器刷新 `RouteDefinitionRepository`，无需重启；灰度可按请求头、用户 ID 或权重分流。全链路灰度还要求标签沿 Feign / Dubbo / MQ 一路透传，否则只在网关生效。

**与 Zuul 的对比【了解】**：Zuul 1 是同步阻塞模型，每个请求占用一个线程，高并发下线程数成为瓶颈；Gateway 基于 WebFlux + Reactor Netty，用事件循环处理连接，少量线程扛住大量请求。Zuul 2 虽然改成非阻塞，但社区生态和维护已弱于 Gateway。

### 2.4 服务调用：OpenFeign 与 RPC【重点】

**OpenFeign**：声明式 HTTP 客户端。`@FeignClient` 接口在启动时被注册为 FactoryBean，用 **JDK 动态代理**生成实现，调用时把方法上的注解解析成 HTTP 请求，由 LoadBalancer 从注册中心选一个实例发送。实践要点：配置连接和读取超时；用 `RequestInterceptor` 透传 Token、TraceId；把默认的 `HttpURLConnection` 替换为带连接池的 OkHttp / Apache HttpClient。

**RPC 调用流程【核心】**：客户端调用本地代理 → 序列化请求 → 从注册中心获取地址并负载均衡 → 网络传输（Netty）→ 服务端反序列化 → 反射调用实现类 → 序列化结果返回。

| 维度 | Feign（HTTP + JSON） | Dubbo | gRPC |
| --- | --- | --- | --- |
| 协议 | HTTP/1.1 | 自定义 TCP 协议；Dubbo 3 的 Triple 兼容 gRPC | HTTP/2，支持双向流 |
| 序列化 | JSON，可读性好、体积大 | Hessian2 等二进制 | Protobuf，体积小、跨语言 |
| 性能 | 一般 | 高 | 高 |
| 适用 | Spring Cloud 体系、对外接口 | Java 内部高性能调用，治理功能丰富 | 多语言、云原生 |

**Dubbo 集群容错【重点】**：Failover（失败自动重试其他服务器，默认，适合读）、Failfast（快速失败，适合非幂等写）、Failsafe（忽略异常，适合日志）、Failback（后台定时重发）、Forking（并行调用多个，一个成功即返回）。

**Dubbo SPI 与 Java SPI【重点】**：Java SPI 一次加载并实例化所有实现，不能按名称获取；Dubbo SPI 用「key=实现类」配置，按需加载、支持 IOC / AOP 和自适应扩展。

**服务暴露与引用【重点】**：这是 Dubbo 面试最容易被追问的部分，分成两条链路。

- **暴露（Provider 启动时）**：`ServiceConfig.export()` → 先做**本地暴露**（InjvmProtocol，同一 JVM 内部直接调用，避免自调走网络）→ 再做**远程暴露**：把实现类包装成 Invoker → `Protocol.export()` 启动 Netty Server 监听端口 → 最后把 URL（含协议、地址、方法、版本）注册到注册中心。
- **引用（Consumer 启动时）**：`ReferenceConfig.get()` → 创建代理 → 从注册中心**订阅**并收到提供者列表 → 封装成 Directory → Cluster 包装（叠加容错策略）→ Router 路由过滤 → LoadBalance 选一个 Invoker → `Protocol.refer()` 建立长连接 → 调用时走代理发起远程调用。

**Dubbo 负载均衡策略【重点】**：

| 策略 | 做法 | 适用 |
| --- | --- | --- |
| Random（默认） | 按权重随机 | 提供者性能接近时最均匀 |
| RoundRobin | 按权重轮询 | 请求耗时稳定；慢提供者会持续积压 |
| LeastActive | 选当前活跃调用数最少的，再按权重随机 | 各实例性能差异大 |
| ConsistentHash | 同参数落到同一实例，默认 160 个虚拟节点 | 有本地缓存的服务 |
| ShortestResponse | 选预估响应时间最短的 | 对延迟敏感、实例性能不均 |

**序列化协议【重点】**：Hessian2 是默认，兼容性好、性能中等；Protobuf 体积最小、跨语言，适合 gRPC / 多语言；Fastjson2、Kryo 更偏性能但兼容性要评估。选型看三点：是否跨语言、对体积和性能的要求、版本升级时字段增删的兼容性（尽量用兼容性好的序列化，并保留默认值）。

**Dubbo 3 的 Triple 与应用级服务发现【了解】**：Triple 基于 HTTP/2，兼容 gRPC，支持 unary 和流式（server/client/bidi stream），能穿过网关和 Service Mesh。应用级服务发现把注册粒度从「接口」改为「应用」，注册中心的数据量从「接口数 × 实例数」降为「应用数 × 实例数」，大规模集群下显著减轻注册中心压力；消费者再通过元数据中心拿到接口到应用的映射。

**线程模型【重点】**：IO 线程（Netty EventLoop）只负责读写和编解码，业务逻辑派发到业务线程池。`Dispatcher` 有四种：`all`（默认，请求、响应、事件都派发）、`direct`（不派发，全在 IO 线程，适合极短逻辑）、`message`（只派发请求和响应）、`execution`（只派发请求）。业务线程池打满时会出现 `RejectedExecutionException`，要考虑线程数与拒绝策略，别让慢业务反压 IO 线程。

## 三、服务治理：限流、熔断、降级

治理的目标是防止**雪崩**：一个下游服务变慢，调用方的线程都卡在等待上，线程池耗尽后调用方也不可用，故障沿调用链向上蔓延。防护手段是：超时、限流、熔断、降级、隔离。

### 3.1 限流算法【核心】

| 算法 | 做法 | 优缺点 |
| --- | --- | --- |
| 固定窗口计数器 | 每个时间窗口计数，超过阈值拒绝 | 简单；**临界问题**：窗口交界处短时间内可通过 2 倍流量 |
| 滑动窗口 | 把窗口分成多个小格，统计最近一个完整窗口内的总和 | 解决临界问题，格子越多越精确；Sentinel 的统计就是这种 |
| 漏桶 | 请求进桶，以固定速率流出处理，桶满拒绝 | 输出流量绝对平滑；不允许突发 |
| 令牌桶 | 以固定速率向桶里放令牌，请求拿到令牌才能处理 | 允许一定突发（桶里积累的令牌），最常用；Guava `RateLimiter` 是它的变体 |

**限流在哪里做**：网关层做全局限流（Redis + Lua 实现分布式令牌桶）；服务层用 Sentinel 做接口级限流；单机可用 Guava 或信号量。

### 3.2 熔断【核心】

当下游的失败率或慢调用比例达到阈值时，调用方**直接返回降级结果**，不再发起调用，给下游恢复的时间，同时保护自己的线程池。

**熔断器三种状态**：

1. **关闭（Closed）**：正常调用，统计失败率。
2. **打开（Open）**：触发阈值后进入，所有请求直接走降级；经过熔断时长后进入半开。
3. **半开（Half-Open）**：放行少量探测请求，成功则回到关闭，失败则重新打开。

&#91;embedded content: 熔断器状态机 · 3 种状态\]

**Sentinel 熔断策略**：慢调用比例（响应时间超过阈值的请求占比）、异常比例、异常数。

### 3.3 降级【核心】

降级是「有损服务」：在资源不足或依赖故障时，关闭或简化非核心功能，保证核心链路。

- **被动降级**：熔断或异常时走 fallback，返回默认值、缓存值或友好提示（如推荐服务挂了就展示热门商品）。
- **主动降级**：大促前通过开关关闭评论、积分、实时推荐等功能，把资源让给下单和支付。

**三者关系**：限流是保护自己不被流量压垮；熔断是不被下游拖垮；降级是两者发生后的处理方式。

### 3.4 超时、重试与「三态」【核心】

- **必须设超时**：没有超时的调用是雪崩的根源。超时时间参考下游 P99 耗时，且**越靠近入口超时越长**（网关 > 上游 > 下游），避免下游还在处理上游已超时放弃。
- **重试只用于幂等接口**：写接口重试可能导致重复下单、重复扣款。Feign 默认不重试，Dubbo 默认 Failover 重试 2 次，写操作要改为 Failfast 或保证幂等。
- **避免重试风暴**：多层都重试会把流量成倍放大（3 层各重试 3 次就是 27 倍）。只在一层重试，用指数退避 + 随机抖动，并设置重试预算。

**为什么一次远程调用会有「三态」**：网络是不可靠的，客户端只能观测到「有没有收到响应」，观测不到「下游到底做没做」。

| 结果 | 判定依据 | 业务含义 | 能否直接重试 |
| --- | --- | --- | --- |
| 成功 | 收到明确的成功响应 | 下游已执行并生效 | 不需要；如需再试必须幂等 |
| 失败 | 收到明确的失败响应（业务错误码、连接被拒绝、明确的 4xx） | 下游未执行或明确未生效 | 可重试，但要区分「可恢复」与「不可恢复」 |
| 未知 | 超时、连接重置、响应丢包、下游进程无响应 | **执行与否不知道** | **不能盲目重试，先查询** |

**未知态才是分布式调用的核心难点**：一次超时可能是三种完全不同的情况——① 请求根本没到下游（重试安全）；② 请求到了、下游正在执行（重试会重复执行）；③ 下游执行完但响应在回程丢了（重试同样重复）。客户端**无法从超时本身区分这三种**，所以超时 ≠ 失败。

**超时后不能简单判失败**：

- 判失败并重试 → 重复扣款、重复下单、重复发券；
- 直接判成功 → 可能根本没执行，造成少发货、漏记账；
- 正确做法是把「未知」显式建模为一个状态，交给幂等 + 查询补偿去收敛，而不是在调用点猜。

**四种落地策略**：

| 策略 | 做法 | 适用 | 代价 |
| --- | --- | --- | --- |
| 幂等 + 查询补偿 | 请求携带业务唯一键（订单号 / 请求号），下游按它去重；超时后按该键查询真实结果，查不到再重试 | 有明确业务主键、下游能提供查询接口 | 需要下游配合幂等与查询 |
| 业务状态机 | 引入 `PROCESSING` 中间态，未知时保持中间态，前端轮询，状态只前进不回退 | 用户可感知的支付、下单流程 | 前端与业务要处理中间态 |
| 本地消息表 / 事务消息 | 本地事务写业务数据 + 消息，异步驱动下游，不依赖同步响应 | 下游「一定会成功」的异步通知 | 需要可靠投递与消费幂等 |
| 最大努力通知 + 对账 | 定时通知 + 主动查询 + T+1 对账兜底 | 跨公司、跨系统 | 时效差，需要核对体系 |

**与重试的关系**：重试解决的是**明确的瞬时失败**（连接被拒、503、限流），它**不解决未知态**；未知态的第一动作是「查询」而不是「重试」。另外两条红线：重试必须带同一个幂等键；重试次数 × 单次超时必须小于上游超时预算，否则上游先放弃，重试白做。

**状态机与代码示例**：

```
INIT ──提交──> PROCESSING ──明确成功──> SUCCESS
                  │  ├────明确失败──> FAILED
                  │  └────超时/异常──> UNKNOWN（对外仍显示「处理中」）
                  └──补偿查询──> 查到成功 → SUCCESS
                                 查到失败 → FAILED
                                 查不到   → 用同一幂等键重试 → PROCESSING
```

| 状态 | 含义 | 对外表现 | 后续动作 |
| --- | --- | --- | --- |
| INIT | 尚未提交 | 待支付 | 允许用户发起 |
| PROCESSING / UNKNOWN | 已提交，结果未定 | 处理中 / 支付确认中 | 轮询 + 定时补偿查询 |
| SUCCESS | 下游确认成功 | 成功 | 由回调驱动发货、记账 |
| FAILED | 下游明确失败 | 失败 | 允许重新发起（同幂等键或换新键） |

```java
public PayResult pay(String orderNo, BigDecimal amount) {
    String idempotentKey = "pay:" + orderNo;                  // 业务唯一键，下游据此去重
    try {
        Resp r = payClient.pay(orderNo, amount, idempotentKey);
        if (r.isSuccess()) {
            markPaid(orderNo, r.getTradeNo());
            return PayResult.success(r.getTradeNo());
        }
        markFailed(orderNo, r.getCode());                      // 明确的业务失败，可判定
        return PayResult.failed(r.getCode());
    } catch (TimeoutException | IOException e) {
        markUnknown(orderNo);                                  // 执行与否未知：只记状态
        return PayResult.unknown();                            // 前端展示「支付确认中」
    }
}

// 补偿任务：先查询、查不到再重试，绝不凭超时直接判失败
@Scheduled(fixedDelay = 30_000)
public void reconcile() {
    for (String orderNo : findUnknownOrders(100)) {
        switch (payClient.query(orderNo).getStatus()) {
            case SUCCESS:   markPaid(orderNo, tradeNo); break;
            case FAILED:    markFailed(orderNo, code);  break;
            case NOT_EXIST: retryPay(orderNo);          break;  // 下游确实没收到
            default:        break;                              // 仍在处理，等下一轮
        }
    }
}
```

**面试落点**：先说三态 → 再点明「超时属于未知、不能当失败」 → 最后给出「幂等键 + 查询补偿 + 中间态 + 对账」的组合，并说明重试只处理明确失败。

### 3.5 负载均衡与隔离【重点】

**负载均衡算法**：轮询、加权轮询、随机、最少活跃调用（优先发给正在处理请求最少的实例，适合响应时间差异大的场景）、一致性哈希（同一参数总发到同一实例，适合有本地缓存的服务；**环形结构、虚拟节点与迁移比例见 3.5.1**）。

**隔离**：线程池隔离（不同下游用不同线程池）、信号量隔离（Sentinel 的并发线程数限流）、服务部署隔离（核心与非核心服务分开部署）。

### 3.5.1 一致性哈希【重点】

**要解决的问题**：缓存、分库分表、会话粘滞都要求「同一个 key 永远落到同一个节点」。取模哈希 `node = hash(key) % N` 最简单，但**节点数一变，几乎所有 key 都要搬家**：N 台扩到 N+1 台时，迁移比例约为 `(N-1)/N`，集群扩容瞬间会把缓存全部打穿。

**环形哈希**：把哈希空间首尾相接成一个环（常见取 `0 ~ 2^32-1`），节点和数据都映射到环上；数据从自己的位置**顺时针**找到第一个节点，就是归属节点。

**增删节点时的迁移比例**：

| 操作 | 受影响范围 | 平均迁移比例 |
| --- | --- | --- |
| 取模哈希，N → N+1 | 几乎全部 key | ≈ (N-1)/N（约 100%） |
| 环形哈希，新增 1 个节点 | 仅新节点逆时针到前一个节点之间的区间 | ≈ 1/(N+1) |
| 环形哈希，删除 1 个节点 | 仅该节点负责的区间转给后继节点 | ≈ 1/N |

这就是一致性哈希的价值：**扩容只搬一小段数据**，既能平滑扩容，也能避免缓存雪崩。

**虚拟节点**：真实节点太少时，环上的位置由 hash 随机决定，很容易出现「一个节点管了半个环、另一个节点只分到几条数据」的倾斜。解法是给每个物理节点映射 M 个虚拟节点（如 `node#0` … `node#M-1`），让它在环上均匀散开：

- 虚拟节点越多分布越均匀，但环上的元数据、内存与查找成本也越大；Dubbo 默认 160 个副本，实践中 100~200 是常用区间；
- 想让性能更强的机器多分担流量，就给它更多虚拟节点（按权重比例），这是「加权一致性哈希」；
- 虚拟节点不足时仍会倾斜，扩容后要观察各节点 key 数量方差，而不是只看总容量。

**数据倾斜与热点**（一致性哈希不解决、必须单独处理）：

- **结构性倾斜**：虚拟节点太少、hash 函数质量差（如直接用 `String.hashCode()`，碰撞与分布都差）；
- **业务热点**：某个 key（爆款商品、大 V）访问量极高，落在哪个节点都会打满——需要本地缓存、热点 key 复制到多个节点、读多副本，或对 key 加盐打散；
- **大 key / 大 slot**：单个 key 数据量过大，迁移时会长时间阻塞，要拆分 key 或限制单个 key 的大小。

**与取模哈希对比**：

| 维度 | 取模哈希 | 一致性哈希 |
| --- | --- | --- |
| 节点变化迁移 | ≈ 全量 | 新增 1/(N+1)、删除 1/N |
| 分布均衡性 | 天然均匀 | 依赖虚拟节点数量与 hash 质量 |
| 实现成本 | 一行取模 | 环 + 二分查找 + 虚拟节点 |
| 典型场景 | 节点数固定的分片 | 节点动态伸缩、会话粘滞、本地缓存路由 |
| 热点问题 | 不解决 | 不解决 |

**典型应用**：

| 场景 | 做法 |
| --- | --- |
| Redis Cluster | 16384 个**槽位**，`CRC16(key) % 16384` 定位槽，节点各自持有槽区间；扩容迁移的是槽，不是环 |
| Dubbo `ConsistentHashLoadBalance` | 默认 160 个虚拟节点，按方法参数哈希选 Invoker，适合有本地缓存的服务 |
| 网关 / Nginx | `hash $request_uri consistent` 等策略做会话粘滞，同一用户固定到同一后端 |
| 分库分表 | ShardingSphere 一致性哈希分片算法，扩分片时只迁移部分数据 |
| 客户端缓存路由 | 同一参数固定到同一实例，提高本地缓存命中率 |

注意 Redis Cluster 与一致性哈希的区别：**槽位是固定分片**，扩缩容时以槽为单位渐进迁移（可暂停、可回滚）；一致性哈希是**动态环**，节点上下线自动重分布。两者目的相同（少迁移、路由可预测），实现不同，面试别混为一谈。

```java
public class ConsistentHashRing {
    private final TreeMap<Long, String> ring = new TreeMap<>();
    private final int vNodes;                                  // 每个物理节点的虚拟节点数

    public ConsistentHashRing(Collection<String> nodes, int vNodes) {
        this.vNodes = vNodes;
        nodes.forEach(this::addNode);
    }

    private long hash(String key) {                            // 生产用 Murmur3 / MD5 前 8 字节
        return Hashing.murmur3_128().hashString(key, StandardCharsets.UTF_8).asLong();
    }

    public void addNode(String node) {
        for (int i = 0; i < vNodes; i++) {
            ring.put(hash(node + "#" + i), node);              // 虚拟节点散开，缓解倾斜
        }
    }

    public void removeNode(String node) {
        for (int i = 0; i < vNodes; i++) ring.remove(hash(node + "#" + i));
    }

    public String route(String key) {
        Map.Entry<Long, String> e = ring.ceilingEntry(hash(key));   // 顺时针第一个节点
        return (e != null ? e : ring.firstEntry()).getValue();     // 越过环尾回绕
    }
}
```

**实现坑**：`TreeMap` 非线程安全，变更节点时要加读写锁或整体重建；环为空要有兜底节点；不同物理节点的 hash 撞到同一位置会被覆盖，需要检测；虚拟节点数量要与内存和 16384/2^32 的空间匹配，不是越多越好。

### 3.6 发布策略【了解】

- **蓝绿发布**：两套完整环境，切换流量，回滚快但资源翻倍。
- **灰度（金丝雀）发布**：先把少量流量（按比例、按用户 ID、按地区）导向新版本，观察指标后逐步放量。全链路灰度需要在网关打标签，并在调用链上透传。
- **滚动发布**：逐批替换实例，K8s 默认方式。

### 3.7 Sentinel 核心机制【重点】

前面的 3.1–3.5 讲的是治理思想和通用算法，这里补 Sentinel 的实现层面，面试常问「你用过 Sentinel 吗，它怎么统计的」。

**核心概念与执行链**：所有受保护的接口称为**资源**（`@SentinelResource` 或 Web 拦截自动生成），每个资源对应一条 **Slot Chain**，按固定顺序执行：

`NodeSelector`（构建调用树）→ `ClusterBuilder`（按 origin 聚类统计）→ `Log` → `Statistic`（滑动窗口计数）→ `Authority`（黑白名单）→ `System`（系统自适应）→ `Flow`（限流）→ `Degrade`（熔断）。

顺序不能乱：统计必须在限流之前，系统保护必须在接口限流之前。

**滑动窗口统计**：默认 1 秒切成 2 个桶，用环形数组（LeapArray）累加每个桶的通过数、异常数、RT；窗口滚动时只淘汰过期桶，所以统计是近似值、无锁（LongAdder）。格子越多越精确，内存和计算成本也越高。

**流控模式【重点】**：

| 模式 | 含义 | 典型场景 |
| --- | --- | --- |
| 直接 | 资源自身达到阈值就限流 | 普通接口限流 |
| 关联 | A 达到阈值时，限流关联资源 B | 写库忙时限读接口，避免读写争抢 |
| 链路 | 只统计从指定入口进来的调用 | 同一资源被多个入口调用，只限制某个入口 |

「链路」模式需要关闭 Web 上下文统一入口（`web-context-unify=false`），否则所有请求都被算到同一个入口，配了也不生效，这是实践中最常见的踩坑点。

**流控效果【重点】**：快速失败（默认，超阈值直接抛 `BlockException`）、Warm Up（冷启动，`coldFactor` 默认 3，从「阈值/3」逐步升到阈值，防止冷系统被瞬间打满）、排队等待（漏桶思路，请求匀速通过，适合消息消费类场景，注意超时时间）。

**熔断策略与状态机【重点】**：慢调用比例（RT 超过最大 RT 且请求数 ≥ 最小请求数时，统计慢调用占比）、异常比例、异常数。熔断时长结束后进入**半开**，放一个请求探测：成功则关闭，失败则重新打开。最小请求数是必备护栏，否则低流量下偶尔一个慢请求就会误熔断。

**热点参数限流【了解】**：对方法参数做统计，按参数值分别限流（如按 `userId`、`skuId`），底层用 LRU 统计 topN 热点值，支持给某个参数值单独配置例外阈值。秒杀、热点商品场景很有用。

**系统自适应保护【了解】**：从全局入口维度保护整机，五个指标——`LOAD1`（按 CPU 核数折算）、CPU 使用率、平均 RT、并发线程数、入口 QPS。任一指标超阈值就拒绝入口流量，用于兜底「谁在打我都不知道」的突发流量；只对入口资源生效，不针对单个接口。

**规则持久化【重点】**：默认规则存在内存，应用重启就丢。三种模式：原始模式（写内存/控制台）、Pull 模式（客户端定时拉取本地文件或配置中心）、Push 模式（控制台写 Nacos，客户端监听推送，生产推荐）。规则必须持久化，否则重启后限流形同虚设。

**与 Hystrix 的对比【了解】**：Hystrix 默认线程池隔离，每个依赖一个线程池，隔离彻底但有线程切换开销，且规则调整难；Sentinel 以信号量（并发线程数）为主、不额外建线程池，开销小，控制台动态改规则，并额外提供热点参数、系统自适应、链路限流。Hystrix 已停止维护，新项目选 Sentinel 或 Resilience4j。

## 四、分布式事务

拆分后一个业务操作要修改多个服务的数据库（如下单扣库存、扣余额），本地事务无法保证一致。方案分为两类：强一致的刚性事务（2PC / XA），和最终一致的柔性事务（TCC、Saga、可靠消息）。**互联网业务绝大多数采用柔性事务**。

### 4.1 方案对比【核心】

| 方案 | 一致性 | 性能 | 业务侵入 | 适用场景 |
| --- | --- | --- | --- | --- |
| 2PC / XA | 强一致 | 低，全程持锁 | 低 | 短事务、并发低、强一致的内部系统 |
| Seata AT | 最终一致（有全局锁） | 较高 | 几乎无，加注解即可 | 快速上手的通用业务 |
| TCC | 最终一致 | 高 | 高，每个操作写三个方法 | 资金、库存等高一致、高性能场景 |
| Saga | 最终一致 | 高 | 中，要写补偿 | 长流程、跨系统（旅行预订、审批） |
| 可靠消息（本地消息表 / 事务消息） | 最终一致 | 高 | 中 | 上游成功后下游「一定要做」、可异步的场景 |
| 最大努力通知 | 最终一致 | 高 | 低 | 跨公司的结果通知，配合对账 |

### 4.2 2PC 与 3PC【重点】

**2PC（两阶段提交）** 是最经典的刚性事务协议，由一个协调者（事务管理器）和多个参与者（资源管理器，通常是数据库）组成。

**第一阶段：Prepare（投票）**。协调者向所有参与者发送 `prepare`，参与者在本地执行事务（写 undo/redo 日志、加行锁），但**不提交**；执行成功回 `Yes`，失败回 `No`。只要有一个 `No`（或超时），协调者就向所有参与者发 `rollback`。

**第二阶段：Commit / Rollback（决议）**。全部 `Yes` 则发 `commit`，参与者提交并释放锁；否则发 `rollback`，参与者用 undo 日志回滚并释放锁。

```
协调者                 参与者 A              参与者 B
  |--- prepare --------->|                    |
  |                      | 执行、加锁、投票 Yes |
  |--- prepare ------------------------------>|
  |                      |                    | 执行、加锁、投票 Yes
  |<-- Yes --------------|                    |
  |<-- Yes ---------------------------------- |
  |--- commit ---------->|  提交、释放锁        |
  |--- commit -------------------------------->|  提交、释放锁
```

**全部失败场景**（面试必追问「协调者/参与者挂了会怎样」）：

| 故障点 | 现象 | 后果 | 处理方式 |
| --- | --- | --- | --- |
| 协调者在**发完 Prepare 后、发决议前**宕机 | 参与者都投了 Yes，却永远等不到第二阶段 | 参与者进入 **in-doubt（不确定）** 状态，一直持锁阻塞，其他事务排队 | 不能自行提交或回滚（自行决定都会错），只能等协调者恢复后重发，或 DBA 用 `XA RECOVER` 人工裁决 |
| 协调者在**发 Commit 途中**宕机 | 部分参与者已提交、部分没收到 | 数据不一致（真正的原子性被破坏） | 恢复后按日志重发 Commit；未收到的一侧仍是 in-doubt，期间可能读到「半提交」数据 |
| 参与者在 **Prepare 阶段**宕机 | 协调者收不到投票 | 投票超时，整体回滚 | 参与者重启后按 undo 日志回滚，天然安全 |
| 参与者在 **Prepare 之后、Commit 之前**宕机 | 该分支已 prepare 但未提交 | 该分支持锁，恢复前阻塞；恢复后重放日志等决议 | in-doubt 分支由协调者恢复后补齐 |
| **网络超时 / 消息丢失** | 投票或决议丢失 | 协调者按失败处理，参与者可能已 prepare | 依赖重试与幂等；决议必须可重发 |
| **悬挂（hanging）** | 回滚决议先到，迟到的 Prepare 后到 | 参与者执行了一个「已被回滚」的事务并持锁等待永远不会来的决议 | 参与者记录全局事务状态，已回滚的 XID 拒绝后续 Prepare；协调者重发 Rollback |

**2PC 的三个固有问题**：**同步阻塞**（全程持锁，RT 等于最慢分支）、**协调者单点**（一阶段后宕机全员 in-doubt）、**数据不一致**（决议阶段无法保证「同时生效」）。

**XA 落地**（MySQL 的 XA 就是 2PC 的标准实现，由外部事务管理器驱动）：

```sql
XA START 'xid-001';                                  -- 开启分支
UPDATE account SET balance = balance - 100 WHERE id = 1;
XA END 'xid-001';
XA PREPARE 'xid-001';                                -- 一阶段：行锁与连接一直不释放
-- 第二阶段，由协调者统一决定
XA COMMIT 'xid-001';                                 -- 或 XA ROLLBACK 'xid-001'
XA RECOVER;                                          -- 查看 in-doubt 分支
```

注意 `PREPARE` 之后**连接和行锁都被占用**，所以 XA 的 RT 高、连接池容易被占满，不适合长事务与高并发热点行；这也是 Seata XA 模式只在短事务、低并发场景可用的原因（见 4.7）。

**3PC（三阶段提交）** 在 2PC 的 Prepare 前插入了 **CanCommit**，并把「执行」推迟到第二阶段：

1. **CanCommit**：只询问「能不能做」，参与者只检查资源、不执行、不加锁；
2. **PreCommit**：参与者真正执行并预留资源（持锁），与 2PC 的 Prepare 相同；
3. **Commit / Rollback**：与 2PC 的第二阶段相同。

**3PC 的改进**：把纯询问与真正执行拆开，参与者可以在 CanCommit 阶段就快速拒绝，减少无效持锁；并引入**超时自动决策**——PreCommit 阶段超时默认回滚，Commit 阶段超时默认提交（因为一旦进入 PreCommit，说明所有参与者都已确认可执行）。这样协调者在 PreCommit 后宕机时，参与者不必无限期 in-doubt。

**3PC 仍不解决的**：如果协调者在 PreCommit 只发给了部分参与者后宕机，收到的一方超时提交、没收到的一方超时回滚，**依然不一致**；而且多了一次网络往返，性能更差，超时阈值依赖节点间时钟大致同步（见 1.6：物理时钟并不可靠）。因此 3PC 在工程上基本只存在于教材。

**为什么线上更倾向 TCC / Saga / 本地消息表**：

| 维度 | 2PC / XA | TCC | Saga | 本地消息表 |
| --- | --- | --- | --- | --- |
| 一致性 | 强一致（持锁） | 最终一致（资源预留，准隔离） | 最终一致（无隔离） | 最终一致（异步） |
| 性能 | 低，RT = 两阶段 + 最慢分支 | 高，无长事务持锁 | 高 | 高，可削峰 |
| 业务侵入 | 低，数据库层协议 | 高，写 Try/Confirm/Cancel | 中，写补偿 | 中，写消息表 + 重试 |
| 资源要求 | 所有参与者都支持 XA | 无特殊要求 | 无特殊要求 | 需要可靠 MQ 或本地表 |
| 典型场景 | 短事务、低并发、同构数据库 | 资金、库存 | 长流程、跨系统 | 下游「一定成功」的异步场景 |

**面试落点**：先讲清两阶段与 in-doubt，再补一句「2PC 保证的是**提交决议的原子性**，但保证不了决议**送达的原子性**」，最后给出选型结论——互联网业务用 TCC / Saga / 可靠消息，只有在数据库同构、事务短、并发低的内部系统才考虑 XA。

### 4.3 Seata AT 模式【核心】

**三个角色**：TC（事务协调者，独立部署的 Seata Server）、TM（事务管理器，发起全局事务的一方，即加了 `@GlobalTransactional` 的服务）、RM（资源管理器，各参与方的数据源代理）。全局事务 ID（XID）随调用链透传。

**一阶段**：RM 解析 SQL，查出修改前的数据（before image），执行业务 SQL，再查出修改后的数据（after image），把两者写入 `undo_log` 表，**与业务数据在同一个本地事务中提交**。提交前向 TC 申请该行的**全局锁**。本地锁提交后就释放了，所以性能比 XA 高。

**二阶段**：全部成功 → TC 通知 RM 异步删除 undo\_log，释放全局锁；任一失败 → RM 用 before image 生成反向 SQL 回滚（回滚前校验当前数据与 after image 一致，不一致说明被全局事务外的操作改过，需要人工处理）。

**局限**：只支持有本地 ACID 事务的关系型数据库；全局锁在高并发热点行上会成为瓶颈；默认是「读未提交」隔离级别，需要读已提交时要用 `SELECT ... FOR UPDATE`。

### 4.4 TCC【重点】

把一个操作拆成三个方法，以扣余额为例：

- **Try**：检查并**预留资源**（余额 100 → 可用 70、冻结 30）。
- **Confirm**：真正执行，使用预留的资源（冻结 30 清零）。
- **Cancel**：释放预留的资源（冻结 30 加回可用）。

Try 全部成功则对所有参与者调用 Confirm，否则调用 Cancel。Confirm / Cancel 失败会被不断重试。

**三大问题【重点】**：

| 问题 | 场景 | 解决 |
| --- | --- | --- |
| 幂等 | Confirm / Cancel 会被重试 | 用事务控制表记录每个分支事务的状态 |
| 空回滚 | Try 因网络超时未执行，却收到了 Cancel | Cancel 时发现没有 Try 记录，就插入一条「已回滚」记录后直接返回成功 |
| 悬挂 | Cancel 先执行完，延迟到达的 Try 才执行，资源被冻结且永远不会释放 | Try 执行前检查，如果已有「已回滚」记录就拒绝执行 |

### 4.5 Saga【了解】

把长事务拆成多个本地事务 T1…Tn，每个都有对应的补偿操作 C1…Cn。任一步失败，就按反序执行已完成步骤的补偿。没有预留阶段，每步直接提交，所以**不保证隔离性**（其他事务可能看到中间状态）。编排方式有协同式（服务间发事件）和编排式（中心协调器按状态机执行，Seata Saga 是这种）。

### 4.6 可靠消息方案【核心】

消息侧的实现细节见《消息队列核心知识点学习文档》5.2 事务消息与 5.3 本地消息表。要点：上游用「本地事务 + 消息」的原子性保证消息一定发出，下游用「重试 + 幂等」保证一定执行成功。前提是**下游业务上不会失败**（只会暂时失败）；如果下游可能「余额不足」这样的业务失败并需要上游回滚，就应该用 TCC 或 Saga。

**选型经验**：能不用分布式事务就不用（通过合理的服务划分让强一致的数据留在同一个服务内）；能异步就用可靠消息；资金类用 TCC；长流程用 Saga；想快速落地用 Seata AT。

#### 4.6.1 最大努力通知【重点】

**语义**：最大努力通知（Best-Effort Notification）是「**我尽力把结果推给你，推不到就算了，你自己来查**」。它只承诺**发起通知的主动性**和**有限的重复次数**，**不承诺必达、不承诺顺序、不承诺只通知一次**。接收方必须假定：可能收不到、可能收到多次、可能收到乱序。

**与可靠消息的本质差别**是「谁承担送达责任」：可靠消息由**上游**用本地事务 + 消息表/MQ 保证消息一定进入「必达」通道，投递失败会无限重试直到成功；最大努力通知则把最终兜底责任**交给接收方的主动查询 + 双方对账**，上游只负责「按时、按次数推」。MQ 侧的事务消息、本地消息表与对账写法见《消息队列核心知识点学习文档》5.2 / 5.3 / 5.6。

**通知频次与退避策略**（工程上的标准做法）：

| 策略 | 做法 | 说明 |
| --- | --- | --- |
| 阶梯退避 | 立即 1 次，之后 1min / 5min / 15min / 30min / 1h / 2h / 6h / 12h / 24h | 越靠前越密，覆盖瞬时故障；总量固定（常见 8~10 次），避免无限打扰 |
| 总时长上限 | 典型 24h（支付回调），超出后停止通知，转为「仅对账」 | 必须与业务的可补偿窗口对齐，超过窗口再通知也没有意义 |
| 通知即幂等 | 每次通知带同一业务单号 + 通知序号 + 时间戳 | 接收方按单号去重，重复通知返回成功即可，不报错 |
| 多通道降级 | HTTP 回调失败 → 短信/邮件/站内信提醒对方运维 | 只用于人工兜底，不作为业务通路 |
| 可手动重推 | 提供后台「重发通知」按钮与通知记录查询 | 联调与线上救火必需，否则只能靠对账被动发现 |

**退避实现（数据库通知表 + 定时扫描）**：

```sql
CREATE TABLE notify_task (
  id            BIGINT PRIMARY KEY,
  biz_no        VARCHAR(64)  NOT NULL,     -- 业务单号，接收方据此幂等
  notify_no     INT          NOT NULL,     -- 第几次通知，从 1 开始
  url           VARCHAR(255) NOT NULL,
  payload       TEXT         NOT NULL,
  status        TINYINT      NOT NULL,     -- 0 待通知 1 成功 2 已达上限
  next_time     DATETIME     NOT NULL,
  UNIQUE KEY uk_biz_no_notify_no (biz_no, notify_no)
);
```

```java
@Scheduled(fixedDelay = 10_000)
public void dispatch() {
    for (NotifyTask t : mapper.findDue(100)) {            // next_time <= now，按时间升序
        try {
            Resp r = httpPost(t.getUrl(), t.getPayload(), t.getNotifyNo());
            if (r.isSuccess()) { mapper.markSuccess(t.getId()); continue; }
        } catch (Exception ignore) { /* 失败按退避继续 */ }
        if (t.getNotifyNo() >= MAX_TIMES) {               // 达到上限：停止推送，标记待对账
            mapper.markGiveUp(t.getId());
        } else {
            mapper.reschedule(t.getId(), nextDelay(t.getNotifyNo()));   // 阶梯退避
        }
    }
}
```

**四维对比**（这是 q1442 的核心考点）：

| 维度 | 最大努力通知 | 可靠消息（本地消息表 / 事务消息） | 备注 |
| --- | --- | --- | --- |
| 一致性 | 弱：不保证送达，最终一致靠**接收方查询 + 对账** | 强（相对）：消息必然投递并被消费，最终一致由上游保证 | 通知失败不会阻塞上游，也就不会「卡单」 |
| 实现成本 | 低：一张通知表 + 定时任务 + 一个查询接口 | 中高：本地消息表与业务同库事务、或引入支持事务消息的 MQ、消费幂等与死信治理 | 通知方案对 MQ 无强依赖 |
| 重试归属 | **发送方**有限次重试 + **接收方**主动查询 + **双方**对账 | **上游**无限重试（或死信 + 人工），接收方只保证消费幂等 | 谁掌握「最终真相」谁负责兜底 |
| 对账要求 | **必须**：T+1 全量对账 + 差异工单，是方案的组成部分 | 可选：主要防「消费成功但业务处理失败」，通常也做，但不是唯一兜底 | 没有对账的最大努力通知等于「不保证」 |
| 耦合与依赖 | 松：接收方只需实现「通知接口 + 查询接口」 | 紧：双方要约定消息格式、MQ 可用性、消费组 | 跨公司场景决定性因素 |
| 时效 | 秒级到小时级，依赖对方系统状态 | 秒级（事务消息）/ 秒级到分钟级（本地消息表轮询） | 都远快于 T+1 对账 |

**与业务状态机的关系**：最大努力通知不能直接改「终态」，它是**驱动状态机的输入之一**，与「主动查询」「对账文件」一起构成同一状态机的三条入口：

```
                     ┌─ 通知回调（可能重复/乱序/缺失）─┐
外部结果 ──发射──> 订单状态机  ── 主动查询（定时补偿）────┼─> 终态（SUCCESS / FAILED）
                     └─ 对账文件（T+1 最终裁决）───────┘
```

状态机要求：状态**只前进不回退**（已 SUCCESS 再收到「失败通知」只记日志不改状态）；每次变更写流水（来源 = 通知/查询/对账）便于溯源；终态判定以**查询与对账**为准，通知只做加速。

**典型场景**：

| 场景 | 谁通知谁 | 兜底方式 |
| --- | --- | --- |
| 支付结果回调（微信/支付宝 → 商户） | 渠道 → 商户 | 商户未应答则渠道按阶梯退避重推；商户侧定时 `query` 订单 + T+1 对账 |
| 第三方渠道回调（物流、开票、实名认证） | 渠道 → 平台 | 平台按状态机置「处理中」，定时查询 + 对账 |
| 跨公司系统对接（ERP、银行、运营商） | 一方 → 另一方 | 双方约定对账文件与差异处理 SLA，人工工单兜底 |
| 内部弱一致通知（积分、短信、站内信） | 上游 → 下游 | 只做重试 + 落库补偿，不追求必达 |

**失败处理边界**（哪些情况不能靠最大努力通知解决）：

1. **资金类强一致要求**：不能只靠通知，必须有查询 + 对账 + 人工工单，且账务以对账结果为准；
2. **对时效敏感的业务**（秒杀库存回补、实时风控）：通知延迟不可接受，应改用同步调用 + 幂等，或可靠消息；
3. **接收方没有查询接口**：方案不成立——最大努力通知的前提就是「你能查到我」，缺查询接口时必须先补接口；
4. **通知目标不可达且无对账**：会变成永久静默丢单，属于设计缺陷而不是实现缺陷；
5. **需要顺序保证的场景**：通知不保证顺序，状态迁移必须靠版本号/状态机约束，而不能依赖到达顺序。

**面试落点**：一句话说清「最大努力通知 = 有限重试 + 接收方查询 + 对账兜底，送达责任在接收方」；再说清它与可靠消息的差别是「谁负责必达」；最后补上「资金场景仍必须对账，通知只是加速」。

### 4.7 AT 脏写隔离与 XA 取舍【了解】

**AT 的脏写防护**：AT 只锁「行 + 全局事务」，不是数据库的排他锁。全局锁保证同一个全局事务提交前，其他**全局事务**不能改同一行；但**全局事务之外的本地事务**（比如运维直接改库、未接入 Seata 的服务）不受全局锁约束，可能把数据改掉，导致二阶段回滚时 before/after image 校验失败。防护手段：用 `SELECT ... FOR UPDATE` 把本地锁也加上，或加唯一约束/版本号做兜底，校验失败的一律告警并人工处理，不要静默跳过。

**全局锁冲突**：拿不到锁的写请求会按配置重试，超过次数后回滚整个全局事务。热点行（如库存、账户余额）上的全局锁会串行化写入，这是 AT 在高并发写入场景下的主要瓶颈——这时应该改用 TCC 或 Redis 预扣 + 异步落库。

**XA 模式**：走数据库自带的 XA 协议（Prepare / Commit / Rollback），由 TC 编排，天然强一致、不需要 undo\_log；代价是事务期间**一直占用数据库连接和行锁**，RT 高、吞吐低，且要求数据库支持 XA。Seata XA 模式相比传统的 XA 外部协调，复用了本地连接、支持多数据源。

**取舍结论**：

| 场景 | 建议 |
| --- | --- |
| 一般业务，想快速接入、并发不高 | AT |
| 强一致、短事务、并发低（内部财务） | XA |
| 高并发热点行、资金扣减 | TCC |
| 长流程、跨系统、可补偿 | Saga |
| 上游成功即可、下游可异步 | 可靠消息 |

## 五、分布式 ID、分布式锁与幂等

这三个是分布式系统里最常用的基础设施，也是前面各章方案的前提：分库分表需要全局 ID，并发修改需要锁，重试和消息需要幂等。

### 5.1 分布式 ID【重点】

**要求**：全局唯一、趋势递增（对 B+ 树友好）、高可用、高性能，最好不暴露业务量。

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| UUID | 本地生成，简单 | 36 字符太长、无序，做主键会频繁页分裂 |
| 数据库自增 | 简单、有序 | 单点、性能瓶颈；多库可用不同步长但难扩展 |
| 号段模式 | 每次从数据库取一段（如 1000 个）在内存分配，数据库压力小 | 服务重启会浪费号段；号段用完时的取数会有延迟尖刺 |
| Redis INCR | 性能高、有序 | 依赖 Redis 的持久化，宕机可能重复 |
| **雪花算法** | 本地生成、性能高、趋势递增、BIGINT | 依赖机器时钟；workerId 需要分配 |

**雪花算法结构**：1 位符号位（固定 0）+ 41 位毫秒时间戳（约 69 年）+ 10 位机器 ID（1024 台）+ 12 位序列号（每毫秒 4096 个）。

**时钟回拨【重点】**：NTP 校时可能让时间倒退，导致生成重复 ID。处理：回拨很小（如 5 ms 内）就等待时间追上；回拨较大就报错并告警，或切换到备用 workerId；也可以不依赖实时时钟，用上次时间戳自增（如百度 UidGenerator 的做法）。

**美团 Leaf【重点】**：同时提供号段和雪花两种模式。号段模式用**双 buffer**：当前号段用到 10% 时就异步加载下一段，切换时无等待；雪花模式用 ZooKeeper 自动分配 workerId 并检测时钟回拨。容器环境下实例频繁起停，workerId 不能写死在配置里，需要由注册中心或 Redis 分配。

### 5.2 分布式锁【核心】

**一个好的分布式锁要满足什么【重点】**：① 互斥，同一时刻只有一个客户端进入临界区；② 不死锁，持有者宕机后锁能自动释放；③ 谁加锁谁解锁，不能被别人误删；④ 业务没执行完锁不能提前失效；⑤ 在此之上才讨论可重入、公平、阻塞等待、吞吐与可用性。任何方案都是在这五条上做取舍，没有全能解。

**单机锁与分布式锁的区别【重点】**

| 维度 | 单机锁（`synchronized` / `ReentrantLock`） | 分布式锁 |
| --- | --- | --- |
| 互斥范围 | 单个 JVM 进程内 | 跨进程、跨主机、跨机房 |
| 状态存放 | 对象头 Mark Word、AQS 队列，内存中 | 外部存储（Redis、ZK、etcd、数据库） |
| 失效方式 | 线程崩溃、异常由 JVM 保证释放 | 必须靠过期时间 / 会话 / 租约兜底 |
| 代价 | 纳秒到微秒级，无网络 | 一次或多次网络往返，毫秒级 |
| 失败模式 | 只可能死锁或阻塞 | 还会遇到网络超时、分区、主从切换、时钟漂移 |

关键差别是**分布式锁的每次加锁都是一次远程写**，所以必须假设「请求超时但服务端可能已成功」，由此才需要唯一持有者标识、幂等和 fencing token。多实例部署后 `synchronized` 完全失效，这是引入分布式锁的唯一理由。

**数据库层实现【重点】**

| 方式 | 做法 | 优点 | 边界与问题 |
| --- | --- | --- | --- |
| 唯一索引 / 唯一约束 | 建锁表，`resource` 建唯一索引，`INSERT` 成功即持锁，`DELETE` 释放 | 不引入新组件；唯一约束天然原子；可留审计记录；是最可靠的兜底 | 不会自动过期，要靠 `expire_at` + 定时清理；数据库是单点与性能瓶颈；释放必须校验 `owner` |
| 悲观锁 `SELECT ... FOR UPDATE` | 事务内对锁行加行锁，事务结束释放 | 与业务数据同库同事务，强一致 | 必须显式事务；`autocommit` 下立即释放等于没锁；where 未走索引会锁全表或大范围间隙；长事务占连接、热点行排队 |
| 乐观锁 / 状态机 | `UPDATE ... WHERE version = ?` 或带前置状态条件 | 无锁等待、吞吐高、天然幂等 | 只在「短事务 + 冲突低」时有效；冲突高时大量失败重试更慢；不能保护长耗时临界区 |

```sql
-- 唯一索引锁表：resource 唯一，owner 标识持有者
INSERT INTO t_lock(resource, owner, expire_at)
VALUES ('order:1001', 'uuid-abc', NOW() + INTERVAL 30 SECOND);

-- 释放：必须带 owner，避免误删别人的锁
DELETE FROM t_lock
WHERE resource = 'order:1001' AND owner = 'uuid-abc';
```

```java
// 乐观锁：影响行数为 0 表示已被别人改过
int updated = jdbcTemplate.update(
    "UPDATE stock SET qty = qty - 1, version = version + 1 WHERE id = ? AND version = ?",
    id, version);
if (updated == 0) {
    // 重试或直接失败，不能假设自己成功
}
```

**边界**：数据库锁适合低并发、可接受毫秒到数十毫秒延迟、且不想多引入中间件的场景。它最适合的角色不是「高并发互斥」，而是**其他锁失效后的最后一道数据防线**——唯一索引与 `version` 校验永远不会因为主从切换而失效。

**Redis 实现：从 SETNX 到安全释放【核心】**

| 版本 | 写法 | 遗留问题 |
| --- | --- | --- |
| 1 | `SETNX lock 1`，用完 `DEL` | 加锁后进程宕机，锁永不释放 |
| 2 | `SETNX` + `EXPIRE` | 两条命令非原子，中间宕机仍死锁 |
| 3 | `SET lock 1 NX EX 30` | 业务超过 30 秒时锁已过期，A 会删掉 B 的锁 |
| 4 | `SET lock <uuid> NX EX 30` + Lua 校验删除 | 业务没做完锁仍可能过期 |
| 5 | 版本 4 + 自动续期（看门狗） | Redisson 的做法，见下一节 |

```java
String token = UUID.randomUUID().toString();
boolean locked = "OK".equals(jedis.set(lockKey, token, SetParams.setParams().nx().px(30_000)));
```

```lua
-- 解锁：比较持有者与删除必须原子，否则仍可能误删
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

- **value 必须是唯一标识**（`UUID:threadId`），只用 `1` 无法区分持有者。
- **加锁必须一条命令**：`SET ... NX PX`，不能拆成 `SETNX` + `EXPIRE`。
- **不可重入**：同一线程再次加锁会失败并可能自锁；原生 `SET NX` 不记录重入次数，需要 Redisson 或自己用 Hash 计数。
- **死锁风险**：过期时间就是「宕机兜底」，没设过期时间等于埋雷；反过来，过期时间短于业务耗时会误删他人锁，必须有续期或校验。
- **阻塞等待**：轮询重试有延迟与空转，Redisson 改为订阅锁释放的 Pub/Sub 消息，比自旋省 CPU。
- **公平性**：原生 Redis 锁是非公平的，后到者可能抢先；公平锁要用队列（Redisson `FairLock` 按超时时间排序）。Lua 脚本的原子性细节与 Pipeline 对比见《Redis 核心知识点学习文档》7.4。

**Redisson 可重入与看门狗【核心】**

```java
RLock lock = redisson.getLock("stock:lock:" + skuId);
lock.lock();          // 不指定 leaseTime，才会启用看门狗
try {
    // 临界区
} finally {
    lock.unlock();    // 只有持有线程才能解锁，否则抛 IllegalMonitorStateException
}
```

**可重入的实现**：锁不是 String 而是 Hash，`key` 是锁名，`field` 是 `UUID:threadId`，`value` 是重入次数。加锁 Lua 分三种情况：key 不存在则 `hset 1` 并设过期；key 存在且 field 是自己则 `hincrby 1`；否则返回剩余 TTL 表示失败。解锁同理 `hincrby -1`，减到 0 才删除 key 并发布释放消息。

**看门狗的机制**：未显式指定 `leaseTime` 时，默认租约 30 秒（`lockWatchdogTimeout` 可改），后台任务每 10 秒（租约的 1/3）检查一次，只要当前线程仍持有锁就把过期时间重置为 30 秒。续期由 Netty 的 `HashedWheelTimer` 时间轮驱动，不占业务线程；客户端进程退出后不再续期，锁在最多 30 秒后自动释放。

| 写法 | 是否启用看门狗 | 适用 |
| --- | --- | --- |
| `lock.lock()` / `tryLock(waitTime, unit)` | 是 | 临界区耗时不确定 |
| `tryLock(waitTime, leaseTime, unit)` / `lock(leaseTime, unit)` | 否 | 临界区耗时确定，且必须严格上限 |
| `tryLock()`（无参） | 是，但不等待，只试一次 | 快速失败 |

**陷阱**：显式 `leaseTime` 会关闭看门狗，业务超时后锁直接失效；`unlock()` 必须在 `finally` 且校验 `isHeldByCurrentThread()`；看门狗依赖 Redisson 客户端存活，客户端被强制 kill -9 时最长 30 秒才释放；Redisson 还提供公平锁、读写锁、信号量、联锁（`MultiLock`），但联锁仍是多节点同时加锁，不解决主从丢锁。

**Redis 主从切换、脑裂与锁失效【重点】**

- **故障切换丢锁**：A 在主库 `SET NX` 成功，主库在把这条写入同步给从库之前宕机；哨兵把从库提升为主库，此时锁在「新主」上不存在，B 加锁成功，于是 A、B 同时持锁。
- **脑裂**：网络分区时客户端切到新主，旧主仍在运行且 A 还连着它，两个「主」各自接受加锁，同样双持有。
- **为什么 Redisson 也绕不开**：锁状态是 Redis 里的普通数据，而 Redis 主从复制是**异步**的；客户端能做的只有「加锁、续期、校验 value」，它没有能力验证「这个主库的写入是否已经成为多数派的既成事实」。锁的可靠性上限由存储层的复制语义决定，不在锁客户端。
- **`min-replicas-to-write` 只能收窄窗口**：要求至少 N 个副本确认且延迟不超过 `min-replicas-max-lag` 才允许写，能降低「刚写完就宕机」的概率，代价是副本不足时直接拒绝写入（可用性下降），而且复制仍有延迟、提升后的新主并不知道旧主上刚发生过什么，所以不能消除问题。
- **正确姿势**：接受「极小概率双持有」，在数据层用唯一索引、`version` 或状态机兜底；关键业务引入 fencing token；要求绝对互斥时改用 CP 系统（ZooKeeper / etcd）。

**RedLock 算法与争议【重点】**

算法（假设 5 个**完全独立**的 Redis 主节点，无主从关系）：

1. 记录开始时间；
2. 依次向 5 个节点执行 `SET lock <uuid> NX PX <ttl>`，每个节点设置较短的连接超时，避免一个慢节点拖垮全局；
3. 至少 3 个节点成功，且总耗时小于 `ttl`，才算加锁成功；
4. 失败则向所有节点发送释放脚本（无论是否成功过）；
5. 锁的实际有效期 = `ttl` − 加锁耗时。

它想解决的是单集群主从切换丢锁：用多数派写入代替单点写入。但争议一直没有停：

| 观点 | 主张 |
| --- | --- |
| Martin Kleppmann（反对） | 分布式系统无法同时保证「时钟可靠、进程不停顿、网络低延迟」；客户端 GC 停顿可能超过 ttl，锁到期被 B 拿走，而 A 醒来后仍会写，RedLock 本身不提供 fencing，所以不能保证互斥 |
| antirez（辩护） | 讨论的前提应是「没有 fencing 的锁」，这是所有带过期锁的通病；RedLock 已从有效期里扣除获取耗时，能减少窗口；真要绝对正确应使用带版本校验的存储，而不是苛求锁本身 |
| 社区实践结论 | RedLock 提升的是「单点故障下的存活率」，不是「绝对互斥」；部署 5 个真正独立的节点成本高，Redisson 已把 `RedissonRedLock` 标记废弃 |

**什么时候不该用 RedLock**：临界区涉及资金、库存且没有幂等兜底；5 个节点其实同机房、同宿主机或共享网络，独立性不成立；运维成本远大于收益。**替代方案**：单集群 Redisson + 数据层约束，或直接用 ZooKeeper / etcd 的 CP 锁 + fencing。

**ZooKeeper：临时顺序节点 + 监听前驱【重点】**

```java
InterProcessMutex lock = new InterProcessMutex(client, "/locks/order-1001");
if (lock.acquire(10, TimeUnit.SECONDS)) {
    try {
        // 临界区
    } finally {
        lock.release();
    }
}
```

- **加锁**：在锁目录下创建**临时顺序节点**（`CreateMode.EPHEMERAL_SEQUENTIAL`），形如 `/locks/order-1001/lock-0000000001`；取所有子节点排序，序号最小的持锁。
- **等待**：没抢到的客户端**只监听自己前一个节点**的删除事件（`exists` + watch），前驱释放后收到通知，再重新判断自己是否最小。若监听父节点，一次释放会唤醒所有等待者（惊群）；监听前驱把唤醒范围收敛到 1，且天然按创建顺序排队，所以是**公平锁**。
- **自动释放**：临时节点绑定会话，客户端与任意节点断连超过 `sessionTimeout` 后会话失效，临时节点被删除，锁释放；不需要过期时间参数。
- **会话超时的边界**：长时间 GC 停顿或网络抖动可能让会话过期，此时临时节点已被删除、别人已持锁，而原客户端仍以为自己持有——ZK 无法感知客户端「还活着但停住了」。所以临界区要短，写操作仍要幂等。
- **Curator 做了什么**：`InterProcessMutex` 内部维护线程级重入计数与 `LockData`（当前持有者、节点路径），自动处理连接丢失、重试、创建父路径、Watcher 重注册；`acquire(timeout)` 支持超时放弃；还有 `InterProcessReadWriteLock`、`InterProcessSemaphoreMutex`。
- **性能**：每次加锁解锁都是一次写操作，要经过 Leader 与过半节点同步，延迟毫秒级、吞吐远低于 Redis；而且 Leader 选举期间集群不可写，锁服务会短暂不可用。

**与 Redis 方案的取舍**：差异见上面的选型对照表，核心结论是「注册中心选 AP，锁服务才考虑 CP」，这与 1.1 的结论一致。

**etcd：lease + CAS + revision【了解】**

```java
Lease lease = client.getLeaseClient().grant(30);               // 租约，到期自动删除关联 key
ByteSequence key = ByteSequence.from("/locks/order-1001", UTF_8);
TxnResponse resp = client.getKvClient().txn()
    .If(Compare.createRevision(key).is(0))                     // 只有 key 从未被创建才写入
    .Then(Op.put(key, ByteSequence.from(owner, UTF_8), PutOption.withLeaseId(lease.getId())))
    .Else(Op.get(key))
    .commit();
```

- **lease**：`grant` 得到租约并绑定 key，客户端定期 `KeepAlive` 续约；进程崩溃后租约到期，key 自动级联删除，等价于 Redis 的过期时间 + ZK 的会话。
- **CAS / 事务**：用 `txn` 的 `If ... Then ... Else` 在服务端原子地「判断不存在再写入」，避免先查后写。
- **revision**：etcd 的每次写入都会让全局 `revision` 递增，且严格单调，拿它当 **fencing token** 最自然：写数据库时带上 `revision`，数据库只接受比已记录值更大的写入。
- **watch**：可监听单 key 或前缀范围，前驱删除后收到事件，思想和 ZK 一致。
- **适用**：已经在用 K8s/etcd 的团队、需要 fencing 或需要强一致的场景；Java 侧用 jetcd。相比 ZK，lease 是显式参数、revision 全局单调更易用，运维也更轻。

**Fencing Token【重点】**：任何带过期时间的锁都可能在持有者 GC 停顿时失效，导致两个客户端都以为自己持锁。解决办法是加锁时返回**单调递增**的 token（ZK 可用 `zxid`、etcd 可用 `revision`、Redis 可用 `INCR` 生成），写存储时一并带上，存储端拒绝比已记录值更小的写入：

```sql
UPDATE account SET balance = balance - 100, last_token = ?
WHERE id = ? AND last_token < ?   -- 旧持有者的写入会被拒绝
```

**工程层面的七个问题【重点】**

| 问题 | 要点 |
| --- | --- |
| 可重入 | 同一线程重复加锁不能自锁；Redis 用 Hash 计数（Redisson），ZK 用 Curator 的线程计数 |
| 公平性 | ZK 天然 FIFO；Redis 默认非公平，公平锁需队列；大多数业务不需要公平 |
| 锁粒度 | 锁业务资源 ID，不要锁整个接口或整张表；热点库存按 100 个分段加锁后汇总；读多用读写锁 |
| 超时与续期 | 按临界区 P99 估算；耗时不确定就用看门狗；显式 `leaseTime` 必须留余量；续期失败要主动放弃写入 |
| 锁降级 / 兜底 | Redis 不可用时降级为「本地锁 + 数据库唯一约束」，牺牲跨机互斥但保可用；降级要有开关、告警和恢复策略 |
| 与事务边界 | 锁必须在**事务外**获取、**事务提交后**释放，否则解锁时事务还没提交，别人进来会读到旧值 |
| 失效后的幂等 | 双持有无法 100% 排除，写操作必须有唯一索引、`version`、状态机或去重表兜底；MQ 消费同样要幂等 |

事务边界的典型错误：

```java
// 错误：unlock 在方法内执行，而事务提交发生在方法返回之后
@Transactional
public void wrong(Long id) {
    lock.lock();
    try { updateDb(id); } finally { lock.unlock(); }
}

// 正确：解锁包在事务提交之后
public void right(Long id) {
    lock.lock();
    try {
        transactionTemplate.executeWithoutResult(status -> updateDb(id));
    } finally {
        lock.unlock();
    }
}
```

若必须在 `@Transactional` 方法内加锁，可用 `TransactionSynchronizationManager.registerSynchronization` 在 `afterCompletion` 中释放。

**监控指标**：加锁失败率、平均等待时长、持锁时长分布、续期次数、解锁失败（`IllegalMonitorStateException`）告警、Redis/ZK 连接异常。持锁时长突然变长通常意味着临界区里出现了慢 SQL 或远程调用。

**选型对照【重点】**

| 方案 | 一致性 | 性能 | 自动释放 | 公平 | 适用 | 主要风险 |
| --- | --- | --- | --- | --- | --- | --- |
| 数据库唯一索引 | 强（同库） | 低 | 需定时清理 | 否 | 兜底、幂等、低并发 | 单点、性能差 |
| 数据库 `FOR UPDATE` | 强（同库） | 低 | 事务结束即释放 | 取决于锁等待 | 与业务同事务的短临界区 | 长事务、锁范围失控 |
| 数据库乐观锁 | 强（单行） | 高 | 无需释放 | 否 | 更新类、冲突低 | 高冲突重试成本 |
| Redis（Redisson） | 弱（异步复制） | 最高 | 过期 + 看门狗 | 可选公平锁 | 绝大多数高并发场景 | 主从切换丢锁 |
| RedLock | 较弱（多数派） | 中 | 过期 | 否 | 单集群故障率不可接受且无兜底 | 争议大、需 5 个独立节点 |
| ZooKeeper（Curator） | 强（ZAB） | 中低 | 会话失效 | 是 | 强一致、需要排队 | 选举期间不可用 |
| etcd | 强（Raft） | 中低 | 租约到期 | 是（前驱） | K8s 生态、需要 fencing | 运维与客户端生态 |

**选型结论**：日常业务用 Redisson + 数据库层兜底；对正确性要求极高（资金、库存核心链路）用 ZooKeeper / etcd，并把 revision / zxid 作为 fencing token；无论选哪种，临界区里的写操作都要幂等。锁的粒度尽量小，热点数据用分段锁而不是一把大锁。

### 5.3 接口幂等设计【重点】

重复请求的来源：用户重复点击、网络超时重试、消息重复投递、第三方回调重发。

| 方案 | 做法 | 适用 |
| --- | --- | --- |
| Token 机制 | 进入页面时先获取一个 token 存入 Redis，提交时带上，服务端用 Lua 「判断存在并删除」，删除成功才处理 | 前端防重复提交 |
| 唯一索引 | 业务唯一键（订单号、支付流水号）建唯一索引，重复插入报错即表示已处理 | 新增类操作，最可靠 |
| 状态机 | 更新时带上前置状态条件 | 状态流转类 |
| 乐观锁 | 更新时校验版本号 | 更新类 |
| 去重表 | 请求 ID 与业务在同一事务内写入 | 通用 |

查询和删除天然幂等；`UPDATE SET x = 5` 幂等，`UPDATE SET x = x + 1` 不幂等。支付类接口必须要求调用方传入幂等号（如商户订单号）。

### 5.4 分布式 Session【了解】

多实例部署后，请求可能落到不同节点，存在服务端内存里的 Session 就不通了。常见方案：

| 方案 | 做法 | 问题 |
| --- | --- | --- |
| 会话保持（粘性） | 网关按 IP / Cookie 哈希固定到同一实例 | 扩容、宕机、灰度时会话丢失，负载不均 |
| Session 复制 | 容器间广播同步 | 节点多时网络与内存开销大，只适合小集群 |
| **集中存储** | Spring Session 把 Session 写入 Redis | 主流方案，需处理序列化与过期 |
| Token / JWT | 服务端不存会话，客户端携带凭证 | 严格说不是 Session，但能替代它，见 Spring 文档 |

**Spring Session + Redis**：`SessionRepositoryFilter` 包装 `HttpServletRequest`，把 `getSession()` 返回的实现替换为 Redis 存储（按 `sessionId` 存 Hash，另有过期索引用于清理）。实操注意：存入的对象要可序列化，多服务共享时优先用 JSON 序列化，避免 JDK 序列化因类版本不一致失败；`spring.session.timeout` 要小于 Redis 键的 TTL；注销时同步删除 Redis 中的会话，否则退出后仍能访问。

**安全**：登录成功后更换 Session ID（防 Session 固定），Cookie 加 `HttpOnly` / `Secure` / `SameSite`；需要限制并发登录时配合 Spring Security 的 `SessionRegistry`。

## 六、链路追踪与可观测性

微服务下一个请求会穿过十几个服务，排障必须依赖可观测性的三大支柱：**日志（Logs）、指标（Metrics）、链路（Traces）**，并用 TraceId 把三者串起来。

### 6.1 链路追踪模型【重点】

- **Trace**：一次完整请求的调用链，由全局唯一的 **TraceId** 标识。
- **Span**：调用链中的一个操作（一次 RPC、一条 SQL），有 SpanId 和父 SpanId，记录开始时间、耗时和标签。所有 Span 按父子关系构成一棵树，一眼就能看出哪一步慢。
- **上下文透传**：跨服务时把 TraceId 和当前 SpanId 放在 HTTP Header（W3C `traceparent` 标准）或 RPC 附件中传递；服务内部存在 ThreadLocal 中。
- **跨线程丢失【重点】**：异步任务、线程池中 ThreadLocal 拿不到 TraceId，需要用 TransmittableThreadLocal 包装线程池，或用链路组件提供的线程池包装器（见并发文档 ThreadLocal 章节）。MQ 场景要把 TraceId 放入消息头。

### 6.2 实现方式【重点】

| 工具 | 特点 |
| --- | --- |
| SkyWalking | **Java Agent + 字节码增强**，无需改代码；自带拓扑图、性能分析和告警，国内使用广泛 |
| OpenTelemetry | CNCF 的可观测性统一标准，提供 API、SDK 和 Java Agent，采集后可以导出到 Jaeger、Tempo、SkyWalking 等后端，是业界的发展方向 |
| Micrometer Tracing | Spring Boot 3 官方链路方案，取代了 Spring Cloud Sleuth |

**SkyWalking 无侵入原理**：启动时加 `-javaagent:skywalking-agent.jar`，利用 `java.lang.instrument` 在类加载时用 ByteBuddy 修改 Spring MVC、Feign、JDBC、Redis 客户端等的字节码，在方法前后插入创建 Span 和透传上下文的代码。

**采样**：全量采集对性能和存储压力大，生产一般按比例采样，但对报错和慢请求全量保留（尾部采样）。

### 6.3 日志与指标【重点】

- **日志**：用 MDC 把 TraceId 打印到每一行日志（Logback pattern 里加 `%X{traceId}`），统一采集到 ELK（Elasticsearch + Logstash / Filebeat + Kibana）或 Loki，按 TraceId 搜索就能看到一次请求在所有服务的日志。
- **指标**：Spring Boot Actuator + Micrometer 暴露指标，Prometheus 拉取、Grafana 展示、Alertmanager 告警。关注「黄金指标」：流量（QPS）、错误率、延迟（P99）、饱和度（CPU、线程池、连接池使用率）。
- **告警原则**：只对影响用户的症状告警（错误率、延迟），而不是对每个原因告警，避免告警疲劳。

## 七、高并发系统设计

高并发设计的总思路是：**让尽量少的请求到达数据库**。每一层都拦截或缓冲一部分流量，最后到达存储的只剩少量必要的写入。这是前面所有文档知识的综合应用。

### 7.1 分层削峰【核心】

| 层次 | 手段 |
| --- | --- |
| 客户端 | 按钮置灰防重复提交、答题 / 验证码打散请求、本地缓存 |
| CDN | 静态资源和静态化的商品详情页 |
| 接入层（Nginx / 网关） | 限流、黑名单、防刷、按用户 / IP 限频 |
| 应用层 | 本地缓存 + Redis 多级缓存、异步化（MQ）、线程池隔离、熔断降级 |
| 数据层 | 读写分离、分库分表、热点数据分段、批量写入 |

**常用指标**：QPS（每秒请求数）、TPS（每秒事务数）、RT（响应时间，看 P99 而不是平均值）、并发数。三者关系（Little 定律）：

```latex
\text{并发数} = \text{QPS} \times \text{平均 RT}
```

例如 QPS 2000、平均 RT 50 ms，则同时处理中的请求约 100 个，这个数字可以用来估算线程池和连接池大小。

### 7.2 秒杀系统设计【核心】

**特点**：瞬时流量是平时的成百上千倍，库存极少，绝大多数请求注定失败。核心问题是：不被流量压垮、不超卖、防刷。

**核心流程**：

1. **前端与接入层拦截**：页面静态化放 CDN；秒杀开始前接口不暴露（动态生成秒杀地址）；网关按用户限频、验证码打散峰值。
2. **库存预热**：活动开始前把库存加载到 Redis。
3. **Redis 预扣库存**：用 Lua 脚本原子地完成「判断是否已购买 + 判断库存 + 扣减 + 记录用户」，库存不足直接返回失败。绝大多数请求在这里结束。可加一个本地「已售罄」标记，售罄后连 Redis 都不访问。
4. **MQ 异步下单**：预扣成功后发消息，由订单服务按自己的能力消费创建订单，前端轮询结果。
5. **数据库扣库存兜底防超卖**：`UPDATE stock SET num = num - 1 WHERE sku_id = ? AND num > 0`，影响行数为 0 即失败。
6. **超时未支付回补库存**：延时消息取消订单并归还 Redis 和数据库库存。

**其他要点**：秒杀服务独立部署，与主站隔离；一人一单用「用户 ID + 商品 ID」唯一索引；单个热点商品的库存可以拆成多份分散到不同的 key，缓解单 key 热点。

### 7.3 容量评估与压测【重点】

1. **估算峰值**：由业务数据推算，如日活 100 万、人均 20 次请求，日请求 2000 万；按「80% 流量集中在 20% 时间」估算峰值 QPS 约 2000 万 × 0.8 ÷（86400 × 0.2）≈ 926，再乘以 2\~3 倍冗余。
2. **压测单机能力**：用 JMeter 或 wrk 压单个实例，得到 RT 不劣化时的最大 QPS。
3. **算出机器数**：峰值 QPS ÷ 单机 QPS，再预留余量。
4. **全链路压测**：在生产环境用影子表 / 压测标记跑真实链路，发现数据库、缓存、MQ 等各环节的瓶颈。

## 八、分布式调度与云原生

### 8.1 分布式调度：XXL-JOB【了解】

**为什么单机 `@Scheduled` 不够**：多实例部署时每个节点都会执行同一任务（重复执行）；没有高可用，节点挂了任务就停；没有执行记录、告警和手动触发；大数据量任务无法拆分并行。

**架构**：调度中心（Admin）+ 执行器（Executor）分离。执行器启动后注册到调度中心并定期心跳；调度中心按 cron 触发，通过 HTTP 调用执行器（执行器内嵌服务端接收请求），执行完成后回调上报结果并写日志。

| 机制 | 说明 |
| --- | --- |
| 路由策略 | 第一个、轮询、随机、一致性哈希、最不经常使用、故障转移、**分片广播** |
| 分片广播 | 调度时把 `shardIndex` / `shardTotal` 下发给每个执行器，各处理自己那一份，适合百万级数据的批量处理 |
| 阻塞处理 | 单机串行、丢弃后续调度、覆盖之前调度，避免任务堆积 |
| 失败重试 | 配置重试次数，失败后按间隔重新调度 |
| 任务类型 | BEAN（调用 Spring Bean 方法）、GLUE（在线编辑脚本） |

**调度中心高可用**：多实例部署，靠数据库行锁（或注册中心抢占）保证同一任务在同一时刻只有一个调度中心触发。

**与 ShedLock 的区别**：ShedLock 只解决「多实例不重复执行」，没有调度编排、分片和可视化；任务规模变大后仍应使用 XXL-JOB 或 ElasticJob。

### 8.2 Service Mesh 与 Istio【了解】

**SDK 模式的问题**：Spring Cloud 这类方案要求每个服务引入治理 SDK，多语言要各实现一套，升级治理逻辑得改代码、改依赖、重新发布。

**Service Mesh 的思路**：把服务发现、负载均衡、超时重试、熔断、mTLS、遥测等能力从业务进程**下沉到 Sidecar 代理**，业务代码只关心业务逻辑。

| 层次 | 组件 | 职责 |
| --- | --- | --- |
| 数据面 | Envoy（每个 Pod 一个 Sidecar） | 劫持进出流量，执行路由、重试、熔断、mTLS 和指标采集 |
| 控制面 | Istiod | Pilot 通过 xDS 下发路由与集群配置；Citadel 签发证书；Galley 校验配置 |

**流量劫持**：Pod 启动时通过 iptables 把入站 / 出站流量重定向到 Sidecar，应用完全无感知。

**能做什么**：金丝雀与灰度发布、流量镜像、故障注入、服务间 mTLS、统一的重试与超时策略、标准化指标（无需改代码）。

**代价**：每次调用多一跳（通常增加 1\~2 ms）、Sidecar 的资源开销、运维与排障复杂度上升，小团队与单体应用没必要引入。

**演进**：传统 Sidecar 模式 → Ambient Mesh（L4 的 ztunnel + 按需的 L7 waypoint），减少每个 Pod 都挂代理的开销。

> SDK 模式（Spring Cloud Alibaba）与 Sidecar 模式（Istio）不是互斥的，选其中一层做治理即可，关键是别在两层重复配置超时和重试。
