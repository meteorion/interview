## 一、分布式理论

理论部分要解决的是一个问题：网络一定会出问题，这时你选择「数据对」还是「服务可用」。

### 1.1 CAP【重点】

- **C（一致性）**：所有节点在同一时刻读到的数据相同（线性一致）。
- **A（可用性）**：每个请求都能在合理时间内得到非错误的响应。
- **P（分区容错）**：节点间网络断开时，系统仍能继续运行。

分布式系统中网络分区无法避免，**P 必须保证**，所以实际是在发生分区时选择 CP 还是 AP：

| 选择 | 发生分区时的行为 | 代表 |
| --- | --- | --- |
| CP | 拒绝请求或等待，保证数据不出错 | ZooKeeper（选举期间不可用）、etcd、Nacos 持久实例 |
| AP | 继续响应，可能返回旧数据，之后再同步 | Eureka、Nacos 临时实例（默认）、Redis Cluster |

**注册中心为什么更适合 AP**：服务列表短暂不一致只会导致少量请求失败（可以重试），而注册中心不可用会让所有服务无法发现彼此。而分布式锁、选主等场景必须保证正确，应选 CP。

### 1.2 BASE【重点】

BASE 是对 AP 的延伸，是互联网系统的实际做法：

- **BA（基本可用）**：出故障时允许损失部分功能或性能，如降级、响应变慢。
- **S（软状态）**：允许存在中间状态，如订单「支付中」。
- **E（最终一致）**：经过一段时间后数据达到一致。前面所有文档中的缓存双写、主从复制、MQ 异步处理，都是最终一致。

### 1.3 一致性协议：Raft 与 ZAB【重点】

**Raft**（etcd、Nacos CP、Kafka KRaft、Redis 哨兵选 leader 都借鉴了它）把问题拆成三部分：

1. **Leader 选举**：节点分 Leader、Follower、Candidate。Follower 在随机的选举超时时间内收不到 Leader 心跳，就把任期（term）加 1、成为 Candidate 并拉票，得到**超过半数**的票就成为 Leader。随机超时是为了避免同时发起选举导致分票。
2. **日志复制**：写请求只发给 Leader，Leader 把日志复制给 Follower，**超过半数**节点写入后即为已提交，再应用到状态机。
3. **安全性**：只有日志至少和大多数节点一样新的 Candidate 才能当选，保证已提交的日志不丢失。

**为什么集群节点数用奇数**：「超过半数」规则下，3 节点和 4 节点都只能容忍 1 个节点故障，多一台反而增加成本。半数机制也天然防止了脑裂：网络分成两半时只有一边能凑够半数。

**ZAB**（ZooKeeper 的协议）思想与 Raft 类似，分为**崩溃恢复**（选出日志最新的 Leader 并同步数据）和**消息广播**（类似两阶段提交：发 Proposal，超过半数 ACK 后发 Commit）两个阶段。Paxos 是更早、更通用的理论算法，但难以理解和工程实现，Raft 就是为易理解而设计的。

### 1.4 ZooKeeper【重点】

- **数据模型**：树形的 ZNode，类型有持久、临时（会话结束自动删除）、顺序（创建时自动加递增编号）以及它们的组合。
- **Watch**：监听节点变化，触发后失效（一次性），需要重新注册；3.6 起支持持久递归 Watch。
- **典型应用**：分布式锁（临时顺序节点 + 监听前一个节点）、选主、配置中心、服务注册（Dubbo 早期、Kafka 早期）。

## 二、微服务架构与组件

微服务把单体按业务能力拆成可以独立开发、部署和扩展的小服务。它解决的是团队和业务规模变大后的协作问题，代价是引入了分布式系统的全部复杂度（组件全景见下图）。

&#91;embedded content: 微服务组件全景 · Spring Cloud Alibaba\]

每个服务只访问自己的数据库；订单服务同步调用库存服务扣减库存，再通过 MQ 通知积分、物流等下游。

### 2.1 单体与微服务【核心】

| 维度 | 单体 | 微服务 |
| --- | --- | --- |
| 开发部署 | 简单，一次打包部署 | 各服务独立发布，需要 CI/CD 与容器化支撑 |
| 扩展 | 只能整体扩容 | 按服务单独扩容热点服务 |
| 故障隔离 | 一处内存泄漏拖垮整个应用 | 故障限制在单个服务（需要熔断隔离配合） |
| 技术栈 | 统一 | 可以异构 |
| 一致性 | 本地事务即可 | 需要分布式事务或最终一致 |
| 排障 | 一个进程的日志 | 跨服务调用链，需要链路追踪 |

小团队、业务初期用单体（或模块化单体）往往更合适。

**拆分原则【核心】**：按业务边界拆（DDD 的限界上下文），而不是按技术分层拆；高内聚、低耦合，一个需求尽量只改一个服务；**每个服务拥有自己的数据库**，禁止跨服务直接访问对方的表；粒度与团队规模匹配，避免拆得太细导致大量跨服务调用和分布式事务。

### 2.2 注册中心与配置中心：Nacos【重点】

**服务注册发现**：服务启动时注册地址，定时发送心跳；调用方拉取并**缓存**服务列表，列表变化时由服务端推送。即使注册中心全部宕机，已有的调用仍能靠本地缓存继续。

- **临时实例（默认）**：靠客户端心跳保活，超时自动剔除，用 Distro 协议（AP）。
- **持久实例**：由服务端主动探测健康状态，不健康也不删除，用 Raft（CP）。
- Nacos 2.x 把客户端与服务端的通信从 HTTP 短连接 + 心跳改为 gRPC 长连接，性能和推送及时性大幅提升。

**配置中心**：用「命名空间（环境）+ Group（项目）+ DataId（配置文件）」三级隔离。动态刷新靠长轮询（1.x）或 gRPC 推送（2.x），客户端用 `@RefreshScope` 或 `@ConfigurationProperties` 让 Bean 拿到新值。

**对比【重点】**：Eureka 只做注册、AP、已停止迭代；ZooKeeper 是 CP、选举期间不可用；Nacos 同时支持 AP / CP，并兼作配置中心，是国内主流选择。

### 2.3 API 网关：Spring Cloud Gateway【重点】

网关是所有外部请求的统一入口，负责**路由、鉴权、限流、日志、灰度**等通用能力，让业务服务不必重复实现。

- **三大概念**：Route（路由，目标服务）、Predicate（断言，匹配条件，如 `Path=/order/**`）、Filter（过滤器，转发前后的处理）。
- **全局过滤器**（GlobalFilter）作用于所有路由，常用于统一鉴权：解析 Token，把用户 ID 放入请求头传给下游。
- **基于 WebFlux + Netty 的非阻塞模型**：少量线程处理大量连接，所以**过滤器中绝对不能有阻塞操作**（同步查库、同步 HTTP 调用），否则整个网关吞吐会崩溃。
- **与 Nginx 的分工**：Nginx 作为流量入口做负载均衡、SSL 终止、静态资源；Gateway 在其后做业务级路由和鉴权。

### 2.4 服务调用：OpenFeign 与 RPC【重点】

**OpenFeign**：声明式 HTTP 客户端。`@FeignClient` 接口在启动时被注册为 FactoryBean，用 **JDK 动态代理**生成实现，调用时把方法上的注解解析成 HTTP 请求，由 LoadBalancer 从注册中心选一个实例发送。实践要点：配置连接和读取超时；用 `RequestInterceptor` 透传 Token、TraceId；把默认的 `HttpURLConnection` 替换为带连接池的 OkHttp / Apache HttpClient。

**RPC 调用流程【核心】**：客户端调用本地代理 → 序列化请求 → 从注册中心获取地址并负载均衡 → 网络传输（Netty）→ 服务端反序列化 → 反射调用实现类 → 序列化结果返回。

| 维度 | Feign（HTTP + JSON） | Dubbo | gRPC |
| --- | --- | --- | --- |
| 协议 | HTTP/1.1 | 自定义 TCP 协议；Dubbo 3 的 Triple 兼容 gRPC | HTTP/2，支持双向流 |
| 序列化 | JSON，可读性好、体积大 | Hessian2 等二进制 | Protobuf，体积小、跨语言 |
| 性能 | 一般 | 高 | 高 |
| 适用 | Spring Cloud 体系、对外接口 | Java 内部高性能调用，治理功能丰富 | 多语言、云原生 |

**Dubbo 集群容错【重点】**：Failover（失败自动重试其他服务器，默认，适合读）、Failfast（快速失败，适合非幂等写）、Failsafe（忽略异常，适合日志）、Failback（后台定时重发）、Forking（并行调用多个，一个成功即返回）。

**Dubbo SPI 与 Java SPI【重点】**：Java SPI 一次加载并实例化所有实现，不能按名称获取；Dubbo SPI 用「key=实现类」配置，按需加载、支持 IOC / AOP 和自适应扩展。

## 三、服务治理：限流、熔断、降级

治理的目标是防止**雪崩**：一个下游服务变慢，调用方的线程都卡在等待上，线程池耗尽后调用方也不可用，故障沿调用链向上蔓延。防护手段是：超时、限流、熔断、降级、隔离。

### 3.1 限流算法【核心】

| 算法 | 做法 | 优缺点 |
| --- | --- | --- |
| 固定窗口计数器 | 每个时间窗口计数，超过阈值拒绝 | 简单；**临界问题**：窗口交界处短时间内可通过 2 倍流量 |
| 滑动窗口 | 把窗口分成多个小格，统计最近一个完整窗口内的总和 | 解决临界问题，格子越多越精确；Sentinel 的统计就是这种 |
| 漏桶 | 请求进桶，以固定速率流出处理，桶满拒绝 | 输出流量绝对平滑；不允许突发 |
| 令牌桶 | 以固定速率向桶里放令牌，请求拿到令牌才能处理 | 允许一定突发（桶里积累的令牌），最常用；Guava `RateLimiter` 是它的变体 |

**限流在哪里做**：网关层做全局限流（Redis + Lua 实现分布式令牌桶）；服务层用 Sentinel 做接口级限流；单机可用 Guava 或信号量。

### 3.2 熔断【核心】

当下游的失败率或慢调用比例达到阈值时，调用方**直接返回降级结果**，不再发起调用，给下游恢复的时间，同时保护自己的线程池。

**熔断器三种状态**：

1. **关闭（Closed）**：正常调用，统计失败率。
2. **打开（Open）**：触发阈值后进入，所有请求直接走降级；经过熔断时长后进入半开。
3. **半开（Half-Open）**：放行少量探测请求，成功则回到关闭，失败则重新打开。

&#91;embedded content: 熔断器状态机 · 3 种状态\]

**Sentinel 熔断策略**：慢调用比例（响应时间超过阈值的请求占比）、异常比例、异常数。

### 3.3 降级【核心】

降级是「有损服务」：在资源不足或依赖故障时，关闭或简化非核心功能，保证核心链路。

- **被动降级**：熔断或异常时走 fallback，返回默认值、缓存值或友好提示（如推荐服务挂了就展示热门商品）。
- **主动降级**：大促前通过开关关闭评论、积分、实时推荐等功能，把资源让给下单和支付。

**三者关系**：限流是保护自己不被流量压垮；熔断是不被下游拖垮；降级是两者发生后的处理方式。

### 3.4 超时与重试【核心】

- **必须设超时**：没有超时的调用是雪崩的根源。超时时间参考下游 P99 耗时，且**越靠近入口超时越长**（网关 > 上游 > 下游），避免下游还在处理上游已超时放弃。
- **重试只用于幂等接口**：写接口重试可能导致重复下单、重复扣款。Feign 默认不重试，Dubbo 默认 Failover 重试 2 次，写操作要改为 Failfast 或保证幂等。
- **避免重试风暴**：多层都重试会把流量成倍放大（3 层各重试 3 次就是 27 倍）。只在一层重试，用指数退避 + 随机抖动，并设置重试预算。

### 3.5 负载均衡与隔离【重点】

**负载均衡算法**：轮询、加权轮询、随机、最少活跃调用（优先发给正在处理请求最少的实例，适合响应时间差异大的场景）、一致性哈希（同一参数总发到同一实例，适合有本地缓存的服务；用虚拟节点解决分布不均）。

**隔离**：线程池隔离（不同下游用不同线程池）、信号量隔离（Sentinel 的并发线程数限流）、服务部署隔离（核心与非核心服务分开部署）。

### 3.6 发布策略【了解】

- **蓝绿发布**：两套完整环境，切换流量，回滚快但资源翻倍。
- **灰度（金丝雀）发布**：先把少量流量（按比例、按用户 ID、按地区）导向新版本，观察指标后逐步放量。全链路灰度需要在网关打标签，并在调用链上透传。
- **滚动发布**：逐批替换实例，K8s 默认方式。

## 四、分布式事务

拆分后一个业务操作要修改多个服务的数据库（如下单扣库存、扣余额），本地事务无法保证一致。方案分为两类：强一致的刚性事务（2PC / XA），和最终一致的柔性事务（TCC、Saga、可靠消息）。**互联网业务绝大多数采用柔性事务**。

### 4.1 方案对比【核心】

| 方案 | 一致性 | 性能 | 业务侵入 | 适用场景 |
| --- | --- | --- | --- | --- |
| 2PC / XA | 强一致 | 低，全程持锁 | 低 | 短事务、并发低、强一致的内部系统 |
| Seata AT | 最终一致（有全局锁） | 较高 | 几乎无，加注解即可 | 快速上手的通用业务 |
| TCC | 最终一致 | 高 | 高，每个操作写三个方法 | 资金、库存等高一致、高性能场景 |
| Saga | 最终一致 | 高 | 中，要写补偿 | 长流程、跨系统（旅行预订、审批） |
| 可靠消息（本地消息表 / 事务消息） | 最终一致 | 高 | 中 | 上游成功后下游「一定要做」、可异步的场景 |
| 最大努力通知 | 最终一致 | 高 | 低 | 跨公司的结果通知，配合对账 |

### 4.2 2PC 与 3PC【重点】

**2PC**：协调者先发 **Prepare**，各参与者执行事务但不提交（持有锁）并投票；全部同意则发 **Commit**，否则发 **Rollback**。

问题：**同步阻塞**（参与者全程持锁等待）、**协调者单点**（发完 Prepare 后宕机，参与者一直锁着）、**数据不一致**（Commit 只发到了部分参与者就宕机）。

**3PC** 在 2PC 前加了 CanCommit 询问阶段，并引入超时自动提交，缓解了阻塞，但仍可能不一致，工程上很少使用。

### 4.3 Seata AT 模式【核心】

**三个角色**：TC（事务协调者，独立部署的 Seata Server）、TM（事务管理器，发起全局事务的一方，即加了 `@GlobalTransactional` 的服务）、RM（资源管理器，各参与方的数据源代理）。全局事务 ID（XID）随调用链透传。

**一阶段**：RM 解析 SQL，查出修改前的数据（before image），执行业务 SQL，再查出修改后的数据（after image），把两者写入 `undo_log` 表，**与业务数据在同一个本地事务中提交**。提交前向 TC 申请该行的**全局锁**。本地锁提交后就释放了，所以性能比 XA 高。

**二阶段**：全部成功 → TC 通知 RM 异步删除 undo\_log，释放全局锁；任一失败 → RM 用 before image 生成反向 SQL 回滚（回滚前校验当前数据与 after image 一致，不一致说明被全局事务外的操作改过，需要人工处理）。

**局限**：只支持有本地 ACID 事务的关系型数据库；全局锁在高并发热点行上会成为瓶颈；默认是「读未提交」隔离级别，需要读已提交时要用 `SELECT ... FOR UPDATE`。

### 4.4 TCC【重点】

把一个操作拆成三个方法，以扣余额为例：

- **Try**：检查并**预留资源**（余额 100 → 可用 70、冻结 30）。
- **Confirm**：真正执行，使用预留的资源（冻结 30 清零）。
- **Cancel**：释放预留的资源（冻结 30 加回可用）。

Try 全部成功则对所有参与者调用 Confirm，否则调用 Cancel。Confirm / Cancel 失败会被不断重试。

**三大问题【重点】**：

| 问题 | 场景 | 解决 |
| --- | --- | --- |
| 幂等 | Confirm / Cancel 会被重试 | 用事务控制表记录每个分支事务的状态 |
| 空回滚 | Try 因网络超时未执行，却收到了 Cancel | Cancel 时发现没有 Try 记录，就插入一条「已回滚」记录后直接返回成功 |
| 悬挂 | Cancel 先执行完，延迟到达的 Try 才执行，资源被冻结且永远不会释放 | Try 执行前检查，如果已有「已回滚」记录就拒绝执行 |

### 4.5 Saga【了解】

把长事务拆成多个本地事务 T1…Tn，每个都有对应的补偿操作 C1…Cn。任一步失败，就按反序执行已完成步骤的补偿。没有预留阶段，每步直接提交，所以**不保证隔离性**（其他事务可能看到中间状态）。编排方式有协同式（服务间发事件）和编排式（中心协调器按状态机执行，Seata Saga 是这种）。

### 4.6 可靠消息方案【核心】

详见消息队列文档的事务消息与本地消息表。要点：上游用「本地事务 + 消息」的原子性保证消息一定发出，下游用「重试 + 幂等」保证一定执行成功。前提是**下游业务上不会失败**（只会暂时失败）；如果下游可能「余额不足」这样的业务失败并需要上游回滚，就应该用 TCC 或 Saga。

**选型经验**：能不用分布式事务就不用（通过合理的服务划分让强一致的数据留在同一个服务内）；能异步就用可靠消息；资金类用 TCC；长流程用 Saga；想快速落地用 Seata AT。

## 五、分布式 ID、分布式锁与幂等

这三个是分布式系统里最常用的基础设施，也是前面各章方案的前提：分库分表需要全局 ID，并发修改需要锁，重试和消息需要幂等。

### 5.1 分布式 ID【重点】

**要求**：全局唯一、趋势递增（对 B+ 树友好）、高可用、高性能，最好不暴露业务量。

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| UUID | 本地生成，简单 | 36 字符太长、无序，做主键会频繁页分裂 |
| 数据库自增 | 简单、有序 | 单点、性能瓶颈；多库可用不同步长但难扩展 |
| 号段模式 | 每次从数据库取一段（如 1000 个）在内存分配，数据库压力小 | 服务重启会浪费号段；号段用完时的取数会有延迟尖刺 |
| Redis INCR | 性能高、有序 | 依赖 Redis 的持久化，宕机可能重复 |
| **雪花算法** | 本地生成、性能高、趋势递增、BIGINT | 依赖机器时钟；workerId 需要分配 |

**雪花算法结构**：1 位符号位（固定 0）+ 41 位毫秒时间戳（约 69 年）+ 10 位机器 ID（1024 台）+ 12 位序列号（每毫秒 4096 个）。

**时钟回拨【重点】**：NTP 校时可能让时间倒退，导致生成重复 ID。处理：回拨很小（如 5 ms 内）就等待时间追上；回拨较大就报错并告警，或切换到备用 workerId；也可以不依赖实时时钟，用上次时间戳自增（如百度 UidGenerator 的做法）。

**美团 Leaf【重点】**：同时提供号段和雪花两种模式。号段模式用**双 buffer**：当前号段用到 10% 时就异步加载下一段，切换时无等待；雪花模式用 ZooKeeper 自动分配 workerId 并检测时钟回拨。容器环境下实例频繁起停，workerId 不能写死在配置里，需要由注册中心或 Redis 分配。

### 5.2 分布式锁【核心】

Redis 实现（SET NX PX、Lua 解锁、Redisson 看门狗、RedLock 争议）详见 Redis 文档第七章。这里补充其他实现与选型。

| 实现 | 原理 | 特点 |
| --- | --- | --- |
| Redis（Redisson） | SET NX + 过期时间 + 看门狗 | AP，性能高；主从切换可能丢锁 |
| ZooKeeper（Curator） | 创建**临时顺序节点**，序号最小的获得锁；其他节点只监听前一个节点（避免惊群）；客户端宕机会话结束，临时节点自动删除 | CP，可靠性高，天然公平；性能低于 Redis |
| 数据库 | 唯一索引插入一行表示加锁；或 `SELECT ... FOR UPDATE`；或乐观锁版本号 | 简单，性能差，适合低并发 |

**Fencing Token【重点】**：任何带过期时间的锁都可能在持有者 GC 停顿时过期，导致两个客户端都以为自己持有锁。解决方式是加锁时返回一个单调递增的 token，写存储时带上，存储端拒绝比已见过的 token 小的写入。实际工程中常用数据库乐观锁或唯一索引做最后一道防线。

**选型**：绝大多数场景用 Redisson + 数据库层兜底；对正确性要求极高用 ZooKeeper / etcd。锁的粒度要尽量小（锁到商品 ID，而不是锁整个接口），热点库存可以拆成多个分段分别加锁。

### 5.3 接口幂等设计【重点】

重复请求的来源：用户重复点击、网络超时重试、消息重复投递、第三方回调重发。

| 方案 | 做法 | 适用 |
| --- | --- | --- |
| Token 机制 | 进入页面时先获取一个 token 存入 Redis，提交时带上，服务端用 Lua 「判断存在并删除」，删除成功才处理 | 前端防重复提交 |
| 唯一索引 | 业务唯一键（订单号、支付流水号）建唯一索引，重复插入报错即表示已处理 | 新增类操作，最可靠 |
| 状态机 | 更新时带上前置状态条件 | 状态流转类 |
| 乐观锁 | 更新时校验版本号 | 更新类 |
| 去重表 | 请求 ID 与业务在同一事务内写入 | 通用 |

查询和删除天然幂等；`UPDATE SET x = 5` 幂等，`UPDATE SET x = x + 1` 不幂等。支付类接口必须要求调用方传入幂等号（如商户订单号）。

### 5.4 分布式 Session【了解】

多实例部署后，请求可能落到不同节点，存在服务端内存里的 Session 就不通了。常见方案：

| 方案 | 做法 | 问题 |
| --- | --- | --- |
| 会话保持（粘性） | 网关按 IP / Cookie 哈希固定到同一实例 | 扩容、宕机、灰度时会话丢失，负载不均 |
| Session 复制 | 容器间广播同步 | 节点多时网络与内存开销大，只适合小集群 |
| **集中存储** | Spring Session 把 Session 写入 Redis | 主流方案，需处理序列化与过期 |
| Token / JWT | 服务端不存会话，客户端携带凭证 | 严格说不是 Session，但能替代它，见 Spring 文档 |

**Spring Session + Redis**：`SessionRepositoryFilter` 包装 `HttpServletRequest`，把 `getSession()` 返回的实现替换为 Redis 存储（按 `sessionId` 存 Hash，另有过期索引用于清理）。实操注意：存入的对象要可序列化，多服务共享时优先用 JSON 序列化，避免 JDK 序列化因类版本不一致失败；`spring.session.timeout` 要小于 Redis 键的 TTL；注销时同步删除 Redis 中的会话，否则退出后仍能访问。

**安全**：登录成功后更换 Session ID（防 Session 固定），Cookie 加 `HttpOnly` / `Secure` / `SameSite`；需要限制并发登录时配合 Spring Security 的 `SessionRegistry`。

## 六、链路追踪与可观测性

微服务下一个请求会穿过十几个服务，排障必须依赖可观测性的三大支柱：**日志（Logs）、指标（Metrics）、链路（Traces）**，并用 TraceId 把三者串起来。

### 6.1 链路追踪模型【重点】

- **Trace**：一次完整请求的调用链，由全局唯一的 **TraceId** 标识。
- **Span**：调用链中的一个操作（一次 RPC、一条 SQL），有 SpanId 和父 SpanId，记录开始时间、耗时和标签。所有 Span 按父子关系构成一棵树，一眼就能看出哪一步慢。
- **上下文透传**：跨服务时把 TraceId 和当前 SpanId 放在 HTTP Header（W3C `traceparent` 标准）或 RPC 附件中传递；服务内部存在 ThreadLocal 中。
- **跨线程丢失【重点】**：异步任务、线程池中 ThreadLocal 拿不到 TraceId，需要用 TransmittableThreadLocal 包装线程池，或用链路组件提供的线程池包装器（见并发文档 ThreadLocal 章节）。MQ 场景要把 TraceId 放入消息头。

### 6.2 实现方式【重点】

| 工具 | 特点 |
| --- | --- |
| SkyWalking | **Java Agent + 字节码增强**，无需改代码；自带拓扑图、性能分析和告警，国内使用广泛 |
| OpenTelemetry | CNCF 的可观测性统一标准，提供 API、SDK 和 Java Agent，采集后可以导出到 Jaeger、Tempo、SkyWalking 等后端，是业界的发展方向 |
| Micrometer Tracing | Spring Boot 3 官方链路方案，取代了 Spring Cloud Sleuth |

**SkyWalking 无侵入原理**：启动时加 `-javaagent:skywalking-agent.jar`，利用 `java.lang.instrument` 在类加载时用 ByteBuddy 修改 Spring MVC、Feign、JDBC、Redis 客户端等的字节码，在方法前后插入创建 Span 和透传上下文的代码。

**采样**：全量采集对性能和存储压力大，生产一般按比例采样，但对报错和慢请求全量保留（尾部采样）。

### 6.3 日志与指标【重点】

- **日志**：用 MDC 把 TraceId 打印到每一行日志（Logback pattern 里加 `%X{traceId}`），统一采集到 ELK（Elasticsearch + Logstash / Filebeat + Kibana）或 Loki，按 TraceId 搜索就能看到一次请求在所有服务的日志。
- **指标**：Spring Boot Actuator + Micrometer 暴露指标，Prometheus 拉取、Grafana 展示、Alertmanager 告警。关注「黄金指标」：流量（QPS）、错误率、延迟（P99）、饱和度（CPU、线程池、连接池使用率）。
- **告警原则**：只对影响用户的症状告警（错误率、延迟），而不是对每个原因告警，避免告警疲劳。

## 七、高并发系统设计

高并发设计的总思路是：**让尽量少的请求到达数据库**。每一层都拦截或缓冲一部分流量，最后到达存储的只剩少量必要的写入。这是前面所有文档知识的综合应用。

### 7.1 分层削峰【核心】

| 层次 | 手段 |
| --- | --- |
| 客户端 | 按钮置灰防重复提交、答题 / 验证码打散请求、本地缓存 |
| CDN | 静态资源和静态化的商品详情页 |
| 接入层（Nginx / 网关） | 限流、黑名单、防刷、按用户 / IP 限频 |
| 应用层 | 本地缓存 + Redis 多级缓存、异步化（MQ）、线程池隔离、熔断降级 |
| 数据层 | 读写分离、分库分表、热点数据分段、批量写入 |

**常用指标**：QPS（每秒请求数）、TPS（每秒事务数）、RT（响应时间，看 P99 而不是平均值）、并发数。三者关系（Little 定律）：

```latex
\text{并发数} = \text{QPS} \times \text{平均 RT}
```

例如 QPS 2000、平均 RT 50 ms，则同时处理中的请求约 100 个，这个数字可以用来估算线程池和连接池大小。

### 7.2 秒杀系统设计【核心】

**特点**：瞬时流量是平时的成百上千倍，库存极少，绝大多数请求注定失败。核心问题是：不被流量压垮、不超卖、防刷。

**核心流程**：

1. **前端与接入层拦截**：页面静态化放 CDN；秒杀开始前接口不暴露（动态生成秒杀地址）；网关按用户限频、验证码打散峰值。
2. **库存预热**：活动开始前把库存加载到 Redis。
3. **Redis 预扣库存**：用 Lua 脚本原子地完成「判断是否已购买 + 判断库存 + 扣减 + 记录用户」，库存不足直接返回失败。绝大多数请求在这里结束。可加一个本地「已售罄」标记，售罄后连 Redis 都不访问。
4. **MQ 异步下单**：预扣成功后发消息，由订单服务按自己的能力消费创建订单，前端轮询结果。
5. **数据库扣库存兜底防超卖**：`UPDATE stock SET num = num - 1 WHERE sku_id = ? AND num > 0`，影响行数为 0 即失败。
6. **超时未支付回补库存**：延时消息取消订单并归还 Redis 和数据库库存。

**其他要点**：秒杀服务独立部署，与主站隔离；一人一单用「用户 ID + 商品 ID」唯一索引；单个热点商品的库存可以拆成多份分散到不同的 key，缓解单 key 热点。

### 7.3 容量评估与压测【重点】

1. **估算峰值**：由业务数据推算，如日活 100 万、人均 20 次请求，日请求 2000 万；按「80% 流量集中在 20% 时间」估算峰值 QPS 约 2000 万 × 0.8 ÷（86400 × 0.2）≈ 926，再乘以 2\~3 倍冗余。
2. **压测单机能力**：用 JMeter 或 wrk 压单个实例，得到 RT 不劣化时的最大 QPS。
3. **算出机器数**：峰值 QPS ÷ 单机 QPS，再预留余量。
4. **全链路压测**：在生产环境用影子表 / 压测标记跑真实链路，发现数据库、缓存、MQ 等各环节的瓶颈。

## 八、分布式调度与云原生

### 8.1 分布式调度：XXL-JOB【了解】

**为什么单机 `@Scheduled` 不够**：多实例部署时每个节点都会执行同一任务（重复执行）；没有高可用，节点挂了任务就停；没有执行记录、告警和手动触发；大数据量任务无法拆分并行。

**架构**：调度中心（Admin）+ 执行器（Executor）分离。执行器启动后注册到调度中心并定期心跳；调度中心按 cron 触发，通过 HTTP 调用执行器（执行器内嵌服务端接收请求），执行完成后回调上报结果并写日志。

| 机制 | 说明 |
| --- | --- |
| 路由策略 | 第一个、轮询、随机、一致性哈希、最不经常使用、故障转移、**分片广播** |
| 分片广播 | 调度时把 `shardIndex` / `shardTotal` 下发给每个执行器，各处理自己那一份，适合百万级数据的批量处理 |
| 阻塞处理 | 单机串行、丢弃后续调度、覆盖之前调度，避免任务堆积 |
| 失败重试 | 配置重试次数，失败后按间隔重新调度 |
| 任务类型 | BEAN（调用 Spring Bean 方法）、GLUE（在线编辑脚本） |

**调度中心高可用**：多实例部署，靠数据库行锁（或注册中心抢占）保证同一任务在同一时刻只有一个调度中心触发。

**与 ShedLock 的区别**：ShedLock 只解决「多实例不重复执行」，没有调度编排、分片和可视化；任务规模变大后仍应使用 XXL-JOB 或 ElasticJob。

### 8.2 Service Mesh 与 Istio【了解】

**SDK 模式的问题**：Spring Cloud 这类方案要求每个服务引入治理 SDK，多语言要各实现一套，升级治理逻辑得改代码、改依赖、重新发布。

**Service Mesh 的思路**：把服务发现、负载均衡、超时重试、熔断、mTLS、遥测等能力从业务进程**下沉到 Sidecar 代理**，业务代码只关心业务逻辑。

| 层次 | 组件 | 职责 |
| --- | --- | --- |
| 数据面 | Envoy（每个 Pod 一个 Sidecar） | 劫持进出流量，执行路由、重试、熔断、mTLS 和指标采集 |
| 控制面 | Istiod | Pilot 通过 xDS 下发路由与集群配置；Citadel 签发证书；Galley 校验配置 |

**流量劫持**：Pod 启动时通过 iptables 把入站 / 出站流量重定向到 Sidecar，应用完全无感知。

**能做什么**：金丝雀与灰度发布、流量镜像、故障注入、服务间 mTLS、统一的重试与超时策略、标准化指标（无需改代码）。

**代价**：每次调用多一跳（通常增加 1\~2 ms）、Sidecar 的资源开销、运维与排障复杂度上升，小团队与单体应用没必要引入。

**演进**：传统 Sidecar 模式 → Ambient Mesh（L4 的 ztunnel + 按需的 L7 waypoint），减少每个 Pod 都挂代理的开销。

> SDK 模式（Spring Cloud Alibaba）与 Sidecar 模式（Istio）不是互斥的，选其中一层做治理即可，关键是别在两层重复配置超时和重试。
