# Java 开发工程师面试重点

按章节整理为“考点—延伸—对比”的复习笔记：先看考点自测，再看延伸补边界，最后用对比表复述差异。版本差异以项目使用的 JDK/组件为准。

## 一、Java 基础

### （一）类型、对象与参数传递

1. **基本类型与包装类型**
   - **考点**：8 种基本类型（boolean、byte、short、char、int、long、float、double）存值，包装类是不可变对象。自动装箱走 `Integer.valueOf()`，拆箱走 `intValue()`；`Integer` 缓存 -128~127（上界可用 `-XX:AutoBoxCacheMax` 调整），`Long/Short/Byte` 固定 -128~127，`Character` 0~127，`Boolean` 只有两个常量。
   - **边界**：`Integer a = 127, b = 127` 时 `a == b` 为 true，128 为 false；包装类与基本类型比较会拆箱；null 拆箱直接 NPE；`equals` 比较值但类型必须一致，`Integer(1).equals(Long(1))` 为 false。
   - **重载**：重载解析分三阶段——不装箱的宽化 → 装箱/拆箱 → 可变参数；`f(int)` 与 `f(Integer)` 同时存在时，传 int 选前者，传 `null` 可能歧义。
   - **延伸**：集合和泛型只能用包装类；金额用 `BigDecimal` 或整数分，不用 float/double；包装类的可空语义要和业务默认值区分。

2. **值传递**
   - **考点**：Java 只有值传递。基本类型传数值；对象传“引用的副本”，方法内重新赋值不影响调用方，但通过引用修改对象内容会生效，数组同理。
   - **延伸**：`swap(a, b)` 交换不了调用方的引用，只能返回新对象或放进 Holder；`String` 不可变，所以方法内“修改”只是换了局部引用。
   - **面试落点**：画内存图说明实参和形参是两个变量，指向同一个堆对象，避免把“引用传递”和“值传递”混为一谈。

3. **重载、重写与面向对象设计**
   - **考点**：重载是编译期静态绑定（参数列表不同）；重写是运行期动态绑定（签名相同、返回类型可协变、异常不能更宽、访问不能更严）。`private/static/final` 方法不能重写，构造器不能重写。
   - **抽象类 vs 接口**：抽象类可有状态、构造器、单继承；接口可有 `default/static/private` 方法、常量、多实现。JDK 8 的 default 方法解决接口演进，JDK 9 的 private 方法做接口内复用。
   - **组合 vs 继承**：继承强耦合、破坏封装；组合用委托，优先组合，只有真符合 `is-a` 才继承。
   - **修饰符**：`static` 属于类、类加载时初始化，用于工具方法/常量/内部类；`final` 类不可继承、方法不可重写、字段引用不可变；访问修饰符从宽到严为 `public → protected → 包 → private`。初始化顺序：父类静态 → 子类静态 → 父类实例 → 子类实例 → 构造器。
   - **延伸**：`final` 字段配合安全发布（JMM）；`static` 方法不能访问实例成员；接口字段隐式 `public static final`。

### （二）Object 契约、字符串与不可变

1. **equals 与 hashCode**
   - **考点**：契约是自反、对称、传递、一致、非 null 返回 false；相等对象 hashCode 必须相同，不等对象可以相同。重写 `equals` 必须同时重写 `hashCode`，否则 HashMap/HashSet 会找不到。
   - **实现**：先 `==`，再 `getClass()` 或 `instanceof`，再逐字段比较；可变字段参与 hashCode 会导致对象放入集合后“丢失”；用 `Objects.equals/hash` 处理 null。
   - **延伸**：`getClass` 与 `instanceof` 的选择影响子类相等语义；`record` 自动生成 `equals/hashCode/toString`；`equals` 与 `compareTo` 应保持一致，否则 TreeMap/TreeSet 行为怪异。
   - **面试落点**：以 HashMap 的 get 为例，hash 不同直接不同桶，hash 相同但 equals 不等则继续在链表/红黑树中查找。

2. **String 不可变、常量池与 intern**
   - **考点**：String 用 final 修饰的字符数组（JDK 9 起改为 `byte[] + coder` 压缩存储），不可变带来线程安全、可缓存 hash、常量池复用和参数安全；`+` 在编译期常量可折叠，循环拼接会生成大量对象（JDK 9 起用 invokedynamic 优化，但仍不宜在循环里用 `+`）。
   - **常量池**：字面量进入 Class 文件常量池，运行时常量池；`intern()` 在 JDK 7+ 把字符串放入堆中的字符串常量池（不再复制到永久代），返回池中引用；`new String("a")` 可能创建堆对象和池中对象两个。
   - **Builder/Buffer**：StringBuilder 非线程安全，单线程拼接首选；StringBuffer 方法 synchronized，只有多线程共享同一缓冲区才用；JDK 9 后两者底层也是 byte[] + coder。
   - **延伸**：不可变是安全基础（SQL、路径、类加载），但反射仍可能破坏封装；批量拼接用 `String.join`、`Collectors.joining` 或预分配容量。

3. **Object 其他方法**
   - **考点**：`toString` 用于日志与调试；`clone` 是浅拷贝，需实现 `Cloneable`，推荐用拷贝构造器替代；`finalize` 不可靠，JDK 9 起不推荐、JDK 18 可关闭，资源释放用 try-with-resources 或 `Cleaner`。
   - **延伸**：`wait/notify/notifyAll` 定义在 Object 上，必须在 synchronized 块内调用；`getClass` 是 final native；`Objects` 是空安全的工具类。

### （三）异常与资源管理

1. **异常体系与处理策略**
   - **考点**：`Throwable` 分 `Error` 和 `Exception`；`Exception` 又分受检异常和 `RuntimeException` 非受检异常。`Error`（OOM、StackOverflowError）通常不捕获；受检异常强制处理，非受检异常多为编程错误。
   - **处理原则**：捕获具体异常，不要空 catch 吞掉；跨层封装时保留 cause；业务异常自定义并配错误码；日志只打一次，避免上层重复打印；异常栈有成本，不要用异常做流程控制。
   - **边界**：`finally` 一定执行（除 `System.exit`、JVM 崩溃）；在 `finally` 中 return 会覆盖原异常；`try` 中 return 后 `finally` 仍会执行。

2. **try-with-resources 与 AutoCloseable**
   - **考点**：编译器把它展开为 try/finally，按资源声明的逆序调用 `close()`；`AutoCloseable.close()` 可抛 `Exception`，`Closeable` 只能抛 `IOException`；JDK 9 起可把已有且 effectively final 的变量放进 try。
   - **延伸**：关闭异常不会覆盖主异常，而是作为 suppressed 挂在主异常上，用 `getSuppressed()` 查看；连接池的 `close()` 是归还连接，不是物理关闭；不要在 try-with-resources 外层再手动 close。

### （四）泛型、反射、代理与 SPI

1. **泛型与擦除**
   - **考点**：泛型在编译后擦除到上界或 Object；不能 `new T()`、`new T[]`、`instanceof List<String>`；泛型数组可用 `(T[]) new Object[]` 或 `Array.newInstance`；编译器生成桥方法保证多态；`List<String>` 与 `List<Integer>` 因擦除不能作为重载参数。
   - **PECS**：`? extends T` 是生产者，只能读；`? super T` 是消费者，只能写；`List<?>` 只能读成 Object、remove 和 clear。
   - **延伸**：反射可通过 `ParameterizedType`、`TypeVariable` 拿到泛型签名，但运行期实例没有泛型信息；可变参数泛型用 `@SafeVarargs` 抑制告警。

2. **反射与注解**
   - **考点**：`Class/Field/Method/Constructor` 可在运行时获取并调用；`setAccessible(true)` 绕过访问检查（模块系统下需要 `opens`）；反射有方法查找、装箱和安全检查开销，可缓存 Method 或改用 MethodHandle。
   - **注解**：`@Retention` 决定 SOURCE/CLASS/RUNTIME，`@Target` 限制使用位置，`@Inherited` 影响子类，`@Repeatable` 支持重复注解；运行时注解靠反射读取，编译期注解处理器（APT）可生成代码。
   - **延伸**：Spring 的 DI/AOP、MyBatis Mapper、Jackson 序列化都依赖反射/注解；Lombok、MapStruct 走 APT；反射不是性能问题的首要嫌疑，缓存后通常够用。

3. **JDK 动态代理与 CGLIB**
   - **考点**：JDK Proxy 只能代理接口，`Proxy.newProxyInstance` + `InvocationHandler`，运行时生成 `$Proxy` 类；CGLIB 通过继承目标类生成子类，`final/private` 方法不能代理。
   - **Spring AOP**：有接口默认 JDK 代理，无接口用 CGLIB；Spring Boot 2.x 默认 `proxyTargetClass=true`，统一用 CGLIB；代理对象内部自调用不走代理，事务/AOP 会失效。
   - **延伸**：JDK 17 对动态代理有模块与包限制；ByteBuddy/ASM 更底层，SkyWalking、Mockito 都用字节码增强；代理类生成有缓存，但大量动态类会占元空间。

4. **SPI 与类加载器**
   - **考点**：Java SPI 在 `META-INF/services/接口全限定名` 中列实现类，`ServiceLoader` 加载所有实现并实例化，不能按名称获取；线程上下文类加载器（TCCL）让父加载器加载的接口能看到子加载器提供的实现，JDBC `DriverManager` 就用它。
   - **Dubbo SPI**：用 `key=value` 配置、按需加载、支持 `@Adaptive` 自适应扩展、`@Activate` 自动激活、IOC/AOP；比 Java SPI 更灵活，是 Dubbo 的扩展基础。
   - **延伸**：Tomcat 每个 webapp 独立类加载器，打破双亲委派以加载应用类；SPI 要注意类加载器泄漏，线程池中的 TCCL 用完要恢复。

### （五）序列化、IO 与现代 Java

1. **Java 序列化**
   - **考点**：`Serializable` 是标记接口；`serialVersionUID` 显式声明，版本不一致抛 `InvalidClassException`；`transient` 字段不序列化，`static` 字段不序列化；可自定义 `writeObject/readObject`；反序列化时会调用第一个不可序列化父类的无参构造器。
   - **安全**：反序列化不可信数据存在 gadget 链风险，应使用白名单或 JSON；`readObject` 要校验；敏感字段用 transient 或加密。
   - **选型**：JSON 可读、跨语言、体积较大；Protobuf 体积小、性能高、需要 schema；Hessian2 兼容 Java 生态。字段增删要保留默认值并避免依赖顺序。

2. **BIO/NIO 与字符集**
   - **考点**：字节流 `InputStream/OutputStream` 面向字节，字符流 `Reader/Writer` 面向字符并带编码；BIO 阻塞、一请求一线程；NIO 用 Buffer/Channel/Selector 做多路复用；AIO 是回调式异步。
   - **字符集**：UTF-8、GBK、ISO-8859-1 编码规则不同；乱码来自编码与解码不一致；`String.getBytes()` 不传参数会用平台默认编码，生产要显式指定 `StandardCharsets.UTF_8`。
   - **延伸**：NIO 的 `Buffer` 有 position/limit/capacity，`flip/clear/compact` 是高频考点；直接内存（DirectByteBuffer）减少拷贝但不受堆管理；零拷贝依赖 `sendfile/mmap`。

3. **Java 8–21 常用特性与数值**
   - **考点**：Java 8 有 Lambda/Stream/Optional/default method/新日期 API/CompletableFuture；9 有模块化、`List.of`、接口私有方法；10 有 `var`；11 有标准 HTTP Client；17 有 record、sealed class、文本块（15 正式）、`instanceof` 模式匹配（16 正式）；21 有虚拟线程、Sequenced Collections、switch 模式匹配正式化。
   - **Stream**：惰性求值、一次性消费、parallel 默认用 ForkJoinPool.commonPool，IO/阻塞任务不要用 parallel stream；`Optional` 适合返回值，不适合字段/参数。
   - **BigDecimal**：必须用 String 构造，`equals` 比较 scale（`1.0` 与 `1.00` 不相等），`compareTo` 只比较值；`divide` 必须指定 scale 和 `RoundingMode`，否则除不尽抛 `ArithmeticException`；金额也可用整数分。
   - **浮点**：IEEE 754 二进制无法精确表示 0.1，累加会漂移；NaN 与任何值比较都为 false，用 `Double.isNaN` 判断。

## 二、集合框架

### （一）体系、复杂度与迭代

1. **集合体系与选型**
   - **考点**：`Collection` 是单元素容器，`Map` 是键值容器。List 有序可重复、支持下标；Set 去重；Queue/Deque 按队列/双端规则进出；Map 用 key 查找 value。
   - **复杂度**：ArrayList 随机访问 O(1)、尾部追加摊还 O(1)、中间插入/删除 O(n)；LinkedList 按下标访问 O(n)、已定位节点的插入/删除 O(1)；HashMap 平均 O(1)、最坏 O(log n)/O(n)；TreeMap O(log n)；ArrayDeque 两端 O(1)；PriorityQueue 入队/出队 O(log n)。
   - **排序**：`Comparable` 是对象自带的自然序，`Comparator` 是外部策略；`Comparator.comparing().reversed().thenComparing()` 可组合；TreeMap/TreeSet 依赖比较结果，相等应返回 0。
   - **延伸**：默认容量、扩容倍数、是否允许 null、是否线程安全，是选型时最容易被追问的四个点。

2. **迭代与 fail-fast**
   - **考点**：`Iterable`/`Iterator` 支持 for-each；集合维护 `modCount`，迭代器创建时记录期望值，结构修改后 `next()`/`remove()` 抛 `ConcurrentModificationException`。
   - **边界**：fail-fast 只是尽力检测，不是线程安全保证；多线程读写仍可能读到脏数据；单线程删除要用 `iterator.remove()` 或 `removeIf()`，不能 for-each 中直接 `list.remove()`。
   - **延伸**：CopyOnWriteArrayList、ConcurrentHashMap 的迭代器是弱一致的，不抛 CME，但不保证看到最新数据；`forEach` 的顺序由集合实现决定。

### （二）List 与队列

1. **ArrayList 与 LinkedList**
   - **ArrayList**：底层 `Object[] elementData`，首次 add 时默认容量 10（JDK 8），扩容为旧容量的 1.5 倍（`old + (old >> 1)`），用 `Arrays.copyOf` 复制；随机访问 O(1)，中间插入/删除要移动元素 O(n)；`ensureCapacity` 可减少扩容，`trimToSize` 回收多余空间。
   - **LinkedList**：双向链表，节点含 prev/item/next；按下标访问要遍历 O(n)，头尾插入/删除 O(1)；每个元素有节点开销、缓存不友好；同时实现 List 和 Deque。
   - **取舍**：绝大多数场景 ArrayList 更快（连续内存、迭代快）；需要频繁头尾进出用 ArrayDeque，而不是 LinkedList；LinkedList 的“插入快”只在已拿到节点时成立。
   - **延伸**：`subList` 是视图，底层 List 结构修改后视图操作会失效；ArrayList 的迭代器同样 fail-fast。

2. **ArrayDeque、PriorityQueue 与 BlockingQueue**
   - **ArrayDeque**：环形数组 + head/tail，两端插入/删除 O(1)，不允许 null，默认容量 16、按 2 倍扩容；做栈/队列比 `Stack`、`LinkedList` 更合适。
   - **PriorityQueue**：数组实现的二叉堆，`peek` O(1)，`offer/poll` O(log n)；只保证堆顶最小/最大，遍历不排序；依赖自然序或 Comparator，不是线程安全。
   - **BlockingQueue**：`put/take` 阻塞，`offer/poll` 可带超时；ArrayBlockingQueue 有界、单锁两条件；LinkedBlockingQueue 默认近似无界、两把锁；SynchronousQueue 不存元素、直接交接；DelayQueue 按延迟到期出队。
   - **延伸**：生产者-消费者用有界队列形成背压，无界队列会把内存撑爆；`wait` 必须用 `while` 循环检查条件，防止虚假唤醒。

### （三）HashMap 与并发 Map

1. **HashMap 的结构与扩容**
   - **考点**：JDK 8 用 `Node[] table`，hash 做高低位异或 `h ^ (h >>> 16)`，下标 `(n - 1) & hash`，容量保持 2 的幂；默认负载因子 0.75，阈值 `capacity * 0.75`；扩容 2 倍，元素按 lo/hi 拆到原位置或原位置 + 旧容量，避免重新计算 hash。
   - **冲突**：链表长度到 8 且 table 长度 ≥ 64 时树化为红黑树，降到 6 退化为链表；树化门槛未到 64 时优先扩容而不是树化；null key 的 hash 为 0，放在 0 号桶。
   - **JDK 7 差异**：Entry 数组 + 头插法；并发扩容时链表可能形成环（A→B→A），get 会死循环、CPU 100%；JDK 8 改尾插避免成环，但仍然不是线程安全——并发 put 会丢更新、size 不准、树化竞争。
   - **延伸**：预估大小时用 `new HashMap<>(expectedSize / 0.75 + 1)` 或 Guava `Maps.newHashMapWithExpectedSize`；key 必须不可变或至少 hashCode/equals 稳定；哈希碰撞攻击可让链表退化。

2. **LinkedHashMap、TreeMap 与 WeakHashMap**
   - **LinkedHashMap**：继承 HashMap，额外维护 before/after 双向链表；默认插入序，`accessOrder=true` 变为访问序，配合 `removeEldestEntry` 可实现 LRU。
   - **TreeMap**：红黑树，按 key 排序，O(log n)；支持 `subMap/headMap/tailMap` 和 `NavigableMap`；自然序时 key 不能为 null，Comparator 可自定义 null 处理。
   - **WeakHashMap**：key 是弱引用，key 没有强引用时 GC 会删除条目；适合缓存/元数据，但 value 可能反向强引用 key 导致无法回收；非线程安全。
   - **延伸**：需要排序用 TreeMap，需要插入序用 LinkedHashMap，需要 LRU 用 LinkedHashMap，弱引用缓存用 WeakHashMap 或 Caffeine。

3. **ConcurrentHashMap**
   - **演进**：JDK 7 用 Segment（默认 16）分段锁，每个 Segment 继承 ReentrantLock；JDK 8 改为 `Node[] + CAS + synchronized 桶头`，锁粒度细化到一个桶，空桶用 CAS 插入，冲突时锁住链表/树头。
   - **读与计数**：get 不加锁，Node 的 val/next 用 volatile 保证可见；size 用 `baseCount + CounterCell[]` 分散计数，`size()` 是近似值，`mappingCount()` 返回 long；扩容时多线程协助 transfer，用 ForwardingNode 标记。
   - **复合操作**：`putIfAbsent`、`computeIfAbsent`、`compute`、`merge` 在单 key 上原子；但“先 get 再 put”仍不是原子的，要直接用这些方法；不允许 null key/value。
   - **延伸**：迭代器弱一致，不抛 CME；`size()` 不能用于强一致业务判断；并发场景优先用 `computeIfAbsent` 做本地缓存，但映射函数里不要做耗时/递归操作。

### （四）Set、视图与不可变集合

1. **Set 家族**
   - **考点**：HashSet 底层是 HashMap，value 固定为 `PRESENT`；LinkedHashSet 底层 LinkedHashMap，保留插入序；TreeSet 底层 TreeMap，按 Comparator/自然序排序；EnumSet 用位向量，性能最好。
   - **去重规则**：HashSet 依赖 hashCode + equals，TreeSet 依赖 compareTo/compare 返回 0；元素可变导致 hashCode 变化会“丢失”。
   - **延伸**：需要顺序去重用 LinkedHashSet，需要排序去重用 TreeSet；EnumSet 只支持同一枚举类型。

2. **视图、固定长度与不可变集合**
   - **Arrays.asList**：返回固定长度视图，底层是数组，`set` 可以，`add/remove` 抛 `UnsupportedOperationException`；传基本类型数组 `asList(int[])` 会得到 `List<int[]>`，size 为 1。
   - **subList**：返回视图不是拷贝，对原 List 的结构修改会让子列表操作失效；`clear()` 会删除原列表对应区间；需要独立列表用 `new ArrayList<>(subList)`。
   - **不可变**：`Collections.unmodifiableList` 是只读视图，原列表仍可变；`List.of/Set.of/Map.of` 是真正不可变、null-hostile，迭代顺序不保证；`List.copyOf` 做防御性拷贝。
   - **常见陷阱**：`remove(int)` 按下标、`remove(Object)` 按值，List<Integer> 要显式装箱；for-each 中删除用迭代器；HashSet 的输出顺序不可依赖；`Arrays.asList` 不能作为可变列表直接传下游。

## 三、并发编程

### （一）线程基础与 JMM

1. **线程状态、中断与常用方法**
   - **考点**：Java 线程有 NEW、RUNNABLE、BLOCKED、WAITING、TIMED_WAITING、TERMINATED 六种状态；RUNNABLE 包含等待 CPU 和等待 IO 的线程，BLOCKED 只表示等待 monitor 锁。
   - **中断**：`interrupt()` 只是设置中断标志，不强制停止线程；线程在 `sleep/wait/join` 上被中断会抛 `InterruptedException` 并清除标志；`isInterrupted()` 不清除，`Thread.interrupted()` 会清除；捕获中断后要么继续抛，要么恢复标志再退出。
   - **方法差异**：`sleep` 不释放锁；`wait` 释放 monitor 并进入等待队列，必须在 synchronized 块内，靠 `notify/notifyAll` 唤醒；`join` 等待目标线程结束；守护线程不阻止 JVM 退出，finally 不保证执行。
   - **延伸**：`Thread.stop()` 不安全，已废弃；`park/unpark` 是 LockSupport 的底层原语；虚拟线程被中断时同样通过中断标志协作取消。

2. **JMM 与 happens-before**
   - **考点**：JMM 规定原子性、可见性、有序性。原子性指操作不可分割；可见性指一个线程的写对另一个线程可见；有序性指禁止影响单线程语义的重排。
   - **happens-before**：程序顺序、monitor 解锁先于加锁、volatile 写先于读、线程 start 先于线程内动作、线程内动作先于 join 返回、中断先于被中断线程检测到、对象构造完成先于 finalize、传递性。满足 happens-before 才保证前一个操作的结果对后一个可见。
   - **重排与屏障**：编译器/CPU 会在 as-if-serial 语义下重排；volatile 通过 LoadLoad/StoreStore 等屏障禁止特定重排；synchronized 通过 monitor 保证临界区内的可见性。
   - **延伸**：非 volatile 的 long/double 在 32 位平台可能撕裂；安全发布可用 final、volatile、静态初始化、并发容器或锁；`this` 在构造器中逃逸会破坏初始化安全。

### （二）synchronized、volatile 与 Lock

1. **synchronized 与锁升级**
   - **考点**：synchronized 通过 monitorenter/monitorexit 和对象头 Mark Word 实现互斥与可见性；实例方法锁当前对象，静态方法锁 Class 对象；可重入，异常自动释放锁。
   - **锁状态**：无锁 → 偏向锁（同一线程反复进入，记录线程 ID）→ 轻量级锁（CAS 自旋）→ 重量级锁（Monitor 阻塞）；锁消除靠逃逸分析，锁粗化把连续加锁合并。
   - **JDK 变化**：JDK 15 起偏向锁默认关闭并标记废弃，因为撤销成本高、现代应用竞争模式收益有限；后续版本已移除相关实现，不要依赖偏向锁做性能假设。
   - **延伸**：锁升级不可逆；synchronized 不能中断、不能超时、非公平；临界区要短，避免在锁内做 IO/RPC。

2. **volatile 与双重检查锁**
   - **考点**：volatile 保证可见性和有序性，不保证复合操作原子性；`i++` 仍然线程不安全，要用 AtomicInteger 或锁。
   - **双重检查锁**：`instance = new Singleton()` 分为分配内存、初始化对象、引用赋值三步，可能重排为“先赋值再初始化”；没有 volatile 时另一个线程可能看到非 null 但未初始化完成的对象，所以实例字段必须 volatile。
   - **内存屏障**：volatile 写前 StoreStore、写后 StoreLoad；volatile 读后 LoadLoad/LoadStore；屏障阻止编译器和 CPU 越界重排。
   - **延伸**：volatile 适合状态标志、一次性安全发布、DCL；不适合计数、check-then-act；volatile 数组只保证引用可见，元素不保证。

3. **ReentrantLock、ReadWriteLock 与 StampedLock**
   - **ReentrantLock**：基于 AQS，支持公平/非公平、`tryLock` 超时、`lockInterruptibly`、多个 Condition；必须在 finally 中 unlock；与 synchronized 相比更灵活但有忘记解锁风险。
   - **ReentrantReadWriteLock**：读读共享、读写互斥、写写互斥；读锁不能升级为写锁（同时持有读写会死锁），写锁可以降级为读锁；适合读多写少。
   - **StampedLock**：乐观读 + 戳记校验，读多写少性能好；不可重入，不支持 Condition；乐观读期间数据可能被改，必须 `validate` 后重试。
   - **延伸**：公平锁吞吐通常更低；Condition 可做多等待队列（如生产者/消费者分开）；锁内不要调用外部慢服务。

### （三）CAS、AQS 与并发工具

1. **CAS 与原子类**
   - **考点**：CAS 比较并交换，依赖 CPU 的 `cmpxchg` 指令和 volatile 可见性；Java 8 用 Unsafe，JDK 9+ 可用 VarHandle；失败通常自旋重试。
   - **ABA**：值从 A 改成 B 又改回 A，CAS 会误判没变；`AtomicStampedReference` 加版本戳，`AtomicMarkableReference` 加布尔标记。
   - **高竞争**：自旋浪费 CPU、缓存一致性流量大；`LongAdder` 用分段 Cell 分散热点，适合高并发计数，`sum()` 是弱一致快照；`AtomicLong` 适合低竞争或需要精确瞬时值。
   - **延伸**：CAS 只保证单个变量原子，多个变量要锁或 AtomicReference；伪共享可用 `@Contended`；CAS 自旋不适合长临界区。

2. **AQS 原理**
   - **考点**：AQS 用 volatile int `state` 表示同步状态，内部维护 CLH 变体的 FIFO 等待队列；节点有 prev/next、waitStatus、thread；独占模式用 `acquire/release`，共享模式用 `acquireShared/releaseShared`。
   - **模板方法**：子类实现 `tryAcquire/tryRelease/tryAcquireShared/tryReleaseShared/isHeldExclusively`；`ConditionObject` 维护条件队列，await 释放锁并挂起，signal 转移到同步队列。
   - **实现**：ReentrantLock 用 state 记重入次数；Semaphore 用 state 记许可数；CountDownLatch 用 state 记剩余计数；ReentrantReadWriteLock 把 state 高低位分给读/写。
   - **延伸**：AQS 默认非公平，可通过 tryAcquire 的队列判断实现公平；中断、超时、取消节点都要正确处理；自定义同步器优先复用 AQS 而不是自写队列。

3. **并发工具类**
   - **CountDownLatch**：一次性门闩，`countDown` 减到 0 后所有 `await` 返回；不能重置；适合“主线程等待多个初始化完成”。
   - **CyclicBarrier**：可循环使用的栅栏，所有线程到达后一起继续，可带 barrierAction；一个线程中断/超时会 broken，其他线程抛 BrokenBarrierException。
   - **Semaphore**：许可计数，`acquire/release` 控制并发数；公平模式按等待顺序；适合限流、连接池、资源池。
   - **Phaser**：可动态注册/注销参与者的多阶段同步；Exchanger 做两线程交换数据。
   - **延伸**：Latch 是“等事件”，Barrier 是“等彼此”；Semaphore 不是锁，release 不一定由 acquire 的线程调用；等待要用超时避免永久挂起。

### （四）线程池与异步编程

1. **ThreadPoolExecutor 参数与执行流程**
   - **考点**：核心参数 corePoolSize、maximumPoolSize、keepAliveTime、unit、workQueue、threadFactory、handler；内部 `ctl` 同时打包运行状态和 worker 数。
   - **执行流程**：worker 数 < core 时新建核心线程；否则尝试入队；队满且 worker 数 < max 时新建非核心线程；仍满则执行拒绝策略。先入队再扩线程是为了避免过早创建大量线程、减少上下文切换。
   - **队列与拒绝**：ArrayBlockingQueue 有界；LinkedBlockingQueue 默认近似无界；SynchronousQueue 直接交接；PriorityBlockingQueue 优先级；DelayedWorkQueue 延迟。拒绝策略有 AbortPolicy（默认抛异常）、CallerRunsPolicy（调用方执行，形成反压）、DiscardPolicy、DiscardOldestPolicy。
   - **生命周期**：`shutdown` 不再接新任务、等已提交任务结束；`shutdownNow` 中断工作线程并返回未执行任务；`awaitTermination` 等待终止；`allowCoreThreadTimeOut` 允许核心线程回收；`prestartAllCoreThreads` 预热。
   - **Executors 风险**：`newFixedThreadPool` 用无界队列可能 OOM；`newCachedThreadPool` 最大线程数为 Integer.MAX_VALUE，可能创建过多线程；`newSingleThreadExecutor` 也是无界队列；`newScheduledThreadPool` 的 DelayedWorkQueue 无界。生产建议手动 `new ThreadPoolExecutor` 并有界队列。
   - **容量**：CPU 密集型约 `N+1`；IO 密集型可用 `N * (1 + 等待时间/计算时间)` 或按 Little 定律 `并发数 = QPS × RT` 估算；最终以压测和监控为准，队列长度、活跃线程数、拒绝次数都要观测。

2. **CompletableFuture**
   - **考点**：`runAsync/supplyAsync` 创建异步任务；`thenApply` 转换、`thenAccept` 消费、`thenRun` 不关心结果；`thenCompose` 扁平化嵌套 Future；`thenCombine` 合并两个结果；`allOf/anyOf` 聚合。
   - **异常**：`exceptionally` 只处理异常并给默认值；`handle` 同时处理正常/异常；`whenComplete` 观察结果但不改变；异常会沿链传播，未被处理的异常在 `get/join` 时抛出 CompletionException。
   - **取消与超时**：`cancel` 对已开始的任务不一定能中断底层执行；JDK 9+ 有 `orTimeout`、`completeOnTimeout`；`get` 可超时，`join` 不抛受检异常。
   - **线程池**：默认用 ForkJoinPool.commonPool（并行度约为 CPU 核数 - 1）；阻塞 IO、数据库调用必须传入自定义 Executor，否则会占满公共池、拖慢其他并行任务；上下文（TraceId、用户、事务）不会自动传递。

### （五）ThreadLocal 与上下文传递

1. **ThreadLocal 原理与内存泄漏**
   - **考点**：每个 Thread 持有 ThreadLocalMap，Entry 的 key 是 ThreadLocal 的弱引用，value 是强引用；ThreadLocal 对象被回收后 key 变 null，但 value 仍被 Entry 强引用，形成 stale entry。
   - **泄漏场景**：线程池线程长期存活，任务结束后不 remove，value 一直挂在 Thread 上；尤其大对象、连接、用户上下文。
   - **正确用法**：`try/finally` 中 `remove()`；ThreadLocal 声明为 static final；不要存可变大对象；`InheritableThreadLocal` 只在创建子线程时复制，线程池不会继承。
   - **延伸**：ThreadLocalMap 用开放寻址和线性探测，不是链表；`expungeStaleEntry` 会清理 key 为 null 的槽；JDK 21 虚拟线程也有 ThreadLocal，但数量大时成本高，考虑 ScopedValue。

2. **跨线程上下文传递**
   - **考点**：ThreadLocal 不会自动跨线程；`InheritableThreadLocal` 只在线程创建时复制父线程值，线程池复用线程时失效；MDC、用户信息、TraceId 都面临同样问题。
   - **方案**：用 TransmittableThreadLocal（TTL）包装线程池的 Runnable/Callable，或使用链路组件提供的线程池装饰器；`CompletableFuture` 每个异步阶段要显式捕获并恢复上下文；MQ 消费把上下文放消息头。
   - **延伸**：传递后必须清理，避免线程复用串数据；异步编排中“提交任务时捕获、执行时恢复、结束后清理”；不要依赖 `InheritableThreadLocal` 解决池化问题。

### （六）并发容器、虚拟线程与排障

1. **并发容器**
   - **考点**：ArrayBlockingQueue 有界、单锁两条件；LinkedBlockingQueue 两把锁、默认近似无界；SynchronousQueue 不存储、直接交接；PriorityBlockingQueue 无界优先级；DelayQueue 延迟到期。
   - **CopyOnWriteArrayList**：写时复制数组，读无锁、读多写少合适；写操作加锁复制，内存翻倍、迭代器是快照弱一致；不适合频繁写或大列表。
   - **ConcurrentLinkedQueue**：CAS 无锁链表，`size()` 要遍历 O(n)，适合高并发队列；弱一致迭代器。
   - **延伸**：阻塞队列是实现生产者-消费者和背压的基础；有界队列防 OOM；`Collections.synchronizedList` 只是包装，复合操作仍需手动同步。

2. **虚拟线程、结构化并发与 Scoped Values**
   - **考点**：虚拟线程 JDK 21 正式，由少量平台线程（carrier）承载，阻塞 IO 时 unmount 释放 carrier，适合高并发 IO；CPU 密集不会更快，反而增加调度开销。
   - **注意**：不要池化虚拟线程，每个任务直接 `Thread.ofVirtual().start()`；JDK 21 中 `synchronized` 块或 native 调用会造成 pinning、阻塞 carrier，可改用 ReentrantLock（后续 JDK 对 synchronized 的 pinning 有改进，但仍建议避免长临界区）；ThreadLocal 数量大时内存成本高；数据库连接、下游容量仍要限流。
   - **结构化并发**：JDK 21 起预览，用 `StructuredTaskScope` 把子任务生命周期约束在作用域内，失败可取消兄弟任务，避免线程泄漏；Scoped Values 也是预览，不可变、作用域内继承、自动清理，替代部分 ThreadLocal。
   - **延伸**：虚拟线程不是“无限并发”的许可证，瓶颈会转移到连接池、CPU、下游服务；用 `jcmd Thread.dump_to_file` 查看虚拟线程。

3. **死锁与线上排障**
   - **考点**：死锁四个必要条件——互斥、持有并等待、不可抢占、循环等待；破坏任一即可预防，常用锁顺序、`tryLock` 超时、缩小锁范围、避免嵌套锁。
   - **排查**：`jstack <pid>` 或 `jcmd <pid> Thread.print` 会输出 “Found one Java-level deadlock”，包含线程、锁和等待链；`top -Hp <pid>` 找高 CPU 线程，线程 ID 转十六进制匹配 `nid`。
   - **区分**：死锁是相互等待；活锁是不断重试但无法推进；饥饿是低优先级线程长期拿不到资源。
   - **延伸**：线程池耗尽表现为大量 WAITING/BLOCKED 和拒绝任务；多抓几份线程转储对比；结合 GC 日志、火焰图区分锁竞争、GC、慢 IO。

## 四、JVM

### （一）运行时内存与对象

1. **内存区域划分**
   - **线程私有**：程序计数器（当前字节码行号，唯一不会 OOM 的区域）、虚拟机栈（栈帧含局部变量表、操作数栈、动态链接、返回地址）、本地方法栈。
   - **线程共享**：堆（对象实例和数组，GC 主战场）、方法区（JDK 8 起用元空间实现，存类元数据、运行时常量池）；JDK 7 起字符串常量池移到堆。
   - **其他**：直接内存（NIO DirectByteBuffer，受 `-XX:MaxDirectMemorySize` 限制）、代码缓存（JIT 编译结果）。
   - **OOM 类型**：`Java heap space`（堆不足）、`GC overhead limit exceeded`（GC 回收效率过低）、`Metaspace`（类元数据/类加载器泄漏）、`Direct buffer memory`（直接内存）、`unable to create native thread`（线程数/内存限制）；`StackOverflowError` 是栈溢出，不是 OOM。

2. **对象创建、布局与访问**
   - **创建过程**：类加载检查 → 分配内存（指针碰撞或空闲列表，TLAB 内快速分配，CAS 处理竞争）→ 零值初始化 → 设置对象头 → 执行构造器。
   - **布局**：Mark Word（hashCode、GC 年龄、锁状态）、Klass 指针（类型元数据）、实例字段、对齐填充；64 位下开启压缩指针，对象头通常 12 字节，按 8 字节对齐后常为 16 字节；数组额外有长度字段。
   - **访问**：句柄访问（稳定，多一次间接寻址）和直接指针（HotSpot 默认，快）。
   - **元空间增长**：动态代理、CGLIB、JSP、热部署会不断生成类；类卸载要求类加载器被 GC 且无实例/无引用，Tomcat 热部署、SPI、线程池 TCCL 都可能让类加载器无法回收，导致 Metaspace 只增不减。
   - **延伸**：逃逸分析可把对象标量替换到栈上，减少堆分配，但不是规范保证，JIT 也可能去优化；大对象可直奔老年代（`PretenureSizeThreshold`）；TLAB 减少分配竞争。

### （二）类加载与执行

1. **类加载过程与双亲委派**
   - **阶段**：加载（读取字节流、生成 Class 对象）→ 链接（验证、准备、解析）→ 初始化（执行 `<clinit>`）。准备阶段给静态变量赋零值，`static final` 编译期常量在准备阶段就赋最终值。
   - **初始化触发**：`new`、访问静态字段/静态方法、反射、初始化子类会先初始化父类、启动 main 类、default 方法所在接口；访问编译期常量不触发。
   - **双亲委派**：Bootstrap → Platform（JDK 9+，JDK 8 为 Extension）→ Application，逐层向上委派、找不到再自己加载；保证核心类不被篡改、避免重复加载。
   - **打破场景**：TCCL（JDBC SPI）、Tomcat 每个 webapp 独立加载器、OSGi 模块化、Java Agent、自定义加载器；`Class.forName` 默认初始化，`ClassLoader.loadClass` 默认只加载不初始化。
   - **延伸**：类卸载需要类加载器被 GC 且无实例/无引用；JDK 9 模块化后 `Class.forName` 还受模块可见性约束。

2. **解释执行、JIT 与逃逸分析**
   - **考点**：字节码先解释执行，热点方法/循环由 JIT 编译；HotSpot 用计数器触发，C1 快速编译、C2 深度优化，分层编译平衡启动与峰值性能；OSR 替换正在运行的方法。
   - **优化**：方法内联、逃逸分析、标量替换、锁消除、公共子表达式消除、死代码消除；推测性优化失败会去优化（deoptimize）回退到解释执行。
   - **逃逸程度**：未逃逸（对象只在方法内使用，可标量替换/栈上分配）、方法逃逸（作为返回值或参数传出）、线程逃逸（被其他线程访问，不能随意优化）；同步块内对象未逃逸可锁消除。
   - **注意**：标量替换/锁消除是 JIT 优化结果，不意味着 Java 语言层面“对象一定分配在栈上”；对象大小、方法大小、循环、同步、虚调用都会影响优化效果；微基准必须用 JMH 预热，避免把解释执行当稳态。
   - **延伸**：`-Xint` 只解释、`-Xcomp` 只编译；CodeCache 满会停止编译；AOT/GraalVM native image 启动快但反射/动态代理/延迟加载受限。

### （三）垃圾回收

1. **可达性、引用与回收算法**
   - **GC Roots**：栈中局部变量引用、静态字段、JNI 引用、常量、同步锁对象、JVM 内部引用；从 Roots 出发不可达即可回收。
   - **引用类型**：强引用（不回收）、软引用（内存不足才回收，适合缓存）、弱引用（下次 GC 回收，ThreadLocalMap key）、虚引用（回收通知，配合 ReferenceQueue）。
   - **算法**：标记-清除（简单、碎片多）、复制（无碎片、浪费空间，适合新生代）、标记-压缩（无碎片、移动对象成本高，适合老年代）、分代收集。
   - **安全点**：STW 只发生在安全点，线程到达安全点后才暂停；GC 线程与用户线程并发时靠读写屏障维护正确性。
   - **延伸**：`finalize` 不可靠且已废弃；软引用在内存紧张时回收，但回收时机不保证；弱引用适合 ThreadLocalMap、缓存 key。

2. **分代收集与收集器**
   - **分代**：新生代 Eden + 两个 Survivor（默认 8:1:1），Minor GC 用复制算法，存活对象年龄加 1，默认 15 岁晋升；动态年龄判定：Survivor 中同龄对象总和超过一半也可晋升。老年代存长期存活对象和大对象。
   - **收集器**：Serial/Serial Old（单线程、客户端）、ParNew/Parallel Scavenge/Parallel Old（多线程、吞吐优先）、CMS（并发标记清除，低停顿，但有碎片和 Concurrent Mode Failure，JDK 9 废弃、JDK 14 移除）、G1（Region 化、可预测停顿、JDK 9+ 默认）、ZGC（着色指针 + 读屏障，亚毫秒停顿，JDK 21 分代）、Shenandoah（低停顿，OpenJDK）。
   - **G1**：堆切成大小相等的 Region（1~32MB），逻辑分 Eden/Survivor/Old/Humongous；Young GC 复制存活对象，Mixed GC 回收部分老年代 Region；用 SATB + RSet 维护跨 Region 引用，按 `MaxGCPauseMillis` 预测停顿。
   - **ZGC**：染色指针把标记信息存在指针里，读屏障在访问对象时修正引用，标记/移动并发执行，停顿与堆大小基本无关；分代 ZGC 在 JDK 21 正式，缓解年轻代回收压力。
   - **选型**：小堆/低延迟选 G1；大堆（几十 GB 以上）和极低停顿选 ZGC；吞吐优先、批处理选 Parallel；CMS 已不推荐。
   - **延伸**：G1 的 Humongous 对象指超过 Region 一半的对象；Full GC 是兜底，频繁 Full GC 要先看晋升失败、Metaspace、显式 `System.gc()`。

3. **三色标记与漏标**
   - **考点**：三色标记把对象分为白（未访问）、灰（已访问但子引用未扫描）、黑（已扫描）。并发标记时用户线程修改引用，可能出现“黑对象指向白对象、且灰对象不再引用它”，导致白对象被漏标回收。
   - **解决**：增量更新（CMS）在黑色对象新增引用时记录下来，重新扫描；原始快照 SATB（G1）在删除引用时记录旧值，按开始时的快照标记。两者都靠写屏障实现。
   - **延伸**：跨代引用用卡表（Card Table）或 RSet 记录，避免全堆扫描；写屏障有开销，但比 STW 全量扫描便宜。

### （四）诊断与调优

1. **常用工具**
   - **命令行**：`jps` 查进程、`jcmd` 综合诊断、`jstat` 看 GC 和类加载、`jmap` 看堆/生成 dump、`jstack` 看线程、`jinfo` 看参数。
   - **进阶**：JFR 低开销采集事件、MAT 分析堆转储（Dominator Tree、Retained Size、GC Roots）、Arthas 在线诊断（trace/watch/thread）、async-profiler 火焰图、NMT 追踪本地内存。
   - **日志**：JDK 9+ 用 `-Xlog:gc*:file=gc.log:time,level,tags`；堆转储 `-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/path`。
   - **延伸**：生产抓 dump 会 STW，先评估堆大小和磁盘；JFR 适合长期低开销采集；Arthas 的 trace 有性能开销，用完即关。

2. **常见问题排查**
   - **CPU 100%**：`top -Hp` 找线程 → 十六进制线程 ID → `jstack` 匹配 `nid`；区分业务死循环、锁竞争、频繁 GC、JIT 编译线程。
   - **内存泄漏**：堆 dump → 找占用最大的对象 → Dominator Tree/Retained Size → 追 GC Roots 引用链；常见是静态集合、缓存无上限、ThreadLocal、监听器未注销、类加载器泄漏。
   - **频繁 GC**：`jstat -gcutil` 看 Eden/Old 增长和 FGC 次数；结合分配速率、晋升速率、GC 日志判断是分配过快、晋升过早还是老年代泄漏。
   - **Metaspace OOM**：动态生成类、热部署、类加载器未释放；看 `jstat -gc` 的 MC/MU 和 `jcmd GC.class_stats`。
   - **直接内存/线程泄漏**：NMT 看 direct buffer，`jstack` 数线程；线程池未关闭、每次请求新建线程池是常见原因。

3. **调优参数与容器环境**
   - **基础**：`-Xms` 与 `-Xmx` 设相等避免动态扩缩；`-Xmn` 或 `NewRatio` 控制新生代；`SurvivorRatio` 控制 Eden/Survivor；`MetaspaceSize/MaxMetaspaceSize` 控制元空间；`MaxDirectMemorySize` 控制直接内存。
   - **GC**：`-XX:+UseG1GC`、`-XX:MaxGCPauseMillis`、`-XX:G1HeapRegionSize`；大堆低延迟用 `-XX:+UseZGC`；JDK 8 默认 Parallel，JDK 9+ 默认 G1。
   - **容器**：JDK 10+ 默认容器感知，按 cgroup 限制算堆；用 `MaxRAMPercentage` 而不是写死 `-Xmx`；K8s 的 OOMKilled 可能是堆外/线程/元空间超限，不一定是堆 OOM。
   - **原则**：先定位瓶颈再调参，用压测验证 P99 和吞吐；不要盲目调大堆，堆越大 Full GC 停顿越长；调优目标在吞吐、延迟、内存占用之间取舍。

## 五、Spring 与持久层

### （一）IoC 容器、Bean 生命周期与循环依赖

1. **IoC/DI 与容器**
   - **考点**：IoC 是容器负责创建、装配、管理对象，DI 是具体的注入方式（构造器、setter、字段）。BeanFactory 是基础容器，默认懒加载；ApplicationContext 在其上增加事件、国际化、资源加载、Environment、AOP 和 BeanPostProcessor 自动注册，单例默认预实例化。
   - **refresh 流程**：准备上下文 → 获取 BeanFactory → 准备 BeanFactory → 执行 BeanFactoryPostProcessor → 注册 BeanPostProcessor → 初始化消息源/事件广播器 → onRefresh（Web 容器）→ 注册监听器 → 实例化所有非懒加载单例 → finishRefresh。
   - **扩展点**：`BeanFactoryPostProcessor` 在 Bean 实例化前修改 BeanDefinition；`BeanPostProcessor` 在 Bean 初始化前后处理实例；`Aware` 回调（BeanName、BeanFactory、ApplicationContext、Environment 等）由 BeanPostProcessor 触发。
   - **延伸**：`FactoryBean` 是“生产 Bean 的 Bean”，`BeanFactory` 是容器；`@Bean` 适合第三方类，`@Component` 适合自己写的类；`ImportSelector`/`ImportBeanDefinitionRegistrar` 是自动配置的底层机制。

2. **Bean 生命周期与作用域**
   - **生命周期**：实例化 → 属性填充 → Aware 回调 → `BeanPostProcessor.postProcessBeforeInitialization` → `@PostConstruct` → `InitializingBean.afterPropertiesSet` → `init-method` → `BeanPostProcessor.postProcessAfterInitialization`（此处生成 AOP 代理）→ 使用 → `@PreDestroy` → `DisposableBean.destroy` → `destroy-method`。
   - **作用域**：singleton（容器内一个）、prototype（每次获取新建）、request/session/application/websocket（Web 作用域）；prototype 注入 singleton 时只在注入那一刻创建一次，不会每次调用重新创建，需要 `ObjectProvider`、`@Lookup` 或 scoped proxy。
   - **延伸**：Spring 只管理 singleton 的销毁，prototype 的销毁不回调；`@Lazy` 可延迟初始化并打破部分循环依赖；`@PostConstruct` 在 Boot 3 是 `jakarta.annotation`，Boot 2 是 `javax.annotation`。

3. **循环依赖与三级缓存**
   - **三级缓存**：`singletonObjects`（一级，完整单例）、`earlySingletonObjects`（二级，提前暴露的引用）、`singletonFactories`（三级，ObjectFactory）。
   - **流程**：创建 A → 实例化后把 A 的 ObjectFactory 放入三级缓存 → 填充属性发现依赖 B → 创建 B → B 依赖 A 时从三级缓存拿到工厂，调用 `getEarlyBeanReference` 得到 A 的早期引用（可能是 AOP 代理），放入二级缓存 → B 完成 → A 完成并放入一级缓存。
   - **为什么三级**：如果只有两级，要么提前暴露原始对象导致 AOP 代理不一致，要么对所有 Bean 都过早创建代理；三级缓存的工厂只在真正发生循环依赖时才生成早期引用，兼顾普通 Bean 和代理 Bean。
   - **解决不了**：构造器循环依赖（对象还没实例化，无法提前暴露）、prototype 循环依赖（不做缓存）、`@Async` 等由 BeanPostProcessor 在初始化后生成代理的循环（早期引用与最终代理可能不一致）。Spring Boot 2.6+ 默认禁止循环依赖，可通过 `spring.main.allow-circular-references=true` 放开，但应优先重构。
   - **延伸**：循环依赖是设计信号，优先拆服务/改用事件/`@Lazy`；`AopContext.currentProxy()` 可解决自调用，但会耦合 Spring。

### （二）AOP 与事务

1. **AOP 原理与通知顺序**
   - **考点**：Spring AOP 是运行期代理，切点（Pointcut）匹配连接点，通知（Advice）在方法前后织入；`@Aspect` 定义切面，`@Around/@Before/@After/@AfterReturning/@AfterThrowing` 定义通知；切点表达式常用 `execution`、`within`、`@annotation`、`args`。
   - **顺序**：同一连接点上，`@Order`/`@Priority` 值越小优先级越高；进入时高优先级 Before 先执行，退出时高优先级 After 后执行；Around 包裹其余通知。
   - **限制**：JDK 代理只能代理接口，CGLIB 不能代理 final/private 方法；同类自调用不走代理；非 Spring 管理的对象没有 AOP；`protected/private` 方法默认不拦截。
   - **延伸**：AOP 本质是代理模式，事务、缓存、日志、权限都基于它；AspectJ 编译期/加载期织入能力更强但更重；Spring Boot 2.x 默认 CGLIB。

2. **事务传播、隔离与回滚**
   - **传播行为**：REQUIRED（默认，有事务加入、无则新建）、REQUIRES_NEW（挂起当前事务、新建独立事务）、SUPPORTS（有则加入、无则非事务）、NOT_SUPPORTED（挂起事务、非事务执行）、MANDATORY（必须已有事务）、NEVER（必须无事务）、NESTED（同一事务内建保存点，回滚到保存点，依赖数据源支持）。
   - **隔离级别**：DEFAULT（跟随数据库）、READ_UNCOMMITTED、READ_COMMITTED、REPEATABLE_READ、SERIALIZABLE；MySQL 默认 RR，Oracle 默认 RC。
   - **回滚规则**：默认只对 `RuntimeException` 和 `Error` 回滚，受检异常不回滚；需要 `rollbackFor = Exception.class`；`readOnly=true` 优化只读事务；`timeout` 控制长事务。
   - **失效清单**：同类自调用；方法非 public；对象不是 Spring Bean（自己 new）；异常被 catch 吞掉；抛受检异常但没配 rollbackFor；多数据源用错事务管理器；`@Async`/新线程导致事务上下文不传递；数据库引擎不支持事务（如 MyISAM）；`final` 方法无法被 CGLIB 代理。
   - **异步与线程切换**：Spring 事务上下文绑定在当前线程的 ThreadLocal，`@Async`、手动 `new Thread`、线程池任务不会自动继承；异步方法要自己开启事务，或把事务操作留在调用线程，避免“事务已提交/连接已归还”后继续写库。
   - **延伸**：事务内不要做 RPC、发消息、长耗时计算，避免长事务持锁和连接耗尽；需要事务提交后执行用 `TransactionSynchronization.afterCommit` 或 `@TransactionalEventListener`；嵌套事务与外层事务的提交/回滚边界要分清。

### （三）Spring Boot、MVC 与 Web

1. **自动配置与配置加载**
   - **考点**：`@SpringBootApplication` = `@SpringBootConfiguration` + `@EnableAutoConfiguration` + `@ComponentScan`；`@EnableAutoConfiguration` 通过 `AutoConfigurationImportSelector` 读取候选配置，Boot 2.7+ 用 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`，Boot 3 只读该文件（旧 `spring.factories` 不再用于自动配置）。
   - **条件装配**：`@ConditionalOnClass`、`@ConditionalOnMissingBean`、`@ConditionalOnProperty`、`@ConditionalOnWebApplication`；`@AutoConfigureBefore/After/Order` 控制顺序；用户自定义 Bean 通常因 `@ConditionalOnMissingBean` 覆盖默认配置。
   - **配置优先级**：命令行参数 > 环境变量 > `application-{profile}.yml` > `application.yml` > 默认值；`@ConfigurationProperties` 支持松散绑定、类型安全、元数据，优于散落的 `@Value`；profile 用于区分环境。
   - **Boot 3 变化**：JDK 17 基线、`javax.*` 迁移到 `jakarta.*`、AOT/GraalVM 原生镜像、Micrometer Tracing/Observability 取代 Sleuth、Spring Cloud 需匹配 2022+ 版本。
   - **Actuator**：提供 health、metrics、env、loggers、threaddump 等运维端点，用于健康检查、指标采集和问题诊断；生产要限制暴露范围、加鉴权，health 分组区分 liveness/readiness。
   - **延伸**：自定义 starter = 自动配置类 + `AutoConfiguration.imports` + 条件注解；`--debug` 可看自动配置报告；配置中心与本地配置要有优先级和兜底。

2. **Spring MVC 请求流程**
   - **流程**：请求进入 `DispatcherServlet` → `HandlerMapping` 找到 Handler 和拦截器链 → `HandlerAdapter` 适配调用 → `HandlerInterceptor.preHandle` → 参数解析（`@RequestBody/@RequestParam/@PathVariable/@Valid`）→ Controller → 返回值处理（`@ResponseBody` 走 `HttpMessageConverter`，否则 ViewResolver）→ `postHandle` → `afterCompletion`。
   - **Filter vs Interceptor vs AOP**：Filter 属于 Servlet 容器，在 DispatcherServlet 之前，拿不到 HandlerMethod；Interceptor 属于 Spring MVC，能拿到 Handler，有 pre/post/afterCompletion；AOP 作用在 Bean 方法上，可覆盖非 Web 调用。
   - **异常与校验**：`@ControllerAdvice` + `@ExceptionHandler` 做全局异常；`@Valid`/`@Validated` 做参数校验，`BindingResult` 收集错误，失败抛 `MethodArgumentNotValidException`；统一返回结构要区分业务异常和系统异常。
   - **延伸**：异步 MVC 用 `Callable`/`DeferredResult`，SSE 用 `SseEmitter` 或 `Flux<ServerSentEvent>`；跨域用 CORS 配置；静态资源、文件上传、内容协商都是 DispatcherServlet 的扩展点。

3. **WebFlux、SSE 与 AOT/GraalVM**
   - **WebFlux**：基于 Reactor Netty 和事件循环，`Mono/Flux` 表达 0/1 和 0..N，支持背压；阻塞调用必须切到 `boundedElastic`，否则阻塞事件循环；ThreadLocal 上下文不会自动跨 reactor 阶段传递。
   - **SSE**：`text/event-stream` 单向服务端推送，浏览器自动重连；适合通知、进度、行情；要注意代理缓冲、连接超时、连接数。
   - **AOT/GraalVM**：编译期生成反射/资源/代理配置，启动快、内存低；但封闭世界限制动态类加载、JSP、部分字节码增强库，构建复杂、调试困难。
   - **延伸**：MVC 适合阻塞 IO 和成熟生态，WebFlux 适合高并发 IO/流式；不要在事件循环里做 JDBC/同步 HTTP；原生镜像要逐项验证依赖。

### （四）MyBatis 与 ORM

1. **执行流程与 `#{}`/`${}`**
   - **流程**：`SqlSessionFactoryBuilder` 解析配置 → `SqlSessionFactory` → `SqlSession` → `Executor`（Simple/Reuse/Batch）→ `StatementHandler` → `ParameterHandler` 设置参数 → `ResultSetHandler` 映射结果；Mapper 接口由 `MapperProxy` 代理，方法签名映射到 `MappedStatement`。
   - **`#{}`**：编译为 `PreparedStatement` 的 `?`，由 TypeHandler 设参，能防 SQL 注入；**`${}`**：直接字符串拼接，存在注入风险，只能用于表名/列名/排序等无法预编译的场景，且必须白名单校验。
   - **延伸**：`selectOne` 查多条会抛异常；`RowBounds` 是内存分页，深分页要用 SQL 改写；`fetchSize` 影响流式读取；主键回填用 `useGeneratedKeys`。

2. **动态 SQL、插件与缓存**
   - **动态 SQL**：OGNL 表达式，`if/choose/when/otherwise/where/set/foreach/trim`；`<sql>` 片段复用；`bind` 创建变量；`foreach` 注意大集合的 SQL 长度。
   - **插件**：`Interceptor` 可拦截 Executor、StatementHandler、ParameterHandler、ResultSetHandler，底层用 JDK 动态代理包装；PageHelper 拦截 Executor 改写 SQL 和 count。
   - **一级缓存**：`SqlSession` 级，默认开启，同一会话/事务内相同 SQL 和参数命中；跨会话失效；Spring 中 `SqlSessionTemplate` 在无事务时每次操作新建会话，一级缓存基本不生效。
   - **二级缓存**：namespace 级，需 `<cache/>` 或 `@CacheNamespace`，跨 SqlSession 共享；要求结果可序列化；提交后写入，其他 namespace 更新同一张表可能读到旧数据，生产慎用，优先用 Redis。
   - **延伸**：`flushCache="true"` 可强制清缓存；`localCacheScope=STATEMENT` 可关闭一级缓存；缓存只适合读多写少且能接受短暂不一致的数据。

3. **事务整合、懒加载与批量**
   - **事务**：MyBatis 通过 `SqlSessionTemplate` 与 Spring 事务同步，同一事务复用同一个 SqlSession 和连接；Mapper 代理参与 Spring 事务，`@Transactional` 生效需要走代理。
   - **懒加载**：`lazyLoadingEnabled=true`，关联对象用代理按需加载；`aggressiveLazyLoading=false` 避免访问任一属性就加载全部；N+1 可用 `fetch join`、`batch` 或二次查询解决。
   - **批量**：`ExecutorType.BATCH` 累积语句，`flushStatements()` 提交；MySQL 连接加 `rewriteBatchedStatements=true` 才能真正合并；大批量要分片，避免一次事务过大。
   - **延伸**：MyBatis-Plus 的 Wrapper、逻辑删除、乐观锁、分页插件只是封装，不能替代索引和 SQL 优化；`${}` 拼接排序字段要防注入。

### （五）依赖注入方式

- **构造器注入**：依赖可声明为 final、对象构造完成即完整、必需依赖缺失会启动失败、易于单测；Spring 4.3+ 单构造器可省略 `@Autowired`；依赖过多说明职责过重。
- **setter 注入**：适合可选依赖、可重新配置，但对象可能处于不完整状态；字段注入：代码短，但隐藏依赖、难以单测、无法 final、容易 NPE，不推荐。
- **选择**：必需依赖用构造器，可选依赖用 setter 或 `ObjectProvider`；`@Qualifier`/`@Primary` 解决同类型多 Bean；JSR-330 的 `@Inject/@Named` 也可用。
- **延伸**：构造器循环依赖无法解决，应重构；`@Lazy` 可打破注入时的循环；字段注入在代理/反射场景更脆弱。

## 六、MySQL 与数据库

### （一）索引与执行计划

1. **InnoDB、B+ 树与索引结构**
   - **存储引擎**：InnoDB 支持事务、行锁、MVCC、崩溃恢复、外键，聚簇索引组织数据；MyISAM 不支持事务、表锁，适合只读/历史归档；Memory 用哈希索引、数据在内存。
   - **B+ 树**：非叶子节点只存索引键和页指针，扇出大、树矮（百万级数据通常 3~4 层）；叶子节点有序链表连接，适合范围查询和排序；相比 B 树，B+ 树查询稳定、范围扫描高效；哈希索引只适合等值查询，InnoDB 的自适应哈希索引是自动维护的。
   - **聚簇索引**：InnoDB 主键索引叶子存整行数据；二级索引叶子存主键值，查非索引列要“回表”；覆盖索引指查询列都在索引中，`Using index` 可避免回表。
   - **索引下推（ICP）**：MySQL 5.6+ 把索引列上的条件下推到存储引擎层过滤，减少回表；`Extra: Using index condition`。
   - **延伸**：主键要短、单调，避免随机 UUID 导致页分裂；二级索引太多会增加写放大；`ORDER BY` 与索引顺序不一致会 filesort。

2. **最左前缀、索引失效与选择**
   - **最左前缀**：联合索引 `(a,b,c)` 能命中 `a`、`(a,b)`、`(a,b,c)`，范围查询后的列不能继续用于精确定位；`(a,b)` 上 `WHERE b=?` 不命中。
   - **失效场景**：列上做函数/运算、隐式类型转换（字符串列传数字）、前导 `%` 模糊、`OR` 中有非索引列、`!=`/`NOT IN` 可能全表、范围条件后继续用索引列、排序方向/顺序不匹配、选择性太低、统计信息过期、优化器估算回表成本过高。
   - **选择**：等值条件放前面、范围条件放后面；区分度高的列优先；用前缀索引控制长字符串索引体积；避免冗余/重复索引；`SHOW INDEX` 看 `Cardinality`；MySQL 8.0 支持降序索引、不可见索引、索引跳过扫描（8.0.13）。
   - **延伸**：索引不是越多越好，写多读少的表要控制；联合索引可覆盖多个查询；`FORCE INDEX` 只用于验证，不要长期依赖。

3. **EXPLAIN 与慢 SQL**
   - **关键列**：`type` 从好到差为 system/const/eq_ref/ref/range/index/ALL；`key` 实际使用的索引；`key_len` 索引使用长度；`rows` 预估扫描行数；`filtered` 过滤比例；`Extra` 看 `Using index`（覆盖）、`Using where`（回表后过滤）、`Using index condition`（ICP）、`Using filesort`（额外排序）、`Using temporary`（临时表）。
   - **分析**：`EXPLAIN ANALYZE`（8.0.18+）给实际耗时和行数；`optimizer_trace` 看成本选择；慢查询日志 + `pt-query-digest` 找 TOP SQL；`performance_schema` 看等待和锁。
   - **优化顺序**：先看数据量和选择性，再看索引，再看 SQL 写法，最后才考虑调参数；`Using filesort`/`Using temporary` 不一定是问题，数据量小可接受。
   - **延伸**：`SELECT *` 增加回表和网络传输；深分页用延迟关联/游标；批量写入分片；统计信息用 `ANALYZE TABLE` 更新。

### （二）事务、MVCC 与锁

1. **ACID 与隔离级别**
   - **ACID**：原子性靠 undo log，持久性靠 redo log，隔离性靠锁 + MVCC，一致性是业务约束 + 数据库机制共同保证。
   - **并发问题**：脏读（读到未提交）、不可重复读（同一行两次读不一致）、幻读（同一范围两次读行数不同）；隔离级别从低到高为 READ UNCOMMITTED、READ COMMITTED、REPEATABLE READ、SERIALIZABLE。
   - **MySQL**：默认 RR；RR 下快照读靠 MVCC 避免不可重复读，当前读靠 Next-Key 锁防幻读；RC 下每条语句生成新 ReadView，间隙锁基本关闭（外键/唯一性检查除外）。
   - **延伸**：隔离级别越高并发越低；互联网业务常用 RC + 应用层幂等/乐观锁，金融核心可能用 RR/串行化；binlog 为 ROW 时 RC 也能保证主从一致。

2. **MVCC 与 ReadView**
   - **隐藏列**：InnoDB 行有 `DB_TRX_ID`（最后修改事务）、`DB_ROLL_PTR`（指向 undo 版本链）、`DB_ROW_ID`（无主键时）。
   - **版本链**：每次更新把旧版本写入 undo log，`roll_ptr` 串成链表；快照读沿版本链找可见版本。
   - **ReadView**：`m_ids`（活跃事务 ID 列表）、`min_trx_id`（最小活跃）、`max_trx_id`（下一个未分配 ID）、`creator_trx_id`。判断：trx_id < min 可见；trx_id ≥ max 不可见；trx_id 在 m_ids 中不可见；否则可见；自己的修改总是可见。
   - **创建时机**：RC 每条快照读创建新 ReadView；RR 在事务第一次快照读时创建并复用，所以可重复读。
   - **当前读**：`SELECT ... FOR UPDATE`、`LOCK IN SHARE MODE`、UPDATE、DELETE 读最新已提交版本并加锁，不走快照。
   - **延伸**：长事务让 undo 版本链变长、purge 滞后，影响性能；`information_schema.innodb_trx` 看长事务；快照读与当前读混用会出现“同一事务读到不同结果”。

3. **锁类型与加锁规则**
   - **锁类型**：记录锁（Record Lock，锁索引记录）、间隙锁（Gap Lock，锁索引区间，防插入）、Next-Key Lock（记录 + 前间隙）、插入意向锁（Insert Intention，插入前设置）、意向共享/排他锁（表级，表示行锁意图）、自增锁、MDL 元数据锁。
   - **加锁规则**：唯一索引等值命中 → 记录锁；唯一索引等值未命中 → 间隙锁；范围查询 → Next-Key Lock；非唯一索引 → Next-Key Lock；无索引/索引失效 → 可能锁全表或大范围。
   - **排查**：`SHOW ENGINE INNODB STATUS` 看 LATEST DETECTED DEADLOCK；`performance_schema.data_locks`/`data_lock_waits`（8.0）；`innodb_lock_wait_timeout` 默认 50s；死锁后 InnoDB 自动回滚代价小的事务。
   - **预防**：按固定顺序访问、缩短事务、命中索引、避免大范围更新、拆批、热点行用乐观锁/队列；RC 下间隙锁少，但唯一性检查仍可能加锁。
   - **延伸**：间隙锁只在 RR 及以上明显；插入意向锁与间隙锁冲突；二级索引加锁也会锁主键；`SELECT ... FOR UPDATE` 必须走索引，否则可能锁很多行。

### （三）日志与崩溃恢复

1. **undo、redo、binlog**
   - **undo log**：逻辑日志，记录反向操作，用于回滚和 MVCC；存在 undo 表空间，purge 线程清理。
   - **redo log**：物理日志，记录页的修改，WAL 先写日志再刷脏页；固定大小、循环写；崩溃恢复重放；`innodb_flush_log_at_trx_commit` 控制刷盘。
   - **binlog**：Server 层逻辑日志，记录 SQL 或行变更，用于主从复制和时间点恢复；格式有 STATEMENT/ROW/MIXED，生产推荐 ROW；`sync_binlog` 控制刷盘。
   - **relay log**：从库接收主库 binlog 后的本地中转日志，SQL 线程重放。
   - **延伸**：redo 保证崩溃恢复，binlog 保证复制和 PITR；两者不是替代关系；`doublewrite buffer` 防止页写一半导致坏页。

2. **两阶段提交与崩溃恢复**
   - **流程**：InnoDB 写 redo 并置为 prepare → 写 binlog 并 fsync → InnoDB 提交 redo（commit）。
   - **崩溃场景**：redo prepare 后、binlog 写完前崩溃 → 回滚；binlog 写完后、redo commit 前崩溃 → 恢复时按 binlog 已落盘提交；保证 redo 和 binlog 一致。
   - **持久性**：`innodb_flush_log_at_trx_commit=1` 且 `sync_binlog=1` 是“双 1”，最安全但性能最低；0/2 提升性能但会丢最近事务。
   - **复制**：异步复制有延迟和丢失窗口；半同步复制等从库 ACK 后返回；Group Replication 基于共识，提供更强一致但配置复杂；GTID 简化主从切换和位点管理。
   - **延伸**：`binlog_format=ROW` 记录每行变更，复制一致但日志大；`binlog_row_image=MINIMAL` 减少体积；PITR 用全量备份 + binlog 回放。

### （四）SQL、Buffer Pool 与高可用

1. **SQL 写法与优化**
   - **JOIN**：MySQL 8.0.18+ 支持 Hash Join；小表驱动大表、连接列有索引；避免在连接列上做函数/隐式转换；`STRAIGHT_JOIN` 仅用于明确优化。
   - **子查询/窗口/CTE**：子查询可能物化或半连接；窗口函数适合排名、累计、分组内 TOP N；CTE 提升可读性，MySQL 8.0 支持递归 CTE。
   - **深分页**：`LIMIT 100000,20` 要扫描并丢弃前 10 万行；用延迟关联（先查主键再回表）或游标 `WHERE id > last_id LIMIT 20`；业务上限制最大页数。
   - **批量/聚合**：批量 insert 分片、`rewriteBatchedStatements`；count 用覆盖索引或维护计数表；避免大事务；`UNION ALL` 优于 `UNION`（不去重时）。
   - **延伸**：SQL 优化要结合执行计划和数据分布，不能只看语法；ORM 生成的 SQL 也要 review。

2. **Buffer Pool 与内存**
   - **Buffer Pool**：缓存数据页和索引页，减少磁盘 IO；LRU 分 young/old 区，新页插入 midpoint，全表扫描不会一次性冲掉热数据；`innodb_buffer_pool_size` 通常设物理内存的 50%~70%。
   - **Change Buffer**：对非唯一二级索引的写操作先缓存，减少随机读；唯一索引必须读页校验，不能用 change buffer。
   - **其他**：自适应哈希索引（等值查询）、doublewrite（防坏页）、log buffer、sort buffer、join buffer、临时表。
   - **延伸**：Buffer Pool 命中率低不一定是内存不足，可能是全表扫描、大查询、索引缺失；`SHOW ENGINE INNODB STATUS` 看命中率和等待。

3. **高可用、分库分表与连接池**
   - **复制**：异步复制性能好但有延迟/丢失；半同步折中；Group Replication 强一致但限制多；主从延迟导致读旧数据，读己之写用写后读主/GTID 位点/版本校验。
   - **切换**：MHA/Orchestrator/云数据库高可用；要处理脑裂、复制中断、数据补偿；切换后应用要能刷新连接。
   - **分库分表**：路由键要高基数、分布均匀、大多数查询能带上；跨片查询用广播/内存归并/冗余表/ES；扩容用双倍分片或一致性哈希，双写 + 迁移 + 对账 + 切读。
   - **连接池**：HikariCP 常用，最大连接数不是越大越好，按数据库承载和业务并发设置；设置连接超时、泄漏检测、心跳；连接池耗尽会拖垮整个服务。
   - **延伸**：ORM 不能替代 SQL/索引/事务知识；分库分表后分布式事务、全局 ID、跨片分页都要重新设计；备份、监控、慢查询治理是长期工作。

## 七、Redis 与缓存

### （一）数据结构与执行模型

1. **数据类型与底层编码**
   - **String**：SDS（简单动态字符串）记录长度、预分配空间，避免 C 字符串的 O(n) 长度计算；编码有 int、embstr、raw。适合计数、缓存对象、分布式锁、Session、Bitmap。
   - **List**：quicklist 由多个 listpack 节点组成的双向链表，兼顾内存和两端操作；适合简单队列/栈，但专业消息队列优先 Stream 或 Kafka。
   - **Hash**：元素少时用 listpack，超过阈值转哈希表；适合对象字段、购物车。
   - **Set**：整数集合 intset、小集合 listpack、大集合哈希表；适合标签、去重、交并差。
   - **ZSet**：listpack（小）或“哈希表 + 跳表”；哈希表按 member 查 score，跳表按 score 范围查询；适合排行榜、延迟队列、带权重排序。
   - **扩展类型**：Bitmap 位图做签到/布隆过滤器；HyperLogLog 用约 12KB 做基数估算（标准误差约 0.81%）；GEO 基于 geohash + ZSet 做附近的人；Stream 支持消费组、ACK、Pending List。
   - **编码阈值**：小对象默认约 128 个元素/64 字节，超过转大编码；阈值可通过 `hash-max-listpack-entries` 等参数调整，不要随意改。
   - **跳表 vs 红黑树**：跳表实现简单、范围查询自然、插入删除只需局部调整；平均 O(log n)、最坏 O(n)，层数按概率提升；Redis 单线程，不依赖并发锁。

2. **单线程模型与 IO 多线程**
   - **为什么快**：纯内存、数据结构简单、避免线程切换和锁竞争、epoll IO 多路复用、RESP 协议简单；瓶颈通常是网络和慢命令，不是 CPU。
   - **单线程含义**：命令执行是单线程串行，天然原子；一个 O(n) 命令（`KEYS`、`HGETALL` 大 Hash、`SMEMBERS` 大 Set）会阻塞所有请求；Lua 脚本也在同一线程执行，必须短小。
   - **Redis 6 多线程**：只把网络读写和协议解析放到 IO 线程，命令执行仍然单线程；解决高并发网络 IO 瓶颈，不改变原子性模型；用 `io-threads` 配置，通常 2~4 个足够。
   - **延伸**：Pipeline 减少 RTT 但不保证原子；事务 MULTI/EXEC 是串行执行但不支持回滚；Lua 可做原子复合操作；`SLOWLOG` 监控慢命令。

### （二）持久化、高可用与淘汰

1. **RDB、AOF 与混合持久化**
   - **RDB**：某时刻全量快照，`bgsave` fork 子进程，依赖 Copy-On-Write；文件紧凑、恢复快，但 fork 有内存和 CPU 开销，两次快照之间宕机会丢数据。
   - **AOF**：追加写命令，支持 `appendfsync always/everysec/no`；`everysec` 最多丢约 1 秒，`always` 最安全但性能差，`no` 交给 OS；AOF 文件会膨胀，用 `bgrewriteaof` 重写。
   - **混合持久化**：`aof-use-rdb-preamble=yes`，AOF 文件前半是 RDB 格式、后半是增量命令，兼顾恢复速度和丢失窗口；Redis 7 用 multi-part AOF（base + incr）。
   - **恢复顺序**：开启 AOF 时优先用 AOF，否则用 RDB；AOF 重写期间新命令写入重写缓冲区，避免丢失。
   - **延伸**：RDB fork 时内存可能翻倍（COW 在写入时复制页）；AOF everysec 的 fsync 由后台线程执行；持久化不是备份，仍要定期异地备份。

2. **过期删除与内存淘汰**
   - **过期删除**：惰性删除（访问时检查）+ 定期删除（周期性随机抽样，`hz`/`active-expire-effort` 控制力度）；不是精确定时器。
   - **淘汰策略**：`noeviction`（不淘汰，写入报错）、`allkeys-lru`、`volatile-lru`、`allkeys-random`、`volatile-random`、`allkeys-lfu`、`volatile-lfu`；`volatile-*` 只淘汰设置了过期时间的 key。
   - **LRU 近似**：Redis 不维护完整 LRU 链表，采样若干 key 选最久未使用的；LFU 用计数器 + 衰减，适合热点稳定的场景；`OBJECT IDLETIME/FREQ` 可查看。
   - **延伸**：缓存场景通常 `allkeys-lru` 或 `allkeys-lfu`；`noeviction` 适合当数据库用但容易写失败；淘汰会导致缓存命中率下降和雪崩，需监控 evicted_keys。

3. **主从、Sentinel 与 Cluster**
   - **主从复制**：全量同步（主库 bgsave + 发送 RDB + 缓冲增量）和增量同步（`PSYNC` + offset + replication backlog）；异步复制，主库写入成功不代表从库已落盘。
   - **Sentinel**：监控、通知、自动故障转移、配置提供；主观下线 SDOWN（单 Sentinel 判定）、客观下线 ODOWN（达到 quorum）；选举新主需要多数 Sentinel 同意；至少 3 个 Sentinel 避免单点。
   - **Cluster**：16384 个槽，`CRC16(key) mod 16384` 路由；`{tag}` 哈希标签让相关 key 落同一槽；MOVED 表示永久重定向，ASK 表示迁移中的临时重定向；节点用 gossip 传播槽和状态，故障转移需多数主节点同意。
   - **限制**：跨槽的多 key 命令、事务、Lua 不支持（除非 hash tag）；Cluster 没有强一致，异步复制可能丢写；Sentinel 是主从高可用，Cluster 是分片 + 高可用。
   - **异步复制风险**：主库宕机时未同步的写会丢；脑裂时新旧主都可能接受写；`min-replicas-to-write` + `min-replicas-max-lag` 要求至少 N 个健康副本才允许写，能缩小窗口，但副本不足时会拒绝写，牺牲可用性，且不能保证绝对不丢。
   - **延伸**：Sentinel 适合数据量小、单主；Cluster 适合大数据量和高吞吐；客户端要支持 MOVED/ASK；扩容迁移用 `redis-cli --cluster reshard`。

### （三）缓存问题与一致性

1. **穿透、击穿与雪崩**
   - **穿透**：查询不存在的数据，缓存和数据库都没有；方案是缓存空值（短 TTL 防污染）、布隆过滤器（可能误判、不能删除）、参数校验/限流。
   - **击穿**：单个热点 key 过期瞬间大量请求打到数据库；方案是互斥重建（`SETNX` 只让一个线程回源）、逻辑过期（返回旧值 + 异步重建）、热点 key 不设过期 + 后台更新。
   - **雪崩**：大量 key 同时失效或 Redis 整体不可用；方案是 TTL 加随机抖动、多级缓存、限流/熔断、集群高可用、预热。
   - **延伸**：布隆过滤器只能判断“一定不存在/可能存在”，删除要用计数布隆或重建；空值缓存要防止被大量随机 key 打爆。

2. **旁路缓存一致性**
   - **读**：先读缓存，未命中读数据库并回填；**写**：先更新数据库，再删除缓存（Cache-Aside 常用）。
   - **为什么删不是更新**：并发更新时“后到的旧值”可能覆盖新值；删除是幂等的，下一次读会回填最新值；更新缓存还可能在写多读少时做无用功。
   - **延迟双删**：更新数据库前删一次、更新后延迟再删一次，降低旧值回填窗口；延迟时间依赖主从复制和读请求耗时，无法精确，仍有不一致窗口。
   - **其他方案**：更新数据库 + 更新缓存（并发顺序问题）；binlog CDC 异步失效缓存（解耦、最终一致）；Read/Write Through；强一致要加锁/版本号或直接读主库。
   - **延伸**：Cache-Aside + TTL 是最终一致，不是强一致；热点 key 更新时可能长期读到旧值；本地缓存还要广播失效。

3. **热点 Key、大 Key 与多级缓存**
   - **热点 Key**：本地缓存、key 分片（如 `hotkey:{1..N}` 汇总）、读写分离/多副本、限流、单独集群；监控 `--hotkeys`（需 LFU）。
   - **大 Key**：拆分（Hash 分桶、List 分页）、压缩、异步删除（`UNLINK`）、避免 `KEYS`/`HGETALL`/`SMEMBERS` 全量；用 `SCAN` 系列渐进遍历；`--bigkeys` 排查。
   - **多级缓存**：Caffeine 本地 + Redis 分布式 + DB；本地缓存要短 TTL、容量上限、失效广播；一致性与命中率取舍。
   - **规范**：key 命名带业务前缀、合理 TTL、避免热 key 集中、控制 value 大小、连接池和超时、Pipeline 批量、Lua 原子、Cluster 同槽。

### （四）分布式锁

- Redis 锁的最小正确实现是 `SET lock <uuid> NX PX <ms>`，value 必须唯一；解锁用 Lua 比较 value 再删除，防止误删别人的锁；过期时间防止宕机死锁。
- Redisson 用 Hash 实现可重入，看门狗默认 30s 租约、每 10s 续期；显式 `leaseTime` 会关闭看门狗，临界区超时后锁会失效。
- 主从切换/脑裂可能双持有；`RedLock` 多数派只提升单点故障存活率，不能提供绝对互斥；关键业务用 fencing token + 数据库唯一约束/版本条件兜底，或改用 ZK/etcd。
- 详细推演见第九章“（四）分布式锁”，这里只记结论：锁是性能优化，不是数据正确性的唯一防线。

### （五）典型应用与使用规范

- **典型场景**：缓存、计数器/限流、分布式锁、Session、排行榜（ZSet）、签到（Bitmap）、UV 估算（HyperLogLog）、附近的人（GEO）、消息流（Stream）、幂等去重（SETNX）。
- **不要当数据库**：持久化有丢失窗口、内存昂贵、复杂查询弱；核心数据落 MySQL，Redis 做加速和临时状态。
- **运维**：监控命中率、延迟、内存、evicted、慢查询、主从延迟、集群槽状态；设置 maxmemory 和淘汰策略；避免 KEYS、大事务、大 Lua；客户端配超时和连接池。
- **延伸**：缓存预热、降级开关、Redis 不可用时回源限流；Cluster 下多 key 用 hash tag；Stream 消费组要处理 Pending List 和消息删除。

## 八、消息队列

### （一）作用、投递语义与选型

1. **作用与代价**
   - **作用**：异步（缩短主链路 RT）、解耦（生产者不关心消费者）、削峰（把瞬时流量缓冲到消费者能力）、广播/事件驱动、最终一致。
   - **代价**：系统复杂度上升、消息重复/乱序/丢失需要处理、端到端延迟增加、运维和排障成本增加、一致性问题从本地事务变成分布式问题。
   - **不该用的场景**：强一致且要求同步返回、低延迟敏感、调用关系简单、没有可靠投递能力；这些场景优先同步调用 + 本地事务。
   - **延伸**：MQ 是架构手段不是目的；引入前要明确“解耦什么、削什么峰、能接受多大延迟和多久不一致”。

2. **投递语义**
   - **至多一次**：先 ack 再处理，宕机丢消息；实现简单，适合允许丢的日志/监控。
   - **至少一次**：处理成功再 ack，宕机可能重复；绝大多数业务采用，消费端必须幂等。
   - **恰好一次**：端到端精确一次很难，通常靠“事务消息/幂等生产者 + 消费端幂等 + 事务性存储”组合；Kafka 的 EOS 只保证 Kafka 内部读-处理-写链路，外部系统仍要幂等。
   - **延伸**：消息重复不可避免（重试、rebalance、网络超时），幂等键要全局唯一；消息乱序要用业务版本/状态机或分区顺序。

### （二）可靠性、顺序与积压

1. **消息丢失与可靠性**
   - **生产端**：发送失败未重试、异步发送未检查结果、事务消息回滚；用同步确认、重试、本地消息表/Outbox、事务消息。
   - **存储端**：未刷盘、副本未同步、单副本故障；用持久化、多副本、`acks=all`、`min.insync.replicas`、同步刷盘。
   - **消费端**：自动 ack 后处理失败、处理一半崩溃、rebalance 丢 offset；用手动 ack（处理成功后提交）、幂等消费、消费位点管理。
   - **可靠性组合**：生产确认 + Broker 多副本/持久化 + 消费手动确认 + 死信/重试 + 对账兜底；任何一环缺失都可能丢消息。
   - **延伸**：可靠性越高吞吐越低，要在业务容忍度内取舍；资金类消息还要 T+1 对账。

2. **顺序消息**
   - **全局有序**：单分区/单队列 + 单消费者，吞吐受限，几乎不用于高并发。
   - **分区有序**：按业务键（订单号、用户 ID）选择分区/队列，保证同一 key 的顺序；不同 key 可并行。
   - **消费端**：多线程消费同一分区会破坏顺序；需要单线程消费或按 key 再哈希到工作线程。
   - **延伸**：重试可能改变顺序，失败消息要阻塞后续或进入死信；顺序消息与扩容/重平衡冲突，要评估分区数和消费并行度。

3. **重试、死信与积压**
   - **重试**：只重试可恢复错误（超时、限流、临时不可用），不可恢复错误直接进死信；指数退避 + 最大次数，避免重试风暴。
   - **死信**：记录原因、原消息、重试次数，提供人工/定时重放；死信队列要有告警和消费。
   - **积压**：监控 lag/堆积量、消费速率、处理耗时；扩容消费者受分区数限制；优化慢处理、批量、降级非核心、临时跳过/回放。
   - **延伸**：积压时先判断是“生产突增”还是“消费变慢”；盲目扩容可能压垮下游数据库；回放要限速并幂等。

### （三）Kafka

1. **架构、存储与生产消费**
   - **核心概念**：Broker、Topic、Partition、Replica、Leader/Follower、Offset、Consumer Group、Coordinator；一个分区同一时刻只有一个 Leader，消费者组内一个分区只被一个消费者消费。
   - **存储**：分区追加写 Commit Log，分段 + 稀疏索引；顺序写、页缓存、批量、压缩；零拷贝 `sendfile` 把页缓存直接送到 socket，减少用户态拷贝。
   - **生产**：分区器按 key 哈希或轮询；`acks=0/1/all`；重试；幂等生产者（`enable.idempotence=true`）避免重试重复；事务生产者支持 EOS。
   - **消费**：poll 循环拉取，`max.poll.records` 控制单次批量，`max.poll.interval.ms` 超时会触发 rebalance；手动提交 offset 更可靠；`seek` 可重置位点。
   - **延伸**：Kafka 是拉模型，消费者按能力消费；分区数决定最大并行度；key 为 null 时轮询，难以保证顺序。

2. **副本、ISR 与 Rebalance**
   - **副本**：每个分区有 Leader 和多个 Follower，Follower 追 Leader；ISR 是与 Leader 保持同步的副本集合；HW 是消费者可见的最大 offset，LEO 是日志末尾。
   - **可靠性**：`acks=all` 要求所有 ISR 写入；`min.insync.replicas>=2` 防止 ISR 只剩一个时仍接收写；`unclean.leader.election.enable=false` 防止落后副本当 Leader 造成丢数据；副本数通常 3。
   - **Rebalance**：Eager 模式先全部撤销再重新分配，停顿大；Cooperative Sticky 增量迁移，减少停顿；静态成员（static membership）减少滚动重启触发的 rebalance。
   - **延伸**：rebalance 期间消费可能暂停，要缩短 `max.poll.interval` 内的处理时间；分区分配策略有 Range/RoundRobin/Sticky；KRaft 模式逐步取代 ZooKeeper。

### （四）RocketMQ、RabbitMQ 与选型

1. **RocketMQ**
   - **架构**：NameServer 做轻量路由，Broker 存消息，Producer/Consumer 客户端；CommitLog 顺序写，ConsumeQueue 逻辑队列，IndexFile 支持按 key 查询。
   - **事务消息**：先发半消息（对消费者不可见）→ 执行本地事务 → 提交/回滚 → 未确认时 Broker 回查本地事务状态；解决“本地事务与发消息”一致。
   - **延迟/顺序**：延迟消息支持固定级别（1s~2h，18 档），5.x 支持任意延迟；顺序消息按队列选择器保证同一 key 落同一队列。
   - **可靠性**：同步/异步刷盘、主从同步/异步复制、DLedger raft；消费失败重试，超过次数进 `%DLQ%` 死信。
   - **延伸**：RocketMQ 在国内电商、交易场景常用，事务/延迟/顺序能力比 Kafka 更贴近业务；吞吐略低于 Kafka。

2. **RabbitMQ**
   - **模型**：Exchange（direct/fanout/topic/headers）+ Queue + Binding + Routing Key；生产者发到 Exchange，按规则路由到队列。
   - **可靠性**：publisher confirm 确认到达 Broker，mandatory 处理不可路由消息；消费者手动 ack/nack，prefetch 控制未确认数量；DLX + TTL 做延迟/死信。
   - **高可用**：经典镜像队列逐步被 Quorum Queue（Raft）替代；懒队列减少内存占用；适合复杂路由、低延迟、中小规模。
   - **延伸**：RabbitMQ 单队列多消费者会破坏顺序；吞吐不如 Kafka/RocketMQ；Erlang 生态运维门槛较高。

3. **选型矩阵**

| 维度 | Kafka | RocketMQ | RabbitMQ |
| --- | --- | --- | --- |
| 吞吐 | 最高，适合日志/流 | 高，适合交易 | 中等 |
| 延迟 | 较低 | 低 | 低 |
| 顺序 | 分区内有序 | 队列内有序 | 队列内有序 |
| 事务消息 | 支持 EOS | 原生事务消息/回查 | 无原生事务消息 |
| 延迟消息 | 需外部方案 | 原生支持 | TTL + DLX |
| 路由 | 简单 | 较简单 | 最灵活 |
| 典型场景 | 日志、埋点、流处理 | 电商、订单、支付 | 业务解耦、复杂路由 |

- **选型维度**：吞吐、延迟、顺序、事务、延迟消息、路由能力、运维生态、团队熟悉度；不要只看 benchmark。
- **延伸**：Pulsar 支持多租户、分层存储、统一消息/流；云厂商托管可降低运维成本；任何 MQ 都要监控 lag、死信、重试和消费耗时。

## 九、分布式与微服务

### （一）基础理论与架构设计

1. **CAP 定理与 BASE 理论**
   - **考点**：C 是一致性（所有节点同一时刻读到相同数据，接近线性一致），A 是可用性（每个请求在合理时间内得到非错误响应），P 是分区容错（节点间网络断开时系统仍能运行）。网络分区无法避免，P 必须保证，实际只能在分区发生时选择 CP 或 AP。
   - **CP**：拒绝请求或等待，保证数据不出错；ZooKeeper（选举期间不可写）、etcd、Nacos 持久实例。
   - **AP**：继续响应，可能返回旧数据，之后再同步；Eureka、Nacos 临时实例（默认）、Redis Cluster、Cassandra。
   - **取舍**：注册中心选 AP——服务列表短暂不一致只会让少量请求失败、可以重试，注册中心整体不可用会让所有服务无法发现彼此；分布式锁、选主、余额/库存扣减必须选 CP，或落到单库事务与唯一约束。
   - **延伸**：BASE 是对 AP 的工程延伸——基本可用（BA，降级、限流、响应变慢）、软状态（S，允许“支付中”等中间态）、最终一致（E，停止写入后副本收敛）。缓存双写、主从复制、MQ 异步、TCC/Saga 都是最终一致。Quorum（多数派）是 CP 的实现基础，NWR 模型中 `W + R > N` 才能保证读写集合相交，但还需版本号或读修复，不等于线性一致。
   - **面试落点**：不要只背“C/A/P 三选二”，要说清 P 必选、分区时选 C 还是 A，并给出注册中心与锁的具体例子。

2. **一致性模型与读己之写**
   - **考点**：强一致（可串行化 + 实时顺序）> 线性一致 > 顺序一致 > 因果一致 > 最终一致。线性一致是单对象、操作在真实时间轴上原子生效；顺序一致只要求所有进程看到相同顺序，不要求与真实时间一致；因果一致只保证有因果关系的操作有序。
   - **延伸**：工程上更常用会话级保证——读己之写（提交后自己一定能看到）、单调读（不会越读越旧）、单调写、读后写（基于读到的版本写）。主从延迟下实现读己之写有四种手段：写后 N 秒读主、按用户路由到主库、记录 GTID/binlog 位点并 `WAIT_FOR_EXECUTED_GTID_SET`、写返回版本号后读时校验版本。
   - **落地**：账户余额/库存需要线性一致或单库事务；订单状态、个人资料只需读己之写 + 单调读；Feed、点赞数可接受最终一致；跨服务组合查询分别保证单对象一致性，前端展示“确认中”。

3. **共识协议与协调服务**
   - **考点**：Raft 把共识拆成 Leader 选举（任期 + 随机选举超时 + 过半投票）、日志复制（写只发 Leader，过半落盘即提交）、安全性（只有日志不旧于多数派的 Candidate 才能当选）。节点数用奇数：3 节点和 4 节点都只能容忍 1 台故障，多数派机制天然防止脑裂。
   - **ZAB/ZooKeeper**：ZAB 分崩溃恢复和消息广播（Proposal → 过半 ACK → Commit）；ZNode 有持久、临时、顺序类型，会话超时后临时节点自动删除，Watch 一次触发后失效；选举比较 `(zxid, myid)`，Observer 不参与投票。ZK 是 CP，Leader 选举期间不可写。
   - **etcd**：Raft + lease（到期自动删 key）+ 全局单调 revision + 前缀 Watch，K8s 用它存集群状态；revision 可当 fencing token。
   - **延伸**：Paxos 是更早的通用共识算法，Multi-Paxos 用 Leader 复用第二阶段；Raft 为易理解而设计，ZAB 靠 zxid 做恢复。注册中心选 Nacos/Eureka 而非 ZK，正是因为 ZK 选举期间不可用；分布式锁、选主才用 ZK/etcd。

4. **微服务拆分原则**
   - **考点**：单一职责、高内聚低耦合、数据自治（每个服务独立库，禁止跨服务直接访问对方表）、业务边界清晰（DDD 限界上下文）、可独立部署、粒度与团队规模匹配。
   - **拆分方式**：按业务能力/限界上下文拆，不按技术分层拆（controller/service/dao 各一个服务是典型反模式）；一个需求尽量只改一个服务，同步调用链尽量短。
   - **延伸**：拆得太细的代价是跨服务调用、分布式事务、链路排障和运维成本成倍增加，容易变成“分布式单体”；小团队、业务初期用单体或模块化单体更合适。单体与微服务的差异主要在独立部署/独立扩容/故障隔离/技术异构，与本地事务简单/排障简单之间取舍。
   - **数据边界**：强一致的数据尽量放同一个服务同一个库，从源头避免分布式事务；跨服务只保留业务上可最终一致的关联。

### （二）微服务架构与核心组件

1. **注册中心**
   - **考点**：服务启动注册地址、定时心跳；调用方拉取并缓存列表，变更由服务端推送。注册中心全挂时，已有调用仍能靠本地缓存继续，这是 AP 设计的价值。
   - **Nacos**：临时实例（默认）靠客户端心跳保活、超时剔除，用 Distro（AP）；持久实例由服务端探测、不健康也不删除，用 Raft（CP）；2.x 改为 gRPC 长连接，推送更及时。
   - **对比**：Eureka 只做注册、AP、已停止迭代；ZK 是 CP、选举期间不可用；Consul 是 CP（Raft）且支持多数据中心；Nacos 同时支持 AP/CP 并兼作配置中心。
   - **延伸**：Eureka 自我保护——短时间大量心跳丢失时不剔除实例，避免网络抖动误删健康实例，要区分“实例下线”和“实例不健康”。优雅下线要先注销/摘流量，等在途请求结束再停进程。注册中心还要有鉴权、命名空间隔离和实例元数据（版本、权重、机房），供灰度路由使用。

2. **配置中心**
   - **考点**：Nacos 用“命名空间（环境）+ Group（项目）+ DataId（文件）”三级隔离；动态刷新靠 1.x 长轮询（客户端挂起 30s，有变更立即返回）或 2.x gRPC 推送；`@RefreshScope` 重建 Bean，`@ConfigurationProperties` 绑定更轻量。
   - **延伸**：配置中心不只是“存配置”，还要有变更审计、版本回滚、灰度发布、权限隔离、敏感配置加密、客户端本地快照容灾（服务端不可用时用本地缓存启动），并能秒级推送到指定实例。
   - **坑**：`@RefreshScope` 对单例 Bean 是代理重建，刷新期间可能拿到旧值；数据库连接池、线程池等资源型配置刷新后需要重建，不能只改字段；配置错误要有兜底默认值和告警。

3. **API 网关**
   - **考点**：网关是所有外部请求的统一入口，负责路由、鉴权、限流、日志、灰度、协议转换，让业务服务不重复实现。
   - **Gateway 三概念**：Route（目标服务）、Predicate（匹配条件，如 `Path=/order/**`）、Filter（转发前后处理）。GlobalFilter 作用于所有路由；全局与路由过滤器合并后按 `getOrder()` 排序，请求正序执行 pre、响应逆序执行 post。
   - **模型**：基于 WebFlux + Reactor Netty 的非阻塞事件循环，少量线程扛大量连接，**过滤器里绝对不能有阻塞操作**（同步查库、同步 HTTP），否则吞吐崩溃；Zuul 1 是同步阻塞，每请求占一个线程。
   - **限流**：`RequestRateLimiter` 基于 Redis + Lua 实现分布式令牌桶，`replenishRate` 是每秒补充、`burstCapacity` 是桶容量，`KeyResolver` 决定按用户/IP/路径限流，超限返回 429。
   - **延伸**：与 Nginx 分工——Nginx 做入口、SSL 终止、静态资源、基础负载均衡，Gateway 在其后做业务级鉴权与路由；动态路由可放配置中心热更新。全链路灰度要求标签沿 Feign/Dubbo/MQ 透传，否则只在网关生效。

4. **服务调用（Feign / RPC / Dubbo / gRPC）**
   - **考点**：Feign 是声明式 HTTP 客户端，`@FeignClient` 启动时注册为 FactoryBean，用 JDK 动态代理生成实现，调用时把注解解析成 HTTP 请求，由 LoadBalancer 从注册中心选实例。要配连接/读取超时，用 `RequestInterceptor` 透传 Token/TraceId，用 OkHttp/Apache HttpClient 连接池替换默认 `HttpURLConnection`。
   - **RPC 流程**：本地代理 → 序列化 → 注册中心取地址 + 负载均衡 → 网络传输（Netty）→ 服务端反序列化 → 反射调用 → 序列化结果返回。
   - **Dubbo 暴露/引用**：Provider `ServiceConfig.export()` 先本地暴露（InjvmProtocol）再远程暴露（Invoker → Protocol → Netty → 注册 URL）；Consumer `ReferenceConfig.get()` 订阅 → Directory → Cluster（容错）→ Router → LoadBalance → `Protocol.refer` 建长连接。
   - **容错与负载**：Failover（默认，适合读）、Failfast（非幂等写）、Failsafe（日志）、Failback（后台重发）、Forking（并行取首个成功）；Random（默认）、RoundRobin、LeastActive、ConsistentHash（默认 160 虚拟节点）、ShortestResponse。
   - **协议/序列化**：Feign 用 HTTP/1.1 + JSON；Dubbo 用自定义 TCP + Hessian2（Dubbo 3 的 Triple 兼容 gRPC）；gRPC 用 HTTP/2 + Protobuf，支持流式与多语言。选型看跨语言、体积性能、字段增删兼容性。
   - **线程模型**：IO 线程只做读写编解码，业务派发到业务线程池；Dispatcher 有 all/direct/message/execution 四种，业务池打满会 `RejectedExecutionException`，不能让慢业务反压 IO 线程。
   - **延伸（三态）**：一次调用只有成功、失败、未知三种结果。超时/连接重置属于未知，可能是请求没到、正在执行、执行完响应丢失，**不能当失败直接重试**；要用幂等键 + 主动查询 + 中间态 + 对账收敛。重试只用于明确失败且幂等的接口。

5. **服务治理（限流、熔断、降级、隔离、超时重试）**
   - **雪崩成因**：下游变慢 → 调用方线程阻塞 → 线程池/连接池耗尽 → 调用方也不可用 → 故障沿链路向上蔓延。
   - **限流算法**：固定窗口简单但有临界问题（窗口交界可过 2 倍流量）；滑动窗口把窗口切格统计，解决临界问题；漏桶固定速率流出，绝对平滑但不允许突发；令牌桶按速率放令牌、允许桶内积累的突发，最常用（Guava `RateLimiter`）。
   - **Sentinel**：资源对应 Slot Chain（统计 → 系统 → 限流 → 熔断，顺序不能乱）；滑动窗口用 LeapArray 环形数组（默认 1s 切 2 桶），统计近似、无锁；流控模式有直接/关联/链路（链路模式需 `web-context-unify=false`）；效果有快速失败、Warm Up（`coldFactor` 默认 3）、排队等待；熔断策略有慢调用比例、异常比例、异常数，并有最小请求数护栏。
   - **熔断三态**：Closed 正常统计；Open 达到失败率/慢调用比例阈值后直接走降级；经过熔断时长进入 Half-Open，放行少量探测，成功回 Closed，失败回 Open。
   - **降级**：被动降级是熔断/异常时返回默认值、缓存值或友好提示；主动降级是大促前关闭评论、积分、实时推荐等非核心功能，把资源让给下单支付。限流保护自己，熔断避免被下游拖垮，降级是发生后的有损处理。
   - **超时**：必须设置，参考下游 P99；越靠近入口超时越长（网关 > 上游 > 下游），并给整条链路留预算，避免下游还在处理上游已放弃。
   - **重试**：只对幂等接口；只在一层重试，指数退避 + 随机抖动 + 重试预算；多层各重试 3 次会放大到 27 倍，形成重试风暴。Feign 默认不重试，Dubbo 默认 Failover 重试 2 次，写接口要改 Failfast 或保证幂等。
   - **隔离与负载**：线程池隔离、信号量隔离（Sentinel 并发线程数）、核心/非核心独立部署；负载均衡有轮询、加权、随机、最少活跃/最小连接、一致性哈希、最短响应。一致性哈希增节点迁移约 `1/(N+1)`、删节点约 `1/N`，取模接近全量；虚拟节点缓解倾斜，但不解决热点 key。
   - **发布**：蓝绿两套环境切换、灰度按比例/用户/地区放量、滚动逐批替换；灰度要能快速回滚并观察错误率与延迟。

6. **链路追踪与可观测性**
   - **考点**：Trace 是一次请求的完整调用链，TraceId 全局唯一；Span 是链上一个操作（RPC、SQL），有 SpanId、父 SpanId、开始时间、耗时和标签，所有 Span 构成树，能直接看出哪一步慢。
   - **透传**：跨服务把 TraceId + 当前 SpanId 放 HTTP Header（W3C `traceparent`）或 RPC 附件；服务内存 ThreadLocal；MQ 放消息头。
   - **跨线程丢失**：异步任务、线程池里 ThreadLocal 取不到 TraceId，要用 TransmittableThreadLocal 包装线程池，或用链路组件提供的线程池装饰器；`CompletableFuture` 每个阶段也要显式传递。
   - **实现**：SkyWalking 用 Java Agent + ByteBuddy 字节码增强，无侵入，自带拓扑/性能分析/告警；OpenTelemetry 是 CNCF 统一标准，API/SDK/Agent 采集后可导出到 Jaeger、Tempo、SkyWalking；Spring Boot 3 用 Micrometer Tracing 取代 Sleuth。
   - **采样与日志**：全量采集成本高，按比例采样，对报错和慢请求尾部全量保留；日志用 MDC 打印 `%X{traceId}`，采集到 ELK/Loki，按 TraceId 串起所有服务日志。
   - **指标**：Actuator + Micrometer → Prometheus 拉取 → Grafana 展示 → Alertmanager 告警；关注黄金指标——流量、错误率、P99 延迟、饱和度（CPU/线程池/连接池）。告警只对影响用户的症状告警，避免告警疲劳。

### （三）分布式事务

1. **方案总览与 2PC/3PC**
   - **背景**：拆分后一次业务要改多个服务的库（下单扣库存、扣余额），本地事务无法保证；方案分刚性事务（2PC/XA，强一致、持锁）和柔性事务（TCC/Saga/可靠消息，最终一致）。互联网业务绝大多数用柔性事务。
   - **2PC**：Prepare 阶段各参与者执行但不提交、加锁并投票；Commit/Rollback 阶段按全体投票决定。协调者在一阶段后宕机，参与者进入 in-doubt 状态一直持锁；决议阶段宕机可能出现部分提交、部分未提交。三个固有问题：同步阻塞、协调者单点、数据不一致。
   - **3PC**：在 Prepare 前加 CanCommit 只询问不执行，并引入超时自动决策（PreCommit 超时回滚、Commit 超时提交）；但如果协调者只通知了部分参与者就宕机，收到与未收到的一方仍会做出相反决定，依然不一致，且多一次往返，工程上基本不用。
   - **XA**：MySQL 的 `XA START/END/PREPARE/COMMIT` 是 2PC 标准实现，`PREPARE` 后连接和行锁一直不释放，RT 高、连接池易耗尽，只适合短事务低并发；`XA RECOVER` 查看 in-doubt 分支。
   - **面试落点**：2PC 保证提交决议的原子性，但保证不了决议送达的原子性；线上优先 TCC/Saga/可靠消息，只有数据库同构、事务短、并发低的内部系统才考虑 XA。

2. **Seata AT 模式**
   - **考点**：TC（独立部署的 Seata Server）、TM（`@GlobalTransactional` 发起方）、RM（各参与方数据源代理），XID 随调用链透传。
   - **一阶段**：RM 解析 SQL，记录 before image，执行业务 SQL，记录 after image，把前后镜像写入 `undo_log`，与业务数据在同一个本地事务提交；提交前向 TC 申请该行全局锁，本地锁提交后即释放，所以比 XA 性能高。
   - **二阶段**：全部成功则异步删 `undo_log`、释放全局锁；任一失败则用 before image 生成反向 SQL，回滚前校验当前数据与 after image 一致，不一致说明被全局事务外的操作改过，必须告警人工处理。
   - **局限**：只支持有本地 ACID 的关系型数据库；全局锁在热点行（库存、余额）上串行化写入，高并发易阻塞甚至雪崩；默认读未提交隔离，需要读已提交时用 `SELECT ... FOR UPDATE`；全局事务外的本地事务不受全局锁约束，可能脏写。
   - **适用**：低侵入、想快速接入、并发不高的通用业务；高并发热点行改用 TCC 或 Redis 预扣 + 异步落库。

3. **TCC（Try-Confirm-Cancel）**
   - **考点**：Try 检查并预留资源（余额 100 → 可用 70、冻结 30），Confirm 使用预留资源真正执行，Cancel 释放预留资源；Try 全成功才 Confirm，否则 Cancel，Confirm/Cancel 失败会不断重试。
   - **三大坑**：幂等（Confirm/Cancel 会被重试，用事务控制表记录分支状态）；空回滚（Try 因超时没执行却收到 Cancel，Cancel 发现无 Try 记录就插入“已回滚”记录并返回成功）；悬挂（Cancel 先执行、延迟的 Try 后到，Try 执行前检查已有“已回滚”记录就拒绝）。
   - **延伸**：TCC 无全局锁、抗压能力强，适合资金扣款、库存扣减等高并发核心链路；代价是业务侵入高（每个操作写三个方法）、要处理预留资源的一致性、Confirm 必须成功（失败要重试/告警/人工）。与 AT 的区别是用资源预留换取更高的并发和更弱的隔离依赖。
   - **注意**：Try 不是“冻结越多越好”，预留粒度要能覆盖业务失败时的补偿；Cancel 必须能释放全部预留，不能有中间态残留。

4. **Saga 模式**
   - **考点**：把长事务拆成多个本地事务 T1…Tn，每步有补偿 C1…Cn；任一步失败按反序执行已完成步骤的补偿。每步直接提交，没有预留阶段，所以不保证隔离性，其他事务能看到中间状态。
   - **编排方式**：协同式（服务间发事件）和编排式（中心协调器按状态机执行，Seata Saga 是后者）。
   - **适用**：长流程、跨服务多、无法长期预留资源的场景，如订单履约、旅行预订、审批流；补偿操作必须幂等，且业务要能接受“中间态可见”。
   - **与 TCC 的区别**：TCC 有 Try 预留、准隔离；Saga 无预留、无隔离，靠补偿回滚，适合无法预留的资源（如已出票、已发货）。

5. **本地消息表 / 事务消息 / Outbox**
   - **考点**：把跨库操作拆成“本地事务 + 消息”，业务数据和消息记录在同一个本地事务里提交，再由投递器/定时任务发到 MQ，发送失败重试；下游消费用唯一索引/去重表保证幂等。上游保证“消息一定发出”，下游保证“一定消费成功”，整体最终一致。
   - **实现方式**：本地消息表 + 定时轮询投递；RocketMQ 事务消息用半消息 + 事务回查（本地事务成功才提交半消息）；Outbox + CDC（Debezium 订阅 binlog）避免轮询延迟。
   - **优势**：无全局锁、性能最好、可削峰；是生产环境保障最终一致性的常用方案。
   - **边界**：要求下游业务上“不会失败”（只会暂时失败）；如果下游可能因余额不足等业务原因失败并需要上游回滚，应改用 TCC/Saga。消息可能重复、可能乱序，消费端必须幂等并按业务版本/状态机处理顺序。

6. **最大努力通知**
   - **考点**：有限次重试 + 接收方主动查询 + 双方对账；只承诺“尽力通知”，不承诺必达、不承诺顺序、不承诺只通知一次。
   - **与可靠消息的区别**：谁承担送达责任。可靠消息由上游用本地事务 + 消息表/MQ 保证必达，失败无限重试；最大努力通知把兜底交给接收方查询和对账，上游只负责按阶梯退避推有限次（如 1min/5min/15min/30min/1h…，总量 8~10 次，24h 上限）。
   - **落地**：通知表记录 bizNo、notifyNo、nextTime、status，接收方按 bizNo 幂等；状态机只前进不回退，终态以查询/对账为准，通知只做加速；资金类仍必须 T+1 对账 + 差异工单。
   - **适用**：支付回调、跨公司系统对接、物流/开票等弱一致通知；秒杀库存回补等时效敏感场景不能用它。

7. **选型矩阵**

| 方案 | 一致性 | 性能 | 业务侵入 | 适用场景 |
| --- | --- | --- | --- | --- |
| 2PC / XA | 强一致 | 低，全程持锁 | 低 | 短事务、低并发、同构数据库 |
| Seata AT | 最终一致，有全局锁 | 较高 | 低，注解 + `undo_log` | 通用业务、快速接入、并发不高 |
| TCC | 最终一致 | 高，无全局锁 | 高，每个操作三个方法 | 资金、库存等高并发核心链路 |
| Saga | 最终一致，无隔离 | 高 | 中，需要补偿 | 长流程、跨系统、无法预留资源 |
| 本地消息表 / 事务消息 / Outbox | 最终一致 | 高 | 中 | 下游必达、可异步、可削峰 |
| 最大努力通知 | 弱，靠查询 + 对账兜底 | 高 | 低 | 跨公司通知、支付回调 |

- **选型顺序**：能不用分布式事务就不用（把强一致数据放同一服务同一库）→ 能异步就用可靠消息 → 资金/库存在高并发下用 TCC → 长流程用 Saga → 想快速落地用 Seata AT → 跨公司结果通知用最大努力通知 + 对账。

### （四）分布式锁

1. **目标与单机锁的差异**
   - 五条要求：互斥；不死锁（宕机自动释放）；谁加锁谁解锁；业务没完锁不能提前失效；可重入、公平、阻塞等待（进阶）。
   - 单机锁在 JVM 内，靠对象头/AQS；分布式锁状态在外部存储，每次加锁都是远程写，必须假设“请求超时但服务端可能已成功”，所以需要唯一持有者标识、过期时间、幂等和 fencing。
   - 多实例部署后 `synchronized` 完全失效，这是引入分布式锁的唯一理由；能靠数据库唯一约束/状态机解决的，不要引入锁。

2. **数据库方案**
   - 唯一索引锁表：`resource` 唯一，`INSERT` 成功即持锁，`DELETE` 释放；要带 `owner` 防止误删，带 `expire_at` + 定时清理防死锁；不引入新组件、最可靠，适合兜底和低并发。
   - `SELECT ... FOR UPDATE`：必须在显式事务内，where 要走索引，否则锁全表或大范围间隙；长事务占连接、热点行排队。
   - 乐观锁：`UPDATE ... WHERE version = ?` 或带前置状态条件，无锁等待、天然幂等，适合短事务低冲突；冲突高时重试成本高。
   - **定位**：数据库锁适合低并发和“最后一道数据防线”，不是高并发互斥的首选；唯一索引与 version 校验不会因主从切换失效。

3. **Redis 方案（Redisson）**
   - 演进：`SETNX`（宕机死锁）→ `SETNX + EXPIRE`（非原子）→ `SET NX PX`（可能误删他人锁）→ value 放 `UUID:threadId` + Lua 比较删除 → 加看门狗续期。
   - 加锁必须一条命令：`SET lock <uuid> NX PX 30000`；解锁必须 Lua 原子比较 value 再删；value 不能是固定 `1`。
   - Redisson 可重入：用 Hash，key 是锁名，field 是 `UUID:threadId`，value 是重入次数；加锁 Lua 分“不存在则 hset 1 并设过期 / 是自己的 field 则 hincrby / 否则返回 TTL”，解锁减到 0 才删 key 并发布释放消息。
   - 看门狗：不指定 `leaseTime` 时默认 30s 租约，后台每 10s（1/3）续期；显式 `leaseTime` 会关闭看门狗，临界区超时后锁直接失效；`unlock()` 放 finally 并校验 `isHeldByCurrentThread()`。
   - **主从丢锁**：A 在主库加锁成功，主库未同步就宕机，哨兵提升从库，B 在新主加锁成功，A/B 双持有；脑裂时新旧主各接受加锁同样双持有。`min-replicas-to-write` 只能收窄窗口，代价是副本不足时拒绝写入。
   - **RedLock**：5 个完全独立节点，多数派成功且总耗时 < ttl 才算成功；争议在于 GC 停顿可能超过 ttl，A 醒来仍会写，而 RedLock 不提供 fencing；Kleppmann 认为不能保证互斥，antirez 认为这是所有带过期锁的通病；实践结论是提升单点故障存活率，不是绝对互斥。
   - **正确姿势**：接受极小概率双持有，在数据层用唯一索引、version、状态机兜底；关键业务用 fencing token（单调递增，etcd revision / ZK zxid / Redis INCR），写库时带 `last_token < token` 条件，拒绝旧持有者的写入；要求绝对互斥改用 CP 系统。

4. **ZooKeeper / etcd 方案**
   - ZK：锁目录下创建临时顺序节点，序号最小者持锁；未抢到的只监听前一个节点的删除事件（避免惊群），前驱释放后重新判断，天然公平；会话超时后临时节点自动删除，无需过期参数；Curator `InterProcessMutex` 封装重入、重试、Watcher 重注册。
   - ZK 边界：每次加解锁都经过 Leader 与过半同步，延迟毫秒级、吞吐远低于 Redis；Leader 选举期间不可写；GC 停顿可能让会话过期而客户端仍以为持锁，临界区要短、写操作要幂等。
   - etcd：lease 租约 + `txn` CAS（`CreateRevision == 0` 才写入）+ 全局单调 revision（可当 fencing token）+ 前缀 Watch；K8s 生态常用，运维比 ZK 轻。

5. **工程细节与选型**
   - 锁粒度：锁业务资源 ID，不要锁整个接口/整张表；热点库存按分段（如 100 段）加锁后汇总；读多用读写锁。
   - 事务边界：锁必须在事务外获取、事务提交后释放；`@Transactional` 方法内 unlock 会先释放锁后提交，别人可能读到旧值；需要时用 `TransactionSynchronizationManager` 在 `afterCompletion` 释放。
   - 续期失败要主动放弃写入；Redis 不可用可降级为“本地锁 + 数据库唯一约束”，要有开关、告警和恢复策略；监控加锁失败率、等待时长、持锁时长、续期次数、解锁失败。
   - 选型：日常高并发用 Redisson + 数据库兜底；资金/库存核心链路用 ZK/etcd + fencing；低并发/兜底用数据库唯一索引；任何方案临界区写操作都要幂等。

### （五）接口幂等

1. **幂等语义与重复来源**
   - 重复来源：用户重复点击、网络超时重试、MQ 重复投递、第三方回调重发、网关重试。
   - 天然幂等：查询、删除（结果已不存在也返回成功）、`UPDATE SET x = 5`；不幂等：`UPDATE SET x = x + 1`、`INSERT`、扣库存。
   - 幂等目标：同一请求执行一次和执行多次对业务状态的影响相同；不是“不报错”，而是“结果一致”。

2. **实现方案**
   - Token：进入页面先取 token 存 Redis，提交时带上，服务端 Lua“判断存在并删除”，删除成功才处理；适合前端防重复提交，token 要一次性且有过期时间。
   - 唯一索引：订单号、支付流水号等业务唯一键建唯一索引，重复插入报错即视为已处理；新增类最可靠，能兜住并发。
   - 状态机：`UPDATE ... WHERE status = '待支付'`，影响行数为 0 说明状态已流转；适合订单、支付回调。
   - 乐观锁：`WHERE version = ?`，适合更新类；冲突高时重试要有上限。
   - 去重表：请求 ID/幂等号与业务数据在同一事务写入，唯一索引兜底；通用性强，要注意保留期限和清理。
   - 结果缓存：幂等号对应的处理结果缓存一段时间，重复请求直接返回同一结果，避免“第一次成功、第二次报错”。

3. **组合落地**
   - 支付/退款：要求调用方传幂等号（商户订单号），服务端唯一索引 + 状态机 + 查询接口；回调可能重复/乱序，状态只前进不回退。
   - MQ 消费：消息自带业务唯一键，消费前查去重表或靠唯一索引，处理成功后再 ack；失败重试不能产生副作用。
   - RPC 未知态：超时不能直接重试，先按幂等键查询下游结果，再决定重试或补偿；对账兜底。
   - 设计要点：幂等键要全局唯一且能定位业务（租户 + 业务类型 + 业务单号）；保留期要覆盖重试/回调窗口；“先查后插”在并发下不可靠，必须有唯一约束。

### （六）分布式 Session

1. **问题与方案对比**
   - 多实例部署后请求可能落到不同节点，存在本地内存的 Session 不通用；扩容、宕机、灰度都会让粘性会话失效。
   - 会话保持（粘性）：网关按 IP/Cookie 哈希固定实例，简单但扩容/宕机丢会话、负载不均。
   - Session 复制：容器间广播同步，节点多时网络和内存开销大，只适合小集群。
   - 集中存储：Spring Session 把 Session 写 Redis，主流方案；要注意序列化和过期。
   - Token/JWT：服务端不存会话，客户端携带凭证；严格说不是 Session，但能替代；吊销困难，需要短期 access token + refresh token + 服务端撤销名单。

2. **Spring Session + Redis 细节**
   - `SessionRepositoryFilter` 包装 `HttpServletRequest`，把 `getSession()` 替换为 Redis 实现，按 sessionId 存 Hash，另有过期索引清理。
   - 存入对象必须可序列化，多服务共享优先 JSON，避免 JDK 序列化因类版本不一致失败；`spring.session.timeout` 要小于 Redis key 的 TTL；注销时同步删除 Redis 会话。
   - 安全：登录成功后更换 Session ID 防会话固定；Cookie 加 `HttpOnly`/`Secure`/`SameSite`；限制并发登录用 `SessionRegistry`；跨域场景注意 SameSite 与 CORS 配置。

### （七）高并发系统设计

1. **分层削峰与总体思路**
   - 总思路：让尽量少的请求到达数据库，每层拦截/缓冲一部分，最后只剩必要写入。
   - 客户端：按钮置灰、验证码/答题打散、本地缓存；CDN：静态资源、页面静态化；接入层：限流、黑名单、防刷、按用户/IP 限频；应用层：本地 + Redis 多级缓存、MQ 异步、线程池隔离、熔断降级；数据层：读写分离、分库分表、热点分段、批量写入。

2. **指标与容量评估**
   - QPS、TPS、RT（看 P99 不看平均）、并发数；Little 定律：并发数 ≈ QPS × 平均 RT（如 2000 QPS × 50ms ≈ 100 个在途请求），可用来估线程池/连接池。
   - 峰值估算：日活 × 人均请求 → 日总量；按 80% 流量集中在 20% 时间算峰值 QPS，再乘 2~3 倍冗余。
   - 压测：JMeter/wrk 压单机得到 RT 不劣化时的最大 QPS → 机器数 = 峰值 QPS ÷ 单机 QPS + 余量；生产全链路压测用影子表/压测标记发现 DB、缓存、MQ 瓶颈。

3. **缓存与数据库**
   - 多级缓存：本地缓存（Caffeine）扛热点 + Redis 扛共享；注意本地缓存一致性（失效广播/短 TTL）和容量。
   - 缓存三大问题：穿透（空值/布隆过滤器）、击穿（互斥重建/逻辑过期）、雪崩（打散 TTL/限流/多级缓存）；热点 key 用本地缓存、分片、限流、复制；大 key 拆分、异步删除。
   - 缓存一致性：旁路缓存先更新库再删缓存，延迟双删只能缩小窗口，仍有并发不一致；强一致要求高时读主库或加版本。
   - 数据库：读写分离 + 读己之写；分库分表选高基数、分布均匀、能覆盖大多数查询的路由键；跨片查询用基因法/冗余表/ES；扩容用双写 + 迁移 + 对账 + 切读。

4. **异步化、隔离与稳定性**
   - MQ 削峰：同步下单改异步，消费者按自身能力拉取；要处理消息积压（扩容消费者、降级、回放）、重复消费（幂等）、顺序（分区键）。
   - 线程池隔离：不同下游独立线程池，避免一个慢依赖拖垮全部；配置核心/最大线程数、有界队列、拒绝策略，并监控活跃数和队列长度。
   - 稳定性：超时、重试、熔断、降级、限流组合；核心链路与非核心链路隔离部署；大促前做预案和开关演练。
   - 扩展：无状态服务水平扩容；有状态数据分片；热点数据分段；读写分离；异步化。

5. **秒杀系统**
   - 特点：瞬时流量成百上千倍、库存极少、绝大多数请求注定失败；目标是抗压、不超卖、防刷。
   - 流程：① 页面静态化 + CDN，动态生成秒杀地址，网关按用户限频/验证码打散；② 活动前库存预热到 Redis；③ Lua 原子完成“是否已购 + 库存判断 + 扣减 + 记录用户”，库存不足直接返回，可加本地售罄标记；④ 预扣成功发 MQ 异步下单，前端轮询；⑤ 数据库 `UPDATE stock SET num = num - 1 WHERE sku_id = ? AND num > 0` 兜底防超卖；⑥ 超时未支付延迟消息取消订单并回补 Redis/DB 库存。
   - 其他：秒杀服务独立部署；一人一单用 `(user_id, sku_id)` 唯一索引；热点商品库存拆多个 key 分散；防刷用风控/限流/黑名单；全链路压测验证不超卖。

6. **可用性与降级预案**
   - 依赖分级：核心（下单/支付）与非核心（推荐/评论/积分）隔离，非核心可降级。
   - 预案：容量水位、限流阈值、熔断阈值、降级开关、缓存预热、数据库连接池上限、MQ 积压告警；大促前演练并准备回滚。
   - 观测：黄金指标 + 业务指标（下单成功率、支付成功率）；告警只对用户可见症状；故障时先止损（限流/降级/切流）再定位。

### （八）其他分布式基础能力

1. **分布式 ID**
   - 要求：全局唯一、趋势递增（B+ 树友好）、高可用、高性能、不暴露业务量。
   - 方案：UUID（本地、无序、太长，主键页分裂）；数据库自增（简单、单点）；号段模式（一次取 1000 个在内存分配，DB 压力小，重启浪费、取号尖刺）；Redis INCR（性能好、依赖持久化）；雪花（1 位符号 + 41 位毫秒 + 10 位机器 + 12 位序列，本地生成、趋势递增）。
   - 时钟回拨：小回拨等待追上，大回拨报错告警或切备用 workerId，或像 UidGenerator 用上次时间戳自增；容器环境 workerId 不能写死，用注册中心/Redis 分配。美团 Leaf 号段双 buffer（用到 10% 异步加载下一段）+ 雪花 ZK 分配 workerId；号段服务不可用时要有本地缓存号段，并降级到雪花/数据库自增，避免取号失败阻断业务。

2. **分库分表**
   - 路由键选择：高基数、分布均匀、大多数查询能带上；用户维度用 userId，订单用 orderId，商家维度可能需基因法把 userId 嵌入 orderId 后缀。
   - 跨片查询：广播路由、内存归并、冗余表/ES 索引；深分页用游标/二次查询。
   - 扩容：双倍分片/一致性哈希减少迁移；双写 + 全量迁移 + 增量追平 + 对账 + 切读 + 回滚预案；全局 ID 与分布式事务要提前考虑。

3. **分布式调度**
   - 单机 `@Scheduled` 多实例会重复执行，且无高可用、无执行记录；ShedLock 用数据库/Redis 锁保证同一时刻只执行一次。
   - XXL-JOB：调度中心 + 执行器分离，执行器注册心跳，调度中心按 cron 通过 HTTP 触发并回调结果；路由策略有轮询、随机、一致性哈希、故障转移、分片广播；分片广播把 `shardIndex/shardTotal` 下发，适合百万级批量；阻塞处理有单机串行/丢弃/覆盖；调度中心多实例用 DB 行锁选主。
   - 选型：任务少用 ShedLock；需要可视化、分片、告警、重试用 XXL-JOB/ElasticJob。

4. **Service Mesh**
   - SDK 模式（Spring Cloud）要求每个服务引依赖，多语言各实现一套，治理逻辑升级要改代码发布。
   - Service Mesh 把服务发现、负载均衡、超时重试、熔断、mTLS、遥测下沉到 Sidecar：数据面 Envoy 劫持流量，控制面 Istiod 通过 xDS 下发配置、签发证书；iptables 重定向，应用无感知。
   - 代价：每次调用多一跳（1~2ms）、Sidecar 资源开销、运维排障复杂；小团队/单体不必引入。SDK 与 Sidecar 不要重复配置超时重试。

## 十、网络、操作系统与 Linux

### （一）TCP/IP 与 HTTP

1. **TCP 连接、可靠性与拥塞控制**
   - **三次握手**：SYN → SYN+ACK → ACK，双方确认收发能力并同步初始序列号；两次不够，防止历史重复连接请求造成错误连接。**四次挥手**：FIN → ACK → FIN → ACK，因为 TCP 全双工，两个方向要分别关闭。
   - **TIME_WAIT**：主动关闭方等待 2MSL，保证最后一个 ACK 能重传、旧连接报文在网络中消失；大量 TIME_WAIT 会占端口，可调 `tcp_tw_reuse` 等参数但别盲目。**CLOSE_WAIT**：被动关闭方收到 FIN 后没有调用 close，通常是应用代码/连接泄漏。
   - **可靠性**：序号 + 确认、超时重传、快速重传、校验和、滑动窗口；流量控制用接收窗口 rwnd，拥塞控制用 cwnd，包括慢启动、拥塞避免、快速重传/恢复；现代还有 BBR。
   - **粘包/拆包**：TCP 是字节流，没有消息边界；应用层用定长、分隔符、长度字段或协议帧解决，Netty 有对应解码器。
   - **延伸**：SYN Flood 用 SYN Cookie/限流；TCP keep-alive 与 HTTP keep-alive 不是一回事；MSS、Nagle、延迟 ACK 会影响小包延迟。

2. **HTTP 演进与 HTTPS**
   - **方法与状态码**：GET/POST/PUT/PATCH/DELETE；1xx 信息、2xx 成功、3xx 重定向（301 永久/302 临时/304 未修改）、4xx 客户端错误（400/401/403/404/429）、5xx 服务端错误（500/502/503/504）。
   - **HTTP/1.1**：keep-alive 复用连接，但同连接请求串行，存在队头阻塞；管道化因代理兼容问题很少用。
   - **HTTP/2**：二进制分帧、多路复用、HPACK 头压缩、流优先级，解决 HTTP 层队头阻塞；底层仍是 TCP，丢包会阻塞所有流。
   - **HTTP/3/QUIC**：基于 UDP，0-RTT/1-RTT 建连、连接迁移、无 TCP 队头阻塞；适合移动网络和弱网。
   - **HTTPS**：TLS 握手用非对称/密钥交换协商会话密钥，之后用对称加密传输；客户端校验证书链、域名、有效期、吊销状态；TLS 1.3 简化握手、支持 1-RTT/0-RTT，但 0-RTT 有重放风险，只应用于幂等请求。
   - **延伸**：DNS 解析走浏览器/OS/hosts/递归服务器，CDN 靠 DNS 调度；Cookie 自动携带、Session 服务端存储、Token 客户端携带；WebSocket 用 HTTP Upgrade 建立全双工连接。

3. **网络分层与常见协议**
   - **分层**：应用层（HTTP/DNS/SSH）、传输层（TCP/UDP）、网络层（IP/ICMP/ARP）、链路层；IP 负责路由，TCP 负责可靠传输，UDP 负责低开销。
   - **排查命令**：`ping` 连通性、`traceroute` 路径、`dig` DNS、`curl -v` HTTP、`ss` 连接状态、`tcpdump` 抓包。
   - **网关错误**：502 是网关从上游收到无效响应，504 是网关等待上游超时；要查上游服务、超时配置和网络，不要只看网关。
   - **延伸**：NAT、CIDR、子网、端口复用；反向代理与负载均衡；HTTP 缓存头 `Cache-Control/ETag/Last-Modified`。

### （二）进程、线程、IO 与零拷贝

1. **进程、线程与协程**
   - **进程**：独立地址空间、PCB、文件描述符；进程间通信有管道、消息队列、共享内存、信号、Socket；创建/切换成本高，隔离性好。
   - **线程**：共享堆和方法区，独立栈、PC、寄存器、TLS；切换涉及用户态/内核态、TLB 和缓存失效；一个线程崩溃可能影响整个进程。
   - **协程**：用户态协作式调度，切换不进入内核，适合高并发 IO；但阻塞调用会卡住调度线程，CPU 密集不占优。
   - **延伸**：Linux 用 clone 实现线程；Java 平台线程映射到 OS 线程，虚拟线程由 JVM 调度；上下文切换要看 `vmstat` 的 cs/in/out。

2. **IO 模型与多路复用**
   - **分类**：阻塞/非阻塞描述“调用是否立即返回”，同步/异步描述“数据拷贝是否完成通知”；BIO 一连接一线程，NIO 用 Selector 多路复用，AIO 是内核完成后回调。
   - **select/poll/epoll**：select 有 1024 fd 限制且 O(n) 扫描；poll 用数组无上限但仍 O(n)；epoll 用红黑树管理 fd + 就绪链表，O(1) 取就绪事件，适合大量连接。
   - **LT/ET**：水平触发只要可读就不断通知，编程简单；边缘触发只在状态变化时通知一次，必须循环读到 `EAGAIN`，否则会丢事件。
   - **Reactor**：一个/多个 event loop 监听事件，把就绪事件分发给 handler；Netty 的 EventLoop 绑定一个线程，避免锁竞争。
   - **延伸**：epoll 不适合普通文件（总是就绪）；Java NIO 的 Selector 底层用 epoll；Netty 的 `IO` 线程不能做耗时业务。

3. **零拷贝**
   - **传统 read/write**：数据从磁盘到内核页缓存，再复制到用户态，再复制回内核 socket 缓冲区，最后到网卡，涉及多次拷贝和上下文切换。
   - **mmap + write**：把内核页缓存映射到用户态，减少一次拷贝；**sendfile**：数据在内核态从页缓存直接送到 socket，减少用户态拷贝和上下文切换；splice 类似。
   - **适用**：大文件传输、日志/消息队列（Kafka/RocketMQ）、静态资源服务；需要修改数据、加密、小文件时收益有限。
   - **延伸**：Java `FileChannel.transferTo` 可用零拷贝；Netty 的 `FileRegion`；零拷贝不等于“完全不拷贝”，DMA 仍参与。

### （三）Linux 线上排障

1. **核心指标与工具**
   - **CPU**：`top`/`htop` 看 us/sy/wa/st，`vmstat` 看 r/b/in/cs，`mpstat` 看多核，`pidstat` 看进程；load average 高不一定 CPU 忙，可能是 IO 等待或不可中断进程。
   - **内存**：`free -h` 看 available 而不是 free，`vmstat` 看 si/so，`/proc/meminfo` 看缓存和 swap；OOM 看 `dmesg` 的 OOM Killer。
   - **磁盘**：`df -h` 看容量，`du` 找大目录，`iostat -x` 看 await/util，`iotop` 找高 IO 进程；`lsof +L1` 找已删除但仍被占用的文件。
   - **网络**：`ss -s` 看连接汇总，`ss -lntp` 看监听，`netstat` 兼容旧系统，`tcpdump` 抓包，`sar -n DEV` 看流量。
   - **延伸**：文件描述符 `ulimit -n`、`lsof`；容器内工具缺失可用 `nsenter` 或宿主机排查。

2. **典型故障路径**
   - **CPU 100%**：`top -Hp` 找线程 → 线程 ID 转十六进制 → `jstack` 匹配 `nid`；区分业务死循环、GC、锁竞争、JIT 编译。
   - **内存增长**：看 RSS 是否持续上涨，区分堆内泄漏（dump + MAT）和堆外/本地内存（NMT、pmap）；容器 OOMKilled 要看 cgroup 限制。
   - **IO 等待高**：`iostat` 看 util/await，`pidstat -d` 找进程，检查大文件写入、日志刷盘、数据库慢查询。
   - **连接异常**：`ss` 看 TIME_WAIT/CLOSE_WAIT、SYN_RECV、Established 数量；CLOSE_WAIT 多通常是应用没 close；端口耗尽要看本地端口范围。
   - **磁盘满**：`df` 确认分区，`du` 找大目录，`lsof +L1` 找未释放的删除文件，日志轮转/临时文件要清理。
   - **延伸**：先用低开销工具缩小范围，再上 `strace`/`perf`/`bpftrace`；生产抓包/采样要评估性能和数据安全。

3. **常用命令与信号**
   - **进程**：`ps aux`、`pgrep`、`kill -15`（SIGTERM，优雅退出）、`kill -9`（SIGKILL，强杀，可能丢数据）；`systemctl`、`nohup`、`crontab`。
   - **文件**：`find`、`xargs`、`tar`、`rsync`、`chmod/chown`；`sed/awk/grep` 处理日志；`journalctl` 看系统日志。
   - **延伸**：优雅下线要先摘流量、等请求结束、再停进程；`ulimit` 和内核参数调优要结合压测；不要在生产随便 `kill -9` 数据库/中间件。

## 十一、Elasticsearch

### （一）核心概念与索引

1. **索引、Mapping 与分词**
   - **概念**：Cluster → Node → Index → Document → Field；Index 是逻辑命名空间，底层由多个 Lucene Shard 组成；7.x 起废弃 type，一个 Index 只有一种文档结构。
   - **Mapping**：定义字段类型（text/keyword/long/date/geo 等），决定如何索引和查询；动态 Mapping 可能把数字识别成 text、日期识别成 keyword，生产要显式定义并关闭不必要的 dynamic。
   - **text vs keyword**：text 会分词、用于全文检索，不能直接排序/聚合；keyword 不分词、用于精确匹配、排序、聚合；一个字段可用 multi-fields 同时提供两种。
   - **分词**：Analyzer = Character Filter + Tokenizer + Token Filter；中文常用 IK（ik_max_word/ik_smart），英文 standard；索引时分词和查询时分词要一致。
   - **倒排索引**：Term Dictionary + Postings List，记录词出现在哪些文档、位置、频率；Segment 是不可变的小索引，doc values 用于排序/聚合，`_source` 存原始文档。

2. **分片、副本与路由**
   - **分片**：Primary Shard 负责写入，Replica Shard 提供读和故障转移；主分片数在索引创建后一般不可改（除非 split/shrink），副本数可动态调整。
   - **路由**：`shard = hash(routing) % number_of_primary_shards`，默认 routing 是 `_id`；自定义 routing 可让相关文档落同一分片，但可能造成热点。
   - **读写**：写请求先到 Primary，再复制到 Replica；读请求可轮询到 Primary/Replica；副本越多读吞吐越高，但写入复制开销和存储成本也越高。
   - **分片规划**：单分片建议 10~50GB，避免过多小分片（集群状态、堆内存、查询扇出）；按数据增长和保留周期估算，用别名 + reindex 支持扩容。
   - **延伸**：别名（alias）实现零停机切换；rollover 按大小/时间滚动；ILM 做热/温/冷/删除生命周期管理。

### （二）写入、近实时与查询

1. **写入流程与近实时**
   - **写入链路**：协调节点路由 → Primary 写 translog 和内存 buffer → 复制到 Replica → 返回；Primary 所在节点挂掉时由 Replica 提升。
   - **refresh**：默认每 1 秒把内存 buffer 生成新 Segment 并打开，使文档可搜索；所以是“近实时”而不是实时；写入后立刻查可加 `refresh=true`，但频繁 refresh 会产生大量小 Segment。
   - **flush**：把 Segment fsync 到磁盘并清空 translog；**merge**：后台合并小 Segment，减少文件数和查询开销；`forcemerge` 适合只读索引，但很耗 IO。
   - **translog**：默认 `request` 级别每次写请求刷盘，保证宕机可恢复；`async` 降低开销但有丢失窗口；`_seq_no`/`_primary_term` 支持乐观并发控制。
   - **延伸**：批量写入用 `_bulk`；refresh interval 可调大以提升写入吞吐，但会增加可见延迟；大量写入后不要频繁 forcemerge。

2. **查询 DSL、评分与聚合**
   - **query context vs filter context**：query 计算相关性得分，filter 只判断是否匹配、可缓存，性能更好；`bool` 的 `must/should/must_not/filter` 组合，`must_not` 和 `filter` 不参与评分。
   - **常用查询**：`match`（分词全文）、`term`（精确值）、`range`、`terms`、`exists`、`wildcard`（慎用）、`nested`（嵌套对象）；默认评分算法 BM25。
   - **评分控制**：`boost`、`function_score`、`constant_score`；业务常把可过滤条件放 filter，评分只用于排序相关性。
   - **聚合**：`terms` 分桶、`cardinality` 基数估算、`date_histogram` 时间分桶、`composite` 多字段分页聚合；聚合依赖 doc values，text 字段默认不能聚合。
   - **深分页**：`from + size` 默认最多 10000 条（`max_result_window`），深分页会占用协调节点内存；`scroll` 适合导出快照，`search_after + PIT` 适合实时翻页，`collapse` 去重。
   - **延伸**：`track_total_hits` 控制总数精度；`explain`/Profile API 分析查询开销；慢查询日志定位重查询。

### （三）集群、数据同步与运维

1. **集群与高可用**
   - **节点角色**：master-eligible、data、coordinating、ingest；生产建议 3 个专用 master 节点，避免数据节点参与选举。
   - **选主与脑裂**：通过 quorum 选出 master，`discovery.seed_hosts` 和 `cluster.initial_master_nodes` 配置集群发现；脑裂会导致数据不一致，要保证网络和投票配置正确。
   - **健康状态**：green 全部分片可用，yellow 主分片可用但副本未分配，red 有主分片不可用；用 `_cluster/health`、`_cat/shards`、`_cat/allocation` 排查。
   - **分配**：分片分配感知（机架/可用区）、磁盘水位线、hot/warm 架构；副本不能与主分片在同一节点。
   - **延伸**：快照仓库（S3/HDFS）做备份；恢复时控制并发；集群滚动升级要禁用 shard allocation。

2. **MySQL → ES 数据同步**
   - **全量 + 增量**：先全量导入建立基线，再增量同步；增量可用 Canal/Debezium 订阅 binlog、Outbox + MQ、应用双写。
   - **幂等**：以业务主键作为 `_id`，重复写入是覆盖；删除用标记删除或 delete by query；版本号防乱序。
   - **可靠性**：同步失败重试 + 死信 + 对账；CDC 位点要持久化；全量切换用别名，避免双写不一致。
   - **一致性**：ES 不是权威数据源，允许秒级延迟；双写易出现“数据库成功、ES 失败”，优先 CDC/Outbox；对账任务定期修复差异。
   - **延伸**：Mapping 变更通常要 reindex；大索引 reindex 用 PIT + sliced scroll；同步链路要有 lag 监控。

3. **运维与规范**
   - **容量**：JVM 堆不超过物理内存 50%，且尽量不超过 32GB（压缩指针失效）；剩余内存留给文件系统缓存；分片数按数据量和并发查询规划。
   - **查询规范**：避免 `wildcard` 前导通配、超大 `terms`、深分页、全字段 `query_string`；控制返回字段 `_source` 过滤；聚合 `size` 不要过大。
   - **监控**：查询延迟、拒绝率（thread pool rejected）、GC、磁盘水位、分片状态、同步 lag；用 `_nodes/stats`、`_cat/indices`。
   - **延伸**：ES 适合搜索和分析，不适合作为强一致事务库；复杂多表关联仍应回数据库或宽表；权限和租户隔离要用索引/别名/文档级安全。

## 十二、系统设计与项目场景

### （一）通用设计方法

1. **需求澄清与容量估算**
   - **功能需求**：核心用例、用户角色、读写路径、数据保留周期、一致性要求。
   - **非功能需求**：日活/峰值 QPS、读写比、P99 延迟、可用性（99.9% 约每年 8.76 小时不可用，99.99% 约 52.6 分钟）、成本、合规。
   - **估算**：QPS = DAU × 人均请求 / 86400，峰值按平均的 2~5 倍；存储 = 日增量 × 单条大小 × 保留天数 × 副本数；带宽 = QPS × 响应大小；并发连接 ≈ QPS × RT（Little 定律）。
   - **延伸**：估算不是精确数学，目的是判断“单机能否扛、要不要分片/缓存/MQ”；留 2~3 倍冗余并说明假设。

2. **架构设计与取舍**
   - **分层**：客户端 → CDN/静态资源 → 网关（鉴权/限流/路由）→ 无状态服务 → 缓存 → 数据库/MQ；按读写路径画时序图，标出同步/异步、缓存命中和失败分支。
   - **数据模型**：先确定查询模式再定表/索引；强一致数据放同一服务同一库；跨服务用最终一致；大字段/全文检索/分析分别放对象存储/ES/OLAP。
   - **取舍**：一致性 vs 可用性、延迟 vs 吞吐、成本 vs 可靠性、自建 vs 托管；每个选择都要说清“代价是什么、什么情况下会失败”。
   - **延伸**：避免过度设计；先满足当前量级，再留扩展点；接口幂等、超时、重试、降级从第一天就要考虑。

3. **验证、上线与演进**
   - **验证**：单测/集成/契约测试、全链路压测、故障注入、容量水位；用 P99、错误率、饱和度验证，不只看平均 RT。
   - **上线**：灰度/蓝绿/滚动、开关和回滚预案；监控黄金指标（流量、错误、延迟、饱和度）和业务指标（下单/支付成功率）。
   - **演进**：按瓶颈扩容（无状态服务水平扩展、数据分片、读写分离、异步化）；定期复盘容量和故障。
   - **延伸**：SLO/SLA、runbook、告警分级；故障时先止损（限流/降级/切流）再定位根因。

### （二）高频业务场景

1. **秒杀与库存**
   - **链路**：页面静态化 + CDN → 网关限流/验证码/黑名单 → Redis 预热库存 → Lua 原子“校验限购 + 扣库存 + 记录用户” → 发送 MQ → 异步创建订单 → DB 条件扣减兜底 → 超时未支付回补库存。
   - **防超卖**：Redis Lua 原子扣减 + 数据库 `UPDATE stock SET num=num-1 WHERE sku_id=? AND num>0` 双保险；库存不足直接返回，本地售罄标记减少无效请求。
   - **幂等/限购**：`(user_id, sku_id)` 唯一索引；消息消费幂等；重复请求返回同一结果；超时取消用延迟消息。
   - **延伸**：秒杀服务独立部署；热点库存分片；压测验证不超卖；详见第九章“（七）高并发系统设计”。

2. **短链系统**
   - **生成**：发号器（号段/雪花）→ Base62 编码，长度短且无冲突；或对 URL 哈希取前几位，冲突时加盐重试；预生成号段可提升写入吞吐。
   - **读写**：写少读多，Redis 缓存短码→长链，未命中查 DB；301 永久/302 临时按业务选择；统计点击可异步写 MQ/日志。
   - **治理**：唯一索引防重复；过期时间/回收；恶意 URL 黑名单、限流、验证码；热点短链本地缓存。
   - **延伸**：自定义短码要防枚举/冲突；跨地域用多活或就近解析；统计去重和 UV 可用 HyperLogLog。

3. **订单超时关闭**
   - **方案**：RocketMQ 延迟消息（固定级别/5.x 任意延迟）、Redis ZSet（score 到期时间 + 定时轮询）、时间轮、定时任务扫描；按精度和可靠性选择。
   - **并发控制**：关单和支付可能同时到达，用状态机 `UPDATE order SET status='CLOSED' WHERE id=? AND status='UNPAID'`，影响行数为 0 说明已被支付/关闭；支付回调也要条件更新，保证只成功一次。
   - **补偿**：关单成功后回补库存/优惠券，发 MQ 异步执行；失败重试 + 对账；已支付订单不能关，先查支付状态。
   - **延伸**：延迟消息可能重复/丢失，要有兜底扫描；大量订单按时间分片扫描；状态只前进不回退。

4. **排行榜、Feed 与 IM**
   - **排行榜**：Redis ZSet 按分数排序，`ZREVRANGE` 取 TOP N，`ZRANK` 查名次；超大规模按业务维度分 key，定时落库；同分按时间/ID 二级排序。
   - **Feed**：推模式（写扩散，收件箱）适合粉丝少、读快；拉模式（读扩散）适合大 V、写少；混合模式按粉丝数切换；收件箱用 Redis List/ZSet，分页用游标。
   - **IM**：WebSocket 长连接 + 消息编号/seq 保证顺序；ACK、离线消息、已读回执、去重、多端同步；消息存储按会话分片，热点群扩散。
   - **延伸**：Feed/IM 的一致性通常是最终一致；大 V 热点要限流/降级；消息顺序按会话而不是全局。

5. **百万级数据导出**
   - **流式**：JDBC `fetchSize` + 游标分批读，POI SXSSF 或 CSV 流式写，避免一次性加载全量；每批清理临时对象。
   - **异步**：提交导出任务 → 后台线程/独立服务分片处理 → 生成文件到 OSS → 通知下载；任务状态、进度、失败重试、过期清理。
   - **保护**：限速/限并发，避免拖垮数据库；大导出走只读库/离线库；临时文件设上限；导出内容脱敏。
   - **延伸**：分页导出要保证顺序稳定（按主键）；断点续传用分片文件；下载链接签名和有效期。

6. **认证、JWT 与 SSO**
   - **JWT**：签名保证不可篡改，不保证机密性，payload 默认只是 Base64，不能放敏感信息；无状态校验适合分布式，但主动吊销困难。
   - **组合**：短期 access token（分钟级）+ 长期 refresh token（服务端存储、可撤销）+ 撤销名单/版本号；敏感操作二次校验。
   - **OAuth2/OIDC**：OAuth2 是授权框架，OIDC 在其上提供身份认证；SSO 用统一认证中心 + 票据/Token 换业务登录态。
   - **延伸**：`alg=none`、弱密钥、Token 泄露、CSRF、重放都要防；JWT 不适合作为服务端 Session 的完全替代。

7. **热点 Key 与大 Key**
   - **热点 Key**：本地缓存、key 分片、读写分离、限流、独立集群；先监控再治理，避免盲目拆分。
   - **大 Key**：拆分、压缩、`UNLINK` 异步删除、`SCAN` 渐进遍历；避免 `KEYS`/全量 `HGETALL`；写入时限制 value 大小。
   - **延伸**：详见第七章“（三）缓存问题与一致性”；热点治理要同时考虑缓存、DB、网络和下游。

### （三）线上排障与项目表达

1. **慢接口逐层定位**
   - **入口**：网关/负载均衡 RT、超时、重试；服务整体 RT 与 P99；线程池活跃数/队列/拒绝；GC 停顿；连接池等待。
   - **依赖**：慢 SQL（执行计划、锁等待）、缓存命中率/大 key、下游 RPC（trace 看哪一跳慢）、MQ 积压、网络丢包/重传。
   - **工具**：Arthas `trace` 看方法耗时、`watch` 看入参/返回值、火焰图/async-profiler 看 CPU、JFR 看事件、链路追踪看 Span。
   - **原则**：先看最近变更和监控基线；能回滚先回滚；不要在生产随手抓 dump/开高开销 trace。

2. **CPU、内存与 GC 异常**
   - **CPU 高**：`top -Hp` → 线程 ID 转十六进制 → `jstack` 匹配 `nid`；区分死循环、锁竞争、GC 线程、JIT。
   - **内存/GC**：`jstat -gcutil`、GC 日志看频率和停顿；堆 dump + MAT 找泄漏；堆外看 NMT/pmap；容器看 cgroup 和 OOMKilled。
   - **证据链**：监控曲线 → 线程栈 → 堆/GC → 慢 SQL/下游；多抓几份样本对比，避免单次快照误判。

3. **项目表达（STAR）**
   - **S/T**：业务背景、目标、规模（QPS、数据量、可用性）、你的角色。
   - **A**：架构方案、关键技术决策、为什么选它、遇到的最大挑战、如何验证；突出你实际写的代码/设计的模块。
   - **R**：量化结果（RT、吞吐、成本、故障率、可用性）、复盘和后续优化；失败案例也要讲清根因和补救。
   - **延伸**：面试官更关心“为什么”和“边界”，不要只罗列技术栈；不会的细节要承认，不要编造。

## 十三、工程化、安全与云原生

### （一）安全基础

1. **常见 Web 攻击与防护**
   - **SQL 注入**：拼接 SQL 导致攻击者改变语义；用 PreparedStatement/参数化、ORM、白名单校验动态表名/排序字段；MyBatis 用 `#{}` 不用 `${}`；数据库账号最小权限。
   - **XSS**：存储型/反射型/DOM 型，把不可信内容当 HTML/JS 执行；按上下文输出编码、CSP、HttpOnly Cookie、输入校验，避免 `innerHTML`/`eval`。
   - **CSRF**：用户已登录时被诱导发出状态变更请求；用 SameSite Cookie、CSRF Token、校验 Origin/Referer，敏感操作二次确认；CORS 不是 CSRF 防护。
   - **SSRF**：服务端代为请求用户提供的 URL，可能访问内网/云元数据；用域名白名单、URL 解析校验、禁止重定向、网络隔离、关闭不必要的元数据访问。
   - **越权/IDOR**：水平越权（改别人的订单 ID）、垂直越权（普通用户调管理员接口）；每个请求都要校验资源归属和角色，不能依赖前端隐藏；UUID 不等于授权。
   - **其他**：反序列化、文件上传（类型/大小/路径/内容检测）、路径穿越、命令注入、暴力破解（限流/验证码）、敏感信息泄露。
   - **延伸**：安全默认拒绝、最小权限、纵深防御；日志脱敏；依赖漏洞扫描；不要自己造加密协议。

2. **密码学与密钥管理**
   - **哈希 vs 加密 vs 签名**：哈希单向（完整性/密码存储），加密可逆（机密性），签名用私钥签、公钥验（身份和完整性）；SHA-256 是哈希，不是加密。
   - **密码存储**：BCrypt/Argon2/scrypt + 随机盐，避免 MD5/SHA 直接存；盐要唯一；密码不明文进日志；限制登录尝试。
   - **对称/非对称**：AES-GCM 带认证，避免 ECB；RSA/ECC 用于密钥交换和签名；TLS 用非对称协商、对称传输；HMAC 做消息认证。
   - **密钥管理**：KMS/Vault/Secret Manager，密钥轮换、分级、最小权限；不要硬编码到代码/镜像；传输和存储加密；敏感字段脱敏。
   - **延伸**：随机数用 `SecureRandom`；JWT 签名 HS256 共享密钥、RS256 公私钥；防时序攻击用恒定时间比较；国密算法按合规要求。

3. **认证、授权与 SSO**
   - **认证 vs 授权**：认证回答“你是谁”，授权回答“你能做什么”；登录成功不代表能访问任意资源；401 未认证、403 无权限。
   - **OAuth2/OIDC**：OAuth2 是授权框架，授权码模式 + PKCE 适合 Web/移动端；OIDC 在 OAuth2 上增加身份层，返回 id_token；不要用隐式模式。
   - **SSO**：CAS/SAML/OIDC 统一认证中心，业务系统跳转认证后换取本地会话；注意票据有效期、重放、跨域 Cookie。
   - **JWT**：无状态、适合服务间传递，但吊销困难；短期 access token + refresh token 轮换 + 服务端撤销名单；不要放敏感信息。
   - **接口安全**：API 签名（参数 + 时间戳 + nonce + 密钥）、防重放（时间窗 + nonce 缓存）、限流、幂等；内部服务用 mTLS/服务身份。
   - **延伸**：RBAC/ABAC、租户隔离、权限缓存；越权测试要覆盖横向和纵向；第三方回调要验签 + 幂等。

### （二）构建、测试与可观测性

1. **Maven/Gradle 与依赖管理**
   - **依赖冲突**：Maven “最短路径优先、同路径先声明”，Gradle 默认取最高版本；用 `dependencyManagement`/BOM 统一版本，`exclusions` 排除冲突，`mvn dependency:tree` 分析。
   - **Scope**：compile/provided/runtime/test；`optional` 避免传递；`provided` 适合容器/服务器已提供的依赖；shade/assembly 打胖包注意签名和冲突。
   - **构建**：Maven Wrapper/Gradle Wrapper 固定版本；多模块聚合；可重复构建；CI 中缓存依赖；不要把密钥打进产物。
   - **Git 与配置**：主干开发或特性分支 + PR review，小步提交、语义化版本和 tag；配置按环境外置，敏感配置不进 Git；提交信息关联需求和缺陷，发布可追溯。
   - **延伸**：Slf4j 多绑定冲突；SNAPSHOT 依赖不可复现；依赖漏洞扫描（OWASP Dependency-Check）。

2. **测试体系**
   - **金字塔**：大量单元测试、适量集成/契约测试、少量端到端；单元测试快、隔离，集成测试验证真实中间件，E2E 验证关键链路。
   - **工具**：JUnit 5、Mockito、AssertJ；Testcontainers 起真实 MySQL/Redis/Kafka；WireMock 模拟外部 HTTP；契约测试保证服务间接口兼容。
   - **性能**：JMH 做微基准（预热、fork、避免死代码消除）；压测工具做系统容量；不要用 JMH 替代全链路压测。
   - **延伸**：测试数据隔离、随机端口、并行测试、flaky 治理；生产问题尽量补回归测试；Mock 过多会掩盖集成问题。

3. **可观测性**
   - **三支柱**：Metrics（聚合指标）、Logs（离散事件）、Traces（请求链路）；加上 Profiling 和事件/审计。
   - **指标**：Micrometer + Prometheus + Grafana；黄金指标——流量、错误率、延迟（P99）、饱和度；业务指标单独看。
   - **日志**：结构化 JSON、统一 TraceId、分级、采样；ELK/Loki 收集；避免打印敏感信息和超大对象。
   - **链路**：OpenTelemetry/SkyWalking/Zipkin，跨线程和 MQ 透传；采样和尾部保留。
   - **告警**：基于 SLO/错误预算，告警用户可见症状而不是每个指标；分级、抑制、值班 runbook。
   - **延伸**：高基数标签会打爆 Prometheus；日志成本要控制；监控本身也要高可用。

### （三）容器与 Kubernetes

1. **容器与镜像**
   - **隔离**：namespace 做视图隔离（PID/网络/挂载/UTS），cgroup 做资源限制（CPU/内存/IO）；容器共享宿主机内核，隔离性弱于虚拟机。
   - **镜像**：分层只读，容器层可写；Dockerfile 多阶段构建、精简基础镜像、非 root、固定版本、`.dockerignore`；镜像扫描和签名。
   - **延伸**：OCI 标准、containerd、rootless；不要把密钥/构建缓存打进镜像；镜像仓库权限和保留策略。

2. **Kubernetes 核心对象**
   - **Pod**：最小调度单元，一个或多个容器共享网络命名空间和卷；sidecar 做代理/日志/监控；Pod 本身可被替换，不要存状态。
   - **工作负载**：Deployment 管理 ReplicaSet，ReplicaSet 管理 Pod；StatefulSet 适合有状态/稳定网络标识；DaemonSet 每节点一个；Job/CronJob 批处理。
   - **服务发现**：Service 提供稳定虚拟 IP/域名（ClusterIP/NodePort/LoadBalancer），kube-proxy 或 eBPF 转发；Ingress/Gateway API 做七层路由。
   - **配置与权限**：ConfigMap 存非敏感配置，Secret 存敏感数据（默认 base64 不是加密）；Namespace 隔离；RBAC 控制 API 权限；NetworkPolicy 控制 Pod 间流量。
   - **资源**：requests 用于调度，limits 用于限制；CPU 超限被 throttle，内存超限被 OOMKilled；QoS 分 Guaranteed/Burstable/BestEffort；HPA 按 CPU/自定义指标扩缩。
   - **延伸**：PDB 防滚动更新一次杀掉太多 Pod；拓扑分布跨可用区；emptyDir/hostPath/PVC 存储差异。

3. **发布、探针与排障**
   - **滚动更新**：`maxSurge` 控制额外创建、`maxUnavailable` 控制不可用比例；两者不能同时为 0；`kubectl rollout status/undo` 查看和回滚。
   - **探针**：startup 保护慢启动（失败会重启），liveness 检测死锁/假死（失败重启容器），readiness 决定是否接流量（失败摘除但不重启）；配置过严会导致反复重启或流量抖动。
   - **优雅下线**：Pod 删除时先摘流量，执行 `preStop`，等待 `terminationGracePeriodSeconds`，再发 SIGTERM；应用要处理 SIGTERM、停止接新请求、等在途完成。
   - **排障**：`kubectl get/describe/logs/exec/port-forward/events`；常见状态 Pending（资源/亲和性）、ImagePullBackOff（镜像/密钥）、CrashLoopBackOff（启动失败/探针）、OOMKilled（内存超限）。
   - **延伸**：Helm/Kustomize 管理多环境；GitOps 审计变更；Service Mesh 做 mTLS/灰度；集群升级和 etcd 备份要演练。

## 十四、数据结构、算法与设计

### （一）基础结构与复杂度

1. **线性结构**
   - **数组**：连续内存、随机访问 O(1)，插入/删除 O(n)；缓存友好，适合下标访问和排序；动态数组扩容摊还 O(1)。
   - **链表**：节点分散、按下标访问 O(n)，已定位节点插入/删除 O(1)；适合频繁头尾操作、LRU；指针开销和缓存不友好。
   - **栈/队列/双端队列**：栈 LIFO，队列 FIFO，Deque 两端操作；单调栈解决“下一个更大元素/接雨水”，滑动窗口最大值用单调队列。
   - **哈希表**：平均 O(1)，冲突用链地址法或开放寻址；负载因子过高会退化，扩容摊还 O(1)；不保证顺序。
   - **延伸**：LRU = HashMap + 双向链表；LFU 需要频率桶；布隆过滤器用位数组 + 多哈希，有误判无漏判。

2. **树、堆与高级结构**
   - **二叉树**：前/中/后序 DFS、层序 BFS；BST 中序有序，查找/插入平均 O(log n)，退化成链 O(n)；AVL 严格平衡、红黑树近似平衡（插入删除旋转少），Java TreeMap 用红黑树。
   - **B/B+ 树**：多叉、矮胖，适合磁盘/数据库；B+ 树非叶子只存键、叶子链表相连，范围查询好。
   - **堆**：完全二叉树，插入/删除 O(log n)，取极值 O(1)；适合 TopK、优先队列、定时任务；建堆 O(n)。
   - **Trie**：前缀树，按字符共享前缀，适合搜索提示、IP 路由、词频统计；空间换时间。
   - **线段树/树状数组**：区间查询/更新 O(log n)；并查集用路径压缩 + 按秩合并，近似 O(1)。
   - **延伸**：红黑树 vs AVL 看插入/删除频率；B+ 树 vs 哈希看范围查询；堆 vs 快速选择看是否需要全排序。

3. **图与字符串**
   - **图**：邻接矩阵 O(V²) 适合稠密图，邻接表 O(V+E) 适合稀疏图；BFS 最短路（无权）、DFS 连通性、拓扑排序（DAG）、Dijkstra（非负权）、Bellman-Ford（负权）、Floyd（全源）。
   - **字符串**：KMP 前缀函数 O(n+m)、Rabin-Karp 哈希、Trie、Manacher；双指针/中心扩展找最长回文。
   - **位运算**：位图去重/排序、状态压缩、lowbit；注意符号位和溢出。
   - **延伸**：递归要注意栈深度；图要标记 visited；大数运算用数组/字符串模拟。

### （二）高频算法模式

1. **双指针、滑动窗口与二分**
   - **双指针**：有序数组两数之和、去重、三数之和、链表环/中点/倒数第 K；快慢指针判环，Floyd 找环入口。
   - **滑动窗口**：最长无重复子串、最小覆盖子串、定长窗口最大值；维护计数/单调队列，窗口收缩条件要写对。
   - **二分**：有序数组查找、左右边界、旋转数组、答案空间二分（最小最大值/最大最小值）；注意 `mid` 溢出、循环不变量和边界。
   - **延伸**：二分答案要证明单调性；窗口题先想“右扩、左缩”的时机；双指针依赖有序或单调性。

2. **排序、堆与 TopK**
   - **排序**：快排平均 O(n log n)、最坏 O(n²)、不稳定、原地；归并稳定、O(n) 额外空间；堆排序 O(n log n)、不稳定、原地；冒泡/插入/选择 O(n²)。
   - **TopK**：小顶堆维护 K 个最大，O(n log k)；快速选择平均 O(n)；数据量大且内存有限用堆/分桶/外部排序。
   - **特殊排序**：计数排序 O(n+k)、桶排序、基数排序，适合整数/固定范围；Java 对象排序用 TimSort（稳定，O(n log n)）。
   - **延伸**：稳定性影响多键排序；比较器要满足自反/对称/传递；海量数据外部排序用多路归并。

3. **搜索、回溯、贪心与动态规划**
   - **DFS/BFS**：树/图遍历、连通分量、层序最短步数；BFS 用队列，DFS 用栈/递归；网格题标记访问。
   - **回溯**：排列/组合/子集/棋盘/N 皇后；做选择 → 递归 → 撤销选择；剪枝和去重（排序后跳过同层重复）。
   - **贪心**：区间调度、跳跃游戏、Huffman 编码；需要证明局部最优能推出全局最优，否则用 DP。
   - **DP**：定义状态、转移方程、初始化、遍历顺序、返回结果；0-1 背包、完全背包、LIS、LCS、编辑距离、股票买卖；可空间压缩。
   - **延伸**：先写递归暴力再记忆化，最后改递推；注意状态数爆炸；DP 与贪心的区别是“是否依赖子问题最优”。

4. **并查集、图算法与正确性**
   - **并查集**：`find` 路径压缩、`union` 按秩/大小合并；适合连通性、朋友圈、冗余连接、Kruskal。
   - **图算法**：拓扑排序（课程表/依赖）、Dijkstra（优先队列）、Bellman-Ford、Floyd、Prim/Kruskal 最小生成树。
   - **正确性**：循环不变量、数学归纳、反证；复杂度要写清时间/空间，递归要算栈空间。
   - **边界**：空数组/单元素、重复值、负数、整数溢出（`mid = left + (right-left)/2`）、索引越界、递归深度、字符集。
   - **延伸**：面试先沟通暴力解，再优化；写完后用手工用例走一遍；不要过早优化导致 bug。

### （三）设计原则与模式

1. **SOLID 与高内聚低耦合**
   - **SRP**：一个类只有一个变化原因；**OCP**：对扩展开放、对修改关闭；**LSP**：子类可替换父类且不破坏契约；**ISP**：接口小而专；**DIP**：依赖抽象而非实现。
   - **高内聚低耦合**：相关逻辑放在一起，模块间通过稳定接口通信；优先组合而非继承；迪米特法则减少链式依赖。
   - **原则**：KISS、DRY、YAGNI；可读性优先于炫技；抽象要有第二个实现或明确扩展点，避免过度设计。
   - **延伸**：设计模式是“意图的语言”，不是 checklist；代码坏味道（重复、过长方法、发散式变化、霰弹式修改）比模式名更重要。

2. **常用设计模式**
   - **创建型**：工厂方法/抽象工厂（解耦创建）、建造者（多参数构造）、单例（全局唯一，注意并发和序列化）。
   - **结构型**：适配器（接口转换）、装饰器（动态增强）、代理（控制访问，Spring AOP）、外观（简化子系统）、组合（树形结构）。
   - **行为型**：策略（可替换算法）、模板方法（固定骨架、扩展步骤）、观察者（事件通知）、责任链（多级处理，Filter/Interceptor）、状态（状态驱动行为）、命令（请求封装/撤销）。
   - **Spring 例子**：BeanFactory 工厂、AOP 代理/装饰、JdbcTemplate 模板、ApplicationEvent 观察者、FilterChain 责任链、策略模式做支付路由。
   - **延伸**：模式会引入间接层，增加理解和调试成本；先重构到模式，不要一开始就套模式。

3. **分层、六边形与 DDD**
   - **分层架构**：Controller → Application → Domain → Infrastructure；依赖方向应指向领域，基础设施实现接口。
   - **六边形/整洁架构**：核心业务不依赖框架/数据库/UI，通过端口和适配器隔离；便于测试和替换。
   - **DDD**：限界上下文划分业务边界，聚合保证一致性边界，实体有身份、值对象无身份、领域服务处理跨实体逻辑、仓储抽象持久化、领域事件解耦副作用。
   - **CQRS/事件溯源**：读写模型分离、事件作为事实来源；复杂度高，适合复杂领域/审计要求高的场景。
   - **延伸**：微服务拆分应基于限界上下文；DDD 不是万能，简单 CRUD 用 DDD 会过度设计；先把业务语言统一。

## 十五、AI 应用开发（按岗位要求准备）

### （一）Spring AI 与模型接入

1. **核心抽象与职责**
   - **ChatModel/ChatClient**：ChatModel 是底层模型调用接口，ChatClient 是面向应用的门面，提供 prompt、流式、结构化输出、Advisor 链；EmbeddingModel 把文本转向量；VectorStore 负责相似度检索。
   - **Advisor**：在调用前后插入逻辑，如 ChatMemory、RAG 检索、租户隔离、日志、敏感词/策略；顺序影响上下文组装和流式输出，要以实际版本 API 为准。
   - **ChatMemory**：保存多轮对话，按会话 ID 隔离；要注意窗口截断、摘要压缩、持久化和隐私。
   - **Tool Calling**：模型返回工具调用意图，应用执行后把结果回传模型；工具 schema 要清晰，参数要校验，执行要有超时/权限/审计。
   - **流式**：SSE/Flux 逐 token 返回，降低首字延迟；要注意断连、取消、错误事件和上下文清理。
   - **与 LangChain4j 对比**：Spring AI 与 Spring/Boot 生态集成更自然，自动配置、Advisor、VectorStore 抽象偏 Spring 风格；LangChain4j 的链、Agent、记忆抽象更接近 LangChain，独立于 Spring，示例和模型适配也较多。选型看团队技术栈、版本成熟度和所需模型/向量库适配。
   - **延伸**：Spring AI 1.x 与 2.x 在 artifact、包名、ChatClient/Advisor API 上有差异，必须按项目 BOM 和官方迁移文档确认，不要凭记忆写版本。

2. **模型接入工程**
   - **上下文窗口**：token 有上限，prompt + 历史 + 检索内容 + 输出都要算；超限要截断、摘要、分层检索；费用按输入/输出 token 计。
   - **稳定性**：设置连接/读取超时、重试（只对幂等请求）、限流、熔断、备用模型/降级；流式请求超时与重试更复杂，要避免重复计费/重复副作用。
   - **可观测**：记录模型、耗时、token 数、命中缓存、错误码、traceId；按租户/用户/链路统计成本；日志脱敏。
   - **缓存**：相同 prompt/检索结果可缓存；语义缓存要评估误命中；模型输出不确定，缓存键要包含模型/参数/版本。
   - **延伸**：温度、top_p、max_tokens 影响稳定性和成本；结构化输出用 JSON Schema/函数调用并做校验；不要直接把模型输出当可信数据。

3. **Spring Boot 3 基础（AI 应用常用）**
   - **自动配置**：`@EnableAutoConfiguration` 通过条件装配按 classpath 和配置生效，Boot 3 从 `AutoConfiguration.imports` 读取；自定义 starter 要提供自动配置类、条件注解和元数据。
   - **Actuator**：暴露 health、metrics、prometheus、loggers 等端点，用于健康检查和监控；生产要限制 endpoint 暴露、加鉴权和网络隔离。
   - **WebFlux/SSE**：AI 流式输出常用 `Flux`/`SseEmitter`；事件循环线程不能阻塞，JDBC/同步 HTTP 要切到弹性线程池；注意反向代理缓冲和连接超时。
   - **AOT/GraalVM**：编译期生成反射/资源/代理配置，启动快、内存低；但封闭世界限制动态类加载、部分字节码增强和 JSP，AI SDK 的反射/序列化要逐项验证，构建和调试成本高。
   - **延伸**：AI 服务多为 IO 密集，重点是连接池、超时、限流和流式背压，不是盲目加线程；Boot 3 基线是 JDK 17、`jakarta.*` 命名空间。

### （二）RAG（检索增强生成）

1. **离线 ingestion 与在线检索**
   - **离线**：文档解析（PDF/HTML/Word/表格）→ 清洗 → 分块（按语义/标题/长度，chunk size + overlap）→ Embedding → 写入向量库，保留 source、页码、租户、权限等 metadata。
   - **在线**：query 改写/扩展 → 向量检索（可混合关键词）→ 过滤 metadata/租户 → Rerank → 组装 prompt（系统指令 + 检索片段 + 引用）→ LLM 生成 → 返回答案和引用。
   - **更新**：文档增删改要增量同步，删除要同步删向量；Embedding 模型变更要全量重建；版本化索引，避免新旧向量混用。
   - **延伸**：分块太大噪声多、太小丢上下文；表格/代码/多语言要特殊处理；metadata 过滤能显著提升准确率和隔离性。

2. **检索质量与评估**
   - **相似度**：cosine/dot/L2，向量要归一化；HNSW/IVF 是近似最近邻，召回率和延迟可调；过滤条件多时暴力/倒排可能更合适。
   - **混合检索**：向量 + BM25/关键词，用 RRF 或加权融合；Rerank 模型对 TopK 重排；query 改写、多 query、HyDE 可提升召回。
   - **指标**：HitRate@K、Recall@K、MRR、NDCG 衡量检索；答案正确性、faithfulness（是否忠于检索内容）、引用正确性衡量生成；还要看延迟和成本。
   - **评估集**：从真实问题采样，标注标准答案/相关文档；离线回归 + 线上 A/B；LLM-as-judge 有偏差，要人工抽检。
   - **延伸**：检索不到时模型应拒答/澄清，不要编造；引用要能回到原文；长上下文不等于高质量，噪声会降低效果。

3. **向量库选型与隔离**
   - **pgvector**：PostgreSQL 扩展，事务/过滤/运维复用现有库，适合中小规模；索引 IVFFlat/HNSW，数据量大时性能受限。
   - **Qdrant**：Rust 实现，过滤和 payload 能力强，适合中大规模、多租户；Milvus 适合十亿级、分布式部署，但运维复杂；Redis/ES 也可做向量检索，适合已有生态。
   - **隔离**：collection/namespace/tenant 字段 + metadata filter；权限要在检索前过滤，不能只靠 prompt；跨租户缓存要隔离。
   - **延伸**：维度、距离度量、索引参数、副本/分片要按数据量和召回要求调；备份和重建成本要提前评估。

### （三）Agent、工具调用与工程边界

1. **Agent 执行循环**
   - **循环**：理解目标 → 计划 → 调工具/检索 → 观察结果 → 再计划，直到完成或达到最大步数；ReAct 是“推理 + 行动”的典型模式。
   - **记忆**：短期对话、长期用户偏好/事实、任务状态；要区分事实与模型推测，支持纠正和删除。
   - **控制**：最大迭代次数、超时、预算、工具白名单、人工确认（高风险操作）；失败要能回退和解释。
   - **延伸**：Agent 不是越自主越好；确定性流程优先用工作流/状态机，开放任务才用 Agent；要可观测每一步。

2. **工具设计**
   - **Schema**：名称、描述、参数类型、必填/枚举、示例；描述决定模型是否会正确调用；参数服务端必须再校验。
   - **副作用**：查询类可重试，写入类要幂等键、权限、审计、超时未知态处理；危险操作（转账、删除）要人工确认/二次授权。
   - **结果**：控制返回大小，结构化；工具输出可能含提示注入，不能直接当指令；错误要可读、可重试分类。
   - **延伸**：工具要最小权限、网络隔离、沙箱；调用链要有 trace；幂等和补偿与普通 RPC 一致。

3. **安全、成本与版本**
   - **提示注入**：直接（用户输入）和间接（网页/文档/工具结果）注入；防录用系统指令隔离、输入输出过滤、工具权限、人工确认，不能只靠 prompt。
   - **敏感信息**：PII 脱敏、租户隔离、日志最小化、密钥托管；不要把密钥放 prompt/前端；输出做合规校验。
   - **成本**：token 预算、上下文压缩、缓存、模型路由（简单任务用小模型）、批处理；按租户/链路统计和限额。
   - **版本兼容**：Spring AI/Boot 版本、模型供应商 API、Embedding 维度、向量库客户端都可能变化；用 BOM 锁定、适配层隔离、回归测试。
   - **延伸**：AI 应用仍遵循超时、重试、幂等、降级、可观测等工程原则；评估集和线上反馈闭环比“调 prompt”更重要。
