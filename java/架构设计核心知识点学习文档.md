## 一、DDD 战略设计

### 1.1 为什么需要 DDD【重点】

软件复杂度分两类：**业务复杂度**来自规则、状态、术语和流程，**技术复杂度**来自框架、存储、集成和部署。DDD 主要解决前者：用限界上下文划清模型边界，用统一语言让代码和业务说同一句话，用聚合保护业务不变量。分层、六边形、CQRS 则更多是在处理后者以及边界内的组织方式。

| 复杂度类型 | 典型表现 | DDD 的应对 |
| --- | --- | --- |
| 业务复杂度 | 同一名词在不同业务含义不同；规则多、状态多、流程长 | 限界上下文、统一语言、聚合、领域事件 |
| 技术复杂度 | 数据库、消息、缓存、第三方接口频繁变化 | 分层、依赖倒置、端口与适配器、防腐层 |

DDD 不是所有系统的默认选项。业务以增删改查为主、规则稳定、交付周期短的系统，直接用事务脚本更划算；只有核心域规则复杂、需要长期演进、业务专家愿意深度参与时，DDD 的建模成本才收得回来。判断标准不是「系统大不大」，而是「业务规则是否复杂到值得建模」。

### 1.2 统一语言与限界上下文【重点】

**统一语言（Ubiquitous Language）** 是业务专家和研发在同一个限界上下文内共同使用的一套术语，它不只存在于词汇表，还要落到类名、方法名、接口、测试用例和对话中。同一个词在不同上下文可以有不同含义，这正是需要边界的原因。

| 上下文 | 「商品」的含义 | 关心的属性 |
| --- | --- | --- |
| 商品目录 | 可展示、可检索的 SPU/SKU | 标题、规格、类目、图片 |
| 订单 | 下单瞬间的价格与数量快照 | 成交价、数量、优惠分摊 |
| 库存 | 可售库存与仓库占用 | 可用量、锁定、预占 |

**限界上下文（Bounded Context）** 是一个模型和它的统一语言有效的显式边界。边界内术语含义唯一，模型只对边界内负责；边界外要通过明确的集成方式通信。限界上下文不是数据库表、不是子系统、也不等于团队，但它通常和团队、发布节奏、数据所有权高度相关。

**子域与限界上下文不是一回事**：子域是问题空间，回答「业务上哪块重要」；限界上下文是解决方案空间，回答「模型边界画在哪」。二者可能一一对应，也可能一个子域拆成多个上下文，或多个子域共用一个上下文。

| 子域类型 | 判定 | 投入策略 | 例子 |
| --- | --- | --- | --- |
| 核心域 | 公司竞争力所在，规则最复杂、差异化最强 | 最好的团队自研，DDD 建模 | 交易撮合、风控定价 |
| 支撑域 | 业务必需但不直接产生差异化 | 自研或外包，适度建模 | 内部审批、报表 |
| 通用域 | 行业通用能力，已有成熟方案 | 采购或复用开源 | 短信、支付通道、邮件 |

划分限界上下文时，常用以下依据交叉验证：

| 划分依据 | 要回答的问题 | 产出 |
| --- | --- | --- |
| 业务能力 | 这块业务是否由一组相对完整的能力组成 | 能力清单、候选上下文 |
| 领域语言边界 | 同一个词在这里是否已经换了含义 | 术语冲突点、模型边界 |
| 团队边界 | 谁负责维护、谁有业务决策权、发布节奏是否一致 | 团队与上下文的映射 |
| 数据变更频率 | 哪些数据总是一起变化，哪些可以最终一致 | 聚合与上下文候选 |
| 一致性与事务 | 哪些规则必须强一致，哪些可以异步 | 聚合边界、事件边界 |

不要按 Controller / Service / DAO 这样的技术层拆上下文，也不要按数据库表拆。技术层是实现细节，限界上下文是业务语言和模型的边界。

### 1.3 上下文映射的七种关系【重点】

上下文映射描述两个上下文（通常也是两个团队）之间的组织关系与集成方式，箭头一般表示上游到下游。选择哪种关系，取决于下游对上游模型的影响力、集成成本和变化频率。

| 关系 | 方向与权力 | 适用场景 | 主要代价 |
| --- | --- | --- | --- |
| 合作关系（Partnership） | 双向对等，双方共同排期 | 两个团队目标高度绑定，必须同步演进 | 沟通成本高，任何一方变更都要协调 |
| 共享内核（Shared Kernel） | 双方共享一小块模型或代码 | 确实存在稳定、少量、双方都认可的公共概念 | 共享代码变更会同时影响双方，需要严格治理 |
| 客户-供应商（Customer-Supplier） | 上游供应、下游消费，下游可提需求 | 下游依赖上游，但上游仍保留决策权 | 需要排期与接口协商，下游仍有被动性 |
| 遵奉者（Conformist） | 下游完全服从上游模型 | 上游强势、下游没有谈判能力，且集成价值高 | 上游模型会污染下游语言，长期难改 |
| 防腐层（Anticorruption Layer） | 下游建翻译层，隔离上游模型 | 上游是遗留系统、第三方、模型差异大 | 多一层转换与维护，性能和复杂度上升 |
| 隔离（Separate Ways） | 双方不集成，各自实现 | 集成价值低、成本高，或团队完全独立 | 功能重复，数据可能不一致 |
| 发布语言（Published Language） | 上游发布稳定、文档化的交换格式 | 多个下游消费同一能力，接口需要长期稳定 | 语言设计成本高，版本管理要求高 |

**开放主机服务（Open Host Service，OHS）** 通常与发布语言一起使用：上游提供一套稳定的、面向多消费者的服务协议，发布语言则是协议中传输的数据格式（JSON Schema、Protobuf、事件契约等）。OHS + 发布语言适合平台型上游；如果下游模型与上游差异很大，再在下游加防腐层。

除同步 API 外，跨上下文也常用**领域事件**做异步集成。事件应使用发布语言定义，下游通过防腐层或独立的事件处理器把外部事件翻译成本地模型。异步集成降低时序耦合，但引入最终一致性、幂等和消息可靠性问题。

### 1.4 事件风暴工作坊【重点】

事件风暴是用时间线把业务流程摊开、让业务专家和研发共同发现领域事件、命令、聚合和边界的建模活动。它不是画一张漂亮的图，而是让分歧尽早暴露。

| 步骤 | 做法 | 产出 |
| --- | --- | --- |
| 1. 铺时间线 | 用橙色贴纸写出业务中已经发生的事实，统一用过去时，如「订单已创建」「库存已锁定」 | 领域事件流 |
| 2. 补触发者 | 用蓝色写命令，补充执行命令的角色、策略、外部系统 | 命令与事件的关系 |
| 3. 找聚合 | 把必须一起变化的事件和命令聚在一起，标出聚合候选 | 聚合与一致性边界候选 |
| 4. 标热点 | 记录术语冲突、规则分歧、数据缺口和异常流程 | 待澄清问题清单 |
| 5. 划边界 | 观察哪些事件总在一起、哪些词已经换义，聚类成限界上下文 | 上下文候选与上下文映射 |
| 6. 定优先级 | 区分核心域、支撑域、通用域 | 投入与迭代计划 |

工作坊通常需要业务专家、产品、研发共同参与，2 到 4 小时为宜。输出的是假设而非最终架构，后续要用代码、数据和真实流程验证。不要一次性做「大而全」的模型，边界应随业务理解迭代。

### 1.5 DDD 与微服务拆分的关系【重点】

「一个限界上下文对应一个微服务」是常见默认，不是教条。上下文边界是模型和语言边界，微服务边界还叠加了团队、部署、伸缩、故障隔离和事务成本。

| 情况 | 更合适的做法 |
| --- | --- |
| 一个上下文由独立团队维护，数据与发布独立 | 一个上下文一个服务，最清晰 |
| 多个小上下文由同一小团队维护，强事务较多 | 先放在一个服务内做模块化，避免分布式事务 |
| 一个上下文内不同能力伸缩差异很大 | 可以拆成多个部署单元，但保持同一模型边界 |
| 上下文边界尚未稳定 | 先单体模块化，边界稳定后再拆服务 |

拆服务前先画上下文映射，明确上下游、共享数据和集成方式。按技术层拆、按表拆、多个服务共享一个数据库，都会得到「分布式单体」：进程分开了，耦合和事务关系没有分开。服务拆分应做到数据所有权清晰、接口契约稳定、失败可隔离；做不到时，单体模块化往往比强行微服务更可控。

## 二、DDD 战术设计

### 2.1 实体与值对象【核心】

**实体（Entity）** 有唯一标识，标识不变，对象就是同一个东西，即使属性变化也不改变身份。**值对象（Value Object）** 没有独立标识，靠属性值判断相等，应当不可变，修改时整体替换。

| 维度 | 实体 | 值对象 |
| --- | --- | --- |
| 身份 | 有唯一 ID，生命周期内保持 | 无独立 ID，由属性共同定义 |
| 相等性 | 比较 ID | 比较全部业务属性（或业务键） |
| 可变性 | 可以经历状态迁移，但只能通过业务方法 | 不可变，修改即创建新对象 |
| 持久化 | 通常对应一张表或聚合根 | 可内嵌为字段、JSON、独立表，但无独立身份 |
| 例子 | 订单、账户、用户 | 金额、地址、日期区间、订单号 |

值对象应在构造时完成校验，例如金额不能为负、币种必须一致，避免把非法状态带进领域。`Money`、`Address` 这类值对象可以封装格式化和比较逻辑，但不要把它们做成只有 getter/setter 的贫血结构。

注意术语冲突：DDD 里的 VO 是 Value Object；分层架构里的 VO 常指 View Object（视图对象）。本文在战术设计中称「值对象」，在 3.5 中称「视图对象」。

### 2.2 聚合与聚合根【核心】

**聚合（Aggregate）** 是一组需要保持业务一致性的实体和值对象的集合，**聚合根（Aggregate Root）** 是聚合对外唯一的入口。外部只能通过聚合根访问和修改内部对象，聚合根负责维护聚合内的不变量。

| 设计规则 | 原因 |
| --- | --- |
| 聚合尽量小 | 聚合是加载、锁和事务的单位，越大冲突越多、性能越差 |
| 外部只引用聚合根 ID | 避免对象图跨聚合蔓延，避免绕过根修改内部对象 |
| 一个事务原则上只修改一个聚合 | 聚合内强一致，跨聚合用领域事件实现最终一致 |
| 聚合根保护不变量 | 总价、状态、数量等规则不能散落在应用服务里 |
| 不暴露可变内部集合 | 防止外部直接增删聚合内实体，破坏一致性 |

以订单为例，订单是聚合根，订单项是聚合内实体。外部不能绕过订单直接修改订单项数量，因为订单总价、优惠分摊和状态需要一起校验。

```java
public class Order {
    private final OrderId id;
    private OrderStatus status;
    private final List<OrderItem> items = new ArrayList<>();
    private long version;

    public void addItem(ProductId productId, Money price, int quantity) {
        if (status != OrderStatus.CREATED) {
            throw new IllegalStateException("订单当前状态不可编辑");
        }
        items.add(new OrderItem(productId, price, quantity));
    }

    public void pay() {
        if (status != OrderStatus.CREATED) {
            throw new IllegalStateException("订单当前状态不可支付");
        }
        status = OrderStatus.PAID;
    }

    public Money total() {
        return items.stream().map(OrderItem::subtotal).reduce(Money.zero(), Money::add);
    }
}
```

上例中 `OrderItem` 只允许在订单内部创建和修改，`Order` 通过 `addItem`、`pay` 维护状态规则，`version` 用于并发控制。聚合根不是「最大的实体」，而是「一致性边界的入口」。

### 2.3 领域服务与应用服务【核心】

**领域服务（Domain Service）** 承载不属于单个实体或值对象的领域规则，通常跨多个聚合，本身无状态，使用统一语言命名。典型例子是转账：规则涉及两个账户，放在任一账户实体上都不自然。**应用服务（Application Service）** 负责编排用例：鉴权、加载聚合、调用领域方法、开启事务、保存聚合、发布事件、转换 DTO，本身不含业务规则。

| 维度 | 领域服务 | 应用服务 |
| --- | --- | --- |
| 所在层 | 领域层 | 应用层 |
| 职责 | 跨实体/跨聚合的领域规则 | 用例编排与事务边界 |
| 状态 | 无状态 | 无状态，但可依赖仓储、领域服务、事件发布器 |
| 事务 | 不拥有事务边界 | 通常在这里声明事务 |
| 依赖 | 只依赖领域模型和领域抽象 | 可以依赖领域层、端口、DTO |
| 例子 | 转账、定价策略、库存分配 | 下单、支付、取消订单 |

不要把应用服务写成新的「事务脚本大管家」：如果一段逻辑只涉及一个聚合，应放回聚合方法；如果涉及多个聚合的业务规则，放领域服务；应用服务只做流程编排。领域服务也不应膨胀成万能类，命名要体现业务动作。

### 2.4 领域事件【重点】

**领域事件** 表示领域里已经发生的一件业务事实，用过去时命名，如 `OrderPaid`、`StockReserved`、`PaymentFailed`。它应包含事件 ID、发生时间、聚合 ID、聚合版本以及下游需要的业务数据；事件一旦发布就代表事实，不应被修改。

领域事件有两个作用：一是解耦聚合之间、上下文之间的协作；二是为审计、投影和后续流程提供触发点。聚合内部可以直接产生事件，由应用服务在事务边界统一发布；跨服务则通过消息中间件发布。事件不是命令：命令表达「请做某事」，可以被拒绝；事件表达「已经发生」，只能被消费或补偿。

不要在简单流程里滥用事件。一个应用服务内两三步同步调用就能完成、且必须强一致的场景，引入事件只会增加最终一致性和排查成本。

### 2.5 仓储与工厂【了解】

**仓储（Repository）** 是聚合的集合式抽象，一个聚合根通常对应一个仓储。接口放在领域层，实现放在基础设施层；对外提供 `findById`、`save`、`delete` 等面向聚合的方法，不暴露 SQL、表名或任意字段查询。复杂列表查询、报表查询不要硬塞进聚合仓储，应走查询服务或读模型。

**工厂（Factory）** 用于封装复杂对象的创建或重建，保证创建出来的聚合满足不变量。简单对象用静态工厂方法即可，不必为每个类建工厂类。工厂不是持久化工厂，不负责数据库细节。

### 2.6 贫血模型与充血模型【重点】

| 维度 | 贫血模型 | 充血模型 |
| --- | --- | --- |
| 逻辑位置 | 实体只有 getter/setter，逻辑集中在 Service | 业务规则放在实体/聚合方法中 |
| 不变量 | 容易被绕过，依赖调用方自觉 | 由对象自身保护 |
| 可测试性 | 需要连着 Service 和依赖一起测 | 领域对象可纯内存单测 |
| 适用场景 | 简单 CRUD、报表、规则稳定的支撑域 | 规则复杂、状态多的核心域 |
| 主要风险 | 逻辑散落、重复、状态非法 | 过度设计、与 ORM 耦合、对象膨胀 |

选择标准是业务复杂度，不是团队喜好。简单增删改查用贫血模型足够；核心域的状态迁移、金额计算、库存规则适合充血模型。实际项目可以混合：核心聚合充血，外围管理功能贫血。

充血模型与 ORM 配合时要注意：领域对象不要继承框架基类，不要把持久化注解散布到核心规则中；JPA 可用 `protected` 无参构造和字段访问，MyBatis 用 `resultMap` 或构造器映射重建对象。事务边界放在应用服务，领域方法不声明 `@Transactional`。

### 2.7 聚合边界判定与并发冲突【重点】

判定聚合边界，先列出业务不变量，再问「这条规则必须在哪个时间点成立」。必须立即强一致的规则放进同一个聚合；可以容忍短暂不一致的跨聚合规则，用领域事件和 Saga 处理。然后检查聚合大小、加载成本、锁竞争和生命周期，避免把客户、商品、库存都塞进订单聚合。

聚合并发冲突常用**乐观锁**：

- 聚合根维护 `version` 字段，更新时执行 `UPDATE ... SET version = version + 1 WHERE id = ? AND version = ?`。
- 受影响行数为 0 表示版本已变，应用服务重新加载聚合、重试或向用户返回冲突。
- JPA 使用 `@Version`，MyBatis-Plus 使用 `@Version` 插件；数据库唯一约束作为最终兜底。
- 重试要有次数上限和退避，避免高冲突下活锁；冲突极高的聚合应拆分热点、串行化命令或改用预留/扣减模型。
- 跨聚合事件也要带版本或序列号，消费者据此识别过期事件。

不要用长事务和悲观锁掩盖聚合设计问题。锁的范围越大，吞吐越低；如果两个操作经常冲突，往往说明它们本应属于同一个聚合，或者需要重新设计业务流程。

## 三、分层与六边形架构

### 3.1 经典四层职责与依赖方向【重点】

| 层 | 职责 | 依赖方向 | 典型内容 |
| --- | --- | --- | --- |
| 接口层（用户接口层） | 接收 HTTP/RPC/MQ/CLI 请求，参数校验，DTO 转换，返回视图对象 | 依赖应用层 | Controller、RPC Facade、消息监听器 |
| 应用层 | 编排用例，开启事务，鉴权，加载/保存聚合，发布事件 | 依赖领域层 | Application Service、命令/查询服务 |
| 领域层 | 实体、值对象、聚合、领域服务、领域事件、仓储接口 | 不依赖其他层 | 业务规则与模型 |
| 基础设施层 | 数据库、缓存、MQ、第三方调用、仓储实现、防腐层适配器 | 依赖领域层（实现其接口） | Repository Impl、Gateway、MQ Producer |

传统三层是「上层依赖下层」，Service 直接依赖 DAO，业务逻辑和数据库、框架绑死。DDD 四层的关键不是多一层，而是**领域层位于中心，技术实现向外围退**。依赖方向应指向领域：接口层依赖应用层，应用层依赖领域层，基础设施层实现领域层定义的接口。

### 3.2 依赖倒置与领域层零依赖【了解】

依赖倒置的做法是：领域层定义 `OrderRepository` 接口，基础设施层提供 `MyBatisOrderRepository` 实现；应用服务只依赖接口，运行时由 Spring 注入实现。这样领域层不 import JDBC、MyBatis、Spring Data 等框架类型，可以脱离数据库做单元测试，替换存储也不影响核心规则。

依赖倒置不是把接口放在基础设施层，也不是让领域层反过来调用基础设施。接口的所有权应跟着「谁需要、谁定义」走：领域需要持久化抽象，就由领域定义仓储接口；应用需要发消息，就由应用定义事件发布端口，基础设施实现适配器。

### 3.3 六边形架构：端口与适配器【了解】

六边形架构把领域和应用放在中心，对外定义端口，外部系统通过适配器接入。依赖方向一律指向中心，核心不感知 HTTP、数据库、MQ 等具体技术。

| 概念 | 含义 | 例子 |
| --- | --- | --- |
| 驱动端口 | 外部主动调用核心的入口 | 下单用例、支付用例 |
| 驱动适配器 | 把外部请求翻译成端口调用 | Controller、RPC、MQ 消费者、CLI |
| 被驱动端口 | 核心需要外部能力的抽象 | 仓储、消息发送、第三方支付、缓存 |
| 被驱动适配器 | 实现端口的技术细节 | MySQL Repository、Kafka Producer、支付 SDK |

六边形与四层并不冲突：四层按职责分层，六边形强调边界和依赖方向。六边形的收益是核心可测试、技术可替换、接入方式可增加；代价是端口和适配器数量增多，简单项目会显得繁琐。它也不等于微服务，单体应用内部同样可以使用。

### 3.4 CQRS 在分层中的位置【了解】

命令侧走「接口层 → 应用服务 → 聚合/仓储」，查询侧可以绕过聚合，直接由查询服务读取读模型并返回 DTO/视图对象。查询逻辑不放进领域层，因为领域层应表达业务规则，而不是页面需要的联表、聚合和格式化。

在四层中，查询服务通常放在应用层或独立的查询模块；它的适配器（如 MyBatis Mapper、ES Client）放在基础设施层。简单系统可以让读写共用数据库，只分离查询方法和 DTO；是否需要独立读库、独立服务，见第五章。

### 3.5 DTO、VO、BO、DO（PO）的区别与转换【重点】

| 对象 | 所在位置 | 职责 | 典型内容 |
| --- | --- | --- | --- |
| DO / PO | 持久化层 | 与数据库表或集合映射，承载持久化字段 | 表字段、JPA/MyBatis 映射 |
| BO | 业务层 | 表达业务对象，可由多个 DO 组合；在 DDD 中通常对应领域对象 | 业务属性、业务方法 |
| DTO | 跨层/跨服务边界 | 传输数据，入参出参契约，通常不含业务逻辑 | 请求/响应字段、校验注解 |
| VO（视图对象） | 接口层 | 面向页面或客户端的展示结构 | 格式化金额、状态文案、聚合字段 |

**不能把 DO 直接返回前端**，原因至少包括：

- 数据库字段变化会直接变成外部接口变化，前端被数据库结构绑死。
- 密码、内部标记、逻辑删除、租户 ID 等敏感字段容易泄露。
- 懒加载对象序列化可能触发额外查询、循环引用或延迟加载异常。
- 页面需要状态文案、金额格式、字段裁剪，DO 不应该承载展示逻辑。
- 入参直接绑定 DO 可能造成越权字段赋值（mass assignment）。

转换建议使用 MapStruct：编译期生成映射代码，类型安全，性能接近手写；避免用 `BeanUtils` 反射拷贝，它在字段改名、嵌套对象和类型转换上容易静默出错。转换应放在接口层或应用层边界，不要让领域对象依赖 Web DTO。简单项目可以合并 BO 与 DTO、减少对象数量，但涉及敏感字段和外部契约时不能省。

### 3.6 防腐层（ACL）【了解】

防腐层是下游隔离上游模型的翻译层：调用第三方或其他上下文时，不直接把对方的 DTO、异常、注解带进自己的领域，而是在边界处转换成自己的值对象、实体或领域事件。对方接口变更时只改 ACL，核心代码不受影响。

ACL 通常实现为一个被驱动端口加适配器，除了模型转换，还统一处理超时、重试、熔断、降级、错误码映射和幂等。它与普通 DTO 转换的区别在于：DTO 转换是内部层之间的数据整形，ACL 是跨系统边界的模型与协议隔离。

## 四、事件驱动架构

### 4.1 事件通知、事件携带状态转移与事件溯源【重点】

| 模式 | 事件内容 | 下游动作 | 优点 | 代价 |
| --- | --- | --- | --- | --- |
| 事件通知（Event Notification） | 只带 ID、类型等少量信息 | 收到后回调上游查询详情 | 耦合低，事件体小 | 回查流量、时序耦合、上游必须提供查询接口 |
| 事件携带状态转移（ECST） | 带上游状态快照或变更数据 | 本地保存副本，直接使用 | 下游免回查，可用性好 | 数据冗余、消息变大、版本与一致性复杂 |
| 事件溯源（Event Sourcing） | 以事件流作为状态的事实来源 | 重放事件得到状态，投影出读模型 | 完整审计、可回溯、可重建 | 查询复杂、Schema 演进难、运维门槛高 |

事件通知适合「通知发生了什么」，下游只关心触发；ECST 适合下游需要频繁读取上游数据、又不想同步回查的场景，例如订单服务把支付结果、订单金额、商品和收货地址冗余到履约服务；事件溯源是一种**持久化方式**，不是简单的消息通知，账户余额由所有存取款事件累加得到，当前状态是事件流的投影。

三者可以组合：事件溯源产生的事件，可以同时以通知或 ECST 的形式发布给其他上下文。使用 Kafka 存消息不等于事件溯源；只有把事件流当作业务状态的唯一事实来源，才叫事件溯源。

### 4.2 发布订阅与事件总线【重点】

| 维度 | 进程内事件（Spring Event） | 跨服务事件（MQ） |
| --- | --- | --- |
| 传输范围 | 同一 JVM | 跨进程、跨服务 |
| 默认语义 | 同步调用，默认在发布线程执行 | 异步，至少一次投递 |
| 事务关系 | 与发布方事务同线程，容易在提交前发出 | 需要 outbox 或事务消息避免双写不一致 |
| 失败处理 | 监听器异常可能影响发布方 | 重试、死信、告警、人工补偿 |
| 适用 | 模块解耦、领域事件通知、提交后副作用 | 服务解耦、削峰、跨团队集成 |

事件总线可以是进程内的（Spring `ApplicationEventPublisher`、Guava EventBus、Axon），也可以是分布式的（Kafka、RocketMQ、RabbitMQ）。跨服务事件建议使用统一的事件信封，至少包含 `eventId`、`eventType`、`eventVersion`、`occurredAt`、`producer`、`correlationId`、`causationId` 和业务载荷，便于幂等、追踪和版本演进。

### 4.3 编排与协同【重点】

| 维度 | 编排（Orchestration） | 协同（Choreography） |
| --- | --- | --- |
| 流程控制 | 中心协调者依次调用参与者，决定下一步 | 各服务监听事件，自行决定是否行动 |
| 状态归属 | 协调者持久化流程状态 | 状态分散在各服务，通过业务 ID 关联 |
| 可观测性 | 流程集中，容易看全貌和补偿 | 流程隐式，排查和追踪困难 |
| 耦合 | 参与者依赖协调者协议 | 服务间只依赖事件契约 |
| 适用 | 步骤多、需要补偿、流程长的 Saga | 步骤少、关系简单、追求解耦 |

编排适合订单履约、退款、跨服务开户这类长流程：协调者可以是订单服务，也可以是工作流引擎，它负责记录每一步状态并触发补偿。协同适合「支付成功后发积分、发通知」这类短流程，服务之间不需要知道完整流程。长流程不要硬用协同，否则流程知识散落在各个服务里，出问题时很难还原；短流程也不必上重型编排器。

Saga 是长事务的补偿方案，不是 ACID。编排器要保存 Saga 状态、设置超时、保证补偿幂等；有些步骤不可补偿（短信已发、货已出库），需要在设计时改为可逆操作或人工处理。实际项目常采用混合方式：大的业务流程用编排，子域内部用协同。

### 4.4 最终一致性、幂等消费、补偿与死信【重点】

跨服务事件没有全局事务，只能保证最终一致。工程上要接受「短暂不一致」，并通过重试、补偿、对账把状态收敛到正确结果。

| 问题 | 常用手段 |
| --- | --- |
| 消息可能重复 | 消费端幂等：唯一消息 ID 表、业务唯一键、状态机条件更新、Redis 去重窗口 |
| 消息可能丢失 | 本地事务 + outbox 表，后台投递；生产端确认、持久化、副本；消费端手动 ack |
| 消费失败 | 有限重试 + 退避；超过次数进入死信队列，告警并支持重放 |
| 顺序错乱 | 以聚合 ID 作为分区键；事件带版本或序列号，状态机拒绝过期事件 |
| 需要回滚 | Saga 补偿、TCC Cancel、反向流水；补偿必须幂等，尽量可交换 |
| 无法补偿 | 设计阶段避免不可逆副作用，或转人工处理并对账 |

端到端的「恰好一次」很难靠消息中间件单独保证；Kafka 事务只覆盖 Kafka 内部的读-处理-写，外部数据库或 HTTP 副作用仍需幂等。**事务性 outbox** 是常用的可靠发布方案：业务表和 outbox 记录在同一个本地事务中写入，再由独立 relay 轮询或 CDC 投递到 MQ，避免「数据库提交成功但消息发送失败」的双写不一致。

死信队列不是垃圾桶。消息进入死信后要保留原始载荷、异常栈、重试次数和 traceId，配置告警、查询和重放工具；重放前要确认下游已修复，并防止重复副作用。

### 4.5 Spring 事件与 @TransactionalEventListener【重点】

`@EventListener` 默认同步执行，监听器在发布方线程、发布方事务内运行。如果监听器里发 MQ、调用外部接口，而发布方事务随后回滚，就会出现「消息已发、数据没落库」的不一致。`@TransactionalEventListener` 可以把监听器绑定到事务阶段，默认阶段是 `AFTER_COMMIT`。

```java
@Service
public class OrderApplicationService {
    private final OrderRepository repository;
    private final ApplicationEventPublisher publisher;

    @Transactional
    public void pay(OrderId orderId) {
        Order order = repository.findById(orderId).orElseThrow();
        order.pay();
        repository.save(order);
        publisher.publishEvent(new OrderPaidEvent(order.getId(), order.getVersion()));
    }
}

@Component
public class OrderPaidListener {
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    public void onOrderPaid(OrderPaidEvent event) {
        // 事务已提交，适合做通知、投影、缓存失效
        // 若这里还要写库，需开启新事务
    }
}
```

| 事务阶段 | 触发时机 | 注意事项 |
| --- | --- | --- |
| `BEFORE_COMMIT` | 提交前 | 监听器异常仍可回滚原事务 |
| `AFTER_COMMIT` | 提交成功后 | 原事务无法回滚；监听器异常不影响已提交数据 |
| `AFTER_ROLLBACK` | 回滚后 | 适合记录失败日志、补偿标记 |
| `AFTER_COMPLETION` | 事务结束后 | 无论提交或回滚都触发 |

使用要点：

- `AFTER_COMMIT` 监听器里如果写数据库，要声明 `REQUIRES_NEW`，否则可能没有可用事务或复用已结束的事务资源。
- 没有活动事务时，`@TransactionalEventListener` 默认不触发；需要触发时设置 `fallbackExecution = true`。
- 加 `@Async` 后异常不会传回发布方，需配置异常处理器；异步线程也拿不到原事务和 MDC 上下文。
- 不要把实体直接放进事件对象，事务结束后懒加载会失败；事件里放 ID、版本和必要快照。
- 即使使用 `AFTER_COMMIT`，进程在提交后、消息发送前崩溃仍会丢消息；跨服务可靠发布仍应使用 outbox。

### 4.6 事件版本演进与兼容【了解】

事件契约一旦发布就很难收回，尤其是事件溯源中历史事件会长期保留。演进原则是**向后兼容、宽容读取**：

| 变更 | 是否兼容 | 做法 |
| --- | --- | --- |
| 新增可选字段 | 通常兼容 | 消费端忽略未知字段，新字段有默认值 |
| 删除字段 | 不兼容 | 先标记废弃，确认所有消费者迁移后再删 |
| 重命名字段 | 不兼容 | 保留旧字段并双写，或发新版本事件 |
| 修改字段语义 | 不兼容 | 新增字段或新事件类型，不要复用旧字段 |
| 新增事件类型 | 兼容 | 消费者按类型订阅，未知类型忽略并记录 |

事件信封中带 `eventVersion`，消费端用 upcasting 把旧版本转换为新模型；重大变更可以双发旧版和新版事件，或使用新 topic。事件溯源回放时必须能处理历史版本，不能假设事件永远是当前 Schema。生产环境建议使用 Schema Registry 和契约测试，避免消费端上线才发现不兼容。

## 五、CQRS 与事件溯源

### 5.1 命令模型与查询模型分离【重点】

CQRS 把「改变状态」和「读取状态」分开建模。命令表达意图，如 `PayOrderCommand`，由命令处理器加载聚合、校验规则、写入并发布事件；查询直接面向读模型，返回为页面或接口定制的 DTO，不经过聚合。

| 维度 | 命令侧 | 查询侧 |
| --- | --- | --- |
| 目的 | 执行业务规则、改变状态 | 高效读取、组装展示数据 |
| 模型 | 聚合、实体、值对象、领域服务 | 读模型、宽表、视图、搜索索引 |
| 返回 | 通常只返回 ID 或成功标识 | 返回 DTO/视图对象 |
| 一致性 | 强一致（聚合内） | 最终一致（投影同步后） |
| 扩展 | 按写压力扩展 | 按读压力独立扩展 |

CQRS 有不同落地层级：同一数据库内分离命令服务和查询服务；同一库内用物化视图/读表；独立读库或 Elasticsearch；独立服务加事件总线；再进一步结合事件溯源。不是一上 CQRS 就必须拆库拆服务。

### 5.2 读模型投影与同步延迟【了解】

读模型通过订阅领域事件构建：事件处理器把变更投影到读库、缓存或搜索索引，并记录消费位点（checkpoint）。投影必须幂等，失败后可以从位点重试；读模型可以按查询场景建多份，例如订单列表宽表、订单搜索索引、运营报表。

投影是异步的，所以存在同步延迟。用户刚下单就查询列表，可能查不到，这是「读己之写」问题。常见处理：关键页面直接读命令侧、返回版本号并等待投影追平、前端乐观展示、对延迟做监控和告警。不能假设投影永远实时。

### 5.3 事件回放重建【了解】

事件溯源把事件流作为事实来源，聚合状态通过「快照 + 快照之后的事件」重建；读模型可以从头回放事件重建。回放常用于修复投影 Bug、新增查询视图、审计追溯。

回放要注意：投影逻辑必须幂等且可重复执行；回放期间不要触发短信、扣款等副作用；使用新索引重建后通过别名切换，避免影响在线查询；记录投影版本，升级逻辑时明确是否需要全量重建；事件量大时依赖快照和批量并行，控制回放对线上资源的冲击。

### 5.4 与事件溯源的关系、适用场景与代价【了解】

| 组合 | 说明 |
| --- | --- |
| 只有 CQRS，没有事件溯源 | 命令写业务库，查询读读库/视图；事件只是同步手段 |
| CQRS + 事件溯源 | 事件流是写侧事实来源，读侧由投影构建，最常见组合 |
| 只有事件溯源，没有 CQRS | 聚合从事件重建，查询仍可直接读事件流或简单索引，但复杂查询会很别扭 |

适合 CQRS/事件溯源的场景：核心域规则复杂且读写模型差异大；读多写少或写多读少导致扩缩容矛盾；需要完整审计、逐笔流水、任意时刻回溯；需要多种查询视图；写侧以追加事件为主。金融账务、交易流水、合规审计是典型场景。

不适合的场景：简单 CRUD；必须强一致读取；查询形态单一；团队缺乏事件基础设施和运维能力；业务 Schema 频繁剧烈变化。代价包括最终一致、投影与回放运维、事件版本管理、重复存储、学习成本、隐私数据删除困难。**不必上 CQRS 的判断标准**：现有单模型能支撑查询和写入；没有明显的读写负载矛盾；无法接受读延迟；团队没有消息与投影运维能力。此时用缓存、读写分离、搜索索引同步往往更划算。

### 5.5 相邻主题：秒杀与稳定性治理【了解】

秒杀系统的核心是层层过滤：前端静态化与 CDN、按钮控制、验证码打散、动态地址；网关按用户和 IP 限流；服务层用 Redis 预热与 Lua 原子扣减、本地售罄标记、用户去重、MQ 异步下单；数据层用条件更新防超卖，并配合独立部署、压测预案和超时未付回补库存。完整的分层方案见《分布式与微服务核心知识点学习文档.md》7.2。

限流控制入口流量，降级牺牲非核心功能，熔断在下游故障时快速失败并按关闭、打开、半开状态机恢复，隔离用线程池舱壁和核心/非核心资源分离。限流算法包括固定窗口、滑动窗口、漏桶和令牌桶；单机可用 Guava RateLimiter 或 Sentinel，分布式可用 Redis + Lua 或集群流控。完整对比见该文档第三章 3.1 至 3.5。

| --- | --- | --- | --- |
| 1 | DDD 的战略设计是什么？限界上下文怎么划分？上下文之间怎么集成？ | 战略设计划系统边界，战术设计管上下文内建模；限界上下文是统一语言有效边界；事件风暴后按业务能力、语言边界、团队边界、数据变更频率划分；子域分核心/支撑/通用；集成用 ACL、OHS + 发布语言、共享内核、领域事件；通常一个上下文一个服务 | 一 |
| 2 | DDD 战术设计里的实体、值对象、聚合、聚合根、领域服务、领域事件是什么？贫血和充血怎么选？ | 实体靠 ID，值对象靠属性相等且不可变；聚合是一致性边界，聚合根是唯一入口；聚合要小，一个事务改一个聚合，跨聚合用 ID 引用加事件；领域服务放跨实体规则，领域事件表达已发生事实；简单 CRUD 用贫血，复杂核心域用充血 | 二 |
| 3 | 经典 DDD 四层和六边形架构？依赖倒置怎么体现？ | 接口层做协议与 DTO，应用层编排用例和事务，领域层放模型与规则，基础设施层做技术实现；依赖指向领域；领域定义仓储接口，基础设施实现；六边形以领域为中心，驱动/被驱动适配器接端口，依赖一律向内 | 三 |
| 4 | DTO、VO、BO、DO（PO）区别？为什么分？防腐层做什么？ | DO/PO 对应表，BO 表达业务，DTO 跨层/跨服务传输，视图对象面向展示；隔离数据库变化与敏感字段，避免 DO 直接返回前端；MapStruct 编译期转换；ACL 翻译外部模型并统一异常、重试、降级 | 三 |
| 5 | 事件通知、事件携带状态转移和事件溯源有什么区别？编排和协同怎么选？ | 通知只带 ID 下游回查；ECST 带快照做本地副本；事件溯源存事件流重放得状态；编排有中心协调者、流程清晰易补偿但可能成瓶颈；协同靠事件解耦、难追踪；长流程用编排，短流程用协同 | 四 |
| 6 | 如果让你设计一个秒杀系统，你会从哪些层面考虑？ | 见分布式文档（第七章 7.2）：前端、网关、服务、数据层层层过滤，Redis + Lua 扣减，MQ 异步下单，条件更新兜底 | 分布式文档 7.2 |
| 7 | 限流、降级、熔断、隔离分别是什么？常见限流算法？ | 见分布式文档（第三章 3.1 至 3.5）：令牌桶、漏桶、滑动窗口、固定窗口；Sentinel/Guava；Redis + Lua 集群限流 | 分布式文档 三 |
| 8 | 限界上下文与子域是什么关系？怎么避免拆错？ | 子域是问题空间，上下文是解决方案空间，不必一一对应；按业务能力、语言边界、团队边界、一致性交叉验证；先事件风暴再拆，边界未稳先模块化 | 一 |
| 9 | 上下文映射有哪七种关系？防腐层何时用？ | 合作、共享内核、客户-供应商、遵奉者、防腐层、隔离、发布语言；OHS + 发布语言用于稳定开放接口；上游遗留/第三方且模型差异大时用 ACL | 一 |
| 10 | 聚合为什么要小？跨聚合一致性怎么保证？ | 聚合是加载、锁、事务单位，越大冲突和加载成本越高；强一致规则放聚合内，跨聚合用 ID 引用、领域事件、Saga 最终一致 | 二 |
| 11 | 聚合并发更新冲突怎么处理？ | 版本号乐观锁，条件更新失败则重载重试；JPA/MyBatis-Plus 的 @Version；唯一约束兜底；高冲突时拆热点或串行化命令 | 二 |
| 12 | 领域服务和应用服务有什么区别？ | 领域服务放跨实体/跨聚合的业务规则，无状态；应用服务编排用例、管事务、鉴权、加载保存聚合、发事件，本身很薄 | 二 |
| 13 | 贫血模型和充血模型怎么选？ | 简单 CRUD、支撑域用贫血；规则复杂、状态多的核心域用充血；混合使用；充血不等于把持久化代码塞进实体 | 二 |
| 14 | 为什么不能把 DO 直接返回前端？ | 数据库结构外泄、敏感字段泄露、前端与表结构耦合、懒加载与序列化问题、展示格式不该改实体；用 DTO/视图对象和 MapStruct 转换 | 三 |
| 15 | 六边形架构的端口与适配器是什么？ | 领域和应用在中心，对外定义端口；HTTP/MQ/CLI 是驱动适配器，数据库/缓存/第三方是被驱动适配器；依赖指向中心，便于单测和替换实现 | 三 |
| 16 | 如何保证事件不丢、消费幂等？ | 本地事务 + outbox 可靠发布；消费端唯一消息 ID/业务唯一键/状态机去重；至少一次加幂等；重试、死信、告警、重放；按聚合 ID 保序 | 四 |
| 17 | 为什么用 @TransactionalEventListener？ | 默认监听器在事务内，可能消息先发而事务回滚；AFTER_COMMIT 在提交后执行；写库要新事务；异常不回滚原事务；跨服务仍建议 outbox | 四 |
| 18 | 事件如何做版本演进与兼容？ | 只加可选字段、宽容读取、保留旧字段；重命名/改语义发新版本或双写；事件带 eventVersion；消费端 upcasting；回放兼容历史 Schema | 四 |
| 19 | CQRS 适合什么场景？什么时候不该上？ | 读写模型差异大、负载不均、复杂查询、审计需求时适合；简单 CRUD、强一致读、团队无运维能力时不该上；可以先做轻量读写分离 | 五 |
| 20 | CQRS 与事件溯源是什么关系？ | CQRS 是读写分离，事件溯源是事件流存储；可单独使用，也常组合；ES 需要投影支撑查询；ES 不是消息队列，CQRS 也不必然拆库拆服务 | 五 |
