## 一、架构与存储引擎

MySQL 分为 Server 层和可插拔的存储引擎层：Server 层负责连接、解析、优化、执行和 binlog，存储引擎负责数据的存取。MySQL 5.5 起默认引擎为 InnoDB。

### 1.1 一条查询 SQL 的执行过程【核心】

1. **连接器**：TCP 握手、校验用户名密码、读取权限。权限在连接建立时读取，之后修改权限只对新连接生效。空闲连接超过 `wait_timeout`（默认 8 小时）会被断开。
2. **查询缓存**：任一表更新都会清空该表全部缓存，命中率低，**MySQL 8.0 已移除**。
3. **分析器**：词法分析和语法分析，生成语法树；表或字段不存在的报错也在这一阶段。
4. **优化器**：基于成本选择索引、决定多表 Join 的连接顺序，生成执行计划。
5. **执行器**：校验表权限后，调用存储引擎接口逐行取数据，并在 Server 层判断 WHERE 条件。
6. **存储引擎**：从 Buffer Pool 读数据页，不在内存则从磁盘加载。

查询缓存未画出，因为 MySQL 8.0 已将其移除。

**一条更新 SQL** 在此基础上还要：记 undo log → 改 Buffer Pool 中的页 → 记 redo log（prepare）→ 记 binlog → redo log 提交（commit），即第五章的两阶段提交。

### 1.2 InnoDB 与 MyISAM 的区别【核心】

| 维度 | InnoDB | MyISAM |
| --- | --- | --- |
| 事务 | 支持 | 不支持 |
| 锁粒度 | 行锁（基于索引） | 只有表锁 |
| 外键 | 支持 | 不支持 |
| 崩溃恢复 | 依靠 redo log 自动恢复 | 容易损坏，需要手动修复 |
| 索引结构 | 聚簇索引，数据存在主键索引叶子节点 | 非聚簇，索引与数据文件分离，叶子存行地址 |
| MVCC | 支持 | 不支持 |
| count(\*) | 需要扫描计数（因 MVCC 各事务可见行数不同） | 保存了总行数，无 WHERE 时 O(1) |
| 文件 | `.ibd`（数据 + 索引） | `.MYD` 数据 + `.MYI` 索引 |

**结论**：除极少数只读场景外一律用 InnoDB。MySQL 8.0 的系统表也已全部改为 InnoDB。

### 1.3 InnoDB 存储结构【重点】

表空间 → 段（Segment）→ 区（Extent，1 MB，连续 64 页）→ **页（Page，默认 16 KB，磁盘与内存交互的最小单位）**→ 行。行格式默认 `DYNAMIC`，每行有隐藏字段 `DB_TRX_ID`（最近修改的事务 ID）、`DB_ROLL_PTR`（指向 undo log 的回滚指针），没有主键时还有 `DB_ROW_ID`。这两个字段是 MVCC 的基础。

**页分裂与页合并【了解】**：页内的记录按主键有序存放。乱序插入主键（如 UUID）时目标页可能已满，InnoDB 会把该页分裂成两页并搬移部分记录，造成写入放大和空间碎片；大量删除后相邻页利用率过低时会触发页合并，阈值由 `MERGE_THRESHOLD`（默认 50%）控制。这是「推荐自增主键」的底层原因。

**行溢出【了解】**：一页至少要能放下两行，VARCHAR、TEXT 等大字段可能让一页放不下两行。`DYNAMIC` 行格式下超长列只存 20 字节指针，数据全部放到溢出页（老的 `COMPACT` 格式存前 768 字节 + 指针）。行溢出多意味着读一行要追额外的页，这也是大字段要拆扩展表的原因之一。

## 二、索引

索引的本质是用有序的数据结构把「全表扫描」变成「少量磁盘 I/O 的查找」。InnoDB 用 B+ 树，一棵 3 层的 B+ 树就能存放千万级数据，查一行只需约 3 次 I/O。

### 2.1 为什么是 B+ 树【核心】

| 结构 | 问题 |
| --- | --- |
| Hash | 等值查询 O(1)，但不支持范围查询、排序、最左前缀 |
| 二叉搜索树 / 红黑树 | 每个节点只有 2 个分叉，树太高，I/O 次数多；二叉搜索树还可能退化成链表 |
| B 树 | 非叶子节点也存数据，一页能放的键少、树更高；范围查询需要中序遍历 |
| **B+ 树** | 非叶子只存键和指针，扇出大、树矮；数据都在叶子，查询性能稳定；叶子间双向链表，范围查询顺序扫描即可 |

**容量估算【重点】**：主键 BIGINT 8 字节 + 指针 6 字节 = 14 字节，一个 16 KB 非叶子页约能存 16384 / 14 ≈ 1170 个指针。假设一行 1 KB，叶子页存 16 行，则 3 层可存 1170 × 1170 × 16 ≈ 2190 万行。根节点常驻内存，实际只需 1\~2 次磁盘 I/O。

### 2.2 聚簇索引与二级索引、回表【核心】

- **聚簇索引（主键索引）**：叶子节点存整行数据，一张表只有一个。选择顺序：主键 → 第一个非空唯一索引 → 隐藏的 `DB_ROW_ID`。
- **二级索引（辅助索引）**：叶子节点存索引列 + 主键值。
- **回表**：通过二级索引找到主键，再到聚簇索引查整行。每一行回表都是一次随机 I/O，匹配行数多时优化器可能宁可全表扫描。
- **为什么二级索引存主键而不是行地址**：页分裂时行的物理位置会变，存主键就不用更新二级索引。

&#91;embedded content: 回表过程 · 两棵 B+ 树\]

如果查询是 `SELECT id FROM t WHERE name = 'Bob'`，第 ① 步就拿到了全部结果，第 ② 步省掉，这就是覆盖索引。

### 2.3 覆盖索引与联合索引【核心】

**覆盖索引**：查询的列都在索引里，不需要回表，EXPLAIN 的 Extra 显示 `Using index`。这是「不要写 SELECT \*」的核心理由之一。

**最左前缀原则**：联合索引 `(a, b, c)` 先按 a 排序，a 相同再按 b，以此类推，所以只有从最左列开始的连续列才能用上索引。

| WHERE 条件 | 用到的列 | 说明 |
| --- | --- | --- |
| `a = 1` | a | 最左列 |
| `a = 1 AND b = 2 AND c = 3` | a, b, c | 全部匹配 |
| `b = 2 AND a = 1` | a, b | 优化器会调整顺序，与书写顺序无关 |
| `b = 2` | 无 | 缺少最左列（8.0 可能用 Skip Scan） |
| `a = 1 AND c = 3` | a | b 断开，c 只能靠索引下推过滤 |
| `a > 1 AND b = 2` | a | 范围查询后的列无法用于定位 |
| `a >= 1 AND b = 2` | a, b | `>=` 中等值部分的 b 仍可用于定位 |

**联合索引设计**：等值条件列放前面、范围列放后面；区分度高的列靠前；尽量让常用查询形成覆盖索引；顺带考虑 ORDER BY 以避免 filesort。

### 2.4 索引下推（ICP）【重点】

MySQL 5.6 引入。以索引 `(name, age)` 和 `WHERE name LIKE '张%' AND age = 20` 为例：没有 ICP 时，引擎按 name 找到所有匹配行后逐行回表，由 Server 层判断 age；有 ICP 时，引擎在遍历索引时就用索引里的 age 过滤，只对符合条件的行回表，减少回表次数。Extra 显示 `Using index condition`。

### 2.5 索引失效场景【核心】

1. 不满足最左前缀。
2. `LIKE '%xx'` 左模糊（`LIKE 'xx%'` 可以用）。
3. 对索引列做计算或函数：`WHERE YEAR(create_time) = 2026`、`WHERE id + 1 = 10`。应改写为范围条件，或使用 8.0 的函数索引。
4. **隐式类型转换**：`phone` 是 VARCHAR，却写 `WHERE phone = 13800000000`，等价于对列使用 CAST。反过来（整数列传字符串）则不失效。
5. 字符集或排序规则不同的字段做 Join（如 utf8 与 utf8mb4）。
6. `OR` 连接的条件中有一个列没有索引。
7. `!=`、`NOT IN`、`IS NOT NULL` 等：不是一定失效，而是优化器估算扫描行数太多时会放弃索引。
8. 优化器估算走索引 + 回表的成本高于全表扫描（通常匹配行占比较高时）。

### 2.6 索引设计原则【重点】

- 为 WHERE、JOIN、ORDER BY、GROUP BY 中的高频列建索引。
- 区分度（`COUNT(DISTINCT col) / COUNT(*)`）低的列（如性别、状态）单独建索引意义不大。
- 长字符串用**前缀索引** `INDEX(email(10))`，但前缀索引无法用于覆盖索引和 ORDER BY。
- 优先扩展已有联合索引，避免冗余索引；单表索引一般不超过 5\~6 个，索引会拖慢写入、占用空间。

### 2.7 优化器选错索引【了解】

统计信息是采样估算的，可能不准。处理顺序：`ANALYZE TABLE` 重新统计 → 改写 SQL 引导优化器 → `FORCE INDEX(idx)` 强制指定（应急手段，索引改名后会报错）。

### 2.8 索引合并与 MRR【了解】

- **索引合并（index merge）**：优化器有时会对同一表的多个二级索引分别扫描，再对主键取交集（intersection）或并集（union），EXPLAIN 的 type 显示 `index_merge`，Extra 显示 `Using intersect(...)` / `Using union(...)`。能用上索引合并通常说明索引设计不佳，多数情况下一个覆盖全部条件的联合索引效率更高。
- **MRR（Multi-Range Read）**：针对回表优化的机制。范围查询时先把二级索引查到的主键收集到 `read_rnd_buffer` 中排序，再按主键顺序回表，把随机 I/O 变成相对顺序的 I/O。Extra 显示 `Using MRR`。默认开启，由优化器决定是否使用。

## 三、事务与 MVCC

InnoDB 默认隔离级别是可重复读（RR），它用 MVCC 解决快照读的一致性，用临键锁解决当前读的幻读，因此在绝大多数场景下避免了幻读。

### 3.1 ACID 及其实现【核心】

| 特性 | 含义 | InnoDB 靠什么实现 |
| --- | --- | --- |
| 原子性 A | 要么全部成功，要么全部回滚 | undo log |
| 一致性 C | 事务前后数据满足完整性约束 | 由 A、I、D 共同保证，加上应用层约束；是目的 |
| 隔离性 I | 并发事务互不干扰 | MVCC + 锁 |
| 持久性 D | 提交后永久生效 | redo log（WAL）+ 双写缓冲 |

### 3.2 并发问题与四种隔离级别【核心】

- **脏读**：读到其他事务未提交的数据。
- **不可重复读**：同一事务两次读同一行，结果不同（侧重修改）。
- **幻读**：同一事务两次按条件查询，第二次多出了行（侧重新增）。

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 实现 |
| --- | --- | --- | --- | --- |
| 读未提交 RU | 可能 | 可能 | 可能 | 直接读最新数据 |
| 读已提交 RC | 避免 | 可能 | 可能 | 每条 SELECT 生成 ReadView |
| 可重复读 RR（默认） | 避免 | 避免 | 基本避免 | 事务内第一条 SELECT 生成 ReadView + 临键锁 |
| 串行化 | 避免 | 避免 | 避免 | 读加共享锁，读写互斥 |

**互联网公司为什么常用 RC**：RC 不加间隙锁，并发更高、死锁更少；配合 binlog\_format=ROW 不会有主从不一致问题。MySQL 当年默认 RR，是因为早期 STATEMENT 格式的 binlog 在 RC 下会导致主从不一致。

### 3.3 MVCC 原理【核心】

MVCC 让读不加锁、读写不冲突，由三部分组成：

1. **隐藏字段**：`DB_TRX_ID` 最后修改该行的事务 ID；`DB_ROLL_PTR` 指向该行上一个版本的 undo log。
2. **undo log 版本链**：每次修改把旧版本写入 undo log，通过 roll\_ptr 串成一条从新到旧的链表。
3. **ReadView**：快照读时生成的「可见性规则」，包含 4 个字段：
   - `m_ids`：生成 ReadView 时活跃（未提交）的事务 ID 列表
   - `min_trx_id`：m\_ids 中的最小值
   - `max_trx_id`：下一个将要分配的事务 ID（不是 m\_ids 的最大值）
   - `creator_trx_id`：创建该 ReadView 的事务 ID

**可见性判断**（拿行的 trx\_id 与 ReadView 比较）：

1. trx\_id == creator\_trx\_id：自己改的，可见。
2. trx\_id < min\_trx\_id：生成 ReadView 前已提交，可见。
3. trx\_id >= max\_trx\_id：生成 ReadView 后才开启，不可见。
4. 在两者之间：在 m\_ids 中说明未提交，不可见；不在则已提交，可见。
5. 不可见就顺着版本链往前找，直到找到可见版本或返回空。

### 3.4 RC 与 RR 的关键区别：ReadView 生成时机【核心】

- **RC**：每次 SELECT 都生成新的 ReadView，所以能读到其他事务新提交的数据，出现不可重复读。
- **RR**：只在事务中**第一次 SELECT** 时生成 ReadView，之后一直复用，所以整个事务看到的是同一份快照。注意不是 `BEGIN` 时生成；如需立即创建可用 `START TRANSACTION WITH CONSISTENT SNAPSHOT`。

### 3.5 快照读、当前读与幻读【核心】

- **快照读**：普通 `SELECT`，走 MVCC，不加锁。
- **当前读**：`SELECT ... FOR UPDATE`、`SELECT ... FOR SHARE`、`INSERT`、`UPDATE`、`DELETE`，读最新已提交数据并加锁。

RR 下快照读靠 MVCC 避免幻读，当前读靠 Next-Key Lock 锁住间隙、阻止其他事务插入来避免幻读。

**仍会发生幻读的例子**：事务 A 快照读 `id=5` 不存在 → 事务 B 插入 `id=5` 并提交 → A 执行 `UPDATE ... WHERE id=5`（当前读，能更新到）→ 该行 trx\_id 变成 A 自己 → A 再快照读就能看到它。这是快照读与当前读混用导致的。规避方法是开启事务后尽早用 `FOR UPDATE` 当前读。

### 3.6 长事务的危害【重点】

- 活跃事务的 ReadView 可能需要旧版本，undo log 无法被 purge，占用空间且版本链变长、查询变慢。
- 长时间持有行锁，阻塞其他事务，增加死锁和主从延迟。
- 排查：`SELECT * FROM information_schema.innodb_trx WHERE TIME_TO_SEC(TIMEDIFF(NOW(), trx_started)) > 60;`
- 预防：事务里不做 RPC 和大批量操作；确认 `autocommit=1`；Spring `@Transactional` 范围要小。

### 3.7 乐观锁与悲观锁【重点】

- **悲观锁**：`SELECT ... FOR UPDATE` 先锁后改，适合冲突多、写多的场景。
- **乐观锁**：加版本号字段，更新时校验，影响行数为 0 就重试或失败，适合冲突少的场景。

```sql
-- 乐观锁扣库存
UPDATE product SET stock = stock - 1, version = version + 1
WHERE id = 1001 AND version = 7;
-- 更简洁的防超卖写法
UPDATE product SET stock = stock - 1 WHERE id = 1001 AND stock >= 1;
```

## 四、锁

InnoDB 的行锁是**加在索引上**的，不是加在数据行上；如果更新条件没有走索引，就会锁住扫描到的所有行，效果等同锁表。

### 4.1 锁的分类【重点】

| 粒度 | 锁 | 说明 |
| --- | --- | --- |
| 全局 | `FLUSH TABLES WITH READ LOCK` | 整库只读，用于全库逻辑备份；InnoDB 更推荐 `mysqldump --single-transaction` |
| 表级 | 表锁 `LOCK TABLES` | 一般不用 |
| 表级 | 元数据锁 MDL | 增删改查自动加 MDL 读锁，DDL 加 MDL 写锁；长事务 + DDL 会把后续所有查询都阻塞 |
| 表级 | 意向锁 IS / IX | 加行锁前先在表上加意向锁，让表锁不必逐行检查是否有行锁；意向锁之间不冲突 |
| 表级 | AUTO-INC 锁 | 自增主键分配，8.0 默认 `innodb_autoinc_lock_mode=2`（轻量级） |
| 行级 | 记录锁 Record Lock | 锁住一条索引记录 |
| 行级 | 间隙锁 Gap Lock | 锁住两条记录之间的开区间，只为阻止插入；间隙锁之间不冲突；只在 RR 下存在 |
| 行级 | 临键锁 Next-Key Lock | 记录锁 + 前面的间隙，左开右闭区间 `(a, b]`，RR 下加锁的基本单位 |
| 行级 | 插入意向锁 | 插入前加的特殊间隙锁，与间隙锁冲突 |

按模式又分为共享锁 S（读锁）和排他锁 X（写锁）：S 与 S 兼容，其余组合均冲突。

### 4.2 RR 下的加锁规则【重点】

以下是《极客时间·MySQL 实战 45 讲》总结的规则：两个原则、两个优化、一个 bug（bug 已在 8.0.18 修复）。

1. **原则 1**：加锁的基本单位是 Next-Key Lock。
2. **原则 2**：查找过程中访问到的对象才会加锁。
3. **优化 1**：唯一索引上的等值查询，命中记录时退化为记录锁。
4. **优化 2**：索引上的等值查询，向右遍历到最后一个不满足条件的值时，退化为间隙锁。

**例子**：表 t 的主键 id 有 0, 5, 10, 15。

| 语句 | 锁住的范围 |
| --- | --- |
| `WHERE id = 5 FOR UPDATE` | 只有记录锁 id=5（优化 1） |
| `WHERE id = 7 FOR UPDATE` | 间隙锁 (5, 10)（优化 2），其他事务插入 id=6\~9 都会被阻塞 |
| `WHERE id >= 10 AND id < 11 FOR UPDATE` | 记录锁 10 + 间隙锁 (10, 15)；8.0.18 前因那个 bug 会锁到临键锁 (10, 15\] |
| 非索引列 `WHERE name = 'x' FOR UPDATE` | 全表扫描，所有记录和间隙都被锁 |

实际加锁情况可以通过 `SELECT * FROM performance_schema.data_locks;`（8.0）查看。

### 4.3 死锁【重点】

**典型场景**：

- 两个事务以相反顺序更新两行（A 先改 1 再改 2，B 先改 2 再改 1）。
- 间隙锁导致：两个事务都对不存在的记录 `SELECT ... FOR UPDATE`（间隙锁互不冲突，都能拿到），然后都去插入，各自的插入意向锁被对方的间隙锁阻塞。「先查再插」的幂等逻辑常见。

**InnoDB 处理方式**：主动死锁检测（`innodb_deadlock_detect=ON`），发现后回滚代价小的事务；另有锁等待超时 `innodb_lock_wait_timeout`（默认 50 秒）。

**排查**：`SHOW ENGINE INNODB STATUS` 中的 `LATEST DETECTED DEADLOCK` 段落会列出两个事务各自持有和等待的锁及 SQL；开启 `innodb_print_all_deadlocks` 可将每次死锁写入错误日志。

**预防**：固定加锁顺序（如按主键升序）；事务尽量短小；更新条件必须走索引；允许的话使用 RC 减少间隙锁；用 `INSERT ... ON DUPLICATE KEY UPDATE` 或唯一索引替代「先查再插」。

## 五、日志体系

redo log 保证持久性、undo log 保证原子性并支撑 MVCC、binlog 用于复制和归档恢复；两阶段提交保证 redo log 与 binlog 的一致。

### 5.1 三大日志对比【核心】

| 维度 | redo log | undo log | binlog |
| --- | --- | --- | --- |
| 所属层 | InnoDB | InnoDB | Server 层，所有引擎都有 |
| 作用 | 崩溃恢复，保证持久性 | 事务回滚 + MVCC 版本链 | 主从复制、按时间点恢复 |
| 内容 | 物理日志：某表空间某页某偏移做了什么修改 | 逻辑日志：反向操作，INSERT 记主键、UPDATE 记旧值 | 逻辑日志：SQL 或行变更 |
| 写法 | 固定大小循环写，已刷盘的部分会被覆盖 | 随事务生成，不再被引用后由 purge 清理 | 追加写，写满切换新文件 |
| 能否恢复误删 | 不能（会被覆盖） | 不能 | 能，全量备份 + binlog 回放 |

### 5.2 redo log 与 WAL【核心】

**为什么需要 redo log**：修改只写在 Buffer Pool 中，如果每次提交都把 16 KB 数据页写回磁盘，是大量随机 I/O。WAL（Write-Ahead Logging）的做法是先顺序写很小的 redo log，脏页之后在后台刷盘，崩溃后用 redo log 重放即可恢复（crash-safe）。

**刷盘策略 `innodb_flush_log_at_trx_commit`**：

| 值 | 行为 | 可能丢失 |
| --- | --- | --- |
| 0 | 提交时只留在 log buffer，后台线程每秒写并刷盘 | MySQL 崩溃丢 1 秒 |
| **1（默认）** | 每次提交都 write + fsync | 不丢 |
| 2 | 每次提交写到 OS page cache，每秒 fsync | 操作系统崩溃或断电丢 1 秒 |

redo log 由多个文件循环使用，`write pos` 是当前写位置，`checkpoint` 是已刷盘可覆盖的位置；写满时必须停下来推进 checkpoint，表现为数据库抖动。MySQL 8.0.30 起用 `innodb_redo_log_capacity` 一个参数管理大小。

### 5.3 binlog【重点】

**三种格式**：

| 格式 | 记录内容 | 优缺点 |
| --- | --- | --- |
| STATEMENT | 原始 SQL | 日志小；`NOW()`、`UUID()`、`LIMIT` 不带 ORDER BY 等会导致主从不一致 |
| **ROW（默认）** | 每行数据改前改后的值 | 精确可靠，可用于闪回和 Canal 同步；批量更新时日志大 |
| MIXED | 一般用 STATEMENT，可能不一致时自动切 ROW | 折中 |

**刷盘策略 `sync_binlog`**：0 由操作系统决定；1（默认）每次提交都 fsync；N 表示累积 N 个事务后 fsync。**「双 1」配置**（两个参数都设为 1）是核心业务的数据安全基线。

### 5.4 两阶段提交与崩溃恢复【核心】

以 `UPDATE t SET c = c + 1 WHERE id = 2` 为例，完整流程见下图：

1. 执行器通过引擎取到 id=2 这行（不在内存就从磁盘读入）。
2. 引擎写 undo log，再更新 Buffer Pool 中的数据页（变为脏页）。
3. 写 redo log，状态为 **prepare**。
4. 写 binlog。
5. 提交事务，redo log 状态改为 **commit**。

蓝色的两步是 redo log 的两个阶段；红色虚线是面试最常追问的两个崩溃时刻。

**为什么要两阶段**：若先写 redo 再写 binlog，中间崩溃会导致主库有数据、从库没有；反过来则从库有、主库没有。两阶段提交让二者要么都生效、要么都不生效。

**崩溃恢复规则**：

- redo log 已 commit → 直接提交。
- redo log 只有 prepare → 用 XID 去 binlog 中查：binlog 完整则提交，不完整则回滚。

**组提交【了解】**：双 1 配置下每次提交要 2 次 fsync，MySQL 用组提交（Group Commit）把多个事务的 redo log 和 binlog 合并成一次 fsync，大幅提升 TPS。

### 5.5 undo log 与 purge【重点】

undo log 分为 insert undo（事务提交后即可删除）和 update undo（要等没有 ReadView 引用后由 purge 线程清理）。DELETE 并不立即物理删除，而是打上删除标记，等 purge 时才真正删除。长事务会阻塞 purge，导致 undo 膨胀。

### 5.6 备份与恢复【了解】

- **逻辑备份 mysqldump**：导出 SQL 文本，恢复慢，适合中小库。InnoDB 用 `--single-transaction` 开 RR 事务拿一致性快照，备份期间不锁表；MyISAM 没有事务，只能 `FLUSH TABLES WITH READ LOCK` 全局只读来备。
- **物理备份 XtraBackup（Percona 开源）**：直接拷贝数据文件，备份期间持续拷贝 redo log 来追平并发修改，恢复时先做类似崩溃恢复的 redo 应用。支持热备、增量备份，大库首选。
- **按时间点恢复（PITR）**：最近一次全量备份 + 从备份位点开始回放 binlog（`mysqlbinlog`）。误删表时的做法：恢复到删表前的位点即截断回放，跳过事故 SQL 后再继续。

## 六、SQL 基础与优化

慢 SQL 优化的主线是：用慢查询日志找到 SQL → 用 EXPLAIN 看执行计划 → 针对 type、rows、Extra 中的问题加索引或改写 SQL → 验证。

### 6.1 SQL 基础要点【重点】

对齐《Java开发工程师核心知识点.md》第六章的 SQL 基础，面试多为手写 SQL，记住以下要点。

**一条 SELECT 的逻辑执行顺序**：`FROM`（含 JOIN、ON）→ `WHERE` → `GROUP BY` → `HAVING` → `SELECT`（含 DISTINCT）→ `ORDER BY` → `LIMIT`。因此 WHERE 中不能使用 SELECT 里定义的别名，HAVING 中可以。

**JOIN 类型**：

| 类型 | 结果 |
| --- | --- |
| `INNER JOIN` | 两边都匹配的行 |
| `LEFT JOIN` | 左表全部 + 右表匹配的行，不匹配处补 NULL |
| `RIGHT JOIN` | 右表全部 + 左表匹配的行 |
| 全连接 | MySQL 不支持 `FULL JOIN`，用 `LEFT JOIN ... UNION ... RIGHT JOIN` 模拟 |

常见坑：`LEFT JOIN` 时右表的过滤条件写在 `ON` 里不影响左表行数；写在 `WHERE` 里会把补 NULL 的行过滤掉，效果退化成 `INNER JOIN`。

**子查询与聚合**：相关子查询对驱动表逐行执行，数据量大时优先改写为 JOIN 或派生表；默认 `ONLY_FULL_GROUP_BY` 模式下，SELECT 中的列必须出现在 GROUP BY 中或被聚合函数包裹（否则用 `ANY_VALUE()`）。

**窗口函数（8.0）**：`ROW_NUMBER() / RANK() / DENSE_RANK() / LAG() / LEAD() / SUM() OVER (...)`，在不折叠行的前提下实现组内排名、求累计值、取相邻行。典型面试题是「每组取 Top N」：

```sql
-- 每个部门工资最高的 3 人
SELECT * FROM (
  SELECT *, DENSE_RANK() OVER (PARTITION BY dept ORDER BY salary DESC) AS rk
  FROM emp
) t WHERE rk <= 3;
```

### 6.2 EXPLAIN 关键字段【核心】

| 字段 | 含义 | 关注点 |
| --- | --- | --- |
| type | 访问类型 | 最重要，至少要达到 range，最好 ref |
| possible\_keys / key | 可能用的索引 / 实际用的索引 | key 为 NULL 说明没走索引 |
| key\_len | 用到的索引长度 | 判断联合索引用了几列 |
| rows | 预估扫描行数 | 越小越好 |
| filtered | 经条件过滤后剩余行的百分比 | 低说明扫了很多无用的行 |
| Extra | 额外信息 | 见下表 |

**type 从好到差**：`system` > `const`（主键或唯一索引等值）> `eq_ref`（Join 时被驱动表按主键/唯一索引匹配）> `ref`（非唯一索引等值）> `range`（索引范围扫描）> `index`（全索引扫描）> `ALL`（全表扫描）。

| Extra | 含义 | 好坏 |
| --- | --- | --- |
| Using index | 覆盖索引，无需回表 | 好 |
| Using index condition | 索引下推 | 好 |
| Using where | Server 层过滤 | 中性 |
| Using filesort | 无法利用索引排序，需要额外排序 | 差，考虑让索引覆盖 ORDER BY |
| Using temporary | 使用临时表，常见于 GROUP BY、DISTINCT | 差 |
| Using join buffer | Join 的被驱动表没有索引 | 差，给 Join 字段加索引 |

8.0.18 起可用 `EXPLAIN ANALYZE` 实际执行并输出每步真实耗时和行数。

### 6.3 慢 SQL 定位与优化思路【核心】

1. **开启慢查询日志**：`slow_query_log=ON`、`long_query_time=1`（秒），可加 `log_queries_not_using_indexes`。
2. **分析日志**：用 `mysqldumpslow` 或 `pt-query-digest` 按总耗时、执行次数排序。
3. **EXPLAIN 分析**：是否全表扫描、是否走错索引、是否 filesort / temporary。
4. **优化手段**：加合适的索引 / 联合索引；做成覆盖索引；改写 SQL 避免索引失效；拆分复杂 SQL；减少返回列和行数。
5. **架构层面**：以上不够时考虑缓存、读写分离、分库分表、把复杂查询交给 ES。

除了索引问题，慢 SQL 还可能来自：锁等待（查 `innodb_trx`、`data_lock_waits`）、刷脏页导致的抖动、Buffer Pool 太小、磁盘 I/O 打满。

### 6.4 ORDER BY 与 filesort【了解】

ORDER BY 用不上索引顺序时走 filesort（不一定写磁盘，结果集能放进 `sort_buffer_size` 时在内存中排）：

- **双路排序（回表排序）**：先按条件读出排序字段和主键，排序后再按主键回表取整行。排序缓冲区占用小，但回表是随机 I/O。
- **单路排序**：一次读出查询所需的全部列，在 sort buffer 中排序后直接返回。MySQL 优先用单路，单行长度超过 `max_length_for_sort_data`（默认 4 KB，典型的是含大 TEXT 列）时退回双路。

优化方向：让联合索引的列顺序同时满足 WHERE 等值条件和 ORDER BY（等值列在前、排序列在后）；`ORDER BY a ASC, b DESC` 这种混合升降序在 8.0 前无法走索引，8.0 可以建降序索引解决；避免 `SELECT *`，防止单行过大退回双路；必要时调大 `sort_buffer_size` 避免磁盘临时文件。

### 6.5 深分页优化【重点】

`SELECT * FROM orders ORDER BY id LIMIT 1000000, 10` 会读取并丢弃前 100 万行，而且每行都要回表。

```sql
-- 方案 1：子查询 / 延迟关联，先在索引上定位主键，只对 10 行回表
SELECT o.* FROM orders o
JOIN (SELECT id FROM orders ORDER BY id LIMIT 1000000, 10) t ON o.id = t.id;

-- 方案 2：游标分页（最优），记住上一页最后一个 id，不支持跳页
SELECT * FROM orders WHERE id > #{lastId} ORDER BY id LIMIT 10;
```

产品层面也可以限制最大页数，或把深度检索交给 ES（用 search\_after）。

### 6.6 count 的性能【重点】

性能大致为 `count(*)` ≈ `count(1)` > `count(主键)` > `count(字段)`。`count(*)` 是 SQL 标准写法，InnoDB 做了专门优化，会选择最小的二级索引来遍历；`count(字段)` 还要判断是否为 NULL。大表精确计数很慢，可用 Redis 计数、单独的计数表，或在允许近似时用 `EXPLAIN` 的 rows 或 `information_schema.tables` 估算值。

### 6.7 Join 优化【重点】

- **小表驱动大表**：这里的「小」是指按条件过滤后参与 Join 的数据量小。
- **被驱动表的 Join 字段必须有索引**：有索引时是 Index Nested-Loop Join；没有时 8.0.18 之前用 Block Nested-Loop，8.0.18 起改为 Hash Join。
- 不要 Join 太多表（《阿里巴巴 Java 开发手册》建议不超过 3 个），可以拆成多次单表查询在应用层组装。

### 6.8 其他常见优化【重点】

- 避免 `SELECT *`，只取需要的列，便于覆盖索引。
- 大批量 INSERT 用多值插入，每批 500\~1000 行；大批量 DELETE / UPDATE 分批执行，避免长事务和主从延迟。
- `IN` 列表不宜过长；`UNION ALL` 优于 `UNION`（无需去重）。
- 大表 DDL：8.0 大部分 DDL 支持 Online DDL（`ALGORITHM=INPLACE / INSTANT`，8.0.12 起加列可 INSTANT）；不支持的用 gh-ost 或 pt-online-schema-change。执行前先确认没有长事务，否则 MDL 写锁会阻塞整张表。

## 七、Buffer Pool 与内存

Buffer Pool 是 InnoDB 在内存中缓存数据页和索引页的区域，读写都先经过它。专用数据库服务器上一般把 `innodb_buffer_pool_size` 设为物理内存的 50%\~75%。

### 7.1 结构【重点】

以 16 KB 页为单位管理，由三个链表组织：

- **Free 链表**：空闲页。
- **LRU 链表**：已使用的页，用于淘汰。
- **Flush 链表**：脏页（内存与磁盘不一致的页），等待刷盘。

### 7.2 改进的 LRU【重点】

普通 LRU 有两个问题：**预读失效**（预读进来的页可能根本用不到，却把热数据挤出去）和 **Buffer Pool 污染**（一次全表扫描把大量冷数据换进来）。

InnoDB 的做法：把 LRU 分为 **young 区（热数据，约 5/8）** 和 **old 区（冷数据，约 3/8，`innodb_old_blocks_pct=37`）**。新页先插入 old 区头部；只有在 old 区停留超过 `innodb_old_blocks_time`（默认 1000 ms）后再次被访问，才移到 young 区。全表扫描的页很快被连续访问完就不再用，不会进入 young 区。此外 young 区前 1/4 的页被访问时不移动，减少链表操作。

### 7.3 Change Buffer【重点】

更新**非唯一二级索引**时，如果目标页不在内存，先把修改记在 Change Buffer 中，等下次读取该页时再 merge，省掉一次随机读。唯一索引不能用，因为必须读出页来校验唯一性。适合写多读少的场景（如日志表）；写入后马上读的场景反而增加开销。这也是「业务能保证唯一时，普通索引写入性能优于唯一索引」的原因。

### 7.4 刷脏页的时机【重点】

1. redo log 写满，需要推进 checkpoint（此时写入会停顿，应尽量避免）。
2. Buffer Pool 空间不足，淘汰的是脏页。
3. 后台线程定期刷盘（由 `innodb_io_capacity` 控制速度，SSD 可调高）。
4. MySQL 正常关闭。

SQL 偶发变慢、抖动，常见原因就是前两种情况触发了集中刷脏。

### 7.5 双写缓冲与自适应哈希【了解】

- **双写缓冲（Doublewrite Buffer）**：16 KB 的页写到磁盘可能只写了一半（部分写失效），redo log 无法修复损坏的页。所以刷脏页前先写一份到双写区，损坏时从副本恢复。
- **自适应哈希索引（AHI）**：InnoDB 发现某些索引值被频繁等值访问时，自动在内存中建立哈希索引，跳过 B+ 树的逐层查找。

## 八、高可用与扩展

单机 MySQL 的瓶颈依次是读压力、写压力和单表数据量：读压力用主从 + 读写分离解决，写压力和数据量用分库分表解决。

### 8.1 主从复制原理【核心】

1. 主库提交事务时写 binlog。
2. 从库的 **I/O 线程**连接主库，主库的 **binlog dump 线程**把 binlog 发给它，I/O 线程写入本地的 **relay log**（中继日志）。
3. 从库的 **SQL 线程**（5.7 起为多个 worker 并行回放）读取 relay log 并重放。

**三种复制模式**：

| 模式 | 主库何时返回客户端 | 特点 |
| --- | --- | --- |
| 异步复制（默认） | 写完 binlog 即返回 | 性能最好，主库宕机可能丢数据 |
| 半同步复制 | 至少一个从库收到 binlog 并写入 relay log 后 | 折中；超时会退化为异步 |
| 组复制 MGR | 多数节点通过 Paxos 达成一致 | 强一致，自动选主，写性能有损耗 |

**GTID【了解】**：全局事务 ID（`server_uuid:事务序号`），从库不再需要记录 binlog 文件名和位置，主备切换时自动定位同步点。

### 8.2 主从延迟【核心】

**查看**：`SHOW REPLICA STATUS` 中的 `Seconds_Behind_Source`（8.0.22 前为 `SHOW SLAVE STATUS` / `Seconds_Behind_Master`）。

**常见原因**：从库机器配置差；从库上跑大量分析查询；大事务（一次删百万行，从库也要执行同样时间）；大表 DDL；从库回放并行度不足。

**解决**：拆分大事务；开启并行复制（`replica_parallel_workers`，8.0 用 WRITESET 依赖追踪）；从库配置不低于主库；分析类查询走专门的从库。

**业务上的「写后读」问题**：刚写入就去从库读可能读不到。常见方案：关键读请求强制走主库；写入后一小段时间内该用户的读走主库；从库等待 GTID 同步后再读；前端做乐观展示。

### 8.3 读写分离与高可用【了解】

读写分离可在应用层实现（ShardingSphere-JDBC、动态数据源），也可通过代理层实现（ProxySQL、MySQL Router、ShardingSphere-Proxy）。高可用方案从 MHA（外部管理节点做故障切换）演进到 MGR + MySQL Router（InnoDB Cluster）；云上直接用 RDS 的主备切换。

### 8.4 分库分表【重点】

**何时拆**：《阿里巴巴 Java 开发手册》建议单表超过 500 万行或 2 GB 时考虑分表。这是经验值，真正的判断依据是索引是否还能放进 Buffer Pool、写入 TPS 是否到单机上限。优先顺序：SQL 与索引优化 → 缓存 → 读写分离 → 分库分表。

**分库分表前可考虑分区表【了解】**：`PARTITION BY RANGE / HASH / LIST (...)` 把一张表在存储层切成多个分区，对应用完全透明；查询命中分区裁剪（pruning）时只扫描相关分区，删除历史数据可以直接 `DROP PARTITION` 而不是 DELETE。局限：所有分区仍在同一实例，写入瓶颈、DDL 阻塞、单点问题依旧；主键和唯一键必须包含分区键。它解决的是「单表数据量」，不解决「并发写入」，到达单机写上限后仍要水平分库。

| 拆分方式 | 做法 | 解决的问题 |
| --- | --- | --- |
| 垂直分库 | 按业务拆：用户库、订单库、商品库 | 业务解耦，分散压力；配合微服务 |
| 垂直分表 | 把大字段、低频字段拆到扩展表 | 减少单行大小，一页放更多行 |
| 水平分表 / 分库 | 同构的数据按分片键分到多张表 / 多个库 | 单表数据量、单库写入上限 |

**分片键与路由**：选择最高频的查询条件（如 user\_id）做分片键，尽量让一次查询只落到一个分片。路由算法有：取模（分布均匀，扩容要迁移数据）、范围（扩容简单，易产生热点）、一致性哈希。订单表常用「基因法」：把 user\_id 的后几位嵌入订单号，让按订单号和按用户都能路由到同一分片。

**带来的问题与方案**：

| 问题 | 方案 |
| --- | --- |
| 全局唯一 ID | 雪花算法（注意时钟回拨）、号段模式（美团 Leaf）、Redis INCR |
| 跨库分页 / 排序 | 各分片取 offset+limit 后归并（深页很慢）；禁止跳页用游标；复杂查询同步到 ES |
| 跨库 Join | 应用层分次查询组装、字段冗余、广播表（字典表每个库存一份） |
| 分布式事务 | 尽量避免；必须时用 Seata、本地消息表 / 事务消息实现最终一致 |
| 扩容迁移 | 双写 → 全量迁移历史数据 → 校验 → 切读 → 停旧写；或用 Canal 订阅 binlog 增量同步 |

中间件常用 ShardingSphere（JDBC 模式无额外部署、Proxy 模式对应用透明）。数据量快速增长且不想自己做分片的，可以考虑 TiDB 等分布式数据库。

## 九、表设计、规范与连接池

好的表设计能从源头上减少后面的索引和性能问题，面试常结合「你们表是怎么设计的」来考。

### 9.1 主键选择【核心】

**为什么推荐自增主键**：聚簇索引按主键有序存放，自增主键每次追加到最后一页，不会触发页分裂；主键短，而每个二级索引都要存一份主键，索引更小。

**为什么不用 UUID**：无序插入导致频繁页分裂和碎片；36 字符的字符串占空间大，比较慢。分布式场景用趋势递增的雪花 ID（BIGINT）。

**自增主键的不足**：暴露业务量、易被遍历；分库后无法保证全局唯一；自增值不保证连续（事务回滚、唯一键冲突都会产生空洞）。8.0 起自增值已持久化，重启不会回退。

### 9.2 数据类型选择【重点】

| 场景 | 推荐 | 说明 |
| --- | --- | --- |
| 金额 | `DECIMAL(M,D)` 或以分为单位存 `BIGINT` | FLOAT / DOUBLE 有精度丢失 |
| 定长字符串 | `CHAR`，如手机号、MD5 | 固定长度，不用记长度前缀 |
| 变长字符串 | `VARCHAR(n)`，n 按需设置 | n 是字符数，过大会增加排序和内存临时表的开销 |
| 时间 | `DATETIME` | 8 字节，范围到 9999 年，与时区无关 |
| 时间（需要按时区转换） | `TIMESTAMP` | 4 字节，只到 2038 年，会按会话时区转换 |
| 状态 / 布尔 | `TINYINT` | 不推荐 ENUM，增加枚举值要改表 |
| 字符集 | `utf8mb4` | MySQL 的 utf8 只支持 3 字节，存不了 emoji |

字段尽量 `NOT NULL` 并设默认值：NULL 让索引和比较更复杂，`count(col)` 会忽略 NULL，`NOT IN` 遇到 NULL 结果为空。

### 9.3 范式与反范式【重点】

- **第一范式**：字段不可再分（原子性）。
- **第二范式**：非主键字段完全依赖于整个主键，不能只依赖联合主键的一部分。
- **第三范式**：非主键字段之间不存在传递依赖。

范式减少冗余、避免更新异常，但查询需要更多 Join。实际工程中常做**适度反范式**：在订单表冗余商品名称、价格快照，用空间换 Join，同时保留下单时的历史值。代价是要维护冗余数据的一致性。

### 9.4 常见开发规范【重点】

- 每张表必须有主键，并包含 `create_time`、`update_time`。
- 不使用外键和级联，关联关系在应用层保证（外键影响写入性能和分库分表）。
- 不使用存储过程和触发器，难以调试和扩展。
- 逻辑删除（`is_deleted`）时，唯一索引要把该字段或删除时间一并包含，否则无法重新创建同名记录。
- 大字段（TEXT / BLOB）拆到独立的扩展表，或放对象存储只存 URL。

### 9.5 连接池【重点】

- **作用**：复用 TCP 连接，省掉握手和认证开销，并限制对数据库的最大连接数。Spring Boot 2.0 起默认 HikariCP。
- **核心参数（HikariCP）**：`maximumPoolSize`、`minimumIdle`、`connectionTimeout`（取连接超时，默认 30 秒）、`maxLifetime`（应小于 MySQL 的 `wait_timeout`）、`leakDetectionThreshold`（连接泄漏检测）。
- **池大小**：不是越大越好。HikariCP 官方建议的起点公式是 `连接数 = CPU 核数 × 2 + 有效磁盘数`。还要保证「应用实例数 × 每实例池大小 < MySQL `max_connections`」。
- **Druid**：特点是自带监控页面、SQL 统计和 SQL 防火墙，在国内项目中常见。
- **HikariCP 为什么快【了解】**：① 自研 `ConcurrentBag` 管理连接，ThreadLocal 缓存 + CAS 借还，避开了 C3P0、Druid 基于锁的连接管理；② 自研 `FastList` 替代 ArrayList，去掉下标范围检查；③ 用 Javassist 生成精简字节码做代理，方法调用层级少、体积小。差距在高并发短操作时最明显，普通场景几个主流连接池差异不大。
- **连接泄漏定位【重点】**：连接被借出后未归还（手动 `getConnection` 后漏了 close、异常路径绕过关闭逻辑），池耗尽后所有请求卡在取连接上。排查手段：HikariCP 设置 `leakDetectionThreshold`（如 30000 ms），连接借出超过该时间未归还就打印借出点的堆栈，按堆栈即可定位到未关闭的代码。注意该检测有开销，建议测试环境常开、生产环境排查时临时开启；同时可配合 `SHOW PROCESSLIST` 看大量 Sleep 连接佐证。
