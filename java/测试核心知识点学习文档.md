## 一、单元测试与 JUnit5

### 1.1 测试金字塔【重点】

| 层次 | 占比 | 单次耗时 | 依赖 | 典型工具 | 失败定位 |
| --- | --- | --- | --- | --- | --- |
| 单元测试 | 约 70% | 毫秒级 | 无 Spring、无网络、无数据库 | JUnit + Mockito | 精确到方法 |
| 集成测试 | 约 20% | 秒到十几秒 | 真实中间件或容器 | 切片测试、Testcontainers | 定位到模块 |
| 端到端测试 | 约 10% | 分钟级 | 完整环境与真实链路 | 接口脚本、UI 自动化 | 只能定位到流程 |

越往上越真实，也越慢、越脆、维护成本越高。倒金字塔（大量端到端、很少单测）是反模式：反馈慢、失败难定位、重构没人敢动。比例不是教条，纯 CRUD 可用集成测试兜底，算法与状态机则应有大量单测。

### 1.2 FIRST 原则【重点】

| 原则 | 含义 | 反例 |
| --- | --- | --- |
| Fast 快速 | 单测毫秒级、整套秒级，才能每次提交都跑 | 单测连真实数据库 |
| Isolated 独立 | 用例之间不共享状态、不依赖执行顺序 | 依赖上一个用例插入的数据 |
| Repeatable 可重复 | 任何机器、任何时间结果一致 | 依赖当前时间、时区、外网 |
| Self-validating 自验证 | 结果由断言自动判定，不靠人看日志 | 只打印结果不写断言 |
| Timely 及时 | 与生产代码同步编写 | 上线前突击补测试 |

### 1.3 JUnit5 三大模块【重点】

| 模块 | 作用 | 关键内容 |
| --- | --- | --- |
| JUnit Platform | 测试运行的基础设施 | TestEngine SPI、Launcher 发现与执行、IDE 与构建工具接入 |
| JUnit Jupiter | JUnit5 编程模型 | 注解、断言、扩展模型、参数化与嵌套测试 |
| JUnit Vintage | 兼容旧版本 | 在 Platform 上运行 JUnit 3/4 用例 |

Platform 可同时挂载 Jupiter 与 Vintage，迁移期新旧用例一起跑。与 JUnit4 的差异：模块化拆分；`@Test` 不再有 `expected` 与 `timeout` 属性；断言迁到 `Assertions`；扩展用 `Extension` 取代 `Runner` 与 `@Rule`；`@Before` 改为 `@BeforeEach`。

### 1.4 常用注解与生命周期【重点】

| 注解 | 作用 |
| --- | --- |
| `@Test` | 标记测试方法，包级可见即可 |
| `@BeforeEach` / `@AfterEach` | 每个测试方法前后各执行一次 |
| `@BeforeAll` / `@AfterAll` | 整个类前后各一次，默认必须 static |
| `@Disabled("原因")` / `@DisplayName` | 跳过用例 / 可读名称，支持中文 |
| `@Tag` / `@Nested` | 分组过滤 / 内部类组织场景 |
| `@ParameterizedTest` / `@RepeatedTest` | 参数化 / 重复执行 |
| `@TestInstance(PER_CLASS)` / `@Timeout` | 类共用一个实例 → BeforeAll 可非 static / 超时失败 |

默认生命周期是 `PER_METHOD`：每个测试方法都新建一次测试类实例，顺序为构造实例 → `@BeforeAll` → 每个方法（`@BeforeEach` → 测试体 → `@AfterEach`）→ `@AfterAll`。这解释了三件事：实例字段无法跨方法共享、`@BeforeAll` 默认必须 static、父类 `@BeforeEach` 先于子类而 `@AfterEach` 相反。

### 1.5 断言【重点】

| 断言 | 用途 |
| --- | --- |
| `assertEquals(expected, actual)` | 值相等，浮点要带 delta |
| `assertTrue` / `assertFalse` / `assertNull` | 布尔与空值 |
| `assertThrows` | 断言指定异常，返回异常对象可继续断言消息与 cause |
| `assertAll` | 执行全部断言后统一汇报，避免首个失败掩盖其余问题 |
| `assertTimeout` / `assertTimeoutPreemptively` | 超时断言，后者另起线程强制中断 |

要点：期望值在前、实际值在后；失败消息用 `Supplier` 延迟拼接；`assertTimeoutPreemptively` 可能破坏线程上下文，慎用；集合需要无序比较时用 AssertJ 的 `containsExactlyInAnyOrder`。团队统一一套断言风格，不要混用。

### 1.6 参数化测试【重点】

```java
@ParameterizedTest(name = "[{index}] amount={0}, expected={1}")
@CsvSource({"0, false", "1, true", "99999, true", "-1, false"})
void isValidAmount(long amount, boolean expected) {
    assertEquals(expected, service.isValidAmount(amount));
}
```

| 数据源 | 适用 |
| --- | --- |
| `@ValueSource` | 单个参数的基础类型或字符串 |
| `@CsvSource` / `@CsvFileSource` | 一行多参数 / 外部 CSV |
| `@MethodSource` | 静态方法返回 `Stream<Arguments>`，适合复杂对象 |
| `@EnumSource` / `@NullAndEmptySource` | 枚举组合 / 空值与空串边界 |

每条数据单独记为用例，失败能定位到参数；参数类型必须匹配，否则报转换错误。参数化适合边界值、等价类与状态组合，不适合堆砌无意义数据。

### 1.7 嵌套测试与动态测试【了解】

`@Nested` 内部类按场景分组（如「库存充足」「库存不足」），可复用外部 `@BeforeEach`，但内部类不能是 static，也不能声明 static 成员。`@TestFactory` 返回 `Stream<DynamicTest>`，运行期按数据生成用例，适合用例数量不确定的场景；普通 `@Test` 能表达清楚时不要引入。

### 1.8 测试命名与可读性【重点】

命名用三段式 `方法名_场景_期望结果`，如 `create_shouldThrow_whenAmountIsZero`；用 `@DisplayName` 写业务语义；一个测试一个行为，出现多个 when 通常应拆分。结构上用 Given-When-Then 或 Arrange-Act-Assert 分段，构造、执行、断言不穿插。复杂数据用 ObjectMother 或 Builder 集中构造，但不要为测试再造框架。

### 1.9 如何隔离外部依赖【重点】

| 依赖 | 隔离手段 |
| --- | --- |
| 数据库 | 仓储接口 + 内存实现或 mock；集成测试才用真实库 |
| HTTP / RPC | 客户端接口 + mock，或 MockWebServer、WireMock |
| 时间 / 文件 / 随机 ID | 注入 `Clock` / `@TempDir` / 注入 `Supplier` 或 `IdGenerator` |
| 消息队列 / Spring 容器 | 端口接口 + 内存事件总线，或嵌入式 broker / 纯逻辑直接 new 被测类，构造器传入 mock |

前提是代码本身可测：构造器注入而非字段注入，依赖面向接口，业务逻辑不藏在静态方法里。需要启动 Spring 才能测的逻辑说明耦合过重，优先重构而不是加注解；测试也禁止访问真实外网，否则 CI 会随网络随机变红。

## 二、Mockito

### 2.1 mock 与 spy 的区别【核心】

| 维度 | mock | spy |
| --- | --- | --- |
| 创建方式 | `Mockito.mock(X.class)`、`@Mock` | `Mockito.spy(real)`、`@Spy` |
| 本质 | 完全生成的假对象 | 包装真实对象的代理，复制字段状态 |
| 未打桩方法 | 返回默认值：null、0、false、空集合、`Optional.empty` | 调用真实实现 |
| 典型场景 | 外部依赖、接口、协作方 | 遗留代码，只替换少数方法 |
| 打桩语法 | `when(mock.m()).thenReturn(v)` | 必须用 `doReturn(v).when(spy).m()` |

spy 最大的陷阱：`when(spy.m())` 会先真实调用一次 `m()`，真实方法有副作用、写库、耗时或抛异常时，打桩过程本身就失败，所以 spy 一律用 do 系列语法。spy 是浅拷贝，内部集合与协作者仍与原对象共享，测试里应构造干净对象。

### 2.2 打桩【核心】

| 写法 | 说明 |
| --- | --- |
| `when(...).thenReturn(...)` / `thenThrow(...)` | 正常返回 / 模拟异常分支 |
| `thenReturn(a, b)` | 连续打桩，第 N 次返回第 N 个，用尽后一直返回最后一个 |
| `doReturn` / `doThrow` / `doNothing` / `doAnswer` | 用于 void 方法、spy 与无法用 when 的场景；`thenAnswer` 可按入参动态计算 |

打桩参数按 `equals` 匹配，传对象时要构造相同值或用 `eq()`；同一方法多次 `when` 以最后一次为准。Mockito 5 默认严格桩，打了桩却未被调用会抛 `UnnecessaryStubbingException`，共享 setup 确有需要时用 `lenient()` 局部放宽，不要全局关闭。

### 2.3 参数匹配器与 ArgumentCaptor【重点】

`any()` 匹配任意值（含 null），`anyString()`、`anyLong()` 按类型匹配，`eq(v)` 精确匹配，`isNull()`、`notNull()` 判断空值，`argThat(lambda)` 自定义条件，`contains`、`startsWith` 匹配字符串。规则：一个方法参数里只要用了匹配器，其余参数也必须用匹配器，否则抛 `InvalidUseOfMatchersException`。

`ArgumentCaptor` 用于无法靠返回值验证的入参，典型是 void 方法与需要检查多个字段的对象：`verify(repo).save(captor.capture())` 之后用 `getValue()` 断言字段，`getAllValues()` 取多次调用的参数。取值必须在 verify 之后，且不能当作打桩返回值使用。

### 2.4 verify 与调用次数【核心】

| 写法 | 含义 |
| --- | --- |
| `verify(mock).m()` / `times(n)` | 恰好一次 / 精确次数 |
| `never()` / `atLeast(n)` / `atLeastOnce()` | 从未调用 / 至少 / 至少一次 |
| `timeout(ms).times(n)` | 异步等待直到满足次数 |
| `verifyNoInteractions(mock)` / `verifyNoMoreInteractions(mock)` | 完全没有交互 / 除已验证调用外不允许再有其他调用 |

`verifyNoMoreInteractions` 很脆：被测类多调一个无关方法就失败，把测试绑死在实现细节上，只在验证严格协议（如「同一订单只发一次消息」）时使用。异步场景用 Awaitility 或 `verify(timeout)` 等待，不要 `Thread.sleep`；验证应优先断言结果与副作用，verify 只留给必须发生的协作。

### 2.5 注解与 Spring Boot 的 Mock 注解【重点】

`@ExtendWith(MockitoExtension.class)` 启用扩展并初始化注解；`@Mock`、`@Spy` 创建对象；`@InjectMocks` 按构造器 → setter → 字段注入 mock；`@Captor` 声明参数捕获器。Spring 中 `@MockBean` 替换容器 bean（Spring Boot 3.4 起推荐 `@MockitoBean`），`@SpyBean` 包装真实 bean（对应 `@MockitoSpyBean`）。

`@InjectMocks` 只注入 mock 与 spy，注入失败时字段为 null，会以 NPE 暴露。`@MockBean` 会改变上下文缓存 key，每种 mock 组合都要重建上下文，用得越多启动越慢；纯逻辑测试用 Mockito 直接做，不要为一个 mock 拉起 Spring。

### 2.6 静态方法、构造器与私有方法 Mock【了解】

Mockito 5 默认 inline mock maker（早期需额外引入 `mockito-inline`），可用 `mockStatic`、`mockConstruction` 直接 mock 静态方法与构造器，必须放在 try-with-resources 中，作用域结束自动关闭。静态 mock 全局生效，并行测试会互相干扰，能改成实例依赖就不要用。私有方法不直接 mock，也不应 mock：它属于内部实现，正确做法是把可变逻辑抽成包级可见的协作者或独立类，通过公共行为验证。PowerMock 依赖反射与字节码改写，与新版 JDK、框架冲突多，已不推荐。

### 2.7 Mock 过度的反模式【重点】

| 反模式 | 后果 | 改法 |
| --- | --- | --- |
| mock 值对象 / 被测类自身 | 断言变成校验 mock，或测的是 mock | 用真实对象，只 mock 协作者 |
| 每个方法都 verify | 重命名或拆分方法就失败 | 断言业务结果与关键副作用 |
| mock 第三方 SDK 深层调用链 | 与版本强耦合、脆弱 | 包一层自己的接口再 mock |
| 全部用 mock 做集成测试 | SQL、序列化、事务问题测不出 | 集成层用 Testcontainers |

判断标准：重构内部实现但不改行为时，如果测试必须改，说明它验证的是实现而不是行为。Fake（内存仓储、内存事件总线）通常比 Mock 更稳，既能验证状态也能验证交互，只在需要模拟异常与边界时才用 Mock。

## 三、Spring Boot 测试与 Testcontainers

### 3.1 @SpringBootTest 与 webEnvironment【重点】

| 取值 | 行为 | 适用 |
| --- | --- | --- |
| `MOCK`（默认） | 不启动真实服务器，配合 MockMvc | 大多数接口测试 |
| `RANDOM_PORT` | 启动内嵌容器并随机端口 | 需要真实 HTTP、过滤器链与序列化 |
| `DEFINED_PORT` / `NONE` | 固定端口易冲突 / 只加载上下文 | 少用 / 非 Web 集成测试 |

`@SpringBootTest` 加载完整上下文（含数据源、缓存、MQ），启动从数秒到数十秒。上下文按配置缓存，`@MockBean`、`@TestPropertySource`、`@ActiveProfiles`、`@Import` 任何变化都会使缓存失效，这是测试套件越写越慢的常见原因。能用切片就不上完整上下文。

### 3.2 切片测试【重点】

| 注解 | 加载范围 | 常用搭配 | 适用 |
| --- | --- | --- | --- |
| `@WebMvcTest` | Controller、`@ControllerAdvice`、Filter、Jackson | MockMvc + `@MockBean` 下层 | 接口契约、参数校验、异常映射 |
| `@DataJpaTest` | JPA 与数据源 | TestEntityManager、`@AutoConfigureTestDatabase(replace = NONE)` | 实体映射、派生查询、自定义 SQL |
| `@JsonTest` / `@RestClientTest` | Jackson / RestTemplate | JacksonTester / MockRestServiceServer | 序列化 / 外部接口客户端 |

切片启动快、依赖少、失败定位准；代价是只覆盖一层，跨层的事务边界、序列化差异、数据源行为测不出，需要少量集成测试补齐。

### 3.3 MockMvc 断言链【重点】

```java
mockMvc.perform(post("/orders")
        .contentType(MediaType.APPLICATION_JSON)
        .content("{\"amount\":0}"))
    .andExpect(status().isBadRequest())
    .andExpect(jsonPath("$.code").value("AMOUNT_INVALID"))
    .andDo(print());
```

`perform` 构造请求（URL、param、header、cookie、body）；`andExpect` 串起断言，常用 `status()`、`jsonPath("$.data.id").exists()`、`jsonPath("$.items").hasSize(2)`、`header().string`；`andDo(print())` 调试打印，`andReturn()` 取 `MvcResult` 做二次断言。断言错误码与关键字段即可，不要整体比对 JSON 字符串，字段顺序变化就会误报。

### 3.4 测试事务回滚【重点】

Spring Test 的 `@Transactional` 默认在测试结束后回滚，`@Rollback(false)` 或 `@Commit` 才提交，`@Sql` 可在类或方法级别初始化数据。回滚的代价是事务一直开着，flush 时机与生产不同，延迟约束、唯一索引冲突、乐观锁版本、二级缓存、`AFTER_COMMIT` 事件都可能测不出来；需要真实提交的用例应显式提交并在之后清理数据。`RANDOM_PORT` 下的 HTTP 请求在另一个线程和事务里执行，不参与测试事务，无法回滚，这类测试要用 Testcontainers 配合每次重建 schema。

### 3.5 Testcontainers 原理与用法【重点】

原理：JUnit5 扩展 `@Testcontainers` 扫描 `@Container` 字段，在测试类或方法开始前调用 Docker 启动容器，结束后停止；端口随机映射，通过 `getMappedPort` 或 `@DynamicPropertySource` 注入配置；Ryuk 边车容器负责回收异常退出时泄漏的容器。

```java
@Testcontainers
@SpringBootTest
class OrderRepositoryIT {
    @Container
    static MySQLContainer<?> mysql = new MySQLContainer<>("mysql:8.0");

    @DynamicPropertySource
    static void props(DynamicPropertyRegistry r) {
        r.add("spring.datasource.url", mysql::getJdbcUrl);
        r.add("spring.datasource.username", mysql::getUsername);
        r.add("spring.datasource.password", mysql::getPassword);
    }
}
```

常用容器有 MySQLContainer、PostgreSQLContainer、KafkaContainer、RedisContainer、LocalStackContainer，以及可跑任意镜像的 GenericContainer。实践要点：容器声明为 static 全类复用，不要每个方法起一次；镜像版本固定，不用 latest；本地可开 `testcontainers.reuse.enable=true` 复用，CI 保持隔离；CI 需要可用的 Docker 守护进程，并预拉镜像、缓存层。

### 3.6 与 H2、嵌入式方案对比【了解】

| 维度 | H2 / HSQLDB | Testcontainers |
| --- | --- | --- |
| 启动速度 / 依赖 | 毫秒级，仅 JDK | 秒到十几秒，需要 Docker 与镜像 |
| 保真度 | 方言、函数、索引、锁、隔离级别有差异 | 与生产同版本，行为一致 |
| 适用 | 快速反馈、简单 CRUD、无 Docker 环境 | 集成测试、SQL 优化、迁移脚本验证 |
| 风险 | 出现「H2 通过、MySQL 报错」 | 资源占用高，并行时端口与内存压力大 |

结论：单元测试不碰数据库；需要真实数据库行为时优先 Testcontainers；H2 只作为无 Docker 时的降级方案，并明确它不能替代真实库验证。

### 3.7 容器启动开销与 CI 实践【了解】

按测试类复用 static 容器，多个测试类共享时抽公共基类或使用单例模式；Spring Boot 3.1 起可用 `@ServiceConnection` 替代手写 `@DynamicPropertySource`。CI 并行分片会各自起容器，资源开销成倍放大，应按模块拆分流水线并控制并发度。容器启动失败要快速失败并输出 docker 日志；无 Docker 时不要静默跳过集成测试，那会制造虚假的绿色。

## 四、测试质量与 CI 集成

### 4.1 覆盖率的度量与 JaCoCo【重点】

| 指标 | 含义 | 价值 |
| --- | --- | --- |
| 行覆盖率 / 分支覆盖率 | 被执行行比例 / if、switch、三元表达式的分支命中比例 | 直观但易虚高 / 更能暴露未测路径 |
| 方法、类、指令覆盖率 | 是否被调用过 / 字节码指令命中比例 | 粗粒度参考 |

JaCoCo 通过 Java Agent 在类加载时插桩记录探针命中，Maven 或 Gradle 插件生成 HTML/XML 报告，CI 再上传 SonarQube。看报告的重点不是总数字，而是未覆盖分支集中在哪些类：核心业务、异常处理、边界判断大面积未覆盖的风险远高于工具类。

### 4.2 为什么覆盖率不等于质量【重点】

没有任何断言的测试也能达到 100%：代码被执行不等于结果被验证。只覆盖正常路径时，异常分支、空集合、超时、并发冲突全没测；getter、setter、DTO、生成代码还会拉高整体数字。为数字补测试，会产出「调用一下、断言非空」的无效用例；覆盖率也发现不了「测错的行为」，测试与实现犯同一个理解错误时依然全绿。

所以覆盖率是下限指标，用来防止大面积未测，而不是质量指标。更有效的信号是变异测试得分、线上缺陷逃逸率，以及每个线上 bug 是否补上了能复现的回归用例。

### 4.3 变异测试思路【了解】

PIT 在字节码层制造变异：大于改大于等于、加号改减号、返回值改 null、删除方法调用，然后重跑测试。测试失败说明变异体被杀死，测试仍通过说明测试没发现这个缺陷，变异得分等于杀死数除以总数。它的价值是直接衡量测试发现缺陷的能力；成本是耗时数倍到数十倍，通常只对核心模块与增量代码运行，设阈值门禁（如核心包 60%），把存活的变异体当作待补用例清单。

### 4.4 有效测试的判断【重点】

| 判断项 | 说明 |
| --- | --- |
| 能否捕获真实缺陷 | 故意改坏实现测试应变红；修复的 bug 必须补回归用例 |
| 是否验证结果与副作用 | 返回值、状态变化、发出的消息、落库的数据 |
| 是否覆盖边界与异常 | 空值、0、负数、上限、超时、重复提交、并发 |
| 是否独立且确定、失败可定位 | 不依赖执行顺序、时间、网络、共享数据；断言消息含期望值、实际值与场景 |

### 4.5 Flaky 测试治理【重点】

| 原因 | 表现 | 处理 |
| --- | --- | --- |
| 时间 | 跨时区、依赖 now() | 注入 Clock，固定时间 |
| 随机 | 随机 ID、随机顺序 | 固定种子或注入生成器 |
| 并发 / 异步 | 线程调度、事件或 MQ 回调尚未到达 | CountDownLatch、Awaitility 轮询等待 |
| 外部依赖 | 网络抖动、第三方限流 | mock 或 Testcontainers，禁止真实外网 |
| 共享状态 / 顺序依赖 | 静态变量、依赖前一个用例的数据 | 每用例独立构造数据，不假设顺序 |

治理原则是先定位再重试。重试只能降低噪音，不能修复缺陷；确认为环境问题的用例打 `@Tag("flaky")` 隔离到独立流水线并限期修复，避免团队对红色构建麻木。

### 4.6 测试分层在 CI 中的执行【重点】

| 阶段 | 触发 | 内容 | 时长目标 |
| --- | --- | --- | --- |
| 提交 / PR | 每次 push | 编译、静态检查、单元测试 | 几分钟内 |
| 合并前 | PR 合并 | 切片测试、Testcontainers 集成测试、契约测试 | 十几分钟 |
| 合并后 | 主干 | 部署测试环境、端到端冒烟 | 半小时内 |
| 每日 | 定时 | 全量回归、变异测试、性能基线压测 | 小时级 |

质量门禁关注新增代码：新增行与分支覆盖率阈值（如 70% 与 60%）、SonarQube 阻断新引入的严重问题、重复率、单测零失败。阈值只对增量生效（干净代码原则），存量代码逐步偿还，否则团队会想办法绕过门禁。缓存依赖、并行分片、只在必要时启动容器，是流水线保持快速的关键。

## 五、性能测试与容量评估

### 5.1 指标含义【核心】

| 指标 | 定义 | 注意点 |
| --- | --- | --- |
| 并发数 | 同时在处理的请求数或压测用户数 | 与线程数不是一回事，排队请求也算 |
| TPS / QPS | 每秒完成的事务数或请求数 | 一个事务可能含多个请求，报告写清口径 |
| RT | 响应时间，看平均、P90、P99、P999 | 平均值会被长尾掩盖 |
| 错误率 / 资源利用率 | 超时、5xx、业务失败的占比 / CPU、内存、GC、磁盘 IO、网络带宽 | 超时也是错误；看饱和度与排队，不只看平均使用率 |

利特尔法则：并发数约等于 TPS 乘以平均 RT，时间单位要一致。TPS 500、RT 100 毫秒时在途请求约 50 个；反过来，200 个线程、RT 200 毫秒，理论上限约 1000 TPS。

### 5.2 平均值与 P99/P999【重点】

| 统计量 | 含义 | 适用 |
| --- | --- | --- |
| 平均值 | 所有请求的算术平均 | 看整体趋势，不代表用户体验 |
| P90 / P99 | 90% / 99% 的请求快于此值 | 常规体验 / SLO 与容量决策 |
| P999 | 最慢 0.1% 的起点 | 支付、交易等核心链路 |

平均值掩盖长尾：99 个请求 10 毫秒、1 个请求 1 秒，平均约 20 毫秒，但每 100 个用户就有 1 个卡 1 秒。长尾的典型来源是 GC 停顿、慢 SQL 与锁等待、连接池排队、线程池队列、下游抖动、冷启动。分位数需要足够样本（1 万个请求的 P999 只有 10 个样本），且不可加，不能对已有 P99 求平均，必须在直方图上聚合（如 `histogram_quantile`）。

### 5.3 JMeter 组件与分布式压测【重点】

| 组件 | 作用 |
| --- | --- |
| 线程组 | 并发数、ramp-up、循环次数或持续时间 |
| Sampler | HTTP、JDBC、Dubbo 等请求 |
| 配置元件 / 断言 / 定时器 | CSV 参数化、HTTP 头与 Cookie 管理 / 响应码与 JSON 校验 / 控制请求节奏 |
| 事务控制器 / 监听器 | 合并 TPS 口径 / 聚合报告与 HTML Dashboard |

实践：GUI 只用于编写脚本，正式压测用命令行 `jmeter -n -t plan.jmx -l result.jtl -e -o report`；断言必须开启，否则错误响应也会被当作成功；数据用 CSV 参数化并准备足够多的账号，避免缓存命中失真。分布式压测由 controller 调度多个 slave，节点版本一致、同一网段、关闭 GUI，并核算每台压测机的 CPU、带宽与端口上限。

### 5.4 梯度加压找拐点【重点】

从低并发开始，按 50、100、200、400 逐级加压，每级稳定运行 3 到 5 分钟，记录 TPS、RT、错误率与资源指标：

| 阶段 | TPS | RT | 错误率 | 解读 |
| --- | --- | --- | --- | --- |
| 线性区 | 随并发线性上升 | 基本平稳 | 接近 0 | 系统有余量 |
| 拐点 | 不再上升或开始下降 | 明显变长 | 开始出现 | 达到最大处理能力 |
| 过载区 | 下降 | 陡增 | 上升 | 排队与重试引发雪崩 |

拐点是 TPS 饱和、RT 陡增、错误率抬头三者同时出现的区间，容量规划按拐点 TPS 的 70% 左右留余量。压测场景要按生产流量比例混合、热点接口加权，单一接口的 TPS 不能直接当作系统容量。

### 5.5 瓶颈定位顺序【重点】

1. 排除压测端：压测机 CPU 打满、带宽跑满、端口耗尽，压力根本没发出去。
2. 网络：带宽、丢包、重传、跨机房延迟。
3. 入口：Tomcat 或 Netty 线程数与队列、网关限流、负载均衡分配不均。
4. JVM：CPU 火焰图找热点，GC 日志看停顿与频率，堆与直接内存。
5. 锁与池：jstack 的 BLOCKED/WAITING 定位同一把锁；数据库、HTTP、Redis 连接池的 active、pending 与等待时间。
6. 数据库与下游：慢 SQL、执行计划、连接数上限、磁盘 IO；第三方接口 RT、超时与重试放大。

### 5.6 TPS 上不去但 CPU 很低【重点】

本质是线程在等待而不是在计算，按下面顺序排查：

| 原因 | 证据 | 处理 |
| --- | --- | --- |
| 池子太小 | Tomcat 线程满，DB/HTTP/Redis 连接池排队 | 结合下游承载力扩池，不盲目加大 |
| 锁竞争 | jstack 大量 BLOCKED，等同一把锁 | 缩小锁粒度、分段锁、无锁结构 |
| 下游慢 | 链路追踪显示耗时集中在某个调用 | 降级、缓存、异步化，收敛超时与重试 |
| 同步日志 | 磁盘 IO 高、日志量巨大 | 异步 Appender、降级别、采样 |
| 数据库热点 | 同一行更新、行锁等待、慢 SQL | 拆热点、批量合并、优化索引 |
| 限流熔断 | 网关或 Sentinel 拦截计数 | 核对阈值与规则是否符合预期 |
| 压测端瓶颈 | 压测机 CPU、带宽、端口耗尽 | 分布式压测，增加压测机 |
| 网络延迟 / 代码阻塞 / GC | RT 高但服务端耗时低 / 存在 sleep、串行调用 / GC 长暂停 | 就近部署与连接复用 / 异步化、并行化 / 调堆与收集器 |

工具组合：jstack 看线程状态分布（BLOCKED 多指向锁，WAITING 在 socketRead 指向下游或 IO）、arthas 的 thread 与 trace、链路追踪、各池监控、GC 日志。

### 5.7 全链路压测与数据隔离【重点】

全链路压测在生产或同构环境模拟真实流量，必须保证压测数据不污染真实业务：

| 维度 | 做法 |
| --- | --- |
| 流量染色 | 请求头（如 `x-pressure-test: true`）标记，网关统一注入并校验 |
| 上下文透传 | HTTP 头、RPC attachment、线程上下文、MQ 消息属性逐跳传递 |
| 数据库 | 影子库或影子表，按标记路由数据源，表结构与主库一致 |
| 缓存 / MQ | 影子 key 前缀 / 影子 Topic 与独立消费组 |
| 第三方 | 短信、支付、物流 mock 或走沙箱，禁止真实扣款 |
| 数据构造 / 预案 | 独立压测账号与商品数据，压完按标记清理；准备一键停止、限流熔断与真实业务监控 |

关键实现是标记在整条链路不丢：线程池切换、异步提交、MQ 发送都可能丢失上下文，需要 TransmittableThreadLocal 或显式传递。

### 5.8 容量评估方法【了解】

先取压测拐点 TPS 乘安全系数 0.7，得到单机安全容量；再估算峰值 QPS，即日均 QPS 乘峰值系数（通常 3 到 10），大促再乘活动倍数；实例数等于峰值 QPS 除以单机安全容量，向上取整后加冗余（N+1 或 1.5 倍），并考虑扩容延迟与 JVM 预热。同步核算数据库连接数、Redis、MQ、带宽、第三方配额，最短板决定整体容量；结果写成基线，随版本回归验证，HPA 阈值与基线对齐。

### 5.9 调优验证与回归【重点】

一次只改一个变量（JVM 参数、池大小、索引、代码），否则无法归因；脚本、数据量、环境、预热状态保持一致，否则前后不可比；对比看 TPS、P99、错误率、资源利用率四项，不看单点。调优后要跑稳定性测试，长时间运行观察内存泄漏与 GC 恶化，并跑功能回归确认未退化。报告留存为基线，版本迭代或容量变化后复测，上线后用小流量灰度对照真实指标。
