# MySQL 面试题集（含参考答案）

> 答案按六段式生成，选题来自《Java架构师技术栈锚点.md》3.1 MySQL。以 MySQL 8.0 / InnoDB 为准，涉及 5.7 与版本差异单独标注。口述版可直接读出声，卡壳处即理解缺口。

## 一、索引与执行计划

### 1. 【必答】索引：为什么 InnoDB 用 B+ 树，聚簇索引和二级索引怎么组织？

**口述版**

InnoDB 的索引是 B+ 树而不是 B 树。原因是磁盘按页读，B+ 树的非叶子节点只存键和指针，一页能放更多键，树高通常两到四层就能覆盖千万级数据；数据都在叶子节点，叶子之间用双向链表串起来，范围查询和排序只要顺着链表扫。InnoDB 的主键索引是聚簇索引，叶子直接存整行数据；二级索引的叶子存的是主键值，所以通过二级索引查非索引列时，要拿主键再回聚簇索引查一次，这就是回表。也正因为如此，主键建议用自增短值，避免随机插入导致页分裂和二级索引膨胀。

**短版**

B+ 树矮胖、叶子存数据且有序链表；聚簇索引叶子是整行，二级索引叶子是主键，查非索引列要回表；主键用自增短值。

**展开版**

- 机制链：按页读取（16KB）→ 非叶子层二分定位 → 叶子页定位记录 → 聚簇索引直接取行，二级索引取主键再回表。
- 关键结构：数据页与页目录、非叶子键值对、叶子双向链表、无主键时自动生成的 row_id。
- 触发条件：等值、范围、排序、分组；区分度低的列建索引收益很小。
- 例外：覆盖索引不回表；主键过长会让所有二级索引变大；无序主键插入会触发页分裂。
- 对比取舍：B+ 树适合磁盘和范围查询，哈希只适合等值，跳表内存友好但磁盘层级多。

**追问预判**

- 为什么不用 B 树 → 非叶子存数据导致扇出小、树更高，范围查询还要中序遍历。
- 叶子链表有什么用 → 范围扫描和 order by 可以顺序读，不用回上层跳转。
- 自增主键没有缺点吗 → 并发插入有热点，分段或雪花能缓解，但会带来随机 IO。

**常见错误答法**

- 把索引说成"排好序的数组"，忽略页和树的结构。
- 认为二级索引叶子直接存整行数据。

**记忆锚点**

B+ 树矮胖、叶子链表；聚簇存整行、二级存主键、非覆盖必回表。

### 2. 【必答】索引：回表、覆盖索引与最左前缀，范围查询后面的列为什么用不上？

**口述版**

联合索引按最左前缀匹配：索引是 a、b、c，条件必须从 a 开始且连续，跳过 a 直接查 b 就用不上。范围查询会截断后面的列：a 用了范围，b 和 c 就不能再用于定位，只能做索引条件下推过滤或者靠覆盖索引。覆盖索引指查询需要的列都在索引里，不用回表，执行计划 Extra 显示 Using index。回表是二级索引拿到主键后再去聚簇索引取整行，多一次随机 IO，所以高频查询尽量设计成覆盖索引，或者把常用列冗余进联合索引。代价是索引变宽、写入变慢，要按查询模式取舍。

**短版**

最左前缀且连续；范围列之后无法继续定位，只能下推过滤或覆盖；覆盖索引不回表，Extra 显示 Using index。

**展开版**

- 机制链：联合索引按 a、b、c 排序 → 先按 a 定位 → a 相同按 b → 再按 c → 范围之后只能顺序扫并回表过滤。
- 关键结构：索引列顺序、key_len 反映用了几个列、索引条件下推 ICP、覆盖索引。
- 触发条件：多条件查询、order by / group by 走索引、分页查询。
- 例外：范围列后的列仍可用于覆盖和 ICP；8.0 有 skip scan，但依赖优化器，不能当设计前提。
- 对比取舍：等值列放前、范围列放后；索引越多写越慢，要按真实查询排序设计。

**追问预判**

- key_len 怎么看用了哪几列 → 按列类型长度累加，遇到范围或未使用就截断。
- order by 怎么用上索引 → 排序顺序和索引顺序一致，且不跨范围。
- 索引下推解决什么 → 在索引层先过滤，减少回表次数。

**常见错误答法**

- 认为联合索引的任意列都能单独用。
- 把范围列放最左，还期望后面的列能用于定位。

**记忆锚点**

最左且连续，范围即截断；覆盖不回表，Extra 看 Using index。

### 3. 【必答】索引：执行计划怎么看，type、key、rows、Extra 各说明什么？

**口述版**

看执行计划先看 type，从好到差是 system、const、eq_ref、ref、range、index、ALL，出现 ALL 或 index 全扫就要警惕。然后看 key 实际用了哪个索引、key_len 用了多少列、rows 是优化器估算的扫描行数、filtered 是过滤后的比例。Extra 信息量最大：Using index 是覆盖索引，Using where 是回表后过滤，Using filesort 是额外排序，Using temporary 是临时表，Using index condition 是索引下推，Using join buffer 说明被驱动表没走索引。要注意 rows 只是估算，真实行数和各阶段耗时要用 EXPLAIN ANALYZE 看。

**短版**

先看 type（const/eq_ref/ref/range 好，index/ALL 差），再看 key、key_len、rows、filtered，重点读 Extra：Using index 覆盖、filesort 排序、temporary 临时表、index condition 下推。

**展开版**

- 机制链：优化器基于统计信息和成本模型选路径 → 生成执行计划 → EXPLAIN 展示估算 → EXPLAIN ANALYZE 真实执行并给出实际行数与耗时。
- 关键结构：type、possible_keys、key、key_len、ref、rows、filtered、Extra、optimizer_trace。
- 触发条件：慢查询、新增索引后验证、上线前 SQL 评审。
- 例外：统计信息过期会让估算偏差很大，需要 ANALYZE TABLE；分区表、子查询、union 要分开看。
- 对比取舍：EXPLAIN 无副作用但只是估算，ANALYZE 真实但会执行，写语句要在事务里回滚或在只读库执行。

**追问预判**

- type=index 和 ALL 有什么区别 → index 是全索引扫描，通常比全表好，但仍然扫完整个索引。
- filesort 一定慢吗 → 小结果集在内存排不慢，大结果集落盘才慢。
- rows 很小为什么还是慢 → 统计偏差、回表随机 IO、锁等待都可能。

**常见错误答法**

- 只看 key 有索引就认为没问题。
- 把 rows 当成真实扫描行数。

**记忆锚点**

type 看路径、key_len 看列数、Extra 看代价；估算用 EXPLAIN，真相用 ANALYZE。

### 4. 【进阶】索引：索引失效的常见场景有哪些，怎么判断和改写？

**口述版**

常见失效有六类。第一，列上做函数或运算，比如 where date(create_time) = ...，索引列被包住就用不了。第二，隐式类型转换，字符串列传数字、数字列传字符串都可能触发转换，等价于在列上套函数，字符集不一致的 join 也会。第三，前导模糊 like 百分号开头，只能全扫；前缀匹配可以走索引。第四，OR 连接的条件里有一侧没索引，整体退化为全表。第五，联合索引不满足最左前缀，或者范围列后面的列无法定位。第六，优化器估算回表成本太高，主动放弃索引，这属于成本选择，不一定是坏事。

**短版**

列上函数或运算、隐式类型转换、前导模糊、OR 一侧无索引、不满足最左前缀、优化器主动放弃；字符集不一致的 join 也会失效。

**展开版**

- 机制链：条件列被表达式包裹 → 无法利用索引有序性定位 → 只能逐行计算比较 → 退化为全表或全索引扫描。
- 关键结构：隐式转换规则、字符集与排序规则、ICP、优化器成本估算与统计信息。
- 触发条件：时间函数、字符串拼接、类型不一致、字符集不一致、参数化查询配合直方图。
- 例外：8.0.13 之后的函数索引能救回一部分场景；覆盖索引下即使条件不全命中也可能仍走索引。
- 对比取舍：改写 SQL 让列"裸奔"最通用；建函数索引方便，但有写入和维护成本。

**追问预判**

- 为什么数字列传字符串也失效 → 转换方向由规则决定，可能对列做转换，索引就用不上。
- 怎么确认是隐式转换 → 看 key_len、列的字符集类型，或 EXPLAIN 的 warning。
- 函数索引怎么用 → 建与表达式完全一致的函数索引，查询写法也必须一致。

**常见错误答法**

- 只说"不要用 like 百分号开头"，漏掉类型转换和字符集问题。
- 认为有索引就一定会走索引。

**记忆锚点**

列裸奔才走索引；函数、转换、前导模糊、OR、最左、成本六类失效。

### 5. 【进阶】索引：Join 有哪几种执行方式，驱动表怎么选？

**口述版**

MySQL 的 Join 主要有三种执行方式。被驱动表的连接列有索引时用嵌套循环 NLJ，外层小结果集驱动内层走索引，成本最低。被驱动表没索引时，旧版本用块嵌套循环 BNL，把驱动表数据放进 join buffer 批量匹配；8.0.18 之后有哈希连接，等值 join 会优先用 hash join，把较小的表建哈希表再探测。驱动表由优化器按过滤后的行数和成本选，通常是小结果集驱动大表，这里的"小"指过滤后的结果集，不是表总行数。大表 join 大表要么靠索引，要么考虑冗余宽表、拆查询，或者放到 OLAP 里做。

**短版**

NLJ（被驱动表有索引）、BNL（无索引，join buffer）、Hash Join（8.0.18+ 等值）；驱动表按过滤后行数和成本选；大表 join 大表考虑宽表或换存储。

**展开版**

- 机制链：选驱动表 → 逐行取驱动表记录 → 到被驱动表按连接列查（索引、join buffer 或哈希表）→ 输出匹配行。
- 关键结构：join buffer、hash join、eq_ref/ref 的 type、驱动表顺序、straight_join 提示。
- 触发条件：多表关联查询、子查询展开、分页 join。
- 例外：连接列类型或字符集不一致会让索引失效，退化成 BNL；不等值 join 用不了等值哈希路径。
- 对比取舍：NLJ 适合有索引的小结果集，hash join 适合大结果集等值，BNL 是兜底但内存和 CPU 开销大。

**追问预判**

- 怎么判断用了哪种 join → 看 EXPLAIN 的 type 和 Extra 里的 join buffer 或 hash join 提示。
- 为什么小结果集驱动大表 → 外层结果集小，内层探测次数就少。
- join 字段要注意什么 → 类型、字符集、排序规则一致，否则索引失效。

**常见错误答法**

- 把"小表"理解成总行数少，忽略 where 过滤后的结果集。
- join 字段类型不一致，还奇怪为什么不走索引。

**记忆锚点**

有索引 NLJ、无索引 BNL、8.0 等值 Hash；驱动表看过滤后结果集。

### 6. 【兜底】索引：慢 SQL 怎么定位，从慢日志到执行计划的完整路径？

**口述版**

定位慢 SQL 的路径是：先开慢查询日志，设合理的 long_query_time，用 pt-query-digest 或 performance_schema 按总耗时排序，找出占比最高的那几条，而不是盯着单次最慢的。拿到 SQL 后用 EXPLAIN 看执行计划和估算行数，8.0.18 以上用 EXPLAIN ANALYZE 看真实行数和各阶段耗时。再结合锁等待、buffer pool 命中率、临时表和排序是否落盘，判断瓶颈在索引、SQL 写法、数据量还是并发锁。优化顺序是索引、SQL 改写、表结构，最后才是读写分离和分片这些架构手段。

**短版**

慢日志加 pt-query-digest 按总耗时排序 → EXPLAIN / EXPLAIN ANALYZE → 看锁等待、buffer pool、filesort、temporary → 按索引、SQL、表结构、架构的顺序优化。

**展开版**

- 机制链：采集慢日志 → 聚合排序 → 取 Top SQL → 执行计划与真实执行 → 定位瓶颈类型 → 改写并验证。
- 关键结构：slow_query_log、long_query_time、performance_schema、pt-query-digest、optimizer_trace。
- 触发条件：RT 上升、DB CPU 或 IO 高、连接数上涨、主从延迟。
- 例外：有些慢来自锁等待而不是执行本身，要看 wait 事件；也有来自网络或结果集过大。
- 对比取舍：采样日志开销小但可能漏，全量采集完整但有性能成本，生产按需开启。

**追问预判**

- 为什么按总耗时排序 → 少量极慢 SQL 和大量中等慢 SQL 对总容量影响不同，要治大头。
- EXPLAIN 和 ANALYZE 区别 → 一个是估算，一个是真实执行。
- SQL 看着没问题但还是慢 → 看锁、并发、buffer pool 命中和硬件。

**常见错误答法**

- 只优化单次最慢的那条，忽略高频的中等耗时 SQL。
- 不看执行计划，凭感觉加索引。

**记忆锚点**

慢日志聚合 → 计划与真实执行 → 分清执行慢还是等锁慢。

## 二、事务与 MVCC

### 7. 【必答】事务：ACID 在 InnoDB 里分别靠什么实现？

**口述版**

InnoDB 里，原子性靠 undo log：修改前的旧值记下来，回滚时反向应用。持久性靠 redo log：先写日志再刷数据页，也就是 WAL，崩溃后用 redo 重放。隔离性靠锁和 MVCC：写写靠锁，读写靠多版本快照。一致性是结果，不是某一个机制，靠约束、事务、业务逻辑和上面三者共同保证。提交过程是两阶段：redo 先写 prepare，然后写 binlog 并刷盘，最后 redo 写 commit 标记，这样崩溃恢复时能保证 redo 和 binlog 一致，主从和备份不会多数据或丢数据。

**短版**

原子性 undo、持久性 redo（WAL）、隔离性锁加 MVCC、一致性是综合结果；提交走 redo prepare → binlog → redo commit 两阶段。

**展开版**

- 机制链：修改前写 undo → 修改页并写 redo（prepare）→ 写 binlog → redo 写 commit → 后台刷脏页。
- 关键结构：undo log、redo log 循环写、binlog、doublewrite buffer、trx_id。
- 触发条件：事务提交、崩溃恢复、主从复制、备份恢复。
- 例外：非事务引擎不支持；`innodb_flush_log_at_trx_commit` 和 `sync_binlog` 不为 1 时会丢最近事务。
- 对比取舍：强持久性牺牲部分性能，双 1 最安全；异步刷盘快，但有丢数据窗口。

**追问预判**

- 为什么需要两阶段提交 → 保证 redo 与 binlog 原子一致，避免主库和从库数据不一致。
- undo 什么时候清理 → 没有事务再需要该版本时，由 purge 线程清理。
- redo 为什么循环写 → 空间固定，靠 checkpoint 推进覆盖旧日志。

**常见错误答法**

- 把一致性说成"靠事务保证"，没有落到约束和业务。
- 忽略 binlog 在复制与恢复中的作用。

**记忆锚点**

undo 回滚、redo 持久、锁与 MVCC 隔离、两阶段提交保一致。

### 8. 【必答】事务：四种隔离级别分别解决什么问题，MySQL 默认用哪个？

**口述版**

四种隔离级别对应三类问题。读未提交会脏读；读已提交解决脏读，但同一事务两次读可能不一样，也就是不可重复读；可重复读解决不可重复读，MySQL 默认就是这个级别，幻读靠间隙锁和 MVCC 在大部分场景下避免；串行化全部串行，性能最差。实现上，读已提交每条语句生成一个新的 Read View，所以能看到别人已提交的新数据；可重复读在事务第一次快照读时生成 Read View 并复用，所以整个事务看到一致快照。互联网业务常改成读已提交来减少间隙锁、提升并发，但要接受不可重复读，并保证 binlog 用 ROW 格式。

**短版**

RU 脏读、RC 不可重复读、RR 可重复读（默认，幻读靠间隙锁加 MVCC）、Serializable 串行；RC 每条语句一个 Read View，RR 事务内复用。

**展开版**

- 机制链：设置隔离级别 → 快照读生成 Read View → 判断可见性 → 当前读加锁 → 不同级别锁范围不同。
- 关键结构：transaction_isolation、Read View、next-key lock、binlog_format。
- 触发条件：事务内多次查询、统计报表、并发写入。
- 例外：RR 下快照读和当前读混用仍可能看到新数据；RC 下间隙锁基本关闭，幻读可能出现。
- 对比取舍：RR 一致性好但间隙锁多、死锁概率高；RC 并发高但要处理不可重复读和复制格式。

**追问预判**

- 为什么互联网常用 RC → 减少间隙锁和死锁、提升并发，配合 ROW binlog 保证复制一致。
- RR 真的完全解决幻读吗 → 快照读靠 MVCC、当前读靠临键锁，混用时仍有边界情况。
- 隔离级别是会话级还是全局 → 两者都能设，会话级优先。

**常见错误答法**

- 认为 RR 下绝对没有幻读。
- 认为把级别改成 RC 没有副作用。

**记忆锚点**

RC 每语句快照、RR 事务快照；幻读靠间隙锁加 MVCC，RC 并发高但一致弱。

### 9. 【必答】事务：MVCC 的版本链、undo log 与 Read View 怎么工作？

**口述版**

InnoDB 每行有两个隐藏列：事务 id 和回滚指针。每次修改都把旧版本写进 undo log，回滚指针把版本串成链，这就是版本链。快照读时生成 Read View，里面有当前活跃事务 id 列表、最小活跃 id、下一个要分配的最大 id 和创建者 id。判断可见性：自己改的可见；事务 id 小于最小活跃 id 可见；大于等于最大 id 不可见；落在活跃列表里不可见；其余可见。读已提交每条语句生成一次，可重复读只在第一次快照读生成并复用，所以两者看到的数据不一样。

**短版**

隐藏的 trx_id 加 rollback_ptr 串起 undo 版本链；Read View 用活跃事务列表、最小和最大 id 判断可见性；RC 每语句生成，RR 事务内复用。

**展开版**

- 机制链：更新时写 undo 并改行指针 → 生成 Read View → 沿版本链找第一个可见版本 → 返回该版本数据。
- 关键结构：DB_TRX_ID、DB_ROLL_PTR、undo log、Read View 的 m_ids、min_trx_id、max_trx_id、creator_trx_id。
- 触发条件：普通 select 快照读、RR 长事务、报表查询。
- 例外：当前读不走 MVCC，直接读最新并加锁；undo 被 purge 后旧版本不再可得。
- 对比取舍：MVCC 让读写不互相阻塞，代价是 undo 膨胀和长事务风险。

**追问预判**

- 版本链太长会怎样 → 回滚和快照读变慢，undo 空间持续增长。
- 为什么长事务危险 → Read View 不释放，旧版本无法 purge。
- 当前读会看到旧版本吗 → 不会，它读最新版本并加锁。

**常见错误答法**

- 认为 MVCC 只靠 undo，不需要 Read View。
- 把 RR 理解成"每次都读最新数据"。

**记忆锚点**

版本链在 undo，可见性看 Read View；RC 每条语句、RR 整个事务。

### 10. 【进阶】事务：快照读与当前读有什么区别，RR 下幻读到底解决了吗？

**口述版**

普通 select 是快照读，读的是 Read View 对应的历史版本，不加锁。加锁读和写操作是当前读：select for update、lock in share mode、update、delete、insert 都读最新版本并加锁。RR 下快照读靠 MVCC 避免幻读，当前读靠临键锁避免幻读，两者机制不同。要注意一个事务里先快照读再当前读，可能看到之前没有、现在有的记录，这不是 bug，而是两种读语义不同。理解这一点，才能解释为什么"同一个事务里查不到却更新成功"。

**短版**

普通 select 快照读、不加锁；for update、lock in share mode 和写操作是当前读、读最新并加锁；RR 下快照读靠 MVCC、当前读靠临键锁。

**展开版**

- 机制链：快照读生成或复用 Read View → 沿版本链取可见版本；当前读定位最新记录 → 加记录锁或临键锁 → 持有到事务结束。
- 关键结构：Read View、next-key lock、共享锁与排他锁、加锁读语法。
- 触发条件：核对余额、扣库存、状态机流转等需要读到最新值的场景。
- 例外：快照读在 RC 下每条语句都新快照；当前读在唯一索引等值命中时可退化为记录锁。
- 对比取舍：快照读并发高但可能读到旧值；当前读一致但阻塞多、死锁风险高。

**追问预判**

- 为什么"查不到却能更新" → 快照读看不到新插入的行，当前读能看到并更新。
- for update 没走索引会怎样 → 可能锁住全表所有记录和间隙。
- 怎么选 → 需要最新值且防并发修改用当前读，否则用快照读。

**常见错误答法**

- 认为所有 select 都不加锁。
- 用快照读替代 for update 做并发控制。

**记忆锚点**

select 快照、for update 当前；一个看历史、一个看最新。

### 11. 【进阶】事务：长事务有哪些危害，怎么治理？

**口述版**

长事务的危害有四个。第一，undo 不能及时清理，版本链越来越长，history list 膨胀，回滚和快照读都变慢，表空间只涨不降。第二，锁持有时间长，阻塞其他 DML 和 DDL，容易引发锁等待和死锁。第三，大事务产生大 binlog，从库回放慢，主从延迟明显。第四，占用连接和内存，连接池容易被拖满。治理上要监控 innodb_trx 里运行时间长的事务，设 max_execution_time、innodb_lock_wait_timeout，把批量操作拆成小批提交，事务里绝对不要做远程调用或等待用户输入。

**短版**

undo 膨胀、锁持有久、binlog 大导致延迟、占用连接；治理靠监控 innodb_trx、拆批提交、设超时、事务内不做远程调用。

**展开版**

- 机制链：事务开启 → 持有 Read View 和锁 → 旧版本无法 purge → undo 和 history list 增长 → 提交或回滚时集中清理。
- 关键结构：information_schema.innodb_trx、history list length、undo 表空间、max_execution_time、锁等待超时。
- 触发条件：批量更新、报表事务、事务里调用外部接口、忘记提交。
- 例外：只读长事务不持锁，但同样阻止 purge；DDL 等待元数据锁也会表现成长事务阻塞。
- 对比取舍：拆批增加提交次数和失败重试复杂度，但资源可控性和可恢复性明显更好。

**追问预判**

- 怎么发现长事务 → 查 innodb_trx 按 trx_started 排序，再结合 processlist。
- 为什么只读事务也有害 → Read View 不释放，undo 无法清理。
- 怎么拆批 → 按主键范围分页，每批固定行数提交并记录位点。

**常见错误答法**

- 只在应用层设超时，不管数据库侧。
- 事务里包远程调用，认为"反正会回滚"。

**记忆锚点**

长事务三宗罪：undo 不清理、锁不放、binlog 太大；拆批、超时、事务内不做远程调用。

### 12. 【兜底】事务：事务不回滚或失效的常见原因怎么排查？

**口述版**

Spring 事务失效常见原因有一串。异常被 catch 没抛出，或者抛的是检查异常但没配 rollbackFor，默认只回滚运行时异常。自调用：同类方法内部调用不走代理，注解不生效。方法不是 public，或者类没被 Spring 管理。数据库引擎不支持事务，比如 MyISAM。多数据源切换顺序不对，事务开在了错误的数据源上。传播行为理解错，比如以为 REQUIRES_NEW 会共享外层事务。异步线程里执行，事务上下文没有传递。排查时先确认代理是否生效、连接是否自动提交、异常类型和传播行为是否符合预期。

**短版**

异常被吞、rollbackFor 没配、自调用绕过代理、非 public、类没托管、引擎不支持、多数据源切错、传播行为误用、异步丢上下文。

**展开版**

- 机制链：调用进入代理 → 事务拦截器开启事务 → 执行业务 → 按异常类型决定回滚 → 提交或回滚。
- 关键结构：TransactionInterceptor、AOP 代理、rollbackFor、propagation、DataSourceTransactionManager。
- 触发条件：同类内部调用、私有方法、异常被捕获、跨数据源、异步执行。
- 例外：切到 AspectJ 模式可以拦截自调用，但配置复杂；编程式事务不受代理限制。
- 对比取舍：声明式简洁但隐式，排查要看代理；编程式啰嗦但边界清晰，核心链路可显式控制。

**追问预判**

- 为什么自调用失效 → 调用没有经过代理对象，拦截器不执行。
- 检查异常为什么不回滚 → 默认规则只对 RuntimeException 和 Error 回滚。
- 怎么验证事务生效 → 看连接是否同一个、日志里有没有开启提交、断点进拦截器。

**常见错误答法**

- 以为加了注解就一定回滚。
- 在事务方法里 try-catch 后继续返回成功。

**记忆锚点**

代理没走到、异常没抛出、类型不匹配、数据源不对，四类先查。

## 三、锁与死锁

### 13. 【必答】锁：行锁、表锁、意向锁是什么关系？

**口述版**

InnoDB 的锁按粒度分行锁和表锁。行锁加在索引记录上，所以更新条件必须走索引，否则会退化成锁全表所有记录和间隙。表级还有意向锁：事务要加行锁前，先在表上加意向共享锁或意向排他锁，用来快速判断表里有没有行锁，避免逐行检查。MDL 是元数据锁，DDL 和 DML 之间靠它互斥，所以一个长查询就能把加字段的操作堵住。共享锁允许并发读，排他锁互斥读写。另外 insert 有隐式锁，插入时不加显式锁，靠事务 id 判断，真正冲突时才转换。锁信息可以在 performance_schema.data_locks 里看。

**短版**

行锁在索引记录上，没走索引会锁全表；意向锁是表级标记，用来快速判断有无行锁；MDL 管 DDL 与 DML 互斥；S 锁共享、X 锁互斥，insert 有隐式锁。

**展开版**

- 机制链：加行锁前先加意向锁 → 在索引记录上加 S 或 X → 事务结束释放 → 表级只需看意向锁判断冲突。
- 关键结构：record lock、IS/IX 意向锁、MDL、隐式锁与事务 id、data_locks 视图。
- 触发条件：update/delete 走索引、显式 lock in share mode、DDL 执行。
- 例外：唯一索引等值命中的加锁范围最小；无索引或函数条件会让行锁退化为全表扫描加锁。
- 对比取舍：行锁并发高但管理开销大，表锁简单但冲突高；InnoDB 只在必要时升级。

**追问预判**

- 为什么没索引会锁全表 → 无法定位具体行，只能扫全部记录并加锁。
- 意向锁会阻塞普通读写吗 → 意向锁之间大多兼容，主要用来和表级锁互斥。
- MDL 为什么会导致故障 → 长事务或长查询持有 MDL，后续 DDL 排队并阻塞新查询。

**常见错误答法**

- 认为行锁和索引无关。
- 把 MDL 当成 InnoDB 的行锁。

**记忆锚点**

行锁在索引上，意向锁在表上，MDL 管 DDL；没索引就锁全表。

### 14. 【必答】锁：间隙锁与临键锁怎么加，为什么容易锁范围过大？

**口述版**

临键锁是记录锁加间隙锁，锁住的是左开右闭区间。在可重复读下，范围查询和非唯一索引等值查询会加临键锁，目的是防止其他事务在区间里插入，从而避免幻读。唯一索引等值命中且记录存在时会退化成记录锁；没命中则退化成间隙锁。间隙锁之间不冲突，但插入意向锁会和间隙锁冲突。代价是锁范围容易过大，并发下降、死锁概率上升，所以很多互联网业务把隔离级别改成读已提交，基本关掉间隙锁。要注意间隙锁只在可重复读及以上生效。

**短版**

临键锁等于记录锁加间隙锁，锁左开右闭区间；RR 下范围和非唯一等值会加，唯一等值命中退化为记录锁；间隙锁防插入防幻读，但范围大、易死锁。

**展开版**

- 机制链：按索引定位区间 → 对区间内记录加记录锁、对间隙加间隙锁 → 阻止其他事务插入 → 事务结束释放。
- 关键结构：next-key lock、gap lock、record lock、插入意向锁、唯一索引的退化规则。
- 触发条件：范围查询、非唯一索引等值查询、for update 未命中记录。
- 例外：RC 下间隙锁基本关闭，只保留外键和唯一性检查需要的部分；唯一等值命中只锁记录。
- 对比取舍：间隙锁换来了 RR 下的幻读防护，代价是并发和死锁；RC 换来并发但接受幻读。

**追问预判**

- 为什么唯一索引等值能退化 → 唯一性保证区间里最多一条记录，不需要防插入。
- 间隙锁之间为什么不冲突 → 它们锁的是"不允许插入"这个意图，彼此不排斥。
- 什么时候最容易死锁 → 两个事务用不同顺序加临键锁，再互相等待对方间隙。

**常见错误答法**

- 认为间隙锁会锁住已有的行（它锁的是间隙）。
- 在 RC 下还按 RR 的加锁范围分析。

**记忆锚点**

临键锁等于记录加间隙；唯一等值退化，RR 才生效，范围越大越容易死锁。

### 15. 【进阶】锁：死锁怎么产生，怎么定位和规避？

**口述版**

死锁是两个或多个事务互相持有对方需要的锁并等待。InnoDB 有死锁检测，用等待图找环，发现后回滚代价较小的事务，报 Deadlock found。定位看 SHOW ENGINE INNODB STATUS 里的 LATEST DETECTED DEADLOCK，或者 performance_schema 的 data_lock_waits，能看到两个事务的 SQL、持有和等待的锁。规避手段：固定加锁顺序、按主键更新、缩短事务、减少范围锁、降低并发、失败重试。重试要幂等，否则回滚后重放可能重复写。要注意死锁不一定是代码写错，高并发下也可能出现，重点是把概率和影响降下来。

**短版**

互相持有并等待；InnoDB 等待图检测并回滚代价小的事务；看 INNODB STATUS 和 data_lock_waits；固定顺序、按主键、短事务、少范围锁、幂等重试。

**展开版**

- 机制链：事务 A 持锁 1 等锁 2 → 事务 B 持锁 2 等锁 1 → 等待图成环 → 检测器选择牺牲者回滚 → 另一个事务继续。
- 关键结构：等待图、LATEST DETECTED DEADLOCK、data_lock_waits、innodb_deadlock_detect。
- 触发条件：批量更新顺序不一致、范围更新、二级索引加锁顺序不同、并发扣减热点行。
- 例外：关闭死锁检测会让死锁表现为锁等待超时，通常不建议；分布式事务的死锁要靠业务层协调。
- 对比取舍：重试能提高成功率，但要有上限和退避；降低并发能减少死锁，但牺牲吞吐。

**追问预判**

- 死锁和锁等待超时什么关系 → 死锁是环，检测到立即回滚一个；锁等待超时是等太久主动放弃。
- 为什么批量更新容易死锁 → 多行加锁顺序不一致，交叉等待。
- 怎么复现 → 两个会话按相反顺序更新同一批主键，手动制造等待。

**常见错误答法**

- 看到死锁就简单加重试，不看加锁顺序。
- 认为死锁只出现在高并发，单条 SQL 不会。

**记忆锚点**

死锁是环，检测回滚代价小的；固定顺序、短事务、幂等重试。

### 16. 【进阶】锁：乐观锁与悲观锁怎么选，库存扣减怎么做？

**口述版**

悲观锁假设冲突多，先 select for update 锁住再改，适合强一致、冲突高的场景，代价是阻塞和死锁。乐观锁假设冲突少，读的时候带版本号，更新时 where version 等于旧值，影响行数为零就重试，适合读多写少。库存扣减最优解是原子更新：update stock set qty 等于 qty 减一 where id 等于多少 and qty 大于等于一，靠行锁和条件保证不超卖，不用先查再改。热点行冲突极高时，单行锁会成为瓶颈，可以分桶、批量合并，或者用 Redis 预扣再异步落库。

**短版**

悲观锁先锁再改，适合冲突高；乐观锁版本号 CAS，适合冲突低；库存用条件原子更新最稳；极热点分桶或 Redis 预扣。

**展开版**

- 机制链：悲观：开启事务 → for update 加行锁 → 判断并更新 → 提交释放；乐观：读版本 → 带版本更新 → 影响行数为零则重试。
- 关键结构：行锁、version 字段或状态机、条件更新、影响行数、重试策略。
- 触发条件：库存扣减、余额变更、状态流转、秒杀。
- 例外：乐观锁在高冲突下重试风暴，反而更慢；悲观锁在长事务里会放大阻塞。
- 对比取舍：悲观锁简单直接但吞吐低；乐观锁吞吐高但要处理重试和失败；原子更新兼顾正确性和性能。

**追问预判**

- 为什么不要先查再减 → 查询和更新之间有竞态，必须靠条件更新或锁保证原子性。
- 乐观锁重试多少次 → 设上限并退避，超过就快速失败或降级。
- 分桶怎么保证总量 → 每个桶独立扣减，总量等于各桶之和，售罄判断要聚合。

**常见错误答法**

- 用"查库存大于零再 update"的两步操作，超卖。
- 乐观锁无上限重试，冲突高时把 DB 打满。

**记忆锚点**

悲观先锁、乐观版本、库存条件更新；热点分桶或预扣。

### 17. 【兜底】锁：锁等待超时与热点行更新怎么优化？

**口述版**

锁等待超时先确认是谁持锁：查 data_lock_waits 和 innodb_trx，找到阻塞源 SQL。常见原因是长事务、没走索引导致锁范围大、批量更新顺序不一致。热点行更新的本质是同一行的排他锁串行化，TPS 上限就是单行锁的吞吐。优化方向：缩短事务、把多次更新合并成一次、按业务分桶把一行拆成多行、异步化削峰、乐观锁重试，或者把扣减放到 Redis 再异步落库。监控上盯锁等待时间和死锁次数，设合理的 innodb_lock_wait_timeout，不要让请求无限等。

**短版**

先找持锁源：data_lock_waits 加 innodb_trx；常见原因是长事务、没走索引、批量顺序不一致；热点行靠短事务、合并、分桶、异步、Redis 预扣。

**展开版**

- 机制链：请求等锁 → 超过 innodb_lock_wait_timeout 报错 → 查等待关系定位持锁事务 → 处理长事务或改加锁范围。
- 关键结构：data_lock_waits、innodb_trx、锁等待超时参数、热点行计数、监控指标。
- 触发条件：秒杀库存、账户余额、计数器、状态机单行流转。
- 例外：有些等待来自 MDL 而不是行锁，要看 metadata_locks；从库上的长查询也会阻塞 DDL。
- 对比取舍：分桶提升并发但增加聚合复杂度；Redis 预扣性能高但要处理一致性和补偿。

**追问预判**

- 怎么快速找到阻塞源 → 查 data_lock_waits 的 blocking 事务 id，再关联 innodb_trx 和 processlist。
- 热点行为什么 TPS 上不去 → 同一行的 X 锁必须串行，CPU 再高也没用。
- 超时时间设多少 → 按业务可接受等待设，通常几秒，配合快速失败和重试。

**常见错误答法**

- 把锁等待当成慢 SQL，去加索引却没看等待关系。
- 无限调大超时时间，请求全堆在数据库上。

**记忆锚点**

先找持锁源，再缩事务、缩锁范围；热点行分桶、合并、异步。

## 四、日志、复制与高可用

### 18. 【必答】日志：redo log、undo log、binlog 各自的职责与两阶段提交？

**口述版**

redo log 是物理日志，记录页的修改，循环写，保证崩溃恢复和持久性，采用 WAL 先写日志再刷数据页。undo log 是逻辑日志，记录修改前的值，用于回滚和 MVCC。binlog 是 Server 层的逻辑日志，记录语句或行变更，用于主从复制和归档恢复。三者协作靠两阶段提交：redo 写 prepare，binlog 写完并刷盘，redo 再写 commit，崩溃恢复时根据 redo 是否 commit 决定提交还是回滚，保证主库和从库一致。生产上建议双 1：innodb_flush_log_at_trx_commit 等于 1、sync_binlog 等于 1，binlog 用 ROW 格式。

**短版**

redo 物理、循环写、保持久和崩溃恢复；undo 逻辑、管回滚和 MVCC；binlog 在 Server 层、管复制和归档；两阶段提交保证 redo 与 binlog 一致，生产用双 1 加 ROW。

**展开版**

- 机制链：修改页并写 undo → redo prepare → binlog 写入并 fsync → redo commit → 后台刷脏页。
- 关键结构：redo log 文件组、undo 表空间、binlog 文件、doublewrite、checkpoint。
- 触发条件：事务提交、实例崩溃、主从复制、备份恢复。
- 例外：组提交能合并 fsync 提升吞吐；关闭双 1 会缩短持久性窗口。
- 对比取舍：双 1 最安全但每次提交两次刷盘；追求吞吐可放宽，但要接受丢最近事务的风险。

**追问预判**

- 崩溃恢复怎么判断提交还是回滚 → redo 有 commit 就提交，处于 prepare 则看 binlog 是否完整。
- binlog 为什么不能用 redo 替代 → redo 是物理页级、循环覆盖，不能做归档和逻辑复制。
- doublewrite 解决什么 → 防止页写一半崩溃导致页损坏，redo 无法修复。

**常见错误答法**

- 把 redo 说成逻辑日志，或者认为 binlog 在 InnoDB 层。
- 认为只要写了 redo 就不会丢数据，忽略刷盘参数。

**记忆锚点**

redo 持久、undo 回滚、binlog 复制；两阶段提交加双 1。

### 19. 【进阶】日志：主从复制的流程、延迟原因与读写分离一致性？

**口述版**

主从复制是三步：主库的 dump 线程把 binlog 发给从库；从库的 IO 线程写入 relay log；SQL 线程回放 relay log。延迟常见原因：大事务、从库回放单线程或并行度不够、从库硬件差、无主键表导致行锁扫描、DDL、从库上有大查询抢资源。读写分离的一致性问题就是主从延迟：写后立刻读可能读不到。兜底手段是写后读走主库、会话粘性、按 GTID 或 binlog 位点等待、关键读强制主库。监控不要只看 Seconds_Behind_Master，它在大事务下不准，要看 GTID 位点差和回放耗时。

**短版**

主库 dump 发 binlog → 从库 IO 线程写 relay log → SQL 线程回放；延迟来自大事务、并行度不足、无主键、DDL、从库负载；兜底走主库、粘会话、等位点。

**展开版**

- 机制链：事务提交写 binlog → dump 线程推送 → 从库落 relay log → SQL 线程按位点回放 → 更新从库数据。
- 关键结构：binlog dump、relay log、GTID、并行复制、Seconds_Behind_Master。
- 触发条件：写多读少、大事务、批量导入、从库跑分析查询。
- 例外：半同步只保证收到，不保证回放；级联复制会放大延迟。
- 对比取舍：并行复制提升回放速度但受事务依赖限制；强一致读主库牺牲读扩展性。

**追问预判**

- 为什么无主键表回放慢 → 行格式下按全表扫描定位行，代价极高。
- Seconds_Behind_Master 为什么不准 → 它基于时间差，大事务或时钟偏差会失真。
- 位点等待怎么做 → 记录主库 GTID，读到从库执行位点追上再返回。

**常见错误答法**

- 认为主从复制是同步的，写完立刻能读到。
- 只看延迟秒数，不看具体卡在哪个事务。

**记忆锚点**

dump → relay → 回放；延迟看大事务、并行度、无主键；一致性靠走主库或等位点。

### 20. 【进阶】日志：半同步、组复制与主从切换怎么保证不丢数据？

**口述版**

半同步复制要求至少一个从库确认收到 binlog，主库才返回提交成功，超时会退化成异步。它降低丢数据概率但不等于零丢失，因为确认的是收到而不是回放。组复制 MGR 基于多数派协议，支持单主和多主，提交需要多数节点确认，一致性更强，但对网络延迟敏感、运维复杂。主从切换要解决选新主、旧主脑裂和数据补偿：传统用 MHA、Orchestrator，云上一般托管。要做到尽量不丢，需要双 1、半同步或 MGR、切换前确认位点、切换后校验，并让应用侧有重连和只读降级。

**短版**

半同步等至少一个从库 ACK，超时退化异步；MGR 多数派确认、一致性强但运维复杂；切换要选主、防脑裂、补数据，配合双 1 和应用重连。

**展开版**

- 机制链：主库提交 → 等从库 ACK（半同步）或多数派确认（MGR）→ 返回成功 → 故障时选位点最新的节点提升。
- 关键结构：after_sync / after_commit、ACK 超时、MGR 组通信、GTID、切换工具。
- 触发条件：主库宕机、网络分区、机房故障、计划内切换。
- 例外：半同步在超时后退化为异步，仍有丢数据窗口；MGR 在 minority 分区不可写。
- 对比取舍：强一致提升安全性但增加写延迟；异步性能好但故障时可能丢最近事务。

**追问预判**

- 半同步能保证零丢失吗 → 不能，只保证至少一个从库收到，且超时会退化。
- 脑裂怎么防 → 多数派机制、fencing、切换前确认旧主已停止写入。
- 切换后应用要做什么 → 重连、刷新路由、只读降级、校验数据。

**常见错误答法**

- 认为开了半同步就万无一失。
- 切换只看新主可用，不校验位点和数据。

**记忆锚点**

半同步等 ACK、MGR 等多数派；切换防脑裂、补位点、应用可重连。

### 21. 【兜底】日志：主从延迟导致读不到数据，怎么排查和兜底？

**口述版**

主从延迟导致读不到刚写的数据，表现是写后读为空或旧值。排查先看 SHOW SLAVE STATUS：Seconds_Behind_Master、Retrieved 和 Executed 的 GTID 差、relay log 是否堆积，再结合从库负载、大事务、无主键表、DDL 和锁等待。兜底方案：写后读强制走主库、同一会话粘主库、按位点等待、缓存刚写入的结果、业务上接受短暂不一致。长期治理靠拆大事务、提升从库配置、开并行复制、避免在从库跑重查询，以及用 GTID 监控真实延迟。要区分是延迟问题还是复制中断，两者的处置完全不同。

**短版**

看 SHOW SLAVE STATUS 的延迟、GTID 差、relay log 堆积，结合大事务、无主键、从库负载；兜底走主库、粘会话、等位点、缓存；长期拆大事务、并行复制。

**展开版**

- 机制链：主库写入 → binlog 传输 → 从库回放滞后 → 读请求落到从库 → 读到旧快照 → 业务表现为数据缺失。
- 关键结构：SHOW SLAVE STATUS、GTID executed 与 retrieved、relay log、并行复制参数。
- 触发条件：大事务、批量导入、DDL、从库资源争用、网络抖动。
- 例外：复制线程报错中断时延迟会持续增长，必须看 Last_Error；从库只读查询也可能被大查询拖慢。
- 对比取舍：全部读主库最稳但失去扩展性；按场景选择强一致读，其余容忍延迟更现实。

**追问预判**

- 怎么判断是延迟还是中断 → 看 IO/SQL 线程是否 Running、Last_Error、GTID 是否推进。
- 位点等待会不会拖慢接口 → 会，要设上限，超时就降级或走主库。
- 大事务怎么拆 → 按主键分批提交，控制单次 binlog 大小。

**常见错误答法**

- 一看到读不到就怀疑缓存，不先看复制状态。
- 用 sleep 等待从库同步，不可控且放大 RT。

**记忆锚点**

先看复制状态和 GTID 差；兜底走主库、等位点；长期拆大事务、提并行。

## 五、分库分表、DDL 与选型

### 22. 【必答】分库分表：什么时候该拆，路由、跨分片查询与全局 ID 怎么处理？

**口述版**

先判断该不该拆：单表到千万级、单库容量或写入到瓶颈，而且索引优化、归档、读写分离都用过了，才考虑分片。拆分方式分水平和垂直：水平按分片键哈希或范围拆成多张同构表，垂直按业务拆库。路由的关键是分片键要覆盖主要查询，否则跨分片查询要广播加内存归并，分页、排序、聚合代价都很高。跨分片事务尽量避免，靠业务设计让同一聚合根落在同一分片。全局 ID 用雪花或号段模式。拆分之后运维复杂度、扩容、数据迁移、监控都会上一个台阶，要提前想清楚。

**短版**

单表千万级、容量或写入到瓶颈且优化手段用尽再拆；水平按分片键、垂直按业务；分片键要覆盖主查询，避免跨分片；全局 ID 用雪花或号段。

**展开版**

- 机制链：确定分片键 → 路由计算定位分库分表 → 单分片执行 → 跨分片则广播并归并 → 返回结果。
- 关键结构：分片键、路由规则、逻辑表与物理表、跨分片归并、全局 ID 生成器。
- 触发条件：单表数据量过大、写入瓶颈、单库磁盘或连接数到上限。
- 例外：小表关联大表可以广播小表；按时间分片适合冷热分离，但热点会集中在新分片。
- 对比取舍：分片换扩展性，代价是跨片查询、事务和运维复杂度；能不拆就不拆。

**追问预判**

- 分片键怎么选 → 选查询必带、分布均匀、能覆盖主要访问路径的字段，比如用户 id。
- 跨分片分页怎么办 → 各分片取前 N 条再归并，深分页代价高，通常限制或改用游标。
- 全局 ID 要趋势递增吗 → 对 B+ 树写入友好，雪花和号段都能做到趋势递增。

**常见错误答法**

- 数据量一涨就拆，不先做索引和归档。
- 分片键选错，导致大部分查询都要广播。

**记忆锚点**

先榨干单机再拆；分片键定路由，跨片查询要归并，ID 用雪花或号段。

### 23. 【进阶】分库分表：扩容与数据迁移怎么做，怎么保证一致和可回滚？

**口述版**

分片扩容优先成倍扩，比如二的幂次翻倍，这样大部分数据不用动，只迁移一半。迁移步骤一般是：先双写新老库，再用全量加增量把存量搬过去，增量靠 binlog 订阅追平，然后做行数和内容校验，抽样比对，确认一致后灰度切读，最后切写并保留回滚开关。关键是可回滚：切读切写都要有开关，出问题能切回。校验要做对账任务，不只比行数，还要比关键字段的 checksum。迁移前要压测新库的容量和连接数，别搬完才发现扛不住。

**短版**

成倍扩容减少迁移量；双写 + 全量增量同步 + 校验 + 灰度切读 + 切写，全程保留回滚开关；对账要比内容和 checksum，不只比行数。

**展开版**

- 机制链：新库建表 → 双写开启 → 全量迁移 → binlog 增量追平 → 校验对账 → 灰度切读 → 切写 → 观察后下线旧库。
- 关键结构：双写开关、binlog 订阅位点、全量校验工具、路由开关、回滚预案。
- 触发条件：分片数不够、单分片过大、机房或云迁移。
- 例外：双写失败要能补偿；增量追平前不能切读；强一致业务需要短暂停写窗口。
- 对比取舍：双写简单但有一致性风险，订阅同步更可控但有延迟；停写最稳但影响业务。

**追问预判**

- 双写怎么保证一致 → 写主库成功后同步写新库，失败进补偿队列并对账修复。
- 校验怎么做 → 分片按主键范围算 checksum，抽样比对，差异记录后修复。
- 什么时候可以下线旧库 → 观察期无回滚、对账连续一致、调用方全部切换完成。

**常见错误答法**

- 只做全量迁移，不做增量追平，切换时丢数据。
- 没有回滚开关，切过去出问题只能硬扛。

**记忆锚点**

成倍扩、双写加增量、校验后灰度切、全程可回滚。

### 24. 【进阶】DDL：在线 DDL 的原理与风险，大表变更怎么控？

**口述版**

MySQL 5.6 之后有 Online DDL，很多操作可以 in-place 执行并允许并发 DML，但并不是完全无锁：开始和结束要拿元数据锁，重建表会消耗大量 IO 和磁盘，还可能让主从延迟。8.0 支持 instant add column，加列很快，但改列类型、加索引、改字符集仍可能重建。风险控制：避开高峰、评估表大小和磁盘余量、用 gh-ost 或 pt-online-schema-change 做影子表加限速、先在从库或预发验证、准备好回滚。最怕的是 MDL 等待把整张表的读写都堵住。

**短版**

Online DDL 可并发 DML，但首尾要拿 MDL、重建表耗 IO 且拉高主从延迟；8.0 加列可 instant；大表用 gh-ost 或 pt-osc，限速、低峰、先验证。

**展开版**

- 机制链：DDL 请求元数据锁 → 短暂阻塞 → 重建或修改表结构 → 应用日志追赶期间的 DML → 换表并释放锁。
- 关键结构：MDL、in-place / copy、instant add column、gh-ost 影子表、pt-osc 触发器。
- 触发条件：加索引、改列类型、加列、改字符集、分区变更。
- 例外：instant 只支持部分操作；修改列顺序、压缩等仍可能重建；从库回放 DDL 也会阻塞。
- 对比取舍：原生 Online DDL 简单但可控性弱；gh-ost 可控、可限速，但需要额外空间和运维。

**追问预判**

- 为什么 DDL 会阻塞查询 → 等 MDL 时后续查询排队，长事务会让等待无限延长。
- gh-ost 和 pt-osc 区别 → gh-ost 靠 binlog 应用变更、无触发器；pt-osc 用触发器，老版本更常见。
- 怎么降低主从延迟 → 限速、分批、低峰执行，必要时先在从库操作。

**常见错误答法**

- 认为 Online DDL 完全不锁表。
- 业务高峰直接对大表加索引，没评估磁盘和 MDL。

**记忆锚点**

Online 不是无锁，MDL 最致命；大表用影子表工具，限速低峰。

### 25. 【兜底】选型：MySQL 与 PostgreSQL 怎么选？

**口述版**

MySQL 胜在简单、生态广、互联网运维经验成熟，主从复制和分库分表方案都很多，适合以 OLTP 为主、团队熟悉的场景。PostgreSQL 功能更强：类型丰富、JSONB、数组、窗口函数、CTE、并行查询，DDL 支持事务，扩展生态好，地理和向量场景有优势。选型看业务和团队：需要复杂查询、地理信息、强 SQL 能力可以选 PG；追求成熟运维体系和高并发简单读写，MySQL 更稳。迁移成本、云厂商支持、合规要求往往是一票否决项，不要只看功能对比。

**短版**

MySQL 简单、生态成熟、适合 OLTP；PG 功能强，JSONB、窗口、CTE、扩展和复杂查询有优势；选型看业务、团队和云支持，迁移与合规常是一票否决。

**展开版**

- 机制链：从数据模型、查询复杂度、并发模型、复制与扩展、运维能力五个维度评估 → 再做 PoC 压测 → 最后看迁移和生态。
- 关键结构：索引类型、JSON 支持、事务 DDL、复制方式、扩展插件、云厂商托管能力。
- 触发条件：新业务选型、地理信息、复杂报表、JSON 半结构化数据、向量检索。
- 例外：MySQL 8 也支持 CTE、窗口函数和 JSON，差距在缩小；PG 高并发简单写入的调优经验相对少。
- 对比取舍：功能强不等于适合，团队熟悉度和长期运维成本往往更决定成败。

**追问预判**

- 什么业务 PG 更合适 → 复杂查询、地理、JSON、需要扩展和强 SQL 能力的场景。
- 什么业务不值得换 → 现有 MySQL 稳定、团队不熟 PG、迁移收益小于成本。
- 一票否决项有哪些 → 合规、云厂商支持、数据迁移风险、团队能力。

**常见错误答法**

- 只对比功能列表，不看团队和运维。
- 认为 PG 全面优于 MySQL，忽略高并发简单读写场景的成熟度。

**记忆锚点**

MySQL 稳在生态，PG 强在功能；选型看业务、团队、云支持。

### 26. 【兜底】选型：分库分表与 NewSQL（TiDB / OceanBase）怎么权衡？

**口述版**

NewSQL 比如 TiDB、OceanBase 提供透明扩展和分布式事务，业务不用改分片逻辑，还能做 HTAP。代价是延迟通常高于单机 MySQL，跨节点事务和查询更明显，运维和成本也更高，SQL 兼容和生态工具有边界。适用场景是数据量大、跨分片事务多、又不想在业务层做路由；如果单机加索引、归档、读写分离就能撑住，或者团队没有分布式数据库运维能力，就不该上。原则是能不拆就不拆，先榨干单机，再考虑分片，最后才是换 NewSQL。

**短版**

NewSQL 透明扩展、分布式事务、HTAP，但延迟、成本、运维更高；适合大数据量且跨片事务多、不想改业务的场景；原则是先单机、再分片、最后 NewSQL。

**展开版**

- 机制链：评估数据量、事务范围、延迟要求、团队能力 → 对比分片方案与 NewSQL → PoC 压测延迟和成本 → 再决定。
- 关键结构：分布式事务、多副本一致性、计算存储分离、HTAP、兼容层。
- 触发条件：单机或分片维护成本过高、跨分片事务频繁、需要实时分析。
- 例外：低延迟核心交易对 NewSQL 的网络和共识开销敏感；小团队缺少分布式运维能力容易踩坑。
- 对比取舍：NewSQL 降低业务改造但抬高基础设施要求；分片改造成本高但可控、延迟低。

**追问预判**

- NewSQL 为什么延迟更高 → 分布式事务、多副本共识和跨节点网络往返。
- 什么时候分片比 NewSQL 好 → 数据模型简单、能选好分片键、团队有中间件经验。
- 迁移要注意什么 → 兼容性、事务语义、性能回归、运维体系和回滚方案。

**常见错误答法**

- 认为上了 NewSQL 就不用管数据模型和索引。
- 数据量不大也上分布式数据库，成本和复杂度双输。

**记忆锚点**

先单机、再分片、最后 NewSQL；透明扩展的代价是延迟、成本和运维。
