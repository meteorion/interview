## 一、类加载

### 1. 【必答】类加载：类加载五个阶段，什么时候真正触发初始化？

**口述版**

类加载分加载、验证、准备、解析、初始化五步。加载把字节流读进来，在方法区建类结构、堆里生成 Class 对象；验证检查魔数和字节码，防止恶意代码破坏虚拟机；准备只给静态变量分配内存并赋零值，所以 `static int a = 10` 这时还是 0，而 `static final` 常量已经是 10；解析把符号引用换成直接引用；初始化执行 `<clinit>`，按代码顺序跑静态赋值和静态块。触发初始化的是主动引用：new、读写非常量静态字段、调静态方法、反射、初始化子类前先初始化父类，以及 main 所在的启动类。不触发的是引用编译期常量、只声明数组、通过子类访问父类静态字段。要注意 `<clinit>` 带锁，多线程同时初始化同一个类只有一个线程执行，其余阻塞，所以静态块里别做耗时操作。

**短版**

加载→验证→准备→解析→初始化，准备赋零值，初始化才跑 `<clinit>`；new、静态字段读写、静态方法、反射、子类初始化前初始化父类才触发。

**展开版**

- 机制链：加载取字节流生成 Class 对象 → 验证（文件格式、元数据、字节码、符号引用）→ 准备（静态变量分配内存 + 零值）→ 解析（符号引用转直接引用）→ 初始化（执行 `<clinit>`）。
- 关键结构：`<clinit>` 由编译器收集静态变量赋值语句和 static 块，按源码顺序合并；JVM 用类对象上的初始化锁保证只执行一次。
- 触发条件：new / getstatic、putstatic（非编译期常量）/ invokestatic / 反射 / 子类初始化 / 启动类。
- 例外：`static final` 基本类型与 String 字面量属编译期常量，在准备阶段就完成赋值，不触发初始化；引用数组类型不初始化元素类。
- 对比取舍：`<clinit>` 只会执行一次且阻塞其他线程，懒加载单例正是利用这一点，但静态块里做 IO 会拖慢首次请求。

**追问预判**

- 准备阶段为什么是零值 → 保证字段即使没显式赋值也有确定初值，引用类型是 null。
- 静态内部类单例为什么线程安全 → 类初始化由 JVM 加锁，天然只执行一次，且首次访问才触发。
- `<clinit>` 抛异常会怎样 → 包成 ExceptionInInitializerError，类变成 Error 状态，后续再用抛 NoClassDefFoundError。

**常见错误答法**

- 把「准备」说成给静态变量赋代码里的初值（只有结论错、混淆阶段）。
- 把「加载」等同于「类加载全过程」（概念混淆）。

**记忆锚点**

加载取流 → 验证防坏 → 准备置零 → 解析换址 → 初始化跑 clinit → 主动引用才触发。

### 2. 【必答】类加载：双亲委派模型解决什么问题？没有它会怎样？

**口述版**

双亲委派是加载器收到请求先交给父加载器，父加载器加载不了自己才去加载。它解决两个问题：一是安全，自己写的 `java.lang.String` 会被一路委派到启动类加载器，最终用 JDK 自带版本，核心类不会被伪造替换；二是避免同一个类被重复加载，保证类的唯一性。没有它，任何人都能往 classpath 塞 `java.lang` 下的类，String、Object 这些基础类可以被随意篡改，整个运行时的行为都不可信了。代价是灵活性差，父加载器看不到子加载器的类，所以才有 SPI、Tomcat 这类打破它的场景。

**短版**

先父后子，父加载不了才自己加载；保证核心类不被伪造替换、避免重复加载；破坏则核心类可被篡改、同一个类出现多份。

**展开版**

- 机制链：`loadClass` 先 `findLoadedClass` 查缓存，再委派 parent，parent 失败后调 `findClass` 自己加载。
- 关键结构：parent 是组合关系而非继承；JDK 9+ 为 Bootstrap（null）→ Platform → Application。
- 触发条件：任何 `loadClass` 调用，默认都走这套逻辑；只有重写 `loadClass` 才绕开。
- 例外：线程上下文类加载器、OSGi 网状委派、Tomcat 的 WebappClassLoader 都不严格遵守。
- 对比取舍：严格委派换来安全与唯一性，牺牲的是隔离与热更新能力——隔离场景必须打破它。

**追问预判**

- 判断两个类相同看什么 → 全限定名 + 定义类加载器，两者都相同才算同一个类。
- 自定义加载器该重写哪个方法 → 只改来源重写 `findClass`，要打破委派才重写 `loadClass`。
- 父加载器能加载子加载器的类吗 → 不能，方向是单向的，所以才有上下文类加载器。

**常见错误答法**

- 只说「防止类重复加载」，漏掉安全这一层（只有结论）。
- 把 parent 说成继承关系（概念混淆）。

**记忆锚点**

先父后子 → parent 组合 → 查缓存再委派再 findClass → 安全 + 唯一性。

### 3. 【必答】类加载：哪些场景需要打破双亲委派？Tomcat、SPI/JDBC 分别怎么做？

**口述版**

典型就三类场景。SPI 是因为 DriverManager 由启动类加载器加载，它要加载 classpath 上厂商的驱动实现，可父加载器看不到子加载器的类，于是用线程上下文类加载器，让父加载器反过来请求子加载器去加载，ServiceLoader 就是这么做的。Tomcat 是应用隔离，一个 Tomcat 部署多个应用，可能依赖同一个库的不同版本，于是每个应用一个 WebappClassLoader，优先加载自己 `WEB-INF` 下的类，找不到再往上委派，但 JDK 核心类仍然先交给上层，防止被业务覆盖。热部署和 OSGi 则是丢掉旧加载器、用新的重新加载，OSGi 是网状委派。落地上，只换加载来源重写 `findClass` 就够，要真正打破才重写 `loadClass`，因为委派逻辑写在它里面。

**短版**

SPI 用线程上下文类加载器反向委派；Tomcat 每个应用一个 WebappClassLoader 先自己后父；热部署换加载器。只改来源重写 findClass，打破委派重写 loadClass。

**展开版**

- 机制链：父加载器持有的 `DriverManager` 通过 `ServiceLoader.load(Driver.class)` 取线程上下文类加载器 → 由它加载子路径下的驱动实现 → 完成注册。
- 关键结构：Tomcat 的 `WebappClassLoaderBase.loadClass` 先查本地缓存，再查 `WEB-INF/classes`、`WEB-INF/lib`，最后才委派；`java.*` 强制走父加载器。
- 触发条件：父加载器需要子加载器可见的类、同一组类需要多版本共存、需要运行时替换代码。
- 例外：Tomcat 只对业务类打破，核心类不打破，否则安全前提就没了。
- 对比取舍：打破委派换来隔离与可插拔，代价是类唯一性不再成立，跨加载器传对象会 ClassCastException。

**追问预判**

- 线程上下文类加载器为什么能解决 → 它存在 Thread 上，父加载器可以拿到并使用子加载器，绕开单向可见性。
- Tomcat 为什么要先自己后父 → 保证应用自带版本生效，实现同库多版本隔离。
- 重写 loadClass 要注意什么 → 要保留 `getClassLoadingLock` 和 `findLoadedClass`，否则并发下会重复加载。

**常见错误答法**

- 说 Tomcat 完全不走双亲委派（答非所问，核心类仍委派）。
- 把 SPI 说成重写了 `loadClass`（机制错位）。

**记忆锚点**

SPI 反委派 → Tomcat 先己后父 → 热部署换加载器 → findClass 改来源 / loadClass 改委派。

### 4. 【必答】类加载：同一个 class 被两个类加载器加载，instanceof 和 equals 结果如何？

**口述版**

判定规则是：全限定名相同还不够，定义它的类加载器也得相同，JVM 才认为它们是同一个类。所以同一个 class 文件被两个加载器各加载一次，得到的是两个互不相干的 Class，彼此的实例做 instanceof 返回 false，equals 也不相等，强转会抛 ClassCastException，因为两者的元信息、静态变量、锁对象都是各自独立的。这也是 Tomcat 能做应用隔离的原理，也是同一个类被反复加载导致 Metaspace 上涨的根源。

**短版**

类身份 = 全限定名 + 定义类加载器；两个加载器加载同一个 class 得到两个类，instanceof 为 false、equals 不等、强转抛 ClassCastException。

**展开版**

- 机制链：`ClassLoader.loadClass` 以「类名 + 加载器」定位类 → 各自在方法区建独立元信息 → 静态字段、常量、锁各自一份。
- 关键结构：`Class` 对象里持有 `classLoader` 引用，`isInstance`、`checkcast` 都会比较类对象地址。
- 触发条件：自定义加载器、Web 容器多应用、插件化、热部署新旧版本共存。
- 例外：父子委派下同一个类只会被加载一次，不会出现两份；但一旦子加载器自己 `findClass` 就打破了这个前提。
- 对比取舍：隔离换来版本共存和可卸载，代价是跨边界只能传 JDK 类型或公共接口（接口也必须由共同父加载器加载）。

**追问预判**

- 怎么跨加载器传对象 → 用共同父加载器加载的接口或 JDK 类型，配合序列化/反射。
- 为什么接口由各自加载器加载也会失败 → 接口的类身份同样不同，实现类和接口对不上。
- 和 Metaspace 泄漏什么关系 → 每份类元信息独立，加载器不释放就都留着。

**常见错误答法**

- 答「相等，因为字节码一样」（只有结论、忽略类身份）。
- 说 instanceof 会返回 true 但 equals 不等（前后矛盾）。

**记忆锚点**

类名 + 加载器 = 类身份 → 两份 Class → 互不 instanceof → 隔离与泄漏同源。

### 5. 【进阶】类加载：一个类被卸载需要满足什么条件？热部署怎么实现？

**口述版**

类卸载要同时满足三个条件：该类的所有实例都已被回收，它的 Class 对象没有被任何地方引用，加载它的类加载器也已经被回收，三者缺一不可，其中加载器被回收是最难的一环。HotSpot 只有自定义加载器加载的类才可能被卸载，启动类加载器加载的核心类基本不会卸载。热部署就是利用这个：每次重部署用一个全新的 ClassLoader 加载应用代码，旧应用停止后整体丢弃，旧加载器可达性消失，它加载的类才有机会被卸载，新代码才能生效。要注意只换类不换加载器不行，同一个加载器里类一旦加载就无法重新定义。

**短版**

实例全回收、Class 对象无引用、类加载器被回收，三条同时满足才卸载；热部署靠新建 ClassLoader 加载新代码、丢弃旧加载器。

**展开版**

- 机制链：卸载发生在 Full GC 的类卸载阶段 → 检查加载器是否可达 → 不可达则回收其加载的全部类元信息。
- 关键结构：`ClassLoader` 与 `Class` 双向引用，还有 `ClassLoader` 上的 `classes` 集合、`protectionDomain`。
- 触发条件：容器重部署、OSGi bundle 卸载、脚本引擎重启。
- 例外：`java.*` 等由 Bootstrap 加载的类不会被卸载；被 JNI 全局引用、JVMTI、静态字段持有的类也不会。
- 对比取舍：换加载器能整体卸载，但内存瞬时翻倍，且跨版本共享状态只能靠外部存储。

**追问预判**

- 热部署后旧类为何还在 → 加载器被线程、ThreadLocal、JMX、连接池持有，可达性未断。
- 能否在同一个加载器里改类 → 不能，只能通过 Instrumentation 的 redefine 做受限修改，签名不能变。
- 卸载时机 → 只能等 GC，没有主动卸载 API。

**常见错误答法**

- 只说「没人引用就卸载」，漏掉加载器条件和「实例必须全回收」（层级缺失）。
- 说 `System.gc()` 能强制卸载类（把建议当命令）。

**记忆锚点**

实例清空 → Class 无引用 → 加载器回收 → 换加载器即热部署。

### 6. 【进阶】类加载：Class.forName 与 ClassLoader.loadClass 的区别？

**口述版**

两者都要走类加载流程，区别在加载之后做不做初始化。`Class.forName` 默认 `initialize=true`，拿到 Class 之后会立即执行初始化，也就是跑静态块，而且用的是调用方的类加载器；`ClassLoader.loadClass` 只加载到解析完，不执行初始化，静态块要等第一次主动使用时才跑。所以 JDBC 老代码写 `Class.forName("com.mysql.jdbc.Driver")`，目的就是触发驱动类的静态块去注册自己。另一个区别是加载来源，`forName` 用调用方的加载器，跨加载器场景可能找不到类，`loadClass` 可以直接指定加载器。所以只拿元信息、做反射时，用 `loadClass` 更轻。

**短版**

forName 默认立即初始化、用调用方加载器；loadClass 只加载不初始化、可指定加载器。JDBC 注册驱动靠的就是 forName 触发静态块。

**展开版**

- 机制链：`forName` → 本加载器 `loadClass` → 若 `initialize` 为 true 则执行 `<clinit>`；`loadClass(name, resolve=false)` 停在解析。
- 关键结构：`Class.forName(name, initialize, loader)` 三参版本可显式控制初始化和加载器。
- 触发条件：需要静态块副作用（注册驱动、加载配置）时用 forName；只做类型判断、反射元数据时用 loadClass。
- 例外：JDK 9+ 的 JDBC 4.0 起支持 SPI 自动发现驱动，不再需要显式 forName。
- 对比取舍：forName 更省事但把初始化开销提前，且异常语义不同（初始化失败抛 ExceptionInInitializerError）。

**追问预判**

- forName 为什么能注册驱动 → 驱动类静态块里 `DriverManager.registerDriver(new Driver())`。
- loadClass 之后怎么手动初始化 → `Class.forName(name, true, loader)` 或反射 newInstance 触发。
- 两者异常有什么不同 → forName 初始化失败包成 ExceptionInInitializerError，loadClass 抛 ClassNotFoundException。

**常见错误答法**

- 说「forName 只加载、loadClass 也初始化」（概念颠倒）。
- 只答参数个数不同，不讲初始化语义（只有结论）。

**记忆锚点**

forName = 加载 + 初始化（默认）→ 触发静态块；loadClass = 只加载 → 可指定加载器。

### 7. 【进阶】类加载：Metaspace 溢出的常见原因？动态生成类如何影响它？

**口述版**

Metaspace 放类元信息，溢出一般报 Metaspace 或 Compressed class space。原因主要有三类：类加载器泄漏，热部署、动态代理、脚本引擎的旧加载器被持有，它加载的类就都卸不掉；动态生成类太多，CGLIB、JDK 动态代理、Groovy、反射生成的 GeneratedMethodAccessor 都在运行时造类，每次生成都是新类；还有参数限制，`MaxMetaspaceSize` 设得太小。动态生成类最麻烦的地方是它不受代码规模约束，跑多久生成多少，尤其每次请求都 new 一个 Enhancer 而不复用，类数量就线性上涨。排查我会先看 `jstat -gc` 的 MC/MU 和已加载类数，再用 `jmap -clstats` 或 arthas 的 classloader 看哪个加载器类最多，用 `-XX:+TraceClassLoading` 确认来源，处理上优先做代理类缓存和修泄漏，而不是单纯调大。

**短版**

三类原因：加载器泄漏、动态生成类过多、MaxMetaspaceSize 过小。动态代理不复用会让类数量线性增长；先看 MC/MU 与 classloader 统计定位，再缓存代理类。

**展开版**

- 机制链：类加载 → 元信息写入 Metaspace → 加载器不可达后随 Full GC 卸载 → 只增不减即溢出。
- 关键结构：Metaspace 分 Class、Non-class 两部分，压缩类空间受 `CompressedClassSpaceSize` 限制（默认 1G）。
- 触发条件：`-XX:MaxMetaspaceSize` 触顶；类数量暴涨；加载器泄漏。
- 例外：JDK 8 之前的永久代受限更死，JDK 8 起元空间默认只受本机内存限制，但生产仍建议设上限。
- 对比取舍：调大上限只是延后爆炸，真正要解决的是持有链；缓存代理类能降数量但不能修泄漏。

**追问预判**

- 怎么确认是泄漏而不是正常增长 → Full GC 后 MC 不回落、类数量单调上升，且与重部署次数相关。
- GeneratedMethodAccessor 是什么 → 反射调用超过阈值后 JVM 用字节码生成器造类加速，可调 `-Dsun.reflect.inflationThreshold`。
- 为什么压缩类空间单独报错 → 指针压缩要求类元信息在 32G 以下的固定区域，空间独立计算。

**常见错误答法**

- 只说「类太多」（不区分泄漏与动态生成，层级缺失）。
- 建议直接 `-XX:MaxMetaspaceSize=2g` 了事（答非所问）。

**记忆锚点**

Metaspace 存元信息 → 加载器泄漏 / 动态生成 / 上限过小 → 代理类缓存 + 断持有链。

### 8. 【兜底】类加载：并行类加载与类加载死锁是怎么产生的？

**口述版**

死锁的根子是类加载的锁粒度。`loadClass` 会对类名加锁保证只加载一次，初始化阶段的 `<clinit>` 也带锁，多个线程各持一把锁再互相请求，就死住了。典型形态是线程 A 加载类 A，A 的静态块要加载 B；线程 B 同时加载 B，B 的静态块要加载 A，两边都在等对方释放锁。并行类加载是 JDK 7 引入的，把锁从 ClassLoader 对象细化成按类名的分段锁，让不同类能并行加载，缓解了竞争，但消不掉这种循环依赖。排查时 `jstack` 会看到线程卡在 `<clinit>` 或 `loadClass` 上状态是 BLOCKED，日志里可能直接打印 deadlock 提示。根治办法是拆掉静态初始化里的循环依赖，别在静态块里调外部类。

**短版**

`<clinit>` 和 loadClass 各持锁，静态块互相触发对方类就形成 AB-BA 死锁；JDK 7 的并行加载把锁细化到类名，只缓解不根治，要靠拆循环依赖。

**展开版**

- 机制链：线程 A 持 lock(A) 等 lock(B) → 线程 B 持 lock(B) 等 lock(A) → 双方 BLOCKED。
- 关键结构：JDK 7 起 `ClassLoader` 用 `parallelLockMap` 做「类名 → 锁对象」映射，`registerAsParallelCapable` 后才生效。
- 触发条件：两个类的静态初始化互相引用，或多线程并发首次初始化。
- 例外：JDK 6 及以前是 ClassLoader 级大锁，反而更容易串行但不一定是死锁；父委派链上的锁顺序固定，一般不死。
- 对比取舍：并行加载提升启动和并发性能，代价是锁对象变多、调试更难，死锁形态更隐蔽。

**追问预判**

- 怎么从 jstack 判断 → 搜 `Found one Java-level deadlock` 或找 BLOCKED 且栈顶是 `<clinit>` 的线程。
- 单线程会死锁吗 → 不会循环等待，但会无限递归初始化，抛 StackOverflowError 或 ExceptionInInitializerError。
- 如何预防 → 静态块只做简单赋值，不在其中调用其他可能初始化类的逻辑。

**常见错误答法**

- 把死锁归因于 synchronized 业务锁（答非所问）。
- 说并行类加载彻底解决了死锁（把缓解当根治）。

**记忆锚点**

初始化锁 + 类名锁 → 静态块循环引用 → AB-BA 死锁 → 并行加载只缓解 → 拆依赖根治。

### 9. 【兜底】类加载：频繁重部署后 Metaspace 持续上涨，怎么确认是类加载泄漏？

**口述版**

我会看三件事。先看总量，`jstat -gc` 里的 MC、MU 和 LoadedClasses，如果 Full GC 之后 MC 几乎不回落、类数量随重部署次数阶梯上涨，基本就定型了，正常的类元信息在 GC 后是会有回落的。再看是谁，用 `jmap -clstats` 或 arthas 的 `classloader -t` 看每个加载器的实例数和加载类数，业务加载器本该只有少量实例，如果某个 WebappClassLoader 存了几十个，那就是旧应用没被回收。最后看引用链，对可疑加载器做引用分析，常见持有方是没停的线程、ThreadLocal、JMX、连接池、日志框架。验证方式是重部署前后各抓一次 histogram 或 dump 对比，也可以开 `-XX:+TraceClassLoading` 看重复加载。处理不是加 `MaxMetaspaceSize`，那是拖延，得把持有方切断。

**短版**

三步：Full GC 后 MC 不回落且类数阶梯上涨 → jmap -clstats 看加载器实例数异常 → 引用链找线程、ThreadLocal、JMX 等持有方；重部署前后抓 dump 对比验证。

**展开版**

- 机制链：重部署 → 新加载器加载新类 → 旧加载器若仍可达 → 其全部类无法卸载 → Metaspace 阶梯上涨。
- 关键结构：`jstat -gc` 的 MC/MU、`jcmd GC.class_stats`、`jmap -clstats` 每个加载器的 classes 计数。
- 触发条件：每次重部署后 MC 只增不减；Full GC 次数增加但回收量很小。
- 例外：动态代理、反射生成类也会让类数上涨，但那与重部署次数不相关，可用重部署前后对比排除。
- 对比取舍：dump 最准但代价大；clstats 轻量但只给统计，需要结合引用链。

**追问预判**

- 为什么 Full GC 也不掉 → 加载器被强引用持有，可达性没断，类元信息就不会被回收。
- 最常见的持有方是什么 → 自建线程池未 shutdown、ThreadLocal 未 remove、注册到 JMX/MBean、驱动注册。
- 不改代码能临时缓解吗 → 只能调大上限或减少重部署频率，属于兜底不是修复。

**常见错误答法**

- 直接答「加大 Metaspace」（只有结论、方向错）。
- 把类数量增长一律当成泄漏，不排除动态代理（层级缺失）。

**记忆锚点**

MC 不回落 → clstats 找加载器 → 引用链找持有方 → 前后 dump 对比 → 断引用而非调参。

### 10. 【必答】JIT：解释执行与编译执行如何切换？热点探测怎么判定？

**口述版**

HotSpot 默认是解释器和 JIT 混合执行。方法第一次调用走解释器，同时累加计数器，方法调用次数或循环回边次数到阈值就提交编译，由后台编译线程编成机器码放进 Code Cache，之后调用直接跑编译版本。热点判定有两种思路：基于采样的周期性看线程栈顶方法，开销小但不够精确，主要用来辅助决策；基于计数器的更常用，HotSpot 就是这种，方法调用计数器加回边计数器，阈值默认服务端一万次左右，具体以 `-XX:CompileThreshold` 和版本为准。回边计数到阈值会触发 OSR 栈上替换，让正在跑的长循环不用等方法返回就能切到编译版本。这个切换也不是单向的，编译版本的假设失效就会逆优化回解释执行。

**短版**

解释器先跑并计数，方法调用或回边计数到阈值就后台编译进 Code Cache，之后直接执行机器码；回边触发 OSR。假设失效会逆优化回解释执行。

**展开版**

- 机制链：解释执行 → 计数器累加 → 达阈值提交编译队列 → 后台 C1/C2 编译 → 安装机器码 → 后续调用走 compiled entry。
- 关键结构：方法调用计数器、回边计数器、`CompileThreshold`、Code Cache、`OnStackReplacePercentage`。
- 触发条件：调用次数达标、循环回边达标（OSR）、方法被标记为热点。
- 例外：计数器有热度衰减（`-XX:CounterHalfLifeTime`），长时间不调用会回退；`-Xint` 只解释，`-Xcomp` 只编译。
- 对比取舍：编译提升峰值性能但增加启动开销和内存；AOT 能省启动时间但优化深度不如 JIT。

**追问预判**

- 为什么需要解释器 → 启动快、省内存，还能在编译期间继续执行，并作为逆优化的退路。
- OSR 解决什么问题 → 长循环方法迟迟不返回，靠栈上替换让循环体尽快跑编译版本。
- 阈值能调小吗 → 能，但太小会编译大量一次性方法，挤占 Code Cache、拖慢启动。

**常见错误答法**

- 说「JVM 一启动就把所有代码编译好」（概念错）。
- 只背「热点代码编译」，说不出计数器和 OSR（只有结论）。

**记忆锚点**

解释器计数 → 调用/回边达阈值 → 后台编译进 Code Cache → OSR 救长循环 → 失效逆优化。

### 11. 【必答】JIT：C1 与 C2 的分工是什么？分层编译各层做了什么？

**口述版**

C1 是客户端编译器，编译快、优化浅，只做内联、去虚拟化、简单逃逸分析这类局部优化，产出代码质量一般但生成快，适合启动阶段。C2 是服务端编译器，编译慢但优化激进，会做全局逃逸分析、循环优化、向量化，峰值性能高。分层编译就是把两者串起来：零层解释执行，一层 C1 不做 profiling，二层 C1 只做方法调用和回边计数，三层 C1 做完整 profiling 收集类型和分支信息，四层交给 C2 编译。方法先在一二层快速拿到编译版本，攒够 profile 后升到四层换高质量代码，这样启动和峰值都能兼顾。JDK 8 起默认开启，可以用 `-XX:-TieredCompilation` 关掉。

**短版**

C1 编译快、优化浅、负责启动；C2 编译慢、优化激进、负责峰值。分层 0 解释、1/2/3 层 C1（2 收调用计数、3 收完整 profile）、4 层 C2。

**展开版**

- 机制链：0 层解释 → 1 层 C1 快速编译（无 profile）→ 2/3 层 C1 带 profile → 攒够数据后 4 层 C2 编译替换。
- 关键结构：每层有各自的调用阈值和解剖阈值（`Tier3InvocationThreshold`、`Tier4InvocationThreshold`）；JDK 9+ 用 `-XX:+PrintCompilation` 与 `-XX:+PrintInlining` 观察。
- 触发条件：默认 `-XX:+TieredCompilation`；服务端模式阈值较高。
- 例外：只开 `-XX:-TieredCompilation` 时直接 C2，启动变慢；`-Xint` 关闭全部编译。
- 对比取舍：分层换来启动与峰值的平衡，代价是 Code Cache 里同时存在多份代码、profile 有额外开销。

**追问预判**

- 为什么要有 2 层和 3 层 → 2 层只知道调用热度，3 层才收集类型和分支，C2 依赖这些数据做激进优化。
- 怎么观察实际走哪层 → `-XX:+PrintCompilation` 输出里的编译级别数字，配合 `jcmd Compiler.perfmap`。
- C2 一定更快吗 → 峰值更快，但编译耗时和内存更高，短生命周期任务反而 C1 更划算。

**常见错误答法**

- 说 C1 是「客户端用、C2 是服务端用」就结束，不讲分层（只有结论）。
- 把三层说成 C2 的早期优化（层级混淆）。

**记忆锚点**

C1 快而浅 → C2 慢而深 → 0 解释 / 1-3 C1 / 4 C2 → 先跑起来再换好代码。

### 12. 【必答】JIT：方法内联的条件有哪些？哪些写法会阻止内联？

**口述版**

内联是 JIT 里收益最大的优化，判断条件主要看大小、热度和类型确定性。大小上，普通方法默认超过 35 字节码就不内联，热点方法放宽到 325 左右，以 `-XX:MaxInlineSize`、`-XX:FreqInlineSize` 为准。热度上，调用次数够高才会被认真考虑。类型上，虚方法必须先确定实际接收者唯一，靠类型 profile 或类层次分析证明是单态，才能守护内联。会阻止内联的写法有：方法体太大、递归、虚方法多态明显、带复杂异常表、`synchronized` 方法在老版本、native 方法、以及被 `CompileCommand=dontinline` 标记。实践上想优化热点路径，就要压小方法体、避免深层继承导致的多态、别在热点循环里写巨大方法。

**短版**

看大小（默认 35 字节码，热点 325）、热度、类型确定性；方法过大、递归、多态、复杂异常表、dontinline 都会阻止内联。

**展开版**

- 机制链：调用点 profile → 判定单态/双态 → 检查字节码大小 → 满足则替换为方法体，必要时加类型守护。
- 关键结构：`MaxInlineSize`、`FreqInlineSize`、`MaxRecursiveInlineLevel`、`InlineSmallCode`。
- 触发条件：调用频繁且方法体小、接收者类型稳定。
- 例外：超小方法即使不热也会被早期内联；`@ForceInline` 仅对 JVM 内部注解生效。
- 对比取舍：激进内联增大 Code Cache 占用和编译时间，过度内联反而可能触发逆优化。

**追问预判**

- 为什么内联这么重要 → 消除调用开销，并把参数常量、字段值暴露给后续优化，是其他优化的前提。
- 怎么确认内联成功 → `-XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining` 看调用点标记。
- 大方法一定不内联吗 → 热点大方法在阈值内仍可内联，超过 `FreqInlineSize` 才放弃。

**常见错误答法**

- 只说「方法小就内联」（忽略热度与类型，只有结论）。
- 把内联说成 JVM 层面的手工优化选项（概念错）。

**记忆锚点**

大小 35/325 → 热度 → 单态守护 → 大方法/递归/多态/异常表阻止内联。

### 13. 【进阶】JIT：逃逸分析与标量替换解决什么问题？什么情况下失效？

**口述版**

逃逸分析判断一个对象会不会跑出方法或线程，分不逃逸、参数逃逸、全局逃逸三档。它的价值是让 JIT 敢做三件事：标量替换，把对象拆成几个局部变量，字段放进栈或寄存器，也就是常说的栈上分配；锁消除，对象只有本线程用，synchronized 直接去掉；还有减少 GC 压力。失效的情况很常见：对象被返回、赋给静态字段或成员字段、传给没被内联的方法、被其他线程看到，都会判成全局逃逸，只能老实堆分配。另外对象太大、字段被反射访问、数组元素不好拆，也会放弃标量替换。要注意所谓栈上分配在 HotSpot 里其实就是标量替换，并不存在真正的栈上对象。

**短版**

逃逸分析判断对象是否逃出方法/线程；不逃逸时可标量替换（字段进栈或寄存器）、锁消除、降 GC 压力。被返回、赋字段、传未知方法、跨线程即失效。

**展开版**

- 机制链：分析对象使用点 → 判定逃逸等级 → 不逃逸则拆字段为标量 → 消除分配与锁。
- 关键结构：逃逸状态 NotEscape / ArgEscape / GlobalEscape，`-XX:+DoEscapeAnalysis`、`-XX:+EliminateAllocations`、`-XX:+EliminateLocks`。
- 触发条件：对象生命周期完全在方法内、未被外部引用、方法被内联。
- 例外：同步块里的对象即使不逃逸，锁消除也要看是否真的无竞争；大对象仍可能留在堆上。
- 对比取舍：优化能省分配和 GC，但分析本身耗编译时间，且对多态、反射不友好。

**追问预判**

- 栈上分配是真的吗 → HotSpot 没有独立栈分配，靠标量替换把字段放到栈帧或寄存器。
- 为什么传到未内联方法就失效 → 编译器看不到被调方法里是否把引用存起来，只能保守判逃逸。
- 怎么验证 → `-XX:+PrintEliminateAllocations`，或对比 JMH 里开闭该参数的分配速率。

**常见错误答法**

- 说「对象一定分配在堆上」或「JDK 8 默认有栈上分配」（概念混淆）。
- 认为逃逸分析能减少对象大小（答非所问）。

**记忆锚点**

逃逸三档 → 不逃逸才拆 → 标量替换 + 锁消除 + 降 GC → 返回/存字段/跨线程即失效。

### 14. 【进阶】JIT：为什么微基准测试容易得出错误结论？JMH 解决了什么？

**口述版**

手写微基准最容易错在几件事上。一是没预热，前几轮还在解释执行，测的是解释器速度；二是 JIT 把结果当死代码消除，循环里算了不用，整段被优化掉；三是常量折叠和循环展开，编译器提前把计算做完，你测的根本不是那段逻辑；四是测量本身有开销，`System.currentTimeMillis` 精度不够，循环里的计时还干扰优化；五是 GC 和 CPU 频率漂移带来的噪声。JMH 就是把这些坑都封起来的框架：固定预热轮次让代码进入稳定编译状态，用 Blackhole 消费结果防止死代码消除，用 `@State` 管理共享变量和线程安全，默认 fork 独立进程隔离环境，最后给出均值、置信区间和吞吐量。所以微基准要么用 JMH，要么别下结论。

**短版**

常见坑：无预热、死代码消除、常量折叠、计时开销、GC 与频率噪声。JMH 用预热、Blackhole、@State、fork 进程和置信区间把这些问题封住。

**展开版**

- 机制链：JVM 优化（内联、常量折叠、死代码消除、循环展开）会让被测代码消失或变形 → 测量值偏离真实。
- 关键结构：`@Warmup`、`@Measurement`、`@Fork`、`@BenchmarkMode`、`Blackhole.consume`、`@State(Scope)`。
- 触发条件：任何纳秒到毫秒级、逻辑很小的性能对比。
- 例外：端到端压测、生产流量观测不属于微基准范畴，JMH 也不适用。
- 对比取舍：JMH 严谨但开发成本高，跑一次要分钟级；快速验证可以用简单循环，但只能看数量级。

**追问预判**

- Blackhole 为什么必要 → 结果不被使用会被 JIT 判定为死代码，整个计算被删掉。
- 为什么每个 benchmark 要 fork → 隔离前一个测试留下的 profile 和 Code Cache 状态。
- 单次运行能信吗 → 不能，要看多轮、多 fork 的置信区间，抖动大说明测量不稳。

**常见错误答法**

- 用一次 `System.nanoTime` 循环就下性能结论（方法错）。
- 认为加了预热就万事大吉（忽略死代码消除）。

**记忆锚点**

无预热 + 死代码 + 常量折叠 + 计时噪声 → JMH 预热 / Blackhole / State / Fork / 置信区间。

### 15. 【进阶】JIT：Code Cache 满了会怎样？逆优化什么时候发生？

**口述版**

Code Cache 存的是 JIT 编出来的机器码，满了之后编译器会被禁用，日志里会打 `CodeCache is full. Compiler has been disabled`，新方法不再编译，只能回解释执行，表现为吞吐明显下降、延迟抖动，但进程不会崩。默认大小在 64 位分层编译下大约 240MB，以版本为准，可以用 `-XX:ReservedCodeCacheSize` 调大，JDK 9+ 还分成 non-profiled、profiled、non-method 三段，并支持启发式清理。逆优化是编译时的乐观假设失效后回退，常见触发有：类层次变化导致单态变多态，走 uncommon trap；依赖的类或字段类型变了；Code Cache 清理把方法踢掉；还有编译级别降级。逆优化本身是正常机制，但频繁发生就意味着代码一直在编译和回退之间震荡，性能会抖。

**短版**

Code Cache 满则 JIT 停止编译、回退解释执行，吞吐下降；调 ReservedCodeCacheSize 并关注分段与清理。逆优化发生在类型假设失效、类层次变化、代码被清理时。

**展开版**

- 机制链：Code Cache 占用超阈值 → 触发清理或禁用编译 → 已编译方法被标记为不可用 → 走解释执行。
- 关键结构：`ReservedCodeCacheSize`、`InitialCodeCacheSize`、三个 CodeHeap 分段、`-XX:+PrintCodeCache`。
- 触发条件：大量动态生成类/方法、JSP 或脚本热加载、内联过深导致代码膨胀。
- 例外：JDK 9+ 的分段与清理策略能缓解，但清理本身也带来编译重做；AOT 不占这部分。
- 对比取舍：调大缓存能减少清理，但占用本机内存；过度内联会加速占满。

**追问预判**

- 怎么确认满了 → `jcmd Compiler.codecache` 或 `-XX:+PrintCodeCache`，看 used 是否接近 max。
- uncommon trap 是什么 → 编译代码里的守卫条件不成立时跳到慢路径，常见于类型假设被打破。
- 逆优化有害吗 → 偶发无害，高频说明代码形态不稳定，要检查类加载和调用点类型。

**常见错误答法**

- 说 Code Cache 满了会 OOM 或崩溃（事实错）。
- 把逆优化等同于 GC（概念混淆）。

**记忆锚点**

Code Cache 满 → 停编译 → 解释执行 → 吞吐掉；假设失效 / 类层次变 / 被清理 → 逆优化。

### 16. 【兜底】JIT：虚方法内联依赖什么？偏向锁被移除的背景是什么？

**口述版**

虚方法内联靠两样东西：类型 profile 和类层次分析。调用点会记录实际接收者类型，如果长期只有一个实现，就是单态，JIT 敢做守护内联，先假设是这个类型，用类型检查守住，成立就直接跑内联后的代码。类层次分析则是在整个已加载类的范围内确认某个虚方法只有一个实现，连检查都能省掉。假设一旦被打破，比如新加载了一个子类，就会走 uncommon trap 逆优化回解释器重新收集 profile，所以动态生成类多的系统容易内联失效。偏向锁被移除是另一条线：它的设计前提是「大多数锁只被一个线程反复获取」，但在现代应用里这个假设收益越来越小，撤销偏向的代价却很高，还要在安全点做 STW 式的批量撤销，维护复杂，又和值类型、虚拟线程等新特性冲突，所以 JDK 15 默认禁用，JDK 18 移除。

**短版**

虚方法内联靠调用点类型 profile 的单态/双态判断加守护，配合类层次分析；假设失效走 uncommon trap 逆优化。偏向锁因收益低、撤销成本高、维护复杂，JDK 15 禁用、18 移除。

**展开版**

- 机制链：调用点收集接收者类型 → 单态则守护内联 → 类型检查失败跳 uncommon trap → 逆优化并重收集。
- 关键结构：`TypeProfileWidth`（默认 2）、`-XX:+PrintInlining` 里的 `virtual call` 标记、CHA 依赖的类层次。
- 触发条件：调用点类型稳定、实现类已加载且无新子类。
- 例外：接口默认方法、Lambda 的 invokedynamic 走另一套链路；多态调用点（megamorphic）基本不内联。
- 对比取舍：守护内联收益大但依赖假设稳定；偏向锁本为无竞争同步省 CAS，现在普通锁路径已足够快。

**追问预判**

- megamorphic 是什么 → 一个调用点出现过多类型，profile 溢出后退化成查虚表，失去内联机会。
- 偏向锁撤销为什么要 STW → 批量撤销要遍历线程栈修改锁记录，只能在安全点做。
- 现在无竞争同步还快吗 → 快，轻量级锁加锁失败才膨胀，偏向锁的边际收益已不明显。

**常见错误答法**

- 说虚方法不能内联（事实错）。
- 把偏向锁移除归因于「锁有 bug」（原因错位）。

**记忆锚点**

类型 profile → 单态守护内联 → CHA 兜底 → 失效 uncommon trap；偏向锁收益低、撤销贵、维护难 → 移除。

## 三、JMM

### 17. 【必答】JMM：happens-before 有哪几条规则？

**口述版**

happens-before 是 JMM 给出的偏序保证，A 先于 B 意味着 A 的结果对 B 可见。核心几条：程序次序规则，同一线程里前面的操作先于后面的；监视器锁规则，解锁先于后续对同一把锁的加锁；volatile 规则，volatile 写先于后续对它的读；线程启动规则，start 先于线程内任何操作；线程终止规则，线程内所有操作先于 join 返回；中断规则，interrupt 调用先于被中断线程检测到中断；对象终结规则，构造完成先于 finalize 开始；最后是传递性，A 先于 B、B 先于 C，就推出 A 先于 C。

**短版**

程序次序、监视器锁、volatile、start、join、interrupt、finalize、传递性，共八条；核心是锁和 volatile 打跨线程的可见性边界。

**展开版**

- 机制链：这些规则构成偏序 → 满足规则的操作对不会被重排出可见性问题 → 不满足则结果不可预期。
- 关键结构：每条规则对应的同步动作：monitorenter/exit、volatile 读写、Thread.start/join/interrupt。
- 触发条件：跨线程共享可变数据时，必须存在一条从写到读的 happens-before 链。
- 例外：happens-before 不保证原子性，也不保证操作的真实执行顺序，只保证可见性结果。
- 对比取舍：用锁能一次覆盖多条规则但代价高；volatile 只覆盖单个变量，适合状态标志。

**追问预判**

- 没有 happens-before 一定会出错吗 → 不保证出错，但不保证正确，属于未定义行为。
- 传递性怎么用 → A 写 volatile 标志、B 读标志后再读普通字段，普通字段的写通过传递性可见。
- happens-before 和同步代码块关系 → 锁规则就是同步块的语义来源。

**常见错误答法**

- 说 happens-before 就是「代码按顺序执行」（概念错）。
- 只记住两三条且漏掉传递性（层级缺失）。

**记忆锚点**

程序次序 → 锁 → volatile → start → join → interrupt → finalize → 传递性。

### 18. 【必答】JMM：volatile 的语义是什么？为什么保证可见性和有序性，却保证不了原子性？

**口述版**

volatile 给的是可见性和有序性，不给原子性。可见性来自写必须刷到主内存、读必须重新从主内存拉，底层在 x86 上是一条带 lock 前缀的写指令，它会锁缓存行并把其他核里的副本置为无效，别的线程再读就得重新加载。有序性来自内存屏障，禁止编译器和 CPU 把 volatile 读写和前后操作乱序。不能保证原子性，是因为它只保证单次读或单次写原子，`i++` 是读、加、写三步，两个线程可能都读到旧值，最后只加了一次。要原子就得用 synchronized 或 AtomicInteger 的 CAS。

**短版**

可见性靠写刷主存、读重新拉，x86 上是 lock 前缀指令；有序性靠内存屏障；不保证原子性因为 `i++` 是读改写三步，需要 CAS 或锁。

**展开版**

- 机制链：volatile 写 → StoreStore 屏障 → 写主存并使其他核缓存行失效 → StoreLoad 屏障；volatile 读 → LoadLoad、LoadStore 屏障 → 从主存取值。
- 关键结构：JSR-133 定义的四种屏障、缓存行失效、`Unsafe` 的 volatile 读写、`VarHandle`。
- 触发条件：一写多读的状态标志、DCL 的实例引用、停止标志。
- 例外：long/double 的 volatile 读写保证原子，普通 long/double 在 32 位 JVM 上可能撕裂；volatile 不能替代复合操作的原子性。
- 对比取舍：volatile 比锁轻，适合单个标志；多变量需要一起保持一致时仍要用锁。

**追问预判**

- volatile 数组能保证元素可见吗 → 只保证数组引用的读写，元素要逐个用 volatile 或 Atomic 数组。
- 什么场景适合 volatile → 状态标志、单次发布、DCL 的引用。
- 为什么 volatile 读比写便宜 → 写要等屏障生效并让其他核失效，读主要禁止后续重排。

**常见错误答法**

- 说 volatile 能保证 `i++` 线程安全（事实错）。
- 只讲可见性不讲禁止重排（层级缺失）。

**记忆锚点**

可见性 + 有序性，无原子性 → lock 前缀 + 四种屏障 → 复合操作用 CAS。

### 19. 【必答】JMM：双重检查锁为什么必须加 volatile？

**口述版**

DCL 的问题出在 `new` 不是原子操作。它分三步：分配内存、调用构造器初始化、把引用赋给变量。后两步在单线程里可以重排，变成先赋引用再初始化。这时线程 A 已经拿到非 null 的引用，但对象字段还是默认值；线程 B 做外层判空发现不为空，直接返回这个半成品，用的时候可能拿到 0 或 null。加 volatile 就是禁止这个重排，写之前的操作不能排到写之后，构造器初始化必须在引用发布前完成，B 看到非空引用时对象一定已经初始化完整。所以 volatile 在这里不是为了可见性，主要是禁止重排。

**短版**

new 分分配、初始化、赋引用三步，后两步可重排，导致别的线程看到非空但未初始化的引用；volatile 禁止重排，保证发布前构造完成。

**展开版**

- 机制链：分配内存 → 初始化对象 → 引用赋值；无 volatile 时可能变成 1-3-2，外层判空直接返回半成品。
- 关键结构：实例字段的 volatile 写屏障、内层 `synchronized` 只保护首次创建。
- 触发条件：两次判空 + 懒加载 + 多线程首次访问。
- 例外：用静态内部类或枚举实现单例就不需要 DCL，也就没有这个问题。
- 对比取舍：DCL 兼顾懒加载与性能，但可读性差、易写错；内部类方案更简洁。

**追问预判**

- 第一次判空能不能去掉 → 能去掉，但每次都要抢锁，性能差。
- 不加 volatile 一定出错吗 → 取决于 JIT 和 CPU，可能长期跑不出来，属于未定义行为。
- 静态内部类为什么安全 → `<clinit>` 由 JVM 加锁，保证只执行一次且完全初始化后才可见。

**常见错误答法**

- 说 volatile 是为了「让实例可见」（只答对一半，漏掉重排）。
- 认为 synchronized 只加在内层就够了（忽略发布语义）。

**记忆锚点**

new = 分配 + 初始化 + 赋值 → 可能 1-3-2 → 半成品 → volatile 禁重排。

### 20. 【必答】JMM：synchronized 的可见性是怎么保证的？

**口述版**

synchronized 的可见性有两层来源。语义上，解锁会把工作内存里的共享变量刷回主内存，加锁时会清掉本地副本重新从主内存读，所以临界区里的修改对下一个拿到同一把锁的线程一定可见。规范上，JMM 的监视器锁规则规定解锁 happens-before 后续对同一把锁的加锁，再配合程序次序和传递性，就能推出前一个临界区的写对后一个临界区可见。所以它同时提供原子性和可见性，覆盖的是一整段代码而不是单个变量。要注意只有同一把锁才有这个保证，不同锁对象之间没有任何可见性关系。

**短版**

解锁刷回主存、加锁重新从主存读；监视器锁规则给出 unlock happens-before lock，配合传递性保证临界区写对下一个持有者可见。

**展开版**

- 机制链：monitorenter 获取锁并失效本地副本 → 执行临界区 → monitorexit 刷回并释放 → 下一个线程获取后重新读取。
- 关键结构：对象头 Mark Word 的锁标志、monitor、锁升级路径。
- 触发条件：多个线程对共享可变状态做复合操作。
- 例外：锁对象不一致等于没有同步；锁粗化、锁消除是 JIT 优化，不改变语义。
- 对比取舍：synchronized 覆盖原子性 + 可见性，使用简单；volatile 更轻但只管单变量。

**追问预判**

- synchronized 和 volatile 能不能互换 → 单变量状态可以，复合操作不行。
- 锁消除会不会破坏可见性 → 不会，只有证明对象不被共享时才会消除。
- 静态方法和实例方法的锁分别是什么 → 类对象和 this，两者互不排斥。

**常见错误答法**

- 只讲「加锁保证互斥」，不讲内存语义（层级缺失）。
- 认为只要用了 synchronized 其他线程就能立刻看到（忽略同一把锁的前提）。

**记忆锚点**

unlock 刷主存 → lock 重读 → 监视器锁规则 → 同一把锁才有效。

### 21. 【进阶】JMM：volatile 底层靠什么实现？内存屏障加在哪几个位置？

**口述版**

JMM 定义了四种屏障：LoadLoad、LoadStore、StoreStore、StoreLoad。volatile 的规则是写之前插 StoreStore，把前面的普通写都刷下去；写之后插 StoreLoad，这是最重的，保证这次写对后面的读写可见；读之后插 LoadLoad 和 LoadStore，保证后面的读写不能提到这次读之前。落到硬件上，x86 本身是强内存模型，只有 StoreLoad 需要显式保证，HotSpot 用一条带 lock 前缀的空操作指令实现，lock 会锁缓存行、让其他核副本失效，顺带起到全屏障作用，代价比其他屏障大，所以 volatile 写通常比读贵。ARM 这类弱内存模型就要真插多条屏障指令。

**短版**

写前 StoreStore、写后 StoreLoad；读后 LoadLoad + LoadStore。x86 用带 lock 前缀指令实现 StoreLoad，弱内存模型平台需要更多真实屏障。

**展开版**

- 机制链：字节码 putfield/getfield 带 ACC_VOLATILE → 解释器和 C2 生成屏障 → 平台相关指令。
- 关键结构：OrderAccess 里的 fence 实现、x86 的 `lock addl`、ARM 的 `dmb ish`。
- 触发条件：任何 volatile 字段的读写。
- 例外：JDK 9+ 用 VarHandle 的 acquire/release 语义，可以只加一半屏障；final 字段有单独的屏障策略。
- 对比取舍：StoreLoad 最贵，所以能用 release/acquire 的场景不要一律用 volatile 全屏障。

**追问预判**

- 为什么写后要 StoreLoad 而不是 StoreStore → 要防止写和后续读重排，StoreLoad 才能覆盖这个方向。
- 读后面为什么要两道 → 防止后续普通读写越过这次 volatile 读。
- 不同 CPU 实现一样吗 → 不一样，JMM 只规定语义，屏障数量由平台决定。

**常见错误答法**

- 说 volatile 直接操作主内存、绕过缓存（不准确）。
- 只记住「加内存屏障」说不出四种和位置（只有结论）。

**记忆锚点**

写前 SS、写后 SL；读后 LL + LS；x86 lock 前缀，弱内存模型多条屏障。

### 22. 【进阶】JMM：final 字段的内存语义？构造器里 this 逃逸会破坏什么？

**口述版**

final 的语义是：对象正确构造完成后，其他线程不需要同步就能看到 final 字段的初始化值。规范上，构造器里对 final 字段的写，和之后把对象引用赋给其他线程，这两步不能重排；读的时候也不会把 final 字段的读提到引用读之前。但前提是构造期间 this 没有逃逸。构造器里把 this 注册到监听器、启动一个线程、赋给静态字段，都属于 this 逃逸，其他线程可能在构造还没结束时就拿到引用，这时 final 字段可能还是默认值，语义就被破坏了。所以别在构造器里启动线程或对外发布 this，要发布就等构造完成之后。

**短版**

正确构造后无需同步即可见 final 值，构造器内 final 写不能重排到引用发布之后；this 提前逃逸则其他线程可能看到默认值，语义失效。

**展开版**

- 机制链：final 写 → 构造器结束处插 StoreStore → 引用发布；读侧加 LoadLoad，保证先读引用再读字段。
- 关键结构：`final` 修饰符、构造器返回前的屏障、`Unsafe.final` 语义、JDK 9+ VarHandle 的 getAcquire。
- 触发条件：发布不可变对象、DCL 单例、缓存里的不可变配置。
- 例外：通过反射修改 final 字段、反序列化绕过构造器，都会破坏这层保证。
- 对比取舍：final 提供免同步的不可变发布，代价是对象必须真正不可变，且不能在构造中泄露 this。

**追问预判**

- this 逃逸的典型写法 → 构造器里 `new Thread(this).start()`、注册监听、把 this 放入静态集合。
- final 集合能保证元素可见吗 → 只保证集合引用和内部结构正确发布，元素本身仍需安全发布。
- 为什么反射能改 final → 是 JVM 的例外通道，修改后语义不再受保证。

**常见错误答法**

- 认为 final 只是「不能改」（只讲语法，不讲内存语义）。
- 说加了 final 就能随便在构造器里发布 this（因果颠倒）。

**记忆锚点**

final 写不越过构造器 → 引用发布后才可见 → this 逃逸即失效。

### 23. 【进阶】JMM：指令重排有哪几种？as-if-serial 与 happens-before 是什么关系？

**口述版**

重排有三种：编译器重排，在不改变单线程语义的前提下调整指令顺序；CPU 的指令级并行重排，也就是乱序执行；内存系统的重排，写缓冲让写对其他核看起来延迟。as-if-serial 是单线程内的规则，有数据依赖就不能重排，没依赖随便重排，但结果必须和串行执行一致。happens-before 是跨线程的偏序，它不要求禁止所有重排，只要求前一个操作的结果对后一个可见。所以两者是不同层次：as-if-serial 保证单线程程序不被优化坏，happens-before 保证多线程之间该看见的能看见，JMM 就是在这对矛盾之间给出的最小保证。

**短版**

编译器重排、CPU 乱序、内存系统重排三类；as-if-serial 管单线程结果不变，happens-before 管跨线程可见，两者层次不同、可以并存。

**展开版**

- 机制链：源码 → 编译器优化重排 → CPU 乱序发射 → 写缓冲延迟可见 → 只有同步动作能建立可见性边界。
- 关键结构：数据依赖、控制依赖、四种内存屏障、JSR-133 的 happens-before 定义。
- 触发条件：多线程共享数据且缺少同步。
- 例外：单线程内无论怎么重排，可观测结果都不变，所以单线程程序不需要关心重排。
- 对比取舍：为了性能放开重排，为了正确性用 happens-before 约束关键路径，粒度越细性能越好。

**追问预判**

- 重排一定导致 bug 吗 → 只在多线程无同步访问共享数据时才暴露。
- as-if-serial 能跨线程用吗 → 不能，它只对单线程成立。
- 怎么禁止重排 → 用 volatile、锁、final 或 VarHandle 的 acquire/release 建立边界。

**常见错误答法**

- 把 as-if-serial 当作跨线程保证（概念混淆）。
- 只答「CPU 乱序」漏掉编译器和内存系统（层级缺失）。

**记忆锚点**

三类重排 → as-if-serial 保单线程 → happens-before 保跨线程 → JMM 取最小保证。

### 24. 【进阶】JMM：安全发布有哪几种方式？对象逸出常见形态有哪些？

**口述版**

安全发布就是让对象引用对其他线程可见时，对象已经完整构造。常见方式有：静态初始化器，类初始化由 JVM 加锁；用 final 字段配合正确构造；用 volatile 或 AtomicReference 发布引用；加锁发布；放进并发容器；以及不可变对象本身天然安全。常见的逸出形态有：构造器里把 this 传出去，比如注册回调、启动线程、加到静态集合；内部类隐式持有外部 this；方法返回可变的内部数组或集合；把 this 传给外部可重写方法。这些都会让对象在没构造完时被看到，volatile 也救不了，因为问题出在构造顺序而不是可见性。

**短版**

安全发布：静态初始化、final 字段、volatile/AtomicReference、加锁、并发容器、不可变对象。逸出：构造器发布 this、内部类持有、返回可变内部集合、传给可重写方法。

**展开版**

- 机制链：构造完成 → 建立 happens-before（锁 / volatile / final / 类初始化）→ 引用对其他线程可见。
- 关键结构：`final`、`volatile`、`ConcurrentHashMap`、`Collections.unmodifiableXxx`、`ThreadLocal` 不算发布。
- 触发条件：对象要被其他线程使用，且包含可变状态或初始化依赖。
- 例外：无状态对象、纯不可变对象不需要额外发布手段。
- 对比取舍：不可变对象最省心，代价是更新要创建新对象；锁发布最通用但开销最大。

**追问预判**

- 逸出和可见性问题的区别 → 逸出是对象过早暴露，根因在构造顺序；可见性是写没被看到。
- 双重检查锁属于哪种发布 → volatile 发布，兼顾懒加载。
- 构造函数里注册监听器为什么危险 → 监听器可能在构造回调时读到未初始化字段。

**常见错误答法**

- 认为「对象赋给静态字段」就完成了安全发布（缺少同步手段）。
- 把 ThreadLocal 当成发布方式（概念错）。

**记忆锚点**

静态初始化 / final / volatile / 锁 / 并发容器 / 不可变 → 别在构造器里交出 this。

### 25. 【进阶】JMM：单例的各种写法在 JMM 视角下分别有什么问题？

**口述版**

饿汉是类加载时创建，类初始化由 JVM 加锁，只执行一次，安全，缺点是不管用不用都创建。懒汉不做判空加锁是有竞态的，两个线程可能都创建一份；同步方法安全但每次都要抢锁。DCL 是两次判空加内层锁，问题在 new 的重排，必须给实例加 volatile，否则可能拿到半成品。静态内部类靠类初始化的锁，天然线程安全又懒加载，也没有锁开销。枚举最省心，JVM 保证实例唯一，还能防反射和反序列化破坏，因为反射创建枚举实例会直接抛异常。所以 JMM 视角下要关注的就两点：构造完成前不能发布引用，发布必须有 happens-before。

**短版**

饿汉安全但不懒；懒汉有竞态；同步方法安全但慢；DCL 必须 volatile 防重排；静态内部类安全且懒；枚举最稳，防反射与反序列化。

**展开版**

- 机制链：饿汉/内部类依赖 `<clinit>` 的锁 → DCL 依赖 volatile 写屏障 → 枚举依赖 JVM 对枚举的专门保证。
- 关键结构：`<clinit>` 初始化锁、volatile 引用、`Enum` 的 `values()` 与序列化 readResolve 机制。
- 触发条件：首次访问、并发首次访问、反射或反序列化攻击。
- 例外：多类加载器下「单例」不再唯一，每个加载器一份；分布式场景还要额外手段。
- 对比取舍：内部类写法可读性好，枚举最防攻击但不够灵活（不能懒加载大对象）。

**追问预判**

- 枚举为什么防反射 → `Constructor.newInstance` 对枚举类型直接抛 IllegalArgumentException。
- 内部类单例怎么防反射 → 防不了，反射仍可创建，需要构造器里加判断。
- 单例在多加载器下还有效吗 → 无效，类身份不同，各有一份。

**常见错误答法**

- 说 DCL 加 synchronized 就安全（漏掉 volatile）。
- 认为饿汉一定比懒汉差（忽略类初始化的零竞争优势）。

**记忆锚点**

类初始化锁 → volatile 禁重排 → 内部类两全 → 枚举最防攻击。

### 26. 【进阶】JMM：伪共享是什么？如何解决？

**口述版**

CPU 缓存以缓存行为单位，一般是 64 字节，多个线程修改同一缓存行里的不同变量，就会互相把对方的行标记失效，明明没共享数据，却像共享一样不停同步，这就是伪共享。它不会算错，但性能会掉得很难看，典型场景是多个线程各自累加一个紧挨着的计数器。解决办法是把热点变量隔开：字段填充，前后补空字段让它独占一行；JDK 8 起可以用 `@Contended` 注解，但要开 `-XX:-RestrictContended`；或者做线程本地累加，最后合并，LongAdder 就是分散热点再汇总的思路。

**短版**

多个线程写同一缓存行的不同变量，导致缓存行反复失效；用字段填充、@Contended 或 ThreadLocal/LongAdder 式的分散汇总解决。

**展开版**

- 机制链：线程 A 写变量 X → 该缓存行进入 Modified → 线程 B 所在核的同一行副本失效 → B 写 Y 触发重新加载，往复。
- 关键结构：缓存行大小（通常 64 字节，部分平台 128）、MESI 状态、`@sun.misc.Contended`。
- 触发条件：高并发写、变量在内存中相邻、缺少填充。
- 例外：只读共享不会伪共享；写频率低时影响可忽略。
- 对比取舍：填充浪费内存，`@Contended` 需额外参数，分散汇总更通用但读时要合并。

**追问预判**

- 怎么发现伪共享 → 性能分析里出现与业务无关的缓存未命中、扩展性差，可用 JMH 对比填充前后。
- LongAdder 为什么快 → 把计数分散到多个 Cell，减少同一行竞争，求和时再汇总。
- 缓存行大小怎么确认 → 一般 64 字节，ARM 部分平台更大，以硬件为准。

**常见错误答法**

- 把伪共享说成「两个线程真的共享了变量」（概念混淆）。
- 只说加锁解决（方向错，锁只会更慢）。

**记忆锚点**

64 字节缓存行 → 不同变量同行互相失效 → 填充 / @Contended / 分散汇总。

### 27. 【兜底】JMM：缓存一致性协议与 JMM 是什么关系？

**口述版**

两者不是一个层次。缓存一致性协议像 MESI 是硬件实现，负责让多核看到一致的物理内存；JMM 是 Java 语言级规范，定义线程之间通过哪些规则能保证可见性和有序性，它不绑定任何具体硬件。JMM 的做法是把抽象语义映射到内存屏障上，不同平台实现不一样，x86 是强内存模型需要屏障少，ARM 弱内存模型需要更多。所以 JMM 保证的是写出来的程序在所有符合规范的 JVM 上语义一致，缓存一致性只是底层实现的一部分，不能反过来当成 JMM。

**短版**

MESI 是硬件层的一致性实现，JMM 是语言层规范，通过内存屏障映射到不同硬件，二者不同层次，不能互相替代。

**展开版**

- 机制链：JMM 规则 → 编译器/解释器插入屏障 → 平台指令 → 触发缓存一致性动作。
- 关键结构：MESI 四态（Modified/Exclusive/Shared/Invalid）、store buffer、invalidate queue。
- 触发条件：多核共享数据写入。
- 例外：缓存一致性只保证单地址的最终一致，不保证跨地址顺序，顺序仍要靠屏障。
- 对比取舍：完全依赖硬件一致性无法表达语言语义；JMM 用最小屏障换取可移植性和性能。

**追问预判**

- 有缓存一致性为什么还要 volatile → 一致性不保证顺序和编译期重排，也不能阻止编译器缓存变量。
- JMM 只针对 Java 吗 → 是 Java 语言规范的一部分，Kotlin、Scala 跑在 JVM 上也遵守。
- 不同 JVM 实现必须一样吗 → 语义一样，底层实现可以完全不同。

**常见错误答法**

- 把 MESI 直接等同于 JMM（概念混淆）。
- 认为有了缓存一致性就不需要内存屏障（因果错）。

**记忆锚点**

MESI 管硬件一致 → JMM 管语言语义 → 屏障做映射 → 层次不同。

### 28. 【兜底】JMM：JSR-133 修复了 final 的什么问题？

**口述版**

旧内存模型有个漏洞：对象构造完、final 字段也写好了，但把引用交给另一个线程时，由于重排，那个线程可能先看到引用，读到的 final 字段却是默认值，等于 final 不 final。JSR-133 在 JDK 5 落地，给 final 加了专门语义：构造器内对 final 字段的写不能重排到引用发布之后，读也不能越过引用读提前，从而保证正确构造后无需同步就能看到 final 值。同时它还强化了 volatile，禁止 volatile 读写与普通读写重排，并修正了旧模型允许的「凭空出现值」问题，happens-before 规则也是这一版正式定义的。

**短版**

旧模型下 final 字段可能被看到默认值；JSR-133（JDK 5）禁止 final 写越过构造器发布，保证正确构造后无需同步可见，同时强化 volatile 并定义 happens-before。

**展开版**

- 机制链：构造器 final 写 → StoreStore 屏障 → 引用发布；读线程先读引用再加 LoadLoad，保证字段读取不提前。
- 关键结构：`final` 字段访问屏障、构造器结束屏障、JSR-133 的 happens-before 规则集。
- 触发条件：不可变对象跨线程发布。
- 例外：构造期间 this 逃逸、反射改 final、反序列化绕过构造器，仍不受保护。
- 对比取舍：新模型让不可变对象可以免同步共享，代价是构造器多一条屏障、编译优化空间略减。

**追问预判**

- 旧模型具体错在哪 → 允许 final 写和引用发布重排，读到未初始化值。
- 为什么 JDK 5 之前代码要小心 → 旧模型语义弱，依赖 final 的不可变假设可能不成立。
- 现在还需要关心吗 → 需要，this 逃逸和反序列化仍会破坏 final 语义。

**常见错误答法**

- 说 JSR-133 修复的是 volatile 性能（答非所问）。
- 认为有了 JSR-133 就万无一失（漏掉 this 逃逸的例外）。

**记忆锚点**

旧模型 final 可见默认值 → JSR-133 禁重排 → 构造完成即可见 → 强化 volatile + happens-before。

## 四、内存结构

### 29. 【必答】内存结构：JVM 运行时数据区有哪些？哪些线程私有、哪些共享？

**口述版**

运行时数据区分五块：程序计数器、虚拟机栈、本地方法栈、堆、方法区，另外还有不属于规范但一定会碰到的直接内存。线程私有的是程序计数器、虚拟机栈、本地方法栈；线程共享的是堆和方法区，方法区在 HotSpot 里 JDK 8 起由元空间实现。程序计数器记当前字节码行号，是唯一不会 OOM 的区域；栈里放栈帧，递归太深抛 StackOverflowError；堆放对象，是 GC 主战场；方法区放类元信息、运行时常量池。直接内存不受 JVM 管理，但用超了照样 OOM，Netty 用得多。

**短版**

私有：程序计数器、虚拟机栈、本地方法栈；共享：堆、方法区（JDK 8 起为元空间）。直接内存不属于数据区但会 OOM。

**展开版**

- 机制链：线程创建分配私有栈和 PC → 方法调用压栈帧 → 对象在堆分配 → 类元信息进方法区。
- 关键结构：栈帧（局部变量表、操作数栈、动态链接、返回地址）、堆（Eden/S0/S1/Old）、元空间。
- 触发条件：线程数、递归深度、对象分配速率、动态类生成量。
- 例外：HotSpot 把本地方法栈与虚拟机栈合并；G1 下分代只是逻辑概念，物理上是 Region。
- 对比取舍：堆越大 GC 停顿越长；栈越大线程数越少，按并发量权衡。

**追问预判**

- 程序计数器为什么不会 OOM → 它只存一个行号偏移，大小固定且随线程创建一次分配。
- 方法区是堆的一部分吗 → 规范上不是，逻辑上属方法区；元空间用的是本地内存。
- 哪个区域最容易 OOM → 堆最常见，其次是元空间和直接内存。

**常见错误答法**

- 把方法区说成堆的一部分（概念混淆，规范与实现混为一谈）。
- 漏掉直接内存（层级缺失，排查题会露馅）。

**记忆锚点**

私有 PC/栈/本地栈 → 共享堆/方法区 → 直接内存额外算 → PC 唯一不 OOM。

### 30. 【必答】内存结构：堆为什么分代？对象在 Eden、S0、S1、Old 之间怎么流转？

**口述版**

分代的理论基础是两个假说：绝大多数对象朝生夕死，熬过越多次 GC 的对象越难死。所以新生代用复制算法，只复制少量存活对象，成本低；老年代用标记-清除或标记-整理，避免反复复制大量长寿命对象。流转是这样的：对象优先在 Eden 分配，Eden 满触发 Minor GC，存活对象复制到 Survivor 并把年龄加一，两个 Survivor 轮换使用；年龄到阈值默认 15 就晋升老年代；大对象可能直接进老年代；Survivor 放不下或者动态年龄判定触发，也会提前晋升。G1 下没有物理连续的新生代，只是按 Region 逻辑划分。

**短版**

两个假说决定分代；Eden 满触发 Minor GC，存活对象进 Survivor 年龄加一，默认 15 岁晋升；大对象、Survivor 放不下、动态年龄判定都提前晋升。

**展开版**

- 机制链：Eden 分配 → Minor GC → 存活对象复制到空的 Survivor → 年龄 +1 → 达到阈值或空间不足 → 晋升 Old。
- 关键结构：Eden : S0 : S1 = 8 : 1 : 1，新生代 : 老年代 = 1 : 2，`MaxTenuringThreshold`、`PretenureSizeThreshold`。
- 触发条件：Eden 满、Survivor 空间不足、动态年龄判定、大对象分配。
- 例外：G1 中是 Region 逻辑分代；ZGC 新一代不再严格按 Eden/Survivor 划分。
- 对比取舍：分代提升回收效率，代价是跨代引用要维护卡表 / RSet，且有晋升开销。

**追问预判**

- 为什么 Survivor 只有 10% → 假设存活对象很少，复制成本低，省下的空间给 Eden 提高分配效率。
- 对象一定在 Eden 出生吗 → 不一定，大对象可直入老年代，TLAB 也在 Eden 内。
- 晋升阈值能调大吗 → 能，但受对象头 4 位年龄限制，最大 15。

**常见错误答法**

- 说「新生代和老年代各占一半」（参数错）。
- 只讲复制算法，不讲晋升路径（机制链断裂）。

**记忆锚点**

两个假说 → Eden 出生 → Minor GC 进 Survivor → 年龄 +1 → 15 岁或放不下晋升。

### 31. 【必答】内存结构：对象布局是什么？Mark Word 存了哪些信息？

**口述版**

对象布局分三块：对象头、实例数据、对齐填充。对象头里 Mark Word 占 8 字节，存 hashCode、分代年龄、锁状态标志、偏向线程 ID 这些，它们是复用同一块空间的，不同锁状态下含义不同；对象头还有类型指针指向类元信息，开压缩指针是 4 字节，数组再多 4 字节长度。实例数据按字段类型和顺序排布，父类字段在前。最后对齐填充补到 8 字节整数倍，所以 `new Object()` 在 64 位、开压缩指针下是 16 字节。

**短版**

对象头（Mark Word 8 字节 + 类型指针 4/8 字节 + 数组长度）+ 实例数据 + 对齐填充；Mark Word 复用存 hashCode、年龄、锁标志、偏向线程 ID。

**展开版**

- 机制链：分配时写 Mark Word（初始无锁、hash 未计算）→ 加锁升级改写标志位 → 对象移动时由 GC 更新转发指针。
- 关键结构：64 位 Mark Word 大致为 hash 31 位、分代年龄 4 位、偏向标志 1 位、锁标志 2 位，其余按状态复用。
- 触发条件：调用 `hashCode()` 才真正写入 hash；锁升级才改变标志位。
- 例外：偏向锁已移除（JDK 15 禁用、18 移除），相关位不再使用；轻量级锁下存栈中锁记录指针。
- 对比取舍：Mark Word 只有 8 字节，所以 hash、年龄、锁信息只能复用，代价是某些组合互斥。

**追问预判**

- 为什么 hashCode 调用后才写入 → 默认是惰性计算，省一次计算，也让 Mark Word 空出来存锁信息。
- 数组对象头多什么 → 多 4 字节数组长度，实例数据里才是元素。
- 对象大小为什么必须 8 字节对齐 → 方便指针压缩用低 3 位做位移编码，也便于内存管理。

**常见错误答法**

- 说 Mark Word 里同时存 hash 和锁信息且互不影响（忽略复用）。
- 漏掉数组长度字段（细节缺失）。

**记忆锚点**

头 + 实例 + 填充 → Mark Word 8 字节复用 → 类型指针 4 字节（压缩）→ 补齐 8 的倍数。

### 32. 【必答】内存结构：对象创建经过哪几步？指针碰撞与空闲列表分别适用什么场景？

**口述版**

创建大概五步：先做类加载检查，new 对应的类没加载就先加载；然后分配内存，堆规整时用指针碰撞，把指针往空闲一侧移动对象大小就行，不规整时用空闲列表，从列表里找一块够大的；分配要考虑并发，靠 TLAB 让每个线程先在 Eden 领一块私有区域，用完再用 CAS 加重试；接着把实例字段初始化为零值；再设置对象头；最后执行构造方法。所以对象在构造方法执行前就已经存在，字段是零值，这也是为什么构造器里能看到字段的默认值。

**短版**

类加载检查 → 分配内存（规整用指针碰撞、不规整用空闲列表，并发靠 TLAB + CAS）→ 零值初始化 → 设置对象头 → 执行构造方法。

**展开版**

- 机制链：new 指令 → 常量池定位类 → 检查加载 → 计算大小 → 分配 → 置零 → 设头 → `<init>`。
- 关键结构：`TLAB`、`CAS` + 失败重试、`-XX:+UseTLAB`、`-XX:PretenureSizeThreshold`。
- 触发条件：任何 new、反射 newInstance、克隆、反序列化。
- 例外：TLAB 剩余空间不够时退化到共享 Eden 加锁分配；大对象可能直接进老年代。
- 对比取舍：指针碰撞快但要求堆规整（有压缩的收集器）；空闲列表通用但需要维护结构。

**追问预判**

- 哪些收集器用指针碰撞 → Serial、Parallel、G1 这类会整理的，空闲空间连续。
- CMS 为什么用空闲列表 → 标记-清除不压缩，空间碎片化。
- TLAB 用完了怎么办 → 当前 TLAB 退役，申请新的，或退化到共享堆用 CAS 分配。

**常见错误答法**

- 把「执行构造方法」放在分配内存之前（顺序错）。
- 认为对象字段一开始就是代码里的初值（忽略零值初始化）。

**记忆锚点**

检查 → 分配（碰撞/列表 + TLAB）→ 置零 → 设头 → 构造。

### 33. 【必答】内存结构：一个对象占多少字节？怎么算出来？

**口述版**

算对象大小就是对象头加实例数据再加对齐填充。64 位 HotSpot 默认开压缩指针，Mark Word 8 字节、类型指针 4 字节，头是 12；字段按类型占位，boolean、byte 是 1 字节，char、short 2 字节，int、float 4 字节，long、double 8 字节，引用 4 字节；父类字段也算进来，最后补齐到 8 的倍数。比如 `new Object()` 是 8 加 4 等于 12，补到 16。实际算的时候别手算，用 JOL 直接打印更可靠，字段重排还会影响结果。

**短版**

对象头（12 字节含压缩指针）+ 字段大小 + 对齐填充到 8 的倍数；`new Object()` 为 16 字节；用 JOL 验证，字段重排会影响结果。

**展开版**

- 机制链：JVM 按字段类型和对齐规则布局 → 父类字段先排 → 可能重排字段减少填充 → 总长补齐 8 的倍数。
- 关键结构：`-XX:+UseCompressedOops`、`-XX:+UseCompressedClassPointers`、`jol-cli`、`Unsafe.objectFieldOffset`。
- 触发条件：评估缓存容量、序列化大小、大对象阈值。
- 例外：关闭压缩指针后引用变 8 字节；数组还要加 4 字节长度；内部类可能带外部引用。
- 对比取舍：压缩指针省内存但限制堆在 32G 内；字段重排省空间但反射按名字访问不受影响。

**追问预判**

- 为什么是 16 而不是 12 → 对象起始地址要 8 字节对齐，12 补到 16。
- 引用类型的字段多大 → 开压缩指针 4 字节，否则 8 字节。
- 数组对象头多大 → 12 加 4 字节长度，再按元素大小和填充计算。

**常见错误答法**

- 直接答「对象头 8 字节」（漏掉类型指针）。
- 忘记对齐填充，算出 12 字节（细节遗漏）。

**记忆锚点**

头 12 + 字段 + 填充 → 8 对齐 → Object 16 字节 → JOL 实测。

### 34. 【进阶】内存结构：栈帧由什么组成？栈溢出和栈帧是什么关系？

**口述版**

栈帧由局部变量表、操作数栈、动态链接、方法返回地址和附加信息组成。局部变量表按槽位存 this、参数和局部变量，long 和 double 占两个槽；操作数栈是执行字节码的工作区；动态链接指向运行时常量池里该方法的符号引用；返回地址记录调用方下一条指令。每次方法调用压一个栈帧，调用链太深或者递归没有出口，栈空间用完就抛 StackOverflowError。这是栈溢出，不是堆 OOM，两者要分清。栈大小由 `-Xss` 控制，默认一般 1M，线程多的时候调小反而能开更多线程。

**短版**

栈帧 = 局部变量表 + 操作数栈 + 动态链接 + 返回地址 + 附加信息；调用太深或无限递归撑满 `-Xss` 就抛 StackOverflowError。

**展开版**

- 机制链：方法调用 → 分配栈帧 → 参数和局部变量入局部变量表 → 字节码在操作数栈上运算 → 返回后弹出栈帧。
- 关键结构：局部变量表槽位（32 位一槽）、操作数栈深度在编译期已确定（`max_stack`、`max_locals`）。
- 触发条件：递归无终止、调用链极深、`-Xss` 太小。
- 例外：栈能动态扩展但受 `-Xss` 上限约束；本地方法栈溢出在 HotSpot 里表现类似。
- 对比取舍：`-Xss` 调大能扛更深递归但减少可创建线程数；线程池场景要权衡。

**追问预判**

- 为什么递归会栈溢出 → 每层调用都保留栈帧不释放，超过 `-Xss` 上限。
- 栈溢出会 OOM 吗 → 通常是 StackOverflowError；创建线程失败才是 `unable to create native thread`。
- 局部变量表里的对象会影响 GC 吗 → 会，局部变量表是 GC Roots 的一部分，但失效槽位可能被复用。

**常见错误答法**

- 把栈溢出和堆 OOM 混为一谈（概念混淆）。
- 认为调大 `-Xss` 没有代价（缺少取舍）。

**记忆锚点**

局部变量表 + 操作数栈 + 动态链接 + 返回地址 → 深调用即溢出 → `-Xss` 权衡。

### 35. 【进阶】内存结构：指针压缩的原理和 32GB 边界是怎么回事？

**口述版**

指针压缩利用的是对象地址 8 字节对齐。64 位引用理论上要 8 字节，但对象起始地址低三位一定是 0，所以可以只存 32 位，解码时左移 3 位，等于把 32 位能表示的 4G 个地址乘以 8，得到 32G 的寻址范围，这就是 32GB 边界。堆一旦超过 32G 压缩就失效，引用退回 8 字节，对象变大、缓存命中率下降，性能可能反而比小堆差，所以堆不要轻易越过这条线。它靠堆基址加偏移的方式寻址，JDK 8 起默认开启，另外还有一块 Compressed Class Space 专门放压缩后的类指针，默认 1G。

**短版**

对象 8 字节对齐，低 3 位可省，32 位存偏移、左移 3 位还原，寻址上限 32G；超过后压缩失效、引用变 8 字节，性能可能回退。

**展开版**

- 机制链：引用存 32 位偏移 → 读时 `base + (ref << 3)` → 还原真实地址。
- 关键结构：`-XX:+UseCompressedOops`、`-XX:HeapBaseMinAddress`、`CompressedClassSpaceSize`（默认 1G）。
- 触发条件：堆 ≤ 约 32G 时自动开启（JDK 8+ 默认）。
- 例外：堆超过 32G 自动关闭；`-XX:-UseCompressedOops` 可手动关；类指针空间与堆空间是两块。
- 对比取舍：压缩省 30% 左右引用空间、提升缓存命中，代价是堆上限受限、多一次位移计算。

**追问预判**

- 为什么是 32G 而不是 4G → 32 位偏移乘 8 字节对齐单位，等于 32G 地址空间。
- 堆 40G 一定更差吗 → 不一定，但失去压缩后对象变大，通常不如两个 20G 实例。
- Compressed Class Space 是什么 → 压缩后的类元信息指针存放区，单独限额，满了报错不同。

**常见错误答法**

- 说「32G 是 JVM 堆的硬上限」（事实错，只是压缩失效）。
- 认为压缩指针能压缩对象本身（概念错，压的是引用）。

**记忆锚点**

8 字节对齐 → 省低 3 位 → 32 位偏移 × 8 = 32G → 超过即失效 → 类指针单独 1G。

### 36. 【进阶】内存结构：TLAB 是什么？为什么需要？何时退化到共享堆分配？

**口述版**

TLAB 是线程本地分配缓冲，每个线程在 Eden 里预先领一小块私有区域，new 对象时在自己的 TLAB 里用指针碰撞直接分配，不需要和其他线程抢 Eden 的公共指针。它的价值是在高并发下消除分配锁，分配只是移动指针，速度很快，是新生代分配的主要方式。退化发生在两种时候：TLAB 剩余空间放不下当前对象，先申请新的 TLAB，申请失败就退化到共享 Eden，用 CAS 加失败重试；对象本身太大，TLAB 装不下，也会直接走共享分配，甚至按大对象规则进老年代。TLAB 默认开启，可以调大小和浪费比例，剩下的碎片叫 TLAB waste。

**短版**

线程在 Eden 预领一块私有区域，用指针碰撞免锁分配；剩余空间不足或对象太大时退化到共享 Eden 的 CAS 分配。

**展开版**

- 机制链：线程启动/首次分配 → 申请 TLAB → 指针碰撞分配 → 空间不足 → 退役并申请新 TLAB → 失败则共享分配。
- 关键结构：`-XX:+UseTLAB`、`-XX:TLABSize`、`-XX:TLABWasteTargetPercent`、`-XX:MinTLABSize`。
- 触发条件：所有普通对象分配；大对象绕过 TLAB。
- 例外：关闭 TLAB 后全部走 CAS；G1 里 TLAB 同样基于 Region 分配。
- 对比取舍：TLAB 提升并发分配效率，代价是每个线程浪费一点空间，线程多时浪费累积。

**追问预判**

- TLAB 会触发 GC 吗 → 不会，它只是 Eden 的切片，Eden 满才触发 Minor GC。
- TLAB 太小有什么问题 → 频繁申请和浪费，退化到共享分配的概率上升。
- 怎么观察 TLAB 浪费 → `-XX:+PrintTLAB` 或 GC 日志里的 waste 统计。

**常见错误答法**

- 说 TLAB 是「栈上分配」（概念混淆）。
- 认为 TLAB 能解决对象逃逸（答非所问）。

**记忆锚点**

Eden 切片 → 指针碰撞免锁 → 空间不足/大对象退化 → 共享 CAS。

### 37. 【进阶】内存结构：对象头里的 hashCode、锁标志、分代年龄怎么复用？

**口述版**

这三样是挤在 Mark Word 这 8 字节里复用的。hashCode 占 31 位，只在调用 `hashCode` 或 `System.identityHashCode` 之后才写入，之前这块空间可以存别的。分代年龄只有 4 位，所以最大 15，这也是 `MaxTenuringThreshold` 的上限。锁标志占 2 位，区分无锁、轻量级锁、重量级锁、GC 标记这几种状态。问题在于它们互斥：一旦算过 hash，hash 就固定不能改；锁升级时 Mark Word 整体换形态，比如轻量级锁会把原内容拷到栈上的锁记录，Mark Word 只留指向锁记录的指针。所以这是典型的用空间复用换对象头的小体积。

**短版**

同一块 8 字节按状态复用：hash 31 位（惰性写入）、年龄 4 位（上限 15）、锁标志 2 位；锁升级时整体换形态，原内容搬到栈上锁记录。

**展开版**

- 机制链：新建对象无锁 + hash 未计算 → 调 hashCode 写入并固定 → 加锁时按竞争程度升级并改写位域。
- 关键结构：Mark Word 位布局（hash、age、biased_lock、lock）、栈上 Lock Record、monitor 指针。
- 触发条件：调用 `hashCode()`、进入 synchronized、发生 GC 标记。
- 例外：偏向锁已移除，相关位不再使用；重锁后 Mark Word 指向 ObjectMonitor。
- 对比取舍：复用让对象头只有 8 字节，代价是 hash 与锁状态互相牵制，例如算过 hash 后偏向撤销更麻烦。

**追问预判**

- 为什么年龄最多 15 → 只有 4 位，二进制最大 1111，对应 `MaxTenuringThreshold` 上限。
- 算过 hashCode 还能偏向吗 → 历史上偏向锁会忽略 hash，二者不能共存，这也是偏向锁被移除的原因之一。
- GC 时 Mark Word 怎么变 → 存转发指针，指向对象的新地址。

**常见错误答法**

- 说 Mark Word 同时完整保存所有信息（忽略复用与互斥）。
- 认为分代年龄可以随意调到 20（超出位宽）。

**记忆锚点**

8 字节复用 → hash 31 / age 4 / lock 2 → 锁升级换形态 → 原内容进栈。

### 38. 【进阶】内存结构：直接内存和堆内存是什么关系？Netty 为什么用它？

**口述版**

直接内存是 NIO 的 DirectByteBuffer 通过 Unsafe 分配的堆外内存，不在堆里，不受 GC 直接管理，但仍然算进程内存，用 `-XX:MaxDirectMemorySize` 限制，默认约等于最大堆。关系上，堆里只有一个 DirectByteBuffer 对象，真正的数据在堆外，靠虚引用加 Cleaner 在对象被回收时释放。Netty 用它主要两个原因：一是零拷贝，堆外内存做 IO 不用先把数据拷到临时堆外缓冲，少一次复制；二是地址稳定，堆内大数组在 GC 时可能被移动，JNI 访问要 pin 住或者复制，堆外地址不会动。代价是分配释放比堆慢，泄漏了不好查，要看 NMT 或 PooledByteBufAllocator 的指标。

**短版**

堆里只有 DirectByteBuffer 对象，数据在堆外，靠 Cleaner 释放，受 MaxDirectMemorySize 限制；Netty 用它是为了零拷贝和地址稳定，代价是分配慢、泄漏难查。

**展开版**

- 机制链：`ByteBuffer.allocateDirect` → Unsafe 分配 → 堆内对象持有地址 → 不可达后 Cleaner 调 `free` → 归还内存。
- 关键结构：`MaxDirectMemorySize`、Cleaner / PhantomReference、`PlatformDependent`、池化 ByteBuf。
- 触发条件：NIO 读写、Netty 网络传输、大文件映射。
- 例外：`MappedByteBuffer` 属 mmap，释放受文件映射影响；JDK 9+ 可用 `Cleaner` API 显式清理。
- 对比取舍：堆外省一次拷贝、避免 GC 移动，但分配贵、排查难，小对象不值得。

**追问预判**

- 为什么堆外内存也会 OOM → 它占进程地址空间和物理内存，超限抛 `Direct buffer memory`。
- 怎么排查堆外泄漏 → NMT 的 `Internal`/`Other` 分类、`BufferPoolMXBean`、Netty 的泄漏检测级别。
- 为什么堆内数组不能直接给 JNI → GC 会移动对象，JNI 需要固定地址，只能 pin 或复制。

**常见错误答法**

- 说直接内存「不受任何限制」（忽略 MaxDirectMemorySize）。
- 认为 Netty 用堆外只是为了快，讲不出零拷贝和地址稳定（只有结论）。

**记忆锚点**

堆内一个壳、数据在堆外 → Cleaner 释放 → 零拷贝 + 地址稳定 → 分配贵、泄漏难查。

### 39. 【进阶】内存结构：大对象直接进老年代吗？动态年龄判定和空间分配担保是什么？

**口述版**

大对象不一定直接进老年代，取决于收集器和参数。Parallel、Serial 里 `PretenureSizeThreshold` 设了，超过阈值才直接进老年代，没设就还是 Eden；G1 里是超过 Region 一半就进 Humongous Region。动态年龄判定发生在 Minor GC 后：Survivor 里某个年龄及以下的对象总大小超过 Survivor 的一半，那么大于等于这个年龄的对象就不用等 15 岁，直接晋升，这个比例由 `TargetSurvivorRatio` 控制，默认 50。空间分配担保是 Minor GC 前的检查，看老年代最大连续可用空间够不够，不够就先做一次 Full GC 再决定；JDK 6 之后只要老年代连续空间大于新生代总量或者历次晋升平均值，就允许担保。

**短版**

大对象只在设了 `PretenureSizeThreshold`（或 G1 超 Region 一半）时才直入老年代；动态年龄判定按 Survivor 一半阈值提前晋升；分配担保检查老年代空间不足则先 Full GC。

**展开版**

- 机制链：分配大对象 → 比较阈值 → 直入老年代或 Eden → Minor GC 后统计各年龄总大小 → 超过一半则提前晋升。
- 关键结构：`PretenureSizeThreshold`、`TargetSurvivorRatio`、`MaxTenuringThreshold`、老年代连续空间。
- 触发条件：大数组、大缓存对象；Survivor 中同龄对象堆积；老年代碎片化。
- 例外：G1 的 Humongous 分配在 Region 中，可能连续多个 Region；ZGC 无传统晋升概念。
- 对比取舍：提前晋升减少复制次数，但加速老年代填满；担保失败触发 Full GC 代价大。

**追问预判**

- 动态年龄判定是「大于」还是「大于等于」 → 通常按年龄从小到大累加，超过一半后该年龄及以上晋升，细节以实现为准。
- 为什么大对象不愿留在新生代 → 复制成本高，且容易挤爆 Survivor。
- 担保失败会怎样 → 退化为 Full GC，停顿变长。

**常见错误答法**

- 答「大对象一定直接进老年代」（绝对化，忽略参数）。
- 把动态年龄判定说成「年龄到了 15 就晋升」（混淆两条规则）。

**记忆锚点**

大对象看阈值 → 动态年龄看 Survivor 一半 → 担保看老年代连续空间。

### 40. 【进阶】内存结构：逃逸分析带来的栈上分配、标量替换会改变对象布局吗？

**口述版**

标量替换不改变对象布局的定义，改变的是分配方式。对象布局还是对象头、实例数据、填充这三段，只是 JIT 判断对象不逃逸后，干脆不创建这个对象，把它的字段拆成独立的标量放进栈帧或者寄存器，访问字段就变成访问局部变量。所以对象从来没有在堆上出现过，也就谈不上布局。所谓栈上分配，在 HotSpot 里就是标量替换的效果，不是真的在栈上放一个完整对象。失效的时候，比如对象被返回、被存进字段、传给未内联的方法，JIT 只能老实堆分配，布局照旧。

**短版**

不改变布局，只改变分配方式：不逃逸就不创建对象，字段拆成标量进栈或寄存器；堆分配时布局仍是头 + 实例 + 填充。

**展开版**

- 机制链：逃逸分析判定不逃逸 → 字段拆为标量 → 消除对象分配 → 锁消除 → 减少 GC。
- 关键结构：`DoEscapeAnalysis`、`EliminateAllocations`、`EliminateLocks`、`PrintEliminateAllocations`。
- 触发条件：对象生命周期完全在方法内、字段可拆、方法已内联。
- 例外：数组通常不能整体标量替换（元素数量不定）；大对象、反射访问字段会放弃。
- 对比取舍：优化省分配和 GC，但依赖内联和类型稳定，动态性强时收益有限。

**追问预判**

- 标量替换后对象还能被 synchronized 吗 → 不能，对象不存在；只有证明无竞争时才做锁消除。
- 为什么说「栈上分配」是俗称 → HotSpot 没有独立栈分配实现，效果来自标量替换。
- 怎么验证 → `-XX:+PrintEliminateAllocations` 看分配是否被消除。

**常见错误答法**

- 说「栈上分配就是在栈上创建完整对象」（实现事实错）。
- 认为逃逸分析会改变 Mark Word 或字段顺序（概念混淆）。

**记忆锚点**

不逃逸 → 拆标量 → 不建对象 → 布局规则不变 → 堆分配照旧。

### 41. 【进阶】内存结构：永久代为什么被元空间取代？

**口述版**

永久代被替换的核心原因是它把方法区实现成堆内一块固定大小的区域，大小很难预估，类多、动态生成类多就容易 PermGen space OOM，而且它受堆大小和 GC 分代管理约束，调优很别扭。JDK 7 先把字符串常量池和静态变量挪到堆，JDK 8 正式用元空间取代，元空间用本地内存，默认只受本机内存限制，不再和堆抢空间，类元信息可以更灵活地回收。另外永久代的回收和 Full GC 绑在一起，元空间可以独立触发类卸载。代价是要自己设 `MaxMetaspaceSize`，否则可能把本机内存吃光。

**短版**

永久代位于堆内、固定大小、难预估，易 PermGen OOM；元空间改用本地内存，默认只受本机内存限制，类卸载更独立，但需设 MaxMetaspaceSize 兜底。

**展开版**

- 机制链：JDK 7 迁移字符串常量池和静态变量 → JDK 8 移除永久代 → 类元信息进元空间 → 本地内存按需增长。
- 关键结构：`MetaspaceSize`（首次高水位）、`MaxMetaspaceSize`、`CompressedClassSpaceSize`。
- 触发条件：动态类生成多、热部署频繁、类加载器泄漏。
- 例外：元空间不是无限，仍会抛 `Metaspace` OOM；压缩类空间单独限额。
- 对比取舍：换本地内存解决容量与调优问题，代价是内存不再受堆上限保护，需要监控。

**追问预判**

- JDK 7 为什么先移字符串常量池 → 它在永久代里 GC 效率低，移到堆可随 Minor GC 回收。
- 元空间会 Full GC 吗 → 触发类卸载的 GC 会被 Metaspace 阈值触发，但不等同于堆的 Full GC。
- 不设上限有什么风险 → 类泄漏时吃光本机内存，容器里可能被 OOM Kill。

**常见错误答法**

- 说元空间就是「无限大」（错误，受本机内存和参数限制）。
- 把永久代问题只说成「容量小」（遗漏堆内管理和 Full GC 绑定）。

**记忆锚点**

堆内固定 → 难预估 OOM → 元空间用本地内存 → 独立卸载 → 需设上限。

### 42. 【兜底】内存结构：字符串常量池、运行时常量池、class 常量池有什么区别？

**口述版**

这是三个不同层次的东西。class 常量池是字节码文件里的那张表，编译期就确定，存字面量和符号引用，比如类名、方法名、字段描述符。运行时常量池是类加载后把 class 常量池搬到方法区的产物，JDK 8 起在元空间，除了符号引用，还能在运行期动态添加，比如 `String.intern` 的结果。字符串常量池是专门存字符串字面量的缓存，JDK 7 起挪到堆里，本质是一个 StringTable，用 intern 可以把字符串引用放进去复用。关系是：class 常量池是源头，运行时常量池是运行期视图，字符串常量池是其中特殊的一部分，而且它在堆里，受 GC 管理。

**短版**

class 常量池在字节码文件里（字面量 + 符号引用）；运行时常量池在方法区（JDK 8 起元空间），可动态添加；字符串常量池在堆里，是 StringTable，支持 intern 复用。

**展开版**

- 机制链：编译生成 class 常量池 → 类加载解析进运行时常量池 → 字符串字面量登记进 StringTable。
- 关键结构：`CONSTANT_Utf8`、`CONSTANT_String`、符号引用与直接引用、StringTable、`intern()`。
- 触发条件：类加载、字符串字面量使用、显式 intern、动态语言运行期加常量。
- 例外：JDK 7 前字符串常量池在永久代，容易 PermGen OOM；JDK 8 后在堆中可被回收。
- 对比取舍：常量池减少重复、加速解析，代价是加载期解析开销和元空间占用。

**追问预判**

- `new String("a")` 创建几个对象 → 常量池已有则只创建堆对象，没有则先入池再创建，通常是 1 到 2 个。
- intern 在 JDK 7 后有什么变化 → 常量池在堆里，intern 不再复制字符串，直接存引用，性能更好。
- 字符串常量池会 GC 吗 → 会，堆里的字符串常量在 Full GC 时可能被回收（无引用时）。

**常见错误答法**

- 把三者当成同一个池的不同叫法（概念混淆）。
- 说字符串常量池在方法区（JDK 8 后事实错）。

**记忆锚点**

class 池在文件 → 运行时常量池在元空间 → 字符串池在堆 → intern 复用。

## 五、GC 收集器

### 43. 【必答】GC 收集器：如何判断对象可以回收？GC Roots 有哪些？

**口述版**

判断对象能不能回收看可达性分析，从 GC Roots 出发沿引用链遍历，不可达就是垃圾。不用引用计数是因为它解决不了循环引用，A 引用 B、B 引用 A，外界都不引用了，计数还不为零。GC Roots 主要有：虚拟机栈里局部变量表引用的对象、本地方法栈 JNI 引用的对象、方法区静态变量和常量引用的对象、被 synchronized 持有的对象，以及 JVM 内部引用比如系统类加载器和常驻异常对象。另外不可达也不是一棍子打死，重写了 finalize 且没执行过的会进队列再给一次机会，不过 finalize 在 JDK 9 已废弃，不该依赖。

**短版**

可达性分析：从 GC Roots 沿引用链遍历，不可达即垃圾；Roots 包括栈上局部变量、JNI 引用、静态变量与常量、被锁持有的对象、JVM 内部引用。

**展开版**

- 机制链：STW 到安全点 → OopMap 定位栈上引用 → 从 Roots 遍历标记 → 不可达对象进入回收集合。
- 关键结构：OopMap、安全点、四种引用强度（强/软/弱/虚）。
- 触发条件：Minor GC / Full GC 的标记阶段；G1、ZGC 的并发标记。
- 例外：被软引用、弱引用、虚引用关联的对象按各自规则回收；finalize 可自救一次但不可靠。
- 对比取舍：可达性分析能处理循环引用，但要 STW 枚举 Roots；引用计数实时性好但有循环引用问题。

**追问预判**

- 局部变量出作用域后对象还可达吗 → 槽位没被复用前仍可达，所以别指望作用域结束就回收。
- 软引用什么时候回收 → 内存不足、即将 OOM 前，适合做缓存。
- 为什么枚举 Roots 要 STW → 遍历时引用关系不能变，否则标记结果不一致。

**常见错误答法**

- 说「引用计数是 JVM 的回收依据」（事实错）。
- 只列栈和静态变量，漏掉 JNI 与锁持有对象（层级缺失）。

**记忆锚点**

可达性分析 → Roots：栈 / JNI / 静态与常量 / 锁 / JVM 内部 → finalize 只给一次机会。

### 44. 【必答】GC 收集器：为什么分代收集？跨代引用怎么处理（卡表 / RSet）？

**口述版**

分代收集是为了把回收成本压到最低：新生代对象朝生夕死，用复制算法只搬少数存活对象；老年代存活率高，用标记-清除或标记-整理避免大量复制。代价是出现跨代引用，Minor GC 只扫新生代，但老年代对象可能引用新生代对象，不处理就得扫整个老年代。解决办法是记忆集，记录哪些老年代区域存在指向新生代的引用；卡表是最常见的实现，把老年代切成 512 字节一张卡，引用赋值时由写屏障把对应卡标脏，Minor GC 只扫脏卡。G1 里是每个 Region 一个 RSet，记录谁引用了我，代价是额外内存，大概占堆的 10% 到 20%。

**短版**

分代按存活率选算法：新生代复制、老年代标记整理；跨代引用靠记忆集，卡表用写屏障标脏卡，G1 用每 Region 的 RSet 记录引用来源。

**展开版**

- 机制链：对象引用赋值 → 写屏障判断跨代 → 标脏对应卡 / 更新 RSet → Minor GC 只扫描脏卡或 RSet 指向的区域。
- 关键结构：卡页（512 字节）、卡表字节数组、RSet、写屏障。
- 触发条件：老年代引用新生代、跨 Region 引用。
- 例外：G1 的 RSet 维护成本高，堆越大内存开销越明显；ZGC 用染色指针和读屏障，不分代时不需要传统 RSet。
- 对比取舍：卡表实现简单、精度低（一张卡可能只有少量引用）；RSet 精度高但占内存。

**追问预判**

- 写屏障是什么 → 引用赋值前后插入的一小段代码，用来维护记忆集，不是内存屏障。
- 卡表为什么要 512 字节 → 精度与开销的折中，卡太大漏扫多，卡太小卡表本身占空间。
- 分代一定更好吗 → 不一定，大堆、长生命周期对象多时，G1/ZGC 的分代策略和并发回收更合适。

**常见错误答法**

- 把写屏障说成内存屏障（概念混淆）。
- 说 Minor GC 会扫描整个老年代来找跨代引用（机制错）。

**记忆锚点**

存活率决定算法 → 跨代引用 → 记忆集 / 卡表 + 写屏障 → G1 用 RSet。

### 45. 【必答】GC 收集器：Minor GC、Major GC、Full GC 分别什么时候触发？

**口述版**

Minor GC 回收新生代，Eden 满了就触发，频率高、速度快。Major GC 一般指只回收老年代，严格说只有 CMS 有独立的老年代回收，很多场景里 Major 和 Full 是混用的。Full GC 回收整个堆加元空间，触发条件有：老年代空间不足、元空间不足、空间分配担保失败、CMS 的 Concurrent Mode Failure、G1 并发标记跟不上分配速度，还有显式调用 `System.gc()`，不过那只是建议，可以加 `-XX:+DisableExplicitGC` 屏蔽。这里要注意不同收集器的触发路径不一样，具体以版本和收集器为准。

**短版**

Minor：Eden 满；Major：仅 CMS 等有独立老年代回收；Full：老年代或元空间不足、担保失败、CMS 并发失败、G1 跟不上分配、System.gc()。

**展开版**

- 机制链：Eden 分配失败 → Minor GC → 晋升失败或老年代不足 → 触发 Full GC → 回收整堆和元空间。
- 关键结构：`InitiatingHeapOccupancyPercent`（G1 默认 45）、`MetaspaceSize` 高水位、担保检查。
- 触发条件：新生代满、老年代满、元空间达阈值、显式 GC、并发模式失败。
- 例外：G1 的 Full GC 在 JDK 10 后是并行的；ZGC 基本没有传统 Full GC，只有 STW 的 Roots 阶段。
- 对比取舍：Full GC 最彻底但停顿最长，生产上要看频率和耗时，偶发可接受，频繁必须查根因。

**追问预判**

- System.gc() 一定会执行吗 → 不一定，取决于 `-XX:+DisableExplicitGC` 和收集器策略。
- 元空间不足会触发 Full GC 吗 → 会，先尝试回收类元信息，再不行就抛 Metaspace OOM。
- 为什么担保失败会 Full GC → 老年代没有足够空间接收晋升对象，只能先整堆清理。

**常见错误答法**

- 把 Major GC 和 Full GC 完全等同（概念含混，未区分收集器）。
- 说 Minor GC 会回收老年代（事实错）。

**记忆锚点**

Eden 满 → Minor；老年代满 / 元空间不足 / 担保失败 / 并发失败 → Full；System.gc 只是建议。

### 46. 【必答】GC 收集器：常见收集器有哪些？各自适用什么场景？

**口述版**

按演进是 Serial、Parallel、CMS、G1、ZGC、Shenandoah。Serial 单线程全程 STW，适合客户端、小内存、单核。Parallel 是 JDK 8 默认，多线程、吞吐优先，适合批处理和离线计算。CMS 是并发标记清除、停顿优先，但 CPU 敏感、有浮动垃圾和碎片，JDK 9 废弃、14 移除。G1 把堆分成 Region，可以设停顿目标，JDK 9 起默认，适合 4 到 32G 的在线业务。ZGC 靠染色指针和读屏障，停顿通常小于 1 毫秒，适合大堆和低延迟，JDK 21 支持分代。选型上我一般先用默认 G1，抓 GC 日志看停顿和频率，再决定要不要换。

**短版**

Serial 小内存单核；Parallel 吞吐优先（批处理）；CMS 已移除；G1 默认，适合 4–32G 在线业务；ZGC 大堆低延迟，停顿通常 <1ms。

**展开版**

- 机制链：STW 单线程 → 多线程并行 → 并发标记清除 → Region 化可预测停顿 → 染色指针全并发。
- 关键结构：`-XX:+UseG1GC`、`-XX:+UseZGC`、`-XX:MaxGCPauseMillis`、`-XX:ParallelGCThreads`。
- 触发条件：堆大小、延迟要求、JDK 版本决定可选范围。
- 例外：ZGC 不支持压缩指针，JDK 21 前不分代；Shenandoah 需特定发行版支持。
- 对比取舍：吞吐与延迟此消彼长，并发回收用 CPU 换停顿，小堆用并发反而浪费。

**追问预判**

- G1 和 CMS 最大区别 → G1 可预测停顿、Region 化、标记整理不产生碎片；CMS 是标记清除。
- 什么时候选 ZGC → 堆很大（几十 G 以上）或延迟极敏感，且 JDK 版本支持。
- 吞吐优先怎么选 → Parallel，配合大堆和较少 GC 次数。

**常见错误答法**

- 说 CMS 现在还能用（JDK 14 已移除）。
- 认为 G1 一定比 Parallel 快（忽略吞吐与延迟目标差异）。

**记忆锚点**

Serial → Parallel → CMS（已移除）→ G1（默认）→ ZGC（亚毫秒）→ 按堆大小和延迟选。

### 47. 【必答】GC 收集器：G1 的 Region、SATB 与 Mixed GC 流程是怎样的？

**口述版**

G1 把堆切成大约 2048 个大小相等的 Region，每个 1 到 32MB，每个 Region 逻辑上是 Eden、Survivor、Old 或 Humongous，分代不再物理连续。回收分几块：Young GC 回收全部年轻代，Eden 满触发；并发标记周期在老年代占堆达到 IHOP 阈值时触发，默认 45%，流程是初始标记搭乘 Young GC、并发标记用 SATB、最终标记 STW、清理阶段统计各 Region 价值；之后是 Mixed GC，回收全部年轻代加部分高价值老年代 Region；实在跟不上分配就 Full GC。它的核心是可预测停顿，用 `MaxGCPauseMillis` 设目标，按回收价值排序，在目标时间内优先收价值大的 Region，Garbage First 的名字就是这么来的。

**短版**

Region 化堆（1–32MB，约 2048 个），逻辑分代；并发标记在 IHOP（默认 45%）触发，用 SATB 防漏标；Mixed GC 收全部年轻代 + 部分高价值老年代 Region。

**展开版**

- 机制链：Young GC → 老年代占比达 IHOP → 初始标记（搭车）→ 并发标记（SATB）→ 最终标记（STW）→ 清理统计 → Mixed GC 按价值回收。
- 关键结构：Region、Humongous（超 Region 一半）、RSet、SATB 队列、`G1HeapRegionSize`。
- 触发条件：Eden 满、老年代占比达阈值、停顿目标约束。
- 例外：Humongous 对象可能横跨多个 Region；并发标记失败会退化 Full GC。
- 对比取舍：可预测停顿换来 RSet 内存开销和写屏障成本，小堆优势不明显。

**追问预判**

- SATB 和增量更新的区别 → SATB 记录删除的旧引用，按快照处理，产生浮动垃圾不漏标；增量更新记录新增引用。
- Mixed GC 收多少老年代 → 在停顿目标内按回收价值从高到低选，不是全收。
- 为什么需要 Humongous → 大对象跨 Region 存放，避免复制，但可能造成空间浪费。

**常见错误答法**

- 说 G1 的新生代老年代是连续内存（忽略 Region 逻辑分代）。
- 把 Mixed GC 说成回收整个老年代（事实错）。

**记忆锚点**

Region 逻辑分代 → IHOP 45% → SATB 并发标记 → 清理统计 → Mixed 按价值收 → 目标停顿优先。

### 48. 【必答】GC 收集器：三色标记为什么漏标？增量更新和原始快照怎么解决？

**口述版**

三色标记把对象分白、灰、黑：白是没访问过，灰是访问了但引用没扫完，黑是扫完了。漏标要同时满足两个条件：黑色对象新增了指向白色对象的引用，同时原来指向这个白色对象的灰色引用被删掉，这样这个白对象永远不会被扫到，被当成垃圾。两种解法思路相反：增量更新是记录黑色对象新增的引用，重新标记时以它们为根再扫一遍，CMS 用这个；原始快照是记录灰色对象被删除的引用，按标记开始时的快照处理，可能留下浮动垃圾但不会漏标，G1 用这个。

**短版**

漏标需同时满足：黑对象新增指向白对象的引用、灰对象删除指向该白对象的引用；增量更新记新增引用（CMS），SATB 记删除引用（G1）。

**展开版**

- 机制链：并发标记时用户线程改引用 → 写屏障记录变更 → 重新标记 / 最终标记按记录补扫。
- 关键结构：三色集合、SATB 队列、增量更新队列、写屏障。
- 触发条件：并发标记阶段发生引用增删。
- 例外：ZGC 用读屏障 + 染色指针，思路不同；串行标记无并发修改则不会漏标。
- 对比取舍：增量更新不漏标但重标记要回溯黑对象，停顿略长；SATB 停顿短但产生浮动垃圾。

**追问预判**

- 为什么两个条件必须同时满足 → 少一个，白对象仍能从灰对象或原引用链被扫到。
- SATB 的浮动垃圾怎么处理 → 留到下次 GC，不影响正确性，只影响内存回收率。
- 写屏障在这里做什么 → 记录引用变更，把旧值或新值入队，供重新标记使用。

**常见错误答法**

- 只说「并发修改导致漏标」，讲不出两个条件（结论无因果）。
- 把增量更新和 SATB 记的内容说反（概念颠倒）。

**记忆锚点**

黑增白 + 灰删白 → 漏标；增量更新记新增（CMS）、SATB 记删除（G1）。

### 49. 【进阶】GC 收集器：CMS 有哪几个阶段？主要缺陷是什么？

**口述版**

CMS 分四步：初始标记 STW，只标 GC Roots 直接关联的对象，很快；并发标记和用户线程一起跑，最耗时；重新标记 STW，修正并发期间的变动；最后并发清除。缺陷有三个：一是 CPU 敏感，并发阶段要占一部分核，吞吐下降；二是浮动垃圾和 Concurrent Mode Failure，并发清除时新产生的垃圾只能等下次，老年代要预留空间，预留不够就退化成 Serial Old 做单线程 Full GC，停顿很长；三是内存碎片，标记-清除不压缩，碎片多了大对象分配失败会提前触发 Full GC。所以它在 JDK 9 被废弃，JDK 14 移除。

**短版**

初始标记 → 并发标记 → 重新标记 → 并发清除；缺陷是 CPU 敏感、浮动垃圾与 Concurrent Mode Failure、内存碎片；JDK 9 废弃、14 移除。

**展开版**

- 机制链：初始标记 STW（Roots 直连）→ 并发标记 → 重新标记 STW（增量更新补扫）→ 并发清除。
- 关键结构：`CMSInitiatingOccupancyFraction`（默认约 92%）、`CMSScavengeBeforeRemark`、增量更新队列。
- 触发条件：老年代占用达阈值、Young GC 后晋升压力大。
- 例外：并发模式失败或碎片导致 promotion failed 时退化为 Serial Old Full GC。
- 对比取舍：并发回收换来低停顿，代价是 CPU、碎片和浮动垃圾，最终被 G1 取代。

**追问预判**

- 为什么重新标记要 STW → 要修正并发期间变动的引用，必须有一致的快照。
- 预留空间怎么定 → 通过 `CMSInitiatingOccupancyFraction` 提前启动，避免并发失败。
- 碎片怎么缓解 → 调大堆、设置 `CMSFullGCsBeforeCompaction`，但治标不治本。

**常见错误答法**

- 说 CMS 是标记-整理（算法错）。
- 漏掉 Concurrent Mode Failure 的退化路径（机制链断裂）。

**记忆锚点**

初标 → 并发标 → 重标 → 并发清；CPU、浮动垃圾、碎片 → 废弃移除。

### 50. 【进阶】GC 收集器：ZGC 的染色指针和读屏障如何做到低停顿？

**口述版**

ZGC 的目标是停顿不超过 1 毫秒，支持 TB 级堆，而且停顿不随堆变大。它靠两样关键技术。染色指针是在 64 位引用的高位里存标记信息，比如 marked0、marked1、remapped，看引用本身就知道对象状态，不用访问对象头。读屏障是用户线程从堆里读引用时插一段检查，发现对象被移动，就通过转发表找到新地址，顺便把引用改好，这叫自愈。正因为读屏障能兜住并发移动，ZGC 才能把标记、转移、重定位都做成并发，STW 只处理 GC Roots。代价是读屏障有吞吐损耗，而且不支持压缩指针。

**短版**

染色指针把标记位存进 64 位引用高位，读屏障在读取引用时检查颜色并转发到新地址（自愈），从而让标记、转移、重定位全部并发，STW 只剩 Roots 阶段。

**展开版**

- 机制链：并发标记 → 并发转移准备 → 转移（对象复制，旧地址存转发表）→ 重定位（修正引用）→ 整个过程由读屏障兜住。
- 关键结构：染色位（Marked0/Marked1/Remapped/Finalizable）、转发表、读屏障、`-XX:+UseZGC`。
- 触发条件：堆达到回收阈值；JDK 21 起支持分代 ZGC。
- 例外：不支持压缩指针，所以对象引用仍是 8 字节；读屏障增加执行开销。
- 对比取舍：极低停顿换吞吐损耗，适合大堆低延迟，不适合极致吞吐场景。

**追问预判**

- 读屏障和写屏障的区别 → 读屏障拦读取引用，用来转发和自愈；写屏障拦赋值，用来维护记忆集或 SATB。
- 停顿还剩哪些 → 只有 Roots 枚举等极短阶段，通常不到 1 毫秒。
- 为什么大堆也能低停顿 → 回收工作与用户线程并发，停顿时间不随堆大小线性增长。

**常见错误答法**

- 说 ZGC 完全无停顿（仍有极短 STW）。
- 把染色指针说成存在对象头里（错，在引用里）。

**记忆锚点**

引用高位染色 → 读屏障检查 + 自愈 → 并发转移 → STW 只剩 Roots。

### 51. 【进阶】GC 收集器：MaxGCPauseMillis 这类目标参数怎样影响回收行为？

**口述版**

`MaxGCPauseMillis` 是 G1 的停顿目标，默认 200 毫秒，它不是硬承诺，是软目标。它影响的是每次回收挑多少 Region：目标设小，G1 每次只敢收少量 Region，单次停顿短了，但回收速度可能赶不上分配，Young GC 更频繁，甚至触发并发标记和 Full GC，整体吞吐下降；目标设大，每次收得多、次数少，吞吐高但单次停顿长。实践里不要设得太激进，低于 50 毫秒就要评估，因为要收的老年代 Region 多了自然顶不住。它和 IHOP、Region 大小是一起起作用的，调它要同时看 GC 日志里的实际停顿分布，而不是只看平均值。

**短版**

G1 的软目标，默认 200ms；设小则每次少收、GC 更频繁、吞吐下降，设大则单次停顿长但吞吐高；要和 IHOP、Region 大小一起调。

**展开版**

- 机制链：目标停顿 → 预测每个 Region 回收耗时 → 按价值排序选择本次回收集合 → 在预算内尽量多收。
- 关键结构：`MaxGCPauseMillis`、`G1HeapRegionSize`、`InitiatingHeapOccupancyPercent`、预测模型。
- 触发条件：每次 Young GC 和 Mixed GC 的 Region 选择。
- 例外：目标太小会导致回收不足，反而触发 Full GC；ZGC 不靠这个参数，停顿本身极短。
- 对比取舍：停顿与吞吐直接冲突，目标值要按业务 P99 反推，不建议照搬默认或极限值。

**追问预判**

- 设成 10ms 会怎样 → 每次只能收极少 Region，GC 频率飙升，最终可能退化 Full GC。
- 为什么实际停顿会超过目标 → 是软目标，且晋升、Humongous 分配等不可控因素会打破预测。
- 除了停顿还要看什么 → 吞吐、Full GC 次数、GC 后老年代占用。

**常见错误答法**

- 说这是「最大停顿的硬保证」（事实错）。
- 只调这个参数不看日志（缺少验证）。

**记忆锚点**

软目标默认 200 → 控制每次 Region 数量 → 太小反噬吞吐 → 看分布不看均值。

### 52. 【进阶】GC 收集器：什么时候该换收集器？怎么用 GC 日志验证效果？

**口述版**

换收集器看三个信号：停顿超标且 G1 已经调不动，比如 P99 超过业务容忍；堆特别大，几十 G 以上 G1 的 RSet 和标记开销明显；或者 Full GC 频繁且每次很长。这时候大堆低延迟考虑 ZGC，纯吞吐的批处理考虑 Parallel。验证不能靠感觉，要看 GC 日志：JDK 9 起用 `-Xlog:gc*:file=gc.log:time,level,tags`，JDK 8 用 `PrintGCDetails` 加 `-Xloggc`。重点看每次停顿的分布而不是平均值，看 Full GC 次数、GC 前后堆占用、晋升速率、Humongous 分配，再看应用的 TP99 和吞吐。换之前最好同流量压测对比，光看 GC 指标可能停顿降了但吞吐掉更多。

**短版**

信号：停顿超标调不动、堆特别大、Full GC 频繁；大堆低延迟换 ZGC，纯吞吐换 Parallel；用统一日志看停顿分布、Full GC 次数、GC 前后占用，并做同流量压测对比。

**展开版**

- 机制链：设定目标 → 采集基线日志 → 换收集器 → 同流量对比停顿、吞吐、内存占用 → 决定保留或回退。
- 关键结构：`-Xlog:gc*`、`-XX:+PrintGCDetails`、`jstat -gcutil`、GC 日志分析工具。
- 触发条件：延迟或吞吐不达标，且已排除代码与堆大小问题。
- 例外：容器环境还要看 CPU 限制，并发收集器在核数少时反而更慢。
- 对比取舍：ZGC 停顿低但吞吐和内存开销高；Parallel 吞吐高但停顿长，按业务取舍。

**追问预判**

- 只看平均停顿够吗 → 不够，要看 P99 和最大值，平均值会掩盖长停顿。
- 换收集器要改哪些参数 → 堆大小、Region 大小、并发线程数、日志配置都要重新评估。
- 怎么算验证通过 → 业务指标（TP99、错误率）和 GC 指标同时改善，且没有新的 Full GC。

**常见错误答法**

- 一上来就说「换 ZGC」（跳过目标和证据）。
- 只看 GC 日志不看业务指标（验证不完整）。

**记忆锚点**

先定目标 → 看日志分布 → 换收集器 → 同流量压测 → 业务 + GC 双指标验收。

### 53. 【进阶】GC 收集器：内存泄漏和内存溢出在 GC 表现上有什么区别？

**口述版**

内存泄漏和溢出在 GC 上的表现不一样。泄漏是对象该回收却一直被引用，GC 后老年代占用一次比一次高，Full GC 越来越频繁但回收量很小，最终 Full GC 也腾不出空间，抛 Java heap space。溢出是堆根本不够用，可能是一次性大对象或者一次查太多数据，GC 很努力但回收后仍然接近满，来得比较突然。区分方法是看 Full GC 前后的老年代占用：如果回收后能降很多，说明不是泄漏，是瞬时压力或者堆太小；如果降不下去、随时间阶梯上涨，就是泄漏。再看 dump 里占大头的是谁，业务集合一直涨基本就是泄漏。

**短版**

泄漏：GC 后老年代阶梯上涨、Full GC 频繁但回收量小；溢出：一次性压力、GC 后仍接近满。看 Full GC 前后占用能否回落，再结合 dump 定位。

**展开版**

- 机制链：对象被意外强引用 → 每次 GC 都无法回收 → 老年代水位抬升 → Full GC 频率上升、回收率下降 → OOM。
- 关键结构：GC 前后 occupancy、`jstat -gcutil` 的 O、`-XX:+HeapDumpOnOutOfMemoryError`。
- 触发条件：静态集合只增不删、缓存无界、ThreadLocal 未清理、监听器未注销。
- 例外：缓存膨胀介于两者之间，有上限的缓存属于正常增长，无上限才是泄漏。
- 对比取舍：dump 分析最准但影响线上；jstat 轻量但只能看趋势，需要结合业务判断。

**追问预判**

- 怎么快速区分 → 连续多次 Full GC 后老年代占用不降且上涨，就是泄漏。
- 泄漏一定要重启吗 → 应急可以扩容或重启，根治要找到持有链。
- 缓存一定是泄漏吗 → 不一定，有淘汰策略且有上限的是正常增长。

**常见错误答法**

- 把两者当同一件事（概念混淆）。
- 说「Full GC 后内存不降就是泄漏」，忽略一次性大对象也可能暂时不降（判断条件不足）。

**记忆锚点**

泄漏看阶梯上涨 + 回收率低；溢出看瞬时压力；Full GC 前后占用对比 + dump 定位。

### 54. 【进阶】GC 收集器：堆外内存不受 GC 管理，为什么也会 OOM？

**口述版**

堆外内存不受 GC 直接管理，但它仍然占进程地址空间和物理内存。OOM 有几类原因：一是超过 `MaxDirectMemorySize`，分配时直接抛 `Direct buffer memory`，这个限制默认约等于最大堆；二是元空间、线程栈、Code Cache 加起来把本机内存吃光，容器里会被 OOM Kill，或者 JVM 报 native memory 分配失败；三是 mmap 的文件映射和 JNI 自己 malloc 的内存泄漏。GC 只能回收堆里的 DirectByteBuffer 壳，靠 Cleaner 触发释放，如果壳一直被引用或者 Cleaner 没跑，堆外就只增不减。所以排查要看 NMT 和 BufferPool 指标，而不是只盯堆。

**短版**

堆外也占进程内存，超过 MaxDirectMemorySize 抛 Direct buffer memory；元空间、栈、Code Cache、mmap、JNI 也会吃光本机内存；GC 只回收 DirectByteBuffer 壳，靠 Cleaner 释放。

**展开版**

- 机制链：分配堆外内存 → 堆内对象持有地址 → 对象不可达 → Cleaner 执行 free → 内存归还；壳被持有则永不释放。
- 关键结构：`MaxDirectMemorySize`、NMT（`-XX:NativeMemoryTracking`）、`BufferPoolMXBean`、Netty 泄漏检测。
- 触发条件：大量 NIO 读写、Netty 池化配置不当、JNI 库泄漏。
- 例外：容器内存超限时表现为 OOM Kill，而不是 Java 异常，日志里看不到堆栈。
- 对比取舍：堆外省拷贝、抗 GC 移动，但生命周期管理更手动，泄漏排查成本高。

**追问预判**

- 只设 -Xmx 够吗 → 不够，容器里还要给元空间、栈、直接内存留空间，建议用 MaxRAMPercentage。
- 怎么确认是堆外问题 → 堆 dump 正常但进程 RSS 很高，NMT 分类里 Other/Internal 异常增长。
- Cleaner 一定执行吗 → 不保证及时，堆压力小的时候可能很久不触发。

**常见错误答法**

- 说堆外内存「不受任何限制」（事实错）。
- 只盯着堆 dump 排查（方向错）。

**记忆锚点**

堆外占进程内存 → MaxDirectMemorySize → NMT + BufferPool → 壳被持有即泄漏。

### 55. 【兜底】GC 收集器：写屏障和读屏障分别用在哪里？

**口述版**

写屏障是在引用赋值前后插的代码，主要用来维护记忆集和 SATB：跨代或跨 Region 赋值时把卡标脏、把旧引用记进 SATB 队列，CMS 的增量更新也是靠它记新增引用。读屏障是在读取引用时插的，ZGC 用它检查染色位，发现对象被移动就转发到新地址并自愈，Shenandoah 也用读屏障做 Brooks 指针转发。区别在于写屏障拦的是修改，服务的是「标记阶段别漏掉变化」；读屏障拦的是访问，服务的是「对象被并发移动了还能找到」。两个都叫屏障但不是内存屏障，别和 volatile 的 LoadLoad、StoreLoad 混在一起。

**短版**

写屏障拦引用赋值，维护卡表/RSet 和 SATB（CMS 增量更新、G1 SATB）；读屏障拦引用读取，ZGC/Shenandoah 用于染色检查与转发自愈。

**展开版**

- 机制链：赋值 → 写屏障 → 标脏卡 / 入 SATB 队列；读取 → 读屏障 → 检查颜色 → 转发并修正引用。
- 关键结构：卡表、RSet、SATB 队列、染色位、转发表。
- 触发条件：并发标记、跨代引用、对象并发移动。
- 例外：串行收集器不需要这些屏障；ZGC 的读屏障在解释器和 JIT 代码里都有对应实现。
- 对比取舍：写屏障成本低但维护的数据结构占内存；读屏障让并发移动成为可能，但每次读都有开销。

**追问预判**

- 屏障和内存屏障是一回事吗 → 不是，一个是 GC 逻辑钩子，一个是 CPU 内存序指令。
- 为什么 G1 用写屏障不用读屏障 → G1 对象不并发移动，只需要维护 RSet 和 SATB。
- 读屏障开销体现在哪 → 每次读引用多几条检查指令，吞吐会下降几个百分点。

**常见错误答法**

- 把写屏障当成 volatile 的 StoreLoad（概念混淆）。
- 说 ZGC 用写屏障做转发（张冠李戴）。

**记忆锚点**

写屏障管修改 → 卡表 / RSet / SATB；读屏障管访问 → 染色检查 + 自愈转发。

### 56. 【兜底】GC 收集器：分代年龄、晋升阈值、动态年龄判定是什么关系？

**口述版**

三者是一条链上的三个控制点。分代年龄是对象头里的 4 位，每次 Minor GC 存活就加一，范围 0 到 15。晋升阈值是 `MaxTenuringThreshold`，默认 15，年龄达到就进老年代，因为只有 4 位，所以最大也只能是 15。动态年龄判定是运行时的提前晋升规则：Minor GC 后把 Survivor 里对象按年龄从小到大累加，某个年龄及以上的总大小超过 Survivor 的一半，`TargetSurvivorRatio` 默认 50，这个年龄及以上的对象就直接晋升，不用等阈值。所以阈值是上限，动态判定是提前触发，年龄是计数器，三者配合决定对象什么时候离开新生代。

**短版**

年龄是 4 位计数器（0–15）；`MaxTenuringThreshold` 默认 15 是晋升上限；动态年龄判定在 Survivor 中某年龄以上对象超一半时提前晋升。

**展开版**

- 机制链：Minor GC 存活 → 年龄 +1 → 达到阈值或触发动态判定 → 复制到老年代。
- 关键结构：Mark Word 中 4 位 age、`MaxTenuringThreshold`、`TargetSurvivorRatio`、Survivor 大小。
- 触发条件：年龄达阈值、某年龄以上总大小超过 Survivor 一半、Survivor 放不下。
- 例外：Parallel 有 `-XX:+AlwaysTenure` 等特殊模式；G1 的晋升还受 Region 和 Mixed GC 影响。
- 对比取舍：调大阈值让对象多在新生代待，减少晋升但增加复制；调小则加速晋升、加重老年代压力。

**追问预判**

- 为什么年龄不能超过 15 → 对象头只有 4 位，硬件与格式限制。
- 动态年龄判定按「超过一半」是严格大于吗 → 通常按累加超过 `TargetSurvivorRatio` 计算，实现细节以版本为准。
- 关掉动态年龄判定会怎样 → 可以设 `-XX:-UseDynamicAgeDecision` 之类，但通常不建议，容易撑爆 Survivor。

**常见错误答法**

- 说「默认晋升年龄是 6」（参数错）。
- 把动态年龄判定说成「Survivor 满了就全部晋升」（机制错）。

**记忆锚点**

4 位年龄 → 阈值 15 上限 → 动态判定提前 → Survivor 一半即晋升。

### 57. 【兜底】GC 收集器：GC 调优应该先定目标还是先调参数？

**口述版**

先定目标，再谈参数。GC 调优的目标是停顿、频率、吞吐三者满足业务要求，比如接口 P99 不超过多少、Full GC 一天不超过几次，先把这些写清楚，否则调参数没有验收标准。定了目标再收集证据：开 GC 日志看停顿分布、晋升速率、Full GC 次数，用 dump 看对象构成，确认问题在堆大小、对象生命周期还是代码泄漏。然后才动参数，而且一次只改一个，改完同流量对比。多数线上问题的根因在代码，比如大对象、缓存无界、ThreadLocal 没清，调参数只是掩盖。我的顺序是：先确认不是代码问题，再调堆和收集器，最后才微调参数。

**短版**

先定停顿、频率、吞吐目标，再采日志和 dump 找根因，最后一次改一个参数并对比；多数问题根因在代码，参数只是兜底。

**展开版**

- 机制链：定 SLA → 建基线 → 定位根因（代码 / 堆大小 / 收集器）→ 单项调参 → 复测 → 固化配置。
- 关键结构：GC 日志、`jstat`、heap dump、压测环境、灰度发布。
- 触发条件：停顿或吞吐不达标、Full GC 频繁、OOM 反复出现。
- 例外：紧急故障先止损（扩容、重启、切收集器），事后仍要补根因分析。
- 对比取舍：调参见效快但治标；改代码成本高但治本，优先解决无界缓存和大对象。

**追问预判**

- 目标怎么定 → 从业务 SLA 反推，比如 P99 200ms 就要求 GC 停顿远小于它。
- 一次改多个参数行不行 → 不行，无法归因，出了问题也回不去。
- 堆越大越好吗 → 不是，堆大停顿长、内存成本高，还要考虑容器限额。

**常见错误答法**

- 上来就背参数清单（跳过目标与证据）。
- 认为调大堆能解决所有 GC 问题（因果不成立）。

**记忆锚点**

定 SLA → 建基线 → 找根因 → 单变量调参 → 复测固化。

### 58. 【必答】排查：CPU 100% 如何定位？从 top 到具体代码的命令链是什么？

**口述版**

CPU 100% 我用 top 加 jstack 这条链。先 `top` 看是哪个进程，再 `top -Hp pid` 看哪个线程占得高，把线程 ID 转成十六进制，然后在 jstack 输出里找这个 `nid` 对应的线程栈，看它卡在什么方法上。如果栈顶是业务代码里的循环、正则、序列化，那就是代码问题；如果是 GC 线程，说明在频繁 GC，要回头看内存；如果是编译线程，可能是编译风暴。频繁出现可以用 arthas 的 `thread -n 3` 直接看最忙的线程，或者用 async-profiler 采 CPU 火焰图，能直接看到热点方法。定位到代码后再看是死循环、锁自旋还是大计算量，分别处理。

**短版**

top 找进程 → `top -Hp` 找线程 → 线程 ID 转十六进制 → jstack 搜 nid 看栈顶；也可用 arthas `thread -n` 或 async-profiler 火焰图。

**展开版**

- 机制链：OS 层定位进程 → 线程层定位 TID → JVM 层映射 nid → 栈顶方法 → 代码热点。
- 关键结构：`top -Hp`、`printf '%x'`、`jstack`、`jcmd Thread.print`、arthas `thread`、火焰图。
- 触发条件：单核跑满、多核跑满、周期性尖刺。
- 例外：容器里 top 看到的是宿主机视图，要用 cgroup 或 `docker stats` 校正；GC 线程占高不是代码问题。
- 对比取舍：jstack 快照便宜但可能错过瞬时热点；火焰图采样更准但需要额外工具和权限。

**追问预判**

- 栈顶是 native 方法怎么办 → 结合 `perf` 或 async-profiler 看内核态和 native 栈。
- GC 线程占高怎么确认 → 线程名是 `GC Thread`，同时看 jstat 的 GC 频率和耗时。
- 多核都满但业务量不大 → 怀疑死循环、正则回溯、频繁序列化或日志拼接。

**常见错误答法**

- 只说「用 jstack 看一下」（缺 top 到线程的映射链）。
- 把 CPU 高直接归因于 GC（未验证）。

**记忆锚点**

top → top -Hp → hex(TID) → jstack nid → 栈顶方法 → 火焰图确认。

### 59. 【必答】排查：内存持续增长，如何区分泄漏、缓存膨胀和正常增长？

**口述版**

区分要看增长曲线和回收表现。先看 GC 后老年代占用：如果每次 Full GC 后能回到一个稳定低点，但很快又涨上去，且对象数量和请求量相关，这是正常增长或者缓存；如果 GC 后的低点一次比一次高，那就是泄漏。再看 dump 里的对象构成：缓存一般是 Map、byte 数组、业务 DTO，大小和 key 数量相关，有淘汰策略就是正常；泄漏常见的是静态集合持续 add、ThreadLocal 里的线程绑定对象、监听器列表、连接或流没关。验证方法是固定流量下看稳态，正常增长会收敛，缓存膨胀随 key 增长，泄漏随时间单调上涨。

**短版**

看 Full GC 后的低点是否逐次抬高：稳定低点 + 随流量波动是正常/缓存，低点单调上升是泄漏；再结合 dump 看是 Map/缓存还是静态集合、ThreadLocal 持有。

**展开版**

- 机制链：分配速率 > 回收速率 → GC 后水位变化 → 低点趋势判断泄漏 → dump 定位持有链。
- 关键结构：`jstat -gcutil` 的 O、GC 前后 occupancy、`jmap -histo:live`、heap dump、MAT 支配树。
- 触发条件：缓存无上限、批量任务、连接未关闭、静态集合累积。
- 例外：堆外内存增长在堆 dump 里看不到，要看 RSS 和 NMT；JIT/元空间增长也算非堆。
- 对比取舍：dump 最准但代价大；histo 轻量但只有类统计，需要多次对比。

**追问预判**

- 缓存和泄漏怎么进一步区分 → 看是否有淘汰策略、key 是否无限增长、重启后是否复现。
- 为什么 Full GC 后还有占用 → 存活对象本来就在，关键是看低点趋势而不是绝对值。
- 怎么证明是泄漏 → 固定流量下多次 GC，低点持续抬升，且 dump 里能找到同一持有链。

**常见错误答法**

- 看到内存上涨就说泄漏（结论先行）。
- 只看堆不看堆外和元空间（排查面不全）。

**记忆锚点**

看 GC 后低点趋势 → 正常收敛 / 缓存随 key / 泄漏单调涨 → dump 找持有链。

### 60. 【必答】排查：Full GC 频繁怎么排查？GC 日志看哪些指标？

**口述版**

Full GC 频繁我按四步看。先确认频率和耗时，`jstat -gcutil` 看 FGC 次数和 FGCT 增长，GC 日志看每次停顿时长；再看触发原因，日志里会写是 Ergonomics、Allocation Failure、Metadata GC Threshold 还是 CMS/G1 的并发失败；然后看回收效果，Full GC 前后老年代占用降了多少，如果降不下去就是泄漏或者堆太小；最后看对象构成，配合 dump 找大对象和持有链。常见根因是堆设置偏小、晋升过快、大对象直接进老年代、元空间频繁扩容，还有显式 `System.gc`。指标上重点看 FGC 次数、单次停顿、GC 后老年代占比和晋升速率。

**短版**

四步：看频率与耗时（FGC/FGCT）→ 看触发原因（Allocation Failure / Metadata / 并发失败）→ 看回收效果（前后占用）→ dump 看对象构成；重点指标是次数、单次停顿、GC 后老年代占比、晋升速率。

**展开版**

- 机制链：分配压力或晋升过快 → 老年代不足 → Full GC → 回收率低 → 再次触发，形成恶性循环。
- 关键结构：`-Xlog:gc*`、`jstat -gcutil`、`GC Cause`、Humongous 分配、`MetaspaceSize`。
- 触发条件：堆小、晋升阈值低、大对象、元空间扩容、显式 GC。
- 例外：G1 的并发标记失败会退化 Full GC；ZGC 基本没有传统 Full GC。
- 对比取舍：加堆能降频率但拉长单次停顿；改代码减少大对象和缓存更治本。

**追问预判**

- 日志里最该先看哪一行 → 触发原因（Cause）和停顿时间，能直接缩小范围。
- 为什么加了堆还是频繁 → 可能是泄漏或晋升过快，加堆只是延后。
- 怎么确认是大对象导致 → 日志里 Humongous 分配增多，dump 里有大数组或大字符串。

**常见错误答法**

- 只看 Full GC 次数不看原因（无法定位）。
- 直接建议调大堆（跳过证据）。

**记忆锚点**

频率 → 原因 → 回收效果 → 对象构成；FGC、停顿、GC 后占比、晋升速率。

### 61. 【必答】排查：OOM 有哪几类？各自对应什么原因？

**口述版**

OOM 按报错分几类。`Java heap space` 是堆满，最常见，泄漏或者一次性大对象；`GC overhead limit exceeded` 是 GC 花了 98% 时间却只回收不到 2%，本质也是堆快满；`Metaspace` 是类元信息太多，动态生成类或加载器泄漏；`Direct buffer memory` 是堆外超限；`unable to create native thread` 是线程太多或者系统 ulimit 限制；`StackOverflowError` 严格说不算 OOM，是栈深超限。还有容器里被 OOM Kill，这种情况 JVM 不会打堆栈，要看 dmesg 和容器事件。所以看到 OOM 先看错误信息定位区域，再对症查。

**短版**

Java heap space（泄漏/大对象）、GC overhead（堆近满）、Metaspace（动态类/加载器泄漏）、Direct buffer memory（堆外超限）、unable to create native thread（线程过多/ulimit）；容器 OOM Kill 无堆栈。

**展开版**

- 机制链：区域容量或系统资源耗尽 → 分配失败 → 抛对应 OutOfMemoryError → 容器场景可能直接被 Kill。
- 关键结构：`HeapDumpOnOutOfMemoryError`、`MaxDirectMemorySize`、`MaxMetaspaceSize`、`ulimit -u`、cgroup 限额。
- 触发条件：泄漏累积、批量加载、线程池无界、动态类生成、堆外未释放。
- 例外：`StackOverflowError` 属 Error 但不叫 OOM；`unable to create native thread` 也可能来自内存不足而非线程数。
- 对比取舍：堆内问题看 dump，堆外和线程看 NMT 与系统指标，排查手段完全不同。

**追问预判**

- 哪种最常见 → Java heap space，通常伴随泄漏或大查询。
- 容器里为什么看不到 OOM 堆栈 → 被 cgroup OOM Killer 杀掉，表现为进程退出码 137。
- GC overhead 和 heap space 区别 → 前者是回收效率过低触发的保护，后者是直接分配失败。

**常见错误答法**

- 把 OOM 一律当成堆问题（区域混淆）。
- 认为加了 `-Xmx` 就不会 OOM（忽略堆外和元空间）。

**记忆锚点**

heap space / GC overhead / Metaspace / Direct buffer / native thread → 先看报错定区域。

### 62. 【进阶】排查：jstack 里哪些线程状态值得关注？如何判断死锁与线程饥饿？

**口述版**

jstack 里重点看几类状态。BLOCKED 是在等 monitor 锁，如果大量线程 BLOCKED 在同一把锁上，说明锁竞争严重或者持锁线程卡住了。WAITING 和 TIMED_WAITING 一般是 park 或 wait，线程池空闲时大量这种是正常的。RUNNABLE 要小心，可能真的在跑，也可能在做 IO 或者自旋。死锁可以直接看 jstack 末尾的 `Found one Java-level deadlock`，也可以用 `jcmd Thread.print`；类加载死锁会显示在 `<clinit>` 上。线程饥饿的表现是任务排队但线程都活着，比如都在等同一个连接池或者同一把锁，CPU 不高但吞吐上不去。

**短版**

BLOCKED 看锁竞争、WAITING 多为 park/wait、RUNNABLE 可能是 IO 或自旋；死锁看 jstack 的 deadlock 提示；饥饿表现为线程都在等同一资源、CPU 低吞吐低。

**展开版**

- 机制链：采集多次 jstack → 观察状态分布与栈顶 → 找共同阻塞点 → 定位持锁或持资源线程。
- 关键结构：`java.lang.Thread.State`、`locked <0x...>`、`waiting to lock`、`Found one Java-level deadlock`。
- 触发条件：锁粒度过大、连接池过小、线程池队列无界、下游变慢。
- 例外：大量 WAITING 在 `park` 且栈顶是线程池 `getTask`，属正常空闲；GC 线程状态也会出现在 jstack。
- 对比取舍：单次快照可能误判，连续抓 3 次看是否同一阻塞点更可靠；JFR 能补时间维度。

**追问预判**

- BLOCKED 和 WAITING 区别 → BLOCKED 等 monitor 进入，WAITING 是主动 wait/park 等通知。
- 怎么找持锁线程 → 搜 `locked <地址>` 找到持有同一 monitor 的线程栈。
- 饥饿和死锁怎么区分 → 死锁是循环等待永不推进，饥饿是资源长期被抢占、仍有进展但极慢。

**常见错误答法**

- 看到 WAITING 就判断卡死（忽略空闲线程池的正常状态）。
- 只抓一次 jstack 下结论（证据不足）。

**记忆锚点**

BLOCKED 锁 / WAITING 等通知 / RUNNABLE 防 IO → deadlock 提示 → 多次采样看共同阻塞点。

### 63. 【进阶】排查：为什么 jmap -dump 可能引起长时间 STW？生产上如何降低影响？

**口述版**

`jmap -dump` 会走到安全点，并且要遍历整个堆把对象写出去，堆越大越久，期间应用是暂停的，所以可能几十秒 STW。降低影响有几个办法：用 `HeapDumpOnOutOfMemoryError` 让它在 OOM 时才 dump，别在健康时手动抓；能接受近似的话用 `jmap -histo` 看类统计，不停机；或者用 async-profiler 的 alloc 采样、JFR 的堆采样，开销小很多。真要抓 dump，就在低峰做，多副本的话把这台从负载均衡摘掉，抓完再放回。另外用 `jcmd GC.heap_dump` 也一样会触发暂停，不是换个命令就没代价。

**短版**

dump 需要到安全点并遍历整堆写文件，堆越大停顿越久；用 OOM 自动 dump、平时用 histo/JFR/alloc 采样，必须抓时低峰摘流。

**展开版**

- 机制链：attach → 到达安全点 → 暂停应用线程 → 遍历堆写 dump → 恢复。
- 关键结构：`-XX:+HeapDumpOnOutOfMemoryError`、`-XX:HeapDumpPath`、JFR 堆采样、`jmap -histo:live`。
- 触发条件：手动 dump、OOM 自动 dump、监控平台定期采集。
- 例外：容器里 dump 文件可能写满磁盘；`jmap -histo:live` 也会触发一次 Full GC。
- 对比取舍：dump 信息最全但代价最大；采样类工具开销小但拿不到完整引用链。

**追问预判**

- 有没有不停机的 dump → 严格意义上的全量 dump 都要停，采样方案只是近似。
- 为什么 `-histo:live` 也慢 → live 模式要先 Full GC，堆大时同样很久。
- dump 文件太大怎么办 → 用 MAT 的索引、裁剪、或只分析支配树。

**常见错误答法**

- 认为换成 jcmd 就不暂停（事实错）。
- 在生产高峰直接 dump（操作风险）。

**记忆锚点**

安全点 + 整堆遍历 → 长 STW；OOM 自动 dump / histo / JFR 采样 / 低峰摘流。

### 64. 【进阶】排查：Arthas 常用命令有哪些？哪些操作在生产上有风险？

**口述版**

Arthas 常用的是 dashboard、thread、jad、watch、trace、monitor、ognl、classloader、heapdump、vmoption。dashboard 看整体，`thread -n` 看最忙线程，`thread -b` 找阻塞，jad 反编译线上类确认版本，watch 看方法入参返回值，trace 看调用链耗时，monitor 统计调用次数和 RT，ognl 可以看静态字段。风险在于增强字节码本身有开销，trace、watch 在高频方法上会让应用变慢，watch 的 condition 写不好会打爆日志；jad 只是读，最安全；ognl 改静态字段、redefine 热替换类风险最高，可能破坏状态；heapdump 会 STW。生产上先用只读命令，增强类命令要限时、限量，用完 stop。

**短版**

常用：dashboard、thread、jad、watch、trace、monitor、ognl、classloader、heapdump。风险：trace/watch 增强高频方法拖慢应用、ognl 改字段和 redefine 破坏状态、heapdump STW。

**展开版**

- 机制链：attach 到目标 JVM → 字节码增强或读取 → 输出结果 → stop/reset 撤销增强。
- 关键结构：`trace -n`、`watch -x`、`monitor -c`、`tt` 时间隧道、`redefine`、`sc`/`sm`。
- 触发条件：线上定位慢调用、参数异常、类版本不一致。
- 例外：JDK 9+ 需注意模块化限制；部分命令在 GraalVM 或特殊 JVM 上不可用。
- 对比取舍：Arthas 上手快但增强有开销；JFR/async-profiler 开销更低但不如 watch 灵活。

**追问预判**

- watch 会不会影响性能 → 会，尤其高频方法，必须限制次数和条件。
- 怎么确认线上类版本 → `jad 类名` 反编译，或 `sc -d` 看类加载器与来源。
- 改完怎么恢复 → `stop` 退出并撤销增强，`redefine` 需要重新加载原字节码。

**常见错误答法**

- 在生产直接对高频方法 trace 且不设次数上限（风险操作）。
- 用 ognl 改静态字段做「热修复」（破坏状态，不可取）。

**记忆锚点**

看：dashboard/thread/jad → 查：watch/trace/monitor → 慎用：ognl/redefine/heapdump。

### 65. 【进阶】排查：线程池打满和应用假死在表象上怎么区分？

**口述版**

区分看线程和任务两个层面。线程池打满的表现是线程数到上限、队列在涨、拒绝策略开始触发，但线程本身还在跑任务，jstack 里是 RUNNABLE 或者 WAITING 在拿任务，CPU 可能很高，日志里能看到 RejectedExecutionException。应用假死更像线程都卡住了：jstack 里大量 BLOCKED 等同一把锁，或者都 WAITING 在同一个下游连接上，CPU 很低，接口全部超时，但线程池队列可能没满。判断方法是看 jstack 里有没有进展、看线程池 activeCount 和 queueSize 的比值、看是否有统一阻塞点，再结合 CPU 使用率，高 CPU 偏打满，低 CPU 加全阻塞偏假死。

**短版**

打满：线程到上限、队列涨、拒绝异常、线程仍在跑，CPU 偏高；假死：线程集中 BLOCKED/WAITING 在同一资源，CPU 低、全接口超时、队列未必满。

**展开版**

- 机制链：任务提交速率 > 消费速率 → 队列增长 → 拒绝；或所有线程阻塞在同一资源 → 任务无法推进 → 假死。
- 关键结构：`activeCount`、`queueSize`、`RejectedExecutionHandler`、jstack 状态分布、CPU 使用率。
- 触发条件：流量突增、下游变慢、锁粒度过大、连接池过小。
- 例外：两者可以叠加，打满后线程又都卡在下游，表现会同时出现。
- 对比取舍：打满靠扩容或限流缓解；假死要先解除阻塞点，扩容无效甚至更糟。

**追问预判**

- 为什么扩容对假死无效 → 新线程也会卡在同一把锁或同一个下游连接上。
- 怎么确认是队列问题还是阻塞 → 看 activeCount 是否等于 maximumPoolSize，再看栈是否统一阻塞。
- 线程池参数怎么定 → 按任务类型（CPU 密集 / IO 密集）和下游容量反推，队列要有界。

**常见错误答法**

- 看到接口超时就说线程池打满（未验证）。
- 认为扩线程数能解决所有超时（忽略阻塞型假死）。

**记忆锚点**

打满看队列 + 拒绝 + CPU 高；假死看统一阻塞点 + CPU 低。

### 66. 【兜底】排查：堆外内存泄漏怎么排查？

**口述版**

先确认是堆外：堆 dump 正常、Full GC 后堆占用正常，但进程 RSS 持续上涨，或者直接报 `Direct buffer memory`。然后开 NMT，用 `jcmd VM.native_memory summary` 看分类，Other、Internal、Thread、Code 哪块在涨；DirectByteBuffer 看 BufferPoolMXBean 的 count 和 memoryUsed，或者 Arthas 的 memory 命令；Netty 应用把泄漏检测级别开到 PARANOID，能在日志里打出分配栈。再不行用 async-profiler 的 alloc 模式采堆外分配栈，或者 pmap 看匿名内存段增长。常见根因是 DirectByteBuffer 壳被缓存住、Netty ByteBuf 没 release、JNI 库自己 malloc 没 free、还有 mmap 文件没关。

**短版**

先确认堆内正常而 RSS 上涨；NMT 看分类，BufferPoolMXBean 看 DirectBuffer，Netty 开 PARANOID 抓分配栈，async-profiler alloc 采样；常见根因是壳被持有、ByteBuf 未 release、JNI/mmap 泄漏。

**展开版**

- 机制链：堆外分配 → 地址被堆内对象或 native 代码持有 → 释放未触发 → RSS 持续上涨。
- 关键结构：NMT、`BufferPoolMXBean`、Netty `ResourceLeakDetector`、`pmap`/`smaps`、JFR 的 NativeMemory 事件。
- 触发条件：NIO 大量使用、池化配置不当、JNI 调用、文件映射。
- 例外：glibc 的 malloc arena 会让 RSS 不回落，属于分配器行为，不一定是泄漏。
- 对比取舍：NMT 需要在启动时开启且有性能开销；pmap 无侵入但只能看地址段，定位不到代码。

**追问预判**

- 为什么堆 dump 看不出来 → 堆外数据不在堆里，堆里只有一个很小的引用壳。
- 怎么拿到分配栈 → Netty 泄漏检测或 async-profiler alloc 采样，NMT 只给分类统计。
- 重启能解决吗 → 只能临时恢复，复现后仍要定位持有方。

**常见错误答法**

- 用 jmap dump 去找堆外对象（方向错）。
- 看到 RSS 不降就认定泄漏（忽略分配器缓存）。

**记忆锚点**

堆正常 + RSS 涨 → NMT 分类 → BufferPool / PARANOID → alloc 采样 → 壳持有 / 未 release / JNI / mmap。

### 67. 【兜底】排查：一个接口偶发超时，如何判断是 GC、锁、IO 还是下游？

**口述版**

我会先分层排除，而不是猜。先看 GC 日志和时间点对不对得上，如果超时时刻正好有长停顿或者 Full GC，那就是 GC；对不上就看线程栈，多抓几次 jstack，如果都卡在同一把锁或者同一个连接池上，就是锁或者资源池；再看下游，用链路追踪看这个接口的 span 是卡在自己的逻辑还是下游调用，下游 RT 涨没涨、有没有超时重试；最后看机器层面，网卡、磁盘 IO、CPU steal。偶发问题要多抓现场，配合 JFR 或者 async-profiler 的 wall clock 模式，看等待时间花在哪，比单次 jstack 有效得多。

**短版**

对齐 GC 日志时间 → 多次 jstack 看统一阻塞点 → 链路追踪看耗时在本地还是下游 → 看机器 IO/网络；偶发用 JFR 或 wall-clock 采样。

**展开版**

- 机制链：超时发生 → 对齐时间轴 → 排除 GC → 看线程等待 → 看链路 span → 定位资源或下游。
- 关键结构：GC 日志时间戳、jstack 多次采样、Trace/Span、`iostat`、`sar`、JFR 事件、wall clock 采样。
- 触发条件：偶发长停顿、连接池耗尽、下游抖动、磁盘或网络抖动。
- 例外：重试放大、超时设置不合理、线程池排队也会表现为「下游慢」。
- 对比取舍：GC 日志与 trace 便宜，JFR/采样更全但需要预先开启；现场证据比事后推断可靠。

**追问预判**

- 怎么判断是排队还是执行慢 → 看 span 的起止时间和线程池等待指标，排队时间单独统计。
- GC 对不上就一定不是 GC 吗 → 也可能，日志时间精度和时区要对齐，最好用同一时钟源。
- 偶发问题怎么复现 → 压测放大、故障注入、或在低峰开启 JFR 长时间采集。

**常见错误答法**

- 直接换机器或扩副本（未定位根因）。
- 只看平均值，忽略 P99 和长尾（判断依据错）。

**记忆锚点**

对齐时间 → 排 GC → 抓栈看锁 → 链路看下游 → 机器看 IO/网络 → 采样看等待。
