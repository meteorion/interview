## 一、RPC 链路与 Dubbo

### 1. 【必答】RPC 链路：一次 RPC 从调用到返回完整经过哪些环节？

**口述版**

从调用方看，注入的接口其实是一个动态代理，调用时先经过 Cluster 层做目录路由、负载均衡和容错，选出一个 Invoker；再经过 Filter 链，把方法名、参数类型、参数值和附件打包成 Invocation；然后序列化成字节流，通过 Netty 长连接写到对端。服务端 IO 线程解码、反序列化，按 serviceKey 从 exporterMap 里找到对应的 Invoker，派发到业务线程池，反射调用真实实现，把结果或异常沿原路序列化返回。客户端 IO 线程收到响应后，按 requestId 唤醒等待中的 Future，代理解除阻塞把结果交给业务代码。要强调一点：同步调用本质是“发出去 + 等 Future”，所以超时、重试、线程池全部挂在这条链路上。

**短版**

代理 → Cluster（路由、负载均衡、容错）→ Filter → 序列化 → Netty 传输 → 反序列化 → 派发业务线程池 → 反射调用 → 原路返回 → 按 requestId 唤醒 Future。

**展开版**

- 机制链：Proxy → InvokerInvocationHandler → ClusterInvoker（Directory 路由 → LoadBalance → Failover）→ Filter 链 → Protocol/Exchange → Netty Channel → 服务端 Decode → Dispatcher → Invoker → 反射调用。
- 关键结构：Invocation（方法名、参数类型、参数值、attachments）、Result/Future、exporterMap（serviceKey → Exporter）、requestId 与 DefaultFuture 的映射表。
- 触发条件：接口被 `@DubboReference` 注入时生成代理；首次调用触发建连，默认懒加载、长连接、多路复用。
- 例外：同进程 injvm 调用不走网络；泛化调用没有接口类；异步或流式 RPC 的返回路径不同，不占业务线程等待。
- 对比取舍：RPC 把远程调用伪装成本地调用，换来透明性，代价是网络的不确定性被隐藏，必须靠超时、重试、熔断把故障显式暴露。

**追问预判**

- 为什么一定要动态代理 → 接口没有实现类，代理负责把方法调用翻译成 Invocation，并按 serviceKey 找到远端实例。
- requestId 是干什么的 → 长连接多路复用下响应可能乱序，靠 id 精确匹配 Future，避免串包。
- 连接什么时候建立 → 默认首次调用懒加载建连，需要提前预热可以配 check 或 warmup。

**常见错误答法**

- 说“RPC 就是发个 HTTP 请求”，忽略协议、序列化、线程派发这些真正决定稳定性的环节。
- 认为同步调用不占线程（业务线程会阻塞等 Future，这正是超时和线程池要管的原因）。

**记忆锚点**

代理 → Cluster（路由/负载均衡/容错）→ Filter → 序列化 → Netty → 派发 → 反射 → Future。

### 2. 【必答】RPC 链路：Dubbo 的 SPI 扩展机制和 URL 驱动的配置模型怎么理解？

**口述版**

Dubbo 几乎所有可扩展点都走 SPI：ExtensionLoader 按扩展名从 META-INF/dubbo 等目录加载实现，`@SPI` 声明默认实现，`@Adaptive` 生成自适应扩展、运行时按 URL 参数选具体实现，`@Activate` 按条件批量激活，Wrapper 类用来做 AOP。它和 JDK SPI 的关键差别是：JDK 一次加载全部实现、不能按名字精确取、没有依赖注入和包装；Dubbo 是按需加载、可以 getExtension("名字") 精确拿，还能注入依赖、包 Wrapper。配置模型是 URL 驱动：所有配置最终拼成一个 URL，协议、地址、参数全在里面，扩展点从 URL 读参数决定行为，所以配置能覆盖、能透传、能做治理。

**短版**

ExtensionLoader 按名加载 META-INF/dubbo 下的实现，`@SPI` 定默认、`@Adaptive` 按 URL 参数选实现、`@Activate` 条件激活、Wrapper 织入 AOP；URL 是统一配置载体。

**展开版**

- 机制链：`@SPI` 声明接口可扩展 → `ExtensionLoader.getExtensionLoader` → 读 META-INF/dubbo/internal、META-INF/dubbo、META-INF/services → 缓存 ExtensionClass → `getExtension(name)` 实例化 → injectExtension 做 setter 注入 → 逐层包 Wrapper。
- 关键结构：ExtensionLoader、ExtensionClass、URL（protocol/host/port/path/parameters）、Adaptive 动态生成的字节码类。
- 触发条件：`<dubbo:protocol name="dubbo"/>`、`loadbalance="roundrobin"`、filter 配置；URL 里参数一变，选中的扩展就变。
- 例外：`@Adaptive` 标在类上是手工自适应，全局只能有一个；`@Activate` 的 group 和 order 决定 Filter 的激活范围与顺序。
- 对比取舍：URL 驱动让配置统一、可透传、可治理，代价是参数散落在字符串里、弱类型，排查时必须会读 URL。

**追问预判**

- Dubbo SPI 比 JDK SPI 强在哪 → 按名加载、IOC 注入、Wrapper 做 AOP、自适应扩展、条件激活。
- `@Adaptive` 生成的类怎么选实现 → 从 URL 的 protocol 或配置 key 里取扩展名，再 getExtension。
- Filter 的顺序怎么定 → `@Activate` 的 order 加配置，按顺序包在 Invoker 链上。

**常见错误答法**

- 把 Dubbo SPI 等同于 ServiceLoader（漏掉按名加载、注入、Wrapper 三点）。
- 忽略 URL 参数对扩展选择的影响，以为配置只写在 XML 里就完事。

**记忆锚点**

`@SPI` 声明 → ExtensionLoader 按名加载 → `@Adaptive` 看 URL 选实现 → `@Activate` 排序激活 → Wrapper 织入。

### 3. 【必答】RPC 链路：Dubbo 的线程模型里 IO 线程和业务线程池怎么分工？

**口述版**

Dubbo 默认是 all 派发：Netty 的 IO 线程只做读包、解码、反序列化这类轻活，然后把请求丢给业务线程池，默认 fixed、200 线程、有界队列，业务线程执行真正的服务实现，结果再交回 IO 线程写回。这样慢业务不会堵住 IO，一个 EventLoop 上其他连接还能继续收发。反过来，如果业务线程池打满、队列也满，就会直接拒绝并抛异常，客户端看到的是 RPC 异常或超时。所以线程模型必须和超时、隔离、限流一起看，光调线程数解决不了问题。

**短版**

IO 线程只负责收发和解码 → 派发到业务线程池（默认 fixed 200）→ 执行业务 → IO 线程写回；all 是默认，direct 在 IO 线程执行，message 只派发请求类消息。

**展开版**

- 机制链：EventLoop 读 → DubboCodec 解码 → DecodeableRpcInvocation → Dispatcher（all/message/execution/direct/connection）→ ThreadPool 取线程 → 执行业务 Invoker → ResponseFuture 回写。
- 关键结构：Dispatcher、ThreadPool（fixed/cached/limited/eager）、ThreadlessExecutor、ChannelHandler 的线程安全约束。
- 触发条件：`dispatcher="all" threadpool="fixed" threads="200" queues="0"`；业务里有 DB、远程调用等阻塞操作时必须用业务线程池。
- 例外：direct 直接在 IO 线程执行，只适合极快的纯内存逻辑；线程池满时抛 RejectedExecutionException，客户端表现为超时。
- 对比取舍：多一层派发换来了 IO 与业务隔离，代价是线程数变多、上下文切换和队列堆积，必须监控 active、queue、rejected。

**追问预判**

- 为什么不能在 IO 线程做业务 → 一个 EventLoop 管多条连接，阻塞会拖垮同组所有连接的心跳和响应。
- 线程池满了会怎样 → 拒绝后请求根本没执行，客户端只能等到超时，服务端日志会出现拒绝异常。
- 线程数怎么定 → 按 QPS × RT 估并发，再配小队列和合理的下游超时，不能无限加线程。

**常见错误答法**

- 认为 Dubbo 默认就在 IO 线程里执行业务（默认恰恰是派发到业务池）。
- 只说“调大线程数”，不看队列、超时和下游容量。

**记忆锚点**

IO 只做收发解码 → 业务线程池执行 → 池满即拒绝 → 客户端超时。

### 4. 【进阶】RPC 链路：Dubbo 超时与重试的默认陷阱，怎么设置才安全？

**口述版**

Dubbo 默认超时 1000 毫秒、重试 2 次，也就是一次调用最多打三次。陷阱在于：重试是客户端超时后自动重发，服务端可能已经执行成功只是响应慢，于是非幂等接口被重复执行，出现重复扣款、重复下单。而且故障时重试会把流量放大三倍，本来快撑不住的服务直接被压垮。正确做法：按接口 P99 设超时并留余量，非幂等接口 retries 设 0，幂等接口才允许有限重试；重试要配退避和熔断；还要保证上游超时大于下游超时，避免超时层层叠加、上游先返回而下游还在跑。

**短版**

默认 timeout 1 秒、retries 2 次；“超时 + 重试”会放大流量并重复执行。非幂等接口 retries=0，幂等接口有限重试，超时按 P99 设且上游大于下游。

**展开版**

- 机制链：调用发起 → DefaultFuture 带 timeout → 超时抛 TimeoutException → Cluster 容错按 retries 换节点重发 → 每次重试重新路由。
- 关键结构：timeout 的优先级（方法 > 接口 > 全局）、retries、cluster 策略（failover/failfast/failsafe/forking）、Mock 降级。
- 触发条件：下游 RT 抖动、GC 停顿、线程池排队、网络丢包；超时返回时服务端很可能已经执行完。
- 例外：failfast 不重试立即失败；failsafe 忽略异常只记日志；forking 并发调多个取最快，但流量翻倍。
- 对比取舍：重试提高成功率，代价是流量放大和非幂等风险；很多时候“快速失败 + 降级”比盲目重试更安全。

**追问预判**

- 重试发生在哪一层 → Cluster 层，换一个 Invoker 重发，不写在业务代码里。
- 超时怎么分层 → 网关 > 上游服务 > 下游服务，逐层递减，给重试和序列化留开销。
- 重试导致重复写怎么兜 → 业务幂等键加唯一索引，不能指望 RPC 层去重。

**常见错误答法**

- 认为“重试能解决超时”，结果把下游打得更惨。
- 全局把 timeout 调大来掩盖下游慢，掩盖了真正的瓶颈。

**记忆锚点**

默认 1 秒 × 3 次 → 非幂等 retries=0 → 上游超时 > 下游 → 重试必配幂等和熔断。

### 5. 【进阶】RPC 链路：服务端线程池隔离与拒绝策略，慢调用的影响面怎么控制？

**口述版**

一个 Provider 往往暴露多个接口，如果共用一个大线程池，某个慢接口把池占满，其他接口全部排队超时，这就是故障扩散。治理手段是隔离：按接口或业务分组配独立线程池，或者用 Sentinel 按接口限流；每个池配有界队列和明确的拒绝策略，拒绝时快速失败并打指标，而不是无限排队把 RT 拖到几十秒。还要盯 active、queue、rejected 三个指标，配合超时把慢调用掐断，避免请求一直占着线程。隔离会多占资源，粒度太粗没效果、太细难管理，通常按核心链路分组。

**短版**

共享池会被慢接口连坐；按接口/业务分组隔离线程池，配有界队列和明确拒绝策略，盯 active/queue/rejected，再用超时掐断慢调用。

**展开版**

- 机制链：请求进入 Dispatcher → 按配置选共享池或隔离池 → 池满入队 → 队列满触发拒绝策略 → 抛异常或降级 → 客户端超时。
- 关键结构：`dubbo:provider` 的 threads/queues/threadpool，`dubbo:service` 级覆盖，Sentinel 的线程数/并发数限流。
- 触发条件：单接口 RT 突增、下游依赖变慢、批量任务挤占；无界队列表现为 RT 慢慢升高但不报错。
- 例外：线程池隔离会增加总线程数和内存，粒度太细反而难治理；虚拟线程模型下“池”的语义不同。
- 对比取舍：隔离换稳定性，代价是资源冗余；共享省资源，但一处慢就全局挂。

**追问预判**

- 被拒绝后客户端看到什么 → 取决于拒绝发生在派发前还是执行中，通常是 RPC 异常或直接超时。
- 队列该开多大 → 宁小勿大，队列只是缓冲不是容量，靠排队消化流量等于把超时往后推。
- 怎么确认是线程池问题 → active 贴近上限、queue 持续堆积、rejected 增长，再看线程栈卡在哪。

**常见错误答法**

- 用无界队列“避免报错”，最后表现为大面积超时而不是快速失败。
- 只加机器不做隔离，慢接口依然能把新机器的池占满。

**记忆锚点**

共享池等于慢接口连坐 → 分组隔离 + 有界队列 + 快速拒绝 + 看 active/queue/rejected。

### 6. 【兜底】RPC 链路：泛化调用、gRPC 流式与 REST 的适用边界？

**口述版**

泛化调用是不依赖接口 jar 的调用方式，参数用 Map 传，适合网关、测试平台、跨语言桥接这类拿不到接口定义的场景，代价是失去编译期校验，性能和可读性都差。gRPC 基于 HTTP/2 和 Protobuf，天然支持流式、双向流、多路复用，适合内部高频、强契约、需要流式的服务间调用。REST 基于 HTTP 语义，资源建模清晰、调试和对外开放友好，适合面向前端或第三方的接口。选择看三点：契约是否足够强、是否需要流式、调用方是谁。

**短版**

泛化调用给没有接口定义的场景（网关、测试）；gRPC 适合内部强契约加流式；REST 适合对外和前端，调试友好、接入成本低。

**展开版**

- 机制链：泛化调用走 `$invoke(method, paramTypes, args)` → GenericService → PojoUtils 转 Map → 正常 RPC 链路；gRPC 走 HTTP/2 Stream + Protobuf + Stub。
- 关键结构：GenericService/GenericFilter、StreamObserver、HTTP/2 帧与多路复用、REST 的资源与状态码。
- 触发条件：网关透传、跨语言调用、开放平台、需要 server streaming 或双向流。
- 例外：泛化调用拿不到泛型信息和注解；gRPC 在浏览器侧需要 grpc-web 代理；REST 不适合双向流。
- 对比取舍：强契约换性能和安全，弱契约换灵活；对外用 REST 降低接入成本，对内用 RPC/gRPC 提升效率。

**追问预判**

- 泛化调用慢在哪 → 多一层 Map 转换和反射，缺少针对性序列化，还有类型推断开销。
- gRPC 为什么快 → HTTP/2 多路复用、Protobuf 二进制编码、头部压缩。
- 什么场景不该用 REST → 高频内部调用、双向流、对延迟极敏感、需要严格 schema 校验。

**常见错误答法**

- 把 gRPC 说成“另一种 REST”，忽略流式和多路复用。
- 认为泛化调用可以替代正常 RPC，忽视性能和类型安全。

**记忆锚点**

无接口定义用泛化，内部强契约流式用 gRPC，对外易调试用 REST。

## 二、序列化与接口兼容

### 7. 【必答】序列化：JSON、Protobuf、Hessian、Kryo 怎么选？

**口述版**

选序列化看四个维度：性能、体积、跨语言、兼容性。JSON 可读、跨语言、调试方便，但体积大、解析慢，适合对外接口和配置；Protobuf 是二进制，体积小、解析快、有 schema 和明确的兼容规则，适合内部高频 RPC，代价是要维护 proto 并做代码生成；Hessian 是 Dubbo 传统默认，对 Java 友好、支持循环引用，但跨语言弱、兼容性坑多；Kryo 性能最好，但需要注册类、不跨语言、版本兼容差，适合封闭的内部场景。生产上常见的组合是“对外 JSON、对内 Protobuf”，历史系统沿用 Hessian。

**短版**

JSON 通用可读但慢；Protobuf 小而快、有 schema，适合内部；Hessian 对 Java 友好但兼容坑多；Kryo 最快但封闭。对外 JSON、对内 Protobuf。

**展开版**

- 机制链：调用方按序列化 id 选 Serialization 实现 → 序列化成字节写入 body → 服务端按同一 id 反序列化；id 或实现不一致直接解不了。
- 关键结构：Dubbo 的 Serialization 扩展点、content-type、Protobuf 的 proto 文件与生成类、Kryo 的注册表。
- 触发条件：跨语言、跨团队、需要人眼排障、对 RT 和带宽敏感的内部调用，各自的取舍不同。
- 例外：Hessian 对泛型、内部类、不可变集合的处理有差异；Kryo 未注册类会退化或报错；JSON 的大数字精度会丢。
- 对比取舍：性能与可读性通常互斥，兼容性取决于是否有显式 schema，选型要和团队排障能力匹配。

**追问预判**

- 为什么 Dubbo 默认用 Hessian 而不是 Protobuf → 历史原因，Java 接口即契约、无需 proto，但跨语言和兼容性弱。
- Protobuf 的性能优势来自哪 → 二进制编码、字段编号代替字段名、varint 压缩、代码生成免反射。
- 换序列化要注意什么 → 两端同时升级、灰度双读、确认没有依赖 Java 原生序列化语义的字段。

**常见错误答法**

- 只说“Protobuf 快”就选它，忽略 proto 维护成本和可读性。
- 认为 JSON 兼容性天然最好，忽略字段改名、精度丢失、日期格式不一致。

**记忆锚点**

对外 JSON、对内 Protobuf、存量 Hessian、封闭场景 Kryo；四个维度对齐选。

### 8. 【必答】序列化：Protobuf 的编码原理与兼容规则？

**口述版**

Protobuf 用的是 TLV 变体：每个字段写成 tag 加值，tag 是字段号左移三位再或上 wire type；int 用 varint 变长编码，负数用 zigzag 处理，string、bytes 和嵌套消息用 length-delimited。关键点是字段靠编号识别而不是靠名字，所以改字段名不影响兼容，但改字段号一定破坏兼容。兼容规则：新增字段用新编号并给默认值；删除字段的编号要 reserved，不能复用；不要随意改类型，int32 和 int64 在某些 wire type 下能读但语义有风险；proto3 去掉了 required，因为强校验会让解析直接失败。

**短版**

tag = 字段号 << 3 | wire type，varint/zigzag/length-delimited 三种编码；字段靠编号识别，加字段用新号、删字段要 reserved、不改类型、proto3 无 required。

**展开版**

- 机制链：写时按 proto 定义遍历字段 → 编码 tag 和值 → 未知字段原样保留；读时按 tag 找字段描述符 → 按 wire type 解码 → 未知编号跳过或存 unknown fields。
- 关键结构：wire type（0 varint、1 64bit、2 length-delimited、5 32bit）、字段号范围、reserved 声明、unknown fields。
- 触发条件：跨版本通信、灰度期新旧实例并存、消息落到 MQ 后被不同版本消费。
- 例外：proto2 的 required 缺失会解析失败；重复字段改 optional 是兼容的；map 本质是 repeated 的 key/value 消息。
- 对比取舍：编号稳定换来极致的兼容性和体积，代价是编号管理和可读性，必须靠规范约束。

**追问预判**

- 为什么字段名改了还能兼容 → 二进制里只有编号，没有字段名，名字只影响代码生成。
- 删除字段为什么必须 reserved → 防止后来的人复用编号，让老数据被按新语义解析。
- 未知字段会丢吗 → proto3 会保留在 unknown fields 里，再序列化时带出去。

**常见错误答法**

- 认为改字段类型没关系（wire type 不同直接解不出来）。
- 删除字段后直接复用编号，导致历史数据解析错乱。

**记忆锚点**

字段号定兼容，名字不定；加用新号、删用 reserved、类型不改、不设 required。

### 9. 【进阶】序列化：新增字段、枚举扩展、版本升级怎么保证兼容？

**口述版**

接口演进的核心是双向兼容：老客户端能读新数据，新客户端能读老数据。新增字段最安全，老端忽略未知字段，新端拿到默认值；删除字段不能直接复用编号或名字，要先标记废弃、观察调用量归零再删，Protobuf 还要 reserved；枚举扩展要留一个 UNKNOWN 兜底，因为 Java 枚举按名字或序号反序列化，新增值可能让老端直接失败；改类型、改语义、改必填性都是破坏性变更。落地策略是版本化加灰度双版本：接口加版本号或新方法，灰度期同时支持新旧，确认调用方迁移完再下线旧版本。

**短版**

新增字段安全，删除要先废弃再 reserved，枚举留 UNKNOWN 兜底，改类型/语义/必填都是破坏性变更；用版本化 + 灰度双版本过渡。

**展开版**

- 机制链：生产方发新结构 → 消费方按自己的 schema 解析 → 未知字段忽略或保留 → 缺失字段取默认值 → 枚举未知值走兜底分支。
- 关键结构：字段编号与 reserved、枚举的 UNKNOWN、接口版本号、双版本路由、消费方版本清单。
- 触发条件：灰度发布、滚动升级、MQ 中滞留旧消息、多个调用方升级节奏不一致。
- 例外：Hessian 对新增字段一般兼容，但改类型、改类名、枚举加值容易炸；JSON 对缺失字段宽容，对类型变化不宽容。
- 对比取舍：只加不删最安全但结构会膨胀；定期清理要靠调用量监控和版本下线流程，不能靠拍脑袋。

**追问预判**

- 新增枚举值为什么会炸 → Java 枚举反序列化按名字匹配，找不到就抛异常；要 catch 或加 UNKNOWN。
- 灰度期怎么保证双版本 → 接口层同时暴露新旧方法或按版本路由，内部做适配转换。
- 怎么确认字段可以删 → 看调用方是否还在读、日志和链路里该字段的访问量是否归零。

**常见错误答法**

- 直接重命名字段或改类型，认为“加了就兼容”。
- 枚举直接加值不做兜底，灰度时老实例批量反序列化失败。

**记忆锚点**

只加不删、删先废弃、枚举留 UNKNOWN、改类型即破坏、版本化 + 灰度双跑。

### 10. 【进阶】序列化：反序列化安全漏洞怎么防？

**口述版**

反序列化漏洞的本质是“攻击者控制字节流，触发类的危险方法”。Java 原生序列化配合 CommonsCollections 这类库能直接 RCE，所以生产上禁止对外暴露 Java 原生序列化，也不要用 ObjectInputStream 读不可信数据。防护分几层：一是换掉原生序列化，用 JSON、Protobuf 这种数据描述型格式；二是必须用时开白名单，限制可反序列化的类；三是入口做长度和嵌套深度限制，防反序列化炸弹；四是组件及时升级，关掉 Hessian 里不必要的危险类。核心原则是：不要反序列化不可信来源的“任意类型”。

**短版**

原生序列化 + 危险类库可 RCE；禁用原生序列化、改用 JSON/Protobuf、必须用时开白名单、限制长度和深度、及时升级组件。

**展开版**

- 机制链：不可信字节流 → readObject → 触发 readObject/readResolve 等回调 → 构造利用链 → 执行任意代码或造成 OOM。
- 关键结构：ObjectInputStream、Hessian 的允许/拒绝类列表、JSON 的 autoType（fastjson 历史问题）、反序列化过滤器。
- 触发条件：RPC 入参、MQ 消息、缓存反序列化、Session、文件导入等任何外部可控的字节流。
- 例外：白名单过严会误伤正常类，需要按业务枚举；JSON 也不是绝对安全，autoType 打开同样有风险。
- 对比取舍：安全与兼容要平衡，最稳的是只传 DTO 且字段类型封闭，不允许携带类名信息。

**追问预判**

- 为什么 JSON 相对安全 → 默认只映射已知字段类型，不会按字节流里的类名去实例化任意类。
- 白名单怎么做 → 按包或类枚举允许反序列化的类型，其余直接拒绝并告警。
- 反序列化炸弹是什么 → 深层嵌套或超大集合，解析时耗尽 CPU 和内存，需要限制深度和大小。

**常见错误答法**

- 认为“内网 RPC 不用管反序列化”，内网横向移动正是利用点。
- 只换 JSON 但打开了 autoType，风险依旧。

**记忆锚点**

不反序列化不可信类型；禁原生、换 JSON/Protobuf、开白名单、限长度深度。

### 11. 【兜底】序列化：线上序列化失败或字段不一致怎么排查？

**口述版**

线上表现一般三类：反序列化直接报错、字段丢失或为 null、版本不一致导致类型转换异常。排查顺序是：先看异常栈，定位是哪个类、哪个字段、哪种序列化方式；再确认两端用的序列化实现和版本是否一致；然后抓包或打日志看原始字节或 JSON，确认发送端到底有没有这个字段；最后核对字段名、字段号、枚举值、泛型信息在演进中是否被改过。常见根因就那几个：两端 jar 版本不一致、字段被重命名、枚举新增值、Hessian 对泛型和内部类的处理差异、JSON 大数字精度丢失。

**短版**

先看异常栈定类与字段 → 核对两端序列化方式和版本 → 看原始报文确认字段是否发出 → 查字段名/编号/枚举/泛型的演进变更。

**展开版**

- 机制链：异常日志 → 定位 Serialization 实现与类版本 → 打印原始 payload → 对比两端 schema → 复现最小用例。
- 关键结构：异常栈里的 Caused by、serialVersionUID、proto 字段号、枚举 name/ordinal、Jackson 的 FAIL_ON_UNKNOWN_PROPERTIES。
- 触发条件：灰度发布、依赖升级、跨团队接口变更、MQ 中滞留历史消息。
- 例外：有些字段为 null 不是序列化问题而是上游没赋值；类型异常也可能来自泛型擦除后的强转。
- 对比取舍：加详细日志便于定位但有性能和脱敏成本，建议只在采样和异常路径打原始报文。

**追问预判**

- serialVersionUID 不一致会怎样 → 直接抛 InvalidClassException，等价于类不兼容。
- 怎么快速确认是版本问题 → 对比两端依赖树里同一个 DTO 的 jar 版本和字段定义。
- MQ 里的历史消息怎么办 → 消费端做兼容解析或加 UNKNOWN 兜底，必要时用新 Topic 重放。

**常见错误答法**

- 只看“反序列化失败”就去改代码，不核对两端版本。
- 把字段为 null 一律归因于序列化，忽略上游本来就没赋值。

**记忆锚点**

异常栈 → 两端版本 → 原始报文 → schema 差异；四步定位。

## 三、连接池与资源治理

### 12. 【必答】连接池：HikariCP 的核心参数与池大小怎么估？

**口述版**

连接池不是越大越好。HikariCP 的核心参数是 maximumPoolSize、minimumIdle、connectionTimeout、idleTimeout、maxLifetime、validationTimeout 和 keepaliveTime。池大小的经典估算是 CPU 核数乘 2 再加有效磁盘数，也就是几十个量级，再按压测修正，因为数据库连接最终是串行执行 SQL 的，超过 DB 并行能力的连接只会增加上下文切换和锁竞争。实践上先按 QPS 乘平均持有时长估并发占用，再和数据库最大连接数、应用实例数一起算总账，保证实例数乘单实例池大小不超过 DB 上限的七成左右，给运维、主从切换和扩容留余量。

**短版**

核心参数是最大/最小连接数、获取超时、空闲超时、最大寿命、校验超时、保活；池大小按 CPU×2+磁盘数估再压测修正，实例数×池大小要留出 DB 上限三成余量。

**展开版**

- 机制链：请求 `getConnection` → 有空闲直接借 → 没有且未到上限则新建 → 到上限则进等待队列 → 超过 connectionTimeout 抛获取超时。
- 关键结构：ConcurrentBag（无锁借还）、maximumPoolSize、minimumIdle、maxLifetime、keepaliveTime、connectionTimeout。
- 触发条件：流量突增、慢 SQL 占住连接、实例扩容导致总连接数翻倍，都会逼近 DB 上限。
- 例外：只读实例、分库分表后单库连接数要按分片重算；DB 侧 max_connections 是硬上限，超了直接拒绝连接。
- 对比取舍：池大能扛瞬时并发，但会压垮 DB；池小排队变多，靠限流和慢 SQL 治理更可持续。

**追问预判**

- 为什么不是越大越好 → DB 连接是昂贵资源，线程和连接切换、锁竞争会让吞吐反而下降。
- connectionTimeout 和 queryTimeout 区别 → 前者是等池里连接的时间，后者是 SQL 执行时间，必须分开设。
- minimumIdle 有什么代价 → 保持常驻连接占资源，但能避免突发时集中建连的毛刺。

**常见错误答法**

- 按“并发用户数”直接设池大小，忽略 DB 实际并行能力。
- 只调大池不治理慢 SQL，结果是连接越堆越多、DB 更慢。

**记忆锚点**

池大小 ≈ CPU×2 + 磁盘；实例数 × 池 ≤ DB 上限 70%；等连接与执行分开设超时。

### 13. 【必答】连接池：连接泄漏怎么识别和定位？

**口述版**

连接泄漏就是借了没还。HikariCP 打开 leakDetectionThreshold 后，连接超过阈值没归还就打印带堆栈的告警，这是定位泄漏最快的手段。常见根因：手动 getConnection 后异常路径没 close、Statement 或 ResultSet 没关、把 Connection 存成成员变量跨请求复用、异步线程里借连接而主线程已经返回、事务没提交导致连接一直挂着。治理上统一用 try-with-resources 或框架托管，禁止业务手写连接管理；监控上 active 连接数持续贴近上限、获取连接等待时间变长，就是泄漏的早期信号。

**短版**

开 leakDetectionThreshold 打堆栈；根因多为异常路径没关、连接被跨请求复用、异步借还不匹配、事务挂住；治理靠 try-with-resources 和框架托管。

**展开版**

- 机制链：借出连接记录借出时间与堆栈 → 后台定时扫描 → 超过阈值未归还打印告警 → 结合堆栈定位到业务代码行。
- 关键结构：leakDetectionThreshold、ProxyConnection 的关闭标记、active/idle/waiting 指标、Druid 的 removeAbandoned。
- 触发条件：异常分支、批量任务、异步编排、长事务、手动管理连接的老代码。
- 例外：阈值设太小会误报正常长查询，要大于最慢 SQL 的耗时；泄漏也可能是连接被外部持有而不是没 close。
- 对比取舍：检测增加少量开销但收益极大，建议非生产环境常开、生产按采样开。

**追问预判**

- 泄漏和慢 SQL 怎么区分 → 泄漏是连接长期不还、堆栈停在业务代码；慢 SQL 是连接在用但执行久，堆栈在 JDBC 调用。
- 为什么成员变量存连接会泄漏 → 连接被对象长期持有，请求结束也不归还，并发下还会共享同一连接。
- 框架托管就不会泄漏吗 → 也会，比如事务未提交、流式查询未关闭、异步线程里用了已关闭的会话。

**常见错误答法**

- 看到连接数高就直接调大池，掩盖泄漏。
- 认为用了 ORM 就不可能泄漏，忽略流式结果集和手动事务。

**记忆锚点**

开泄漏检测拿堆栈；异常分支、跨请求持有、事务挂住是三大来源。

### 14. 【必答】连接池：连接有效性检测与池化对象的生命周期？

**口述版**

连接会因网络中断、数据库重启、防火墙会话超时、服务端 wait_timeout 被动断开而失效。池子需要有效性检测：HikariCP 优先用 JDBC4 的 isValid，没有才用 connectionTestQuery，配合 validationTimeout 控制检测耗时；keepaliveTime 定期探活，maxLifetime 强制淘汰老连接，避免撞上 DB 或中间件的空闲断连。maxLifetime 必须小于数据库 wait_timeout 和负载均衡的空闲超时，通常设 30 分钟左右并对齐。要注意检测本身有开销，不要每次借连接都做重量级校验，也不要让所有连接同一时刻到期。

**短版**

用 isValid 或测试 SQL 做校验，keepaliveTime 探活，maxLifetime 强制淘汰；maxLifetime 要小于 DB wait_timeout 和中间件空闲超时，并打散到期时间。

**展开版**

- 机制链：借出前校验（可配）→ 后台保活 → 到达 maxLifetime 标记淘汰 → 归还时关闭并新建补充。
- 关键结构：validationTimeout、keepaliveTime、maxLifetime、idleTimeout、JDBC4 isValid、连接测试语句。
- 触发条件：DB 重启、主从切换、网络抖动、云上 LB/NAT 空闲回收、wait_timeout 到期。
- 例外：某些驱动不支持 isValid，需要配置测试语句；maxLifetime 设 0 表示永不淘汰，长期运行会积累半死连接。
- 对比取舍：检测提高可用性但增加延迟，通常只在借出时做轻量校验，重校验交给保活线程。

**追问预判**

- 为什么会出现“连接被对端关闭” → 服务端 wait_timeout 或中间设备空闲回收，池里还留着陈旧连接。
- maxLifetime 为什么要打散 → 避免所有连接同时到期，瞬间集中重建造成抖动。
- 校验失败会怎样 → 标记连接失效并销毁，重新建连；连续失败应该触发告警而不是无限重试。

**常见错误答法**

- 只配 testOnBorrow 不做保活和最大寿命，半死连接仍会被借出。
- maxLifetime 设得比 DB wait_timeout 还大，必然周期性拿到断开的连接。

**记忆锚点**

校验 + 保活 + 最大寿命；maxLifetime 小于对端超时并打散。

### 15. 【进阶】连接池：连接池、线程池与超时三者怎么传递？

**口述版**

一次请求从入口到数据库会穿过网关超时、HTTP 客户端超时、RPC 超时、连接池获取超时、SQL 执行超时，这些必须逐层递减。上游给 3 秒，下游最多给 2.5 秒，到 DB 可能只剩 1 秒，否则上游已经超时返回，下游还在跑，线程和连接被白白占用，流量一大就雪崩。连接池的 connectionTimeout 是等连接的时间，SQL 的 queryTimeout 是执行时间，两者要分开设。实践上最好把剩余时间往下传，也就是 deadline 透传，而不是每层写死一个值，这样上层收紧预算时下层能自动跟着收。

**短版**

网关 > HTTP > RPC > 等连接 > SQL 执行，逐层递减；connectionTimeout 与 queryTimeout 分开设；用 deadline 透传代替每层写死。

**展开版**

- 机制链：入口计算剩余预算 → 透传到下游请求头或 RPC attachment → 每层扣减自身耗时 → 连接池和 JDBC 用剩余值设超时。
- 关键结构：Deadline/Timeout 上下文、connectionTimeout、queryTimeout、RPC timeout、线程池队列等待时间。
- 触发条件：多层调用链、重试、异步编排、批处理，任何一层超时设置倒挂都会导致资源悬挂。
- 例外：有些驱动不支持 queryTimeout 或精度有限；MQ 消费的超时语义与同步调用不同，需要单独设。
- 对比取舍：统一 deadline 治理成本高但最有效；各层写死简单，但改一处要全链路对齐，容易倒挂。

**追问预判**

- 超时倒挂会发生什么 → 上游已返回失败，下游继续执行并占用连接，重试再来一遍，资源被成倍消耗。
- 为什么等连接也要设超时 → 池满时无限等待会把业务线程全部挂住，比快速失败更危险。
- 怎么排查超时叠加 → 看链路每一段的耗时分布，确认是哪一层吃掉了预算。

**常见错误答法**

- 所有层都设 30 秒“保险”，结果故障时全链路堆满线程。
- 只设 RPC 超时不设 SQL 超时，慢 SQL 一直占着连接。

**记忆锚点**

预算逐层递减，等连接与执行分开，deadline 往下传。

### 16. 【进阶】连接池：HTTP 客户端连接池、DNS 缓存与长连接怎么治理？

**口述版**

HTTP 客户端如果每次新建连接，压测时会出现大量 TIME_WAIT 和握手开销，正确做法是用带连接池的客户端，比如 Apache HttpClient、OkHttp 或 WebClient，设置最大连接数、每路由连接数、keepAlive 和空闲回收，让长连接复用。还要注意 DNS 缓存：JVM 默认的 DNS 缓存策略可能是永久缓存或过短，服务端扩缩容后 IP 变了还打到老地址，要显式设置 networkaddress.cache.ttl 并给一个合理 TTL。长连接要配 keepalive 探活和最大空闲时间，避免被中间的 LB 或 NAT 静默断开后拿到半死连接。

**短版**

用带池的 HTTP 客户端，配最大连接、每路由上限、keepAlive、空闲回收；显式设 DNS TTL；长连接加探活和最大空闲，防半死连接。

**展开版**

- 机制链：请求 → 从池里取可用长连接 → 无可用则建连（含 DNS 解析和 TLS 握手）→ 用完归还 → 空闲超时或保活失败则关闭。
- 关键结构：PoolingHttpClientConnectionManager、OkHttp ConnectionPool、perRoute 上限、networkaddress.cache.ttl、keepAlive。
- 触发条件：下游扩容、容器漂移、LB 空闲回收、DNS 记录变更、TLS 会话过期。
- 例外：HTTP/2 多路复用下连接数语义不同；服务端 Connection: close 会强制每次重建，池化无效。
- 对比取舍：连接复用降低延迟和端口消耗，代价是要处理陈旧连接和 DNS 变更，必须配探活与 TTL。

**追问预判**

- 为什么会出现 UnknownHost 或连到旧 IP → DNS 缓存未过期，或连接池里保留了旧地址的长连接。
- perRoute 上限有什么用 → 防止一个下游占满整个池，导致其他下游饿死。
- 怎么发现半死连接 → 偶发的连接重置、读超时，且集中在空闲较久的连接上。

**常见错误答法**

- 用默认的 HttpURLConnection 或每次 new 客户端，连接完全不复用。
- 只调大连接数不设 perRoute，单个慢下游拖垮全局。

**记忆锚点**

连接要池化、DNS 要 TTL、长连接要探活，perRoute 防饿死。

### 17. 【进阶】连接池：多数据源与读写分离下的路由和事务边界？

**口述版**

多数据源的核心是路由加数据源上下文。常用实现是 AbstractRoutingDataSource，用 ThreadLocal 存当前要用的数据源 key，getConnection 时按 key 选真实数据源。读写分离要把“读主库”的语义显式化：强一致读、事务内读、写后立即读都必须走主库，否则会读到延迟的从库。事务边界要注意：一个本地事务只能用一个数据源，跨库要拆成分布式事务或业务补偿；`@Transactional` 与动态数据源切换的代理顺序不对会失效，必须在事务开启前完成数据源选择。还要防止 ThreadLocal 在异步线程和线程池里串数据源。

**短版**

AbstractRoutingDataSource + ThreadLocal 存 key 做路由；强一致读、事务内读、写后读走主库；一个本地事务只用一个数据源，切库必须在事务开启前，异步要清理上下文。

**展开版**

- 机制链：注解或上下文设置数据源 key → 事务拦截器开启事务前调用 determineCurrentLookupKey → 获取对应 DataSource 的连接 → 事务绑定该连接。
- 关键结构：AbstractRoutingDataSource、ThreadLocal 上下文、`@DS`/自定义注解、AOP 顺序、事务同步器。
- 触发条件：读写分离、分库分表、多租户、冷热库分离；事务内混用读写会读到不一致数据。
- 例外：某些框架的连接绑定发生在事务开启后，切库不生效；异步任务和线程池必须手动传递或清理上下文。
- 对比取舍：路由灵活但隐式，出问题难排查；显式指定数据源啰嗦但可控，核心写路径建议显式。

**追问预判**

- 为什么事务里切数据源无效 → 事务已绑定连接，切 key 只影响下一次获取，当前事务仍用旧连接。
- 写后立即读怎么保证 → 强制走主库，或基于 binlog 位点等待从库同步。
- 多数据源下分布式事务怎么办 → 尽量按业务垂直拆库避免跨库事务，必须跨库时用 TCC/消息最终一致。

**常见错误答法**

- 认为读写分离对业务透明，忽略主从延迟导致的读不到刚写的数据。
- 在事务方法内部通过注解切库，结果切了但没生效。

**记忆锚点**

ThreadLocal 定路由，事务前定数据源；强一致与写后读走主库。

### 18. 【兜底】连接池：数据库连接打满，怎么快速止血和定位？

**口述版**

先止血再定位。止血手段有：限流或摘掉异常实例、把非核心功能降级、谨慎地临时调大池和数据库上限、对确认泄漏的实例重启。定位看三个地方：连接池的 active、idle、waiting 指标，数据库的 processlist 和当前活跃 SQL，应用的线程栈看谁在等连接。常见原因就几类：慢 SQL 长时间占住连接、连接泄漏、突发流量、事务里包了远程调用。一定要把“等连接超时”和“SQL 执行慢”分开看，前者是池不够或被占满，后者是 SQL 或 DB 本身的问题，处置方式完全不同。

**短版**

先限流、降级、摘实例止血；再看池指标、DB processlist、线程栈定位；区分等连接超时和 SQL 慢，前者治池与泄漏，后者治 SQL 与容量。

**展开版**

- 机制链：连接耗尽 → 借连接排队 → connectionTimeout 抛异常 → 上层 RT 飙升 → 线程池被占满 → 故障扩散。
- 关键结构：active/idle/waiting、DB 的 processlist 与慢查询日志、线程栈里的 getConnection 等待、监控告警。
- 触发条件：慢 SQL、批量任务、泄漏、流量突增、DB 主从切换后的连接风暴。
- 例外：DB 侧 max_connections 满时新连接直接被拒，表现是建连失败而不是等待；云数据库还有代理层连接数限制。
- 对比取舍：调大池能立刻缓解但可能压垮 DB；根治要靠 SQL 治理、池隔离和限流，止血只是争取时间。

**追问预判**

- 怎么判断是泄漏还是慢 SQL → 泄漏的连接长期不还且堆栈在业务代码；慢 SQL 的连接在跑，堆栈在 JDBC 执行。
- 为什么不能直接调大 DB 连接数 → 超过 CPU 和 IO 承载后，吞吐下降、RT 更长，问题被放大。
- 事务里调远程接口有什么问题 → 事务不提交，连接一直被占用，外部慢调用直接转化为连接耗尽。

**常见错误答法**

- 一上来就重启所有实例，丢掉现场且可能引发连接风暴。
- 只加池上限不降级，DB 被打到不可用。

**记忆锚点**

先止血（限流/降级/摘实例）→ 看池、DB、线程栈 → 分清等连接与 SQL 慢。

### 19. 【兜底】连接池：Druid 与 HikariCP 的差异与选型？

**口述版**

HikariCP 胜在快和简单，做了字节码优化和无锁的 ConcurrentBag，Spring Boot 默认，适合绝大多数业务。Druid 胜在监控和治理，自带 SQL 监控、慢 SQL 统计、防火墙、连接泄漏检测，国内很多团队用它补可观测能力。性能上 Hikari 通常更好，功能上 Druid 更全。选型看团队现状：监控体系薄弱、需要 SQL 审计可以选 Druid；追求极致性能和简洁选 Hikari，监控用 Micrometer 加 Prometheus 补。不要同时引入两套池，也不要因为“功能多”就选更重的方案。

**短版**

Hikari 快而简，Boot 默认；Druid 监控治理强，带 SQL 统计和防火墙。性能选 Hikari，审计监控选 Druid，不要两套并存。

**展开版**

- 机制链：Hikari 用 ConcurrentBag 做无锁借还、代理连接做状态跟踪；Druid 用锁加统计 Filter，对每条 SQL 做计数和耗时采集。
- 关键结构：Hikari 的 ConcurrentBag、ProxyConnection；Druid 的 StatFilter、WallFilter、内置监控页。
- 触发条件：需要 SQL 级监控、防注入审计、慢 SQL 排行时偏向 Druid；高并发低延迟场景偏向 Hikari。
- 例外：Druid 的统计有额外开销，高 QPS 下要评估；Hikari 本身不带 UI，需要外部监控体系。
- 对比取舍：功能与性能通常互斥，选型要和团队运维能力匹配，而不是只看 benchmark。

**追问预判**

- Druid 的防火墙能替代 SQL 注入防护吗 → 只能兜底，根本还是用参数化查询。
- Hikari 怎么做监控 → 通过 Micrometer 暴露指标，配合 Prometheus 和 Grafana。
- 换池要注意什么 → 参数语义不同，maxLifetime、校验、泄漏检测阈值都要重新校准。

**常见错误答法**

- 认为 Druid 性能更好，实际高并发下统计开销明显。
- 两套池同时引入，连接数翻倍却没人察觉。

**记忆锚点**

Hikari 快、Druid 全；性能选 Hikari，审计选 Druid，别混用。

## 四、工程规范与 API 契约

### 20. 【必答】工程规范：分层与依赖方向怎么定，包结构怎么随规模演进？

**口述版**

分层的目的不是画格子，而是控制依赖方向和变更传播。典型四层是：接口层放 Controller 和 RPC Provider，应用层做用例编排和事务边界，领域层放领域模型和业务规则，基础设施层封装数据库、缓存、MQ 和外部调用。依赖必须单向：外层依赖内层，内层不感知外层，基础设施通过接口倒置被领域层依赖。包结构建议按业务域垂直切分，而不是按技术层水平切分；规模变大后按限界上下文拆成独立模块，用 Maven 模块或 ArchUnit 把依赖规则固化进构建，防止出现一个万能的 commons 变成垃圾桶。

**短版**

接口层 → 应用层 → 领域层 ← 基础设施层（依赖倒置）；依赖单向、内层不感知外层；按业务域垂直切包，规模化后拆模块并用 ArchUnit 固化规则。

**展开版**

- 机制链：请求进接口层 → 应用层编排用例、开事务 → 领域层执行规则 → 基础设施层落库或调外部 → 结果逐层返回。
- 关键结构：Controller/Provider、ApplicationService、DomainService/聚合、Repository 接口、基础设施实现、模块依赖图。
- 触发条件：团队扩大、服务拆分、多人并行改同一模块、公共包被到处引用。
- 例外：简单 CRUD 业务不必强行套 DDD 四层，过度分层会让一个查询穿过四五个类。
- 对比取舍：分层清晰便于替换和测试，代价是类变多、链路变长；要按业务复杂度选择分层深度。

**追问预判**

- 为什么领域层不能依赖基础设施 → 一旦依赖具体实现，业务规则就被 DB 和框架绑死，无法单测和替换。
- commons 为什么会变成垃圾桶 → 缺少 owner 和边界，谁都能往里塞，最后形成隐性全局耦合。
- 怎么防止依赖腐化 → 用 ArchUnit 写规则进 CI，模块间只允许通过 API 包依赖，禁止直接引实现。

**常见错误答法**

- 把分层理解成“必须有 Controller/Service/Mapper”三个包，忽略依赖方向。
- 所有模块都依赖一个巨大的 common，改一处全量重编译、全量回归。

**记忆锚点**

外层依赖内层，内层定义接口；垂直切域，模块固化依赖。

### 21. 【必答】工程规范：日志、异常、超时、重试的统一约定怎么落地？

**口述版**

日志要结构化：TraceId、用户或租户、关键业务主键、耗时、结果码，统一 JSON 输出，别打大对象和敏感字段。异常要分层：业务异常用错误码表达、不打堆栈；系统异常记录堆栈并上报；不要 catch 了不处理，也不要每层都 catch 一遍再包一层。超时必须显式配置，禁止默认无限等待，上下游逐层递减。重试只对幂等操作、只对可重试错误，比如超时、连接失败、5xx，要有次数上限、退避和熔断，禁止在循环里无脑重试。这些约定的关键是靠框架和 SDK 兜底，而不是靠人记文档。

**短版**

结构化日志带 TraceId 和业务主键；业务异常用错误码、系统异常留堆栈；超时显式且逐层递减；重试只对幂等和可重试错误，带上限、退避、熔断。

**展开版**

- 机制链：统一日志框架与 MDC → 全局异常处理器翻译错误码 → 客户端 SDK 内置超时与重试策略 → 重试计数进指标。
- 关键结构：MDC/TraceId、ErrorCode 枚举、GlobalExceptionHandler、RetryTemplate/Resilience4j、超时配置中心。
- 触发条件：跨服务调用、批量任务、第三方接口、消息消费；任何一处没约定都会破坏整体可观测性。
- 例外：审计日志和业务流水不能用同一套采样策略；重试对写操作默认关闭，除非有幂等键。
- 对比取舍：统一约定降低排障成本，代价是需要框架封装和推广；靠人工遵守的规范最终一定会失效。

**追问预判**

- 为什么业务异常不打堆栈 → 业务异常是预期分支，打堆栈会淹没真正的系统错误并浪费 IO。
- 重试哪些错误不能重 → 参数错误、鉴权失败、业务校验失败这类确定性错误，重试也不会有不同结果。
- 日志怎么防敏感信息 → 统一脱敏注解或序列化器，禁止直接打印请求体和证件、手机号。

**常见错误答法**

- 每一层都 catch 再包一层 RuntimeException，堆栈被吃掉，定位时看不到根因。
- 在 for 循环里对下游重试，没有上限也不退避，故障时把下游打穿。

**记忆锚点**

日志带 TraceId，异常分业务与系统，超时逐层递减，重试要幂等 + 上限 + 退避。

### 22. 【进阶】工程规范：REST 与 gRPC 的边界，资源建模与错误码怎么设计？

**口述版**

REST 适合资源建模清晰、面向浏览器或第三方、需要缓存和调试友好的场景；gRPC 适合内部服务之间强契约、高频、低延迟、需要流式的场景。错误码设计上，REST 用 HTTP 状态码表达传输语义，业务码放在响应体里，两者不要混；gRPC 用标准状态码，比如 INVALID_ARGUMENT、NOT_FOUND、UNAVAILABLE，再通过 details 带业务信息。版本策略上，REST 用 URL 版本或媒体类型版本，gRPC 用 package 版本加字段兼容。不该用 REST 的场景很明确：双向流、极高频内部调用、需要严格 schema 校验和代码生成。

**短版**

REST 面向资源和外部，gRPC 面向内部强契约与流式；REST 用 HTTP 码 + 业务码，gRPC 用标准状态码 + details；REST 按 URL/媒体类型版本，gRPC 按 package 加字段兼容。

**展开版**

- 机制链：REST 走 HTTP 方法加资源路径映射到 Controller；gRPC 走 proto 定义生成 Stub，服务端实现方法，HTTP/2 传输。
- 关键结构：资源路径与状态码、Problem Details、gRPC Status 与 trailers、proto package 版本。
- 触发条件：对外开放、前端联调、内部高频调用、流式推送、跨语言客户端。
- 例外：REST 也能做流式（SSE），但双向流支持弱；gRPC 经网关暴露给浏览器需要额外代理。
- 对比取舍：REST 接入成本低、生态好；gRPC 性能和契约强，但调试和网关适配成本高。

**追问预判**

- 为什么不能所有接口都用 REST → 高频内部调用下 JSON 开销和 HTTP/1.1 队头阻塞会成瓶颈。
- 业务错误码该放哪 → REST 放响应体，HTTP 码只表达传输和粗粒度语义；不要把业务码塞进 500。
- 版本怎么演进 → 优先兼容演进（加字段），必须破坏时用新版本路径或新 proto package，灰度双跑。

**常见错误答法**

- 所有错误都返回 200 再在 body 里写 code，导致监控和网关无法按状态码识别故障。
- 用 gRPC 做对外开放接口，却没考虑浏览器和第三方的接入成本。

**记忆锚点**

对外 REST、对内 gRPC；HTTP 码管传输、业务码管语义；能兼容就不升版本。

### 23. 【进阶】工程规范：契约测试与消费者驱动契约怎么落地？

**口述版**

契约测试解决的是提供方和消费方对接口理解不一致的问题。消费者驱动契约由消费方定义期望，生成契约文件，提供方在 CI 里验证自己满足所有契约，这样提供方改接口时能在合并前发现破坏性变更。工具上 Spring Cloud Contract 和 Pact 都支持。落地的关键实践：契约纳入版本库、CI 必跑、提供方不满足就阻断发布；灰度期支持双版本；字段只加不删，删除先标记废弃并观察调用量归零。契约测试不能替代集成测试，它验证的是接口形状和交互约定，不验证业务正确性。

**短版**

消费方定义契约 → 提供方在 CI 验证；用 Spring Cloud Contract 或 Pact；契约入库、CI 阻断、灰度双版本、字段只加不删。

**展开版**

- 机制链：消费方写期望 → 生成契约文件或 Pact 文件 → 提供方 CI 拉取并回放请求 → 校验响应结构 → 不匹配则构建失败。
- 关键结构：契约仓库、Pact Broker、provider verification、契约版本与消费方清单。
- 触发条件：多团队共用接口、服务频繁发布、接口由提供方单方面演进。
- 例外：契约测试覆盖不到性能、时序和真实中间件行为；消费方契约过多时维护成本高，需要收敛核心接口。
- 对比取舍：契约测试比端到端快且稳定，代价是要推动消费方参与并维护契约，组织成本大于技术成本。

**追问预判**

- 契约测试和集成测试的区别 → 契约只校验双方约定的形状与交互，不启动完整链路，也不验证业务规则。
- 消费方太多怎么管 → 按核心接口建契约，非核心用 schema 校验和监控兜底。
- 契约过期怎么办 → 契约随消费方版本管理，消费方下线后同步清理，避免僵尸契约阻碍演进。

**常见错误答法**

- 把契约测试当成接口文档或 mock 测试，没有提供方验证环节。
- 只让提供方自己写契约，失去了“消费者驱动”的意义。

**记忆锚点**

消费方定契约，提供方 CI 验证；契约入库、失败阻断、只加不删。

### 24. 【进阶】工程规范：API 规范（分页、幂等、鉴权）怎么从文档变成约束？

**口述版**

API 规范最容易变成“发一份文档没人看”。落地要靠工具和流程：分页统一用 cursor 或 page 加 size，并限制最大 size；幂等要求写操作带幂等键，服务端用唯一索引或状态机兜底；超时和重试写进 SDK 默认值；错误码集中管理、有码表、有 owner；鉴权统一在网关或框架层做，业务代码不各写一套。再用 OpenAPI 生成文档和客户端，用 lint 在 CI 卡不规范的定义，用契约测试卡行为。规范只有变成编译期或 CI 的硬约束，才可能长期执行。

**短版**

分页统一并限最大 size；写操作带幂等键、服务端唯一索引兜底；错误码集中管理；鉴权统一在网关；用 OpenAPI + lint + 契约测试把规范变成 CI 约束。

**展开版**

- 机制链：OpenAPI 定义 → 代码生成/校验 → CI 跑 lint 和契约测试 → 不合规阻断合并 → 网关按规范做鉴权限流。
- 关键结构：OpenAPI/Swagger、Spectral 规则、幂等键与唯一索引、统一错误码表、网关鉴权插件。
- 触发条件：多团队开放接口、对外 API、频繁新增接口、历史接口风格混乱。
- 例外：内部临时接口可以简化，但一旦有外部消费方就必须纳入规范；老接口改造要渐进，不能一刀切。
- 对比取舍：强约束保证一致性，代价是初期接入成本；弱约束灵活，但半年后接口风格必然分裂。

**追问预判**

- 幂等键放哪、怎么生成 → 放请求头，由客户端按业务单号生成，服务端用唯一索引或幂等表去重。
- 深分页怎么规范 → 禁止大 offset，改用 cursor 或基于游标/时间的翻页。
- 规范怎么推广 → 先从新接口和核心链路开始，配套脚手架和代码生成，降低遵守成本。

**常见错误答法**

- 只写文档不做工具校验，规范停留在 Wiki 上。
- 幂等只在应用层判断，没有唯一索引兜底，并发下依然重复写入。

**记忆锚点**

规范进 CI：OpenAPI + lint + 契约；幂等靠键 + 唯一索引；鉴权统一在网关。

### 25. 【兜底】工程规范：依赖治理与版本收敛怎么做？

**口述版**

依赖治理的目标是版本收敛、减少冲突、控制升级风险。手段上，用 BOM 统一管理版本，父 POM 锁定，禁止子模块随意指定版本；定期跑依赖树和漏洞扫描，把重复和冲突的包清理掉；升级走小步快跑，先在非核心服务验证，再推全量；对不再维护的库设替代计划。要特别小心传递依赖带来的版本漂移和已知漏洞，很多线上问题不是自己写的代码，而是某个三层依赖里的旧版本组件。治理要有 owner 和节奏，否则就是一次性运动。

**短版**

BOM + 父 POM 锁版本，禁止子模块乱指定；定期跑依赖树和漏洞扫描；升级小步快跑先非核心；传递依赖的漂移和漏洞是重点。

**展开版**

- 机制链：父 POM/BOM 声明版本 → 子模块继承 → CI 跑 dependency:tree 和漏洞扫描 → 冲突或高危阻断 → 灰度升级验证。
- 关键结构：dependencyManagement、BOM、dependency:tree、OWASP Dependency-Check/Trivy、版本对齐矩阵。
- 触发条件：多模块项目、框架大版本升级、安全通告、第三方 SDK 引入旧依赖。
- 例外：某些库必须锁旧版本（比如与容器或字节码不兼容），要有白名单和到期时间，而不是永久豁免。
- 对比取舍：强收敛降低冲突但升级牵一发动全身；适度分散灵活但长期维护成本高，核心平台建议强收敛。

**追问预判**

- 怎么发现冲突 → dependency:tree 看同一 artifact 的多个版本，结合 mvn dependency:analyze 找未使用依赖。
- 大版本升级怎么控风险 → 先升非核心服务，补测试和契约，观察指标后再推广。
- 漏洞扫描误报怎么办 → 建豁免清单并写清原因和复核时间，不能静默忽略。

**常见错误答法**

- 每个子模块各自指定版本，最后运行时的实际版本谁也说不清。
- 看到漏洞通告直接全量升级，没评估兼容性导致大面积故障。

**记忆锚点**

BOM 锁版本、CI 扫依赖、升级小步走、豁免要有期限。

### 26. 【兜底】工程规范：测试金字塔与测试环境治理怎么落？

**口述版**

测试金字塔是大量单元测试、适量集成测试、少量端到端测试。单元测试快、定位准，覆盖领域逻辑和边界；集成测试验证数据库、MQ、缓存、序列化这些真实依赖；端到端只保留关键链路，因为它慢且不稳定。测试数据用工厂或 Builder 构造，避免共享一份脏数据；测试环境要隔离，禁止连生产库，用 Testcontainers 起真实中间件。CI 里分层跑：单元测试每次提交都跑，集成测试按需或合并前跑，端到端在发布前跑。关键指标不是覆盖率数字，而是关键路径是否被覆盖、失败能否快速定位。

**短版**

单元多、集成适量、端到端少量；数据用工厂构造、环境隔离、Testcontainers 起中间件；CI 分层执行，关注关键路径覆盖而非覆盖率数字。

**展开版**

- 机制链：本地提交跑单测 → 合并前跑集成测试 → 发布前跑端到端和契约 → 失败阻断流水线。
- 关键结构：JUnit、Mockito、Testcontainers、契约测试、测试数据 Builder、环境隔离与数据清理。
- 触发条件：核心交易链路、序列化与 DB 交互、跨服务接口变更、线上故障复盘后的回归补充。
- 例外：遗留系统单测成本极高，可以先补集成测试和契约测试，逐步重构出可测单元。
- 对比取舍：单测快但覆盖不到集成问题；端到端真实但慢且脆，比例要按系统阶段调整，不必教条。

**追问预判**

- 覆盖率有意义吗 → 有参考价值但不能作为目标，关键路径覆盖和缺陷逃逸率更能说明问题。
- 集成测试怎么保证稳定 → 用容器化中间件、固定数据、独立 schema，禁止依赖共享测试库。
- 端到端为什么容易失败 → 依赖多、环境差异、数据竞争，应该只保留少量核心链路并做好重试与隔离。

**常见错误答法**

- 追求 100% 覆盖率，写了大量不断言行为的测试。
- 所有测试都连同一个共享测试库，数据互相污染，失败无法复现。

**记忆锚点**

单测多、集成适量、端到端少；数据自造、环境隔离、CI 分层。
