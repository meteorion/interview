## 一、线程池

### 1. 【必答】线程池：七个核心参数如何互相制约？

**口述版**

线程池的核心参数是 corePoolSize、maximumPoolSize、keepAliveTime、unit、workQueue、threadFactory、handler。它们是联动关系：任务进来先看当前线程数是否小于核心数，小于就直接新建核心线程；不小于就尝试入队；队列满了才扩容到最大线程数；再到最大还满就触发拒绝策略。所以要理解一个反直觉的点：只有队列满了之后，最大线程数才会起作用，如果用无界队列，maximumPoolSize 等于摆设。keepAliveTime 只管超过核心数的那部分线程的回收。另外 allowCoreThreadTimeOut 打开后核心线程也能超时回收。实际配置要整体看下游承受能力和队列积压的延迟，参数不是孤立调优的。

**短版**

核心->入队->扩容到最大->拒绝，这条顺序决定了队列和最大线程数是耦合的；无界队列会让最大线程数失效，keepAliveTime 只作用于非核心线程（除非开启核心超时回收）。

**展开版**

- 机制链：execute → 线程数 < core 则 addWorker → 否则 offer 入队 → 入队失败则 addWorker 到 max → 仍失败执行拒绝策略。
- 关键结构：`ctl` 用一个 int 同时存运行状态和线程数（高 3 位状态、低 29 位数量）；`Worker` 继承 AQS 做不可重入的独占锁。
- 触发条件：任务提交、线程空闲超时、`shutdown` 与 `shutdownNow` 状态切换。
- 例外：`SynchronousQueue` 不存储任务，所以会直接走扩容到最大线程数；`CallerRunsPolicy` 会让提交线程自己跑，形成天然背压。
- 对比取舍：先扩容再入队能降低延迟但线程创建成本高；先入队能削峰但会拉长排队时间，两者取决于任务类型。

**追问预判**

- 为什么线程数到 core 后先入队而不是继续建线程 → 复用已有线程比新建更省资源，队列起到削峰作用。
- maximumPoolSize 什么时候完全没用 → 使用无界队列（如默认的 LinkedBlockingQueue）时永远不会触发扩容。
- 核心线程会超时吗 → 默认不会，设置 `allowCoreThreadTimeOut(true)` 后才会。

**常见错误答法**

- 说任务一来就判断是否达到最大线程数（顺序是 core → 队列 → max）。
- 认为 maximumPoolSize 是线程数硬上限（核心线程数在特殊配置下可超过它，实际以 max 为扩容上限）。

**记忆锚点**

core → 队列 → max → 拒绝，队列决定 max 是否生效。

### 2. 【必答】线程池：任务提交流程与拒绝策略怎么选？

**口述版**

提交流程就是刚才说的四步。拒绝策略有四种：AbortPolicy 直接抛 RejectedExecutionException，是默认值，适合不能丢任务的场景，让上游感知并重试；CallerRunsPolicy 用提交任务的线程自己执行，形成背压，适合能接受变慢但不能丢的任务；DiscardPolicy 静默丢弃，DiscardOldestPolicy 丢掉队列最老的任务再尝试提交，这两个都会丢数据，只适合可丢弃的采集类任务。工程上更常见的是自定义策略：记录日志和指标、落库或写 MQ 做补偿、或者按业务分级降级。选型的关键是先回答"这个任务丢了会怎样"，不能丢就别用 Discard，能接受延迟就用 CallerRuns 做背压。

**短版**

Abort 抛异常（默认）、CallerRuns 让提交线程执行形成背压、Discard 静默丢弃、DiscardOldest 丢最老任务；按"任务能否丢、能否接受变慢"选，生产多用自定义策略做记录和降级。

**展开版**

- 机制链：`execute` 在 addWorker 失败或线程池非 RUNNING 时调用 `reject` → handler 决定抛异常、丢弃或回退执行。
- 关键结构：`RejectedExecutionHandler` 四个内置实现、`ThreadPoolExecutor` 的状态判断、`CallerRunsPolicy` 里的 `!isShutdown()` 检查。
- 触发条件：队列满且线程达 max、线程池已 shutdown、`shutdownNow` 后仍有提交。
- 例外：`CallerRunsPolicy` 在线程池关闭后会静默丢弃任务，不会执行。
- 对比取舍：抛异常让问题暴露但可能打挂上游；背压保护下游但拖慢调用方；丢弃保吞吐但丢数据，必须配合补偿。

**追问预判**

- 默认策略是哪个 → AbortPolicy，直接抛 RejectedExecutionException。
- CallerRuns 有什么副作用 → 提交线程被占住，线程池满时会连锁拖慢上游，甚至造成死锁式等待。
- 怎么做到不丢任务 → 队列持久化、本地落盘或写 MQ，再配补偿和对账。

**常见错误答法**

- 说 DiscardPolicy 会打日志（它是静默丢弃，什么都不做）。
- 认为 CallerRuns 一定安全（在线程池已关闭时会直接丢弃任务）。

**记忆锚点**

Abort 抛 / CallerRuns 背压 / Discard 静默丢 / 自定义做补偿。

### 3. 【必答】线程池：为什么不能用无界队列，池隔离怎么做？

**口述版**

无界队列的两个问题：一是 maximumPoolSize 永远不生效，线程数卡在核心数，吞吐上不去；二是任务只进不出，堆积会把堆撑爆，最后 OOM，而且从提交到执行的延迟不可控，超时和熔断都会失效。正确做法是有界队列加明确的拒绝策略，让压力在入口就暴露出来。池隔离是指不同业务、不同依赖用不同的线程池，避免一个慢接口把公共池占满，把其他业务一起拖死。隔离维度可以按业务线、按下游依赖、按任务优先级来分。代价是线程总数变多、上下文切换和内存开销上升，所以要配合容量估算和监控，不能无脑拆池。

**短版**

无界队列让 max 失效、任务无限堆积直到 OOM，延迟不可控；应使用有界队列加拒绝策略；池隔离按业务或下游拆池，防止慢调用互相拖死，代价是线程总数和切换开销上升。

**展开版**

- 机制链：无界队列 `offer` 永远成功 → 不会触发扩容和拒绝 → 积压增长 → 堆内存耗尽或延迟爆炸。
- 关键结构：`LinkedBlockingQueue` 默认容量 `Integer.MAX_VALUE`、`ArrayBlockingQueue` 必须指定容量、`SynchronousQueue` 容量为 0。
- 触发条件：下游变慢、流量突增、批量任务集中提交。
- 例外：纯计算型且任务量可控的内部池可以用较大队列，但也要设上限并监控积压。
- 对比取舍：有界队列把压力前移，代价是拒绝率上升；隔离提升稳定性，代价是资源利用率和运维复杂度上升。

**追问预判**

- 队列长度怎么定 → 按可接受的最大排队延迟乘以处理速率估算，而不是拍脑袋。
- 隔离后线程数暴涨怎么办 → 用统一容量预算分配，配合监控看每个池的活跃度和队列深度。
- 拒绝之后业务怎么兜 → 同步降级返回兜底值，或转异步补偿，不能让异常直接冒到用户。

**常见错误答法**

- 说用无界队列就不会丢任务（会 OOM，且延迟不可控）。
- 认为池隔离就是每个接口一个池（过度拆分，反而放大切换开销）。

**记忆锚点**

无界队列 = max 失效 + 堆积 OOM → 有界 + 拒绝 → 按业务/下游隔离。

### 4. 【进阶】线程池：线程数怎么定，CPU 密集和 IO 密集有什么差别？

**口述版**

经典公式是 CPU 密集设为核数加一，IO 密集设为核数乘以（1 加平均等待时间除以平均计算时间）。原理是 CPU 密集时线程基本不阻塞，多一个线程只是补上偶发缺页的间隙；IO 密集时线程大量时间在等，所以要更多线程把 CPU 喂满。但这个公式只是起点，实际要用压测找拐点：固定下游和数据集，逐步加线程数，看 QPS 和 P99，QPS 不再上升而延迟开始陡增的位置就是上限。还要注意线程数不是越多越好，超过下游连接池容量、DB 连接数或带宽之后，加线程只会加剧排队和上下文切换。真正要控的是对下游的并发度，而不是本机线程数。

**短版**

CPU 密集约等于核数加一，IO 密集约等于核数乘（1 加等待比计算）；公式只是起点，靠压测找 QPS 拐点；线程数要受下游连接池和容量约束，控的是端到端并发而不是本机线程数。

**展开版**

- 机制链：线程数增加 → 并行度提升 → 达到下游瓶颈 → 排队加剧 → 延迟上升而吞吐不再增长。
- 关键结构：`availableProcessors`、`Runtime` 获取核数、容器环境下要按 CPU limit 而不是物理核数算。
- 触发条件：新服务容量规划、大促前扩容、下游 RT 变化后重新评估。
- 例外：容器里 `availableProcessors` 在 JDK 8 早期不感知 cgroup 限额，需要显式 `-XX:ActiveProcessorCount`。
- 对比取舍：线程多提升 IO 并发但增加切换和内存；线程少省资源但 CPU 利用率不足，要靠压测取平衡。

**追问预判**

- 为什么 CPU 密集要加一 → 补上偶发的缺页和 GC 停顿间隙，避免 CPU 空转。
- 容器里核数取错会怎样 → 按宿主机核数配线程，实际被 CPU limit 限制，线程大量排队、延迟抖动。
- 线程数和连接池的关系 → 线程数不应显著超过连接池大小，否则线程都在等连接。

**常见错误答法**

- 死记 2N+1 之类的公式，不看任务类型（公式有适用前提）。
- 认为线程越多吞吐越高（超过瓶颈后只增延迟）。

**记忆锚点**

CPU 密集 N+1 → IO 密集 N×(1+等待/计算) → 压测找拐点 → 受下游容量约束。

### 5. 【进阶】线程池：监控指标有哪些，动态调参怎么做？

**口述版**

核心指标有四类：池状态，包括当前线程数、核心数、最大数、活跃线程数；队列，包括队列长度和剩余容量；任务，包括完成任务数、提交速率和被拒绝次数；时间，包括任务排队时长和执行时长。前三个 ThreadPoolExecutor 直接能拿到，排队时长要自己包一层记录入队和执行的时间戳。拒绝次数是最该告警的指标，它直接说明容量不足。动态调参分两步：参数要能被配置中心推送，同时把 `setCorePoolSize`、`setMaximumPoolSize`、`setRejectedExecutionHandler` 这些 setter 暴露成运维接口。注意线程池没有 setQueueCapacity，队列容量是 final 的，要动态调整队列只能自己实现可扩容队列或直接换池。调整后要观察活跃线程数和拒绝率的反馈，不能只看配置生效。

**短版**

看线程数/活跃数、队列长度、完成与被拒绝数、排队与执行耗时；拒绝数是核心告警项；动态调参靠配置中心加 setCorePoolSize/setMaximumPoolSize/setRejectedExecutionHandler，队列容量改不了，需要自定义队列或换池。

**展开版**

- 机制链：采集 getPoolSize 等指标 → 上报到 Micrometer/Prometheus → 配置中心下发参数 → setter 生效 → 观察反馈。
- 关键结构：`getActiveCount`、`getQueue().size()`、`getCompletedTaskCount`、`getTaskCount`、`largestPoolSize`。
- 触发条件：大促前扩容、下游 RT 恶化、拒绝率告警、队列持续积压。
- 例外：`getActiveCount` 是估算值，遍历 worker 得到，高并发下不精确；队列容量无法通过 setter 修改。
- 对比取舍：动态调参缩短响应时间，代价是参数变更缺少评审容易越调越乱，需要变更记录和回滚。

**追问预判**

- 队列长度能动态改吗 → 不能，`workQueue` 容量是构造时确定的，只能自定义队列或重建线程池。
- 怎么判断线程池快被打满 → 活跃线程数接近 max 且队列持续非空、拒绝数上升。
- 为什么活跃数不准 → `getActiveCount` 遍历 Worker 统计，存在并发误差。

**常见错误答法**

- 只看 QPS 不看队列和拒绝数（瓶颈在排队时 QPS 可能还在涨）。
- 认为所有参数都能热更新（队列容量不行）。

**记忆锚点**

线程/队列/拒绝/耗时 → 拒绝率告警 → setter 热更 → 队列容量不可变。

### 6. 【兜底】线程池：execute 和 submit 的区别，任务异常去哪了？

**口述版**

execute 接收 Runnable，没有返回值，任务里抛的异常会直接传给线程的 UncaughtExceptionHandler，默认是打印到 stderr，所以经常在日志里看不到。submit 接收 Runnable 或 Callable，返回 Future，异常不会直接抛，而是被捕获后包进 Future，只有调用 get 时才会以 ExecutionException 抛出来；如果一直不 get，异常就静默消失了。这就是线上"任务没执行也没报错"的常见原因。所以用 submit 要么 get，要么用 CompletableFuture 的 whenComplete 处理，要么在任务内部自己 try-catch 打日志。另外 submit 会把任务包成 FutureTask，多一层对象开销。选择上，不需要结果且希望异常暴露就用 execute，需要结果或编排就用 submit 并显式处理异常。

**短版**

execute 无返回值，异常交给 UncaughtExceptionHandler（默认打到 stderr）；submit 返回 Future，异常被包进 Future，只有 get 时才抛，不 get 就静默丢失；不取结果用 execute，取结果必须处理异常。

**展开版**

- 机制链：submit → 包装成 FutureTask → 异常存进 outcome 字段 → 状态置为异常完成 → get 时抛 ExecutionException。
- 关键结构：`FutureTask.run` 里的 try-catch、`UncaughtExceptionHandler`、`ExecutionException` 的 cause。
- 触发条件：任务抛运行时异常、Callable 内部失败、任务被取消。
- 例外：`Future.get` 抛 InterruptedException 和 TimeoutException 属于调用侧异常，与任务失败不同。
- 对比取舍：submit 支持结果和编排，代价是异常被延迟暴露；execute 简单直接，代价是拿不到结果。

**追问预判**

- 为什么日志里看不到异常 → submit 把异常吞进 Future，没有 get 就不会打印。
- 怎么统一兜底异常 → 自定义 ThreadFactory 设置 UncaughtExceptionHandler，或在任务外层包 try-catch。
- Future.get 阻塞怎么办 → 用带超时的 get，或改用 CompletableFuture 做回调式处理。

**常见错误答法**

- 说 submit 抛的异常会直接打到控制台（会被 Future 捕获）。
- 认为 execute 不能执行 Callable（它只接受 Runnable）。

**记忆锚点**

execute 异常上抛 → submit 异常进 Future → 不 get 就静默丢。

## 二、线程与锁

### 7. 【必答】线程与锁：Java 线程的六种状态与转换？

**口述版**

Thread.State 定义了六种状态：NEW、RUNNABLE、BLOCKED、WAITING、TIMED_WAITING、TERMINATED。NEW 是创建了还没 start；RUNNABLE 是正在跑或可运行，注意它把操作系统的就绪和运行合并了，所以看不到真正的"运行中"；BLOCKED 是等 synchronized 锁；WAITING 是无超时的等待，比如 wait、join、park 不带时间；TIMED_WAITING 是带超时的等待，比如 sleep、wait(timeout)、join(timeout)；TERMINATED 是 run 结束。转换上要记两条：进入 synchronized 竞争失败是 BLOCKED，调 wait 是 WAITING 并释放锁；BLOCKED 只有等锁这一种来源，别把 IO 阻塞说成 BLOCKED，IO 在 Java 看来仍然是 RUNNABLE。

**短版**

NEW、RUNNABLE、BLOCKED、WAITING、TIMED_WAITING、TERMINATED；BLOCKED 只表示等 synchronized，wait/join/park 进 WAITING，带超时的进 TIMED_WAITING，IO 阻塞在 Java 里仍算 RUNNABLE。

**展开版**

- 机制链：`start` → NEW 转 RUNNABLE → 竞争锁失败转 BLOCKED → `wait` 转 WAITING → 超时或唤醒回 RUNNABLE → run 结束 TERMINATED。
- 关键结构：`Thread.State` 枚举、`Thread.getState()`、native 层线程状态与 JVM 状态的映射。
- 触发条件：锁竞争、`wait`/`notify`、`sleep`、`join`、`park`/`unpark`、IO 等待。
- 例外：IO 阻塞在 JVM 层仍是 RUNNABLE，所以 jstack 看到 RUNNABLE 不代表在烧 CPU；虚拟线程的阻塞状态映射另有规则。
- 对比取舍：状态合并简化了模型，代价是排查时不能只靠 RUNNABLE 判断是否在算，要结合栈和 CPU 采样。

**追问预判**

- BLOCKED 和 WAITING 的区别 → BLOCKED 是被动等锁、不释放已持有的其他锁；WAITING 是主动等待通知，通常会释放锁。
- 为什么 IO 是 RUNNABLE → JVM 不去细究底层是等 socket 还是等磁盘，统一视为可运行。
- jstack 里状态和代码对不上怎么办 → 多看几次采样、结合 CPU 占比和锁信息判断。

**常见错误答法**

- 说 Java 有"运行中"和"就绪"两个独立状态（合并为 RUNNABLE）。
- 把 IO 阻塞归为 BLOCKED（那是等 monitor 锁）。

**记忆锚点**

六态 → BLOCKED 只等锁 → WAITING 主动等通知 → IO 仍 RUNNABLE。

### 8. 【必答】线程与锁：interrupt、sleep、wait 的差异与正确用法？

**口述版**

interrupt 不是强制终止线程，它只是设置中断标志，如果线程正阻塞在 sleep、wait、join 上，会抛 InterruptedException 并清除标志。sleep 是 Thread 的静态方法，不释放锁，只是让出 CPU 一段时间；wait 是 Object 的方法，必须在 synchronized 块里调用，会释放锁并进入等待队列，需要 notify 或超时唤醒。核心区别是释放锁与否，这决定了它们能不能用于线程间协作。正确用法是：捕获 InterruptedException 后要么继续向上抛，要么恢复中断标志 `Thread.currentThread().interrupt()`，绝不能吞掉；不要用 stop 强制结束，它会留下不一致状态，要用标志位加 interrupt 协作式退出。

**短版**

interrupt 只设中断标志，阻塞中的 sleep/wait/join 会抛 InterruptedException 并清标志；sleep 不释放锁，wait 必须持锁且会释放锁；捕获后要恢复中断标志，禁止用 stop。

**展开版**

- 机制链：`interrupt` 置位并唤醒阻塞 → 阻塞方法检测到标志 → 抛 InterruptedException → 清除标志 → 调用方决定恢复或退出。
- 关键结构：`Thread.interrupted()`（清除标志）、`isInterrupted()`（不清除）、`InterruptedException`、`LockSupport.park` 对中断的响应。
- 触发条件：线程池关闭、任务超时取消、请求被上游取消、优雅停机。
- 例外：`synchronized` 等锁不可中断，`ReentrantLock.lockInterruptibly` 才可以；IO 流的中断行为依赖具体实现。
- 对比取舍：协作式中断安全但响应不即时，需要业务代码配合检查；强制停止即时但会破坏一致性。

**追问预判**

- 为什么捕获后要再 interrupt 一次 → 上层可能还要感知中断，吞掉会让取消信号丢失。
- wait 为什么必须在 synchronized 里 → 判断条件和进入等待必须原子，否则会丢通知。
- 怎么优雅停止线程池 → `shutdown` 拒绝新任务，配合业务检查中断标志，超时后再 `shutdownNow`。

**常见错误答法**

- 说 interrupt 会立刻终止线程（只是协作信号）。
- 捕获 InterruptedException 后打印一下就继续（丢失取消语义）。

**记忆锚点**

interrupt 只置标志 → sleep 不释放锁 / wait 释放锁 → 异常后恢复标志。

### 9. 【必答】线程与锁：synchronized 的锁升级与对象头 Mark Word？

**口述版**

synchronized 的锁信息存在对象头的 Mark Word 里，64 位下包含 hashCode、分代年龄、锁标志位。升级路径是无锁、偏向锁、轻量级锁、重量级锁。偏向锁针对同一个线程反复进入的场景，把线程 ID 记在 Mark Word 里，之后进来只比对 ID，不做 CAS；轻量级锁是在有竞争但竞争不激烈时，把 Mark Word 复制到栈上的 Lock Record，用 CAS 抢，失败就自旋；自旋失败或竞争加剧就膨胀成重量级锁，靠 monitor 对象的等待队列，线程进入阻塞。要注意偏向锁从 JDK 15 起默认关闭并标记废弃，因为维护成本高、收益有限。升级是单向的，不能降级，这样设计是为了避免反复切换的开销。

**短版**

Mark Word 存 hashCode、年龄和锁标志；升级路径无锁→偏向→轻量级（Lock Record + CAS + 自旋）→重量级（monitor 阻塞）；偏向锁是记录线程 ID 免 CAS，JDK 15 起默认关闭；升级单向不可逆。

**展开版**

- 机制链：首次加锁 CAS 写偏向线程 ID → 有竞争撤销偏向 → 复制 Mark Word 到栈帧 Lock Record → CAS 抢 → 失败自旋 → 膨胀为 monitor。
- 关键结构：64 位 Mark Word 的锁标志位（001 无锁、101 偏向、00 轻量、10 重量、11 GC 标记）、ObjectMonitor 的 entryList 与 waitSet。
- 触发条件：同一线程重复进入、多线程交替进入、真正的并发争用。
- 例外：调用 `hashCode` 会让偏向锁失效，因为 Mark Word 空间被占用；JDK 15+ 默认关闭偏向锁，直接走轻量级。
- 对比取舍：锁升级减少无竞争开销，代价是状态机复杂、撤销偏向需要安全点，反而拖慢高并发场景。

**追问预判**

- 为什么偏向锁要撤销 → 出现第二个线程竞争，必须恢复成可竞争的锁状态，撤销需要到达安全点。
- 轻量级锁自旋失败后怎样 → 膨胀为重量级锁，线程进入 monitor 的阻塞队列，避免一直空转。
- 锁能降级吗 → 不能，只有 GC 时可能重置对象头，正常路径单向升级。

**常见错误答法**

- 说锁升级可以来回降级（单向）。
- 认为偏向锁在所有 JDK 版本都默认开启（JDK 15 起默认关闭）。

**记忆锚点**

Mark Word 存锁状态 → 偏向免 CAS → 轻量级 CAS 自旋 → 重量级阻塞 → 单向升级。

### 10. 【必答】线程与锁：AQS 的 state 与等待队列是怎么工作的？

**口述版**

AQS 用一个 volatile 的 int state 表示同步状态，加一个 FIFO 的双向等待队列，队列节点是 Node，记录线程、前驱后继和等待状态。获取锁时先 tryAcquire 尝试改 state，失败就包装成节点入队，然后在队列里自旋检查前驱是不是头节点，是才再尝试获取，不是就 park 挂起，避免空转。释放锁时改 state 并 unpark 后继节点。AQS 把排队、阻塞、唤醒这些公共逻辑做好了，子类只需要实现 tryAcquire、tryRelease 这些模板方法，所以 ReentrantLock、Semaphore、CountDownLatch 都是它的实现。它同时支持独占和共享两种模式，共享模式下 release 会向后传播唤醒，这就是 CountDownLatch 能一次唤醒所有等待线程的原因。

**短版**

AQS 用 volatile int state 表示同步状态，用 FIFO 双向队列管理等待线程，节点自旋检查前驱并 park；子类只实现 tryAcquire/tryRelease 等模板方法；支持独占与共享，共享模式释放时向后传播唤醒。

**展开版**

- 机制链：`acquire` → `tryAcquire` 改 state → 失败则 `addWaiter` 入队 → `acquireQueued` 自旋判断前驱 → 必要时 `LockSupport.park`。
- 关键结构：`state`、`head`/`tail`、`Node.waitStatus`（SIGNAL、CANCELLED、CONDITION、PROPAGATE）、`ConditionObject` 的单向条件队列。
- 触发条件：锁获取失败、超时获取、可中断获取、条件等待。
- 例外：`tryAcquire` 抛异常时 AQS 不负责回滚；公平锁在 tryAcquire 里多一次 `hasQueuedPredecessors` 判断。
- 对比取舍：模板方法让同步器复用排队机制，代价是子类必须正确实现 state 语义，写错会导致唤醒丢失或死等。

**追问预判**

- state 是做什么的 → 表示同步状态，ReentrantLock 里是重入次数，Semaphore 里是可用许可数，CountDownLatch 里是剩余计数。
- 为什么节点要自旋再 park → 避免无谓的挂起和唤醒，只有前驱是头节点时才值得再抢一次。
- 共享和独占的区别 → 独占同一时刻只有一个线程成功，共享允许多个，释放时 wakeStatus 传播方式不同。

**常见错误答法**

- 说 AQS 队列是单向链表（是双向的 CLH 变体）。
- 认为 AQS 直接实现锁（它是框架，具体语义由子类 tryAcquire 决定）。

**记忆锚点**

volatile state → FIFO 双向队列 → 前驱判断 + park → 子类实现 tryXxx → 独占/共享。

### 11. 【必答】线程与锁：公平锁与非公平锁的差别，为什么默认非公平？

**口述版**

公平锁在获取时先检查队列里有没有排队的线程，有就老老实实排队，保证先来先得；非公平锁不管队列，直接 CAS 抢，抢到就执行。非公平吞吐更高，因为刚释放锁的线程和被唤醒的线程之间存在时间差，新来的线程可以趁机直接拿到锁，省掉一次挂起和唤醒的开销，而唤醒本身是有成本的。代价是可能饥饿，理论上后来的线程可以一直插队。ReentrantLock 默认非公平，可以用构造函数指定公平。要注意公平锁也不保证严格的公平语义，它只保证不插队，线程调度仍由操作系统决定。实践上除非有明确的顺序要求，比如某些资源分配或任务编排，否则都用非公平。

**短版**

公平锁先查队列有排队就排队，非公平锁直接 CAS 抢、允许插队；非公平省掉唤醒开销、吞吐更高但可能饥饿；ReentrantLock 默认非公平，公平锁只保证不插队，不保证调度顺序。

**展开版**

- 机制链：非公平 `tryAcquire` 直接 CAS 改 state → 成功则执行；公平版本先 `hasQueuedPredecessors`，有前驱就返回失败去排队。
- 关键结构：`ReentrantLock(boolean fair)`、`Sync` 的 FairSync/NonfairSync 两个子类、`hasQueuedPredecessors`。
- 触发条件：高并发争抢、对执行顺序有业务要求、需要避免饥饿。
- 例外：公平锁下 `tryLock()` 仍然可以插队成功，因为它不走排队逻辑。
- 对比取舍：非公平换吞吐，公平换顺序；公平锁的上下文切换更多，吞吐通常低一个量级。

**追问预判**

- 非公平一定饥饿吗 → 不保证，只是理论上可能，实际多数场景不会。
- 公平锁性能差多少 → 高竞争下差距明显，因为每次都要检查队列并频繁唤醒。
- synchronized 是公平的吗 → 不是，它不保证任何顺序，属于非公平实现。

**记忆锚点**

公平先看队列 → 非公平直接抢 → 省唤醒开销换吞吐 → 默认非公平。

### 12. 【进阶】线程与锁：ReentrantLock、读写锁、StampedLock 与 synchronized 怎么选？

**口述版**

synchronized 最简单，JVM 内置、自动释放、有锁升级，适合绝大多数场景，缺点是等锁不可中断、不支持超时和公平。ReentrantLock 是它的增强版，支持可中断、超时、公平和多个 Condition，适合需要这些能力的场景。ReentrantReadWriteLock 适合读多写少，读读可以并发，读写和写写互斥，但它不支持锁升级，只支持降级，而且读锁获取期间不能升级为写锁，容易写错。StampedLock 在 JDK 8 引入，支持乐观读，读的时候不加锁只拿一个 stamp，校验失败再退化成悲观读，性能更好，但它不可重入、不支持 Condition、写锁可能饥饿，适合读极多写极少的内部数据结构。选型顺序是先 synchronized，需要高级能力再往上选。

**短版**

synchronized 简单自动释放，默认首选；ReentrantLock 补可中断、超时、公平、多 Condition；读写锁适合读多写少，只支持降级不支持升级；StampedLock 有乐观读、性能最好但不可重入、无 Condition、写锁可能饥饿。

**展开版**

- 机制链：synchronized 走 monitor 与锁升级 → ReentrantLock 走 AQS 独占 → 读写锁用 state 高低 16 位分别记读锁和写锁 → StampedLock 用版本号 stamp 做乐观校验。
- 关键结构：`ReentrantReadWriteLock` 的 `Sync` 高低位拆分、`StampedLock.tryOptimisticRead` 与 `validate`、`ConditionObject`。
- 触发条件：读多写少、需要超时或可中断、缓存类数据结构、需要多个等待条件。
- 例外：StampedLock 不可重入，同一线程重复获取写锁会死锁；读写锁的读锁不能直接升级成写锁。
- 对比取舍：能力越强、使用约束越多，StampedLock 性能好但 API 容易误用，synchronized 简单但灵活性差。

**追问预判**

- 为什么读写锁不支持升级 → 两个读线程同时想升级会互相等待对方释放读锁，形成死锁，所以设计上禁止。
- StampedLock 的乐观读怎么用 → 先拿 stamp，读数据，再 `validate(stamp)`，失败就改用悲观读重读。
- ReentrantLock 一定比 synchronized 快吗 → 不一定，无竞争时 synchronized 有偏向和轻量级优化，性能相当甚至更好。

**常见错误答法**

- 说读写锁支持读锁升级为写锁（不支持）。
- 认为 StampedLock 可以替代所有锁（不可重入、无 Condition，限制多）。

**记忆锚点**

默认 synchronized → 要能力上 ReentrantLock → 读多写少读写锁 → 极致读用 StampedLock。

### 13. 【兜底】线程与锁：wait/notify 与 Condition 怎么配合，为什么必须持有锁？

**口述版**

wait 必须放在 synchronized 块里，因为"检查条件"和"进入等待"必须是原子的。如果不持锁，你判断条件不满足准备 wait 的间隙，另一个线程可能已经改了条件并 notify 了，这次通知就丢了，线程会一直等下去。wait 会释放锁并进入对象的 waitSet，notify 从 waitSet 里唤醒一个，notifyAll 唤醒全部，但它们都不释放锁，要等当前同步块执行完才真正释放。标准写法是在 while 循环里判断条件，不能用 if，因为被唤醒后条件可能又被别人改回去了，这叫虚假唤醒。Condition 是 Lock 版的实现，一个 Lock 可以有多个 Condition，能精确唤醒不同等待队列，比如生产者唤醒消费者、消费者唤醒生产者，比单一 waitSet 更细粒度。

**短版**

wait 必须持锁，否则条件判断和进入等待之间有竞态会丢通知；wait 释放锁，notify 不释放锁；必须用 while 而非 if 防虚假唤醒；Condition 支持一个锁多个等待队列，唤醒更精确。

**展开版**

- 机制链：持锁 → while 检查条件 → wait 释放锁入 waitSet → notify 移入 entryList → 重新竞争锁 → while 再检查。
- 关键结构：`Object.wait/notify/notifyAll` 的 monitor waitSet、`Condition` 的 `await/signal`、`ReentrantLock.newCondition()`。
- 触发条件：生产者消费者、有界队列、线程间状态同步。
- 例外：`wait(0)` 等价于无限等待；`notify` 唤醒哪个线程由 JVM 决定，不可控。
- 对比取舍：wait/notify 简单但只有一个等待集，容易误唤醒；Condition 精确但要多写几行代码。

**追问预判**

- 为什么用 while 不用 if → 虚假唤醒和被唤醒后条件再次变化，必须重新检查。
- notify 会释放锁吗 → 不会，只把线程从 waitSet 移到等待锁的队列，当前线程退出同步块才释放。
- Condition 比 wait 好在哪 → 一个锁可以建多个条件队列，能做到只唤醒该唤醒的那一类线程。

**常见错误答法**

- 在 if 里 wait（虚假唤醒后条件不成立仍继续执行）。
- 认为 notify 之后等待线程立刻继续执行（还要重新抢锁）。

**记忆锚点**

持锁判断 → while 等待 → wait 放锁 / notify 不放 → Condition 多队列精确唤醒。

## 三、CAS 与原子类

### 14. 【必答】CAS 与原子类：CAS 的原理、ABA 问题与解决？

**口述版**

CAS 是比较并交换，包含三个值：内存地址、期望值、新值。执行时先读内存当前值，和期望值相等才写入新值，否则失败，整个过程由 CPU 的一条指令保证原子性，Java 里通过 Unsafe 的 compareAndSwap 系列或者 VarHandle 调用。失败后通常自旋重试，这就是乐观锁的思路：先假设没人改，改的时候再校验。ABA 问题是：值从 A 变成 B 又变回 A，CAS 检查时看到的还是 A，就误以为没被改过，在链表、栈这类结构里可能导致引用错乱。解决办法是加版本号：AtomicStampedReference 带一个 int 版本戳，AtomicMarkableReference 带一个布尔标记，每次修改都递增版本，比较时连版本一起比。

**短版**

CAS 由内存值、期望值、新值三部分组成，靠 CPU 原子指令保证，失败自旋重试；ABA 是值改回原值导致误判，用 AtomicStampedReference 加版本号或 AtomicMarkableReference 加标记解决。

**展开版**

- 机制链：读内存值 → 与期望值比较 → 相等则写入并返回成功 → 不等则失败重试。
- 关键结构：`Unsafe.compareAndSwapInt`、`VarHandle.compareAndSet`、`AtomicStampedReference` 的 `stamp` 字段。
- 触发条件：无锁计数器、状态位切换、原子引用替换、并发栈与队列的入队出队。
- 例外：CAS 只能保证单个变量的原子性，多变量组合要用锁或 AtomicReference 包对象。
- 对比取舍：CAS 无阻塞、开销小，代价是自旋耗 CPU、高竞争下失败率高、只能保护一个变量。

**追问预判**

- ABA 在什么场景真的有害 → 无锁栈里节点被弹出、释放、复用后又压回来，CAS 会误认为栈顶没变。
- 版本号一定能彻底解决吗 → 能解决误判，但要注意版本号回绕，实际业务几乎不会触发。
- CAS 和 synchronized 的本质区别 → 一个乐观重试不加锁，一个悲观互斥会阻塞。

**常见错误答法**

- 说 CAS 是加锁实现的原子操作（是无锁指令）。
- 认为 ABA 只是理论问题，实际不会出（无锁数据结构里真实存在）。

**记忆锚点**

比较再交换 → CPU 原子指令 → 失败自旋 → ABA 用版本戳。

### 15. 【必答】CAS 与原子类：LongAdder 为什么比 AtomicLong 快？

**口述版**

AtomicLong 所有线程抢同一个 value 做 CAS，并发高了之后大量线程自旋失败，CPU 空转，竞争越激烈越慢。LongAdder 的思路是分散热点，它维护一个 base 加一个 Cell 数组，每个线程通过哈希映射到自己那个 Cell 上累加，不同的 Cell 分布在不同缓存行，互不竞争，最后 sum 的时候把 base 和所有 Cell 加起来。所以写操作几乎没有争用，代价是 sum 不是原子的，它只是遍历求和得到的一个近似快照，并发累加时可能不精确。另外 Cell 会按需扩容，最高到 CPU 核数级别。选型上，如果是高频计数、只关心最终结果、不要求强一致，用 LongAdder；如果需要精确的实时值或者要拿来做 CAS 判断，还是用 AtomicLong。

**短版**

AtomicLong 所有线程抢一个值 CAS，竞争激烈时自旋失败多；LongAdder 用 base 加 Cell 数组分散热点，各线程写各自的 Cell，sum 时汇总；写快但 sum 非原子、可能不精确，高频计数用 LongAdder，要精确值用 AtomicLong。

**展开版**

- 机制链：`add` 先尝试 CAS base → 失败则定位线程对应的 Cell → 对 Cell 做 CAS 累加 → `sum` 遍历 base 与 cells 求和。
- 关键结构：`base`、`Cell[] cells`、`cellsBusy` 自旋锁、`@sun.misc.Contended` 填充避免伪共享。
- 触发条件：高并发计数、监控埋点、QPS 统计、限流器计数。
- 例外：Cell 数组最多扩到接近 CPU 核数，扩容后单线程仍可能落到同一个 Cell 上。
- 对比取舍：分散竞争换来吞吐，代价是内存占用更高、sum 非原子、无法用于需要读后判断的场景。

**追问预判**

- LongAdder 的 sum 为什么不准 → 遍历时其他线程还在写 Cell，得到的是瞬时近似值。
- 什么时候不该用 LongAdder → 需要基于当前值做 CAS 判断，比如阈值控制、序列号生成。
- 伪共享是怎么处理的 → Cell 用 Contended 注解或填充字段，让每个 Cell 独占缓存行。

**常见错误答法**

- 说 LongAdder 的 sum 是强一致的（只是近似快照）。
- 认为 LongAdder 在所有场景都比 AtomicLong 好（读多写少时反而更慢）。

**记忆锚点**

base + Cell 分散 → 各写各的 → sum 近似 → 高频计数用它，精确判断用 AtomicLong。

### 16. 【进阶】CAS 与原子类：原子类全家桶怎么选，字段更新器有什么用？

**口述版**

原子类大致分四组：基本类型有 AtomicInteger、AtomicLong、AtomicBoolean；引用类型有 AtomicReference、AtomicStampedReference、AtomicMarkableReference；数组有 AtomicIntegerArray 这类，能对数组单个元素做原子更新；累加器有 LongAdder、LongAccumulator，适合高频统计。字段更新器 AtomicIntegerFieldUpdater 这类的作用是给已有类的 volatile 字段做原子更新，不用把字段改成原子类，省掉一层对象包装，适合对象数量大、内存敏感的场景，比如 Netty 的引用计数。使用条件是字段必须是 volatile、不能是 private 也不能是 final，而且要通过反射创建，有访问检查开销，通常声明成 static final 缓存起来。JDK 9 之后更推荐 VarHandle，它是标准的替代方案，性能更好，但 API 更偏底层。

**短版**

基本类型、引用类型（含带版本戳的）、数组、累加器四组；字段更新器能给已有 volatile 字段做原子更新、省对象包装，要求字段 volatile 且非 private/final，需静态缓存；JDK 9 起可用 VarHandle 替代。

**展开版**

- 机制链：字段更新器通过反射拿到字段偏移 → 调 Unsafe 的 CAS → 直接改对象内存，不额外创建包装对象。
- 关键结构：`AtomicIntegerFieldUpdater.newUpdater`、字段偏移量、`VarHandle` 的 `compareAndSet` 与内存序参数。
- 触发条件：海量小对象需要原子字段、引用计数、状态位、无锁队列的节点状态。
- 例外：字段是 private 时更新器创建会失败（除非调用方有权限）；继承来的字段要用父类做参数创建。
- 对比取舍：省内存和一层间接，代价是字段必须 volatile、类型受限、反射创建有启动开销。

**追问预判**

- 为什么不直接用 AtomicInteger 字段 → 每个对象多一个原子对象头和一次引用跳转，数量大时内存和缓存开销明显。
- 更新器能操作 static 字段吗 → 不能，静态字段要用 AtomicInteger 本身。
- VarHandle 和更新器的关系 → VarHandle 是 JDK 9 引入的标准 API，能力更强，更新器属于过渡方案。

**常见错误答法**

- 用非 volatile 字段创建更新器（运行时会报错）。
- 认为更新器能操作 final 字段（final 不可变，不能原子更新）。

**记忆锚点**

基本/引用/数组/累加器 → 字段更新器省包装 → 必须 volatile → JDK 9 用 VarHandle。

### 17. 【兜底】CAS 与原子类：CAS 的缺点是什么，高竞争下为什么会退化？

**口述版**

CAS 有三个明显缺点。第一是自旋开销，失败就要重试，高竞争下大量线程反复失败，CPU 全耗在无效比较上，吞吐反而下降。第二是只能保证单个变量的原子性，要同时改两个变量就得用锁，或者把它们包成一个对象用 AtomicReference。第三是 ABA 问题，需要版本号兜底。高竞争退化的本质是 CAS 的失败率随并发度上升，线程数和争用成正比，重试次数也成正比，最后有效工作占比越来越低。缓解手段有：分散热点，像 LongAdder 那样拆成多个计数单元；退化为锁，竞争超过阈值时用 synchronized 或 ReentrantLock；限制并发度，用信号量或分段。所以 CAS 适合低到中等竞争的场景，不是越无锁越好。

**短版**

自旋耗 CPU、只能保证单变量原子、存在 ABA；高竞争下失败率和重试次数一起上升，有效吞吐下降；缓解靠分散热点（LongAdder）、超阈值退化为锁、限制并发度。

**展开版**

- 机制链：多线程同时 CAS → 只有一个成功 → 其余自旋重试 → 失败率随并发度上升 → CPU 空转比例增加。
- 关键结构：自旋次数、`Thread.onSpinWait`、退避策略、分段计数。
- 触发条件：秒杀计数、高频状态切换、无锁队列的入队冲突。
- 例外：单生产者或低竞争下 CAS 几乎没有失败，性能优于锁。
- 对比取舍：无锁避免阻塞和上下文切换，代价是高竞争下退化和实现复杂度上升。

**追问预判**

- 怎么判断 CAS 已经成为瓶颈 → 看 CPU 使用率高但吞吐上不去，火焰图集中在原子操作和自旋。
- 竞争激烈时怎么改 → 换 LongAdder、加分段、或用锁保护临界区，减少无效重试。
- CAS 能替代锁吗 → 不能，多变量一致性、需要阻塞等待的场景仍然要用锁。

**常见错误答法**

- 认为无锁一定比加锁快（高竞争下会退化）。
- 说 CAS 能保证多个变量的原子性（只能单变量）。

**记忆锚点**

自旋耗 CPU → 单变量 → ABA → 高竞争退化 → 分散 / 退化锁 / 限并发。

## 四、并发容器与 ThreadLocal

### 18. 【必答】并发容器：ConcurrentHashMap 和 synchronizedMap 有什么区别？

**口述版**

Collections.synchronizedMap 是一个包装器，把所有方法都加同一把 mutex 锁，等于整张表串行化，读和读之间也互斥，并发度是 1。ConcurrentHashMap 是桶级并发，JDK 8 用 CAS 加 synchronized 锁单个桶头节点，读操作完全不加锁，靠 volatile 保证可见性，并发度约等于数组长度。所以高并发下 ConcurrentHashMap 吞吐高一个量级，而且它提供了 putIfAbsent、computeIfAbsent、merge 这些原子复合操作，synchronizedMap 没有。要注意两点：synchronizedMap 遍历时必须手动 synchronized 整个 map，否则会 CME；ConcurrentHashMap 的迭代器是弱一致的，不抛 CME 但可能读到旧数据，size 也只是估算。它的 key 和 value 都不允许 null。

**短版**

synchronizedMap 一把全局锁，读写全串行，遍历要手动加锁；ConcurrentHashMap 桶级锁加 CAS、读无锁、并发度约等于桶数，提供原子复合操作，迭代器弱一致、size 估算、不允许 null。

**展开版**

- 机制链：synchronizedMap 每个方法 `synchronized (mutex)` → 单线程通过；CHM 定位桶 → 空桶 CAS → 非空桶锁头节点。
- 关键结构：`SynchronizedMap` 的 mutex、CHM 的 `table`、`Node` 的 volatile 字段、`sizeCtl`、`CounterCell`。
- 触发条件：高并发读写缓存、本地状态表、去重集合、计数器映射。
- 例外：CHM 的复合操作只在单个 key 上原子，跨 key 仍需额外同步；`Collections.synchronizedMap` 允许 null。
- 对比取舍：CHM 吞吐高但语义是弱一致；synchronizedMap 语义直观但并发能力差，基本只适合极低并发或遗留代码。

**追问预判**

- CHM 的 size 为什么不准 → 并发下用 CounterCell 估算，不阻塞写操作，只能作为参考。
- 什么时候还必须额外加锁 → 需要跨 key 的原子性，比如转账式的同时更新两个条目。
- synchronizedMap 遍历为什么要加锁 → 迭代器不是线程安全的，外部修改会抛 CME。

**常见错误答法**

- 说 ConcurrentHashMap 用分段锁（JDK 8 已改为桶级锁）。
- 认为 CHM 的所有操作组合起来都是原子的（只有单 key 复合操作原子）。

**记忆锚点**

synchronizedMap 一把大锁 → CHM 桶级锁 + 无锁读 → 弱一致 → 跨 key 仍需同步。

### 19. 【必答】并发容器：阻塞队列怎么选，Array 和 Linked 版本差在哪？

**口述版**

常见的有五种。ArrayBlockingQueue 基于数组、必须指定容量、有界，用一把锁加两个 Condition 控制非空非满，内存紧凑、性能稳定，适合固定容量的生产消费。LinkedBlockingQueue 基于链表，默认容量是 Integer.MAX_VALUE，等于近似无界，用两把锁分别控制入队和出队，吞吐更高，但一定要手动指定容量，否则就是线程池 OOM 的常见来源。SynchronousQueue 不存储元素，生产者必须等到消费者接手，适合传递性场景，线程池配合它时会直接扩容线程。PriorityBlockingQueue 是无界优先队列，按优先级出队，不保证同优先级顺序。DelayQueue 按延迟时间出队，适合定时任务和重试。选型先看需不需要有界和排序，再看吞吐。

**短版**

ArrayBlockingQueue 有界数组、单锁双条件；LinkedBlockingQueue 链表、双锁、默认近似无界（务必指定容量）；SynchronousQueue 不存储、必须交接；PriorityBlockingQueue 无界按优先级；DelayQueue 按延迟出队。

**展开版**

- 机制链：入队 `put` 在满时 `notFull.await` → 出队 `take` 在空时 `notEmpty.await` → 操作后 signal 对方条件。
- 关键结构：`ReentrantLock` + `Condition`、`LinkedBlockingQueue` 的 `takeLock`/`putLock` 与 `AtomicInteger count`。
- 触发条件：生产者消费者、线程池工作队列、异步任务缓冲、重试与延迟调度。
- 例外：`PriorityBlockingQueue` 无界，`put` 不会阻塞，只会在扩容时短暂加锁；`SynchronousQueue` 支持公平模式。
- 对比取舍：数组有界可控但容量固定；链表吞吐高但易被误用成无界；同步队列零存储但耦合生产消费节奏。

**追问预判**

- 为什么 LinkedBlockingQueue 默认容量这么大 → 历史设计为了兼容，实际生产必须显式传容量。
- 双锁队列一定比单锁快吗 → 入队出队能并行，但计数用 AtomicInteger 有额外开销，低竞争下差距不大。
- DelayQueue 怎么实现延迟 → 元素实现 Delayed 接口，堆顶按到期时间排序，取不到就 awaitNanos。

**常见错误答法**

- 认为 LinkedBlockingQueue 天然有界（默认接近无界）。
- 说 SynchronousQueue 会缓存一个元素（它不存储）。

**记忆锚点**

Array 有界单锁 → Linked 双锁但要限容 → Synchronous 交接 → Priority 排序 → Delay 延时。

### 20. 【必答】ThreadLocal：引用链是什么，为什么会内存泄漏？

**口述版**

ThreadLocal 的值不是存在 ThreadLocal 对象里，而是存在 Thread 内部的 ThreadLocalMap 里，key 是 ThreadLocal 的弱引用，value 是强引用。引用链是 Thread 到 ThreadLocalMap 到 Entry，Entry 的 key 是弱引用，value 是强引用。泄漏的原因是：当外部不再持有 ThreadLocal 引用，key 会被 GC 回收变成 null，但 value 还被 Entry 强引用着，只要线程活着，这个 Entry 和 value 就一直存在，而且 key 为 null 的 Entry 无法再通过正常方式访问。线程池里的核心线程长期存活，这个问题会被放大。所以规范做法是用完必须 remove，尤其是在线程池任务里要用 try-finally 保证清理。get 和 set 时会顺带清理一部分 key 为 null 的 Entry，但不能依赖它。

**短版**

值存在 Thread 的 ThreadLocalMap 里，Entry 的 key 是 ThreadLocal 弱引用、value 是强引用；外部引用消失后 key 被回收成 null，value 仍被线程强引用，线程不死就不释放；线程池会放大，必须 try-finally remove。

**展开版**

- 机制链：`set` 写入当前线程的 ThreadLocalMap → Entry 弱引用 key → 外部引用断开后 key 被 GC → value 仍可达 → 泄漏。
- 关键结构：`Thread.threadLocals`、`ThreadLocalMap.Entry extends WeakReference<ThreadLocal<?>>`、`expungeStaleEntry` 的探测式清理。
- 触发条件：线程池复用、Web 容器请求线程、异步任务上下文传递。
- 例外：线程结束被回收时，整个 ThreadLocalMap 一起回收，泄漏只发生在长生命周期线程上。
- 对比取舍：弱引用 key 让 ThreadLocal 对象本身可回收，代价是产生 key 为 null 的僵尸 Entry，需要用完 remove。

**追问预判**

- 为什么 key 用弱引用 → 让 ThreadLocal 对象在外部不再引用时能被回收，否则连 key 都泄漏。
- 只用 get/set 不 remove 会怎样 → 部分 stale Entry 会被顺带清理，但不确定，长期运行仍会积累。
- 子线程能拿到父线程的值吗 → 默认不能，需要 InheritableThreadLocal 或手动透传。

**记忆锚点**

值在 Thread 里 → key 弱引用、value 强引用 → key 没了 value 还在 → 必须 remove。

### 21. 【进阶】ThreadLocal：线程池下怎么传递上下文，InheritableThreadLocal 为什么不够？

**口述版**

InheritableThreadLocal 的原理是在创建子线程时，把父线程的 inheritableThreadLocals 复制一份给子线程，所以只在线程创建那一刻生效。线程池的线程是复用的，池里的线程通常是池初始化时创建的，不会为每个任务新建线程，所以任务拿到的上下文是创建时的那份，甚至可能是上一个任务残留的。线程池下正确的做法有三种：一是在任务提交时手动捕获上下文，用装饰器模式包一层 Runnable，执行前 set、执行后 remove，Spring 的 TaskDecorator 就是这个思路；二是用 TransmittableThreadLocal 这类组件，通过字节码增强在任务提交和执行时做快照和恢复；三是显式把上下文作为参数传下去，最笨但最可靠。注意异步链路里 TraceId、用户身份、租户信息都属于这类问题。

**短版**

InheritableThreadLocal 只在线程创建时复制父线程的值，线程池线程复用导致不生效或串数据；解法是提交时捕获并用装饰器透传（TaskDecorator）、用 TTL 做快照恢复、或显式参数传递。

**展开版**

- 机制链：创建线程 → 复制父线程 inheritableThreadLocals → 线程复用后不再复制 → 任务读到旧值或残留值。
- 关键结构：`ThreadLocal.createInheritedMap`、`Thread.inheritableThreadLocals`、`TaskDecorator`、`TransmittableThreadLocal` 的 holder。
- 触发条件：线程池执行异步任务、CompletableFuture 链路、MQ 消费线程、定时任务。
- 例外：`InheritableThreadLocal` 在手动 new Thread 的场景仍然有效，只是不适用于池化线程。
- 对比取舍：装饰器方案零依赖但要覆盖所有提交入口；TTL 透明但引入字节码增强和额外维护成本。

**追问预判**

- 为什么 TraceId 会丢 → 异步线程没有继承 MDC 里的 ThreadLocal，日志框架拿不到。
- 装饰器方案要注意什么 → 执行完必须 remove，否则池线程残留上下文会串到下一个任务。
- TTL 的原理 → 在任务提交时捕获快照，执行前回放、执行后恢复，依赖对线程池的增强。

**常见错误答法**

- 认为 InheritableThreadLocal 在线程池里也能自动传递（只在创建时复制）。
- 用静态变量代替上下文传递（并发下互相覆盖）。

**记忆锚点**

只在建线程时复制 → 池化失效 → 装饰器 / TTL / 显式传参 → 用完 remove。

### 22. 【兜底】并发容器：CopyOnWriteArrayList 的适用场景与代价？

**口述版**

CopyOnWriteArrayList 的思路是写时复制：所有读操作都不加锁，直接读当前数组；写操作先加锁，复制出一个新数组，在新数组上修改，然后把内部引用指向新数组。因为读的是快照，读多写少时性能非常好，而且迭代器不会抛 ConcurrentModificationException。代价有三个方面：写操作要复制整个数组，内存瞬时翻倍，频繁写会非常慢；数据有延迟，写完的瞬间其他线程可能还读到旧数组；只适合元素少且几乎不变的场景。典型用途是监听器列表、白名单、配置快照，读多写极少。反过来，如果写操作占比高或者元素很多，就应该用 ConcurrentLinkedQueue 或者加锁的集合，绝不能用它做高频更新的缓存。

**短版**

写时复制：读无锁读快照，写加锁复制新数组再替换引用；读多写少、元素少时合适，迭代器不抛 CME；代价是写复制、内存翻倍、数据延迟，写多的场景不适合。

**展开版**

- 机制链：`add` 加锁 → `Arrays.copyOf` 复制 → 新数组写入元素 → 替换 `array` 引用 → 解锁。
- 关键结构：volatile 的 `array` 引用、`ReentrantLock`、`COWIterator` 持有旧数组快照。
- 触发条件：监听器注册、路由表、黑白名单、配置热更新。
- 例外：批量写用 `addAll` 只复制一次；迭代器的 `remove` 直接抛 UnsupportedOperationException。
- 对比取舍：读性能和无锁换来写放大与内存占用，元素多时复制成本线性上升。

**追问预判**

- 为什么迭代器不抛 CME → 迭代的是创建时的数组快照，和后续修改完全隔离。
- 内存翻倍会 OOM 吗 → 大数组高频写会，所以只适合小集合。
- 和读写锁怎么选 → 写少读多且要快照语义用 COW，读写都频繁用读写锁或 CHM。

**常见错误答法**

- 用它做高频更新的缓存（写放大严重）。
- 认为迭代器能删除元素（会抛 UnsupportedOperationException）。

**记忆锚点**

读快照无锁 → 写复制数组 → 内存翻倍、有延迟 → 只适合读多写少。

## 五、异步编排与虚拟线程

### 23. 【必答】异步编排与虚拟线程：CompletableFuture 的常用编排方法与异常传播？

**口述版**

创建有两个入口：runAsync 接 Runnable 没有返回值，supplyAsync 接 Supplier 有返回值。编排分三类：串行用 thenApply 做转换、thenCompose 做扁平化、thenRun 只执行不消费结果；并行组合用 thenCombine 合并两个结果、allOf 等全部完成、anyOf 等任意一个完成；异常处理用 exceptionally 兜底、handle 同时处理正常和异常、whenComplete 只做收尾不改变结果。异常传播有个关键点：链上任何一步抛异常，后续的 thenApply 都会被跳过，异常被包成 CompletionException 往后传，直到遇到 exceptionally 或 handle 才被处理；如果一直没处理，只有在 join 或 get 时才抛出。所以异步链必须显式收尾，否则异常会静默丢失。

**短版**

runAsync 无返回值、supplyAsync 有；thenApply 转换、thenCompose 扁平化、thenCombine/allOf/anyOf 组合；exceptionally、handle、whenComplete 处理异常；链上异常会跳过后续步骤并以 CompletionException 传递，不处理就只能靠 join/get 才发现。

**展开版**

- 机制链：任务完成 → 触发依赖的 Completion → 沿依赖栈执行 → 异常写入 result 字段 → 后续阶段判断异常则跳过。
- 关键结构：`CompletableFuture` 的 `result` 字段、`Completion` 栈、`AltResult` 包装异常、`CompletionException`。
- 触发条件：并行 RPC 聚合、异步流水线、多数据源合并、超时降级。
- 例外：`whenComplete` 里抛异常会覆盖原结果；`handle` 无论成功失败都会执行并能改变结果。
- 对比取舍：链式编排可读性好、无阻塞，代价是异常语义隐晦、调试栈不直观、线程来源不明确。

**追问预判**

- thenApply 和 thenCompose 的区别 → 前者返回普通值、会产生嵌套，后者返回新的 CompletableFuture、用于扁平化。
- 异常不处理会怎样 → 链路静默失败，只有 get/join 时才抛，日志里可能什么都没有。
- allOf 能直接拿结果吗 → 不能，它返回 CompletableFuture<Void>，要自己遍历各个 future 取结果。

**常见错误答法**

- 认为 thenApply 会自动处理异常（异常会跳过该阶段）。
- 以为 allOf 返回结果列表（只返回 Void，需逐个 join）。

**记忆锚点**

thenApply 转换 / thenCompose 扁平 → combine/allOf 组合 → 异常跳过后续 → 必须 exceptionally/handle 收尾。

### 24. 【必答】异步编排与虚拟线程：默认线程池有什么坑，线程池串用风险在哪？

**口述版**

supplyAsync 不传 Executor 时用的是 ForkJoinPool.commonPool，线程数是 CPU 核数减一，全局共享。第一个坑是阻塞：如果任务里做 RPC 或查库，会把 commonPool 的线程占满，所有用默认池的异步任务一起排队甚至饿死。第二个坑是隔离缺失：不同业务共用同一个池，一个慢业务能把其他业务拖垮。第三个坑是线程来源不确定：thenApply 这类回调可能在完成任务的那个线程上执行，也可能在调用线程上执行，导致同一个链上的代码跑在不同池里。所以规范是每个业务显式传自己的线程池，并且让整条链用同一个池，避免跨池串用造成死锁式等待，比如 A 池的任务等 B 池的结果，而 B 池的任务又在等 A 池。

**短版**

默认用全局 ForkJoinPool.commonPool（核数减一），阻塞任务会拖垮所有默认异步；不同业务共用池没有隔离；回调线程来源不确定；应显式传业务线程池并保证整条链同池，避免跨池互相等待。

**展开版**

- 机制链：`supplyAsync` 无 Executor → 提交到 commonPool → 阻塞占满工作线程 → 其他任务排队；回调阶段在完成线程或调用线程执行。
- 关键结构：`ForkJoinPool.commonPool()`、`AsyncSupply`/`UniApply` 的 executor 字段、`ThreadPerTaskExecutor`（虚拟线程场景）。
- 触发条件：异步调用下游、批量并行查询、混合多个数据源的聚合。
- 例外：JDK 21 起 `Executors.newVirtualThreadPerTaskExecutor()` 可作为每任务一线程的执行器，适合阻塞场景。
- 对比取舍：默认池省事但无隔离，自定义池隔离好但线程资源要规划和监控。

**追问预判**

- 为什么回调线程不固定 → 如果任务已完成，回调直接在调用线程执行；未完成则由完成它的线程执行。
- 跨池串用的典型死锁 → 两个池的线程互相等待对方池里的任务完成，池满后谁也无法推进。
- 怎么选执行器 → IO 密集用独立池或虚拟线程执行器，CPU 密集用有界池，别用 commonPool 跑阻塞。

**常见错误答法**

- 认为 thenApply 一定在同一个线程执行（同步或异步取决于完成时机）。
- 把所有异步任务都丢给默认池（阻塞会互相拖累）。

**记忆锚点**

默认 commonPool 全局共享 → 阻塞即拖垮 → 显式传池 → 整条链同池。

### 25. 【进阶】异步编排与虚拟线程：超时、降级与批量聚合怎么做？

**口述版**

超时有三层手段：一是 JDK 9 的 orTimeout，超时后以 TimeoutException 完成；二是 completeOnTimeout，超时给一个默认值，更适合降级；三是底层 RPC 客户端自己的超时，这是最可靠的，因为上层超时只是不再等待，请求可能还在下游跑。批量聚合一般用 allOf 等全部完成，但要注意它一个失败就整体失败，所以要配合 handle 把每个 future 转成"成功或失败"的结果对象，再统一汇总，做到部分成功可用。如果要求整体响应时间可控，就用 orTimeout 或配合 ScheduledExecutorService 做竞速，先到先返回。还要注意别让超时的任务继续占用线程和连接，超时后要能取消，取消不了至少要有熔断和限流兜底。

**短版**

超时用 orTimeout/completeOnTimeout 加下游自身超时；批量聚合用 allOf 配 handle 把每个结果转成成功或失败再汇总，支持部分成功；整体时限用竞速或超时兜底，并注意超时后取消任务、释放线程与连接。

**展开版**

- 机制链：`orTimeout` 注册一个延时任务 → 到点 CAS 把结果置为 TimeoutException → 后续阶段走异常分支。
- 关键结构：`Delayer` 调度、`completeExceptionally`、`handle` 聚合、`anyOf` 竞速。
- 触发条件：多下游并行聚合、首页聚合接口、批量查询、第三方接口降级。
- 例外：`orTimeout` 不会中断底层任务，只是让 future 提前完成，资源仍可能被占用。
- 对比取舍：超时保护响应时间，代价是可能产生无用的下游调用；部分成功提升可用性，代价是结果语义变复杂。

**追问预判**

- orTimeout 会中断任务吗 → 不会，只改变 future 状态，底层调用需要自己的超时和取消机制。
- 怎么实现部分成功 → 每个 future 用 handle 包成 Result 对象，allOf 后再按成功失败分类汇总。
- 超时后线程还在跑怎么办 → 设置下游超时、用可取消的客户端、配熔断限流，避免线程和连接被长期占用。

**常见错误答法**

- 认为 orTimeout 会终止正在执行的任务（只是让 future 提前完成）。
- 用 allOf 后直接 join，一个失败整条链路异常（没有做部分成功处理）。

**记忆锚点**

orTimeout 提前完成 → completeOnTimeout 给默认值 → allOf + handle 部分成功 → 下游自身超时才是根本。

### 26. 【必答】异步编排与虚拟线程：虚拟线程解决什么问题，适合什么场景？

**口述版**

虚拟线程是 JDK 21 正式的特性，由 JVM 调度而不是操作系统调度。它挂载在少量载体线程上，遇到阻塞 IO 时会从载体线程卸载，把状态存到堆里，IO 就绪后再重新挂载继续执行。所以它的创建成本极低，可以做到一个请求一个线程，把原来靠线程池加异步回调的复杂度降下来，代码回到同步写法，可读性和可调试性都更好。它适合 IO 密集、阻塞时间长的场景，比如调下游 HTTP、查数据库、发消息。不适合 CPU 密集任务，因为核还是那几个，虚拟线程不会让计算更快；也不适合长时间持有锁或大量 ThreadLocal 的场景。要注意它是更省资源，不是更快，吞吐提升来自能同时容纳更多阻塞请求。

**短版**

虚拟线程由 JVM 调度、阻塞时从载体线程卸载，创建成本极低，可以一请求一线程；适合 IO 密集高并发，把异步回调改回同步写法；CPU 密集无收益，不是更快而是更省资源。

**展开版**

- 机制链：虚拟线程挂载到载体线程 → 遇到阻塞 IO 卸载 → Continuation 保存栈到堆 → IO 就绪重新挂载恢复执行。
- 关键结构：载体线程池（默认 ForkJoinPool）、Continuation、`Thread.ofVirtual()`、`newVirtualThreadPerTaskExecutor()`。
- 触发条件：高并发 HTTP 调用、数据库访问、消息等待、并发量远超核数的服务。
- 例外：JNI 调用和 JDK 21 的 synchronized 长阻塞会钉住载体线程，后者在 JDK 24 的 JEP 491 已改善。
- 对比取舍：同步代码换高并发，代价是失去线程池的排队与隔离、监控工具适配滞后、下游要扛住真实并发。

**追问预判**

- 虚拟线程比平台线程快吗 → 不更快，单任务延迟接近，优势在高并发下的资源占用。
- 什么时候不该用 → CPU 密集计算、需要精细控制并发排队、依赖 ThreadLocal 缓存的场景。
- 怎么限制并发 → 用 Semaphore 控制对下游的并发度，而不是限制虚拟线程数量。

**常见错误答法**

- 说虚拟线程能提升单任务计算速度（不会）。
- 把虚拟线程当线程池的替代品来池化使用（不该池化）。

**记忆锚点**

JVM 调度 → 阻塞即卸载 → 一请求一线程 → IO 密集专用，不是更快是更省。

### 27. 【兜底】异步编排与虚拟线程：虚拟线程和现有线程池模型怎么共存？

**口述版**

共存的原则是分工：IO 密集、阻塞时间长的入口用虚拟线程，每个任务一个；CPU 密集的计算任务仍用固定大小的平台线程池，避免抢占核。不要池化虚拟线程，创建成本极低，池化只会引入排队和状态复用问题；限流要用信号量控制对下游的并发，而不是限制线程数。迁移时要注意三点：把线程池执行器换成虚拟线程执行器；检查 synchronized 里的长阻塞，JDK 21 会钉住载体线程，改用 ReentrantLock；清理 ThreadLocal，虚拟线程数量巨大时 ThreadLocal 会放大内存占用。另外连接池大小、下游限流阈值这些容量参数要按真实并发重新评估，否则虚拟线程把并发放大后会把下游打垮。

**短版**

IO 阻塞用虚拟线程、CPU 密集仍用固定平台线程池；不要池化虚拟线程，限流用 Semaphore；迁移要替换执行器、把 synchronized 长阻塞改 ReentrantLock、清理 ThreadLocal，并重新评估连接池和下游容量。

**展开版**

- 机制链：请求线程改为虚拟线程 → 阻塞时卸载 → 载体线程继续调度其他虚拟线程 → 下游并发量被信号量或连接池约束。
- 关键结构：`Executors.newVirtualThreadPerTaskExecutor()`、`Semaphore`、`ReentrantLock`、连接池上限、载体线程池大小。
- 触发条件：Web 容器线程模型改造、异步任务替换、批量 IO 任务。
- 例外：`synchronized` 在 JDK 21 仍会钉住载体线程（JDK 24 已修复）；部分阻塞库基于 native 或 JNI，卸载不掉。
- 对比取舍：虚拟线程简化并发模型，代价是并发度失控风险、监控和诊断工具适配不足、依赖库兼容性要验证。

**追问预判**

- 为什么不能池化虚拟线程 → 创建和销毁几乎无成本，池化反而带来排队和状态污染。
- 怎么控制对下游的压力 → 连接池上限加信号量，必要时配合熔断和超时。
- 迁移后线程数指标怎么变 → 平台线程数大幅下降，虚拟线程数上升，监控要看虚拟线程数量和载体线程利用率。

**常见错误答法**

- 用固定大小的虚拟线程池来"控制并发"（应使用信号量）。
- 直接把所有任务切到虚拟线程，不评估下游容量（可能把下游打垮）。

**记忆锚点**

IO 用虚拟线程 → CPU 用平台线程池 → 不池化、信号量限流 → 换执行器 + 改 synchronized + 清 ThreadLocal。

## 六、死锁与并发排查

### 28. 【必答】死锁与并发排查：死锁怎么产生，怎么用 jstack 定位？

**口述版**

死锁要同时满足四个条件：互斥、持有并等待、不可剥夺、循环等待，破坏任意一个就能避免。工程上最常见的是两个线程以相反顺序抢两把锁，形成 AB-BA。定位上，先 jps 找到进程，再 jstack 打印线程栈，JVM 会自动检测并输出 Found one Java-level deadlock，下面会列出涉及的线程、各自持有的锁和等待的锁，非常直观。如果没有自动检测到，就看 BLOCKED 状态且栈顶停在等锁位置的线程，逐个对照持有的监视器。解决思路有三：统一加锁顺序，这是最有效的；用 tryLock 带超时，拿不到就放弃并回退；缩小锁范围或用无锁结构。排查完还要复盘为什么会写出这种代码，通常和嵌套调用、回调有关。

**短版**

四条件：互斥、持有并等待、不可剥夺、循环等待；典型是 AB-BA 反序加锁。jstack 会自动打印 Found one Java-level deadlock 和持有/等待的锁；解决靠统一加锁顺序、tryLock 超时、缩小锁范围。

**展开版**

- 机制链：线程 A 持锁 1 等锁 2 → 线程 B 持锁 2 等锁 1 → 双方 BLOCKED → 循环等待无法推进。
- 关键结构：jstack 输出的 deadlock 段落、`Thread.getAllStackTraces`、`ThreadMXBean.findDeadlockedThreads`。
- 触发条件：多锁嵌套、锁顺序不一致、事务中调用外部服务回调、线程池跨池等待。
- 例外：数据库死锁由数据库自己检测并回滚其中一个事务，和 JVM 死锁不是一回事。
- 对比取舍：统一顺序预防成本低但需要全局约定；超时重试实现简单但会放大流量、需配合退避。

**追问预判**

- 只有 BLOCKED 就是死锁吗 → 不一定，可能只是短暂竞争，要看是否存在环和长时间不推进。
- 代码里怎么主动检测 → `ThreadMXBean.findDeadlockedThreads` 定时巡检并告警。
- 死锁和活锁的区别 → 死锁线程阻塞不动，活锁线程一直在重试但无法推进。

**常见错误答法**

- 说加锁就可能导致死锁、无法避免（破坏循环等待即可）。
- 认为 jstack 只能看到线程栈，不能检测死锁（会自动检测）。

**记忆锚点**

四条件 → AB-BA 反序 → jstack 自动报死锁 → 统一顺序 / tryLock 超时。

### 29. 【进阶】死锁与并发排查：CPU 飙高和线程阻塞分别怎么定位？

**口述版**

CPU 飙高先确认是不是业务线程在烧：top 找到进程，top -Hp 找到占用最高的线程，把线程 ID 转成十六进制，再到 jstack 里按 nid 找对应栈。如果栈顶是业务代码，就看是不是死循环、正则回溯、大对象序列化或加密计算；如果栈顶是 GC 线程，那问题在内存，用 jstat 看 GC 频率和耗时，jmap 或堆 dump 找大对象和泄漏。线程阻塞则是另一套：看 BLOCKED 找等锁的线程和锁持有者，看 WAITING 找 park 或 await 的位置，重点看是不是线程池满、连接池耗尽或者下游无响应。实践上两者经常同时出现：下游变慢导致线程堆积，线程堆积又加剧 GC 和上下文切换，所以要结合 CPU、GC、线程数、连接池指标一起看，不能只盯一个。

**短版**

CPU 高：top 找进程、top -Hp 找线程、转十六进制后在 jstack 按 nid 定位，区分业务死循环和 GC 线程；阻塞：BLOCKED 查锁持有者、WAITING 查 park/await，结合线程池、连接池、下游 RT 一起判断。

**展开版**

- 机制链：定位进程 → 定位线程 → 栈映射 → 判断是计算密集、GC 还是锁等待 → 结合指标确认根因。
- 关键结构：`top -Hp`、`printf '%x'`、jstack 的 nid、`jstat -gcutil`、`jcmd Thread.print`。
- 触发条件：接口超时、线程数暴涨、GC 频繁、CPU 打满但吞吐下降。
- 例外：容器里要按容器 CPU 限制看，宿主机 top 会包含其他容器；短时飙高可能只是 JIT 编译。
- 对比取舍：单次采样可能抓到瞬时状态，要连续多次采样对比；dump 有停顿成本，生产要谨慎。

**追问预判**

- 为什么 jstack 里同一线程栈在变 → 说明在正常执行，死循环的栈通常固定在同一位置。
- GC 导致的 CPU 高怎么确认 → jstat 看 YGC/FGC 次数与耗时，GC 线程在 jstack 里会出现。
- 线程数暴涨但 CPU 不高是什么问题 → 大量线程阻塞在 IO 或等待，查下游和连接池。

**常见错误答法**

- 只 dump 一次就下结论（采样有偶然性）。
- 看到 RUNNABLE 就认为在烧 CPU（IO 阻塞也显示 RUNNABLE）。

**记忆锚点**

top → top -Hp → 十六进制 nid → jstack 对栈 → 分业务/GC/锁。

### 30. 【兜底】死锁与并发排查：伪共享和指令重排导致的 bug 怎么复现与避免？

**口述版**

伪共享是多个线程修改同一个缓存行里的不同变量，缓存行是 64 字节，一个变量被改会让整行失效，其他线程的缓存副本全部作废，看起来没共享数据却互相拖慢。典型现象是加了多线程反而更慢，或者压测时 CPU 高但吞吐上不去。解决靠填充或 `@Contended`，让热点变量独占缓存行，Disruptor 的 Sequence 就是经典实现。指令重排是编译器和 CPU 为了优化调整执行顺序，单线程看起来没问题，多线程就会读到半初始化对象，最典型的是双重检查锁单例，instance 必须加 volatile，否则可能拿到构造未完成的对象。复现靠压测、jcstress 这类并发测试工具，避免靠 JMM 的 happens-before 规则：用 volatile、锁、final 字段或线程安全容器建立可见性，不要依赖代码书写顺序。

**短版**

伪共享是多线程改同一缓存行的不同变量导致缓存行反复失效，用填充或 @Contended 让变量独占缓存行；指令重排会让多线程看到半初始化对象，DCL 单例必须加 volatile；靠压测和 jcstress 复现，靠 happens-before 规则避免。

**展开版**

- 机制链：缓存行 64 字节 → 一个变量写入使整行失效 → 其他核重新加载 → 伪共享；重排则让写操作对其他线程可见顺序与源码不一致。
- 关键结构：缓存行大小、`@sun.misc.Contended`、对象字段填充、`volatile` 的内存屏障、happens-before 规则。
- 触发条件：高并发计数器、队列的 head/tail 指针、无锁数据结构、DCL 单例。
- 例外：单核或缓存行对齐恰好不冲突时不会出现；重排在单线程内不可观察，只有跨线程才暴露。
- 对比取舍：填充浪费内存换性能，`@Contended` 需要开启参数；volatile 有性能开销，但比锁轻。

**追问预判**

- 怎么确认是伪共享 → 压测对比加填充前后的吞吐，或用 perf 看缓存未命中率。
- DCL 为什么必须 volatile → 防止指令重排把引用赋值提前到构造完成之前。
- 除了 volatile 还能怎么保证可见性 → 锁、final 字段、线程安全容器的内部同步、线程的 start/join。

**常见错误答法**

- 认为单例的 DCL 不加 volatile 也没问题（可能拿到半初始化对象）。
- 把伪共享当成逻辑 bug 去查业务代码（本质是硬件缓存行为）。

**记忆锚点**

缓存行失效 → 填充 / Contended；重排 → volatile + happens-before；复现靠压测与 jcstress。
