## 一、一致性理论与共识

### 1. 【必答】CAP：CAP 和 BASE 到底怎么取舍，为什么说 P 是必选项？

**口述版**

CAP 说的是网络分区发生时，一致性和可用性只能保一个，不是平时三选二。因为分布式系统里分区无法避免，所以 P 是前提，真正要决策的是分区期间选 C 还是选 A。选 C 就是少数派拒绝服务、等多数派恢复；选 A 就是继续读写，但可能读到旧数据。BASE 是 AP 路线的工程化：基本可用、软状态、最终一致，允许中间态存在，用补偿、对账、幂等把数据收敛回来。实际系统还要看 PACELC：没有分区时，一致性和延迟也要权衡，强一致往往意味着多一次协调往返。落地时要按业务分级：资金账务、库存扣减这类要强一致或准强一致；商品详情、Feed、统计报表可以最终一致。答这题的关键不是背定义，而是能说清选每条路要付什么代价。

**短版**

P 不可避免，分区时在 C 和 A 之间选；BASE 是 AP 的工程化；无分区时还有 PACELC 的延迟与一致性权衡；按业务分级。

**展开版**

- 机制链：网络分区 → 少数派无法与多数派通信 → 要么拒绝写入保一致，要么继续服务接受旧读 → 恢复后靠同步或补偿收敛。
- 关键结构：一致性模型、可用性定义、分区检测超时、Quorum、BASE 的三要素。
- 触发条件：跨机房部署、网络抖动、主从切换、脑裂。
- 例外：单机或单副本不存在分区问题；有些系统用“分区期间只读”折中，既不完全 C 也不完全 A。
- 对比取舍：CP 安全但故障时不可写；AP 可用但有脏读和冲突合并成本；工程上多数业务选 AP 加对账。

**追问预判**

- 为什么 P 必须选 → 网络分区是客观故障，不可通过设计消除，只能选择分区时的行为。
- CAP 的 C 和 ACID 的 C 是一回事吗 → 不是，CAP 的 C 偏线性一致，ACID 的 C 是约束不被破坏。
- 最终一致的代价是什么 → 需要幂等、补偿、对账，且业务要能接受一段时间的不一致。

**常见错误答法**

- 把 CAP 当成平时可以任意三选二的配置项。
- 说“我们选了 BASE 所以不用管一致性”，忽略对账和补偿。

**记忆锚点**

P 必选，分区时 C/A 二选一；无分区看延迟与一致性。

### 2. 【必答】共识：Raft 的选举和日志复制怎么保证不丢已提交的数据？

**口述版**

Raft 里节点有三种状态：follower、candidate、leader，用任期 term 标识逻辑时间。选举时 follower 选举超时后变 candidate，term 加一，先投自己，向其他节点拉票，拿到多数派就当选。选举超时是随机化的，避免同时竞选。日志复制是 leader 收到写请求后先追加本地日志，再并发发 AppendEntries 给 follower，多数派持久化后 leader 提交并应用到状态机，然后返回客户端。保证不丢的关键有两点：一是日志匹配特性，相同 index 和 term 的日志前缀一定相同；二是选举限制，只有日志不比多数派旧的节点才能当选，所以已经提交的日志一定在至少一个能当选的节点上。脑裂也靠 term 和多数派解决，两个 leader 不可能同时拿到多数派。

**短版**

term 加随机选举超时选主；日志多数派持久化才提交；日志匹配加选举限制保证已提交不丢；多数派保证不会双主。

**展开版**

- 机制链：选举超时 → term 加一拉票 → 多数派当选 → 收写追加日志 → 复制到多数派 → 提交并应用 → 返回客户端。
- 关键结构：term、votedFor、log index、commitIndex、AppendEntries、选举限制。
- 触发条件：leader 宕机、网络分区、心跳超时、节点重启。
- 例外：leader 只能直接提交当前任期的日志，旧任期日志要靠新任期日志间接提交；网络分区恢复后旧 leader 要回退未提交日志。
- 对比取舍：Raft 可理解性好、工程实现多；Paxos 更通用但难落地；多数派写入牺牲了一部分可用性换安全。

**追问预判**

- 为什么选举超时要随机 → 避免所有 follower 同时变成 candidate，导致选票分裂、反复选举。
- 复制失败怎么回退 → leader 递减 nextIndex 重试，或按冲突 term 快速回退，直到找到共同前缀。
- leader 提交后就一定安全吗 → 还要多数派持久化，单机写日志不算提交。

**常见错误答法**

- 认为 leader 本地写完就算提交，忽略多数派确认。
- 把 term 当成节点编号或请求 ID。

**记忆锚点**

term 加多数派；日志匹配加选举限制，已提交不丢。

### 3. 【进阶】一致性模型：线性一致和最终一致分别影响什么业务决策？

**口述版**

线性一致性要求所有操作像在一条全局时间线上原子执行，任何读都能看到最近一次已完成的写。实现它要么单点串行，要么靠共识和多数派读写。顺序一致性弱一些，只要求每个客户端看到的顺序一致，不要求和真实时间对齐。最终一致性只保证停止写入后副本会收敛，中间可能读到旧值。业务上要区分：扣款后立刻查余额，必须读到自己刚才的写，这叫读己之写；下单后查订单列表可以容忍几百毫秒延迟，读从库就行；商品库存展示可以最终一致，但真正扣减要走主库或强一致通道。工程上用会话粘滞、读主库、版本号、令牌来补体验，而不是所有读都上强一致。

**短版**

线性一致等于全局实时可见，靠单点或多数派；最终一致只保证收敛；用读己之写、读主库、版本号按场景补。

**展开版**

- 机制链：写请求完成 → 强一致需多数派确认后才可见 → 弱一致异步复制 → 读可能命中旧副本 → 会话层或版本层补偿。
- 关键结构：线性一致、顺序一致、因果一致、读己之写、单调读。
- 触发条件：主从复制、多副本、跨机房、缓存。
- 例外：同一会话内可以做到读己之写，但跨设备不保证；因果一致能解决部分顺序问题。
- 对比取舍：越强的一致，协调成本越高、延迟越大；弱一致要靠业务兜底和体验设计。

**追问预判**

- 读己之写怎么实现 → 写后短时间内读主库、会话粘滞、或客户端带上写版本号让从库等待追平。
- 为什么线性一致需要多数派 → 任意两次读写的先后要有全局共识，单副本或多数派才能排出唯一顺序。
- 最终一致会不会读到很旧的数据 → 正常情况下是毫秒到秒级，异常时可能更久，要有监控和兜底。

**常见错误答法**

- 把最终一致理解成“可以不一致”，不设计收敛机制。
- 所有读都走强一致，导致延迟和成本失控。

**记忆锚点**

线性等于全局实时，最终等于收敛；按会话和场景补一致性。

### 4. 【兜底】协调服务：ZooKeeper 和 etcd 分别怎么用，watch 和会话有哪些坑？

**口述版**

ZooKeeper 用 ZAB 协议，etcd 用 Raft，两者都提供强一致的协调能力。常见用法是临时节点做服务注册和故障检测，顺序节点做选主和分布式锁，watch 做变更通知，版本号或 revision 做乐观并发。会话超时后临时节点会被删除，所以会话时间要合理：太短会因 GC 或网络抖动误判下线，太长故障发现慢。watch 是一次性触发，触发后要重新注册，而且事件可能丢，所以必须配合全量拉取和版本号比对，不能只靠 watch 增量。常见坑还有把 ZK 当高吞吐配置存储，频繁写入会放大写压力；大量 watcher 同时触发造成惊群；跨机房部署时 quorum 写入被异地延迟拖慢。用的时候要明确它适合低频写、强一致的协调场景，不适合大数据量存储。

**短版**

ZK 用 ZAB、etcd 用 Raft；临时节点做注册、顺序节点做选主、watch 一次性且可能丢要配版本号；会话超时别太短。

**展开版**

- 机制链：客户端建会话 → 写临时节点 → 其他节点 watch → 会话超时节点删除 → watcher 触发 → 客户端全量拉取并重新注册。
- 关键结构：会话与心跳、临时/顺序节点、watch、zxid 与 revision、quorum。
- 触发条件：服务注册发现、选主、配置变更、分布式锁。
- 例外：watch 丢失或合并时只能靠版本号发现；ZK 读可扩展但写不可扩展。
- 对比取舍：ZK 成熟但运维重、写性能有限；etcd 接口简单、Raft 清晰，生态偏云原生。

**追问预判**

- watch 丢了怎么办 → 定期全量拉取加版本号比对，watch 只做加速。
- 会话超时怎么定 → 结合 GC 停顿和网络抖动，通常几秒到十几秒，并配健康检查。
- 为什么 ZK 不适合做配置高频写 → 所有写走 leader 和 quorum，写放大明显，延迟高。

**常见错误答法**

- 把 watch 当持续订阅，触发一次后不重新注册。
- 用 ZK 存大量业务数据，把它当数据库用。

**记忆锚点**

ZAB/Raft 加临时节点；watch 一次性，版本号兜底。

## 二、分布式事务

### 5. 【必答】2PC：两阶段提交怎么工作，为什么工程上很少直接用 XA？

**口述版**

2PC 有一个协调者和多个参与者。第一阶段 prepare：协调者让参与者执行事务但不提交，参与者锁住资源、写 undo/redo 日志，回复 yes 或 no。第二阶段如果全是 yes，协调者发 commit，否则发 abort。问题有三个：一是同步阻塞，prepare 之后参与者的资源一直被锁着，直到收到最终指令；二是协调者单点，协调者宕机后参与者可能长期悬挂；三是网络分区时部分参与者提交、部分回滚，出现不一致。3PC 加了 canCommit 和超时，减少了阻塞，但没有消除脑裂和不一致，实际很少用。XA 是 2PC 的标准实现，由数据库层保证，跨库跨资源时性能差、锁时间长，互联网系统通常用本地事务加消息、TCC 或 Saga 替代。

**短版**

prepare 锁资源、commit/abort 两阶段；同步阻塞、协调者单点、分区不一致；3PC 减阻塞不减不一致；XA 性能差。

**展开版**

- 机制链：协调者写事务日志 → 参与者 prepare 并锁资源 → 汇总投票 → 发 commit/abort → 参与者释放锁。
- 关键结构：事务协调者、参与者、prepare/commit 日志、XA 接口、事务管理器。
- 触发条件：跨库转账、跨服务资源操作、异构数据源。
- 例外：单库本地事务不需要 2PC；部分数据库支持一阶段提交优化，但仍有一致性边界。
- 对比取舍：2PC 强一致但阻塞、吞吐低；TCC/Saga 用业务补偿换性能，但实现复杂、只能最终一致。

**追问预判**

- prepare 阶段锁了什么 → 行锁或资源预留，直到事务结束才释放，这是阻塞的根源。
- 协调者宕机怎么办 → 参与者会一直等待，需要超时策略、日志恢复或人工介入。
- 为什么 XA 性能差 → 两阶段多次网络往返，锁持有时间长，连接和线程占用高。

**常见错误答法**

- 认为 3PC 完全解决了阻塞和不一致。
- 把 2PC 当成跨服务强一致的默认方案，不考虑吞吐和可用性。

**记忆锚点**

prepare 锁资源，两阶段提交；阻塞加单点加不一致。

### 6. 【必答】TCC：Try-Confirm-Cancel 怎么落地，空回滚、悬挂、幂等怎么解？

**口述版**

TCC 是业务层的两阶段：Try 预留资源，比如冻结余额、预占库存；Confirm 确认扣减；Cancel 释放预留。它把数据库锁换成了业务资源的状态。三个经典问题：空回滚是 Try 没执行，Cancel 先到了，通常是网络超时或重复调用导致，解决方法是记录事务状态，Cancel 发现没有 Try 记录就直接返回成功并记一笔空回滚；悬挂是 Cancel 先执行，之后延迟的 Try 才到，资源被扣了却没人释放，解决方法是 Try 执行前检查是否已经 Cancel，已 Cancel 就拒绝；幂等是 Confirm 和 Cancel 都可能重复，用事务控制表的唯一键加状态机保证只生效一次。TCC 侵入业务、要写三个接口，适合资金、库存这类能预留且一致性要求高的场景，必须配协调器、重试、补偿日志和对账。

**短版**

Try 预留、Confirm 扣减、Cancel 释放；空回滚记状态直接成功，悬挂让 Try 先查 Cancel，Confirm/Cancel 靠唯一键幂等。

**展开版**

- 机制链：协调器发起 Try → 业务预留资源 → 全部成功发 Confirm → 任一步失败发 Cancel → 补偿重试直到成功。
- 关键结构：事务控制表、Try/Confirm/Cancel 三接口、幂等键、状态机、补偿日志。
- 触发条件：跨服务扣款、库存预占、权益发放。
- 例外：没有预留语义的业务不适合 TCC；Confirm 失败要重试，不能简单回滚。
- 对比取舍：TCC 一致性和性能较平衡，但侵入大、开发成本高；Saga 侵入小但无隔离；2PC 简单但阻塞。

**追问预判**

- 为什么要有 Try 而不是直接扣 → 预留让后续 Confirm 有确定性，失败可释放，避免中间态不可逆。
- 空回滚怎么判断 → 查事务控制表没有 Try 成功记录，就认为是空回滚，返回成功并记录。
- TCC 和 Saga 怎么选 → 需要资源预留和较强一致性选 TCC，流程长、跨系统多、可接受最终一致选 Saga。

**常见错误答法**

- 只实现 Try 和 Confirm，Cancel 不幂等或不做空回滚判断。
- 对没有预留语义的业务硬套 TCC。

**记忆锚点**

Try 预留、Confirm 扣减、Cancel 释放；空回滚、悬挂、幂等三坑。

### 7. 【进阶】Saga：长事务怎么拆，补偿失败和隔离性怎么处理？

**口述版**

Saga 把一个长事务拆成一串本地事务，每一步都有对应的补偿动作，失败时逆序补偿已经完成的步骤。有两种组织方式：编排式是有一个中心协调器按流程调用各服务，链路清晰、便于观测；协同式是各服务通过事件驱动，耦合低但整体流程难追踪。Saga 最大的问题是没隔离性，中间状态对外可见，别人可能读到“已扣款但未发货”的中间态。缓解办法是语义锁、状态位、延迟展示、业务上只暴露终态。补偿必须幂等且可能失败，所以要有重试、死信、人工兜底和对账。Saga 适合订单履约、出行、审批这类流程长、跨服务多、能接受最终一致的业务，不适合资金强扣减这种要求原子性的核心环节。

**短版**

拆本地事务加逆序补偿；编排有中心、协同靠事件；无隔离靠语义锁和状态位；补偿要幂等可重试。

**展开版**

- 机制链：正向执行各步骤 → 某步失败 → 逆序调用已完成步骤的补偿 → 补偿重试 → 对账兜底。
- 关键结构：Saga 日志、补偿接口、编排器、状态机、幂等键。
- 触发条件：跨多个服务的长流程、外部系统调用、人工审批。
- 例外：补偿不是回滚，可能产生新的业务动作；不可补偿的步骤要前移或改为可重试。
- 对比取舍：编排可观测但中心重；协同解耦但排障难；无隔离换来了高吞吐。

**追问预判**

- 补偿失败怎么办 → 重试加死信加人工处理，最终靠对账发现差异。
- 隔离性怎么补 → 语义锁、状态位、只展示终态、把关键校验放在第一步。
- 编排和协同怎么选 → 流程固定、需要可视化选编排；事件多、团队自治选协同。

**常见错误答法**

- 认为 Saga 的补偿一定能成功，不设计重试和人工兜底。
- 把 Saga 当强一致事务，忽略中间态对外可见。

**记忆锚点**

本地事务加补偿；无隔离靠语义锁，补偿要幂等。

### 8. 【进阶】可靠消息：本地消息表、事务消息、最大努力通知各适合什么？

**口述版**

本地消息表是把业务数据和消息记录放在同一个本地事务里写，提交后由定时任务或 CDC 把消息投到 MQ，消费端幂等，失败重试。它解决的是“业务成功但消息没发出去”，实现简单、可靠，缺点是消息表和业务库绑在一起，有投递延迟。事务消息以 RocketMQ 为代表：先发半消息， broker 存下来但不投递；再执行本地事务；根据结果 commit 或 rollback；broker 定时回查本地事务状态。本质还是两阶段，但把协调放在 MQ 侧。最大努力通知是主动重试若干次，并提供查询接口让对方对账，适合外部渠道，比如支付回调、银行通知。三者都只能做到最终一致，都不保证消息不重复，所以消费端必须用业务唯一键做幂等。

**短版**

本地消息表同库事务加定时投递；事务消息半消息加本地事务加回查；最大努力通知重试加查询对账；消费端都要幂等。

**展开版**

- 机制链：业务写库并写消息 → 投递 MQ → 消费并幂等处理 → 失败重试 → 超限进死信或人工。
- 关键结构：本地消息表、半消息、事务回查、重试次数、查询接口、幂等键。
- 触发条件：订单创建后通知库存、支付成功后通知履约、跨系统状态同步。
- 例外：事务消息依赖 MQ 支持；最大努力通知无法保证送达，必须有查询兜底。
- 对比取舍：本地消息表最通用但要自己维护投递；事务消息省事但绑定 MQ；最大努力通知适合弱依赖的外部系统。

**追问预判**

- 事务消息回查怎么做 → 提供回查接口，按事务 ID 查本地事务表，返回 commit、rollback 或未知。
- 本地消息表积压怎么办 → 加投递线程、分片、监控 lag，避免和业务库争资源。
- 消息重复怎么处理 → 业务唯一键加唯一索引或去重表，消费逻辑幂等。

**常见错误答法**

- 业务和消息不在同一个事务里提交，仍然会丢消息。
- 消费端假设消息只来一次，不做幂等。

**记忆锚点**

本地消息表靠同库事务；事务消息靠半消息加回查；消费必须幂等。

### 9. 【兜底】最终一致：对账怎么做，分布式事务方案怎么选型？

**口述版**

最终一致靠三件套：可靠消息、补偿重试、对账。对账分准实时和日终：准实时用 binlog 或消息比对关键状态，日终做全量核对；差异分级，能自动重试的自动修，修不了的进人工，涉及资金的挂账并告警。选型顺序是：能不做分布式事务就不做，比如合并服务、单库事务、状态机推进；必须跨服务时优先本地消息表或事务消息；需要资源预留和较强一致用 TCC；流程长、跨系统多、可接受最终一致用 Saga；XA 只在不得不跨多资源且能接受性能损失时考虑。判断标准是业务能接受多长的不一致、能不能补偿、出错后能不能发现。最后一定要有资损监控和演练，否则“最终一致”只是口号。

**短版**

消息加补偿加对账；差异分级处理；选型从“不做分布式事务”开始，再消息、TCC、Saga、XA；要有资损监控。

**展开版**

- 机制链：正向流程 → 消息或补偿驱动 → 定时对账发现差异 → 自动修复或人工介入 → 资损告警。
- 关键结构：对账任务、差异表、重试策略、挂账、资损监控、演练。
- 触发条件：跨服务写入、外部渠道回调、日终结算。
- 例外：对账本身也可能漏，需要多口径比对；补偿可能引入新差异，要可回滚。
- 对比取舍：强一致简单但性能差；最终一致性能好但要建设对账体系；方案越重，运维和排障成本越高。

**追问预判**

- 对账数据量太大怎么办 → 分片、增量加全量结合、按业务键哈希、只比对关键字段和状态。
- 消息丢了怎么发现 → 对账、状态长时间不推进的监控、消息轨迹查询。
- 怎么证明最终一致有效 → 故障注入、消息丢失演练、差异率和修复时长指标。

**常见错误答法**

- 所有跨服务场景都上 TCC，忽略业务是否真的需要。
- 只做重试不做对账，丢了也不知道。

**记忆锚点**

能不做就不做；消息加补偿加对账兜底。

## 三、分布式锁

### 10. 【必答】分布式锁：Redis 锁怎么写才对，为什么释放要用 Lua？

**口述版**

加锁用一条命令：SET key value NX PX 30000，NX 保证只有不存在才能设置，PX 保证一定带过期时间，两者必须原子，不能拆成 setnx 再 expire。value 要唯一，一般用 UUID 加线程标识，代表锁的持有者。释放时不能直接 del，因为业务可能已经超时、锁被别人拿走，直接删会删掉别人的锁，所以要用 Lua 先比较 value 再删除。生产上多用 Redisson，它封装了看门狗续期、可重入、公平锁和红锁。加锁失败要退避重试，比如几十毫秒后再试，不能自旋把 Redis 打满。锁的 TTL 要大于正常业务耗时并留余量，同时靠续期覆盖长任务。还要注意锁的粒度和范围：只锁必要的资源，锁内不要做远程调用和长事务。

**短版**

SET key value NX PX 一条命令加锁，value 唯一；释放用 Lua 比较后删；失败退避重试；TTL 加续期。

**展开版**

- 机制链：SET NX PX 抢锁 → 业务执行 → 看门狗定期续期 → Lua 校验持有者并删除 → 失败则退避重试。
- 关键结构：NX、PX、唯一 value、Lua 脚本、看门狗、可重入计数。
- 触发条件：防重复提交、定时任务互斥、库存扣减、缓存重建。
- 例外：主从异步复制下锁可能丢；单实例故障时锁随实例消失，靠 TTL 恢复。
- 对比取舍：Redis 锁性能高、实现轻；可靠性弱于 ZK/etcd；业务正确性最终靠幂等兜底。

**追问预判**

- 为什么不能 setnx 加 expire 两条命令 → 两条之间宕机会导致锁没有过期时间，永久不释放。
- 可重入怎么实现 → 用 hash 存持有者和重入次数，同一个持有者再次加锁次数加一。
- 续期会不会掩盖业务卡死 → 会，所以要监控持锁时长，超长任务要告警或强制中断。

**常见错误答法**

- 直接 del 释放锁，不校验 value。
- 加锁不设 TTL，进程崩溃后锁永久占用。

**记忆锚点**

SET NX PX 加唯一值；Lua 比较再删，失败退避。

### 11. 【进阶】分布式锁：业务超过 TTL 会发生什么，怎么保证正确性？

**口述版**

业务执行时间超过 TTL，锁会自动过期，第二个线程可以拿到锁，此时两个线程同时操作同一份资源，互斥被打破。看门狗能续期，但进程 STW、长时间 GC、网络分区都会让续期失败，所以不能假设锁永远有效。解决办法有三层：第一层是 fencing token，每次加锁拿一个单调递增的令牌，下游存储校验令牌，拒绝比已见过的更小的令牌，这样旧持有者的写会被挡住；第二层是业务幂等和乐观锁，用版本号或状态条件更新，保证重复或并发写不会破坏状态；第三层是缩短持锁时间，把长任务拆小，锁内不做远程调用、不做大事务。锁只能降低并发概率，正确性最终要靠令牌、版本号和幂等来保证。

**短版**

锁过期后互斥失效；用 fencing token 让下游拒绝旧令牌，再加乐观锁和幂等；缩短持锁、锁内不做远程调用。

**展开版**

- 机制链：业务超时 → 锁过期 → 第二个持有者进入 → 旧持有者继续写 → fencing token 或版本号拒绝旧写。
- 关键结构：fencing token、版本号、CAS 更新、持锁时长监控。
- 触发条件：长事务、慢 SQL、下游超时、Full GC。
- 例外：下游不支持令牌校验时，只能靠幂等和业务状态机兜底。
- 对比取舍：令牌最严格但要改下游；乐观锁侵入小但要求状态可比较；缩短持锁最简单但受业务限制。

**追问预判**

- fencing token 怎么落地 → 锁服务返回单调递增序号，存储层记录已见最大序号，写入时比较。
- STW 导致锁失效怎么办 → 接受锁会失效，用令牌和幂等保证正确，而不是指望续期。
- 锁粒度怎么定 → 按最小可冲突资源加锁，避免大范围锁导致排队和超时。

**常见错误答法**

- 认为有看门狗续期就不会失效。
- 在锁内做远程调用或等待用户输入，持锁时间不可控。

**记忆锚点**

锁会失效；靠 fencing、版本号、幂等保正确。

### 12. 【进阶】分布式锁：主从切换为什么会丢锁，Redlock 的争议在哪？

**口述版**

Redis 主从是异步复制。客户端在主库加锁成功，主库还没把这条写同步到从库就宕机了，哨兵把从库提升为新主，新主上没有这把锁，另一个客户端就能加锁成功，出现两个持有者。Redlock 的思路是向 N 个独立 master 依次加锁，只有在多数派成功、且总耗时小于锁有效期时才认为加锁成功。它的问题在于安全性依赖时钟漂移和网络延迟有上界：进程 GC 停顿、虚拟机暂停、网络延迟抖动，都可能让客户端在“自认为持锁”的时间里锁已经过期。Martin Kleppmann 对此有系统批评。所以结论是：Redis 锁适合效率型场景，比如防重复、降低竞争；正确性型场景，比如资金扣减，应该靠数据库唯一约束、幂等、状态机，或者用 ZooKeeper/etcd。

**短版**

异步复制导致主从切换丢锁；Redlock 靠多数派但依赖时钟和延迟假设；效率型用 Redis，正确性型靠幂等或 ZK。

**展开版**

- 机制链：主库加锁 → 未同步即宕机 → 从库升主无锁 → 第二个客户端加锁成功 → 双持有者并发写。
- 关键结构：异步复制、哨兵切换、Redlock 的多数派与总耗时、时钟假设。
- 触发条件：主库故障、网络分区、主从延迟大、跨机房部署。
- 例外：单实例部署不存在主从丢锁，但实例故障锁全丢，只能靠 TTL。
- 对比取舍：Redlock 提升安全性但运维成本高、仍有假设；ZK/etcd 会话锁更安全但性能低。

**追问预判**

- Redlock 为什么需要多数派 → 单个节点故障不至于丢锁，多数派同时故障概率低。
- 为什么不用单点 Redis 加业务幂等 → 很多场景这样更简单，幂等本来就必须做。
- ZK 锁为什么更安全 → 顺序临时节点加会话，会话失效才释放，且写走 quorum。

**常见错误答法**

- 认为 Redlock 绝对安全，不做业务幂等。
- 主从切换后不校验锁的归属，直接继续写。

**记忆锚点**

异步复制会丢锁；Redlock 有假设，正确性靠幂等/ZK。

### 13. 【兜底】分布式锁：ZK/etcd 怎么实现，和 Redis 锁怎么选？

**口述版**

ZK 锁用临时顺序节点：每个客户端在锁目录下创建 /lock/lock-00000001 这样的临时顺序节点，判断自己是不是最小节点，是就获得锁，不是就 watch 前一个节点，前一个删除后自己被唤醒。只 watch 前一个可以避免羊群效应。会话断开后临时节点自动删除，锁自动释放。etcd 用 lease 加事务加 revision，思路类似。ZK 锁的优点是安全性高，会话绑定、写走 quorum，不会因为客户端 GC 停顿就误释放，因为是否存活由服务端会话超时判定；缺点是性能低于 Redis，写有放大，运维重。选型看场景：高并发、短临界区、能接受极小概率失效的用 Redis；强一致、低频率、不能出错的用 ZK/etcd；无论选哪个，业务都要有幂等兜底。

**短版**

ZK 临时顺序节点，判断最小、watch 前驱，会话断开自动释放；etcd 用 lease 加事务；Redis 快、ZK 稳，都要幂等兜底。

**展开版**

- 机制链：创建临时顺序节点 → 判断是否最小 → 不是则 watch 前驱 → 前驱删除后重新判断 → 获锁执行 → 会话结束节点删除。
- 关键结构：临时节点、顺序节点、watch、会话超时、lease、revision。
- 触发条件：选主、任务互斥、配置变更互斥。
- 例外：会话超时设置不当会误判存活或故障发现慢；大量节点会增加 ZK 压力。
- 对比取舍：Redis 性能高但可靠性弱；ZK/etcd 安全但吞吐低；工程上按失败代价选。

**追问预判**

- 为什么 watch 前一个而不是父节点 → 父节点变化会唤醒所有等待者，造成羊群效应。
- 会话超时怎么定 → 考虑 GC 和网络抖动，通常几秒到十几秒，并配健康检查。
- ZK 锁的性能瓶颈在哪 → 所有写走 leader 和 quorum，频繁创建删除节点成本高。

**常见错误答法**

- 用永久节点做锁，客户端崩溃后锁不释放。
- 所有等待者 watch 同一个节点，造成惊群。

**记忆锚点**

临时顺序节点加 watch 前驱；Redis 快、ZK 稳。

## 四、幂等与状态机

### 14. 【必答】幂等：幂等键怎么设计，去重表为什么不能先查再插？

**口述版**

幂等键要能唯一标识一次业务操作，常见来源是客户端生成的请求 ID、网关生成的全局 ID，或者业务唯一键，比如订单号加操作类型、消息 ID。落地方案里最可靠的是数据库唯一索引：把幂等键建成唯一键，重复请求插入直接冲突，只有一个能成功。去重表是在唯一索引基础上多存状态，比如处理中、成功、失败，失败要允许重试，处理中要有超时兜底。也可以用 Redis SETNX 做快速拦截，但 Redis 可能丢数据，必须用数据库唯一索引兜底。不能先查再插，因为两个并发请求可能都查到不存在，然后都插入成功；要靠唯一索引让数据库来串行化。去重表还要设置过期和归档，幂等窗口按业务可接受重复的时间来定，不能永久保留。

**短版**

幂等键用请求 ID 或业务唯一键；唯一索引最可靠，去重表存三态；Redis 只做快速拦截；不能先查再插。

**展开版**

- 机制链：请求带幂等键 → 插入去重表或唯一索引 → 冲突则读已有结果 → 成功返回 → 失败允许重试。
- 关键结构：唯一索引、去重表、状态字段、过期时间、幂等窗口。
- 触发条件：支付回调、下单、MQ 消费、重试接口。
- 例外：处理中状态可能因进程崩溃卡住，需要超时扫描和补偿；删除后重建的数据要注意幂等键复用。
- 对比取舍：唯一索引最稳但写放大；Redis 快但可能丢；状态机天然幂等但只适用于状态流转。

**追问预判**

- 先查再插为什么不行 → 并发下两个请求都查到不存在，随后都插入，唯一索引才能保证只有一个成功。
- 处理中卡住怎么办 → 设置超时，超时后允许重试或补偿任务接管，并记录状态。
- 幂等键谁生成 → 入口层生成最可靠，客户端生成要防伪造和重复使用。

**常见错误答法**

- 只用 Redis 去重，Redis 丢数据后重复请求穿透。
- 去重表不清理，容量无限增长。

**记忆锚点**

唯一索引兜底；处理中/成功/失败三态加过期。

### 15. 【必答】状态机：怎么防止非法状态跳转和并发覆盖？

**口述版**

订单、支付、履约这类业务都有明确的状态流转。做法是维护一张合法迁移表，每个状态只允许迁移到指定状态，非法跳转直接拒绝并告警。并发下不能用“先查状态再更新”，因为两个线程可能都查到旧状态然后都更新成功；要用条件更新，也就是 update 语句带上原状态，比如 where status = 待支付，影响行数为零说明被别人改过，需要重读再判断。状态变更要记录流水，包含 who、when、from、to、原因和请求 ID，便于对账和排查。终态不可逆，成功和关闭之后不能再改，退款走逆向单据而不是把状态改回去。状态机放在领域层统一实现，不要散落在各个服务的 if-else 里，否则很容易出现绕过校验的入口。

**短版**

合法迁移表加条件更新 CAS；影响行数为零说明并发冲突；状态流水要留；终态不可逆，逆向走新单据。

**展开版**

- 机制链：读取当前状态 → 校验迁移合法 → 带原状态条件更新 → 成功记流水 → 失败重读判断。
- 关键结构：状态枚举、迁移表、CAS 更新、状态流水表、版本号。
- 触发条件：支付回调、发货、取消、退款、关单。
- 例外：补偿和人工干预也要走状态机，不能直接改库；跨服务状态要有一致性方案。
- 对比取舍：CAS 简单高效但需要状态可比较；悲观锁一致但阻塞；事件驱动解耦但最终一致。

**追问预判**

- CAS 更新失败怎么办 → 重读当前状态，如果已经是目标态就幂等返回，否则判断是否允许重试。
- 状态和业务表分不分 → 简单业务可同表，复杂流程建议独立状态表加流水，便于审计。
- 怎么防跳步 → 迁移表里只允许相邻或明确允许的跳转，服务入口统一校验。

**常见错误答法**

- 先查状态再更新，并发下两个请求都成功。
- 状态流转不记录流水，出问题无法追溯。

**记忆锚点**

迁移表加 CAS；终态不可逆，变更留流水。

### 16. 【进阶】乱序与重入：重复消息、乱序消息、补偿重跑怎么处理？

**口述版**

分布式里重复、乱序、重入是常态。重复来自至少一次投递和网络重试，处理靠业务唯一键加唯一索引或去重表。乱序来自多生产者和分区，处理不能靠“最后一条赢”，因为消息可能后发先到，要靠版本号或状态机：每条消息带业务版本，消费时只有版本大于当前才应用，旧版本直接丢弃。顺序敏感的场景按业务键分区，保证同一业务键进同一分区。补偿任务重跑要可重入：执行前先查当前状态，已经是目标态就跳过，中间态要判断是否超时。定时补偿要带版本，避免旧补偿覆盖新状态。核心原则是让每次操作都基于当前真实状态做判断，而不是假设消息只来一次、按顺序来。

**短版**

重复靠唯一键；乱序靠版本号或状态机，不能最后一条赢；顺序敏感按业务键分区；补偿先查状态再执行。

**展开版**

- 机制链：消息带业务键和版本 → 按业务键分区 → 消费幂等 → 版本比较决定是否应用 → 补偿前查状态。
- 关键结构：业务唯一键、版本号、分区键、状态机、补偿日志。
- 触发条件：MQ 重投、多生产者、网络延迟、定时任务重跑。
- 例外：没有版本字段的老系统只能靠状态机和时间窗口兜底。
- 对比取舍：版本号严格但要求生产端配合；状态机通用但表达能力有限；分区保序牺牲并行度。

**追问预判**

- 怎么发现消息乱序 → 版本跳跃、状态回退、业务对账差异；埋点记录消息版本。
- 版本号存哪 → 业务表字段或缓存，更新时用 CAS 带上版本。
- 补偿重复执行怎么保证安全 → 先查当前状态，动作设计成幂等，重复执行结果一致。

**常见错误答法**

- 用时间戳判断新旧，机器时钟不一致时会出错。
- 消费端只判断“已处理就跳过”，不处理失败和中间态。

**记忆锚点**

幂等键加版本号；补偿先查状态再执行。

### 17. 【进阶】落地：幂等体系的容量怎么估，应该覆盖哪些层？

**口述版**

容量按峰值 QPS 乘幂等窗口乘平均 key 大小估算。比如峰值一万 QPS、窗口 24 小时，就是八亿多条，这个量级放数据库要分区和归档，放 Redis 要算内存和过期策略。选型上，数据库唯一索引是最终兜底，Redis 用来挡高频重复，两者结合。热点幂等键会打到同一个分片，要考虑分桶或本地缓存。监控要看重复率、冲突率、处理中超时数和去重表增长量。幂等不是某一个接口的事，要覆盖四层：网关层防重复提交，服务层用业务幂等键，消费层用消息 ID 或业务键，回调层用渠道流水号。任何一层缺失都可能让重复穿透到最里面。窗口长度要和业务确认，退款、对账这类可能要几个月，那就不能只靠 TTL。

**短版**

容量等于峰值 QPS 乘窗口乘 key 大小；DB 唯一索引兜底、Redis 挡高频；覆盖网关、服务、消费、回调四层。

**展开版**

- 机制链：入口生成或透传幂等键 → 各层校验 → 冲突返回已有结果 → 定期清理归档 → 监控重复率。
- 关键结构：幂等键规范、唯一索引、Redis TTL、分区表、监控指标。
- 触发条件：大促、回调重试、消息积压、批量任务。
- 例外：长窗口业务不能只依赖 TTL，需要落库和归档；跨系统幂等键要统一。
- 对比取舍：全链路幂等成本高但可靠；只在关键接口做成本低但可能漏；窗口越长成本越高。

**追问预判**

- 去重表放 DB 还是 Redis → 最终一致性要求高放 DB，性能要求高放 Redis 并用 DB 兜底。
- 幂等窗口怎么定 → 按业务可能重复的最长时间，支付回调通常几天到几个月。
- 历史数据怎么清理 → 按时间分区，定期归档到冷存储，保留索引查询能力。

**常见错误答法**

- 所有接口都加 Redis 去重，但没有数据库兜底。
- 幂等窗口设成永久，表无限增长。

**记忆锚点**

窗口乘 QPS 定容量；四层覆盖，DB 兜底。

## 五、分布式 ID

### 18. 【必答】分布式 ID：雪花算法的 64 位怎么分配，时钟回拨怎么处理？

**口述版**

雪花是 64 位长整型：一位符号位不用，41 位毫秒时间戳大概能用 69 年，10 位机器位支持 1024 个节点，12 位序列号表示同一毫秒内最多 4096 个 ID。趋势递增，适合做 InnoDB 主键，能减少页分裂，但多机器之间不是严格递增。时钟回拨是最大的坑：服务器时间被 NTP 往回拨，可能导致同一时间戳重复发号。处理策略分三档：小幅回拨，比如几毫秒，就等待追平；大幅回拨，直接拒绝服务并告警，避免发重复 ID；也可以记录上次时间戳，回拨时用上次时间戳加序列号继续发，保证不重复。机器位不能手写配置，容易重复，要用 ZooKeeper、etcd 或数据库统一分配 workerId，并做租约续期。序列号用满时要等到下一毫秒，不能简单溢出。

**短版**

1 加 41 时间戳加 10 机器位加 12 序列；回拨小幅等待、大幅拒绝，或上次时间戳加序列兜底；workerId 统一分配。

**展开版**

- 机制链：取当前毫秒 → 与上次比较 → 同一毫秒序列加一 → 序列溢出等到下一毫秒 → 回拨按策略处理 → 拼装 ID。
- 关键结构：时间戳位、workerId 位、序列位、上次时间戳、workerId 注册中心。
- 触发条件：多实例部署、NTP 校时、容器漂移、跨机房。
- 例外：41 位时间戳会耗尽，需要预留或换方案；容器环境下 workerId 不能按 IP 简单推导。
- 对比取舍：雪花性能高、趋势递增，但依赖时钟；号段不依赖时钟但要访问 DB；UUID 无依赖但无序。

**追问预判**

- workerId 怎么分配 → 启动时向注册中心申请并续约，释放后回收，避免重复。
- 回拨为什么会产生重复 ID → 时间戳回到之前用过的值，序列号也重置，组合就重复了。
- 41 位用完了怎么办 → 提前规划，缩短机器位或序列位，或改用号段加时间混合方案。

**常见错误答法**

- 回拨时直接抛异常但不监控，导致发号不可用。
- workerId 写死在配置文件里，扩容时重复。

**记忆锚点**

41 加 10 加 12；回拨等待或拒绝，workerId 统一分配。

### 19. 【进阶】分布式 ID：数据库自增、Redis、号段怎么选，双 buffer 解决什么？

**口述版**

号段模式是在数据库存一张表，记录业务类型、当前最大 ID 和步长。服务一次取一段，比如一千个，放在内存里慢慢发，快用完时再异步取下一段。双 buffer 是同时维护当前段和下一段，当前段用到一定比例就异步加载下一段，切换时无缝衔接，避免取号时同步等数据库。优点是数据库压力小、ID 趋势递增；缺点是服务重启会浪费当前段，多实例要协调步长避免交叉，数据库故障时只能用到当前段。数据库自增最简单，但单点、分库分表后不唯一；Redis INCR 性能好，但持久化配置不当可能丢数据导致 ID 回退，需要接受或配合号段。UUID 无序、占空间、做聚簇索引会导致页分裂，一般不作为主键。

**短版**

DB 存 max_id 和 step，一次取一段放内存；双 buffer 预加载避免同步等待；重启浪费一段，DB 故障只能用存量。

**展开版**

- 机制链：服务启动取一段 → 内存发号 → 用到阈值异步取下一段 → 切换 buffer → 取号失败降级或等待。
- 关键结构：号段表、step、双 buffer、预加载阈值、多实例步长协调。
- 触发条件：订单号、交易流水、需要趋势递增的业务主键。
- 例外：多实例各自取段会导致 ID 不连续，但唯一性没问题；数据库故障时要有本地兜底。
- 对比取舍：号段 DB 压力小但依赖 DB；Redis 快但可能回退；雪花无依赖但时钟敏感；美团 Leaf 就是号段与雪花两条线的工程化封装。

**追问预判**

- 双 buffer 怎么切换 → 当前段消耗到阈值时异步加载下一段，当前段用完直接切换，加载失败则阻塞或降级。
- 号段取完 DB 挂了怎么办 → 用当前段剩余 ID，同时告警；恢复后继续，必要时预留应急段。
- 为什么不用 UUID 做 MySQL 主键 → 无序导致随机写和页分裂，占 16 字节以上，二级索引也膨胀。

**常见错误答法**

- 每取一个 ID 访问一次数据库，完全失去号段的意义。
- step 设得太小，频繁访问 DB；设得太大，重启浪费严重。

**记忆锚点**

一次取一段加双 buffer；DB 压力小，重启浪费一段。

### 20. 【兜底】分布式 ID：唯一、有序、分片路由和对外安全怎么平衡？

**口述版**

唯一性是底线，有序性是加分项。趋势有序的好处是 B+ 树顺序插入、减少页分裂、范围查询和分页友好；代价是暴露业务量、可被遍历、多机房时钟不一致时排序不可靠。分片路由有几种做法：ID 里嵌分片位，比如用户 ID 取模决定库表；基因法把分片信息写进 ID，保证同一用户的数据落同一分片；或者用独立的映射表。对外安全要求不能直接暴露自增主键，否则会泄露业务规模、可被爬取，做法是用独立的对外 ID，或者对内部 ID 做加密、混淆、加随机前缀。工程上常见组合是：内部主键用雪花或号段保证唯一和趋势递增，对外展示用独立编码或加密串，分片键单独设计，不把敏感信息编进 ID。

**短版**

唯一是底线、有序是加分；ID 嵌分片位或基因法做路由；对外用独立编码防遍历；内部主键和外部 ID 分离。

**展开版**

- 机制链：生成内部唯一 ID → 按分片键路由 → 需要对外时转换为外部编码 → 查询时反解或映射。
- 关键结构：分片位、基因法、映射表、对外编码、加密混淆。
- 触发条件：分库分表、对外开放接口、订单号展示。
- 例外：强有序 ID 在多机房下难保证，只能保证单机房趋势；加密会增加 CPU 开销。
- 对比取舍：有序 ID 对数据库友好但暴露信息；随机 ID 安全但索引差；分离内外 ID 最稳但多一层转换。

**追问预判**

- 基因法怎么保证均匀 → 用分片键的哈希低位作为基因位，使同一分片键稳定落同一分片。
- 对外 ID 怎么防遍历 → 用不可预测的编码或加密，配合限流和鉴权。
- 有序 ID 会有热点吗 → 单库自增会有写热点，雪花多节点可缓解，但仍可能集中在某些分片。

**常见错误答法**

- 直接把自增主键暴露给前端。
- 在 ID 里编码手机号、用户等级等敏感信息。

**记忆锚点**

内部有序、外部脱敏；分片位嵌进 ID。

## 六、数据同步

### 21. 【必答】Canal：binlog 订阅的原理是什么，怎么保证不丢不重？

**口述版**

Canal 的原理是伪装成 MySQL 从库，向主库发送 dump 协议请求，主库把 binlog 推过来，Canal 解析后得到结构化的行变更，再投递到 MQ 或直接给消费端。前提是 binlog 必须是 row 格式，否则拿不到变更前后的值；还要开 log_slave_updates，保证级联复制也能拿到；每个 Canal 实例要有唯一的 serverId。位点管理是关键：要把 position 或 GTID 持久化，重启后从位点续传；投递到 MQ 时，先用本地事务或两阶段保证位点和消息一致，避免消息发了位点没存导致重复，或位点存了消息没发导致丢失。消费端必须幂等，因为至少一次投递一定会重复。DDL 要单独处理，大事务会被拆成多条，订阅时只选需要的库表，减少流量。

**短版**

伪装从库发 dump 拿 binlog；必须 row 格式加唯一 serverId；位点持久化续传，投递配事务；消费端幂等。

**展开版**

- 机制链：Canal 注册为从库 → 请求 dump → 主库推送 binlog → 解析 row 变更 → 投递 MQ → 消费并更新下游。
- 关键结构：binlog 格式、serverId、position/GTID、位点存储、MQ。
- 触发条件：缓存失效、ES 同步、数仓入湖、审计。
- 例外：statement 格式拿不到行值；DDL 和大事务要特殊处理；主库 binlog 过期会导致位点失效需要重新全量。
- 对比取舍：Canal 解耦、可靠，但链路长、有延迟；业务双写实时但易不一致；触发器侵入数据库，不推荐。

**追问预判**

- 为什么必须 row 格式 → 只有 row 记录了每行变更前后的值，statement 只有 SQL，无法可靠还原。
- GTID 和 position 怎么选 → GTID 更适合主从切换和断点续传，position 简单但切换后可能失效。
- Canal 挂了会丢数据吗 → 位点持久化加 MQ 持久化可做到不丢，但可能重复，消费要幂等。

**常见错误答法**

- 用 statement 格式做订阅，解析不出行变更。
- 位点只存内存，重启后重复消费或丢变更。

**记忆锚点**

伪装从库 dump；row 格式加位点续传。

### 22. 【进阶】全量与增量：历史数据迁移怎么和实时变更衔接，怎么校验？

**口述版**

标准流程是三步：先做一致性快照并记录快照位点，比如在可重复读事务里导出，或用备份工具拿到 binlog 位点；然后启动增量订阅，从该位点开始消费；全量数据导入下游后，再追平增量，最后切读。关键是全量期间产生的变更不能丢，所以增量必须从快照位点开始，而不是从迁移开始的时间点。导入要限速、分批，避免把目标库打挂；写入用按主键 upsert，保证重跑幂等。切换前要校验：比对源和目标的总数、主键范围、关键字段校验和、抽样明细；有差异要能定位到具体行并修复。工具上可以用 DataX 做全量、Canal 或 Flink CDC 做增量，Debezium 也支持快照加流式。切换时最好有双读对比或灰度读，确认无误再全量切。

**短版**

快照记位点、增量从位点追、导入后追平再切；限速分批、主键 upsert；校验总数、校验和、抽样。

**展开版**

- 机制链：一致性快照 → 记录位点 → 全量导入 → 增量订阅从位点开始 → 追平 → 校验 → 切读。
- 关键结构：快照位点、GTID、upsert、校验和、双读对比。
- 触发条件：数据库迁移、ES 重建、缓存预热、机房搬迁。
- 例外：大表快照耗时长，要用备份或从库；DDL 变更要暂停或特殊处理；网络中断要能从断点续。
- 对比取舍：停机迁移简单但影响业务；不停机迁移复杂但平滑；双写过渡简单但有一致性风险。

**追问预判**

- 怎么保证全量和增量不重不漏 → 增量从快照位点开始，写入幂等，重复可覆盖，漏的靠校验发现。
- 校验怎么做 → 总数加主键范围加关键字段 checksum，再加抽样明细比对。
- 切换时要不要停写 → 尽量不停，用双读灰度；强一致场景可短暂停写或切主。

**常见错误答法**

- 先全量再开增量，中间窗口的变更直接丢了。
- 全量导入不限速，把源库或目标库打挂。

**记忆锚点**

快照位点加增量追平加校验；导入用幂等 upsert。

### 23. 【兜底】异构同步：MySQL 到 ES/缓存/数仓有哪些坑，双写和订阅怎么选？

**口述版**

异构同步的常见问题有六个：延迟，正常是毫秒到秒级，业务要能接受；乱序，多分区消费时同一主键的变更可能乱序，要按主键分区；重复，至少一次投递必然重复，下游要幂等 upsert；字段映射和类型转换，比如时间、金额精度、枚举；删除，物理删除在 binlog 里是一条 delete，下游要么逻辑删除要么用 tombstone 标记；全量和增量的一致性，靠位点和校验保证。双写和订阅的取舍：双写实时、不依赖 binlog，但代码侵入，且两个写可能一个成功一个失败，需要补偿；订阅解耦、可靠、可重放，但有延迟、依赖 binlog 和中间件。推荐以数据库为准，用订阅同步，双写只做过渡并配对账。同步失败要有死信、重试和定时对账修复。

**短版**

延迟、乱序、重复、类型映射、删除、全增量一致；双写实时但易不一致，订阅解耦但有延迟；DB 为准加对账。

**展开版**

- 机制链：业务写 DB → binlog → 同步服务 → 转换 → 写 ES/缓存/数仓 → 失败重试 → 对账修复。
- 关键结构：分区键、幂等 upsert、tombstone、字段映射、死信队列、对账任务。
- 触发条件：搜索、商品详情、报表、风控。
- 例外：缓存同步要注意删除而不是更新；ES 的 refresh 延迟会让刚写的数据查不到。
- 对比取舍：双写简单但一致性差；订阅可靠但链路长；CDC 加 Flink 灵活但运维重。

**追问预判**

- 删除怎么同步 → 逻辑删除或发 tombstone，下游按主键删除，避免全量重建。
- 同步延迟怎么监控 → 比对 binlog 位点与消费位点、端到端延迟指标、业务对账。
- 双写不一致怎么修 → 对账发现差异后以 DB 为准回灌，双写逐步下线。

**常见错误答法**

- 双写不做失败补偿，一边成功一边失败长期不一致。
- 同步时用“更新缓存”而不是删除，导致并发覆盖旧值。

**记忆锚点**

DB 为准、订阅同步；删除用 tombstone，失败靠对账。

## 七、缓存一致性

### 24. 【必答】更新策略：先更新数据库还是先删缓存，为什么是删而不是更新？

**口述版**

主流方案是 Cache Aside：先更新数据库，再删除缓存。原因是删除幂等、不会出现并发写互相覆盖、也不会做无用的计算。相比之下，先删缓存再更新数据库，会在删除之后、更新之前被读请求读到旧库并回填旧值，不一致窗口很明显；先更新数据库再更新缓存，并发写可能以错误顺序覆盖，而且缓存值如果是多表聚合，更新成本高还容易算错；先更新缓存再更新数据库，失败时不一致更严重。所以推荐先更库后删缓存。但它也不是绝对一致：读请求可能在写之前读到旧值，写请求更新库并删缓存后，读请求再把旧值回填。要消除这个窗口，用延迟双删或订阅 binlog 删除。删除失败要靠重试、消息或对账补偿。

**短版**

先更库后删缓存是主流；删幂等、无并发覆盖、无无效计算；仍有回填窗口，用双删或 binlog 补。

**展开版**

- 机制链：写请求更新 DB → 删除缓存 → 读请求未命中 → 读库（可能旧值）→ 回填 → 脏数据。
- 关键结构：Cache Aside、删除重试、消息补偿、binlog 订阅、主从延迟。
- 触发条件：读写并发、热点 key、主从延迟、删除失败。
- 例外：读多写少且能接受短暂不一致时，Cache Aside 足够；强一致业务不该把缓存当权威。
- 对比取舍：删除简单可靠但有窗口；更新缓存省一次读但一致性和计算成本高；加锁串行化最一致但吞吐差。

**追问预判**

- 为什么不是更新缓存 → 并发写会以错误顺序覆盖，聚合值计算贵且可能算错。
- 删除失败怎么办 → 本地重试表加定时补偿、发 MQ、或订阅 binlog 异步删。
- 主从延迟下怎么办 → 删缓存后延迟一段时间再删一次，或强制读主。

**常见错误答法**

- 认为先更库后删缓存就完全一致，忽略回填旧值的窗口。
- 用更新缓存代替删除，还认为更实时。

**记忆锚点**

先更库后删缓存；删是幂等，失败要补偿。

### 25. 【进阶】补偿方案：延迟双删怎么定延迟，binlog 订阅怎么保证顺序和幂等？

**口述版**

延迟双删是在更新数据库前删一次缓存，更新后延迟再删一次。第二次删是为了清掉更新期间被读请求回填的旧值。延迟时间要覆盖一次读请求的耗时加上主从同步延迟，实际很难精确估，估短了没用，估长了不一致窗口变长，所以它只是降低概率的兜底，不是主方案。更可靠的是 binlog 订阅：Canal 解析变更发到 MQ，消费端按 key 删除缓存。要保证同一 key 的变更顺序，用业务主键做分区键；消费要幂等，重复删除没有副作用，但要防止旧消息覆盖新状态，可以带版本号。删除失败要重试并进死信，配合定时对账扫描热点 key。这套方案是秒级最终一致，不是强一致；强一致业务要么读主库，要么不缓存。

**短版**

双删延迟覆盖读耗时加主从延迟，只是兜底；binlog 订阅按 key 分区保序、消费幂等、失败重试加对账。

**展开版**

- 机制链：写库 → binlog → Canal 解析 → MQ 按 key 分区 → 消费删除缓存 → 失败重试 → 对账修复。
- 关键结构：延迟时间、分区键、版本号、死信队列、对账任务。
- 触发条件：缓存与库不一致投诉、多写入口、跨服务更新同一份数据。
- 例外：binlog 延迟大、MQ 积压会拉长不一致窗口；DDL 和大事务影响解析。
- 对比取舍：双删零依赖但不可靠；binlog 订阅重但可靠；业务发消息轻量但要求覆盖所有写路径。

**追问预判**

- 延迟时间怎么定 → 压测读接口耗时加上主从延迟，取分位值再加余量，宁可长一点。
- 消息乱序怎么办 → 同一 key 用相同分区键，或带版本号让旧消息失效。
- binlog 延迟大怎么处理 → 监控位点差、扩容消费、必要时降级读主库。

**常见错误答法**

- 延迟双删当成强一致方案，不做对账和补偿。
- 消费端不幂等，重复删除或重复回填导致新问题。

**记忆锚点**

双删兜底、binlog 正解；按 key 保序加幂等。

### 26. 【兜底】强一致：为了缓存强一致要付什么代价，不一致怎么排查？

**口述版**

要缓存强一致，常见做法有：读写都加分布式锁串行化、读写都走主库、缓存只读不写由 DB 事务驱动、或者用支持线性一致的存储。代价是吞吐下降、RT 上升、可用性降低，锁还会带来死锁和超时问题。所以大多数业务选择最终一致，只在资金、库存等关键读上走主库或强一致通道。排查不一致的顺序是：先分层比对数据库、Redis、本地缓存的值，确认是哪一层旧；再查删除链路，消息有没有发出、有没有消费、消费有没有报错；然后查 TTL 是否过长、写路径是不是更新而不是删除、有没有漏掉的写入口；再看主从延迟、并发回填、binlog 位点和消费 lag。临时止血可以清缓存、重放消息、切读主库，但事后要加版本号、对账和监控，否则还会复发。

**短版**

强一致靠锁、读主、缓存只读，代价是吞吐、延迟和可用性；排查先分层比对，再查删除链路、TTL、写入口和主从延迟。

**展开版**

- 机制链：发现不一致 → 比对三层数据 → 定位旧值来源 → 查消息与写路径 → 修复 → 加防护。
- 关键结构：三层比对、binlog 位点、消费 lag、版本号、TTL、写入口清单。
- 触发条件：用户投诉、对账差异、发布后异常、主从切换。
- 例外：短暂不一致可能是最终一致窗口内的正常现象，要先确认业务承诺的时效。
- 对比取舍：强一致牺牲性能和可用；最终一致要靠对账兜底；分层缓存让排查更复杂。

**追问预判**

- 怎么证明缓存和 DB 一致 → 定时抽样比对加热点 key 实时校验，差异率和修复时长作为指标。
- 主从延迟导致读到旧值怎么办 → 关键读走主库，或记录写位点让从库等到位点再读。
- 缓存不一致监控看什么 → 差异率、删除失败率、消息 lag、回填旧值次数。

**常见错误答法**

- 出问题只清缓存不查根因，过一会又出现。
- 对强一致业务仍然走缓存读，靠短 TTL 自我安慰。

**记忆锚点**

强一致牺牲吞吐；排查先分层比对，再查删除链路。
