# 缓存面试题集（含参考答案）

> 答案按六段式生成，选题来自《Java架构师技术栈锚点.md》3.2 Redis 与 3.3 本地缓存与多级缓存。以 Redis 6.x / 7.x 为主，版本差异单独标注；本地缓存以 Caffeine 为主。口述版可直接读出声，卡壳处即理解缺口。

## 一、数据结构与线程模型

### 1. 【必答】线程模型：Redis 单线程为什么还快，6.0 的多线程到底多线程了什么？

**口述版**

Redis 的“单线程”指的是命令执行主线程只有一个。快的原因有四条：数据全在内存，没有磁盘 IO；用 epoll 做 IO 多路复用，一个线程能管几万个连接；命令执行串行，没有锁竞争和线程上下文切换；协议和数据结构的实现足够轻，RESP 简单，SDS 二进制安全，集合在小数据量时用紧凑编码。6.0 引入的 IO 多线程只负责网络读写和协议解析，命令执行仍然是单线程，靠 io-threads 配置，默认是 4；io-threads-do-reads 默认关闭。所以多线程解决的是网络带宽和 CPU 在读写上的开销，不是命令执行的并发。真正跑不快时，通常是大 key、O(N) 命令、fork 阻塞、AOF fsync 或者 swap，而不是“单线程”本身。

**短版**

单线程指命令执行；快在纯内存、epoll 多路复用、无锁无切换、结构轻；6.0 多线程只做网络读写解包，执行仍单线程。

**展开版**

- 机制链：连接接入 → epoll 就绪 → 主线程读取并解析 → 单线程顺序执行命令 → 写回响应；6.0 后读写与解析可分摊到 IO 线程，执行仍回主线程。
- 关键结构：事件循环 ae、epoll、RESP 协议、SDS、listpack、客户端的输入输出缓冲区。
- 触发条件：QPS 高、连接数多、单 value 大、命令复杂度高时才会暴露瓶颈。
- 例外：后台还有 bio 线程负责关闭文件、AOF fsync、lazy free，所以并不是进程里只有一个线程。
- 对比取舍：单线程简单、无锁、延迟稳定；要榨干多核就做分片多实例，而不是把命令执行改成多线程。

**追问预判**

- 单线程怎么保证并发安全 → 单条命令原子，但多条命令的组合不原子，需要 MULTI/Lua 或分布式锁。
- IO 多线程怎么配 → 一般 4 到 8，且实例 CPU 要够；读多写少可以只开写侧多线程。
- CPU 打不满怎么扩 → 拆实例分片、避免大 key、读写分离，而不是继续调 io-threads。

**常见错误答法**

- 说 Redis 是纯单线程，忽略 6.0 的 IO 线程和 bio 线程。
- 认为单线程就天然支持多命令的事务原子性。

**记忆锚点**

内存加 epoll 加无锁；命令单线程，IO 6.0 多线程。

### 2. 【必答】数据结构：五种基本类型分别用什么底层编码，跳表为什么用在 zset？

**口述版**

String 用 SDS，带 len 和 alloc 字段，二进制安全，小于 1MB 翻倍扩容、超过 1MB 每次加 1MB；短字符串用 embstr 一次分配，长字符串用 raw。List 在 3.2 之后是 quicklist，由多个 listpack 节点串成双向链表，7.0 之前节点里是 ziplist。Hash 小数据用 listpack，超过 512 个字段或单个值超过 64 字节就转成 dict。Set 全整数且数量小于 512 用 intset，7.2 之后小集合还可以用 listpack，否则是 hashtable。ZSet 小数据用 listpack，大了转成 skiplist 加 dict：dict 存 member 到 score 的映射，保证 O(1) 查分值，skiplist 按 score 有序，支持范围查询和 rank。用跳表而不是红黑树，是因为范围查询顺着底层链表扫就行，实现简单，还容易维护 rank 和插入删除。

**短版**

String 是 SDS；List 是 quicklist 套 listpack；Hash 小用 listpack 大用 dict；Set 用 intset/listpack/hashtable；ZSet 小用 listpack 大用 skiplist 加 dict。

**展开版**

- 机制链：写入时按阈值判断编码 → 小数据用紧凑结构省内存 → 超阈值一次性或渐进式转换 → 转换不可逆，删小后也不会退回。
- 关键结构：SDS 的 len/alloc/free、quicklist 节点、listpack 的连续内存、dict 的渐进式 rehash、skiplist 的多层索引。
- 触发条件：字段数、单值长度、元素个数超过 hash-max-listpack-entries、zset-max-listpack-entries 等配置。
- 例外：编码阈值可调，调大省内存但单次操作变慢；7.0 用 listpack 替代 ziplist 解决连锁更新。
- 对比取舍：紧凑编码省内存、CPU 换空间；skiplist 范围查询强于红黑树，内存开销略大。

**追问预判**

- 跳表和红黑树怎么选 → 跳表范围查询和 rank 更自然、实现简单；红黑树内存更紧，但范围遍历要中序回溯。
- 渐进式 rehash 解决什么 → 避免大字典一次性扩容卡住主线程，分批搬桶。
- 为什么 zset 要 dict 加 skiplist 两份 → 一个管按 member 查分值，一个管按分值范围与排名，各取所长。

**常见错误答法**

- 把 zset 说成红黑树或纯跳表，漏掉 dict。
- 认为编码转换后数据量变小会退回紧凑编码。

**记忆锚点**

小数据 listpack、大数据 dict/skiplist；zset 双结构，一个查分一个排序。

### 3. 【进阶】原子操作：Pipeline、Lua 和事务的原子性边界差在哪？

**口述版**

Pipeline 是客户端把一批命令一次性发出去，省的是网络往返，服务端还是逐条执行，中间可以插入其他客户端的命令，所以不保证原子，某条失败也不影响后面的，会部分成功。MULTI/EXEC 事务是服务端把命令排队，EXEC 时连续执行不被别人插入，但它没有回滚：入队阶段报错比如命令不存在，整个 EXEC 会放弃；运行阶段报错比如对 string 执行 lpush，只有这一条失败，其他照样执行。WATCH 提供乐观锁，key 被改过 EXEC 就返回 nil。Lua 脚本是真正的原子执行，整段跑完才处理别的命令，可以写判断加删除这种组合逻辑；但脚本必须短，超过 lua-time-limit 只会打日志不会中断，只能用 SCRIPT KILL 或 SHUTDOWN NOSAVE。Cluster 下事务和脚本涉及的 key 必须在同一个槽。

**短版**

Pipeline 省 RTT 不原子；事务顺序执行但无回滚，只保证不被插入；Lua 真原子，可写逻辑，但必须快且同槽。

**展开版**

- 机制链：客户端攒命令 → 一次发送 → 服务端按序执行 → 一次性返回；事务多一步入队和 EXEC；Lua 则把脚本整体交给服务端执行。
- 关键结构：输入缓冲区、MULTI 队列、WATCH 的脏 key 标记、Lua 解释器与 lua-time-limit。
- 触发条件：批量读写、需要“判断再写”的原子逻辑、分布式锁释放、库存扣减。
- 例外：事务里的运行时错误不回滚；脚本里不能用随机命令（7.0 前）和阻塞命令；集群模式多 key 要 hash tag。
- 对比取舍：Pipeline 最快但无原子；事务弱原子；Lua 原子但会阻塞主线程，长脚本等于拖垮实例。

**追问预判**

- Pipeline 和 mget 什么区别 → mget 是单条命令、原子且省 RTT；pipeline 是客户端批量，命令之间可被插入。
- Lua 会不会阻塞其他请求 → 会，执行期间主线程不处理其他命令，所以脚本要控制在毫秒级。
- 分布式锁释放为什么必须用 Lua → 判断 value 和删除要原子，否则可能删掉别人的锁。

**常见错误答法**

- 认为 Redis 事务能像数据库一样回滚。
- 认为 Pipeline 里的命令不会被其他客户端打断。

**记忆锚点**

Pipeline 省 RTT、事务无回滚、Lua 真原子但要短。

### 4. 【兜底】容量治理：大 key 和热 key 怎么发现、怎么治？

**口述版**

大 key 一般指 String 超过 10KB 到 1MB，或者集合元素超过五千到一万。危害在四个地方：网络一次传太多阻塞其他请求；删除时同步释放内存会卡主线程，要用 unlink 配合 lazyfree；持久化 fork 和 AOF 重写时复制放大；集群里造成数据和流量倾斜。发现手段是 redis-cli --bigkeys 抽样、MEMORY USAGE 精确看单个 key、离线分析 RDB、慢日志和 scan 采样。治理就是拆：hash 按桶拆成多个 key，大 list 分片，只存必要字段，压缩 value，删除用 unlink。热 key 是单个 key 的 QPS 极高，打满一个分片或一个核。发现靠代理层统计、monitor 短时采样、LFU 策略下的 --hotkeys、业务埋点。治理是本地缓存挡一层、key 加随机后缀拆成多副本分散读、读写分离、必要时限流。

**短版**

大 key 拆、压缩、unlink、lazy free；热 key 本地缓存、加后缀打散、读写分离、限流；发现靠 bigkeys、MEMORY USAGE、hotkeys、monitor 采样。

**展开版**

- 机制链：采样或统计发现异常 key → 判断是大 key 还是热 key → 评估影响面（网络、阻塞、倾斜）→ 拆分或加缓存 → 回归验证 RT 与倾斜。
- 关键结构：--bigkeys 的抽样逻辑、MEMORY USAGE、RDB 离线分析、LFU 计数器、代理层 key 维度统计。
- 触发条件：大促、批量导入、榜单类结构、单商品详情页、秒杀。
- 例外：大 key 不一定是问题，低频访问的大 key 影响有限；热 key 也可能来自代码里的全量扫描。
- 对比取舍：拆分增加代码复杂度但根治；加本地缓存最快但引入一致性成本；限流保系统但伤体验。

**追问预判**

- 为什么 del 大 key 会卡 → 释放内存是同步的，元素多时主线程被占；用 unlink 交给后台线程。
- 热 key 加随机后缀后怎么读 → 读时随机选一个副本，或写多读时全量聚合，取决于业务。
- 大 key 拆分后怎么保证原子 → 用 Lua 或事务操作同槽的多个子 key，或者接受最终一致。

**常见错误答法**

- 只说“不要用大 key”，说不出发现手段和删除阻塞的原因。
- 热 key 只靠扩容，没意识到单个 key 永远落在一个槽。

**记忆锚点**

大 key 拆加 unlink，热 key 打散加本地缓存。

## 二、持久化与内存治理

### 5. 【必答】持久化：RDB、AOF 与混合持久化各自怎么工作，怎么选？

**口述版**

RDB 是快照，bgsave 时 fork 子进程，靠写时复制拿到一致的内存视图，写成紧凑的二进制文件。优点是文件小、恢复快，适合备份和全量同步；缺点是会丢最后一次快照之后的数据，fork 在内存大时会有明显的延迟和内存放大。AOF 是追加写命令，appendfsync 三种：always 每条刷盘最安全最慢，everysec 每秒刷，最多丢一秒，no 交给操作系统。AOF 文件大、恢复慢，所以有重写，也就是 bgrewriteaof，用当前数据生成最小命令集，重写期间的增量写进重写缓冲区，最后合并。4.0 之后有混合持久化，AOF 重写时前半段写 RDB 格式，后面追加增量 AOF，aof-use-rdb-preamble 打开，兼顾恢复速度和丢数据窗口。生产上一般是主从加 AOF everysec 或者混合，RDB 用来做冷备和跨机房传输。

**短版**

RDB 快照 fork 加 COW，恢复快但会丢数据；AOF 追加命令，everysec 最多丢一秒，文件大要重写；混合持久化 RDB 头加 AOF 尾。

**展开版**

- 机制链：bgsave fork → COW 共享页 → 子进程写 RDB → 父进程继续服务；AOF 则是写命令先进缓冲区 → fsync 策略决定刷盘时机 → 重写时生成新文件并合并增量。
- 关键结构：fork 与 COW、RDB 文件格式、AOF 缓冲区、重写缓冲区、aof-use-rdb-preamble。
- 触发条件：save 配置、主从全量同步、手动 BGSAVE、AOF 增长率触发重写。
- 例外：fork 本身会阻塞主线程，内存越大越久；COW 期间写入多会让内存接近翻倍；磁盘满会导致持久化失败。
- 对比取舍：RDB 快但可能丢；AOF 安全但慢且大；混合是默认推荐，代价是兼容性和实现复杂度。

**追问预判**

- fork 时内存会立刻翻倍吗 → 不会，只有被修改的页才复制，但写多时可能接近翻倍。
- 为什么不用 always → 每条命令一次 fsync，吞吐掉一个数量级，通常用 everysec 加业务补偿。
- 主从全量同步用 RDB 还是 AOF → 用 RDB，先传快照再追增量，AOF 太大不适合传输。

**常见错误答法**

- 认为开了 AOF 就完全不丢数据。
- 认为 bgsave 期间内存一定翻倍。

**记忆锚点**

RDB 快照恢复快、AOF 追加更安全、混合两头兼顾。

### 6. 【必答】过期与淘汰：过期 key 怎么删，内存满了按什么策略淘汰？

**口述版**

过期删除是惰性加定期。惰性删除是访问到这个 key 时才检查是否过期，过期就删并返回空，所以不访问的过期 key 会一直占内存。定期删除是每 100 毫秒随机抽一批设了 TTL 的 key，过期比例超过 25% 就继续抽，同时限制占用的 CPU 时间不超过 25%，避免影响主线程。内存达到 maxmemory 后触发淘汰，策略有八种：noeviction 是默认，写请求直接报 OOM；allkeys-lru、allkeys-lfu、allkeys-random 在所有 key 里淘汰；volatile-lru、volatile-lfu、volatile-random、volatile-ttl 只在设了过期时间的 key 里淘汰。LRU 是近似实现，采样几个挑最久没用的；LFU 是 4.0 加入的，用计数加时间衰减，适合热点稳定的缓存场景。缓存场景一般用 allkeys-lfu 或 allkeys-lru，不要用 volatile 系列，因为可能没有带 TTL 的 key 可淘汰，最后还是 OOM。

**短版**

惰性删除加定期抽样，过期不一定立刻释放；淘汰八种策略，缓存用 allkeys-lru/lfu，别用 volatile，noeviction 会直接报错。

**展开版**

- 机制链：写入时检查 maxmemory → 超限按策略挑 victim → 删除并回收 → 仍不足则拒绝写入；过期则是访问检查加后台抽样。
- 关键结构：expires 字典、抽样比例、maxmemory-policy、LRU 时钟与 LFU 计数器、evicted_keys 指标。
- 触发条件：缓存无 TTL、流量增长、value 变大、批量导入。
- 例外：从库不主动过期，等主库 DEL 复制过来，读从库可能读到逻辑上已过期的数据。
- 对比取舍：LRU 简单但对扫描型流量不友好；LFU 抗扫描但计数需要衰减，冷启动阶段容易误判。

**追问预判**

- 过期 key 为什么还占内存 → 不访问就不会触发惰性删除，定期删除又是抽样，可能长期残留。
- volatile 策略有什么坑 → 只淘汰带 TTL 的 key，如果没有带 TTL 的 key 就淘汰不了，写请求照样失败。
- 从库读到过期数据怎么办 → 业务容忍或强制读主，3.2 之后从库读会返回空但不删除。

**常见错误答法**

- 认为 Redis 默认策略是 LRU。
- 认为设了 TTL 就一定会准时释放内存。

**记忆锚点**

惰性加定期抽样；缓存用 allkeys-lfu，慎用 volatile。

### 7. 【进阶】内存治理：碎片率怎么判断，容量该按什么口径规划？

**口述版**

碎片率看 mem_fragmentation_ratio，也就是 RSS 除以 used_memory。大于 1.5 说明碎片偏多，小于 1 说明有一部分内存被换到 swap 了，这时候延迟会很差。碎片来源是 jemalloc 按大小类分配、频繁增删不同大小的对象、大 key 释放、以及 fork 时的写时复制。处理可以开 activedefrag 让后台整理，配置阈值和最小收益，或者低峰重启、主从切换重建实例。容量规划不能只按业务数据量算，要按“条目数乘平均大小乘开销系数乘副本数”，再预留 30% 到 50% 的 buffer 给碎片、COW、AOF 重写缓冲和突发写入。单实例不建议太大，一般 10 到 16GB 上限，因为 fork 停顿、全量同步、故障恢复时间都跟内存成正比。超了就分片，而不是继续堆内存。

**短版**

碎片率 RSS/used_memory，大于 1.5 偏高、小于 1 在 swap；activedefrag 或重建；容量按条目乘大小乘副本再留 30% 到 50%，单实例 10 到 16GB。

**展开版**

- 机制链：分配器按大小类给页 → 对象增删造成空洞 → 碎片率上升 → 开启主动整理或重建实例 → 指标回落。
- 关键结构：used_memory、used_memory_rss、mem_fragmentation_ratio、activedefrag 阈值、jemalloc 的 size class。
- 触发条件：频繁写入删除、大量不同长度 value、大 key 批量删除、长期运行。
- 例外：RSS 高也可能是正常的分配器预留，不一定是碎片；开了 swap 时碎片率反而小于 1，是更危险的信号。
- 对比取舍：主动整理消耗 CPU；重启最彻底但有中断；分片从根本上控制单实例规模。

**追问预判**

- fork 时内存怎么估 → 按写入速率和 COW 页数估，最坏接近翻倍，规划时要留出余量。
- maxmemory 该设多少 → 小于实例物理内存，扣掉副本缓冲、碎片和系统占用，通常 60% 到 70%。
- 为什么不建议单实例太大 → fork 和全量同步的停顿随内存增长，故障恢复也慢。

**常见错误答法**

- 只按业务数据量估容量，不留碎片和 COW 的余量。
- 看到碎片率高就直接重启，不先判断是不是 swap 或正常预留。

**记忆锚点**

碎片率 1.5 警戒、小于 1 查 swap；单实例 10G 量级，预留三到五成。

### 8. 【兜底】故障排查：内存打满、RT 抖动、慢查询，按什么顺序定位？

**口述版**

先看现象属于哪类：写入报 OOM command not allowed，说明到了 maxmemory 且淘汰不动；连接超时或 RT 抖动，可能是大 key、阻塞命令、fork、swap 或网络。排查顺序是 info memory 看 used_memory、maxmemory、碎片率；info stats 看 evicted_keys、keyspace_hits 和 misses；slowlog get 看慢命令；latency monitor 或 latency history 看延迟事件；client list 看输出缓冲区 omem，找出大结果集的客户端；再用 --bigkeys 和 info commandstats 找 O(N) 命令。常见根因是无 TTL 的 key 堆积、大 key、输出缓冲区超限被断开、AOF 重写或 fork 阻塞、swap、带宽打满、热 key。处置按根因来：扩容或分片、scan 加 unlink 清理、调整淘汰策略、限流降级、把热点挪到本地缓存。

**短版**

先分 OOM 还是延迟；看 info memory/stats、slowlog、latency、client list、bigkeys、commandstats；根因多为无 TTL 堆积、大 key、fork、swap、热 key。

**展开版**

- 机制链：告警或用户反馈 → 区分写入失败与延迟升高 → 拉取内存、统计、慢日志 → 定位到具体 key 或命令 → 处置并回归。
- 关键结构：info memory/stats、slowlog-log-slower-than、latency monitor、client-output-buffer-limit、commandstats。
- 触发条件：大促、批量任务、发布后流量突增、主从切换、AOF 重写。
- 例外：延迟抖动也可能来自宿主机、虚拟化、网络抖动，要结合监控一起看。
- 对比取舍：限流止血快但影响业务；扩容彻底但成本高；清 key 见效快但可能误删，要按前缀和确认。

**追问预判**

- 输出缓冲区为什么会爆 → 客户端读得慢或用了 monitor，主库持续推送把缓冲区撑大，超过限制会被强制断开。
- 慢日志阈值怎么设 → 按业务 RT 目标设，比如 10ms，先采样再调整，避免日志本身成为负担。
- 怎么确认是 fork 导致 → 看 latest_fork_usec 和延迟时间点是否与 bgsave、重写重合。

**常见错误答法**

- 一上来就扩容，不先确认是大 key 还是淘汰策略问题。
- 用 keys 命令找大 key，反而把实例打挂。

**记忆锚点**

先分 OOM 与延迟；memory、stats、slowlog、latency、bigkeys 五连查。

## 三、集群与高可用

### 9. 【必答】复制与哨兵：主从复制的全量增量流程是什么，哨兵怎么完成故障转移？

**口述版**

主从复制分全量和增量。从库第一次连上来发 psync 问主库的 runid 和 offset，主库执行 bgsave 生成 RDB，同时把期间的写命令放进复制缓冲区，RDB 传完从库加载，再追复制缓冲区里的增量，之后主库持续把写命令传播给从库。断线重连时如果 offset 还在 repl_backlog 环形缓冲区里，就只补增量；不在就退化成全量。复制是异步的，主库写完就返回，所以有丢数据窗口。哨兵负责监控、通知、故障转移和配置提供。单个哨兵 ping 超时是主观下线，达到 quorum 个哨兵同意才是客观下线，然后哨兵之间选一个 leader，由它挑新主，规则是优先级、复制 offset 最大、runid 最小，再把其他从库指过去，最后通知客户端。哨兵本身至少三个且是奇数，客户端要能感知新地址，通常靠哨兵感知加客户端刷新，或者 VIP、代理。

**短版**

全量是 psync 加 bgsave 加复制缓冲区，增量靠 repl_backlog 和 offset；哨兵主观下线、quorum 客观下线、leader 选举、按优先级和 offset 选新主。

**展开版**

- 机制链：从库 psync → 主库 bgsave 并缓冲增量 → 传 RDB → 从库加载 → 追增量 → 持续传播；故障时哨兵判死、选举、切换、通知。
- 关键结构：runid、offset、repl_backlog、复制缓冲区、sentinel quorum、sentinel leader 选举。
- 触发条件：首次建立复制、网络闪断、主库重启、主库宕机。
- 例外：repl-backlog 太小或断线太久会全量同步；哨兵切换期间写入会失败或丢失；旧主恢复后会被降为从库并清空数据重同步。
- 对比取舍：异步复制性能好但有丢失窗口；quorum 太大降低可用性，太小容易误切。

**追问预判**

- 什么时候触发全量同步 → 首次复制、runid 不匹配、offset 不在 backlog 范围内。
- 哨兵为什么至少三个 → 要能形成多数派，两个节点在网络分区时无法可靠判定。
- 切换后旧主回来怎么办 → 被降级为从库，全量同步新主数据，期间旧主上未同步的写会丢。

**常见错误答法**

- 认为主从复制是同步的、主库要等从库确认。
- 认为哨兵也存数据、能分担读流量。

**记忆锚点**

全量 RDB 加增量 backlog；哨兵 quorum 判死、leader 选举、选 offset 最大的从库。

### 10. 【必答】Cluster：16384 个槽怎么分片，MOVED 和 ASK 有什么区别？

**口述版**

Redis Cluster 把整个键空间分成 16384 个槽，用 CRC16 对 key 取模落槽，每个主节点负责一部分槽，通常至少三主三从。客户端本地缓存槽到节点的映射，算错或者映射过期时，节点返回 MOVED 告诉客户端这个槽现在归谁，客户端更新映射重试。槽迁移过程中，源节点对已迁走的 key 返回 ASK，让客户端临时去目标节点查一次，但客户端不更新映射，因为迁移还没完成。这就是 MOVED 是永久重定向、ASK 是临时重定向的区别。集群的限制是多 key 命令和事务、Lua 涉及的 key 必须在同一个槽，可以用 hash tag 把相同前缀的 key 固定到一个槽；跨槽的 mget 要客户端拆成多次。节点之间用 gossip 协议走集群总线通信，故障转移是主观下线、多数主节点客观下线、从节点按 offset 选举提升。

**短版**

16384 槽，CRC16 取模；MOVED 永久改映射，ASK 迁移中临时跳转；多 key 要同槽，用 hash tag；从节点按 offset 选举。

**展开版**

- 机制链：客户端算槽 → 请求任意节点 → 节点判断归属 → 本地执行或返回 MOVED/ASK → 客户端重试并更新缓存。
- 关键结构：16384 个槽位、槽位图、gossip 总线端口、clusterState、迁移状态 importing 和 migrating。
- 触发条件：扩容缩容、槽迁移、节点故障、客户端映射过期。
- 例外：迁移期间同一个 key 可能先被 ASK 到目标节点；批量迁移时大 key 会阻塞；集群模式不支持跨槽事务。
- 对比取舍：客户端分片简单但扩缩容难；Cluster 原生支持自动分片和故障转移，但多 key 操作受限；代理方案对业务透明但多一跳。

**追问预判**

- 为什么是 16384 个槽 → 槽位图用位图存，16384 个 bit 是 2KB，心跳包能带得下，再大就浪费带宽。
- ASK 期间源节点怎么处理请求 → 已迁走的 key 返回 ASK，没迁走的正常处理。
- 集群下 pipeline 和事务怎么做 → 按槽分组发 pipeline，事务和 Lua 只能操作同槽 key。

**常见错误答法**

- 把 MOVED 当成错误码直接抛给业务，不做重定向。
- 认为 Cluster 下所有多 key 命令都能直接用。

**记忆锚点**

16384 槽 CRC16；MOVED 永久、ASK 临时；多 key 靠 hash tag 同槽。

### 11. 【进阶】脑裂与一致性：主从切换为什么会丢数据，怎么把窗口压到最小？

**口述版**

根因是复制异步。网络分区时，主库和哨兵失联，但客户端还能写这个旧主；哨兵在另一侧选出新主开始服务；等网络恢复，旧主被降为从库，做全量同步，分区期间写在旧主上的数据就被覆盖掉了，这就是脑裂丢数据。就算没有分区，主库宕机时还没 fsync 的写也会丢，AOF everysec 最多丢一秒。缓解手段有三个层次：一是配置 min-replicas-to-write 和 min-replicas-max-lag，要求至少有 N 个从库且延迟不超过 M 秒才允许写，代价是可用性下降；二是用 WAIT 命令等指定数量的从库确认，属于按需的准同步；三是业务侧做幂等、对账和补偿，把丢数据的影响兜住。任何自动切换都做不到零丢失，要强一致就得牺牲可用性或者换用支持同步复制的系统。

**短版**

异步复制加分区导致旧主仍可写，恢复后被覆盖；用 min-replicas、WAIT 缩小窗口，业务靠幂等和对账兜底；强一致必然牺牲可用性。

**展开版**

- 机制链：网络分区 → 哨兵判定主库下线 → 选新主 → 旧主仍接受写 → 分区恢复 → 旧主降级全量同步 → 未同步写丢失。
- 关键结构：min-replicas-to-write、min-replicas-max-lag、WAIT 的 numreplicas 与 timeout、offset 与 backlog。
- 触发条件：机房网络抖动、主库假死、GC 或 fork 导致心跳超时、跨机房部署。
- 例外：min-replicas 配置过严会让主库在从库故障时直接拒绝写，等于把可用性押在从库上。
- 对比取舍：WAIT 提高一致性但增加延迟；多数派写入更安全但 Redis 原生不支持；业务补偿最实用但只能做到最终一致。

**追问预判**

- WAIT 能保证不丢吗 → 只能保证发出命令时指定数量的从库已收到，不保证之后不丢，也不是强一致协议。
- 怎么发现已经丢了数据 → 业务对账、binlog 或消息补偿、比对主从 offset 和写入日志。
- 假死怎么避免 → 合理设置超时和复制缓冲，避免 fork、大 key 删除造成心跳超时。

**常见错误答法**

- 认为加了哨兵就不会丢数据。
- 把 WAIT 当成同步复制，认为能完全避免脑裂。

**记忆锚点**

异步复制必有窗口；min-replicas 加 WAIT 缩小，幂等对账兜底。

### 12. 【兜底】扩缩容：槽迁移怎么做，热点槽和数据倾斜怎么处理？

**口述版**

扩容是加节点、cluster meet 建立连接、再用 reshard 把一部分槽从老节点迁到新节点。迁移以槽为单位，先标记 importing 和 migrating，然后逐个 key 用 migrate 搬到目标，搬完把槽归属改过去，客户端通过 ASK 和 MOVED 无感切换。要注意大 key 会阻塞、迁移要限速、尽量在低峰做，并且监控延迟和迁移进度。缩容反过来，先把槽全部迁走，再删节点，注意别破坏多数派。热点槽的本质是某个 key 或某类 key 的哈希集中，单 key 永远落在一个槽，扩节点也没用。处理办法是 key 加随机后缀拆成多份，读的时候随机选或者聚合；或者用业务维度预分片，先建固定数量的逻辑桶再映射；再叠加本地缓存挡最热的那一层。数据倾斜要看是槽数不均还是单槽数据量不均，前者 rebalance，后者拆 key。

**短版**

加节点、meet、reshard 按槽迁移，迁移中 ASK；缩容先迁槽再删节点；热点槽靠 key 拆分、预分片、本地缓存，槽不均靠 rebalance。

**展开版**

- 机制链：加入节点 → 分配槽 → 标记迁移状态 → 逐 key MIGRATE → 改槽归属 → 客户端重定向完成切换。
- 关键结构：cluster nodes 的槽分布、migrating/importing 标记、MIGRATE 的批量参数、rebalance 权重。
- 触发条件：容量不足、单节点 CPU 或带宽打满、故障后节点替换、业务增长。
- 例外：迁移中如果源节点宕机，槽状态可能不一致，需要人工修复；大 key 迁移会长时间占用连接。
- 对比取舍：原生 reshard 无需停服但慢；离线迁移快但要停机；代理分片扩容简单但多一层。

**追问预判**

- 迁移时业务会不会报错 → 正常不会，客户端跟随 ASK 重试即可，但 RT 会上升，重试逻辑不完善的客户端会暴露问题。
- 怎么判断是槽不均还是 key 不均 → 看各节点 key 数量和槽数量，槽少但 key 多说明单槽倾斜。
- 预分片怎么设计 → 一开始就建远多于当前节点数的逻辑桶，扩容时搬桶而不是搬 key。

**常见错误答法**

- 认为加机器就能解决热 key，忽略单 key 落单槽。
- 迁移不看大 key 和限速，直接把主线程拖住。

**记忆锚点**

按槽迁移、ASK 过渡；热点拆 key、预分片、本地挡。

## 四、三大问题与一致性

### 13. 【必答】缓存穿透：查不存在的数据怎么防，布隆过滤器怎么用？

**口述版**

穿透是请求的数据在缓存和数据库里都不存在，缓存永远不命中，每次都打到数据库，常见于恶意攻击或者非法 ID。三层防护：第一层参数校验和限流，ID 格式不对、超出范围直接拒掉，接口做鉴权和风控；第二层布隆过滤器，把所有可能存在的 key 放进位图，请求先过布隆，判断不存在就直接返回，它有误判无漏判，也就是说不存在的可能被误判为存在，但存在的不会被漏掉；第三层空值缓存，查不到也写一个空值或特殊标记，设一个较短的 TTL，比如几十秒到几分钟，防止同一个不存在的 key 反复打库。三者组合使用：布隆挡住绝大部分，空值缓存兜住漏网的，限流防止被打垮。注意布隆不支持删除，数据变更要么重建，要么用计数布隆，空值缓存的 TTL 不能太长，否则数据后来真的新增了会不一致。

**短版**

参数校验加限流、布隆过滤器前置、空值缓存短 TTL；布隆有误判无漏判、不支持删除。

**展开版**

- 机制链：请求进来 → 参数与鉴权校验 → 布隆判断 → 未命中直接返回 → 命中查缓存 → 再查库 → 空值也回填短 TTL。
- 关键结构：布隆位图与多个哈希函数、空值标记、TTL、限流器与风控规则。
- 触发条件：恶意爬取、非法 ID 遍历、数据被删除后仍被查询、业务 ID 不连续。
- 例外：布隆容量和误判率要预估，元素远超预期时误判率会上升；新增数据要同步写布隆，否则会被误拦。
- 对比取舍：布隆省内存但有误判和删除难题；空值缓存简单但占内存且有一致性延迟；限流最直接但可能误伤正常用户。

**追问预判**

- 布隆为什么有误判 → 多个哈希落位都被其他元素置为 1，判断存在时可能是假阳性，但不存在一定判不存在。
- 布隆怎么删除 → 原生不支持，用计数布隆或定期重建，重建要双写过渡。
- 空值缓存会不会把库打爆 → 不会，但会占内存，TTL 要短，并且要和限流配合防大规模攻击。

**常见错误答法**

- 只用空值缓存，不给 TTL，导致脏数据长期存在。
- 用了布隆但新增数据不更新过滤器，把正常请求拦掉。

**记忆锚点**

校验限流、布隆、空值短 TTL，三层一起上。

### 14. 【必答】缓存击穿：单个热点 key 过期瞬间怎么扛？

**口述版**

击穿是某一个热点 key 过期的那一瞬间，大量并发请求同时未命中，全部回源打数据库。两种主流方案。第一种是互斥重建：只让一个线程或一个实例去查库重建，其他请求等待或者直接返回旧值。单机用 synchronized 或 singleflight，跨实例用 Redis 分布式锁，锁要设超时、value 用唯一标识、释放用 Lua 校验，避免死锁和误删。第二种是逻辑过期：key 不设物理 TTL，value 里带一个过期时间，读到发现逻辑过期就返回旧值，同时异步起一个任务去重建，重建期间所有请求都读旧值。互斥方案一致性好，但等待的请求 RT 会抖动，还有锁失效风险；逻辑过期可用性高、没有等待，但有短暂不一致，实现也更复杂。热点数据也可以干脆永不过期加后台定时刷新。

**短版**

互斥重建只放一个回源；逻辑过期返回旧值异步刷新；前者一致但有等待和锁风险，后者可用但有短不一致。

**展开版**

- 机制链：读缓存未命中或逻辑过期 → 抢锁或触发异步任务 → 只有一个执行回源 → 回填缓存 → 其他请求等待或读旧值。
- 关键结构：分布式锁的 SET NX PX、唯一 value、Lua 释放、value 内的 expireAt、异步线程池。
- 触发条件：秒杀、大促、首页榜单、明星热点、单 key QPS 极高。
- 例外：锁超时短于重建耗时会导致重复回源；重建失败要保留旧值，不能把缓存删掉。
- 对比取舍：互斥简单但 RT 有毛刺；逻辑过期平滑但有脏读窗口；永不过期最简单但要保证刷新机制可靠。

**追问预判**

- 锁怎么避免死锁和误删 → 设过期时间，value 用 UUID 加线程标识，释放时 Lua 比较再删。
- 逻辑过期下数据库压力怎么控 → 异步重建只起一个任务，用本地标记或分布式锁保证单飞。
- 重建失败怎么办 → 保留旧值并告警，退避重试，不要清空缓存。

**常见错误答法**

- 用 setnx 加锁但不设过期时间，宕机后锁永久不释放。
- 重建失败时把缓存删掉，导致下一波请求继续打库。

**记忆锚点**

互斥重建或逻辑过期；锁要超时加唯一值加 Lua 释放。

### 15. 【必答】缓存雪崩：大面积失效或 Redis 整体故障怎么防？

**口述版**

雪崩有两种形态：一是大量 key 在同一时刻过期，二是 Redis 整体不可用，两种都会让流量瞬间全压到数据库。针对同时过期，核心是打散 TTL，在基础过期时间上加随机抖动，比如基础 30 分钟加 0 到 5 分钟；热点 key 用逻辑过期或永不过期加后台刷新。针对 Redis 故障，要多级缓存兜底，本地缓存能挡住一部分读；要有熔断限流，缓存不可用时限制回源 QPS，保护数据库；要有降级策略，比如返回默认值、空列表或者旧数据，具体看业务能不能接受；架构上主从加哨兵或者 Cluster 保证高可用，持久化保证恢复；DB 侧连接池和限流也要设好，避免被打穿后连锁失败。另外要有预热，重启或扩容后不要让冷缓存直接接全量流量。

**短版**

TTL 加随机抖动、热点逻辑过期；Redis 故障靠本地缓存、熔断限流、降级兜底、集群高可用和预热。

**展开版**

- 机制链：大批 key 同时过期或实例不可用 → 命中率骤降 → 回源 QPS 暴涨 → DB 连接池耗尽 → 接口雪崩 → 上游重试进一步放大。
- 关键结构：TTL 抖动、多级缓存、熔断器状态机、限流算法、连接池上限、预热任务。
- 触发条件：批量导入同一批 TTL、凌晨定时任务、缓存实例重启、主从切换、网络分区。
- 例外：抖动只能防同时过期，防不了实例整体故障；降级返回旧数据要业务能接受。
- 对比取舍：限流保 DB 但会拒绝部分请求；本地缓存挡流量但有一致性成本；扩容最直接但成本高。

**追问预判**

- 抖动范围怎么定 → 按业务对过期时间的敏感度，一般基础 TTL 的 10% 到 20%，别让过期集中。
- Redis 挂了应用会怎样 → 取决于有没有超时、熔断和本地兜底，没做的话 RT 飙升、线程池打满。
- 预热怎么做 → 启动时按 TopN 榜单加载，分批限速，校验加载结果，监控命中率。

**常见错误答法**

- 只加随机 TTL，不考虑 Redis 整体不可用。
- 缓存异常时无限重试，把故障放大成雪崩。

**记忆锚点**

TTL 抖动加多级缓存加限流降级，四件套。

### 16. 【进阶】更新策略：先删缓存还是先更新数据库，为什么推荐删而不是更新？

**口述版**

常见四种组合。先删缓存再更新库，并发读会在删完之后读到旧库、再回填旧值，不一致很明显。先更新库再删缓存，也就是 Cache Aside，是主流方案，但它也不是绝对一致：读请求在写之前读到了旧值，写请求更新库并删缓存，读请求再把旧值回填进去，就留下了脏数据。先更新库再更新缓存，问题更多，并发写会覆盖，缓存值还要重新计算，写多读少时纯属浪费。先更缓存再更库，失败时不一致更严重。所以推荐先更新数据库再删除缓存，原因是删除幂等、不会出现并发写互相覆盖、也不会做无用的计算。删除失败要靠重试、消息或者订阅 binlog 来补偿。要彻底消除那个回填窗口，就用延迟双删或者 binlog 驱动删除。

**短版**

先更库后删缓存是主流；删比更新幂等、无并发覆盖、无无效计算；仍有回填旧值的窗口，用双删或 binlog 补偿。

**展开版**

- 机制链：写请求更新 DB → 删除缓存 → 读请求未命中 → 读库（可能读到旧值）→ 回填；窗口就在读库和回填之间。
- 关键结构：Cache Aside 模式、删除重试表、消息队列、binlog 订阅、读写分离下的主从延迟。
- 触发条件：读写并发、热点 key、主从延迟大、删除失败。
- 例外：读多写少、能接受短暂不一致的业务，Cache Aside 足够；强一致业务不该把缓存当权威数据源。
- 对比取舍：删除简单可靠但有窗口；更新缓存省一次读但有一致性和计算成本；加锁串行化最一致但吞吐最差。

**追问预判**

- 为什么不是更新缓存 → 并发写会以错的顺序覆盖，且很多缓存值是多表聚合，更新代价高还可能算错。
- 删除失败怎么办 → 本地重试表加定时补偿，或者发 MQ，最可靠的是订阅 binlog 异步删。
- 能做成强一致吗 → 可以加分布式锁串行化读写，但吞吐会大幅下降，通常不值得。

**常见错误答法**

- 认为先更库后删缓存就完全一致了，忽略回填旧值的窗口。
- 用“更新缓存”代替删除，还认为这样更实时。

**记忆锚点**

先更库、后删缓存；删是幂等，失败要补偿。

### 17. 【进阶】最终一致性：延迟双删和 binlog 订阅各解决什么问题，怎么落地？

**口述版**

延迟双删是在更新数据库之前删一次缓存，更新之后再延迟一段时间删第二次。第二次删是为了清掉在更新期间被读请求回填的旧值。延迟时间要覆盖一次读请求的耗时加上主从同步延迟，实际很难精确估，估短了没用，估长了不一致窗口变长，所以它只能算兜底，不能当主方案。更可靠的是 binlog 订阅：用 Canal、Debezium 或者 Maxwell 伪装成从库，解析 row 格式的 binlog，把变更发到消息队列，消费端按 key 删除缓存。好处是和业务解耦、不依赖应用是否记得删、消息可重放可补偿；要注意按 key 分区保证同一 key 的顺序、消费要幂等、删除失败要重试并进死信。这套方案做到的是秒级最终一致，不是强一致。余额、库存这类强一致场景，要么不走缓存，要么只缓存非权威的展示数据。

**短版**

延迟双删是兜底，延迟难估且第二次可能失败；binlog 订阅 Canal 加 MQ 加消费删缓存，解耦可靠，做到秒级最终一致。

**展开版**

- 机制链：业务写库 → binlog 落盘 → Canal 解析 → 发 MQ（按 key 分区）→ 消费删除缓存 → 失败重试进死信。
- 关键结构：ROW 格式 binlog、Canal 的 serverId 与位点、MQ 分区键、幂等表、死信队列。
- 触发条件：缓存与库不一致投诉、写路径多、跨服务更新同一份数据。
- 例外：binlog 延迟、MQ 积压会让不一致窗口变长；DDL 和大事务会影响解析；非 row 格式拿不到变更前后值。
- 对比取舍：双删零依赖但不可靠；binlog 方案重但可靠；业务发消息轻量但要求所有写路径都覆盖。

**追问预判**

- Canal 的原理 → 伪装成从库向主库发 dump 请求，拿到 binlog 流后解析成结构化变更。
- 消息重复和乱序怎么办 → 同一 key 用相同分区键保证顺序，消费端按版本号或删除幂等处理。
- 删除失败怎么保证最终成功 → 消费重试加死信队列，配定时对账任务扫描热点 key。

**常见错误答法**

- 延迟时间拍脑袋定，既没覆盖主从延迟，也没考虑第二次删除失败。
- 只靠延迟双删就宣称强一致，不给消费端做幂等和补偿。

**记忆锚点**

双删是兜底、binlog 是正解；按 key 保序、消费幂等。

### 18. 【进阶】分布式锁：用 Redis 怎么实现可靠的锁，Redlock 有什么争议？

**口述版**

基本做法是一条命令 SET key value NX PX 30000，把加锁和过期合成原子操作，value 用 UUID 加线程标识，保证只删自己的锁；释放时用 Lua 先比较 value 再删除。业务执行时间不确定时要续期，Redisson 的看门狗默认 30 秒锁、每三分之一周期续一次；可重入用 hash 记录重入次数。锁的核心风险是业务执行超过 TTL 而续期失败，锁被释放后另一个线程进来，出现并发写，解决办法是续期加 fencing token 或者业务幂等。第二个风险是主从切换丢锁：主库加锁成功但还没同步到从库就宕机，从库升主后锁不存在。Redlock 的思路是向 N 个独立节点多数派加锁，但它依赖时钟和网络假设，GC 停顿、时钟漂移、网络延迟都可能破坏安全性，Martin Kleppmann 对此有明确批评。生产上更常见的是单实例或主从加锁，靠业务幂等兜底；对安全性要求极高用 ZooKeeper 或 etcd。

**短版**

SET NX PX 加唯一 value，Lua 比较后删；看门狗续期；主从切换会丢锁，Redlock 有争议；兜底靠幂等或换 ZK/etcd。

**展开版**

- 机制链：SET NX PX 抢锁 → 执行业务 → 看门狗续期 → Lua 校验并删除 → 失败则退避重试。
- 关键结构：NX/PX 原子性、唯一 value、看门狗、可重入计数、fencing token、Redlock 的多数派。
- 触发条件：定时任务防重、库存扣减、幂等控制、跨实例互斥。
- 例外：锁只能保证互斥不能保证业务正确，超时、重试、异步都可能破坏假设；主从异步复制让锁不是绝对安全。
- 对比取舍：Redis 锁性能高、实现简单，但一致性弱；ZK/etcd 靠会话和顺序节点更安全，但性能低、运维重。

**追问预判**

- 为什么不能先 setnx 再 expire → 两条命令之间宕机会导致锁永不过期，必须用一条 SET 带 NX 和 PX。
- Redlock 的问题是什么 → 依赖各节点时钟和网络延迟上界，进程停顿可能让锁在自以为持有期间失效。
- 锁和幂等什么关系 → 锁防并发，幂等防重复，分布式环境下最终要靠幂等保证正确性。

**常见错误答法**

- 释放锁直接 del，不校验 value，删掉别人的锁。
- 认为有了 Redlock 就绝对安全，不做业务幂等。

**记忆锚点**

SET NX PX 加唯一值，Lua 释放；续期加幂等，Redlock 不是银弹。

### 19. 【兜底】故障应对：Redis 不可用或变慢时，应用侧怎么降级？

**口述版**

第一步是超时和熔断。连接超时、读超时都要设短，几十到两百毫秒，失败率超过阈值就熔断，半开探测恢复，不要让请求堆在缓存调用上把线程池占满。第二步是本地缓存兜底，Redis 不可用时读本地 Caffeine，TTL 短一点，接受旧数据。第三步是业务降级，能返回默认值、空列表、旧快照的就返回，非核心链路直接关掉缓存依赖。第四步是限流保护数据库，缓存挡不住的时候，回源 QPS 必须限住，否则数据库会被打穿。第五步是隔离，不同业务用不同实例或至少不同连接池，避免一个业务的热 key 拖垮所有业务。恢复后要有回填和补偿，把降级期间缺的数据补上。最忌讳的是无超时、无限重试、缓存异常直接抛给用户，这三点会把局部故障放大成整体雪崩。

**短版**

短超时加熔断、本地缓存兜底、业务降级默认值、限流保护 DB、连接池隔离；恢复后回填补偿。

**展开版**

- 机制链：缓存调用变慢 → 超时触发 → 熔断打开 → 走本地缓存或降级逻辑 → 限流保护 DB → 半开探测恢复 → 回填。
- 关键结构：连接与读超时、熔断器阈值与半开、本地缓存 TTL、限流器、连接池隔离、降级开关。
- 触发条件：实例宕机、主从切换、网络分区、慢查询拖垮、集群槽迁移。
- 例外：降级返回旧数据要业务确认可接受；熔断太敏感会误伤，阈值要按基线调。
- 对比取舍：降级保可用但伤体验；重试提成功率但会放大流量；本地缓存兜底快但有一致性成本。

**追问预判**

- 怎么判断该降级还是重试 → 看错误类型，连接拒绝和超时适合快速失败，偶发网络错误可以有限重试，且必须带退避和上限。
- 降级期间的数据怎么恢复 → 恢复后按 key 回填或订阅 binlog 补偿，热点数据主动预热。
- 怎么验证降级有效 → 混沌演练，主动注入 Redis 超时和宕机，看 RT、错误率和 DB 负载。

**常见错误答法**

- 缓存异常时无限重试，把 Redis 和 DB 一起打挂。
- 把缓存当强依赖，Redis 一挂整个接口就不可用。

**记忆锚点**

短超时、熔断、本地兜底、限流保 DB、隔离。

## 五、本地缓存与多级缓存

### 20. 【必答】本地缓存：Caffeine 和 Guava Cache 有什么区别，Caffeine 为什么命中率更高？

**口述版**

Guava Cache 是比较老的方案，用分段 LRU，加锁粒度是 segment，淘汰和清理偏弱一致，很多操作要等写入或者手动 cleanUp 才生效，功能上只有基本的过期、容量和加载。Caffeine 是它的替代品，核心是 W-TinyLFU：一个小的窗口 LRU 区接一个 SLRU 主区，再配一个 TinyLFU 的频率草图，用 Count-Min Sketch 记录访问频率并做时间衰减。窗口区保证新对象能进来，主区按频率保留，草图负责把“扫表式”的一次性访问挡在外面，所以抗扫描污染能力比纯 LRU 强，官方基准里命中率明显更高。Caffeine 还支持异步加载、refreshAfterWrite 定期刷新但返回旧值、maximumSize 或 maximumWeight、弱引用、移除监听和命中率统计。要注意它的淘汰是异步维护的，size 是估算值，不是严格即时，所以不能拿它当精确容量控制。

**短版**

Guava 是分段 LRU、清理弱一致；Caffeine 用 W-TinyLFU（窗口加 SLRU 加频率草图），抗扫描、命中率高，支持 refreshAfterWrite 和异步加载。

**展开版**

- 机制链：读请求先进窗口区 → 频率草图记录 → 淘汰时窗口和主区候选比较频率 → 胜者留下 → 异步执行清理。
- 关键结构：window LRU、SLRU 的 probation 与 protected、Count-Min Sketch、maximumWeight 与 weigher。
- 触发条件：本地热点缓存、需要高命中率和低延迟、要防批量扫描污染缓存。
- 例外：淘汰异步导致瞬时超容量；频率草图有误差；refreshAfterWrite 刷新时读到的仍是旧值。
- 对比取舍：Caffeine 命中率和功能都更好，代价是内存开销略高、行为不如简单 LRU 直观；Guava 胜在存量系统兼容。

**追问预判**

- refreshAfterWrite 和 expireAfterWrite 区别 → 前者到点后异步刷新、期间返回旧值；后者到点后失效，下一个请求同步加载。
- 本地缓存容量怎么定 → 用 maximumWeight 按字节估，结合堆大小和 GC 目标，别超过老年代的合理比例。
- 怎么统计命中率 → 开 recordStats，看 hitRate、loadTime、evictionCount，按 key 维度再做埋点。

**常见错误答法**

- 认为 Caffeine 的淘汰是同步精确的，靠它做严格容量控制。
- 用本地缓存存大对象或大结果集，把堆和 GC 拖垮。

**记忆锚点**

W-TinyLFU 抗扫描；refresh 异步刷新返回旧值。

---

### 21. 【进阶】分层设计：多级缓存怎么分层，每层放什么数据、读写路径怎么走？

**口述版**

典型三层是本地缓存、Redis、数据库。本地缓存在进程内，纳秒到微秒级，容量受堆限制，多实例之间天然不一致；Redis 是共享层，毫秒级，容量大，一致性好管；数据库是权威数据源。分层原则是按热度和一致性要求放：极热、变化少、能容忍秒级不一致的放本地，比如配置、类目、榜单快照；一般热数据放 Redis；冷数据和长尾不缓存。读路径是本地未命中查 Redis，再未命中查库，回填时先写 Redis 再写本地，避免本地拿到比 Redis 更新的数据。写路径是先更新数据库，再删 Redis，再广播失效本地，本地靠短 TTL 兜底。一致性优先级要提前定：本地层一般只承诺最终一致，强一致业务不放本地，或者直接读主库。多级缓存的收益是挡住热点和 Redis 故障，成本是一致性复杂度和内存开销。

**短版**

本地放极热且容忍短暂不一致的，Redis 放一般热数据，DB 是权威；读逐层回源、写先更库再删 Redis 再失效本地。

**展开版**

- 机制链：请求 → 本地 → Redis → DB → 逐层回填；写请求 → 更新 DB → 删 Redis → 广播失效本地 → TTL 兜底。
- 关键结构：本地 Caffeine 实例、Redis 集群、回填顺序、失效广播通道、TTL 梯度。
- 触发条件：热点集中、Redis 带宽或 QPS 到瓶颈、需要抗 Redis 故障、RT 要求极低。
- 例外：本地缓存不适合个性化、长尾和强一致数据；多实例扩容后本地命中率会被摊薄。
- 对比取舍：层数越多 RT 越低但一致性越难；只加本地不加失效通道，等于人为制造脏数据。

**追问预判**

- 为什么先写 Redis 再写本地 → 本地是最近的一层，先写 Redis 保证其他实例和后续回源看到的是新值，减少本地比共享层更新的窗口。
- 本地缓存 TTL 设多长 → 按业务不一致容忍度，通常几秒到几分钟，并且必须配失效广播。
- 怎么监控分层效果 → 分别统计本地命中率、Redis 命中率、回源 QPS 和 RT 分位。

**常见错误答法**

- 所有数据都往本地塞，认为层数越多越好。
- 加了本地缓存但没有失效机制，只靠 TTL。

**记忆锚点**

本地极热、Redis 共享、DB 权威；读逐层、写先库后删。

### 22. 【进阶】失效同步：多实例本地缓存怎么保证及时失效，广播丢了怎么办？

**口述版**

本地缓存最大的问题是各实例各存一份，数据库更新后其他实例还是旧值。主流做法是广播失效：数据变更后发一条消息，所有实例收到后删掉对应的本地 key。通道可以用 MQ 的广播消费、Redis Pub/Sub、Redis Stream、配置中心推送，或者服务间的广播接口。Pub/Sub 最快但不可靠，断线期间的消息直接丢，所以必须配兜底：本地 TTL 不能太长，或者用 Stream、MQ 这种可持久化、可重放的通道。第二种做法是版本号：Redis 里存一个全局版本号，本地 value 带上版本，读的时候比较版本，落后就刷新，这样即使消息丢了也能在下次读时发现。第三种是定时全量刷新，适合配置类数据。工程上一般是广播删除加短 TTL 兜底，关键数据再加版本号校验；消息要幂等，重复消费只是多删一次，乱序则用版本号比较或者按 key 分区保序。

**短版**

广播失效用 MQ 广播或 Pub/Sub，Pub/Sub 会丢消息要配短 TTL 或 Stream；版本号兜底；消息幂等、按 key 保序。

**展开版**

- 机制链：数据变更 → 发失效消息（带 key 和版本）→ 各实例消费 → 比对版本 → 删除本地 → 下次读回源重建。
- 关键结构：广播通道、消息里的 key 与 version、本地 TTL、版本号存储、消费幂等表。
- 触发条件：多实例部署、本地缓存、数据更新频繁、发布扩容导致实例数变化。
- 例外：新扩容的实例收不到历史消息，只能靠 TTL 或启动预热；网络分区时部分实例失联。
- 对比取舍：Pub/Sub 实时但不可靠；MQ 可靠但有延迟和积压；版本号最稳但每次读多一次比较或查询。

**追问预判**

- Pub/Sub 丢了怎么办 → 短 TTL 兜底加定期对账，重要数据改用 Stream 或 MQ 持久化通道。
- 广播风暴怎么控制 → 合并同一批 key、按 key 哈希分片发送、限制发送频率。
- 版本号方案怎么落地 → Redis 存业务维度版本，本地缓存 value 带版本，读时异步校验，落后则删除重载。

**常见错误答法**

- 只依赖 Pub/Sub，假设消息一定送达。
- 本地 TTL 设成几小时，又没有广播，等于长期脏读。

**记忆锚点**

广播删除加短 TTL 兜底，关键数据加版本号。

### 23. 【进阶】预热：缓存冷启动怎么预热，怎么避免预热把数据库打挂？

**口述版**

冷启动有三种场景：大促前、服务重启、缓存扩容或故障恢复。预热的目标是把最热的那部分数据提前放进缓存，让真实流量进来时直接命中。做法是先找热点：看历史访问日志、业务埋点、Redis 的 hotkeys、榜单和运营配置。然后按 TopN 加载，分批、限速、可中断，先核心后长尾，加载完校验条数和抽样比对。触发方式可以是启动时异步任务、定时任务、发布流程里的预热步骤，或者 binlog 变更驱动的增量预热。注意几点：预热不能全量扫库，会把 DB 打挂；预热任务要和在线流量隔离，用独立线程池和连接；预热失败要能降级，不能阻塞启动；预热完要看命中率曲线确认效果。大促场景还可以用影子流量提前把缓存跑热。

**短版**

找热点（日志、埋点、hotkeys、榜单），TopN 分批限速加载，启动异步或定时触发，独立线程池，校验命中率。

**展开版**

- 机制链：统计热点 → 生成 key 列表 → 分批限速查询 → 写 Redis 和本地 → 校验 → 监控命中率。
- 关键结构：热点榜单、分批大小与 QPS 上限、独立线程池、预热任务状态、命中率指标。
- 触发条件：大促、发布、扩容、缓存实例重启、数据迁移后。
- 例外：热点会漂移，预热列表过期就白做；新品没有历史数据，只能靠运营配置或实时探测。
- 对比取舍：全量预热最全但风险大；TopN 预热收益高但覆盖不全；实时探测灵活但引入额外开销。

**追问预判**

- 怎么找热点 → 离线分析访问日志、在线埋点统计、Redis LFU 的 hotkeys、业务榜单。
- 预热和 TTL 怎么配合 → 预热时设置错开的 TTL，避免同一批又同时过期。
- 预热期间真实流量进来怎么办 → 未命中的正常回源并加锁单飞，预热只是加速，不是唯一依赖。

**常见错误答法**

- 启动时同步全量加载，把启动时间和数据库都拖垮。
- 预热不限速、不与在线流量隔离，直接把 DB 打满。

**记忆锚点**

TopN 加热点榜单，分批限速，独立线程池。

### 24. 【进阶】并发回源：本地缓存也会击穿吗，多级缓存下怎么防止回源放大？

**口述版**

会，而且会放大。本地缓存过期的那一瞬间，每个实例都有请求未命中，各自回源 Redis；如果 Redis 也恰好过期，就变成 N 个实例同时查库，N 等于实例数。流量越大、实例越多，放大越明显。三层防护：第一层是进程内 singleflight，用 ConcurrentHashMap 把同一个 key 的并发请求合并成一个 CompletableFuture，只有一个线程真正回源，其他等结果；第二层是跨实例的分布式锁，Redis 未命中时只放一个实例去查库重建，其他实例短暂等待或者返回旧值；第三层是逻辑过期或 refreshAfterWrite，先返回旧值，后台异步刷新，避免请求阻塞。回填时也要注意顺序，先写 Redis 再写本地，批量场景要合并写，别让回填本身把 Redis 打满。刷新失败要保留旧值并告警，不能删缓存。

**短版**

会，N 个实例同时未命中就放大 N 倍；用进程内 singleflight、跨实例分布式锁、逻辑过期或 refresh 返回旧值，回填先 Redis 后本地。

**展开版**

- 机制链：本地过期 → 多实例同时未命中 → Redis 也未命中 → 并发回源放大 → 用单飞和锁收敛成一个回源 → 回填。
- 关键结构：singleflight 的 key 到 Future 映射、分布式锁、逻辑过期时间、refreshAfterWrite、批量回填。
- 触发条件：热点 key、实例数多、TTL 集中过期、Redis 同时失效。
- 例外：singleflight 只在本进程有效；锁等待会拉高 RT，要设短超时并允许降级读旧值。
- 对比取舍：singleflight 无网络开销但只管单机；分布式锁跨实例但增加一次 Redis 往返；逻辑过期最平滑但实现复杂。

**追问预判**

- singleflight 怎么实现 → 一个 ConcurrentHashMap 存 key 到 CompletableFuture，抢到 putIfAbsent 的线程执行加载，完成后移除并唤醒等待者。
- 跨实例怎么只放一个回源 → Redis SET NX PX 抢锁，拿不到锁的实例短暂等待后读缓存或返回旧值。
- 刷新失败怎么办 → 保留旧值，记录失败指标，退避重试，不清空。

**常见错误答法**

- 每个实例都加了本地锁，但仍然各自回源，没解决跨实例放大。
- 回源失败时删掉缓存，下一波流量继续放大。

**记忆锚点**

单机 singleflight、跨机分布式锁、旧值兜底。

### 25. 【兜底】容量与成本：命中率怎么评估，缓存成本和容量怎么算？

**口述版**

命中率要分层看：本地命中率、Redis 命中率、整体回源率，只看一个总数会掩盖问题。命中率低的常见原因有 TTL 太短、容量不足导致频繁淘汰、key 设计太分散、写多读少、缓存了本来就不该缓存的长尾数据。成本口径是条目数乘平均大小乘开销系数乘副本数，Redis 还要算主从和集群的冗余，本地缓存要算堆内存和它对 GC 的影响。评估收益看回源 QPS 下降多少、P99 降多少、数据库压力降多少，再看省下的 DB 扩容成本够不够覆盖缓存成本。降成本的手段是压缩 value、只存必要字段、按热度分层、缩短冷数据 TTL、用更紧凑的序列化。要注意缓存不是越多越好，命中率从 95% 提到 99% 可能要多花一倍内存，收益要看边际。

**短版**

分层看本地、Redis、回源率；容量等于条目乘大小乘开销乘副本；收益看回源 QPS 和 P99，按边际收益决定要不要继续加缓存。

**展开版**

- 机制链：统计各层命中 → 分析未命中原因 → 调整 TTL、容量和 key 设计 → 重新评估成本与收益。
- 关键结构：hits/misses、回源 QPS、evicted_keys、平均 value 大小、内存单价、堆占用。
- 触发条件：成本评审、容量规划、命中率下降、RT 上升。
- 例外：命中率高但 RT 不降，说明瓶颈不在缓存；命中率低但数据量小，可能不影响 DB。
- 对比取舍：加内存提命中率简单但成本线性；优化 key 和 value 性价比高但需要改造；分层缓存省 Redis 但增加复杂度。

**追问预判**

- 命中率多少算正常 → 没有统一值，读多写少的热点数据通常 90% 以上，写多或个性化场景会低很多。
- 怎么降低 Redis 内存成本 → 压缩 value、去掉冗余字段、按热度分层、缩短 TTL、必要时换更便宜的存储。
- 本地缓存的内存怎么估 → 用 maximumWeight 按对象大小估，留出堆余量，观察 GC 和晋升情况。

**常见错误答法**

- 只看命中率不看 RT 和成本，认为命中率高就一定有价值。
- 把所有数据都缓存，包括低频长尾，成本高收益低。

**记忆锚点**

分层看命中，成本等于大小乘副本；按边际收益决策。

### 26. 【兜底】选型与排查：什么场景不该加本地缓存，出现不一致怎么定位？

**口述版**

不该加本地缓存的情况有五类：强一致数据，比如余额、库存的权威值；写多读少，缓存刚写就被改；数据量远大于可用堆内存；高度个性化或长尾，命中率极低；没有失效通道的老系统，加了只会长期脏读。另外本地缓存会带来 GC 压力、实例间不一致、扩容冷启动和排查困难，这些成本要提前算。出现不一致时的排查顺序：先确认是本地层还是 Redis 层，直接比对数据库和两层缓存的值；再看失效消息有没有发出、有没有消费、消费是否报错；然后看版本号和 TTL 是否合理；再确认写路径是不是“更新缓存”而不是删除，或者有没有漏掉的写入口；最后看是否有实例没订阅广播、时钟是否偏移、序列化是否丢字段。快速止血可以下发一次全量失效、清本地缓存或者重启实例，但事后一定要补上版本号和监控，否则还会复发。

**短版**

强一致、写多读少、超内存、长尾个性化、无失效通道，都不该加本地；排查先分层比对，再查消息、版本、TTL、写路径和订阅。

**展开版**

- 机制链：发现不一致 → 比对 DB、Redis、本地三层 → 定位是哪一层旧 → 查失效链路和写路径 → 修复并加防护。
- 关键结构：三层数据比对、失效消息日志、版本号、TTL 配置、实例订阅状态、序列化字段。
- 触发条件：用户投诉、对账差异、发布后数据异常、扩容后部分实例不一致。
- 例外：短时间不一致可能是正常的最终一致窗口，要先确认业务承诺的时效。
- 对比取舍：清缓存止血快但会打回源；重启最彻底但影响面大；加版本号最稳但要改读写路径。

**追问预判**

- 怎么快速确认是本地缓存的问题 → 灰度摘掉一个实例的本地缓存做对比，或者临时关闭本地层看差异是否消失。
- 本地缓存和 Redis 都旧怎么办 → 说明写路径没删干净或消息没到，重点查写入口和 binlog 订阅。
- 怎么防止复发 → 版本号校验加失效监控加定期对账，关键业务不放本地。

**常见错误答法**

- 出问题只会重启，不定位是消息、TTL 还是写路径的问题。
- 给强一致业务加本地缓存，再用短 TTL 安慰自己。

**记忆锚点**

强一致不放本地；排查先分层比对，再查消息与版本。
